Lançar guia de migração

Mudanças importantes

  • [client-v2, jdbc-v2] As opções de buffer de soquete socket_rcvbuf e socket_sndbuf não tem mais valor padrão. Agora as opções são aplicadas somente quando o aplicativo as define (Client.Builder#setSocketRcvbuf, Client.Builder#setSocketSndbuf, ou as propriedades de mesmo nome). Isso é feito para permitir o ajuste automático da pilha TCP do SO valores. Não os configure até que seja absolutamente necessário. (https://github.com/ClickHouse/clickhouse-java/issues/3121)

  • [client-v2, jdbc-v2] Erro de servidor 159 (TIMEOUT_EXCEEDED) não é mais repetido por padrão. Tem seu próprio causa de nova tentativa, ClientFaultCause.ServerTimeoutExceeded, que ServerRetryable não inclui e que não está em a lista client_retry_on_failures padrão. Adicione ServerTimeoutExceeded à lista para repetir este erro. (https://github.com/ClickHouse/clickhouse-java/issues/3072)

  • [r2dbc] O artefato pré 1.0.0 não é mais suportado porque R2DBC API atingiu a versão 1.0.0 estável.

  • [jdbc-v2] DatabaseMetaData#getTables agora retorna null em REMARKS (comentário da tabela) e TYPE_SCHEM por padrão, porque os metadados são lidos com instruções SHOW (consulte a entrada jdbc_metadata_use_show_statements em Novo Recursos). Configure jdbc_metadata_use_show_statements=false para obter os comentários da tabela. (https://github.com/ClickHouse/clickhouse-java/issues/2907)

  • [client-v2,jdbc-v2] Adicionado suporte de compactação ZSTD para fluxo de compactação de bloco e usado por padrão para não compactar solicitações client. Anteriormente, apenas LZ4 era suportado neste caso. Nota: Adicionada biblioteca ZSTD e nativa bibliotecas para o pacote -all JDBC porque agora ele é necessário para trabalhar com o servidor. (https://github.com/ClickHouse/clickhouse-java/issues/3105).

Mudanças importantes

  • [client-v2] com.clickhouse.client.api.observability.SpanSupport agora usa operação QUERY e INSERT constantes (nomes de span QUERY <database> e INSERT <database>.<table>). O atributo db.operation.name está definido como INSERT para operações de inserção e não definido para consultas porque as instruções SQL não são analisadas no client.

  • [client-v2] com.clickhouse.client.api.metrics.OperationMetrics agora tem um único construtor, OperationMetrics(ClientStatisticsHolder, OperationType); o construtor sem um tipo de operação foi removido. As métricas são criadas pelo client, que sempre sabe o tipo de operação que executa, e o construtor leva um tipo interno (com.clickhouse.client.api.internal.ClientStatisticsHolder), portanto o código do aplicativo não é esperado para chamá-lo. (https://github.com/ClickHouse/clickhouse-java/issues/2974)

Novos recursos

Tipos de dados

  • [client-v2, jdbc-v2] Adicionado suporte para o tipo de dados geográficos MultiPoint (ClickHouse 26.8+). Anteriormente o tipo era desconhecido para o client, portanto, a leitura ou gravação de uma coluna MultiPoint falhou com Unknown data type: MultiPoint, e um valor MultiPoint dentro de uma coluna Geometry falhou com um discriminador de variante fora do intervalo. MultiPoint é Array(Point) no fio, exatamente como Ring e LineString, por isso é lido e escrito como double[][] através registros genéricos, leitores binários, ligação POJO e formatação de parâmetros SQL e é lido a partir de colunas Dynamic. Em o driver JDBC (jdbc-v2) MultiPoint mapeia para java.sql.Types.ARRAY, é retornado como double[][] de getObject e como java.sql.Array de getArray, e é relatado por ResultSetMetaData e DatabaseMetaData. ClickCasa 26.8 também adiciona MultiPoint ao Geometry variante; o servidor o anexa após as seis variantes existentes em vez de ordená-lo por nome de tipo, então o client agora mantém essa ordem e decodifica um MultiPoint mantido em uma coluna Geometry. Porque MultiPoint compartilha seu Java representação (double[][]) com Ring e LineString, não é selecionável através do Geometry baseado em forma caminho de gravação - um valor 2D continua resolvendo para Ring como antes, e escrever MultiPoint requer um MultiPoint concreto coluna. (https://github.com/ClickHouse/clickhouse-java/issues/3048)

  • [client-v2, jdbc-v2] Adicionado suporte para o tipo de dados BFloat16 (ClickHouse 24.11+). As colunas BFloat16 são lidas como Valores Java float (ampliação sem perdas) e gravados a partir de valores float/Float, inclusive por meio de registros genéricos, POJO valores de ligação, Nullable(BFloat16) e BFloat16 mantidos nas colunas Dynamic/Variant. Ao escrever, o client mantém o 16 bits altos do float, correspondendo à conversão Float32 → BFloat16 do próprio servidor ClickHouse. No driver JDBC (jdbc-v2) BFloat16 mapeia para java.sql.Types.FLOAT / java.lang.Float e é lido e gravado através do padrão Acessadores getFloat/setFloat e getObject, e relatados como tal por ResultSetMetaData e DatabaseMetaData. A leitura ou gravação anterior de uma coluna BFloat16 falhou com um erro de tipo de dados não suportado. (https://github.com/ClickHouse/clickhouse-java/issues/2279)

  • [client-v2, jdbc-v2] Adicionado suporte para o tipo de dados vetorial experimental QBit(element_type, dimension[, stride]) (ClickHouse 25.10+; a configuração do servidor allow_experimental_qbit_type é necessária para criar uma coluna). O nome do tipo o analisador aceita dois ou três parâmetros (o terceiro opcional é o passo) e reconhece os tipos de elementos documentados Int8, BFloat16, Float32 e Float64; um tipo de elemento fora desse conjunto é analisado com um aviso em vez de rejeitado, portanto, um tipo de elemento do lado do servidor mais recente continua sendo analisado. Um valor QBit é transmitido pelo RowBinary exatamente como Array(element_type), portanto é lido e escrito como um array Java do tipo de elemento (float[] para BFloat16/Float32, double[] para Float64) através de registros genéricos, leitores binários e ligação POJO, através de um caminho de leitura/serialização QBit dedicado. Um QBit mantido dentro de uma coluna Dynamic/Variant/JSON também é decodificado (seu a codificação do tipo binário é lida de volta para o tipo QBit(...) concreto). No Driver JDBC (jdbc-v2) QBit mapeia para java.sql.Types.ARRAY e é retornado como um java.sql.Array de getObject/getArray. Anteriormente, QBit era uma constante de tipo não implementada e a leitura ou gravação de tal coluna falhou. Uma coluna QBit simples de nível superior com um tipo de elemento Float32, Float64 ou BFloat16 também é lida o formato de saída Native: lá o servidor o transmite usando seu plano de bits interno transposto Layout Tuple(FixedString(...)), e o client inverte essa transposição para reconstruir o mesmo Vetor float[]/double[] como RowBinary. Um QBit que é pisado (QBit(element_type, dimension, stride)), envolto em Nullable/LowCardinality, aninhado dentro de outro tipo (por exemplo, Array/Tuple/Map(String, QBit(...))), ou carregar qualquer outro tipo de elemento ainda não foi decodificado em Native e falha rapidamente com um erro claro direcionando você para um formato RowBinary como RowBinaryWithNamesAndTypes. (https://github.com/ClickHouse/clickhouse-java/issues/2610)

Observabilidade

  • [client-v2, jdbc-v2] Adicionada uma implementação Micrômetro das métricas SPI. Client.Builder.setMetricsRecorder(new MicrometerMetricsRecorder(meterRegistry)) relata as métricas de cada client operação para um Micrômetro MeterRegistry: um temporizador db.client.operation.duration por operação concluída, um temporizador clickhouse.client.operation.serialization.duration quando o client mediu a etapa de serialização, um contador clickhouse.client.operation.count por operação concluída e um contador clickhouse.client.operation.retries por tentativa repetida. Anteriormente, o client podia vincular apenas seus medidores de pool de conexão ao Micrômetro, exportando assim o as métricas das próprias operações foram deixadas para o aplicativo. Os nomes dos medidores, unidades, descrições e chaves de tag são os padrões do SPI - o gravador os deriva através do MetricsSupport, portanto são os nomes dos MetricName e as teclas de MetricAttribute significam o mesmo que para qualquer outro gravador. Uma operação bem sucedida não carrega nenhuma tag error.type e uma falha sim, então os resultados são séries temporais separadas do mesmo medidor e um a falha relatada pelo servidor também carrega db.response.status_code; uma duração que o client não mediu não é registrada, portanto nenhuma operação é reportada com duração inventada. Os segundos do SPI são entregues ao registro como nanossegundos, porque um temporizador Micrômetro mantém sua própria unidade de tempo, então um back-end publica a duração na unidade que ele espera. O construtor sem argumentos se reporta a Metrics.globalRegistry, que é o que o jdbc-v2 A propriedade jdbc_metrics_recorder precisa, portanto, uma conexão JDBC exporta suas métricas para o Micrometer nomeando a classe - jdbc_metrics_recorder=com.clickhouse.client.api.observability.micrometer.MicrometerMetricsRecorder - sem código do aplicativo. micrometer-core permanece uma dependência opcional de client-v2 e não está incluído no all artefatos, portanto, um client que não usa este gravador não precisa de nenhum Micrômetro no caminho de classe. (https://github.com/ClickHouse/clickhouse-java/issues/2975)

  • [client-v2, jdbc-v2] Adicionado um SPI de métricas que permite que um aplicativo exporte as métricas de operações client para qualquer back-end de métricas. Client.Builder.setMetricsRecorder(MetricsRecorder) registra um gravador independente de backend do pacote com.clickhouse.client.api.observability, e a propriedade jdbc-v2 jdbc_metrics_recorder nomeia o gravador classe uma conexão registra com seu próprio client. Anteriormente, o client coletava métricas de operação, mas retornava apenas para o chamador, portanto, exportá-los ficou para o aplicativo. Cada operação concluída reporta exatamente um sucesso ou um evento de falha, e cada nova tentativa relata um evento de nova tentativa, que fornece a duração da operação, o duração da serialização, o número de operações por resultado e o número de novas tentativas. O SPI segue o padrão de o span SPI: uma implementação estende a classe base DefaultMetricsRecorder e substitui apenas o que lhe interessa sobre, então ele continua funcionando quando o client começa a relatar um evento que ele não conhece, e o reutilizável A classe MetricsSupport deriva os valores padrão das mesmas estruturas, portanto sua lógica é opcional e substituível. Nomes de métricas, unidades e chaves de atributos seguem as convenções semânticas OpenTelemetry para banco de dados clients onde um a convenção existe e é colocada em clickhouse. onde não existe; eles são definidos pelo MetricName e enums MetricAttribute, as durações são relatadas em segundos e uma duração que o client não mediu é relatada como MetricsSupport.DURATION_UNKNOWN em vez de um valor inventado. Os atributos métricos são deliberadamente um conjunto menor do que os atributos de span, porque um atributo de uma métrica se torna uma série temporal: o texto da instrução, o ID da consulta e os parâmetros da instrução permanecem nos intervalos. Nada é registrado e nenhum trabalho relacionado às métricas é feito quando nenhum gravador está registrado. (https://github.com/ClickHouse/clickhouse-java/issues/2975)

  • [client-v2] Adicionada uma implementação OpenTelemetry do SPI de observabilidade. Client.Builder.setSpanRecorder(new OpenTelemetrySpanRecorder(openTelemetry)) relata cada operação client e cada solicitação de transporte como um intervalo OpenTelemetry CLIENT: um intervalo de operação é iniciado como filho do contexto OpenTelemetry atual, portanto ele se junta ao próprio rastreamento da aplicação e cada solicitação span - incluindo um por nova tentativa - é filho de seu intervalo de operação. Nomes de span e chaves de atributos são os padrão do SPI (o gravador os deriva através de SpanSupport), cada valor é registrado com o atributo OpenTelemetry tipo que corresponde a ele, e uma falha define o status de span para ERROR e é registrada como uma exceção OpenTelemetry evento próximo aos atributos error.type e db.response.status_code. O gravador reporta a um fornecido instância OpenTelemetry, para um Tracer dado a new OpenTelemetrySpanRecorder(Tracer), ou para GlobalOpenTelemetry - lido quando um intervalo é iniciado - quando construído sem argumentos. Anteriormente um aplicativo que desejavam extensões OpenTelemetry tiveram que escrever esse mapeamento sozinho. O OpenTelemetry API é uma dependência somente de compilação de client-v2: o gravador é utilizado apenas por uma aplicação que já disponibiliza o opentelemetry-api em tempo de execução, portanto nada é adicionado ao classpath de um client que não o utiliza. (https://github.com/ClickHouse/clickhouse-java/issues/2974)

  • [client-v2] Adicionado um SPI de observabilidade que permite que um aplicativo observe as operações do client como intervalos. Client.Builder.setSpanRecorder(SpanRecorder) registra um gravador independente de backend do novo Pacote com.clickhouse.client.api.observability: cada operação (uma consulta, um comando ou uma inserção - incluindo o chamadas ping e getTableSchema, que executam uma consulta) iniciam um intervalo de operação, e cada solicitação de transporte feita para ele - incluindo cada nova tentativa - inicia um período de solicitação filho. SpanRecorder e Span são interfaces simples; um implementação amplia o Classe base DefaultSpanRecorder e substitui apenas o que lhe interessa, por isso continua funcionando quando o client inicia um tipo de extensão que ele não conhece. O gravador registrado é chamado primeiro e recebe tudo o que o client sabe sobre a operação (seu QuerySettings/InsertSettings, a instrução, a tabela de destino, o tamanho do lote, o endpoint, as métricas da operação concluída e da falha), portanto, é livre para registrar o que for necessário e em qualquer que seja a forma; a classe reutilizável SpanSupport deriva os nomes de span padrão e valores de atributos desses mesmos estruturas e é chamado por uma implementação de gravador que as deseja, portanto sua lógica é opcional e substituível. Período nomes e chaves de atributos seguem as convenções semânticas OpenTelemetry para bancos de dados e extensões HTTP client; as chaves são definidos pelo enum SpanAttribute e os valores são derivados por SpanSupport, para que todos os gravadores que o utilizam reportem as mesmas informações (texto da instrução, banco de dados e tabela de destino, ID de consulta, parâmetros de instrução, tamanho do lote, o primeiro endpoint configurado no intervalo de operação e o valor por tentativa endereço do servidor e porta nos intervalos de solicitação, status HTTP, linhas retornadas e o tipo de erro e código de erro ClickHouse em caso de falha). O resultado de uma operação concluída é reportado por tipo de operação - recordQuerySuccess para uma leitura e recordInsertSuccess para uma inserção - porque as métricas que descrevem uma leitura não são aquelas que descrever uma gravação: uma consulta relata db.response.returned_rows, clickhouse.response.read_rows e clickhouse.response.read_bytes, um encarte informa clickhouse.response.written_rows e clickhouse.response.written_bytes. A mesma distinção está disponível nas próprias métricas através do novo OperationMetrics#getOperationType(), que retorna o novo com.clickhouse.client.api.metrics.OperationType - o tipo de chamada que o aplicativo fez, portanto, um comando que escreve é relatado como uma consulta. Um intervalo de operação é iniciado no thread de chamada, para que ele se junte ao rastreamento do ambiente do chamador mesmo quando a operação é executada no executor do client, e termina exatamente uma vez para cada operação iniciada. Anteriormente, o client não expunha nenhum gancho para rastreamento, então um o aplicativo não pôde atribuir uma consulta ou uma solicitação repetida ao seu próprio rastreamento. Quando nenhum gravador está registrado, nada é registrado e nenhum trabalho relacionado ao intervalo é realizado, portanto, o caminho padrão permanece inalterado. Uma implementação OpenTelemetry do SPI está disponível como OpenTelemetrySpanRecorder. (https://github.com/ClickHouse/clickhouse-java/issues/2974)

Melhorias

  • [migration-helpers] Adicionado módulo migration-helpers contendo ConfigurationMigrationHelper e ConfigPropertyCache para converter propriedades de configuração e URLs de conexão do formato v1 (0.7.1) para v2 (0.9.8+) formato (prefixando automaticamente as configurações do servidor ClickHouse com clickhouse_setting_, cabeçalhos personalizados com http_header_ e mapeamento de chaves de propriedade renomeadas).

  • [client-v2, jdbc-v2] Adicionada seleção de conjunto de criptografia TLS. Client.Builder.setSSLCipherSuites(String...) (client-v2) e a propriedade de conexão ssl_cipher_suites separada por vírgula (client-v2 e jdbc-v2) restringe os conjuntos de criptografia habilitado em conexões seguras; quando não definido, os padrões de transporte são usados. A seleção do conjunto de criptografia é independente de a configuração trust e ssl_mode. (https://github.com/ClickHouse/clickhouse-java/issues/2882)

  • [client-v2, jdbc-v2] Adicionado suporte para colunas Nested(...) não niveladas (tabelas criadas com flatten_nested = 0). Anteriormente, o gravador RowBinary lançava UnsupportedOperationException: Unsupported tipo de dados: Nested when inserting such a column. client-v2 now serializes a Nested(f1 T1, ..., fN TN) coluna da mesma forma que é lida - de forma idêntica a Array(Tuple(T1, ..., TN)) (uma contagem de linhas var-uint seguida por uma tupla por linha aninhada) — para que possa ser escrita através do caminho de inserção /RowBinaryFormatWriter. Em jdbc-v2, uma coluna Nested(...) não nivelada é exposta como um JDBC ARRAY cujo tipo de elemento é Tuple(f1 T1, ..., fN TN): pode ser inserido através de Connection#createArrayOf/setArray ou setObject e leia getArray/getObject, e java.sql.Array#getResultSet() itera as linhas aninhadas como Pares (INDEX, VALUE) onde cada VALUE é a tupla. (https://github.com/ClickHouse/clickhouse-java/issues/2477)

  • [client-v2, jdbc-v2] Adicionado registro em erros anteriormente silenciosos e caminhos de diagnóstico (nenhum funcional ou público-API mudança). (https://github.com/ClickHouse/clickhouse-java/issues/2969)

  • [jdbc-v2] DatabaseMetaData#getSchemas, #getTables e #getColumns agora leem metadados com SHOW DATABASES, SHOW TABLES e DESCRIBE TABLE em vez das tabelas system.databases, system.tables e system.columns. O servidor não mostra algumas tabelas nas tabelas do sistema por padrão (por exemplo, tabelas de DataLakeCatalog bancos de dados), portanto as ferramentas que utilizam DatabaseMetaData não os encontraram. A nova propriedade do driver jdbc_metadata_use_show_statements (padrão true) seleciona a implementação; configure-o para false para usar o sistema tabelas. Com as instruções SHOW, getTables() retorna null em REMARKS (comentário da tabela) e TYPE_SCHEM; getColumns() envia uma consulta DESCRIBE TABLE para cada tabela que corresponde e ignora uma tabela que foi descartada entretanto, que o usuário não pode descrever ou cujos metadados do data lake não podem ser lidos. Todas as outras colunas e valores são o mesmo. (https://github.com/ClickHouse/clickhouse-java/issues/2907)

Correções de bugs

  • [jdbc-v2] Corrigida uma instrução INSERT ... VALUES cuja lista de valores contém um literal, uma expressão (por exemplo, ? + 1) ou, com o analisador JAVACC, uma sequência de escape JDBC ou um parâmetro de consulta, sendo escrito com o gravador RowBinary quando beta.row_binary_for_simple_insert está habilitado. O escritor pega um valor vinculado por coluna, então os valores vinculados foram transferidos para outras colunas: a instrução falhou com um erro enganoso ou armazenou dados errados sem nenhum erro. O analisadores não relataram tais valores: o analisador JAVACC descartou o resultado de sua verificação da lista de valores e o Os analisadores ANTLR4 relataram apenas chamadas de função. Agora o escritor é usado apenas para uma lista de valores de espaços reservados ?, e outras instruções usam o caminho padrão PreparedStatement. (https://github.com/ClickHouse/clickhouse-java/issues/3083)

  • [client-v2,jdbc-v2] - Substituída a compactação HTTP LZ4 lenta pela compactação do fluxo de Biblioteca lz4-java. Client usa Apache Compress para lidar com compactação HTTP (porque possui fábrica conveniente para muitos métodos de compressões. No entanto, o Apache Compress usa implementação LZ4 lenta, o que causa inserções muito lentas. Agora lz4-java usado para inserção. A consulta ainda é lenta, mas será corrigida em versões futuras (precisa de refatoração e personalização implementação para resolvê-lo). Usar ZSTD para consultas deve resolver o problema. (https://github.com/ClickHouse/clickhouse-java/issues/2273).

  • [client-v2] Corrigida a gravação de um valor String em uma coluna UUID (também como um elemento Array/Tuple ou um Map chave) falhando com ClassCastException. A string agora é analisada com UUID.fromString; uma string que não pode analisar é rejeitado no client com um IllegalArgumentException. (https://github.com/ClickHouse/clickhouse-java/issues/3132)

  • [client-v2] Corrigida a leitura de uma coluna Nullable no formato Native falhando com Falha ao ler o bloco ... Fim do fluxo alcançado antes da leitura de todos os dados ou retorno de valores das linhas erradas. O leitor consumiu um nulo marcador antes de cada valor, que é o layout RowBinary. Native` é colunar: armazena um mapa nulo de um byte por linha antes dos valores de toda a coluna, e uma linha nula ainda possui um valor de espaço reservado. Os marcadores foram, portanto, retirado dos bytes de valor e a coluna foi lida fora de alinhamento. O mapa nulo agora é lido como um bloco. (https://github.com/ClickHouse/clickhouse-java/issues/3137)

  • [client-v2] Colunas geográficas fixas (Point, Ring, LineString, MultiPoint, Polygon, MultiLineString, MultiPolygon) sendo mal interpretado no formato Native. O leitor decodificou uma coluna geográfica linha por linha com o RowBinary decodificadores, enquanto Native escreve coluna principal: um bloco Point voltou com suas coordenadas embaralhadas nas linhas e nenhum erro, e todos os outros tipos geográficos dessincronizaram o bloco e falharam com Non-empty typeName is required. Uma coluna geográfica agora é decodificada do layout nativo - os dois Float64 subcolunas de um ponto e deslocamentos cumulativos mais os elementos nivelados para os níveis da matriz - e retorna o mesmo valores como RowBinaryWithNamesAndTypes, que permanece inalterado. (https://github.com/ClickHouse/clickhouse-java/issues/3088)

  • [client-v2, jdbc-v2] Corrigido um tipo de coluna com um elemento JSON que é seguido por um tipo parametrizado, para exemplo Tuple(JSON, FixedString(3)), sendo analisado incorretamente. JSON é válido com e sem lista de parâmetros, e o analisador procurou o colchete de abertura dessa lista em qualquer lugar após a palavra-chave, então pegou os colchetes da próxima elemento para os parâmetros do elemento JSON. Tudo até esses colchetes foi consumido, o que derrubou o elementos entre eles, ou falhou com Unknown data type: <parameter> quando o seguinte tipo tinha mais de um parâmetro, por exemplo Tuple(JSON, Decimal(10, 2)). Lendo tal coluna e Client#getTableSchema de uma tabela que possui um, falhou ou retornou um tipo incompleto. Uma lista de parâmetros agora é reconhecida apenas quando é imediatamente segue a palavra-chave JSON. (https://github.com/ClickHouse/clickhouse-java/issues/3098)

  • [jdbc-v1] Corrigida falha na análise de WITH RECURSIVE <name> AS (...). A gramática JavaCC não conhecia o palavra-chave RECURSIVE, portanto foi tomada como o nome da primeira expressão de tabela comum e a instrução foi rejeitada. A consulta em si ainda foi executada, porque o driver volta a enviar o SQL original, mas cada A chamada createStatement/prepareStatement registrou uma falha de análise WARN e a instrução foi classificada como desconhecida. RECURSIVE agora é aceito após WITH e permanece utilizável como um identificador comum (coluna, alias, tabela ou CTE nome). (https://github.com/ClickHouse/clickhouse-java/issues/3122)

  • [jdbc-v2] Corrigida falha na análise de WITH RECURSIVE <name> AS (...). Nem a gramática SQL conhecia o RECURSIVE palavra-chave, então ela foi usada como o nome da primeira expressão de tabela comum e a instrução foi rejeitada. A consulta em si ainda funcionou, porque o driver volta a enviar o SQL original, mas cada createStatement / A chamada prepareStatement registrou uma falha de análise (WARN com o backend JavaCC) e a instrução foi classificada como desconhecido. RECURSIVE agora é aceito após WITH pelas gramáticas JavaCC e ANTLR4 e permanece utilizável como identificador comum (coluna, alias, tabela ou nome CTE). (https://github.com/ClickHouse/clickhouse-java/issues/3122)

New Features

Data Types

  • [client-v2, jdbc-v2] Added support for the MultiPoint geo data type (ClickHouse 26.8+). Previously the type was unknown to the client, so reading or writing a MultiPoint column failed with Unknown data type: MultiPoint, and a MultiPoint value inside a Geometry column failed with an out-of-range variant discriminator. MultiPoint is Array(Point) on the wire, exactly like Ring and LineString, so it is read and written as double[][] through generic records, binary readers, POJO binding, and SQL parameter formatting, and is read from Dynamic columns. In the JDBC driver (jdbc-v2) MultiPoint maps to java.sql.Types.ARRAY, is returned as double[][] from getObject and as a java.sql.Array from getArray, and is reported by ResultSetMetaData and DatabaseMetaData. ClickHouse 26.8 also adds MultiPoint to the Geometry variant; the server appends it after the existing six variants instead of ordering it by type name, so the client now keeps that order and decodes a MultiPoint held in a Geometry column. Because MultiPoint shares its Java representation (double[][]) with Ring and LineString, it is not selectable through the shape-based Geometry write path — a 2D value keeps resolving to Ring as before, and writing MultiPoint requires a concrete MultiPoint column. (https://github.com/ClickHouse/clickhouse-java/issues/3048)

  • [client-v2, jdbc-v2] Added support for the BFloat16 data type (ClickHouse 24.11+). BFloat16 columns are read as Java float values (widening is lossless) and written from float/Float values, including through generic records, POJO binding, Nullable(BFloat16), and BFloat16 values held in Dynamic/Variant columns. On write the client keeps the high 16 bits of the float, matching the ClickHouse server's own Float32 → BFloat16 conversion. In the JDBC driver (jdbc-v2) BFloat16 maps to java.sql.Types.FLOAT / java.lang.Float and is read and written through the standard getFloat/setFloat and getObject accessors, and reported as such by ResultSetMetaData and DatabaseMetaData. Previously reading or writing a BFloat16 column failed with an unsupported-data-type error. (https://github.com/ClickHouse/clickhouse-java/issues/2279)

  • [client-v2, jdbc-v2] Added support for the experimental QBit(element_type, dimension[, stride]) vector data type (ClickHouse 25.10+; the allow_experimental_qbit_type server setting is required to create a column). The type-name parser accepts two or three parameters (the optional third is the stride) and recognizes the documented element types Int8, BFloat16, Float32, and Float64; an element type outside that set is parsed with a warning rather than rejected, so a newer server-side element type keeps parsing. A QBit value is transmitted over RowBinary exactly like Array(element_type), so it is read and written as a Java array of the element type (float[] for BFloat16/Float32, double[] for Float64) through generic records, binary readers, and POJO binding, via a dedicated QBit read/serialize path. A QBit held inside a Dynamic/Variant/JSON column is also decoded (its binary type encoding is read back to the concrete QBit(...) type). In the JDBC driver (jdbc-v2) QBit maps to java.sql.Types.ARRAY and is returned as a java.sql.Array from getObject/getArray. Previously QBit was an unimplemented type constant and reading or writing such a column failed. A plain top-level QBit column with a Float32, Float64, or BFloat16 element type is also read through the Native output format: there the server transmits it using its internal bit-plane-transposed Tuple(FixedString(...)) layout, and the client reverses that transposition to reconstruct the same float[]/double[] vector as RowBinary. A QBit that is strided (QBit(element_type, dimension, stride)), wrapped in Nullable/LowCardinality, nested inside another type (e.g. Array/Tuple/Map(String, QBit(...))), or carrying any other element type is not yet decoded over Native and fails fast with a clear error directing you to a RowBinary format such as RowBinaryWithNamesAndTypes. (https://github.com/ClickHouse/clickhouse-java/issues/2610)

Observability

  • [client-v2, jdbc-v2] Added a Micrometer implementation of the metrics SPI. Client.Builder.setMetricsRecorder(new MicrometerMetricsRecorder(meterRegistry)) reports the metrics of every client operation to a Micrometer MeterRegistry: a timer db.client.operation.duration per completed operation, a timer clickhouse.client.operation.serialization.duration when the client measured the serialization step, a counter clickhouse.client.operation.count per completed operation, and a counter clickhouse.client.operation.retries per retried attempt. Previously the client could bind only its connection-pool gauges to Micrometer, so exporting the metrics of the operations themselves was left to the application. Meter names, units, descriptions and tag keys are the standard ones of the SPI - the recorder derives them through MetricsSupport, so they are the names of MetricName and the keys of MetricAttribute and mean the same as for every other recorder. A successful operation carries no error.type tag and a failed one does, so the outcomes are separate time series of the same meter and a failure the server reported also carries db.response.status_code; a duration the client did not measure is not recorded, so no operation is reported with a made-up duration. The seconds of the SPI are handed to the registry as nanoseconds, because a Micrometer timer keeps its own time unit, so a backend publishes the duration in the unit it expects. The no-argument constructor reports to Metrics.globalRegistry, which is what the jdbc-v2 jdbc_metrics_recorder property needs, so a JDBC connection exports its metrics to Micrometer by naming the class - jdbc_metrics_recorder=com.clickhouse.client.api.observability.micrometer.MicrometerMetricsRecorder - without application code. micrometer-core stays an optional dependency of client-v2 and is not shaded into the all artifacts, so a client that does not use this recorder needs no Micrometer on the classpath. (https://github.com/ClickHouse/clickhouse-java/issues/2975)

  • [client-v2, jdbc-v2] Added a metrics SPI that lets an application export the metrics of client operations to any metrics backend. Client.Builder.setMetricsRecorder(MetricsRecorder) registers a backend-agnostic recorder from the com.clickhouse.client.api.observability package, and the jdbc-v2 property jdbc_metrics_recorder names the recorder class a connection registers with its own client. Previously the client collected operation metrics but only returned them to the caller, so exporting them was left to the application. Each completed operation reports exactly one success or one failure event, and each retried attempt reports a retry event, which gives the operation duration, the serialization duration, the number of operations by outcome and the number of retries. The SPI follows the pattern of the span SPI: an implementation extends the DefaultMetricsRecorder base class and overrides only what it cares about, so it keeps working when the client starts reporting an event it does not know about, and the reusable MetricsSupport class derives the standard values from the same structures, so its logic is opt-in and overridable. Metric names, units and attribute keys follow the OpenTelemetry semantic conventions for database clients where a convention exists and are placed under clickhouse. where it does not; they are defined by the MetricName and MetricAttribute enums, durations are reported in seconds, and a duration the client did not measure is reported as MetricsSupport.DURATION_UNKNOWN instead of a made-up value. The metric attributes are deliberately a smaller set than the span attributes, because an attribute of a metric becomes a time series: the statement text, the query id and the statement parameters stay on spans. Nothing is recorded and no metrics-related work is done when no recorder is registered. (https://github.com/ClickHouse/clickhouse-java/issues/2975)

  • [client-v2] Added an OpenTelemetry implementation of the observability SPI. Client.Builder.setSpanRecorder(new OpenTelemetrySpanRecorder(openTelemetry)) reports every client operation and every transport request as an OpenTelemetry CLIENT span: an operation span is started as a child of the current OpenTelemetry context, so it joins the application's own trace, and each request span - including one per retry - is a child of its operation span. Span names and attribute keys are the standard ones of the SPI (the recorder derives them through SpanSupport), every value is recorded with the OpenTelemetry attribute type that matches it, and a failure sets the span status to ERROR and is recorded as an OpenTelemetry exception event next to the error.type and db.response.status_code attributes. The recorder reports to a supplied OpenTelemetry instance, to a Tracer given to new OpenTelemetrySpanRecorder(Tracer), or to GlobalOpenTelemetry - read when a span is started - when constructed without arguments. Previously an application that wanted OpenTelemetry spans had to write that mapping itself. The OpenTelemetry API is a compile-only dependency of client-v2: the recorder is used only by an application that already provides opentelemetry-api at runtime, so nothing is added to the classpath of a client that does not use it. (https://github.com/ClickHouse/clickhouse-java/issues/2974)

  • [client-v2] Added an observability SPI that lets an application observe client operations as spans. Client.Builder.setSpanRecorder(SpanRecorder) registers a backend-agnostic recorder from the new com.clickhouse.client.api.observability package: each operation (a query, a command or an insert - including the ping and getTableSchema calls, which run a query) starts one operation span, and every transport request made for it - including each retry - starts a child request span. SpanRecorder and Span are plain interfaces; an implementation extends the DefaultSpanRecorder base class and overrides only what it cares about, so it keeps working when the client starts a kind of span it does not know about. The registered recorder is called first and receives everything the client knows about the operation (its QuerySettings/InsertSettings, the statement, the target table, the batch size, the endpoint, the metrics of the completed operation and the failure), so it is free to record whatever it needs and in whatever form; the reusable SpanSupport class derives the standard span names and attribute values from those same structures and is called by a recorder implementation that wants them, so its logic is opt-in and overridable. Span names and attribute keys follow the OpenTelemetry semantic conventions for database and HTTP client spans; the keys are defined by the SpanAttribute enum and the values are derived by SpanSupport, so all recorders that use it report the same information (statement text, target database and table, query id, statement parameters, batch size, the first configured endpoint on the operation span and the per-attempt server address and port on the request spans, HTTP status, returned rows, and the error type and ClickHouse error code on failure). The outcome of a completed operation is reported per operation kind - recordQuerySuccess for a read and recordInsertSuccess for an insert - because the metrics that describe a read are not the ones that describe a write: a query reports db.response.returned_rows, clickhouse.response.read_rows and clickhouse.response.read_bytes, an insert reports clickhouse.response.written_rows and clickhouse.response.written_bytes. The same distinction is available on the metrics themselves through the new OperationMetrics#getOperationType(), which returns the new com.clickhouse.client.api.metrics.OperationType - the kind of the call the application made, so a command that writes is reported as a query. An operation span is started on the calling thread, so it joins the caller's ambient trace even when the operation runs on the client's executor, and it is ended exactly once for every operation that starts. Previously the client exposed no hook for tracing, so an application could not attribute a query or a retried request to its own trace. When no recorder is registered nothing is recorded and no span-related work is done, so the default path is unchanged. An OpenTelemetry implementation of the SPI is available as OpenTelemetrySpanRecorder. (https://github.com/ClickHouse/clickhouse-java/issues/2974)

  • [client-v2] Fixed a null query-parameter value being sent as the literal string "null", so Client.query(sql, params, ...) binding a Java null to a scalar placeholder such as {x:Nullable(Decimal128(8))} was rejected by the server with BAD_QUERY_PARAMETER (Value null cannot be parsed as Nullable(...)). A top-level scalar null is now sent as the ClickHouse \N NULL sentinel so it binds SQL NULL; a null nested inside an Array/Map parameter value continues to render as the SQL NULL keyword. (https://github.com/ClickHouse/clickhouse-java/issues/2977)

  • [client-v2] Fixed binary array decoding for nullable element types so Array(Nullable(Float64)) and similar columns now return boxed arrays such as Double[] instead of Object[]. This keeps null-supporting arrays aligned with their element type while preserving the existing Object[] fallback for Variant/Dynamic/Geometry arrays. (https://github.com/ClickHouse/clickhouse-java/issues/2846)

  • [client-v2] Fixed Float32/Float64 columns throwing ClassCastException when a value of a non-matching boxed numeric type was supplied through the Object-typed insert surface — for example a Double (the natural type of Java literal like 1.5) for a Float32 column, or a Float for a Float64 column. The RowBinary serializer now narrows any Number (and, like the Int* columns, a String/ Boolean) through Number#floatValue()/Number#doubleValue(), so the float columns accept the same value types the integer columns already did. (https://github.com/ClickHouse/clickhouse-java/issues/2930)

  • [client-v2] Fixed a NullPointerException when serializing a null value into a non-nullable Enum8/Enum16 column. SerializerUtils.serializeEnumData had no null guard, so a null in a non-nullable enum column reached value.getClass() and failed the RowBinary insert path with a confusing NPE instead of a clear error. It now throws IllegalArgumentException naming the column, consistent with the existing IllegalArgumentException for other unsupported enum values. Nullable enum columns are unaffected. (https://github.com/ClickHouse/clickhouse-java/issues/2931)

  • [client-v2] Fixed silent data corruption when serializing a Java null into a non-nullable Array(...) column via RowBinaryFormatWriter. RowBinaryFormatSerializer.writeValuePreamble special-cased Array, emitting a stray marker byte on top of the array length; the server read the extra byte as a phantom extra row (single-column inserts) or as a column shift that failed the insert with CANNOT_READ_ALL_DATA (multi-column inserts). A non-nullable Array cannot represent a null, so it now throws IllegalArgumentException naming the column — consistent with every other non-nullable type — in both the RowBinary and RowBinaryWithDefaults paths. Empty arrays ([]) still serialize correctly, and Dynamic columns, which can hold a null as the implicit Nothing type, are unaffected. (https://github.com/ClickHouse/clickhouse-java/issues/2938)

  • [client-v2] Fixed POJO insert error classification so transport write failures such as java.net.SocketException: Broken pipe (Write failed) are now surfaced as transfer/network errors instead of being wrapped as DataSerializationException. This only changes the exception type reported for request-body transport failures during Client.insert (...); actual POJO reflection/serialization failures are still reported as DataSerializationException. (https://github.com/ClickHouse/clickhouse-java/issues/2729)

  • [client-v2] Fixed binary varint decoding for length and count fields so overflowing or overlong values fail with an IOException instead of being decoded into corrupted or negative int values. (https://github.com/ClickHouse/clickhouse-java/issues/2902)

  • [client-v2] Fixed container query parameters being sent unquoted, so Client.query(sql, params, settings) binding a List<LocalDate> (or an array/Map) to a placeholder like {ids:Array(Date)} was rejected by the server with CANNOT_PARSE_INPUT_ASSERTION_FAILED. Parameter values are now formatted by DataTypeConverter#convertParameterToString(Object) before being sent: pass the raw Java value and the client renders it into the text the server's param_<name> interface expects — a Collection, array (object or primitive), or Map becomes ClickHouse Array (['2026-05-13']) / Map ({'k':'v'}) text with String/temporal leaves single-quoted and numeric/boolean leaves left unquoted, while a scalar is passed through unquoted as before. No manual pre-formatting of container parameters is needed. (https://github.com/ClickHouse/clickhouse-java/issues/2897)

  • [client-v2] Fixed DateTime/DateTime64 columns declared with a synthetic fixed-offset timezone name (Fixed/UTC±HH:MM:SS, e.g. Fixed/UTC+05:30:00) being silently read in UTC instead of the declared offset. The RowBinary reader now recovers the offset from the column's declared type. (https://github.com/ClickHouse/clickhouse-java/issues/2876)

  • [jdbc-v2] Fixed the ANTLR4 SQL parser backends (jdbc_sql_parser=ANTLR4 and ANTLR4_PARAMS_PARSER) lexing the body of a heredoc string ($$body$$, $tag$body$tag$) as ordinary SQL. The lexer had no heredoc token, so every $ was dropped as an unrecognized character and the body was parsed as identifiers, operators and statement separators: a body that still looked like valid SQL was silently mis-parsed (wrong table name and VALUES-list positions), and a body containing ; — as well as the empty heredoc $$$$ — was reported as a parse error, which classifies an INSERT as a result-set-bearing statement with no values-list positions. A heredoc is now lexed as a single string literal and accepted as a literal value (INSERT ... VALUES lists, column expressions, settings), and a $ inside an identifier (a$b, or an unterminated tag such as $foo$bar) is part of the identifier, as the server reads it. (https://github.com/ClickHouse/clickhouse-java/issues/3031)

  • [jdbc-v2] Fixed the beta RowBinary writer (DriverProperties.BETA_ROW_BINARY_WRITER) throwing NoSuchColumnException for INSERT statements whose column names are backtick-quoted, in particular the canonical Nested sub-column wire form `directory`.`id`. The SQL parser now unescapes each backtick-quoted INSERT column-name component before the by-name server-schema lookup, matching how the table and database identifiers are already handled. (https://github.com/ClickHouse/clickhouse-java/issues/2896)
