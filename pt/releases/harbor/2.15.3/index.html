[!AVISO] Alteração significativa: webhooks para endereços internos são bloqueados por padrão

A correção para GHSA-2phj-cp9f-qq6w bloqueia a entrega de webhook e Slack para endereços privados, de loopback, de link local e outros endereços não públicos. Isso inclui nomes de host que resolvem para eles, como *.svc.cluster.local. Após a atualização, os webhooks existentes para endpoints internos não são entregues e os novos são rejeitados.

Para permiti-los novamente, defina a opção de exclusão em tanto core quanto jobservice:

  • harbor.yml: network.allow_private_network_access: true, depois ./prepare e reinicie
  • Leme: adicione {name: HARBOR_ALLOW_PRIVATE_NETWORK_ACCESS, value: "true"} a core.extraEnvVars e jobservice.extraEnvVars

Isto desativa totalmente a proteção. Use-o apenas se você trust todos os administradores do projeto e bloquear 169.254.169.254 no nível da rede.

[!AVISO] Alteração significativa: a assinatura de imagens não assinadas falha quando o conteúdo trust é aplicado

A correção para GHSA-wrw5-gmvj-gf23 remove a isenção baseada em User-Agent que permite que cosign e notation extraiam imagens não assinadas. Em projetos que permitem apenas imagens assinadas, cosign sign e notation sign em uma imagem nova e não assinada agora falham com 412 Precondition Failed. Imagens que já possuem assinatura não são afetadas.

Para permitir a assinatura de clients novamente, configure CONTENT_TRUST_LEGACY_SIGNER_PULL_ENABLED=true em core. O valor deve ser exatamente true.

  • Leme: adicione-o ao core.extraEnvVars
  • Instalação do harbor.yml: não há opção harbor.yml. Adicione-o ao common/config/core/env e reinicie. A nova execução do ./prepare substitui esse arquivo.

A isenção ainda trusts o User-Agent do client, mas apenas para usuários ou robôs com permissão push no projeto. Projetos que bloqueiam imagens vulneráveis ​​não têm opção de exclusão: um client assinado não pode mais extrair uma imagem que a política de vulnerabilidade bloqueia.

[!AVISO] Problema conhecido: falha na replicação push para registros específicos, como AWS ECR (regressão GHSA-wjpm-hv5w-gxr6)

A correção de segurança para cabeçalhos de localização de upload estritamente validados GHSA-wjpm-hv5w-gxr6 em relação ao endpoint de registro configurado estaticamente (c.url). Como o adaptador AWS ECR configura o endpoint do plano de controle API (https://api.ecr.<region>.amazonaws.com) enquanto as solicitações são reescritas no host do plano de dados (<account>.dkr.ecr.<region>.amazonaws.com), o cabeçalho Location de resposta do ECR é rejeitado como um destino de origem cruzada.

Solução alternativa/resolução:

Uma correção foi fornecida no PR #24113 e será lançada no próximo patch. Se o seu ambiente depende da replicação push, recomendamos adiar a atualização até o próximo lançamento do patch ou aplicar o patch diretamente.

[!WARNING] Breaking change: webhooks to internal addresses are blocked by default

The fix for GHSA-2phj-cp9f-qq6w blocks webhook and Slack delivery to private, loopback, link-local and other non-public addresses. That includes hostnames that resolve to them, such as *.svc.cluster.local. After you upgrade, existing webhooks to internal endpoints fail to deliver, and new ones are rejected.

To allow them again, set the opt-out on both core and jobservice:

  • harbor.yml: network.allow_private_network_access: true, then ./prepare and restart
  • Helm: add {name: HARBOR_ALLOW_PRIVATE_NETWORK_ACCESS, value: "true"} to both core.extraEnvVars and jobservice.extraEnvVars

This disables the protection entirely. Only use it if you trust all project admins, and block 169.254.169.254 at the network level.

[!WARNING] Breaking change: signing unsigned images fails when content trust is enforced

The fix for GHSA-wrw5-gmvj-gf23 removes the User-Agent based exemption that let cosign and notation pull unsigned images. In projects that only allow signed images, cosign sign and notation sign on a new, unsigned image now fail with 412 Precondition Failed. Images that already have a signature are not affected.

To allow signing clients again, set CONTENT_TRUST_LEGACY_SIGNER_PULL_ENABLED=true on core. The value must be exactly true.

  • Helm: add it to core.extraEnvVars
  • harbor.yml installs: there is no harbor.yml option. Add it to common/config/core/env and restart. Re-running ./prepare overwrites that file.

The exemption still trusts the client's User-Agent, but only for users or robots with push permission on the project. Projects that block vulnerable images have no opt-out: a signing client can no longer pull an image that the vulnerability policy blocks.

[!WARNING] Known Issue: Push Replication Fails for Specific Registries such as AWS ECR (GHSA-wjpm-hv5w-gxr6 Regression)

The security fix for GHSA-wjpm-hv5w-gxr6 strictly validated upload Location headers against the statically configured registry endpoint (c.url). Because the AWS ECR adapter configures the API control-plane endpoint (https://api.ecr.<region>.amazonaws.com) while requests are rewritten to the data-plane host (<account>.dkr.ecr.<region>.amazonaws.com), ECR's response Location header is rejected as a cross-origin target.

Workaround / Resolution:

A fix has been provided in PR #24113 and will be released in the upcoming patch release. If your environment depends on push replication, we recommend postponing the upgrade until the next patch release or applying the patch directly.
