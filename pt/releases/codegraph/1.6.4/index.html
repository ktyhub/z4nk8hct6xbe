#gráfico de código v1.6.4

[1.6.4] - 20/11/2026

Destaques

  • Perguntas pequenas custam menos. Pergunte ao seu agente o que é uma função ou constante, ou quem a chama, e codegraph_explore agora responde com a definição e cada linha que a utiliza, em vez de uma resposta longa sobre arquivos relacionados.
  • Respostas mais rápidas no Claude Code. O gancho de prompt agora pergunta ao servidor CodeGraph já em execução para o seu projeto, em vez de carregar o índice novamente em cada prompt, o que é mais importante em projetos grandes, e codegraph impact é tão rápido quanto era em 1.6.2 novamente.
  • Mais seguro em um computador compartilhado. Cada sessão do agente agora verifica se o servidor em segundo plano ao qual ele se conecta funciona como você antes de enviar qualquer coisa.
  • Mais do seu código no gráfico. Rotas Elysia (Bun), PHP inclui construído a partir da raiz do servidor web ou da própria pasta do arquivo, construtores primários Dart 3.13 e sintaxe Kotlin mais recente agora são lidos, e rotas ASP.NET Core são nomeadas da maneira como o ASP.NET as atende.
  • Links mais precisos. Dezenas de correções ajudam as chamadas a alcançar o código que significam, principalmente em JavaScript e TypeScript, Python, Rust, C#, PHP e Java, e codegraph affected não seleciona mais testes no lado oposto de uma chamada HTTP, uma fila ou um evento, a menos que você passe em --cross-tier.
  • Menos comandos travados. Um git add ou commit não falha mais com "index.lock: Arquivo existe" enquanto o CodeGraph sincroniza, um arquivo cuja análise nunca termina não impede mais que codegraph init ou sincronização termine, e um servidor cuja pasta do projeto foi excluída agora é encerrado.
  • Atualização: reindexe seus projetos com codegraph index após este lançamento. Muitas dessas correções são escritas durante a indexação, e codegraph status e seu agente informam quando um índice foi criado por uma versão mais antiga.

Segurança

  • Em um computador compartilhado com outros usuários, cada sessão do agente agora verifica se o servidor de segundo plano do CodeGraph ao qual ele se conecta funciona como você antes de enviar qualquer coisa e atende a própria sessão quando o servidor não pode provar isso, para que outro usuário não possa mais substituir o seu servidor para ler as consultas do seu agente ou alimentá-lo com respostas inventadas. Obrigado @aidenpan0x por apontar isso.

Novos recursos

  • O gancho de prompt do Claude Code agora obtém seu contexto do servidor CodeGraph já em execução para o seu projeto, em vez de carregar o índice novamente em cada prompt, para que os prompts estruturais sejam respondidos mais rapidamente, principalmente em projetos grandes; sem nenhum servidor em execução, um que esteja ocupado ou que não possa provar que funciona como você, o gancho funciona sozinho como antes. Obrigado @aidenpan0x pelo relatório, pelas medidas e pela solicitação pull. (#3284)
  • Os backends Elysia (Bun) agora têm suas rotas HTTP no gráfico, nomeadas pelo caminho completo que uma solicitação percorre, com os prefixos de new Elysia({ prefix }), .group() e .use() em outro arquivo incluídos e vinculados a seus manipuladores, para que codegraph_explore possa seguir uma solicitação de sua rota até seu código. Obrigado @ChampPABA pelo relatório. (#3255)
  • PHP inclui construído a partir da raiz do servidor web, como require $_SERVER['DOCUMENT_ROOT'] . '/inc/header.php', agora link para seu arquivo: CodeGraph descobre qual pasta o servidor serve de onde seus arquivos de nomes de caminhos de inclusão, não vincula nada quando eles não resolvem em vez de adivinhar, e leva "webRoot": "public" em codegraph.json (ou "." para a raiz do projeto) quando você preferir nomeá-lo você mesmo. Obrigado @artisanya pelo relatório. (#3298)
  • Kotlin agora é lido com uma versão mais recente de sua gramática, então o código que costumava ser lido incorretamente, como uma classe anotada cujos métodos apareciam como funções de nível superior, uma classe que delega outro objeto a by, ou sintaxe mais recente como guardas when e campos de apoio explícitos, agora tem suas classes, funções e chamadas no gráfico a que pertencem. (#3410)
  • codegraph_explore agora responde a uma pergunta sobre um símbolo, como "quem liga para toValidURL?" ou "o que é MAX_RETRIES?", com a fonte daquele símbolo e cada linha que o utiliza, cada uma com a função que ocupa e o texto da linha, em vez de preencher toda a sua resposta com arquivos que compartilham apenas palavras com o nome, então essas pequenas questões custam menos e não deixam nada para pesquisar depois. Obrigado @GeorgeTaveras1231 pelas medições. (#3407)

Correções

Configuração, o servidor de segundo plano e o CLI

  • codegraph affected não seleciona mais testes do outro lado de uma chamada HTTP, uma fila ou um evento, como as especificações de um aplicativo Angular para uma mudança no controlador Spring que ele chama, uma vez que esses testes zombam desse limite; passe --cross-tier para incluí-los. Obrigado @jotder pelo relatório. (#3320)
  • CodeGraph não usa mais o bloqueio de índice do git enquanto verifica alterações em seu repositório, portanto, um git add em um gancho de pré-confirmação, um commit ou checkout executado enquanto o CodeGraph sincroniza não falha mais com "index.lock: Arquivo existe". Obrigado @iamclaudia-ai pelo relatório. (#3295)
  • codegraph impact e codegraph_impact são tão rápidos quanto eram em 1.6.2 novamente, com os mesmos resultados: 1.6.3 lê os dependentes de cada símbolo de uma forma que desacelera cada passo da caminhada. Obrigado @inth3shadows pelo relatório e pela correção, e @Marcos-199-GitHub pelo #3285. (#3248)
  • Quando a sincronização de atualização do servidor CodeGraph em um projeto grande é interrompida porque as chamadas de ferramenta que ele está servindo evitam que seu log de gravação antecipada diminua, ele agora espera antes de tentar novamente, um pouco mais de cada vez, em vez de recomeçar a cada segundo enquanto você continua trabalhando. Obrigado @kiliman pelo relatório. (#3273)
  • Um servidor CodeGraph MCP iniciado em uma pasta sem índice não inicia mais seu processo hang-watchdog separado até que a sessão primeiro chame uma ferramenta ou abra um projeto, portanto, sessões que listam apenas as ferramentas, já que muitos hosts as abrem, usam menos memória. Obrigado @AiurArtanis pelo relatório e @johnhldiver-beep pelo #3257. (#3250)
  • Um servidor CodeGraph cuja pasta do projeto foi excluída, como uma árvore de trabalho git removida, agora sai em cerca de meio minuto, fechando seu inspetor de arquivos e saindo das listas codegraph daemon dos servidores, em vez de executar até que sua última sessão termine e expire. No Windows, ele também impede que os arquivos de índice dessa pasta sejam excluídos. Obrigado @deniskern pelo relatório e @johnhldiver-beep pelo #3259. (#3245)
  • codegraph upgrade executado a partir de sua pasta pessoal não trata mais a configuração de todo o usuário de seus agentes como um projeto: o servidor CodeGraph do Cursor continua seguindo o espaço de trabalho que você abre em vez de ser fixado em sua pasta pessoal, e nenhuma seção CodeGraph é gravada em ~/AGENTS.md, ~/GEMINI.md ou ~/QWEN.md. Obrigado @shoma-endo pelo relatório e @b84330808 e @LuisAlbertoMK. (#3234)
  • No OpenCode, as instruções do CodeGraph, tanto as que seu servidor envia quanto a seção que codegraph install escreve no AGENTS.md do OpenCode, agora nomeiam suas ferramentas da maneira que o OpenCode as lista (codegraph_codegraph_explore), para que o agente não chame mais um nome de ferramenta que não existe. Obrigado @expiren pelo relatório. (#1267)
  • codegraph init em um projeto cuja última execução do índice foi interrompida ou falhou parcialmente agora diz que o índice está incompleto e deve executar codegraph index, em vez de "Já inicializado", que parece uma configuração funcional. Obrigado @maxmilian pelo relatório e @LuisAlbertoMK. (#3228)
  • codegraph callers, callees e impact agora avisam quando um arquivo na resposta foi alterado no disco após ter sido indexado pela última vez, como codegraph node e explore já fizeram, então um número de linha deslocado não é mais lido como atual. Com --json o aviso vai para stderr e a resposta lista esses arquivos em changedOnDisk. Obrigado @arifpambudi242 pelo relatório e @mohitdixit02. (#3260)
  • codegraph status agora relata edições, novos arquivos e exclusões em fontes gitignored que codegraph.json include traz para o índice, em vez de atualizar o índice até que uma sincronização os detecte. Obrigado @mixxer pelo relatório e pela solicitação pull. (#3086)
  • No Linux e macOS, quando o sistema mata o CodeGraph com um sinal, como quando fica sem memória durante codegraph init ou codegraph index, o comando agora diz qual sinal e sai como um shell faria (137 para SIGKILL), em vez de sair 1 sem mensagem. Obrigado @inth3shadows pelo relatório e @johnhldiver-beep. (#3277)
  • Uma solicitação de teste Spring ou Laravel agora está vinculada apenas a uma rota de seu próprio aplicativo, não a uma rota do servidor JavaScript ou TypeScript que corresponde ao caminho, então codegraph affected não seleciona mais testes Java ou PHP para uma alteração em seu código web. Obrigado @jotder pelo relatório. (#3320)

Indexação e sincronização

  • codegraph sync e o inspetor de arquivo agora seguem uma edição que adiciona, remove ou renomeia um membro de um objeto exportado, como export const api = { getUser, saveUser }, portanto, uma chamada como api.saveUser() em um arquivo cuja edição não tocou em links para o novo membro ou de volta para o objeto, como faz um novo índice. Obrigado @ inth3shadows pelo relatório. (#3015)
  • Um arquivo cuja análise nunca termina, como um arquivo .tsx com um atributo JSX meio digitado, não impede mais a saída de codegraph init ou deixa codegraph sync e o inspetor de arquivo girando em CPU cheia: sua análise agora para no limite de tempo de análise do arquivo e o arquivo é listado como uma análise que expirou. Obrigado @ inth3shadows pelo relatório. (#3274)
  • Após a atualização, codegraph status e a primeira resposta do CodeGraph em cada sessão do agente agora sinalizam um projeto indexado por 1.6.3 ou anterior como desatualizado, já que esta versão lê o código em que esses índices estão faltando, como construtores primários Dart, rotas Elysia, PHP inclui construído a partir de __DIR__ e os métodos de um objeto export default; execute codegraph index em cada projeto para reconstruí-lo. (#3411)

JavaScript e TypeScript

  • Os manipuladores de eventos JavaScript e TypeScript registrados com on() agora são vinculados apenas a partir do código que emite no mesmo emissor e ao manipulador definido onde estão registrados, portanto, dois módulos que mantêm cada um seu próprio emissor e usam o mesmo nome de evento não fazem mais link cruzado. Obrigado @ inth3shadows pelo relatório. (#2973)
  • No JavaScript, os métodos escritos da maneira clássica, Ctor.prototype.m = function () {…} e um Ctor.m = function () {…} estático, agora são indexados como métodos de seu construtor, e as funções de um objeto module.exports = {…} como as exportações desse módulo, então this.m() dentro deles atinge o m do construtor ou do próprio objeto em vez de uma função não relacionada de mesmo nome em outro lugar. Obrigado @ inth3shadows pelo relatório. (#2966)
  • Em JavaScript e TypeScript, as funções de um objeto que um módulo exporta por padrão, como um armazenamento Vuex dividido em actions.js, getters.js e mutations.js (export default { fetchUser() {…} }), agora são indexadas como default::fetchUser, então codegraph_explore, node, query, callers e impacto os encontram, e uma chamada através do importação padrão do módulo, this.fetchUser() ou um Vuex dispatch('fetchUser') vinculado a eles; um Vuex commit agora sempre está vinculado a uma mutação e um dispatch a uma ação. Obrigado @daniel-luan-tran pelo relatório. (#3393)
  • Em JavaScript e TypeScript, this.findAll() em uma classe que agrupa um auxiliar importado de mesmo nome agora vincula-se ao próprio método da classe em vez do auxiliar importado. Obrigado @ inth3shadows pelo relatório. (#2954)
  • Em JavaScript e TypeScript, uma chamada escrita em this, como this.cast() ou this.validate(), não se vincula mais a um const, a um bind require ou a uma declaração de função que apenas compartilha seu nome, no mesmo arquivo ou outro, pois o que a chamada atinge é uma propriedade do objeto.
  • No TypeScript, uma chamada a um parâmetro ou local nomeado como uma importação, como stream.write() dentro de stream(c, async (stream) => …), agora passa por esse parâmetro ou local, e um método chamado em uma função importada não se vincula mais à própria função; o mesmo erro no require já foi corrigido no 1.6.3. Obrigado @ inth3shadows pelo relatório. (#2953)
  • Em JavaScript e TypeScript, uma chamada para um nome que uma função em torno do chamador declara para si mesma, como um auxiliar que uma função de seta interna chama, agora é vinculada a essa declaração local em vez da importação do arquivo com o mesmo nome. Obrigado @ inth3shadows pelo relatório. (#2949)
  • Em JavaScript e TypeScript, uma chamada para um auxiliar declarado dentro de um bloco describe(…), ou qualquer outro retorno de chamada, agora é vinculada ao auxiliar que o bloco declara, em vez de um auxiliar de mesmo nome de outro bloco que esteja mais próximo. Obrigado @ inth3shadows pelo relatório. (#2944)
  • Em JavaScript e TypeScript, uma chamada dentro de um spread, como <input {...register('email')} /> com register retirado de useForm(), não está mais vinculada a uma função de projeto não relacionada que compartilha o nome. Obrigado @ inth3shadows pelo relatório. (#2962)
  • Em JavaScript e TypeScript, um namespace de módulo que outro módulo transmite por nome, como o import { z } from 'zod' de import * as z from './external'; export { z } de zod, ou export * as ns from './schemas', agora leva z.string() ao que esse módulo exporta, como import * as z faz, em vez de um método com o mesmo nome em outro lugar. Obrigado @ inth3shadows pelo relatório. (#2951)
  • Em JavaScript e TypeScript, uma importação através de um barril de várias linhas export * agora vincula-se ao módulo que exporta o próprio nome, a linha que vier primeiro, em vez de um método de mesmo nome de um objeto que outro módulo exporta. Obrigado @ inth3shadows pelo relatório. (#3233)
  • Em JavaScript e TypeScript, um método chamado em uma variável preenchida por uma chamada de biblioteca, como const root = createRoot(el) do react-dom, net.createServer() ou canvas.getContext('2d'), não está mais vinculado ao único método de projeto que compartilha seu nome. Obrigado @ inth3shadows pelo relatório. (#2947)
  • No TypeScript, um método chamado em uma variável preenchida pela fábrica estática de uma classe, como const writer = DatabaseConnection.initialize(path), agora é vinculado ao método da classe que a fábrica diz que retorna, em vez de uma classe adivinhada pelo nome da variável. Obrigado @ inth3shadows pelo relatório. (#2946)
  • No TypeScript, uma chamada através de uma propriedade do tipo função da interface, como matcher.snapshot(), não é mais vinculada a um método de classe não relacionado de mesmo nome; uma classe que implementa a interface, ou a constrói, ainda está vinculada. Obrigado @ inth3shadows pelo relatório. (#3035)
  • Em JavaScript e TypeScript, uma chamada com dois ou mais campos de profundidade de this, como this.cache.list.push(1) ou this.extractor.functionTypes.includes(type), não está mais vinculada a um método de projeto não relacionado nomeado como o próprio push, includes, has ou set do próprio JavaScript, ou a uma propriedade que apenas compartilha o nome. Obrigado @ inth3shadows pelo relatório. (#2948)
  • Em JavaScript e TypeScript, uma entrada workspaces que aponta para fora do projeto, como "../shared" em package.json ou pnpm-workspace.yaml, não faz mais com que o pacote daquela pasta conte como parte do projeto, portanto uma chamada através de uma importação dela não fica mais vinculada a uma função não relacionada sua com o mesmo nome. Obrigado @bompus pelo relatório e @johnhldiver-beep. (#3093)
  • Em JavaScript e TypeScript, uma chamada a uma variável local declarada após outra na mesma instrução, como let n = 0, ob = make(), ou ao lado de um padrão em uma desestruturação, como const { ob = make() } = o, vincula-se novamente quando uma variável de mesmo nome fora da função contém um tipo de biblioteca, como acontecia antes de 1.6.3. Obrigado @inth3shadows pelo relatório e @mohitdixit02. (#3293)
  • No JavaScript, uma chamada para um membro que um módulo obrigatório do seu projeto não possui, como utils.missing() após const utils = require('./utils'), não está mais vinculado a um método de classe não relacionado com esse nome. Obrigado @inth3shadows pelo relatório e @johnhldiver-beep. (#3272)
  • Uma chamada fetch ou HTTP-client para o API de outra empresa, como fetch('https://api.github.com/users/…'), não se vincula mais à rota do seu próprio servidor com o mesmo caminho; uma chamada para localhost, para um host que seu código preenche ou por meio de um URL base de client ainda vincula. Obrigado @inth3shadows pelo relatório e @johnhldiver-beep. (#2974)
  • Em JavaScript e TypeScript, uma chamada ou new de um global, como parseInt(…), new Response(…) ou new URL(…), em um módulo que não importa esse nome não vincula mais a uma exportação de mesmo nome de outro arquivo em seu projeto. Obrigado @ inth3shadows pelo relatório. (#3238)
  • No JavaScript, um require() de uma pasta por um caminho relativo, como require('..') dos testes de um pacote, agora carrega o arquivo com os nomes package.json da pasta como main, como o Node faz, então chama através dele o link para a função que o arquivo exporta. Antes não era seguida uma pasta sem index.js, e a chamada era vinculada à variável que contém o resultado require(); no fastify, cada Fastify() de teste vinculado ao seu próprio arquivo de teste. Obrigado @ inth3shadows pelo relatório. (#2964)
  • No JavaScript, uma variável que contém o que a função de um módulo necessário retorna, como const app = require('./app')(), não conta mais como o próprio módulo, portanto, uma chamada como app.listen() não está mais vinculada à função de fábrica do módulo e vinculada ao método da classe que a fábrica retorna quando isso é conhecido. Obrigado @ inth3shadows pelo relatório. (#2964)
  • Em JavaScript e TypeScript, um nome importado de um pacote que seu package.json não lista, mas seu projeto instalou, como import { useForm } from 'react-hook-form' içado para a raiz de um monorepo node_modules, não está mais vinculado a uma função não relacionada de mesmo nome em outro lugar em seu projeto (#3271). Reindexe os projetos JavaScript e TypeScript após a atualização. ####Python
  • No Python, import time não vincula mais o arquivo de importação a uma função de projeto que passa a ser denominada time, portanto tal função deixa de listar cada arquivo que importa o módulo de biblioteca padrão entre seus chamadores e em seu impacto. O mesmo vale para json, copy, random, logging e qualquer outro módulo, e para uma variável de fallback como brotli = None ao lado de um import brotli protegido. Obrigado @ inth3shadows pelo relatório. (#3239)
  • Em Python, uma chamada para uma função ou método declarado com typing.overload, como command e prompt de click, agora é vinculado ao def que é executado em vez do primeiro stub @overload, de modo que a implementação mostra seus chamadores e um caminho de chamada passa por ele. Um stub sem implementação abaixo dele, como em um Protocol, permanece o alvo, e o overload de outra biblioteca, cujos corpos são executados, é deixado sozinho. Obrigado @inth3shadows pelo relatório e @nilotpal-n7. (#2963)
  • Em Python, uma chamada como self.create_app() em um atributo que contém um chamável não está mais vinculado a uma função ou variável de mesmo nome em outro arquivo, nem, quando a classe define esse atributo, para o método de outra classe com esse nome, então o carregamento do aplicativo do flask para de mostrar um aplicativo de exemplo como seu receptor. Um método que a classe possui, herda ou uma subclasse substitui ainda é vinculado, assim como uma função que a classe armazena com esse nome. Obrigado @inth3shadows pelo relatório e @nilotpal-n7. (#2958)
  • No Python, um código interno escrito, como raise TimeoutError(…), class Bad(ValueError) ou sorted(rows), não é mais vinculado a uma classe de projeto ou função com esse nome em um arquivo que o código não importa, portanto, o próprio TimeoutError do projeto para de coletar todos os arquivos que geram o integrado. Um nome que o arquivo define ou importa ainda é vinculado. Obrigado @ inth3shadows pelo relatório. (#3232)
  • No Python, uma chamada de um nome, o código ao seu redor se vincula, como um flat = lambda … local, um parâmetro, um loop ou variável de compreensão, um parâmetro lambda ou um local ou parâmetro de uma função envolvente, não é mais vinculado a uma função ou variável de nível de módulo com esse nome, esteja no mesmo arquivo ou em um que o código nunca importa. Obrigado @inth3shadows pelos relatórios e @johnhldiver-beep. (#3037, #3230, #3231)
  • No Python, um local construído a partir de uma classe através de seu módulo, como client = httpx.AsyncClient(), ou vinculado por with ou async with … as client, agora possui essa classe, então client.get() vincula-se a AsyncClient.get ao invés do método de uma classe nomeada como a variável, como Client.get. Um with cuja classe distribui outra coisa de __enter__, e uma classe de um módulo fora do seu projeto, ainda não fornece nenhum tipo ao local. Obrigado @inth3shadows pelo relatório e @nilotpal-n7. (#2957)
  • Em Python, um método chamado em um limite local a partir de uma chamada, como made = make(q) ou s = store.stage(), agora atende pelo tipo que a função ou método chamado declara que retorna: um Path, um str ou outra classe de fora do seu projeto não vincula nada, onde qualquer método de projeto que por acaso compartilhasse o nome poderia, e uma de suas próprias classes vincula seu próprio método mesmo quando outras classes têm um com esse nome. Obrigado @inth3shadows pelos relatórios e @johnhldiver-beep. (#3038, #3240)
  • No Python, um from x import name escrito dentro de uma função agora se aplica apenas a essa função, então as chamadas de name no restante do arquivo alcançam o próprio def name do arquivo em vez da função importada, como um wrapper que importa o original que ele encapsula espera. Obrigado @ inth3shadows pelo relatório. (#3229)

Java, Kotlin, C# e ASP.NET

  • Em Java, quando dois pacotes declaram uma classe de mesmo nome, uma chamada estática, uma chamada em um novo objeto ou uma chamada através de uma variável agora atinge aquela que o arquivo chamador pode ver, inclusive através de uma importação curinga, e uma chamada escrita com o pacote, como com.x.b.Util.log(…), atinge a classe desse pacote. Obrigado @inth3shadows pelos relatórios e @johnhldiver-beep. (#2976, #3290, #3291)
  • No Kotlin, uma extensão declarada em um alias de importação de um tipo de biblioteca, como fun DeclAlias.pad() após import androidx.compose.ui.Modifier as DeclAlias, agora vincula chamadas desse tipo, qualquer que seja o nome sob o qual o arquivo de chamada o importe. Obrigado @mixxer pelo relatório e pela solicitação pull. (#3084)
  • Em C#, um método chamado sobre o que um método da mesma classe retorna, como GetMailer().Send(), agora é vinculado ao método do tipo que o método é declarado para retornar. Obrigado @Gobakabana pelo relatório. (#2906)
  • No ASP.NET Core, as rotas de atributos agora são nomeadas da maneira como o ASP.NET as atende: [controller] e [action] são preenchidos, cada controlador usa seu próprio [Route] (ou seu controlador base), os caminhos ~/ são independentes e as ações marcadas como [HttpHead], [HttpOptions] ou [AcceptVerbs], com seu próprio [Route] ou em uma lista de atributos são não faltou mais. Obrigado @Gobakabana pelo relatório. (#2905)
  • Em C#, um método de extensão agora é correspondido pelo tipo que seu parâmetro this assume, então "hi".Shout() e mailer.Shout() alcançam cada uma sua própria extensão, e uma chamada do próprio método de uma string não atinge mais uma extensão de projeto com o mesmo nome. Obrigado @Gobakabana pelo relatório. (#2906)
  • Em C#, um método chamado através de ?. ou !., como _mailer?.Send(), agora é vinculado ao método do tipo do receptor. Obrigado @Gobakabana pelo relatório. (#2906)

codegraph v1.6.4

[1.6.4] - 2026-11-20

Highlights

  • Small questions cost less. Ask your agent what a function or constant is, or who calls it, and codegraph_explore now answers with the definition and every line that uses it, instead of a long answer about related files.
  • Faster answers in Claude Code. The prompt hook now asks the CodeGraph server already running for your project instead of loading the index again on every prompt, which matters most in large projects, and codegraph impact is as fast as it was in 1.6.2 again.
  • Safer on a shared computer. Each agent session now checks that the background server it connects to runs as you before sending it anything.
  • More of your code in the graph. Elysia (Bun) routes, PHP includes built from the web server's root or the file's own folder, Dart 3.13 primary constructors and newer Kotlin syntax are now read, and ASP.NET Core routes are named the way ASP.NET serves them.
  • More accurate links. Dozens of fixes help calls reach the code they mean, most of all in JavaScript and TypeScript, Python, Rust, C#, PHP and Java, and codegraph affected no longer picks tests on the far side of an HTTP call, a queue or an event unless you pass --cross-tier.
  • Fewer stuck commands. A git add or commit no longer fails with "index.lock: File exists" while CodeGraph syncs, a file whose parse never ends no longer keeps codegraph init or sync from finishing, and a server whose project folder was deleted now shuts down.
  • Upgrading: re-index your projects with codegraph index after this release. Many of these fixes are written while indexing, and codegraph status and your agent both tell you when an index was built by an older version.

Security

  • On a computer shared with other users, each agent session now checks that the CodeGraph background server it connects to runs as you before sending it anything, and serves the session itself when the server can't prove it, so another user can no longer stand in for your server to read your agent's queries or feed it made-up answers. Thanks @aidenpan0x for pointing it out.

New Features

  • The Claude Code prompt hook now gets its context from the CodeGraph server already running for your project instead of loading the index again on every prompt, so structural prompts are answered sooner, most of all in large projects; with no server running, one that is busy, or one that can't prove it runs as you, the hook works it out itself as before. Thanks @aidenpan0x for the report, the measurements and the pull request. (#3284)
  • Elysia (Bun) backends now have their HTTP routes in the graph, named by the full path a request takes, with the prefixes of new Elysia({ prefix }), .group() and a .use() in another file included, and linked to their handlers, so codegraph_explore can follow a request from its route into your code. Thanks @ChampPABA for the report. (#3255)
  • PHP includes built from the web server's root, like require $_SERVER['DOCUMENT_ROOT'] . '/inc/header.php', now link to their file: CodeGraph works out which folder the server serves from where your includes' paths name files, links nothing when they don't settle it rather than guess, and takes "webRoot": "public" in codegraph.json (or "." for the project root) when you'd rather name it yourself. Thanks @artisanya for the report. (#3298)
  • Kotlin is now read with a newer version of its grammar, so code it used to misread, such as an annotated class whose methods showed up as top-level functions, a class that delegates by another object, or newer syntax like when guards and explicit backing fields, now has its classes, functions and calls in the graph where they belong. (#3410)
  • codegraph_explore now answers a question about one symbol, like "who calls toValidURL?" or "what is MAX_RETRIES?", with that symbol's source and every line that uses it, each with the function it sits in and the line's text, instead of filling its whole answer with files that only share words with the name, so these small questions cost less and leave nothing to search for afterwards. Thanks @GeorgeTaveras1231 for the measurements. (#3407)

Fixes

Setup, the background server and the CLI

  • codegraph affected no longer selects tests on the other side of an HTTP call, a queue or an event, like an Angular app's specs for a change to the Spring controller it calls, since those tests mock that boundary; pass --cross-tier to include them. Thanks @jotder for the report. (#3320)
  • CodeGraph no longer takes git's index lock while it checks your repository for changes, so a git add in a pre-commit hook, a commit or a checkout that runs while CodeGraph syncs no longer fails with "index.lock: File exists". Thanks @iamclaudia-ai for the report. (#3295)
  • codegraph impact and codegraph_impact are as fast as they were in 1.6.2 again, with the same results: 1.6.3 read each symbol's dependents in a way that slowed down every step of the walk. Thanks @inth3shadows for the report and the fix, and @Marcos-199-GitHub for #3285. (#3248)
  • When the CodeGraph server's catch-up sync on a large project is stopped because the tool calls it is serving keep its write-ahead log from shrinking, it now waits before trying again, a little longer each time, instead of starting over every second while you keep working. Thanks @kiliman for the report. (#3273)
  • A CodeGraph MCP server started in a folder with no index no longer starts its separate hang-watchdog process until the session first calls a tool or opens a project, so sessions that only list the tools, as many hosts open them, use less memory. Thanks @AiurArtanis for the report and @johnhldiver-beep for #3257. (#3250)
  • A CodeGraph server whose project folder is deleted, like a removed git worktree, now exits within about half a minute, closing its file watcher and dropping out of the servers codegraph daemon lists, instead of running until its last session ends and it times out. On Windows it also stops keeping that folder's index files from being deleted. Thanks @deniskern for the report and @johnhldiver-beep for #3259. (#3245)
  • codegraph upgrade run from your home folder no longer treats your agents' user-wide setup as a project's: Cursor's CodeGraph server keeps following the workspace you open instead of being pinned to your home folder, and no CodeGraph section is written into ~/AGENTS.md, ~/GEMINI.md or ~/QWEN.md. Thanks @shoma-endo for the report and @b84330808 and @LuisAlbertoMK. (#3234)
  • In OpenCode, CodeGraph's instructions, both the ones its server sends and the section codegraph install writes to OpenCode's AGENTS.md, now name its tools the way OpenCode lists them (codegraph_codegraph_explore), so the agent no longer calls a tool name that doesn't exist.   • codegraph init in a project whose last index run was killed or failed partway now says the index is incomplete and to run codegraph index, instead of "Already initialized", which read like a working setup. Thanks @maxmilian for the report and @LuisAlbertoMK. (#3228)

With --json the warning goes to stderr and the answer lists those files under changedOnDisk. Thanks @arifpambudi242 for the report and @mohitdixit02. (#3260)

  • codegraph sync and the file watcher now follow an edit that adds, removes or repoints a member of an exported object, like export const api = { getUser, saveUser }, so a call such as api.saveUser() in a file the edit didn't touch links to the new member, or back to the object, as a fresh index does.   • In Kotlin, a call named after a modifier keyword at the start of a statement, like annotation("jakarta.persistence.Entity") in a Gradle allOpen { } block or a class's own open(), is now read as the call it is, so a build script made of such calls no longer warns that it contributes nothing to the graph. Thanks @clayly for the report. (#3410)

PHP and Laravel

  • In PHP, a method called on a freshly built object, like (new SettingClient())->getSet(1), now links to the class the file's namespace and use imports name, or to a method it inherits, so these calls show up in callers and impact. Thanks @holysor for the report. (#3244)
  • In Laravel, a route written like [UserController::class, 'show'] now links to the controller the routes file imports, through a plain or aliased use, a group use, an imported namespace or a fully qualified name, instead of a same-named controller elsewhere or nothing. Thanks @inth3shadows for the reports and @johnhldiver-beep. (#2975, #3292)
  • In PHP, a method called in a different letter case than its declaration, like PriceConverter::CalcBasePrice(1) or $c->GetRate() for calcBasePrice and getRate, now links to that method, as PHP reads method names without regard to case, so those calls show up in callers and impact. Thanks @artisanya for the report and @johnhldiver-beep. (#3297)
  • In PHP code written for PHP 7 and older, a string offset in braces, like $code{0}, no longer makes the function or class around it disappear from the index with its calls credited to the file; it now reads like $code[0]. Thanks @artisanya for the report. (#3299)
  • In PHP, a require or include of a file inside a function or method now counts as that function depending on the file, so callers and impact follow code in the included file back to the function and its callers. Thanks @artisanya for the report. (#3296)
  • In PHP, an include built from the file's own directory, like require_once __DIR__ . '/inc/a.php' or dirname(__FILE__) . '/inc/b.php', now links to that file the way a plain require_once 'lib.php' does, and a path starting with ./ or ../ links only to the file named exactly, as PHP loads it, never one with .php added. Thanks @artisanya for the report and @inth3shadows. (#3298)

Rust

  • In Rust, a call through a module that a glob use brings in, like gzip::write() in a test module with use super::*, or that a use inside the function names, now links to that module's function again. Thanks @Egrn for the report and @mohitdixit02. (#3253)
  • In Rust, codegraph_explore's blast radius now recognizes unit tests in a #[cfg(test)] module or a tests.rs file, instead of reporting "no tests found" for the functions they test. Thanks @moogiemode for the report and @maxmilian. (#3265)
  • In Rust, a function or method passed as a value through its path, like g.map(Graph::counts) or .map(Self::helper), now counts in its callers and impact the way a function passed by name already did, linked only when the path names it for certain: never another type's method of the same name, and never a method of a trait implementation, since which one Rust uses there depends on the type of the argument. Thanks @Egrn for the report and @inth3shadows. (#3254)
  • In Rust, a call on a value whose type comes from outside your project, like an outside crate's builder chain or stdout.flush(), no longer links to one of your methods that only shares its name, such as your own impl Write's write and flush or an associated function like Graph::build(n), and Rules::default() on a #[derive(Default)] type no longer links to another type's default. Thanks @Egrn for the report. (#3252)
  • In Rust, a call written in the arguments of format!, println!, write!, assert_eq!, vec!, matches! or serde_json's json! now links to the function or method it calls, as the same call outside the macro does, and a variant in a matches! pattern now counts as a use of its enum. Thanks @Egrn for the report. (#3251)

Go, Swift, Dart, C and C++

  • A C++ .h header that only declares functions and extern variables, with no class, namespace or template in it, is now read as C++ when it uses a template type like CComPtr<IDiaDataSource>, a reference parameter like bstr_t& path or const qstring &name, or a default argument like int depth = 0, instead of as C, which dropped its symbols and warned "parse produced no symbols (tree has errors)". Thanks @sonyps5201314 for the report. (#3397)
  • In Swift, a type no longer picks up the inheritance of a type nested inside it, which linked a name used in the type to an unrelated type's nested type and put it in the wrong impact results. Thanks @bob-codedaptive for the report and @remote-controlled-man. (#3213)
  • In Go, a method called on new(T) or make(T) now links to that type's method, not a same-named method of another type that happened to be found first. Thanks @inth3shadows for the report. (#3237)
  • In Swift, an if or while whose condition is try await f() no longer breaks the method around it: the next member landed inside that method, and calls were recorded under names made of source text. Swift files are now read with a newer Swift grammar, which also parses more Swift 6 code without errors. Thanks @bob-codedaptive for the report. (#3212)
  • In Dart, a class declared with a Dart 3.13 primary constructor, like class Point(final int x, final int y) {…} or class const Foo({required final int a}), is now indexed under its own name with its members, where it had been named const or dropped with the rest of its file; Dart files are now read with a newer Dart grammar, which also parses dot shorthands and other recent Dart syntax without errors. Thanks @cutehackers for the report. (#3270)
