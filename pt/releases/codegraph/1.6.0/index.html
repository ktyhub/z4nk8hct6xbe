#gráfico de código v1.6.0

[1.6.0] - 26/08/2026

Destaques

  • GitHub Copilot agora é suportado — codegraph install configura-o no VS Code, no Copilot CLI e nos IDEs JetBrains, ao lado dos agentes que já conhecia.
  • Configuração em um comando — codegraph install --yes --init conecta seus agentes e indexa seu projeto sem avisos, ideal para um novo contêiner ou CI.
  • Melhores respostas para seu agente — codegraph_explore não repete mais o código que já lhe mostrou, sempre traz de volta os arquivos e símbolos que você solicitou pelo nome e gasta seu espaço no código que realmente responde à pergunta, em vez de sósias, arquivos gerados e correções de tipo.
  • Seu gráfico permanece correto enquanto você continua codificando — um índice de longa execução não muda mais de um novo e as edições em codegraph.json (como exclude) são aplicadas imediatamente, sem reinicialização.
  • Chega de travamentos ou travamentos silenciosos — arquivos C/C++ profundamente aninhados, projetos Swift Vapor e grandes lotes de sincronização que costumavam interromper ou interromper a indexação agora terminam de forma limpa.
  • Um vazamento de espaço em disco foi corrigido — uma sessão forçada poderia deixar o log write-ahead do banco de dados para trás para crescer sem limites (dezenas de gigabytes foram relatadas); o log restante agora é dobrado de volta no índice e cortado automaticamente na próxima vez que o projeto for aberto. O índice em si não tem limite de tamanho.
  • Funciona a partir de um espaço de trabalho ou raiz monorepo — o servidor MCP encontra seu projeto indexado quando iniciado a partir de uma pasta acima dele e diz isso claramente quando não consegue encontrar um.
  • Gráficos de código mais precisos para projetos TypeScript, Rust, Erlang, C/C++ e Python — veja a lista completa abaixo.
  • Também novo: configuração do Codex por projeto (codegraph install --location=local), uma configuração deprioritize para evitar que pastas auxiliares superem seu código real, o comando codegraph context e estatísticas de uso que agora permanecem inteiramente nos próprios servidores do CodeGraph. Após a atualização, execute codegraph index uma vez em cada projeto para que seu gráfico existente receba essas correções - codegraph status lembra você quando for necessário.

Novos recursos

  • GitHub Copilot agora é um agente compatível: codegraph install pode configurar o Copilot Chat no VS Code (copilot-vscode), o GitHub Copilot CLI (copilot-cli) e o plugin Copilot em JetBrains IDEs (copilot-jetbrains). As superfícies do Copilot instaladas são detectadas automaticamente como qualquer outro agente, as entradas existentes do servidor MCP em seus arquivos de configuração são preservadas e o codegraph uninstall reverte a configuração de forma limpa. Reinicie o VS Code ou seu JetBrains IDE após a instalação para que o Copilot pegue o servidor.
  • codegraph install --init conecta seus agentes e cria o índice do projeto atual em um comando, e codegraph init --yes é executado sem nenhum prompt - portanto, um novo contêiner ou trabalho de CI pode inicializar o CodeGraph com uma única linha não interativa (codegraph install --yes --init). O instalador ainda nunca indexa nada, a menos que você solicite isso com o sinalizador, e a recusa de segurança usual para um diretório inicial ou raiz do sistema de arquivos se aplica. (#1578)
  • O Codex CLI agora pode ser configurado por projeto, em vez de apenas para todo o usuário: codegraph install --location=local grava ./.codex/config.toml e o bloco CodeGraph no AGENTS.md do seu projeto, portanto, o CodeGraph é conectado apenas a esse repositório, em vez de a cada sessão do Codex na máquina. codegraph uninstall --location=local inverte isso e a instalação global permanece intacta de qualquer maneira. O Codex só aplica a configuração de um projeto depois que você marca o projeto como trusted, então o instalador diz isso após uma instalação local. Obrigado @maxmilian. (#1531)
  • Uma nova configuração deprioritize em codegraph.json evita que os caminhos que você nomeia superem o código do seu produto na pesquisa e nas respostas codegraph_explore, sem remover nada do índice. Ele usa padrões no estilo gitignore, assim como exclude, mas é apenas de classificação: árvores de script auxiliar, saída gerada ou diretórios complementares opcionais cujos nomes de símbolos genéricos (usage, run, status) de outra forma excluiriam o código que realmente responde a uma consulta permanece totalmente indexado e localizável - e uma consulta que realmente visa tal árvore ainda a retorna. Obrigado @maxmilian. (#982)
  • codegraph_explore não reenvia mais a fonte que já retornou anteriormente na mesma conversa. Um arquivo que ele já mostrou retorna como um ponteiro curto — o caminho, os símbolos e o intervalo exato de linhas, com a confirmação de que o arquivo não mudou desde então — e o espaço liberado é gasto em código que você ainda não viu, portanto, uma chamada de acompanhamento cobre novos caminhos em vez de repetir o último. Se um arquivo foi editado no meio, sua fonte sempre será mostrada novamente por completo. Configure CODEGRAPH_EXPLORE_DEDUP=0 para desligar isso.
  • Quando um agente se conecta pelo MCP, o CodeGraph agora declara antecipadamente que indexa mais de 30 idiomas — TypeScript/JavaScript, Python, Go, Rust, Java, C#, C/C++, PHP, Ruby, Swift, Kotlin e muito mais — para que os agentes não presumam mais que uma linguagem não é suportada e pulem o gráfico. (#671)
  • A telemetria de uso anônimo agora é armazenada inteiramente na infraestrutura própria da CodeGraph – nenhum fornecedor de análise terceirizado recebe nada disso, e o endpoint que a recebe não faz nenhuma solicitação de saída. Os eventos individuais são excluídos após 90 dias, deixando apenas totais diários anônimos. Nada mudou no que é coletado, seu endereço IP ainda nunca é lido ou armazenado e cada interruptor funciona exatamente como antes (codegraph telemetry off, CODEGRAPH_TELEMETRY=0, DO_NOT_TRACK=1). TELEMETRY.md continua sendo a lista completa campo por campo.

Correções

Melhores respostas de codegraph_explore

  • Nomear um arquivo pelo seu caminho em uma consulta codegraph_explore agora funciona de forma confiável: o caminho é resolvido em relação ao índice e esse arquivo tem um lugar garantido no topo da resposta. Anteriormente, o caminho era dividido em fragmentos - segmentos de rota entre colchetes, como [id] do SvelteKit, tornavam isso pior - e partes como page ou runs correspondiam a todos os arquivos irmãos, de modo que o arquivo que você realmente nomeou poderia ser totalmente excluído da resposta. Um caminho que não corresponde a nenhum arquivo indexado agora é chamado em vez de ser ignorado silenciosamente.
  • Nomear um arquivo kebab-case sem sua extensão em uma consulta codegraph_explore - background-image-table em vez de background-image-table.tsx, como os caminhos de importação e a prosa o escrevem - agora retorna esse arquivo exato também. Anteriormente, o nome era dividido em hífens e, em um frontend com caixa de kebab, essas partes (background, image, table) estão entre as palavras mais comuns na base de código, portanto, arquivos irmãos semelhantes preenchiam a resposta enquanto o arquivo nomeado nunca aparecia. Palavras hifenizadas que não nomeiam um arquivo indexado, como "chamada cruzada" ou "sem bloqueio", são deixadas em paz.
  • Perguntas codegraph_explore claramente formuladas agora encontram o código camelCase: uma consulta como "rolagem automática para baixo" pode alcançar uma função chamada scrollFeedToBottom, porque as palavras de consulta são comparadas com as palavras dentro dos identificadores, não apenas com nomes inteiros.
  • Variáveis ​​e constantes agora contam quando codegraph_explore escolhe seus símbolos iniciais, então o estado mantido em variáveis ​​simples - variáveis ​​estilo $state em Svelte, por exemplo - não é mais esquecido.
  • O codegraph_explore agora concentra sua resposta no código que realmente responde à sua pergunta, em vez de espalhá-la em arquivos que apenas compartilham uma palavra com ele, para que mais respostas cheguem em uma única chamada. Obrigado @LeDuyViet pelas medições detalhadas e reprodução. (#1500)
  • Arquivos pouco relacionados à sua pergunta agora retornam como nome, símbolo e número de linha, em vez de gastar a resposta em sua fonte - nomeie um deles em um acompanhamento codegraph_explore para recuperá-lo por completo. (#1500)
  • Uma camada CRUD ou protobuf gerada não exclui mais o código escrito à mão ao lado dela: os arquivos gerados agora são reconhecidos pelo banner estilo // Code generated by … DO NOT EDIT. escrito na parte superior do arquivo, não apenas por um nome de arquivo que parece gerado. Reindexe após a atualização para obter a nova detecção. (#1500)
  • Os arquivos de teste e especificações no diretório test/ ou spec/ de nível superior de um repositório agora são reconhecidos como tal, portanto, eles não ocupam mais espaço do código que você perguntou. (#1500)
  • Arquivos de declaração de tipo gerados que se anunciam com um banner "Gerado por... executando..." — o worker-configuration.d.ts do Cloudflare Wrangler é o comum — agora são reconhecidos como gerados. Anteriormente, um arquivo como esse poderia conter a maior parte de uma resposta codegraph_explore com nada mais do que algumas palavras comuns, eliminando totalmente o código escrito à mão sobre o qual você perguntou da resposta. Reindexe após a atualização para obter a nova detecção.
  • Um arquivo de declaração de tipo escrito à mão - um ambiente .d.ts de correções globais, digitações de fornecedores, aumento de módulo - não substitui mais uma resposta codegraph_explore sobre como algo funciona. Arquivos como esses declaram nomes comuns (Body, Message, ImageMetadata) e nada mais, portanto, uma pergunta redigida de maneira clara poderia corresponder a outra com força suficiente para ser classificada em primeiro lugar e excluir o manipulador real da resposta. Eles agora têm classificação inferior em questões sobre comportamento e ainda são listados por nome, de modo que uma ligação de acompanhamento os busca. Perguntar sobre um tipo pelo nome ainda retorna sua declaração primeiro, e um módulo de tipos compartilhados que o restante do seu código importa não é afetado.
  • Quando você nomeia um símbolo em uma consulta codegraph_explore, sua definição agora retorna. Dois casos anteriormente perderam. Se os símbolos que você nomeou não se chamam - funções irmãs dentro da mesma fábrica ou módulo são o exemplo cotidiano - o CodeGraph parou de tratá-los como símbolos que você havia solicitado e respondeu com o que quer que estivesse no topo do arquivo; em um arquivo de 1.400 linhas que significava que uma interface QueuedMessage de mesma haste na linha 70 voltou, enquanto a função queueMessage na linha 1087 não. E quando uma resposta precisava ser cortada para caber, ela era cortada da parte inferior do arquivo para baixo, de modo que um símbolo próximo ao final de um arquivo longo era sempre a primeira coisa a ser cortada. O corte agora protege as definições que você nomeou onde quer que estejam no arquivo.
  • Um arquivo construído em torno de uma função muito longa não ocupa mais toda a resposta do codegraph_explore - ou desaparece dela. Anteriormente, esse arquivo era mostrado por completo, por maior que fosse, o que ocupava o espaço de cada arquivo necessário, e quando a função era maior que a resposta inteira, o arquivo era descartado sem uma palavra. Esses arquivos agora retornam como uma janela delimitada em linhas inteiras - a assinatura e a parte superior do corpo, mais o local da chamada quando o caminho da chamada passa por ele - com o restante a um codegraph_explore de acompanhamento de distância.
  • codegraph_explore não permite mais que o primeiro arquivo de uma resposta ocupe o espaço reservado para os arquivos abaixo dele, então o restante da resposta ainda chega. Anteriormente, um arquivo grande próximo ao topo poderia silenciosamente consumir tudo o que restava, e os arquivos classificados abaixo dele - cada um já considerado relevante o suficiente para ser incluído - eram descartados sem nenhuma fonte; em uma pergunta, apenas um dos seis respondeu. Cada arquivo agora mantém o que foi fornecido, e uma pergunta que realmente é sobre um arquivo ainda se concentra nesse arquivo.
  • Quando uma resposta codegraph_explore atinge seu limite de tamanho, ela agora descarta as notas finais em vez da fonte de um arquivo inteiro. Anteriormente, o último arquivo era cortado, embora apenas o corte das notas pudesse caber, então um arquivo que já havia sido lido, classificado e renderizado era jogado fora no último momento. Em vários projetos reais, isso retorna mais um arquivo e até 20% mais fonte por chamada.
  • Cada arquivo que codegraph_explore decide incluir agora chega de fato. Um arquivo mostrado na íntegra ainda poderia gastar espaço reservado para os arquivos abaixo dele - a correção acima cobria os arquivos mostrados como trechos, mas não os arquivos mostrados inteiros - e a contabilidade do próprio tamanho da resposta subestimava o título de cada arquivo, então a resposta ultrapassou seu limite e um arquivo totalmente preparado foi descartado no final. Um arquivo que não cabe mais no todo agora é mostrado como trechos em vez de desaparecer, e um que ultrapassa um pouco é cortado para caber em vez de descartado.
  • A lista de arquivos que uma resposta não poderia cobrir - as dicas "explore esses nomes em busca de sua fonte" - não é mais descartada quando a resposta está completa. Agora ele está orçado e ajustado para caber, então uma resposta completa ainda informa o que foi deixado de fora e quais nomes pedir em seguida, em vez de terminar sem nenhuma indicação.
  • Quando uma resposta codegraph_explore mostra um arquivo como trechos, um trecho grande que não cabe mais foi totalmente descartado em vez de ser encurtado. Se o primeiro trecho do arquivo fosse trivial - um bloco de importação, um auxiliar de uma linha ao lado do código que você perguntou - o trecho que continha a resposta real era aquele jogado fora, e o arquivo voltava com um quarto do espaço que lhe foi concedido. Em projetos reais, isso significava que o arquivo mais bem classificado entregava uma fração de sua parcela, enquanto um arquivo muito menos relevante ficava com o restante. Os trechos agora são encurtados para caber, método inteiro por método inteiro, e somente descartados quando o que resta é pequeno demais para conter qualquer coisa legível.
  • A seção de raio de explosão do codegraph_explore sinalizou "nenhum teste de cobertura encontrado" sempre que nenhum teste chamou um símbolo diretamente - marcando falsamente os auxiliares que testam o exercício através de seus chamadores como não testados (cerca de 40% dos símbolos sinalizados em uma amostra medida). A verificação agora segue as cadeias de chamadores em até 3 saltos e relata a cobertura indireta como “testada por meio de chamadores”; quando nada é encontrado, ele indica exatamente o que foi verificado, em vez de um aviso incondicional. Obrigado @inth3shadows por medir a taxa de falsos positivos. (#1475)
  • Quando um arquivo é alterado no disco após sua última sincronização de índice, codegraph_node e codegraph_explore podem retornar um código de símbolo diferente sob o nome solicitado - bytes atuais do arquivo cortados em posições de linha desatualizadas - enquanto o apresentam como fonte literalmente, trustworthy. Isso atingiu mais fortemente os projetos consultados por meio de projectPath (por exemplo, subprojetos de um monorepo), que não possuem um observador de arquivos ativo para sinalizar edições pendentes. Ambas as ferramentas agora verificam cada arquivo em relação ao índice antes de mostrar o código fatiado: um arquivo desatualizado é mostrado inteiro com sua fonte atual completa ou seu código é retido com um aviso claro de "alterado no disco" - nunca servido como uma fatia errada. Uma nova reindexação restaura a saída normal automaticamente. Obrigado @inth3shadows pelo relatório completo e pelas verificações. (#1474)

Encontrando seu projeto, atualizações ao vivo e o CLI

  • O servidor MCP agora encontra seu projeto quando ele é iniciado a partir de uma pasta de espaço de trabalho acima dele: se o diretório de inicialização não tiver índice próprio, mas exatamente um projeto indexado estiver abaixo dele (um contêiner de repositório, um espaço de trabalho de agente, uma raiz monorepo), esse projeto se tornará o padrão da sessão - observação de arquivos ao vivo e o daemon compartilhado incluído - em vez de cada chamada de ferramenta falhar até que um projectPath ou --path seja fornecido. Obrigado @nakisen. (#1606)
  • Quando nenhum projeto pode ser resolvido, o servidor MCP agora diz isso em vez de iniciar silenciosamente: uma linha de log de inicialização nomeia o diretório pesquisado e as chamadas de ferramenta listam os subprojetos indexados que podem ser vistos nas proximidades, para que você possa passar um como projectPath. Anteriormente, o servidor parecia saudável visto de fora, enquanto todas as ferramentas silenciosamente não tinham nenhum projeto para responder. Obrigado @nakisen. (#1607)
  • A edição do exclude ou include (ou .gitignore) do codegraph.json enquanto o servidor MCP está em execução agora entra em vigor imediatamente. Anteriormente, o inspetor de arquivos em execução mantinha o escopo que tinha quando foi iniciado, então um arquivo recém-excluído foi removido pelo codegraph sync e então adicionado silenciosamente pelo inspetor segundos depois - o que parecia que o exclude não estava funcionando - até que o servidor fosse reiniciado. Uma mudança de escopo agora atualiza o inspetor e aciona uma reconciliação completa, e um arquivo alterado que o inspetor sincroniza é verificado novamente em relação ao escopo atual primeiro, para que o CLI e o servidor ativo não possam mais discordar sobre o que pertence ao índice. Obrigado @K1nG11. (#1590)
  • codegraph status agora vê novos arquivos em diretórios totalmente novos. O Git relata um diretório totalmente não rastreado como uma única entrada recolhida, então os arquivos de origem criados lá - um frontend/ recém-construído, por exemplo - estavam faltando no relatório de alterações pendentes, que poderia alegar que tudo estava atualizado enquanto esses arquivos ainda não haviam sido indexados. Obrigado @maxmilian. (#1213)
  • O comando codegraph context <task> documentado na ajuda do CLI agora realmente existe - ele cria um pacote de contexto pronto para injetar para uma tarefa (símbolos relevantes, seus relacionamentos e código) em markdown ou JSON, restaurando o contrato de integrações externas como o Memorix depende (--path, --format json, --max-nodes, --no-code). (#1611)
  • No Windows, o gancho de prompt do Claude Code escrito por codegraph install falhou com "comando não encontrado" quando os ganchos são executados no Git Bash, que precisa da extensão .cmd para encontrar o inicializador. O instalador agora escreve o comando de correção de plataforma e a nova execução do codegraph install (ou codegraph upgrade) repara uma instalação existente no local. (#1466)
  • Procurar um símbolo pelo nome não lê mais o gráfico inteiro. Cada pesquisa fez uma passagem completa por todos os símbolos indexados para cada palavra digitada, e uma pergunta que nomeou vários símbolos fez mais duas passagens por nome – inclusive para uma palavra que não corresponde a nada, o que é o caso comum. O custo, portanto, cresceu com o tamanho do projeto e foi pago novamente em cada mensagem quando o prompt hook foi ativado. Essas pesquisas agora passam pelo índice de nomes. Os resultados são idênticos; apenas o tempo para obtê-los muda, e não cresce mais com o projeto. Obrigado @maxmilian.

Confiabilidade da indexação e uso do disco

  • A indexação não trava mais todo o processo — uma falha de segmentação sem mensagem e sem índice parcial — em um arquivo C/C++ (ou qualquer outro) com aninhamento extremamente profundo, como os acessórios de teste de estresse do analisador nos conjuntos de testes clang e gcc ou um corpus fuzzer. Esse arquivo agora é entregue ao analisador substituto e registrado com um aviso de análise enquanto o restante do repositório indexa normalmente. Obrigado @apollo600 pelo diagnóstico exato. (#1581)
  • A indexação não trava mais em um projeto Swift Vapor contendo uma chamada com uma longa lista de argumentos. Uma única chamada no estilo .get(...) com muitos argumentos rotulados e nenhum manipulador use: - a forma gerada pelos construtores de solicitação - poderia paralisar codegraph index, codegraph sync e o servidor MCP indefinidamente. A detecção de rota agora lida com esses arquivos em milissegundos, e cada formato de rota reconhecido anteriormente ainda é analisado exatamente como antes. Obrigado @maxmilian. (#1544) (Rápido)
  • A sincronização de um grande lote de arquivos alterados não trava mais com "Tamanho máximo da pilha de chamadas excedido" no meio do processo. A falha abortou a resolução de referência depois que os símbolos dos arquivos já estavam armazenados, deixando o gráfico com muito menos conexões do que um novo índice teria – e atingiu exatamente os cenários que analisam novamente muitos arquivos de uma vez, incluindo o reparo automático acima. Obrigado @netbrah por identificar a falha. (#1558)
  • Um índice de longa duração não se afasta mais do que um novo codegraph index produziria. Quando um arquivo ganhava ou perdia um símbolo, as referências a esse nome em arquivos que a sincronização nunca tocou continuavam apontando para a definição que estava correta antes da alteração e - como nada distinguia duas definições com o mesmo nome - o vencedor poderia se resumir à ordem em que os arquivos foram gravados, que difere entre um índice completo e uma sincronização. No próprio repositório deste projeto, a repetição de 80 commits por meio de sync deixou 5.7% de conexões erradas; agora é 1.3%, e a metade das respostas erradas ainda sendo afirmadas cai em 99.7%. Como as bordas de chamada são o que as perguntas de fluxo seguem e o que codegraph_explore classifica os arquivos, isso degrada silenciosamente as respostas à medida que um índice envelhece, sem nada que indique isso. A velocidade da sincronização permanece inalterada e uma edição que altera apenas o corpo de uma função não gera nenhum trabalho extra. Configure CODEGRAPH_NO_REBIND=1 para cancelar.
  • Corrigida uma regressão v1.5.0 onde um arquivo perfeitamente válido poderia ser registrado permanentemente como tendo 0 símbolos, sem nenhum erro relatado. Quando a primeira tentativa de análise de um arquivo foi interrompida — uma falha ou tempo limite do trabalhador de análise, provavelmente em máquinas lentas ou muito carregadas — a nova tentativa automática armazenou um resultado vazio para qualquer idioma no caminho de extração nativo, de modo que as funções e classes do arquivo desapareceram silenciosamente da pesquisa, dos chamadores e do impacto até que o arquivo fosse editado novamente. As novas tentativas agora armazenam os símbolos reais do arquivo, e um arquivo já gravado como livre de símbolos é detectado e reparado automaticamente na próxima sincronização ou reindexação após a atualização. Obrigado @Baiae pelo relatório. (#1541)
  • Um processo CodeGraph que é eliminado à força — pelo watchdog do processo travado, por uma falha ou pelo sistema operacional — não deixa mais o log de gravação antecipada do banco de dados para crescer sem limites. Anteriormente, cada sessão eliminada empilhava mais dados no mesmo arquivo de log e nada os reduzia, o que em máquinas onde as sessões eram encerradas regularmente poderia consumir silenciosamente dezenas de gigabytes de disco. O tamanho restante do log agora é limitado (64 MB por padrão; CODEGRAPH_WAL_HEAL_MB o altera) e qualquer sobra de tamanho grande é dobrada de volta no índice e cortada automaticamente na próxima vez que o projeto for aberto. Isso limita apenas o log — o índice em si não tem limite de tamanho, e o log de um grande repositório ainda pode crescer proporcionalmente ao seu índice enquanto está sendo construído. Obrigado @tiendungdev pelo relatório excepcional do Windows que definiu isso. (#1431)
  • O watchdog do servidor em segundo plano não mata mais um servidor íntegro que está apenas esperando em um disco lento: assim como a indexação já faz, ele agora verifica se os arquivos do banco de dados ainda estão progredindo antes de concluir que o processo está travado. Menos mortes espúrias também significam menos registros de write-ahead restantes. (#1431)
  • codegraph status agora mostra o tamanho do log write-ahead próximo ao tamanho do banco de dados e avisa quando as sessões encerradas o deixaram superdimensionado, e cada linha no log do servidor em segundo plano agora carrega um carimbo de data / hora para que as eliminações e reinicializações possam ser feitas a tempo. (#1431)
  • Um daemon em segundo plano deixado para trás por uma eliminação por falta de memória ou eliminação forçada não pode mais bloquear todas as sessões futuras quando o sistema operacional reutiliza seu ID de processo: o gerenciamento de daemon agora verifica se um processo gravado é realmente um daemon CodeGraph antes de trusting ou sinalizá-lo, e codegraph unlock limpa artefatos de daemon obsoletos, bem como o bloqueio de indexação. Obrigado @hcg1023 pelo relatório e @danusha2345 pela correção. (#1553)
  • Quando a indexação precisa voltar a analisar um arquivo com suas linhas de comentários removidas — uma recuperação de último recurso após falhas repetidas do analisador — o arquivo agora é sinalizado com um aviso visível em vez de ser relatado como indexado de forma limpa. O resultado recuperado pode estar incompleto, e o relatório de sucesso fez com que um novo índice discordasse discretamente de uma nova análise posterior do mesmo arquivo inalterado. Obrigado @jeremypetz pela contabilidade precisa do símbolo init-versus-sync que expôs isso. (#1565)
  • Cabeçalhos C/C++ somente de dados próximos ao limite de tamanho de arquivo não retêm mais um trabalho do analisador por vários minutos antes do tempo limite; o orçamento padrão de análise de arquivos grandes agora é limitado, enquanto um tempo limite maior configurado explicitamente ainda é respeitado. (#1555)
  • Reabrir um índice após uma falha durante o carregamento em massa agora restaura todos os índices de banco de dados descartados, e uma sincronização de recuperação bem-sucedida marca o índice como concluído, em vez de deixá-lo permanentemente sinalizado como interrompido. (#1556)
  • Os arquivos ignorados porque são muito grandes ou falham repetidamente na análise agora são gravados com o motivo, portanto, os arquivos rejeitados inalterados não são mais cobertos e repetidos em cada verificação de status e sincronização - e uma análise posterior bem-sucedida de tal arquivo substitui o registro por seus símbolos reais. Obrigado @netbrah pela excepcional análise de falhas por trás deste lote e @danusha2345 pelas correções. (#1557)
  • A análise de ponteiro de função C/C++ agora limita seus caches de padrão compilado, de modo que repositórios muito grandes não podem mais esgotar o espaço de código de expressão regular do mecanismo JavaScript durante a indexação. (#1559)
  • A análise de renderização JSX agora é executada apenas em arquivos da família JavaScript, portanto, strings com aparência de JSX em C/C++ (ou qualquer outra linguagem) não criam mais bordas de chamada impossíveis - em projetos C puro e em monorepos de linguagem mista. (#1560)

Precisão da linguagem e da estrutura

  • Chamadas para os métodos de uma constante literal de objeto exportada — export const api = { call() { … } } usada como namespace de um módulo, uma forma comum de organizar uma superfície TypeScript API — agora resolvem para o método, tanto no arquivo de definição quanto por meio de importações. Anteriormente, tal chamada não estava vinculada a nada (ou à própria constante), então codegraph callers e a análise de impacto relataram zero chamadores para métodos que são chamados de qualquer lugar. Reindexe após a atualização para capturar as bordas. Obrigado @IAliceBobI pelo relatório preciso e pela causa raiz. (#1573)
  • Os aliases de importação definidos em uma configuração compartilhada do TypeScript agora são selecionados. Os monorepos estilo Nx mantêm todos os alias @scope/... em um tsconfig.base.json que a raiz tsconfig.json só herda por meio de extends, então o CodeGraph não encontrou nenhum alias e cada importação de pacote cruzado voltou a corresponder apenas ao nome - o que silenciosamente anexa resultados a símbolos não relacionados que compartilham um nome, exatamente onde um monorepo precisa que codegraph_impact e codegraph_callers estejam certo. Encadeia várias configurações profundas, uma configuração herdada de um pacote em node_modules e um baseUrl declarado em uma configuração herdada são todos seguidos agora, e um tsconfig.base.json é lido diretamente quando o tsconfig.json raiz é apenas um shell de referências de projeto ou não existe. Reindexar após a atualização. Obrigado @maxmilian. (#1534)
  • Os métodos implementados em um bloco impl genérico ou com parâmetros de vida útil (impl<T> Source for BufSource<T>, impl<'a> Iterator for Parents<'a>) agora são registrados no tipo de implementação em vez da característica. Anteriormente, tal método não podia ser encontrado por seu tipo - "quem chama BufSource::read" não tinha resposta - e colidia com a própria declaração do traço, que poderia até inventar uma borda de gráfico de chamada a partir de um corpo impl que não contém nenhuma chamada. As impls em uma referência (impl Trait for &Foo) e em um tipo qualificado para módulo (impl Trait for m::Foo) também são atribuídas ao seu tipo. Reindexar após a atualização. Obrigado @Dshuishui. (#1588) (Rust)
  • Uma chamada de método em um campo struct — self.inner.run() com inner: Inner — agora resolve o método no tipo declarado do campo. Anteriormente, a chamada era reduzida ao nome do método simples e correspondia ao método com o mesmo nome mais próximo, que geralmente era o próprio método de chamada, registrando a recursão que não está na origem (algumas centenas dessas bordas próprias apenas no ripgrep) ou um método de um tipo não relacionado. As referências e os campos Box/Rc/Arc são consultados, assim como as chamadas de método do próprio Rust; um campo cujo tipo é externo (um tipo padrão ou de terceiros), um parâmetro genérico ou um contêiner como Option/Vec é deixado sem solução em vez de adivinhado. Reindexar após a atualização. Obrigado @Dshuishui. (#1585) (Rust)
  • Funções Erlang que compartilham um nome, mas diferem em aridade agora são símbolos separados com a própria identidade module:fun/arity da linguagem, então o f/1 diário delegando para f/2 mostra como uma borda de chamada real em vez de um auto-loop, cada aridade mantém seu próprio -spec e extensão de fonte, -export([f/1]) marca exatamente essa aridade como pública e pede a codegraph_explore um símbolo da maneira como Erlang soletra it — cowboy_req:header/3 — retorna essa definição. Reindexe projetos Erlang após a atualização. Obrigado @Dshuishui. (#1610) (Erlang)
  • O despacho de comportamento Erlang não conta mais erroneamente a aridade de um site de chamada quando um argumento é um literal binário como <<1,2,3>> - as vírgulas internas eram contadas como separadores de argumento, o que eliminava silenciosamente (ou poderia vincular incorretamente) a borda de despacho ao retorno de chamada de comportamento. (#1358) (Erlang)
  • Um cabeçalho C++ .h cuja única construção C++ é um tipo derivado simples - struct Derived : Base sem macro de exportação, palavra-chave class ou seção de acesso - agora é reconhecido como C++ (anteriormente apenas o formato de macro de exportação era). Tal cabeçalho foi lido como C, então a estrutura derivada desapareceu do índice e uma função fantasma com o nome do tipo base apareceu em seu lugar. A verificação agora também cobre todo o arquivo, em vez de seus primeiros kilobytes, de modo que um longo preâmbulo compatível com C não oculta mais o sinal. Reindexe após a atualização para coletar os cabeçalhos afetados. Obrigado @Jaysenpeng. (#1592)
  • As uniões C, C++, Objective-C e Rust agora são indexadas como nós union de primeira classe. Uma declaração union anteriormente não produzia nenhum símbolo, então ela nunca apareceu na pesquisa ou codegraph_explore, e qualquer coisa anexada a ela desapareceu com ela - em Rust, cada impl SomeTrait for MyUnion perdeu sua borda, os métodos daquele impl foram deixados apontando para um tipo que o gráfico não continha, e perguntar quais tipos implementam uma característica ignorava silenciosamente as uniões. Uma tabela de despacho em forma de união em C agora resolve seus ponteiros de função como uma tabela em forma de estrutura. Um typedef union { … } Name; em C mantém o nome do typedef e não é mais confundido com um alias de tipo simples. Obrigado @ctype-lab. Reindexar após a atualização para selecionar sindicatos em projetos existentes. (#1515)
  • Classes Python usadas como valores — return SomeSerializer de um método de fábrica, aliases handler = SomeClass, dictos e listas de registro e classes passadas como argumentos — agora produzem arestas de referência no gráfico. Anteriormente, esses idiomas eram invisíveis, portanto, nos projetos do Django e do Django REST Framework, solicitar os chamadores de um serializador ou o impacto da edição perdia as visualizações que realmente o utilizam. Reindexe após a atualização para obter as novas arestas. (#1478)
  • As importações SAP HANA .xsjs/.xsjslib agora são resolvidas entre arquivos: um import { x } from './helpers' sem extensão em um arquivo .xsjs encontra helpers.xsjslib, então a borda de chamada entre arquivos é criada e codegraph_callers/codegraph_impact a vê. Anteriormente, o caminho de importação não era resolvido e a chamada voltava para a correspondência de mesmo nome, o que poderia vincular a borda a um arquivo não relacionado que exportasse o mesmo símbolo. Complementa o suporte de extração .xsjs / .xsjslib. Obrigado @maxmilian. (#556)

codegraph v1.6.0

[1.6.0] - 2026-08-26

Highlights

  • GitHub Copilot is now supported — codegraph install sets it up in VS Code, the Copilot CLI, and JetBrains IDEs, next to the agents it already knew.
  • Set up in one command — codegraph install --yes --init wires up your agents and indexes your project with no prompts, ideal for a fresh container or CI.
  • Better answers for your agent — codegraph_explore no longer repeats code it already showed you, always brings back the files and symbols you asked for by name, and spends its space on the code that actually answers the question rather than look-alikes, generated files, and type shims.
  • Your graph stays right as you keep coding — a long-running index no longer drifts from a fresh one, and edits to codegraph.json (such as exclude) apply immediately without a restart.
  • No more silent crashes or hangs — deeply nested C/C++ files, Swift Vapor projects, and large sync batches that used to kill or stall indexing now finish cleanly.
  • A disk-space leak is fixed — a force-killed session could leave the database's write-ahead log behind to grow without bound (tens of gigabytes was reported); the leftover log is now folded back into the index and trimmed automatically the next time the project opens. The index itself has no size limit.
  • Works from a workspace or monorepo root — the MCP server finds your indexed project when launched from a folder above it, and says so clearly when it can't find one.
  • More accurate code graphs for TypeScript, Rust, Erlang, C/C++, and Python projects — see the full list below.
  • Also new: per-project Codex setup (codegraph install --location=local), a deprioritize setting to keep helper folders from outranking your real code, the codegraph context command, and usage stats that now stay entirely on CodeGraph's own servers.

After upgrading, run codegraph index once in each project so your existing graph picks up these fixes — codegraph status reminds you when it's needed.

New Features

  • GitHub Copilot is now a supported agent: codegraph install can configure Copilot Chat in VS Code (copilot-vscode), the GitHub Copilot CLI (copilot-cli), and the Copilot plugin in JetBrains IDEs (copilot-jetbrains). Installed Copilot surfaces are auto-detected like every other agent, existing MCP server entries in their config files are preserved, and codegraph uninstall reverses the setup cleanly. Restart VS Code or your JetBrains IDE after installing so Copilot picks up the server.

  • codegraph install --init wires up your agents and builds the current project's index in one command, and codegraph init --yes runs without any prompts — so a fresh container or CI job can bootstrap CodeGraph with a single non-interactive line (codegraph install --yes --init). The installer still never indexes anything unless you ask for it with the flag, and the usual safety refusal for a home directory or filesystem root applies. (#1578)

  • Codex CLI can now be set up per project instead of only user-wide: codegraph install --location=local writes ./.codex/config.toml and the CodeGraph block in your project's AGENTS.md, so CodeGraph is wired into that repo only rather than every Codex session on the machine. codegraph uninstall --location=local reverses it, and the global install is untouched either way. Codex only applies a project's config once you've marked the project trusted, so the installer says so after a local install. Thanks @maxmilian. (#1531)

  • A new deprioritize setting in codegraph.json keeps the paths you name from outranking your product code in search and codegraph_explore answers, without removing anything from the index. It takes gitignore-style patterns just like exclude, but is ranking-only: helper-script trees, generated output, or optional add-on directories whose generic symbol names (usage, run, status) would otherwise crowd out the code that actually answers a query stay fully indexed and findable — and a query that genuinely targets such a tree still returns it. Thanks @maxmilian. (#982)

  • codegraph_explore no longer re-sends source it already returned earlier in the same conversation. A file it has already shown you comes back as a short pointer — the path, the symbols and the exact line range, with confirmation that the file hasn't changed since — and the space that frees is spent on code you haven't seen yet, so a follow-up call covers new ground instead of repeating the last one. If a file was edited in between, its source is always shown again in full. Set CODEGRAPH_EXPLORE_DEDUP=0 to turn this off.

  • When an agent connects over MCP, CodeGraph now states up front that it indexes 30+ languages — TypeScript/JavaScript, Python, Go, Rust, Java, C#, C/C++, PHP, Ruby, Swift, Kotlin, and more — so agents no longer assume a language isn't supported and skip the graph. (#671)

  • Anonymous usage telemetry is now stored entirely on CodeGraph's own first-party infrastructure — no third-party analytics vendor receives any of it, and the endpoint that receives it makes no outbound requests at all. Individual events are deleted after 90 days, leaving only anonymous daily totals. Nothing about what is collected changed, your IP address is still never read or stored, and every off-switch works exactly as before (codegraph telemetry off, CODEGRAPH_TELEMETRY=0, DO_NOT_TRACK=1). TELEMETRY.md remains the complete field-by-field list.

Fixes

Better answers from codegraph_explore

  • Naming a file by its path in a codegraph_explore query now works reliably: the path is resolved against the index and that file is guaranteed a place at the top of the answer. Previously the path was broken into fragments — bracketed route segments like SvelteKit's [id] made this worst — and pieces like page or runs matched every sibling file, so the file you actually named could be crowded out of the answer entirely. A path that doesn't match any indexed file is now called out instead of silently ignored.

  • Naming a kebab-case file without its extension in a codegraph_explore query — background-image-table rather than background-image-table.tsx, the way import paths and prose spell it — now returns that exact file too. Previously the name was split at the hyphens, and in a kebab-cased frontend those pieces (background, image, table) are among the most common words in the codebase, so look-alike sibling files filled the answer while the named file never appeared. Hyphenated words that don't name an indexed file, like "cross-call" or "non-blocking", are left alone.

  • Plainly-worded codegraph_explore questions now find camelCase code: a query like "auto-scroll to bottom" can reach a function named scrollFeedToBottom, because query words are matched against the words inside identifiers, not just whole names.

  • Variables and constants now count when codegraph_explore picks its starting symbols, so state held in plain variables — $state-style variables in Svelte, for example — no longer gets overlooked.

  • codegraph_explore now concentrates its answer on the code that actually answers your question instead of spreading it across files that merely share a word with it, so more of the answer arrives in a single call. Thanks @LeDuyViet for the detailed measurements and reproduction. (#1500)

  • Files only weakly related to your question now come back as a name, symbol and line number instead of spending the answer on their source — name one of them in a follow-up codegraph_explore to get it back in full. (#1500)

  • A generated CRUD or protobuf layer no longer crowds out the hand-written code sitting beside it: generated files are now recognized by the // Code generated by … DO NOT EDIT. style banner written at the top of the file, not just by a filename that looks generated. Re-index after upgrading to pick up the new detection. (#1500)

  • Test and spec files in a repository's top-level test/ or spec/ directory are now recognized as such, so they no longer take room from the code you asked about. (#1500)

  • Generated type-declaration files that announce themselves with a "Generated by … by running …" banner — Cloudflare Wrangler's worker-configuration.d.ts is the common one — are now recognized as generated. Previously a file like that could take most of a codegraph_explore answer on nothing more than a few common words, pushing the hand-written code you asked about out of the response entirely. Re-index after upgrading to pick up the new detection.

  • A hand-written type-declaration file — an ambient .d.ts of global shims, vendored typings, module augmentation — no longer takes over a codegraph_explore answer about how something works. Files like these declare common names (Body, Message, ImageMetadata) and nothing else, so a plainly-worded question could match one strongly enough that it ranked first and crowded the actual handler out of the answer. They are now ranked lower for questions about behaviour, and are still listed by name so one follow-up call fetches them. Asking about a type by name still returns its declaration first, and a shared types module the rest of your code imports is unaffected.

  • When you name a symbol in a codegraph_explore query, its definition now actually comes back. Two cases previously lost it. If the symbols you named don't call one another — sibling functions inside the same factory or module are the everyday example — CodeGraph stopped treating them as symbols you had asked for, and answered with whatever sat at the top of their file instead; on one 1,400-line file that meant a same-stem QueuedMessage interface on line 70 came back while the queueMessage function on line 1087 did not. And when an answer had to be trimmed to fit, it was trimmed from the bottom of the file down, so a symbol near the end of a long file was always the first thing cut. Trimming now protects the definitions you named wherever they sit in the file.

  • A file built around one very long function no longer takes the whole codegraph_explore answer for itself — or disappears from it. Previously such a file was shown in full however big it was, which used up the room every file after it needed, and when the function was larger than the entire response the file was dropped without a word. These files now come back as a bounded window on whole lines — the signature and the top of the body, plus the call site when the call path runs through it — with the rest one follow-up codegraph_explore away.

  • codegraph_explore no longer lets the first file in an answer spend the room set aside for the files below it, so the rest of the answer still arrives. Previously a large file near the top could quietly use up everything left, and the files ranked under it — each already judged relevant enough to include — were dropped with no source at all; on one question only one of six made it into the answer. Every file now keeps what it was given, and a question that really is about one file still concentrates on that file.

  • When a codegraph_explore answer runs right up against its size limit, it now drops the trailing notes rather than a whole file's source. Previously the last file was cut even though trimming the notes alone would have fit, so a file that had already been read, ranked and rendered was thrown away at the last moment. Across a range of real projects this returns one more file and up to 20% more source per call.

  • Every file codegraph_explore decides to include now actually arrives. A file shown in full could still spend room set aside for files below it — the fix above covered files shown as excerpts but not files shown whole — and the answer's own size bookkeeping under-counted each file's heading, so the answer ran past its limit and a fully prepared file was discarded at the end. A file that no longer fits whole is now shown as excerpts instead of vanishing, and one that overshoots by a little is trimmed to fit rather than dropped.

  • The list of files an answer could not cover — the "explore these names for their source" pointers — is no longer thrown away when the answer is full. It is now budgeted for and trimmed to fit, so a full answer still tells you what it left out and which names to ask for next, instead of ending with no pointers at all.

  • When a codegraph_explore answer shows a file as excerpts, a large excerpt that no longer fit was dropped entirely instead of being shortened. If the file's first excerpt happened to be a trivial one — an import block, a one-line helper next to the code you asked about — the excerpt carrying the actual answer was the one thrown away, and the file came back with a quarter of the room it had been given. On real projects that meant the top-ranked file delivered a fraction of its share while a far less relevant file took the rest. Excerpts are now shortened to fit, whole method by whole method, and only dropped when what is left is too small to hold anything readable.

  • The blast-radius section of codegraph_explore flagged "no covering tests found" whenever no test called a symbol directly — falsely branding helpers that tests exercise through their callers as untested (about 40% of flagged symbols in a measured sample). The check now follows caller chains up to 3 hops and reports indirect coverage as "tested via callers"; when nothing is found it states exactly what was checked instead of an unconditional warning. Thanks @inth3shadows for measuring the false-positive rate. (#1475)

  • When a file changed on disk after its last index sync, codegraph_node and codegraph_explore could return a different symbol's code under the requested name — current file bytes cut at outdated line positions — while presenting it as verbatim, trustworthy source. This hit hardest on projects queried through projectPath (for example, sub-projects of a monorepo), which have no live file watcher to flag pending edits. Both tools now verify each file against the index before showing sliced code: an out-of-date file is either shown whole with its full current source, or its code is withheld with a clear "changed on disk" notice — never served as a wrong slice. A fresh re-index restores normal output automatically. Thanks @inth3shadows for the thorough report and verification passes. (#1474)

Finding your project, live updates, and the CLI

  • The MCP server now finds your project when it's launched from a workspace folder above it: if the launch directory has no index of its own but exactly one indexed project sits below it (a repo container, an agent workspace, a monorepo root), that project becomes the session's default — live file watching and the shared daemon included — instead of every tool call failing until a projectPath or --path is supplied. Thanks @nakisen. (#1606)

  • When no project can be resolved at all, the MCP server now says so instead of starting silently: a startup log line names the directory it searched, and tool calls list the indexed sub-projects it can see nearby so you can pass one as projectPath. Previously the server looked healthy from the outside while every tool quietly had no project to answer from. Thanks @nakisen. (#1607)

  • Editing codegraph.json's exclude or include (or a .gitignore) while the MCP server is running now takes effect immediately. Previously the running file watcher kept the scope it had when it started, so a newly excluded file was removed by codegraph sync and then quietly re-added by the watcher seconds later — which looked like exclude not working at all — until the server was restarted. A scope change now refreshes the watcher and triggers a full reconcile, and a changed file the watcher hands to sync is re-checked against the current scope first, so the CLI and the live server can no longer disagree about what belongs in the index. Thanks @K1nG11. (#1590)

  • codegraph status now sees new files inside brand-new directories. Git reports an entirely-untracked directory as a single collapsed entry, so source files created there — a freshly scaffolded frontend/, for example — were missing from the pending-changes report, which could claim everything was up to date while those files had not yet been indexed. Thanks @maxmilian. (#1213)

  • The codegraph context <task> command documented in the CLI help now actually exists — it builds a ready-to-inject context pack for a task (relevant symbols, their relationships, and code) in markdown or JSON, restoring the contract external integrations like Memorix rely on (--path, --format json, --max-nodes, --no-code). (#1611)

  • On Windows, the Claude Code prompt hook written by codegraph install failed with "command not found" when hooks run through Git Bash, which needs the .cmd extension to find the launcher. The installer now writes the platform-correct command, and re-running codegraph install (or codegraph upgrade) repairs an existing install in place. (#1466)

  • Looking a symbol up by name no longer reads the whole graph. Every search made one full pass over all indexed symbols for each word you typed, and a question that named several symbols made two more passes per name — including for a word that matches nothing, which is the common case. The cost therefore grew with the size of the project, and it was paid again on every message when the prompt hook is enabled. These lookups now go through the name index instead. Results are identical; only the time to get them changes, and it no longer grows with the project. Thanks @maxmilian.

Indexing reliability and disk usage

  • Indexing no longer crashes the whole process — a segmentation fault with no message and no partial index — on a C/C++ (or any other) file with extremely deep nesting, such as the parser stress-test fixtures in the clang and gcc test suites or a fuzzer corpus. Such a file is now handed to the fallback parser and recorded with a parse warning while the rest of the repository indexes normally. Thanks @apollo600 for the exact diagnosis. (#1581)

  • Indexing no longer hangs on a Swift Vapor project containing a call with a long argument list. A single .get(...)-style call with many labeled arguments and no use: handler — the shape generated request builders produce — could stall codegraph index, codegraph sync, and the MCP server indefinitely. Route detection now handles such files in milliseconds, and every previously-recognized route shape still parses exactly as before. Thanks @maxmilian. (#1544) (Swift)

  • Syncing a large batch of changed files no longer crashes with "Maximum call stack size exceeded" partway through. The crash aborted reference resolution after the files' symbols were already stored, leaving the graph with far fewer connections than a fresh index would have — and it hit exactly the scenarios that re-parse many files at once, including the automatic repair above. Thanks @netbrah for pinpointing the failure. (#1558)

  • A long-lived index no longer drifts away from what a fresh codegraph index would produce. When a file gained or lost a symbol, references to that name in files the sync never touched kept pointing at the definition that was correct before the change, and — because nothing distinguished two same-named definitions — the winner could come down to the order files happened to be written, which differs between a full index and a sync. On this project's own repository, replaying 80 commits through sync left 5.7% of connections wrong; it is now 1.3%, and the wrong-answers-still-being-asserted half drops by 99.7%. Since call edges are what flow questions follow and what codegraph_explore ranks files by, this quietly degraded answers as an index aged, with nothing to indicate it. Syncing is unchanged in speed, and an edit that only changes a function's body does no extra work at all. Set CODEGRAPH_NO_REBIND=1 to opt out.

  • Fixed a v1.5.0 regression where a perfectly valid file could be permanently recorded as having 0 symbols, with no error reported. When a file's first parse attempt was interrupted — a parsing worker crash or timeout, most likely on slow or heavily loaded machines — the automatic retry stored an empty result for any language on the native extraction path, so the file's functions and classes silently vanished from search, callers, and impact until the file was next edited. Retries now store the file's real symbols, and a file already recorded as symbol-free is detected and repaired automatically by the next sync or re-index after upgrading. Thanks @Baiae for the report. (#1541)

  • A CodeGraph process that gets force-killed — by the stuck-process watchdog, a crash, or the OS — no longer leaves the database's write-ahead log behind to grow without bound. Previously each killed session stacked more data onto the same log file and nothing ever shrank it, which on machines where sessions were killed regularly could quietly eat tens of gigabytes of disk. The log's resting size is now bounded (64 MB by default; CODEGRAPH_WAL_HEAL_MB changes it), and any oversized leftover is folded back into the index and trimmed automatically the next time the project is opened. This bounds only the log — the index itself has no size limit, and a large repository's log is still allowed to grow in proportion to its index while it is being built. Thanks @tiendungdev for the exceptional Windows report that pinned this down. (#1431)

  • The background server's watchdog no longer kills a healthy server that is just waiting on a slow disk: like indexing already does, it now checks whether the database files are still making progress before concluding the process is stuck. Fewer spurious kills also means fewer leftover write-ahead logs. (#1431)

  • codegraph status now shows the write-ahead log's size next to the database size and warns when killed sessions have left it oversized, and every line in the background server's log now carries a timestamp so kills and restarts can be placed in time. (#1431)

  • A background daemon left behind by an out-of-memory kill or force-kill can no longer block every future session when the operating system reuses its process ID: daemon management now verifies a recorded process is really a CodeGraph daemon before trusting or signaling it, and codegraph unlock clears stale daemon artifacts as well as the indexing lock. Thanks @hcg1023 for the report and @danusha2345 for the fix. (#1553)

  • When indexing has to fall back to parsing a file with its comment lines stripped — a last-resort recovery after repeated parser crashes — the file is now flagged with a visible warning instead of being reported as cleanly indexed. The recovered result can be incomplete, and reporting success made a fresh index quietly disagree with a later re-parse of the same unchanged file. Thanks @jeremypetz for the precise init-versus-sync symbol accounting that exposed this. (#1565)

  • Data-only C/C++ headers near the file-size limit no longer hold a parser worker for several minutes before timing out; the default large-file parse budget is now bounded, while an explicitly configured larger timeout is still honored. (#1555)

  • Reopening an index after a crash during bulk loading now restores every dropped database index, and a successful recovery sync marks the index complete instead of leaving it permanently flagged as interrupted. (#1556)

  • Files skipped because they are too large or repeatedly fail to parse are now recorded with the reason, so unchanged rejected files are no longer rediscovered and retried on every status check and sync — and a later successful parse of such a file replaces the record with its real symbols. Thanks @netbrah for the exceptional failure analysis behind this batch, and @danusha2345 for the fixes. (#1557)

  • C/C++ function-pointer analysis now bounds its compiled-pattern caches, so very large repositories can no longer exhaust the JavaScript engine's regular-expression code space during indexing. (#1559)

  • JSX rendering analysis now runs only on JavaScript-family files, so JSX-looking strings in C/C++ (or any other language) no longer create impossible call edges — in pure-C projects and in mixed-language monorepos alike. (#1560)

Language and framework accuracy

  • Calls to the methods of an exported object-literal constant — export const api = { call() { … } } used as a module's namespace, a common way to organize a TypeScript API surface — now resolve to the method, both in the defining file and through imports. Previously such a call linked to nothing (or to the constant itself), so codegraph callers and impact analysis reported zero callers for methods that are called from everywhere. Re-index after upgrading to pick up the edges. Thanks @IAliceBobI for the precise report and root-cause. (#1573)

  • Import aliases defined in a shared TypeScript config are now picked up. Nx-style monorepos keep every @scope/... alias in a tsconfig.base.json that the root tsconfig.json only inherits through extends, so CodeGraph found no aliases at all and every cross-package import fell back to matching on name alone — which quietly attaches results to unrelated symbols that happen to share a name, exactly where a monorepo needs codegraph_impact and codegraph_callers to be right. Chains several configs deep, a config inherited from a package in node_modules, and a baseUrl declared in an inherited config are all followed now, and a tsconfig.base.json is read directly when the root tsconfig.json is only a project-references shell or isn't there at all. Re-index after upgrading. Thanks @maxmilian. (#1534)

  • Methods implemented in a generic or lifetime-parameterized impl block (impl<T> Source for BufSource<T>, impl<'a> Iterator for Parents<'a>) are now recorded under the implementing type instead of the trait. Previously such a method could not be found by its type — "who calls BufSource::read" had no answer — and it collided with the trait's own declaration, which could even invent a call-graph edge out of an impl body that contains no call at all. Impls on a reference (impl Trait for &Foo) and on a module-qualified type (impl Trait for m::Foo) are attributed to their type too. Re-index after upgrading. Thanks @Dshuishui. (#1588) (Rust)

  • A method call on a struct field — self.inner.run() with inner: Inner — now resolves to the method on the field's declared type. Previously the call was reduced to the bare method name and matched whichever same-named method was nearest, which was often the calling method itself, recording recursion that isn't in the source (a few hundred such self-edges in ripgrep alone), or a method of an unrelated type. References and Box/Rc/Arc fields are looked through, as Rust's own method calls are; a field whose type is external (a std or third-party type), a generic parameter, or a container like Option/Vec is left unresolved rather than guessed. Re-index after upgrading. Thanks @Dshuishui. (#1585) (Rust)

  • Erlang functions that share a name but differ in arity are now separate symbols with the language's own module:fun/arity identity, so the everyday f/1 delegating to f/2 shows as a real call edge instead of a self-loop, each arity keeps its own -spec and source span, -export([f/1]) marks exactly that arity as public, and asking codegraph_explore for a symbol the way Erlang spells it — cowboy_req:header/3 — returns that definition. Re-index Erlang projects after upgrading. Thanks @Dshuishui. (#1610) (Erlang)

  • Erlang behaviour dispatch no longer miscounts a call site's arity when an argument is a binary literal like <<1,2,3>> — the commas inside were counted as argument separators, which silently dropped (or could mislink) the dispatch edge to the behaviour callback. (#1358) (Erlang)

  • A C++ .h header whose only C++ construct is a plain derived type — struct Derived : Base with no export macro, class keyword, or access section — is now recognized as C++ (previously only the export-macro form was). Such a header was read as C, so the derived struct vanished from the index and a phantom function named after the base type appeared in its place. The check now also covers the whole file rather than its first few kilobytes, so a long C-compatible preamble no longer hides the signal. Re-index after upgrading to pick up affected headers. Thanks @Jaysenpeng. (#1592)

  • C, C++, Objective-C and Rust unions are now indexed as first-class union nodes. A union declaration previously produced no symbol at all, so it never appeared in search or codegraph_explore, and anything attached to it disappeared with it — in Rust, every impl SomeTrait for MyUnion lost its edge, the methods from that impl were left pointing at a type the graph did not contain, and asking which types implement a trait quietly skipped the union ones. A union-shaped dispatch table in C now resolves its function pointers like a struct-shaped one. A typedef union { … } Name; in C keeps the typedef's name and is no longer mistaken for a plain type alias. Thanks @ctype-lab. Re-index after upgrading to pick up unions in existing projects. (#1515)

  • Python classes used as values — return SomeSerializer from a factory method, handler = SomeClass aliases, registry dicts and lists, and classes passed as arguments — now produce reference edges in the graph. Previously these idioms were invisible, so on Django and Django REST Framework projects, asking for a serializer's callers or the impact of editing it missed the views that actually use it. Re-index after upgrading to pick up the new edges. (#1478)

  • SAP HANA .xsjs / .xsjslib imports now resolve across files: an extensionless import { x } from './helpers' in a .xsjs file finds helpers.xsjslib, so the cross-file call edge is created and codegraph_callers / codegraph_impact see it. Previously the import path resolved to nothing and the call fell back to same-name matching, which could bind the edge to an unrelated file that happened to export the same symbol. Complements the .xsjs / .xsjslib extraction support. Thanks @maxmilian. (#556)
