#gráfico de código v1.1.2

[1.1.2] - 28/06/2026

Novos recursos

  • Agora você pode excluir diretórios confirmados do índice com uma lista exclude em codegraph.json — mesmo quando eles são rastreados pelo git. .gitignore não pode eliminar um diretório que o git já rastreia, portanto, um tema vendido ou SDK que foi verificado em seu repositório (um tema Metronic comprometido em static/, uma biblioteca de fornecedor agrupada) não tinha maneira suportada de ser mantido de fora - apenas inchou o gráfico e desacelerou a indexação. Adicione uma raiz codegraph.json com, por exemplo, { "exclude": ["static/", "**/vendor/**"] } e esses caminhos serão ignorados na indexação, sincronização e observação de arquivos, em projetos git e não git. Os padrões são do estilo gitignore e correspondem aos caminhos relativos à raiz do repositório. Isso complementa o includeIgnored existente (seu oposto - opte por in para repositórios incorporados gitignorados). (#999)
  • CodeGraph agora segue comandos C/C++ que são despachados por meio de tabelas de ponteiros de função construídas em macro, para que as funções de manipulador que eles alcançam não sejam mais becos sem saída no gráfico. Muitos projetos C registram um manipulador no campo de ponteiro de função de uma estrutura por meio de uma macro e uma tabela gerada - redis é o caso clássico: cada comando (getCommand, decrbyCommand,…) é conectado ao campo proc da estrutura de comando por uma tabela MAKE_CMD(…) que reside em um arquivo #include-d gerado e então invocado como c->cmd->proc(c). CodeGraph agora lê essas tabelas construídas por macro - incluindo aquelas cujo tipo de estrutura é um alias de macro, cuja tabela fica em um arquivo #include-d que nunca é indexado por conta própria ou que são agrupados em compilação condicional (#ifdef) e definidos em linha com a estrutura. Ele reconhece campos de ponteiro de função declarados por meio de uma função typedef e segue o receptor - um acesso encadeado (c->cmd->proc) ou um subscrito de array por meio de uma tabela de escopo de arquivo ((cmdnames[i].cmd_func)(…)) - entre tipos de campo. Ele também segue o despacho por meio de uma matriz simples de ponteiros de função sem nenhum wrapper de estrutura - o padrão opcode/tabela de manipulador comum em interpretadores e emuladores, onde uma tabela como opcodes[op](…) invoca uma das muitas funções de manipulador registradas por índice - vinculando o despachante a cada manipulador na matriz. O resultado: solicitar os chamadores ou o raio de explosão de um manipulador de comando agora encontra o despachante que o alcança. Para redis, call aparece como chamador de cada comando; para SQLite, as funções SQL integradas registradas por meio de FUNCTION(...) vinculam-se ao local onde são invocadas; para Vim, todos os links de comando :ex e de modo normal do despachante. (#991, estendendo #932)
  • O CodeGraph não expira mais quando muitos agentes o consultam ao mesmo tempo. O servidor de segundo plano compartilhado que atende todas as sessões do editor e do agente usado para executar todas as consultas em um único thread, portanto, uma explosão de solicitações simultâneas - por exemplo, um enxame de subagentes explorando um grande monorepo juntos - enfileiradas umas atrás das outras e, enquanto as pesadas eram executadas, congelavam a conexão, de modo que as respostas concluídas não podiam nem ser enviadas de volta até que todo o lote fosse drenado. Passamos por um punhado de chamadores simultâneos que apareciam rotineiramente quando o tempo limite da solicitação do MCP expirava. O servidor compartilhado agora responde a consultas em um conjunto de threads de trabalho, de forma que as solicitações simultâneas sejam executadas em paralelo e a conexão permaneça responsiva o tempo todo; quando está genuinamente saturada, uma chamada retorna uma breve nota "ocupado, tente novamente em breve" (não é um erro) em vez de ultrapassar o tempo limite do client. O pool se ajusta à sua máquina — aproximadamente um trabalhador por núcleo, deixando um para coordenação — e uma única sessão do editor não é afetada (sem pool, sem sobrecarga). Configure CODEGRAPH_QUERY_POOL_SIZE para escolher um número específico de trabalhadores ou 0 para reverter para consultas em processo de thread único.
  • A indexação agora analisa arquivos em vários núcleos de CPU em vez de um, portanto, construir o gráfico de um projeto — codegraph index, o primeiro índice de um projeto e a reindexação em segundo plano após alterações — é mais rápido em máquinas com vários núcleos, mais notavelmente em bases de código grandes ou com muita análise. O gráfico produzido é idêntico ao anterior e a reindexação permanece determinística: a análise é executada em paralelo, mas os resultados ainda são confirmados em uma ordem fixa, portanto, o mesmo projeto sempre produz o mesmo gráfico. CodeGraph dimensiona o pool para sua máquina automaticamente (deixando um núcleo livre para todo o resto); defina CODEGRAPH_PARSE_WORKERS para escolher um número específico de trabalhadores de análise ou CODEGRAPH_PARSE_WORKERS=1 para restaurar o comportamento anterior de núcleo único. O pico de memória permanece inalterado — os trabalhadores recuperam a memória do analisador de forma independente, para que ela não cresça com o número de núcleos. (#1015, #320)
  • Quando o servidor MCP do CodeGraph é executado sem nenhum projeto padrão próprio - iniciado fora de qualquer repositório (por exemplo, atrás de um gateway MCP) ou em uma raiz monorepo cujos índices residem em subprojetos - ele agora marca projectPath como um argumento obrigatório em cada chamada de ferramenta. Antes, projectPath era sempre opcional, então um agente conversando com tal servidor muitas vezes o omitia, recebia orientação para passá-lo e não tentava novamente de forma confiável - você tinha que empurrá-lo manualmente todas as vezes. Agora o requisito faz parte da definição da ferramenta que o agente vê, portanto ele fornece o caminho para o projeto no qual está trabalhando pela primeira vez. Quando o servidor tem um projeto padrão - o caso normal, lançado dentro do seu repositório - projectPath permanece opcional e uma chamada sem ele retorna para esse projeto exatamente como antes. Obrigado @wauxhall pelo relatório. (#993)
  • As ferramentas MCP do CodeGraph agora funcionam no modo Ask do Cursor (e qualquer outro client que permite apenas ferramentas somente leitura). Cada ferramenta CodeGraph apenas lê seu código indexado - ela nunca altera seu espaço de trabalho - mas não anuncia isso, então o modo Ask do Cursor bloqueou todas as chamadas com "você está no modo ask e não pode executar ferramentas não somente leitura" e você teve que mudar para o modo Agente para usar o CodeGraph. CodeGraph agora declara todas as suas ferramentas somente leitura usando as anotações de ferramenta MCP padrão, então Cursor (e clients semelhantes) permitem-nas em contextos somente leitura. Nada muda sobre como as ferramentas se comportam. Obrigado @CDsouza315 pelo relatório. (#1018)

Correções

  • Um codegraph index ou codegraph init que fica órfão ou preso agora para sozinho em vez de fixar um núcleo da CPU para sempre. Se você interrompeu o comando (ou o terminal/agente que o iniciou), o processo indexador subjacente continuaria em execução em segundo plano - o pai não poderia transmitir o sinal - e um índice genuinamente travado também não teria nada observando, já que os watchdogs de auto-recuperação foram conectados apenas ao servidor MCP em segundo plano. Ambas as lacunas foram fechadas: a indexação agora termina automaticamente quando seu pai desaparece, e um thread principal que para de progredir é eliminado para que não possa travar indefinidamente. Desative com CODEGRAPH_NO_WATCHDOG=1 (vivacidade) ou CODEGRAPH_PPID_POLL_MS=0 (detecção de órfãos), correspondendo ao servidor. (#999)
  • A indexação não trava mais em "Resolvendo referências" em um repositório que envia um tema JavaScript/TypeScript grande ou SDK. Um tema de administração fornecido (Metronic é o caso clássico - aproximadamente 1.300 arquivos .js confirmados) declara novamente os mesmos nomes de método (init, update, render, destroy,…) em centenas de widgets e resolução usada para pontuar cada definição com o mesmo nome contra cada chamada - trabalho que cresce com o quadrado de quantas vezes um nome se repete. Nesse repositório, ele fixou um núcleo de CPU por 15 a 30 minutos e efetivamente nunca terminou. A resolução agora permite adivinhar quando um nome é definido mais vezes do que qualquer base de código real jamais o repete (o corte é generoso - projetos normais ficam muito abaixo dele e não são completamente afetados), já que nenhuma heurística de proximidade pode escolher o único alvo verdadeiro entre milhares de qualquer maneira. A indexação anteriormente bloqueada agora é concluída em segundos e a resolução precisa (importações, nomes qualificados, correspondências de nomes de classe) permanece inalterada. Esta é a mesma classe de desaceleração que a correção do nome de importação 1.1.0, agora fechada para nomes de métodos/símbolos repetidos. Ajuste o corte com CODEGRAPH_AMBIGUOUS_NAME_CEILING se precisar. Obrigado @DANOX2 pelo relatório detalhado e reprodução. (#999)
  • O gancho de prompt de carregamento frontal do Claude Code agora é acionado para prompts que não sejam em inglês. O gancho opcional que injeta o contexto do CodeGraph para questões estruturais reconhecia apenas palavras-chave em inglês, portanto, uma questão estrutural escrita em chinês - ou qualquer linguagem de escrita não latina - injetava nada silenciosamente: o gancho parecia não estar conectado, apesar de uma configuração correta, sem nenhum erro para explicar o porquê. O portão agora reconhece o idioma. Ele reconhece palavras-chave estruturais chinesas (如何/流程/调用/依赖/实现/架构…) e - em qualquer idioma - um prompt que nomeia um símbolo de código real do seu projeto, como getUserId, article_publish, user.login ou parseToken() (o nome é verificado no índice, portanto, uma palavra comum que apenas se parece com código não aciona). Os prompts não estruturais ("corrigir este erro de digitação", em qualquer idioma) permanecem autônomos como antes, portanto, nada é acionado onde não há resposta estrutural a ser dada. Obrigado @whinc pelo relatório detalhado e reprodução. (#994)
  • O servidor de sincronização automática em segundo plano agora é iniciado para projetos mantidos em uma unidade externa ExFAT ou FAT (e algumas montagens de rede). Esses sistemas de arquivos não suportam as operações nas quais o servidor depende para coordenar e escutar localmente, então ele falhou imediatamente e registrou novamente o mesmo erro a cada nova tentativa - a indexação em segundo plano foi quebrada, então você teve que executar codegraph sync manualmente após as alterações. (As ferramentas MCP, o gancho de prompt e o manual codegraph index/sync não foram afetados, pois nenhum deles precisa do servidor.) O servidor agora contorna essas limitações automaticamente - voltando para um método de coordenação diferente e realocando seu soquete local para o diretório temporário do sistema - para que a indexação em segundo plano funcione lá exatamente como em qualquer outro lugar, sem necessidade de configuração. Verificado de ponta a ponta em sistemas de arquivos de unidades removíveis reais no macOS, Linux e Windows. Obrigado @zengwenliang416 pelo relatório detalhado. (#997)
  • Se você usar CodeGraph como uma biblioteca, o auxiliar QueryBuilder.deleteResolvedReferences() não lança mais "muitas variáveis SQL" quando recebe uma lista muito grande de ids - ele emite uma consulta ilimitada, portanto, uma lista maior que o limite de parâmetro do SQLite aborta a chamada. Agora ele divide o trabalho em lotes como qualquer outra consulta em massa no API. A própria indexação e resolução de referência do CodeGraph nunca chamou esse método (eles usam um caminho diferente, já em lote), portanto, o servidor CLI e MCP não foram afetados. Obrigado @inth3shadows pela análise estática. (#1001)
  • As propriedades computadas do Swift agora são indexadas, para que você possa procurá-las. Uma propriedade computada - um var isCloudProxy: Bool { … } lido em toda uma base de código, um var body: some View { … } de visualização SwiftUI, um requisito var title: String { get } de protocolo - não produziu nenhum símbolo, então codegraph query e codegraph_explore responderam "Nenhum resultado encontrado" para ele, e um agente que trusts um resultado vazio concluiria erroneamente que a propriedade não existe. Propriedades computadas (e requisitos de propriedades de protocolo) agora são símbolos gráficos que você pode encontrar e explorar como qualquer outra coisa. O getter de uma propriedade computada também é lido como seu corpo, portanto, o body de uma visualização SwiftUI se vincula às subvisualizações e auxiliares que ela cria - tornando o fluxo de renderização de uma visualização rastreável por meio da propriedade. As propriedades armazenadas já estavam indexadas; isso fecha a lacuna de propriedades computadas. Obrigado @ monochrome3694 pelo relatório e reprodução precisos. (#1020)

codegraph v1.1.2

[1.1.2] - 2026-06-28

New Features

  • You can now exclude committed directories from the index with an exclude list in codegraph.json — even when they're git-tracked. .gitignore can't drop a directory git already tracks, so a vendored theme or SDK that's checked into your repo (a committed Metronic theme under static/, a bundled vendor library) had no supported way to be kept out — it just bloated the graph and slowed indexing. Add a root codegraph.json with, e.g., { "exclude": ["static/", "**/vendor/**"] } and those paths are skipped on indexing, sync, and file-watching, on both git and non-git projects. Patterns are gitignore-style and matched against repo-root-relative paths. This complements the existing includeIgnored (its opposite — opt in to gitignored embedded repos). (#999)
  • CodeGraph now follows C/C++ commands that are dispatched through macro-built function-pointer tables, so the handler functions they reach are no longer dead-ends in the graph. Many C projects register a handler into a struct's function-pointer field through a macro and a generated table — redis is the classic case: every command (getCommand, decrbyCommand, …) is wired into the command struct's proc field by a MAKE_CMD(…) table that lives in a generated, #include-d file, then invoked as c->cmd->proc(c). CodeGraph now reads those macro-built tables — including ones whose struct type is itself a macro alias, whose table sits in an #include-d file that is never indexed on its own, or that are wrapped in conditional compilation (#ifdef) and defined inline with the struct. It recognizes function-pointer fields declared through a function typedef, and follows the receiver — a chained access (c->cmd->proc) or an array subscript through a file-scope table ((cmdnames[i].cmd_func)(…)) — across field types. It also follows dispatch through a bare array of function pointers with no struct wrapper at all — the opcode/handler-table pattern common in interpreters and emulators, where a table like opcodes[op](…) invokes one of many registered handler functions by index — linking the dispatcher to every handler in the array. The upshot: asking for the callers or blast radius of a command handler now finds the dispatcher that reaches it. For redis, call shows up as a caller of every command; for SQLite, the builtin SQL functions registered through FUNCTION(...) link to where they're invoked; for Vim, every :ex and normal-mode command links from the dispatcher. (#991, extending #932)
  • CodeGraph no longer times out when many agents query it at once. The shared background server that serves all your editor and agent sessions used to run every query on a single thread, so a burst of concurrent requests — for example a swarm of subagents exploring a large monorepo together — queued up behind one another and, while the heavy ones ran, froze the connection so finished answers couldn't even be sent back until the whole batch drained. Past a handful of simultaneous callers that routinely surfaced as MCP request timeouts. The shared server now answers queries across a pool of worker threads, so concurrent requests run in parallel and the connection stays responsive the whole time; when it's genuinely saturated a call returns a brief "busy, retry shortly" note (not an error) instead of hanging past your client's timeout. The pool sizes itself to your machine — roughly one worker per core, leaving one for coordination — and a single editor session is unaffected (no pool, no overhead). Set CODEGRAPH_QUERY_POOL_SIZE to choose a specific number of workers, or 0 to revert to single-threaded in-process queries.
  • Indexing now parses files across multiple CPU cores instead of one, so building a project's graph — codegraph index, the first index of a project, and the background re-index after changes — is faster on multi-core machines, most noticeably on large or parse-heavy codebases. The graph it produces is identical to before and re-indexing stays deterministic: parsing runs in parallel, but results are still committed in a fixed order, so the same project always yields the same graph. CodeGraph sizes the pool to your machine automatically (leaving a core free for everything else); set CODEGRAPH_PARSE_WORKERS to choose a specific number of parse workers, or CODEGRAPH_PARSE_WORKERS=1 to restore the previous single-core behavior. Peak memory is unchanged — workers reclaim parser memory independently, so it doesn't grow with the number of cores. (#1015, #320)
  • When CodeGraph's MCP server runs with no default project of its own — started outside any repository (for example behind an MCP gateway), or at a monorepo root whose indexes live in sub-projects — it now marks projectPath as a required argument on every tool call. Before, projectPath was always optional, so an agent talking to such a server would often omit it, get back guidance to pass it, and not reliably retry — you had to nudge it by hand every time. Now the requirement is part of the tool definition the agent sees, so it supplies the path to the project it's working on the first time. When the server does have a default project — the normal case, launched inside your repo — projectPath stays optional and a call without it falls back to that project exactly as before. Thanks @wauxhall for the report. (#993)
  • CodeGraph's MCP tools now work in Cursor's Ask mode (and any other client that only permits read-only tools). Every CodeGraph tool just reads your indexed code — it never changes your workspace — but it didn't advertise that, so Cursor's Ask mode blocked every call with "you are in ask mode and cannot run non read-only tools," and you had to switch to Agent mode to use CodeGraph at all. CodeGraph now declares all its tools read-only using the standard MCP tool annotations, so Cursor (and similar clients) allow them in read-only contexts. Nothing about how the tools behave changes. Thanks @CDsouza315 for the report. (#1018)

Fixes

  • A codegraph index or codegraph init that gets orphaned or wedged now stops itself instead of pinning a CPU core forever. If you killed the command (or the terminal/agent that launched it), the underlying indexer process used to keep running in the background — the parent couldn't pass the signal along — and a genuinely stuck index had nothing watching it either, since the self-recovery watchdogs were wired only into the background MCP server. Both gaps are closed: indexing now self-terminates when its parent goes away, and a main thread that stops making progress is killed so it can't hang indefinitely. Opt out with CODEGRAPH_NO_WATCHDOG=1 (liveness) or CODEGRAPH_PPID_POLL_MS=0 (orphan detection), matching the server. (#999)
  • Indexing no longer hangs at "Resolving refs" on a repo that commits a large JavaScript/TypeScript theme or SDK. A vendored admin theme (Metronic is the classic case — ~1,300 committed .js files) re-declares the same method names (init, update, render, destroy, …) on hundreds of widgets, and resolution used to score every same-named definition against every call — work that grows with the square of how many times a name repeats. On such a repo it pinned a CPU core for 15–30 minutes and effectively never finished. Resolution now declines to guess when a name is defined more times than any real codebase ever repeats one (the cutoff is generous — normal projects top out far below it and are completely unaffected), since no proximity heuristic can pick the one true target among thousands anyway. Indexing that previously wedged now completes in seconds, and precise resolution (imports, qualified names, class-name matches) is unchanged. This is the same class of slowdown as the 1.1.0 import-name fix, now closed for repeated method/symbol names. Tune the cutoff with CODEGRAPH_AMBIGUOUS_NAME_CEILING if you ever need to. Thanks @DANOX2 for the detailed report and repro. (#999)
  • Claude Code's front-load prompt hook now fires for non-English prompts. The optional hook that injects CodeGraph context for structural questions only recognized English keywords, so a structural question written in Chinese — or any non-Latin-script language — silently injected nothing: the hook looked like it wasn't wired up despite a correct setup, with no error to explain why. The gate is now language-aware. It recognizes Chinese structural keywords (如何/流程/调用/依赖/实现/架构…), and — in any language — a prompt that names a real code symbol from your project, such as getUserId, article_publish, user.login, or parseToken() (the name is checked against the index, so an ordinary word that merely looks like code doesn't trigger it). Non-structural prompts ("fix this typo", in any language) stay a no-op as before, so nothing fires where there's no structural answer to give. Thanks @whinc for the detailed report and repro. (#994)
  • The background auto-sync server now starts for projects kept on an ExFAT or FAT external drive (and some network mounts). Those filesystems don't support the operations the server relies on to coordinate and to listen locally, so it failed immediately and re-logged the same error on every retry — background indexing was broken, so you had to run codegraph sync by hand after changes. (The MCP tools, the prompt hook, and manual codegraph index/sync were unaffected, since none of them need the server.) The server now works around those limitations automatically — falling back to a different coordination method and relocating its local socket to your system temp directory — so background indexing works there exactly like anywhere else, with no configuration needed. Verified end-to-end on real removable-drive filesystems on macOS, Linux, and Windows. Thanks @zengwenliang416 for the detailed report. (#997)
  • If you use CodeGraph as a library, the QueryBuilder.deleteResolvedReferences() helper no longer throws "too many SQL variables" when handed a very large list of ids — it issued one unbounded query, so a list longer than SQLite's parameter limit aborted the call. It now splits the work into batches like every other bulk query in the API. CodeGraph's own indexing and reference resolution never called this method (they use a different, already-batched path), so the CLI and MCP server were unaffected. Thanks @inth3shadows for the static analysis. (#1001)
  • Swift computed properties are now indexed, so you can search for them. A computed property — a var isCloudProxy: Bool { … } read all over a codebase, a SwiftUI view's var body: some View { … }, a protocol's var title: String { get } requirement — produced no symbol at all, so codegraph query and codegraph_explore answered "No results found" for it, and an agent that trusts an empty result would wrongly conclude the property doesn't exist. Computed properties (and protocol property requirements) are now graph symbols you can find and explore like anything else. A computed property's getter is also read as its body, so a SwiftUI view's body links to the subviews and helpers it builds — making a view's render flow traceable through the property. Stored properties were already indexed; this closes the computed-property gap. Thanks @monochrome3694 for the precise report and repro. (#1020)
