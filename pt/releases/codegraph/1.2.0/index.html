#gráfico de código v1.2.0

[1.2.0] - 02/07/2026

Novos recursos

  • Chamadas de método feitas através de uma variável local agora resolvem o método em muitos outros idiomas. Quando o código faz const logger = new Logger(); logger.log(); (ou equivalente), o CodeGraph infere o tipo da variável local a partir de sua declaração ou inicializador e vincula a chamada ao método correto - portanto, essas chamadas agora aparecem em chamadores, impacto/raio de explosão e rastreamentos de fluxo codegraph_explore em vez de serem descartados. Anteriormente, apenas C++ lidava com isso; agora também abrange TypeScript, JavaScript, Python, Java, C#, Kotlin, Swift, Go, Rust, Dart, Scala e PHP. (#1108)
  • Chamadas de método Ruby feitas em um receptor (logger.log) agora registram uma vantagem no método. Anteriormente, o indexador Ruby mantinha apenas o receptor e descartava o nome do método, portanto, um método chamado por meio de uma variável ou objeto não tinha chamadores registrados e estava faltando no raio de impacto/explosão e nos rastreamentos de fluxo; combinado com a inferência de tipo de variável local acima, logger = Logger.new; logger.log agora é vinculado a Logger#log. Chamadas para um método de classe (Foo.bar) e construção de objeto (Foo.new) também são registradas. (#1110)
  • A mesma resolução de chamada de método de variável local agora se estende a Lua, Luau, R e Pascal/Delphi. Um método invocado através de um local — Lua/Luau local lg = Logger.new(); lg:log(), R lg <- Logger$new(); lg$log() ou Pascal var lg: TLogger; ... lg.Log — agora é vinculado ao método correto em vez de ser descartado. (#1112)

Correções

  • A indexação de um projeto grande não é mais interrompida no meio com uma mensagem "Thread principal sem resposta — encerrando o processo travado". O cão de guarda de segurança que interrompe um índice genuinamente travado estava confundindo o trabalho lento, mas normal, com um travamento: em um grande repositório, vincular referências e relacionamentos entre arquivos pode ser executado legitimamente por um tempo, e esse trabalho agora cede regularmente para que o cão de guarda possa distinguir o progresso real de uma verdadeira parada. Projetos que anteriormente não conseguiram concluir codegraph init / codegraph index (e tiveram que voltar para CODEGRAPH_NO_WATCHDOG=1) agora são concluídos normalmente, enquanto um processo genuinamente travado ainda é detectado. Obrigado @zmcrazy, @YoungLiao e @GeeLab-Mob pelos relatórios. (#1091)
  • No Windows, uma janela do console não pisca mais brevemente quando o CodeGraph é executado como um servidor MCP em segundo plano. Quando o iniciador do npm iniciou o tempo de execução do pacote - o que acontece toda vez que um editor inicia o servidor ou se reconecta após o daemon ficar inativo - e durante sua etapa de autocura que extrai um pacote de plataforma ausente, o Windows abriria uma janela preta do console (conhost) por um momento. Ambos agora iniciam ocultos, combinando com o comportamento do daemon; a etapa de abertura do navegador do codegraph login foi reforçada da mesma maneira. Obrigado @luoyerr pelo relatório e análise da causa raiz. (#1092)
  • As declarações futuras de C++ não impedem mais a definição de classe real. Uma declaração direta class Foo; — comum em grandes bases de código C++ e Unreal Engine, onde uma classe muito usada é declarada adiante em dezenas de cabeçalhos — era indexada como seu próprio nó de classe sempre que aparecia. Portanto, explorar essa classe retornou principalmente sites de declaração direta e poderia até escolher um deles como representante do raio de explosão, enterrando a definição real e seus membros e chamadores. As declarações diretas sem corpo agora são ignoradas para C e C++, exatamente como as estruturas e enums declaradas adiante já o eram, portanto, apenas a definição real é indexada. Idiomas onde uma classe sem corpo é uma definição completa — como class Empty e Scala de Kotlin — não são afetadas. Obrigado @luoyxy pelo relatório e análise da causa raiz. (#1093)
  • Os métodos C++ que retornam uma referência e os operadores de conversão definidos pelo usuário agora são indexados com seus nomes corretos. Um getter embutido como const FGameplayTagContainer& GetActiveTags() const - em todos os cabeçalhos do Unreal Engine - foi indexado como & GetActiveTags() const em vez de GetActiveTags, e um operador de conversão como operator EALSMovementState() const manteve seu () const final em vez de ler operator EALSMovementState. Em ambos os casos, o nome ilegível significava que você não conseguia encontrar o símbolo pelo nome e seus chamadores não estavam vinculados. Ambos agora são lidos de forma limpa, combinando como os métodos de retorno de ponteiro e retorno de valor já funcionavam. (#1096)
  • Funções C++ escritas com uma macro de especificador embutido antes do tipo de retorno agora são indexadas corretamente. No Unreal Engine, os auxiliares embutidos são comumente escritos FORCEINLINE FString GetEnumerationToString(...); a macro FORCEINLINE fez o analisador ler o tipo de retorno como parte do nome da função (FString GetEnumerationToString em vez de GetEnumerationToString) e perder o tipo de retorno real, então a função não pôde ser encontrada pelo nome e seus chamadores não foram vinculados. CodeGraph agora reconhece as macros in-line padrão do Unreal (FORCEINLINE, FORCENOINLINE, FORCEINLINE_DEBUGGABLE), portanto, tanto o nome quanto o tipo de retorno são capturados. (#1100)
  • A mesma recuperação de nome de função agora cobre macros embutidas de bibliotecas C++ comuns de terceiros, não apenas do Unreal Engine - incluindo pugixml (PUGI__FN, PUGIXML_FUNCTION), Godot (_FORCE_INLINE_), Boost (BOOST_FORCEINLINE) e ALWAYS_INLINE/FORCE_INLINE genérico. As funções decoradas com estes agora são indexadas com seus nomes reais. Em um grande projeto Unreal que vende essas bibliotecas, isso eliminou a grande maioria da distorção restante do nome da função. (#1101)
  • Os nomes das funções C++ agora são recuperados mesmo quando decorados com uma macro que o CodeGraph não conhece especificamente. Uma função escrita SOME_LIBRARY_MACRO ReturnType doWork(...) anteriormente tinha a macro ou tipo de retorno absorvido em seu nome sempre que a macro não era reconhecida pelo CodeGraph; agora o nome real (doWork) é recuperado independentemente da macro, portanto pode ser encontrado e vinculado ao chamador - não é necessária configuração por biblioteca. A lista de macros reconhecidas também foi ampliada (Qt, Folly, Abseil, LLVM, V8, Eigen, rapidjson) para que capturem adicionalmente o tipo de retorno. Isso apenas limpa um nome já distorcido e é limitado a C e C++, portanto, nomes comuns — e linguagens como Kotlin e Scala, onde os identificadores podem conter espaços legitimamente — não são afetados. (#1102)
  • O conjunto de bibliotecas C++ cujas macros são reconhecidas para recuperação completa do tipo de retorno foi expandido muito além do Unreal Engine - agora abrangendo Mozilla, Protobuf, {fmt}, nlohmann/json, GLM, Bullet, Skia, OpenCV, EASTL, Cocos2d-x, GLib, SQLite e as convenções de chamada comuns do Windows (portanto, HRESULT WINAPI CreateThing(...) indexa como CreateThing retornando HRESULT). Funções de bibliotecas que não estão na lista ainda têm seus nomes recuperados automaticamente; sendo listado recupera adicionalmente o tipo de retorno. (#1103)
  • Os resultados de travessia de gráfico e raio de explosão não descartam mais ou contam incorretamente relacionamentos em alguns casos extremos. Quando um símbolo pudesse ser alcançado por mais de um caminho, uma consulta de impacto/raio de explosão poderia deixar de fora uma dependência direta entre dois símbolos que já estavam vinculados de outra maneira; separadamente, a travessia de gráfico de nível inferior usada pela biblioteca API poderia manter apenas um dos vários relacionamentos entre o mesmo par de símbolos (por exemplo, um símbolo que chama e faz referência a outro), contar um chamador alcançado por meio de dois locais de chamada diferentes duas vezes ou retornar um pouco mais resultados do que o limite de tamanho solicitado em um símbolo altamente conectado. Eles eram de longa data e principalmente mascarados pela desduplicação posterior, portanto, os resultados das consultas diárias não foram afetados, mas a travessia agora retorna o conjunto completo e corretamente delimitado. Obrigado @inth3shadows pelos relatórios precisos e rastreados individualmente. (#1086, #1087, #1088, #1089, #1090)
  • Chamadas de método para classes com o mesmo nome em arquivos diferentes agora são resolvidas com a definição correta. Se dois arquivos declarassem, digamos, uma classe Logger com seu próprio método log(), uma chamada poderia ser vinculada a qualquer definição que fosse indexada primeiro - portanto, uma chamada em um arquivo apontava erroneamente para a classe em outro, confundindo os chamadores e o raio de explosão desse método. Isso afetou chamadas escritas como obj.log(), Logger.log() e Logger::log() em muitas linguagens, incluindo C++, Python, TypeScript, Java, C# e Rust. Quando o nome de um método é ambíguo, o CodeGraph agora prefere a definição no próprio arquivo de chamada - o destino correto no caso comum - enquanto as chamadas Java/Kotlin que um import já está fixado em outro arquivo não são afetadas. Obrigado @ inth3shadows pela reprodução mínima e análise de causa raiz. (#1079)

codegraph v1.2.0

[1.2.0] - 2026-07-02

New Features

  • Method calls made through a local variable now resolve to the method in many more languages. When code does const logger = new Logger(); logger.log(); (or the equivalent), CodeGraph infers the local variable's type from its declaration or initializer and links the call to the right method — so these calls now show up in callers, impact/blast-radius, and codegraph_explore flow traces instead of being dropped. Previously only C++ handled this; it now also covers TypeScript, JavaScript, Python, Java, C#, Kotlin, Swift, Go, Rust, Dart, Scala, and PHP. (#1108)
  • Ruby method calls made on a receiver (logger.log) now record an edge to the method. Previously the Ruby indexer kept only the receiver and discarded the method name, so a method called through a variable or object had no recorded callers and was missing from impact/blast-radius and flow traces; combined with the local-variable type inference above, logger = Logger.new; logger.log now links to Logger#log. Calls to a class method (Foo.bar) and object construction (Foo.new) are still recorded too. (#1110)
  • The same local-variable method-call resolution now extends to Lua, Luau, R, and Pascal/Delphi. A method invoked through a local — Lua/Luau local lg = Logger.new(); lg:log(), R lg <- Logger$new(); lg$log(), or Pascal var lg: TLogger; ... lg.Log — now links to the right method instead of being dropped. (#1112)

Fixes

  • Indexing a large project no longer gets killed partway through with a "Main thread unresponsive — killing the wedged process" message. The safety watchdog that stops a genuinely stuck index was mistaking slow-but-normal work for a hang: on a big repo, linking up references and cross-file relationships can legitimately run for a while, and that work now regularly yields so the watchdog can tell real progress from a true stall. Projects that previously failed to finish codegraph init / codegraph index (and had to fall back to CODEGRAPH_NO_WATCHDOG=1) now complete normally, while a genuinely hung process is still caught. Thanks @zmcrazy, @YoungLiao, and @GeeLab-Mob for the reports. (#1091)
  • On Windows, a console window no longer briefly flashes when CodeGraph runs as a background MCP server. When the npm launcher started the bundled runtime — which happens every time an editor starts the server or reconnects after the daemon idles out — and during its self-heal step that extracts a missing platform bundle, Windows would pop up a black console (conhost) window for a moment. Both now launch hidden, matching how the daemon already behaved; the browser-open step of codegraph login was hardened the same way. Thanks @luoyerr for the report and root-cause analysis. (#1092)
  • C++ forward declarations no longer crowd out the real class definition. A class Foo; forward declaration — common in large C++ and Unreal Engine codebases, where a heavily used class is forward-declared across dozens of headers — was indexed as its own class node every time it appeared. So exploring that class returned mostly forward-declaration sites, and could even pick one of them as the representative for blast-radius, burying the actual definition and its members and callers. Bodiless forward declarations are now skipped for C and C++, exactly as forward-declared structs and enums already were, so only the real definition is indexed. Languages where a class with no body is a complete definition — such as Kotlin's class Empty and Scala — are unaffected. Thanks @luoyxy for the report and root-cause analysis. (#1093)
  • C++ methods that return a reference, and user-defined conversion operators, are now indexed under their correct names. An inline getter like const FGameplayTagContainer& GetActiveTags() const — everywhere in Unreal Engine headers — was indexed as & GetActiveTags() const instead of GetActiveTags, and a conversion operator like operator EALSMovementState() const kept its trailing () const instead of reading operator EALSMovementState. In both cases the garbled name meant you couldn't find the symbol by name and its callers weren't linked. Both now read cleanly, matching how pointer-returning and value-returning methods already worked. (#1096)
  • C++ functions written with an inline-specifier macro before the return type are now indexed correctly. In Unreal Engine, inline helpers are commonly written FORCEINLINE FString GetEnumerationToString(...); the FORCEINLINE macro made the parser read the return type as part of the function's name (FString GetEnumerationToString instead of GetEnumerationToString) and lose the real return type, so the function couldn't be found by name and its callers weren't linked. CodeGraph now recognizes the standard Unreal inline macros (FORCEINLINE, FORCENOINLINE, FORCEINLINE_DEBUGGABLE), so both the name and the return type are captured. (#1100)
  • The same function-name recovery now covers inline macros from common third-party C++ libraries, not just Unreal Engine — including pugixml (PUGI__FN, PUGIXML_FUNCTION), Godot (_FORCE_INLINE_), Boost (BOOST_FORCEINLINE), and generic ALWAYS_INLINE / FORCE_INLINE. Functions decorated with these are now indexed under their real names. On a large Unreal project vendoring these libraries this cleaned up the large majority of remaining function-name garbling. (#1101)
  • C++ function names are now recovered even when decorated with a macro CodeGraph doesn't specifically know about. A function written SOME_LIBRARY_MACRO ReturnType doWork(...) previously had the macro or return type absorbed into its name whenever the macro wasn't one CodeGraph recognized; now the real name (doWork) is recovered regardless of the macro, so it's findable and its callers link — no per-library configuration needed. The recognized-macro list was also broadened (Qt, Folly, Abseil, LLVM, V8, Eigen, rapidjson) so those additionally capture the return type. This only ever cleans up an already-garbled name and is limited to C and C++, so ordinary names — and languages like Kotlin and Scala where identifiers can legitimately contain spaces — are unaffected. (#1102)
  • The set of C++ libraries whose macros are recognized for full return-type recovery was expanded well beyond Unreal Engine — now spanning Mozilla, Protobuf, {fmt}, nlohmann/json, GLM, Bullet, Skia, OpenCV, EASTL, Cocos2d-x, GLib, SQLite, and the common Windows calling conventions (so HRESULT WINAPI CreateThing(...) indexes as CreateThing returning HRESULT). Functions from libraries not on the list still get their name recovered automatically; being listed additionally recovers the return type. (#1103)
  • Graph traversal and blast-radius results no longer drop or miscount relationships in a handful of edge cases. When a symbol could be reached by more than one path, an impact/blast-radius query could leave out a direct dependency between two symbols that were already linked another way; separately, the lower-level graph traversal used by the library API could keep only one of several relationships between the same pair of symbols (for example a symbol that both calls and references another), count a caller reached through two different call sites twice, or return slightly more results than the requested size limit on a very highly-connected symbol. These were long-standing and mostly masked by later de-duplication, so day-to-day query results were largely unaffected, but the traversal now returns the complete, correctly-bounded set. Thanks @inth3shadows for the precise, individually-traced reports. (#1086, #1087, #1088, #1089, #1090)
  • Method calls to same-named classes in different files now resolve to the right definition. If two files each declared, say, a Logger class with its own log() method, a call could be linked to whichever definition happened to be indexed first — so a call in one file wrongly pointed at the class in another, mixing up that method's callers and blast radius. This affected calls written as obj.log(), Logger.log(), and Logger::log() across many languages, including C++, Python, TypeScript, Java, C#, and Rust. When a method name is ambiguous, CodeGraph now prefers the definition in the calling file itself — the correct target in the common case — while Java/Kotlin calls that an import already pins to another file are unaffected. Thanks @inth3shadows for the minimal repro and root-cause analysis. (#1079)
