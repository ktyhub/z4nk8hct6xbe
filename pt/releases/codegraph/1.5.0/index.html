#gráfico de código v1.5.0

[1.5.0] - 21/07/2026

⚡ Lançamento do motor Rust – com sincronização quase instantânea

Esta versão reconstrói o mecanismo de análise do CodeGraph como um kernel Rust nativo, revisa o pipeline de resolução em torno dele e torna o gráfico ao vivo efetivamente instantâneo: um salvamento agora chega ao gráfico em menos de um segundo, mesmo em um repositório de 27.000 arquivos. É a maior atualização de desempenho na história do projeto — e cada gráfico é verificado byte por byte de forma idêntica ao mecanismo anterior.

  • Análise Rust nativa para 20 idiomas — TypeScript, JavaScript (+TSX/JSX), Java, Python, Go, C, C++, Rust, C#, Ruby, PHP, Swift, Kotlin, Scala, Dart, R, Lua e Luau agora analisam em um kernel Rust compilado (Metal e CUDA Ride o caminho C++). Plataformas sem um binário pré-construído e arquivos individuais com erros de sintaxe retornam automaticamente ao mecanismo anterior - mesmo gráfico de qualquer maneira, comprovado em repositórios de pequenas bibliotecas para o kernel Linux.
  • Adaptável à sua máquina — CodeGraph dimensiona seus trabalhadores de análise, conjunto de resolvedores e caches com base no que o sistema realmente possui: contagens reais de núcleos (com reconhecimento de contêiner/cgroup, não do host), memória disponível honesta no macOS e Linux e custo de resolução medido por projeto. Uma grande estação de trabalho obtém o pipeline paralelo completo; um VPS de 2 núcleos recebe um pipeline ajustado para terminar de forma confiável em vez de ficar sem memória – o kernel do Linux (arquivos de 70 mil) indexa até a conclusão em uma máquina de 6 GB de 2 núcleos em menos de 12 minutos – abaixo dos 26 no início deste ciclo.
  • A resolução é dramaticamente mais rápida em todos os aspectos — resolução paralela adaptável, pesquisa mais inteligente de métodos candidatos e caminhada de supertipo/conformidade memorizada. O repositório do compilador Swift (arquivos 27k, Swift + C++) passou de mais de 3 minutos para cerca de 100 segundos neste ciclo de lançamento; Todos os projetos Rust, Lua e da família Java apresentam melhorias de dois dígitos.
  • A sincronização agora é quase instantânea — um salvamento chega ao gráfico em menos de um segundo, mesmo na escala do compilador. O observador sempre ativo é acionado após uma janela silenciosa de 300 ms para salvamentos solitários (rajadas de edições ainda se unem) e entrega os caminhos exatos alterados para sincronizar em vez de verificar novamente a árvore inteira - trabalho medido de salvar para gráfico fresco de ~0,3s em um projeto Java de 4.400 arquivos e ~0,4s no repositório do compilador Swift de 27.000 arquivos, byte idêntico a uma reconciliação completa. Detalhes completos nas entradas abaixo.

Novos recursos

  • A indexação de projetos TypeScript, TSX, JavaScript, JSX, Java, Python, Go, C, C++, Rust, C#, Ruby, PHP, Swift, Kotlin, Scala, Dart, R, Lua e Luau é mais rápida: a análise e a extração de símbolos agora são executadas em um mecanismo nativo quando um binário pré-construído está disponível para sua plataforma (os pacotes de lançamento incluem um), produzindo exatamente o mesmo gráfico - verificado byte por byte em relação ao mecanismo anterior em repositórios reais, de pequenas bibliotecas até vscode-, dubbo-, django-, git-, protobuf-, tokio-, rust-analyzer-, jellyfin-, rails-, symfony-, swift-nio-, kotlinx.coroutines-, ggplot2-, Kong-, Scala-3-compiler- e Flutter-scale bases de código (membros gerados pelo Lombok, tabelas de ponteiros de função C e cabeçalhos pesados ​​de macro no estilo Unreal-Engine incluídos; fontes CUDA e Metal seguem o caminho C++). A aceleração é maior em máquinas com recursos limitados, como executores de CI. Nenhuma configuração necessária: plataformas sem o binário nativo e arquivos individuais com erros de sintaxe usam automaticamente o mecanismo anterior e CODEGRAPH_KERNEL=0 desativa totalmente o caminho nativo.
  • A resolução de referência funciona agora em paralelo em grandes projetos. Quando um projeto tem referências pendentes suficientes para valer a pena (aproximadamente 150k+, típico para grandes bases de código Java/Kotlin/Spring), a resolução se espalha pelos threads de trabalho enquanto os resultados são aplicados na ordem exata que o caminho de thread único teria usado - o gráfico sai byte por byte idêntico, cerca de duas vezes mais rápido de ponta a ponta em um projeto Java de 4.000 arquivos em nossos testes. Projetos pequenos mantêm o caminho de thread único automaticamente (a distribuição custa mais do que economiza). Defina CODEGRAPH_NO_PARALLEL_RESOLVE=1 para desabilitar ou CODEGRAPH_PARALLEL_RESOLVE_MIN=<count> para sintonizar quando for acionado.
  • A indexação de grandes projetos obteve outra aceleração considerável – cerca de um quarto a menos de tempo de espera no mesmo projeto Java de 4.000 arquivos, com o gráfico ainda idêntico, byte por byte. Duas mudanças: o banco de dados não intercala mais a manutenção cara do ponto de verificação no meio da resolução em um novo índice (em vez disso, ele é dobrado uma vez no final) e, enquanto os resultados de um lote estão sendo gravados, os threads de trabalho já estão resolvendo o próximo lote em vez de ficarem ociosos.
  • A análise de despacho dinâmico que é executada no final da indexação (retorno de chamada, evento e fiação de estrutura) agora executa suas passagens em paralelo em grandes projetos, cortando esse estágio aproximadamente pela metade - e uma passagem que trava agora tenta novamente com segurança em vez de falhar em todo o índice, o que também aumenta a probabilidade de bases de código muito grandes que morreram anteriormente neste estágio serem indexadas até a conclusão. Os gráficos permanecem idênticos byte por byte.
  • Em projetos grandes, a indexação grava seus dados de relacionamento visivelmente mais rápido: os índices do banco de dados secundário são deixados de lado durante a maior parte da resolução de referência e reconstruídos uma vez no final, em vez de serem mantidos linha por linha. Os gráficos permanecem idênticos byte por byte e pequenos projetos não são afetados.
  • Confiabilidade de base de código muito grande: em projetos de vários milhões de símbolos, uma passagem de análise que falha em um thread de trabalho agora é ignorada com uma mensagem clara, em vez de ser repetida de uma forma que poderia derrubar todo o índice, e a reconstrução do índice de fim de indexação não corre mais o risco de tropeçar no cão de guarda de atividade em gráficos enormes. Validado de ponta a ponta no kernel Linux (70 mil arquivos, 2 milhões de símbolos, 6,4 milhões de relacionamentos) — agora ele indexa até a conclusão, mesmo em uma máquina de 2 núcleos.
  • A indexação é significativamente mais rápida - um codegraph init novo em um projeto TypeScript médio leva cerca de um terço a menos do tempo de parede, com o mesmo gráfico produzido byte por byte. Os ganhos vêm do processamento em lote do banco de dados, do armazenamento de arquivos em um thread de gravador dedicado, da memorização de pesquisas repetidas de resolução de importação, da pular a manutenção do índice de pesquisa por linha durante a construção em massa (reconstruída uma vez no final) e - apenas em bancos de dados completamente novos - adiando a durabilidade do disco até que o índice seja concluído, uma vez que um primeiro índice interrompido é simplesmente executado novamente. Defina CODEGRAPH_NO_FAST_INIT=1 para manter durabilidade total contra falhas durante a construção inicial ou CODEGRAPH_NO_STORE_WORKER=1 para armazenar no thread principal.

  • Cada lançamento agora é verificável criptograficamente: pacotes npm são publicados com origem npm (o emblema "Provenance" em npmjs.com, provando que cada versão foi construída pelo fluxo de trabalho de lançamento deste repositório a partir de um commit específico), e os pacotes de lançamento GitHub carregam atestados de construção assinados que você pode verificar com gh attestation verify <file> -R colbymchenry/codegraph.
  • A indexação dentro de contêineres limitados por CPU ou memória (Docker, executores de CI) agora dimensiona seus pools de trabalhadores a partir da permissão real do contêiner em vez da da máquina host, e bases de código gigantes não aumentam mais arquivos de banco de dados temporários durante a indexação (anteriormente dezenas de GB de disco transitório em projetos em escala de kernel Linux). Juntos, eles evitam falhas de falta de memória e de disco em máquinas restritas; configure CODEGRAPH_RESOLVE_WORKERS para substituir explicitamente a contagem de trabalhadores de resolução.
  • A indexação de projetos muito grandes em máquinas multi-core ficou mais rápida novamente: os trabalhadores de resolução paralela agora atualizam periodicamente suas conexões de banco de dados somente leitura, o que permite que a manutenção do banco de dados avance em vez de criar silenciosamente um backlog atrás de leitores de longa duração — um backlog que estava sobrecarregando as próprias gravações do indexador. Os gráficos permanecem idênticos byte por byte; a vitória é maior na escala do kernel Linux em máquinas com muitos núcleos.
  • A indexação no macOS agora usa o espaço de memória real da máquina ao dimensionar seus trabalhadores de resolução paralela. O macOS mantém deliberadamente a RAM preenchida com cache recuperável, de modo que a leitura de memória livre anterior voltou minúscula (~ 1 GB em uma máquina ociosa) e reduziu silenciosamente pela metade o pool de trabalhadores - o novo índice de um projeto Java médio foi executado cerca de 15 a 20% mais lento do que o hardware permitia. Os gráficos permanecem idênticos byte por byte; a mesma correção também permite que um cache de análise baseado em memória seja totalmente ativado no macOS para grandes bases de código C.
  • A nova indexação obteve uma aceleração geral considerável: durante a construção inicial, os índices de pesquisa secundários do banco de dados são deixados de lado e reconstruídos uma vez após a análise, em vez de serem mantidos linha por linha - o mesmo truque comprovado que a fase de vinculação posterior já usou, agora aplicado a toda a pista de análise - e o loop de resolução de referência da mesma forma para de manter índices de pesquisa que nunca lê, reconstruindo-os no final, quando quase nada resta na tabela. A fase de análise de um projeto Java médio é executada cerca de 58% mais rápido e seu índice completo cerca de 19% mais rápido de ponta a ponta; um índice em escala de kernel Linux que levava cerca de 15 minutos em uma máquina de 8 núcleos agora é concluído em cerca de 11, com a fase de resolução sozinha caindo em um terço. Os gráficos permanecem idênticos byte a byte e as sincronizações incrementais não são afetadas.
  • Salvar um arquivo agora atualiza o gráfico quase imediatamente: o inspetor de arquivo é acionado após uma janela silenciosa de 300 ms para um ou dois arquivos alterados (rajadas ainda se aglutinam sob o debounce completo e CODEGRAPH_WATCH_DEBOUNCE_MS permanece o limite superior) e as sincronizações acionadas pelo inspetor reconciliam exatamente os caminhos alterados em vez de percorrer todo o repositório. Exclusões de diretórios e tempestades de eventos ainda executam o scan-diff completo, portanto, nada que os eventos não possam descrever será perdido. Medido: o trabalho de sincronização do gráfico salvar em fresco cai para ~0,3s em um projeto de 4.400 arquivos e ~0,4s em um projeto de 27.000 arquivos, com gráficos resultantes byte por byte idênticos a uma reconciliação completa.
  • A indexação do Swift e outras bases de código com muitos protocolos/interfaces ficou dramaticamente mais rápida: a caminhada de conformidade que verifica se um método reside nos supertipos de um receptor (protocolos, classes base, extensões) agora lembra suas respostas durante cada lote de resolução, em vez de consultar novamente o gráfico para cada site de chamada - no repositório do compilador Swift (27 mil arquivos) que a caminhada foi executada quase um milhão de vezes por índice. Um novo índice desse repositório cai de cerca de 185 segundos para menos de 100, com o gráfico byte por byte idêntico. A pesquisa de candidato de método também ganhou um índice de proprietário por nome, portanto, nomes com sobrecarga pesada (init em Swift, execute em Java) não pagam mais uma varredura completa de candidato por tipo de receptor.
  • Resolver chamadas de método por meio de variáveis ​​locais (recv.method(), recv:method() de Lua, recv$method() de R) ficou muito mais barato em repositórios onde o mesmo receptor é chamado repetidamente: a varredura de declaração que digita o receptor agora lembra o que já foi varrido por escopo em vez de reler as mesmas linhas de origem para cada site de chamada, e os padrões regex com os quais ele varre são compilados uma vez por receptor em vez de por chamada. O novo índice de Kong cai outros 8% além da correção de exigência de resolução (23% cumulativo), com gráficos byte por byte idênticos em todos os lugares - incluindo projetos Java, onde essa mesma varredura digita com sucesso dezenas de milhares de receptores.
  • A indexação de projetos Lua e Luau obteve uma aceleração considerável: a resolução de cada require(...) não verifica mais a lista inteira de arquivos do projeto quatro vezes - um índice de nome de arquivo por projeto responde à mesma pesquisa instantaneamente, reduzindo a resolução por necessidade de cerca de um milissegundo para microssegundos. Um novo índice de Kong (1.870 arquivos Lua) é executado cerca de 16% mais rápido de ponta a ponta, com o gráfico byte por byte idêntico. A mesma limpeza também fecha uma borda de obsolescência latente, onde as pesquisas de copybook COBOL poderiam continuar servindo uma lista de arquivos em cache após a alteração dos arquivos.
  • A resolução de referência paralela agora é acionada de forma adaptativa, em vez de um limite fixo de tamanho de projeto: o indexador mede a taxa real de resolução por referência no primeiro lote e aumenta o pool de trabalhadores no meio da execução sempre que o trabalho restante o justificar. Idiomas cujas referências são caras para resolver se beneficiam mais - especialmente Rust: um novo índice de tokio roda cerca de 23% mais rápido, com o gráfico byte por byte idêntico. Projetos pequenos e máquinas de baixo núcleo (executores de CI de 2 núcleos) mantêm o caminho de thread único exatamente como antes.
  • A análise de despacho dinâmico no final da indexação agora ignora passagens que provavelmente não podem produzir nada para o projeto em questão: React re-renderiza ponte quando nenhuma classe tem um método render, emparelhamento de plataforma cruzada React Native e Expo quando os idiomas necessários não estão presentes e link de mapeador MyBatis quando não há XML de mapeador. Anteriormente, cada um deles escaneou todo o gráfico antes de ficar vazio - em um projeto Java de 4.000 arquivos que representava cerca de 0.9 segundos de análise desperdiçada por novo índice. O passe de ponte de implementação de interface também ficou mais barato no trabalho real: ele não busca mais a lista de métodos de uma interface de hub uma vez por implementador, e as classes que estendem ou implementam nada são ignoradas antes de qualquer pesquisa por classe. Os gráficos permanecem idênticos byte por byte.
  • A indexação de grandes bases de código C e C++ gasta muito menos tempo na análise de despacho do ponteiro de função (a passagem que conecta tabelas de manipuladores como uma tabela de comando ou uma estrutura de operações aos seus sites de chamada): cada arquivo de origem agora é lido e preparado uma vez em vez de quatro vezes, os arquivos que não podem contribuir com nenhuma fiação de despacho são ignorados imediatamente nas etapas de vinculação posteriores e, em plataformas com o mecanismo nativo, a verificação por arquivo agora também é executada nativamente. Em uma árvore em escala de kernel Linux, a passagem é executada cerca de um terço mais rápido de ponta a ponta, com gráficos idênticos byte por byte; plataformas sem binário nativo mantêm os mesmos resultados do caminho anterior.

Correções

  • Os arquivos TypeScript, TSX e JavaScript agora são analisados com gramáticas atualizadas — sintaxe moderna, como declarações using e atributos de importação, não gera mais erros de análise que poderiam descartar símbolos adjacentes. (As gramáticas agrupadas anteriormente datavam de 2023.)
  • Os arquivos Rust também são analisados com uma gramática atualizada agora (a compilação anteriormente empacotada datada de 2023), que adicionalmente aprimora a atribuição de chamada de método: chamadas por meio de campos struct são resolvidas com o contexto do receptor em vez de voltar à correspondência ambígua de nome simples, removendo uma classe de arestas de chamada erradas em nomes comuns como len e start.
  • Os arquivos Ruby também são analisados ​​com uma gramática atualizada agora (a compilação anteriormente empacotada datada do início de 2024), que corrige uma análise incorreta de chamadas de método de operador de navegação segura (recv&.!= x) que registraram o nome errado do receptor.
  • Os arquivos PHP também são analisados ​​com uma gramática atualizada agora (a versão anteriormente empacotada datava de 2023): arquivos que usam recursos PHP modernos - constantes enum, ganchos de propriedade PHP 8.4, encadeamento new X()->method() sem parênteses - não atingem mais erros de análise ou análises incorretas que descartaram ou distorceram seus símbolos, portanto, bases de código como Symfony e Laravel indexam substancialmente com mais precisão.
  • Os arquivos Swift também são analisados ​​​​com uma gramática atualizada agora (a compilação anteriormente empacotada datada de 2023): teste rápido #expect, macros estilo #Preview, o modificador de acesso package e throws digitado não produzem mais erros de análise que descartaram símbolos circundantes - projetos Swift do lado do servidor, como Vapor, apresentam a maior recuperação.
  • A gramática do Dart agora é empacotada com o próprio CodeGraph em vez de ser resolvida a partir de um pacote de terceiros cuja construção do Dart flutuou em uma referência upstream não fixada - uma atualização de dependência de rotina não pode mais alterar silenciosamente a forma como os arquivos Dart são analisados.
  • Pesquisar ou explorar por nomes de campos agora encontra o código que os define. Uma consulta feita de chaves de objeto ou nomes de campo API (profileInfo isTrialEligible quotaInfo billingMethod) usada para retornar resultados não relacionados enquanto os arquivos de definição nunca apareceram, porque três etapas de recuperação eliminaram termos camelCase de várias palavras: um bug interno de comparação de casos, uma etapa de correspondência que considerou apenas classes (nunca funções ou métodos) e propagação de exploração que exigia correspondências exatas de nomes de símbolos. Todos os três são fixos – codegraph_explore com um conjunto de nomes de campos agora mostra os controladores e serviços que montam esses campos. (#1196)
  • O includeIgnored do codegraph.json funciona novamente para o layout de "pasta de repositórios": quando uma regra .gitignore cobre um diretório pai (/repos/) contendo vários repositórios git incorporados, optando pelos repositórios individuais ("includeIgnored": ["repos/a/"] - a grafia exata que a própria dica do codegraph init sugere) anteriormente não correspondia a nada e indexava zero arquivos, repetindo a mesma sugestão de volta para você. Ambas as grafias agora funcionam – nomeie o diretório pai para ativar tudo nele ou nomeie repositórios individuais para ativar apenas aqueles – e a dica não sugere mais repositórios que já estão configurados. (#1295)
  • Chamadas de método em literais (", ".join(...) em Python, "x".split(...) em JavaScript e similares) não produzem mais bordas de chamada para funções de projeto não relacionadas que compartilham o nome do integrado - uma base de código com uma função chamada join, get ou update pode mostrar chamadores fantasmas de cada uso integrado de string. Além disso, uma função aninhada dentro de outra função agora só é correspondida como um destino de chamada de dentro de seu contêiner, já que não pode ser acessada de nenhum outro lugar. Os resultados do raio de explosão e dos testes afetados ficam mais limpos especialmente nas bases de código Python e JavaScript. (#1230)
  • As chamadas de método Go através de um campo struct (target.conn.Exec(...)) não se vinculam mais a métodos locais não relacionados de mesmo nome quando o tipo do campo é externo - as chamadas conn *sql.DB estavam sendo atribuídas a uma interface local que declarava Exec, fabricando dependências internas. As chamadas de campo encadeadas agora são resolvidas inferindo o tipo declarado do campo a partir da definição da estrutura: tipos no projeto (incluindo aqueles não exportados como tree *node do chi) obtêm bordas de chamada corretas e validadas que nunca existiram antes, e tipos externos (biblioteca padrão, módulos de terceiros) são deixados desvinculados em vez de adivinhados. (#1276)
  • As chamadas de método TypeScript/JavaScript por meio de um singleton importado (import { store } from './store'; store.notify()) agora são resolvidas para o método de classe em vez da constante exportada, então codegraph callers vê chamadores de arquivos cruzados do método - anteriormente apenas chamadas do mesmo arquivo eram atribuídas e um método usado em qualquer lugar poderia parecer não utilizado. A mesma inferência de tipo baseada em declaração se aplica às linguagens que a compartilham (Python, Java, Kotlin, Go e mais), e uma inferência com falha mantém a vantagem antiga em vez de adivinhar. (#1292)
  • codegraph node <symbol> -f <file> agora imprime o corpo de origem do símbolo. Fixar um nome ambíguo em um arquivo específico (o objetivo principal do -f quando muitos arquivos definem a mesma função) retornou apenas o local e a trilha do chamador sem código. (#1284)
  • A exclusão de um diretório inteiro agora é realizada pelo modo de observação: os arquivos dentro dele são removidos do índice na próxima sincronização automática, em vez de permanecerem como registros obsoletos até que uma edição não relacionada acione um. Os sistemas operacionais geralmente relatam uma exclusão de diretório como um evento único no próprio diretório (sem eventos por arquivo para seu conteúdo), que o inspetor descartou anteriormente. (#1285)
  • codegraph sync agora obtém a mesma correção de disco lento que tornou a indexação completa rápida no 1.4.0: o checkpoint do banco de dados é adiado para toda a execução incremental em vez de disparar a cada poucos megabytes de gravações. Em unidades mecânicas e outros tipos de armazenamento de alta latência, uma pequena sincronização em um índice grande não fica mais parada por minutos com CPU próxima de zero — o custo de uma sincronização aumenta com o que mudou, não com o tamanho do índice existente. O mesmo interruptor CODEGRAPH_NO_WAL_DEFER=1 desliga. (#1248)
  • Funções C declaradas com uma macro de atributo específica do projeto na frente de um tipo de retorno digitado (SEC_ATTR UINT32 MyFunc(VOID) — comum em código incorporado e de kernel) agora são indexadas sob seus nomes reais. Anteriormente, o analisador tropeçava na macro desconhecida e armazenava a lista de parâmetros como o nome da função, deixando entradas como "(VOID)" no gráfico e tornando a função real impossível de ser encontrada. (#1211)
  • Índices de código C e C++ pesados ​​em macros são muito mais completos. Quinze idiomas onipresentes que anteriormente acionavam o analisador na recuperação de erros - eliminando símbolos, distorcendo nomes, cunhando entradas fantasmas ou perdendo os relacionamentos entre os reais - agora analisam de forma limpa: a proteção de compatibilidade #ifdef __cplusplus / extern "C" { em cabeçalhos C, macros iteradoras em posição de instrução (list_for_each_entry(pos, head, member) { … } e toda a família Linux-kernel/git/jemalloc - incluindo chamadas que quebram linhas, como hlist_for_each_entry_rcu(…) com um argumento lockdep_is_held), as anotações de declaração esparsa/Linux (static int __init foo(void), void __user *buf, container_of(p, struct T, m)), anotações parametrizadas (__free(kfree), __printf(4, 0), __counted_by(count)), macros de declaração por CPU e fila de trabalho (static DEFINE_PER_CPU(struct T, name);, formulários inicializados incluídos), argumentos de tipo simples para macros de alocador e lista (kzalloc_obj(struct T), list_entry(p, struct T, member)), va_arg com um tipo qualificado ou de ponteiro, definições de macro variáveis ​​nomeadas GNU (#define dbg(fmt, args...)), marcadores de compilador estilo static notrace, declarações C23 auto, anotações de parâmetros finais (int argc UNUSED, estilo doméstico do git), macros de gerenciamento de namespace sozinhas em uma linha (FMT_BEGIN_NAMESPACE, Q_OBJECT do Qt) e macros de atributos de função na frente dos tipos de retorno C++. No kernel Linux, isso reduz quase pela metade os arquivos perdidos para analisar erros nos diretórios principais e recupera milhares de relacionamentos de chamada e referência que a recuperação de erros descartou silenciosamente, com git e redis vendo cortes menores do mesmo tipo; os gráficos permanecem idênticos byte por byte entre os mecanismos nativos e substitutos. Uma correção relacionada impede que o próprio manuseio da macro corrompa as linhas #define que mencionam os mesmos nomes de macro, o que removeu uma classe de erros de análise fantasma em cabeçalhos de estilo fmt.
  • Métodos C++ definidos fora de linha dentro de um namespace (namespace sim { Output MyClass::Apply(...) { ... } }) agora carregam o namespace em seu nome qualificado, correspondendo à sua classe. Sites de chamada totalmente qualificados de outros arquivos (sim::MyClass::Apply(...)) resolvem a definição novamente, portanto, codegraph callers e o impacto do arquivo não ficam mais vazios para esse padrão. (#1291)
  • Os métodos C++ definidos fora de linha em uma classe de modelo (template <typename T> T Box<T>::get() { ... }) não mantêm mais a lista de parâmetros do modelo em seu nome qualificado. Eles agora indexam como Box::get - idêntico a uma definição embutida do mesmo método - então eles se vinculam à sua classe e resolvem a partir de sites de chamada novamente, e listas patológicas de parâmetros de modelos multilinhas não podem mais estourar o nome qualificado além dos limites de nome do sistema de arquivos. (#1286)
  • A detecção de rotas Go não identifica mais chamadas de métodos comuns que compartilham nomes de verbos HTTP — cache.Put("key", value), store.Get("config", out), bus.Handle("user.created", handler) e similares estavam sendo indexados como rotas HTTP, poluindo listagens de rotas em bases de código com muito cache. Um registro agora deve se parecer com um: seu primeiro argumento deve ser um caminho prefixado / (todos os roteadores) ou um padrão Go 1.22 "METHOD /path" em Handle/HandleFunc, que agora também extrai o método em vez de listar a rota como ANY. (#1259)
  • A saída de progresso no Windows não mistura mais os trilhos ASCII | com o quadro Unicode │ ◆ ● ao redor deles. Em terminais que renderizam Unicode (Windows Terminal, VS Code, ConEmu/Cmder, JetBrains, Alacritty), todo o bloco codegraph init / index / sync agora desenha com caracteres de desenho de caixa correspondentes; consoles legados não reconhecidos mantêm a saída totalmente ASCII segura que evita caracteres ilegíveis. CODEGRAPH_ASCII=1/CODEGRAPH_UNICODE=1 ainda substituem em qualquer direção. (#398)
  • A saída CLI agora respeita a convenção NO_COLOR e os novos sinalizadores --color / --no-color, e fica clara automaticamente quando canalizada: comandos como codegraph status, query, callers e files não incorporam mais códigos de cores ANSI quando stdout não é um terminal e um canal codegraph init / index / sync imprime linhas simples por fase em vez de caracteres de controle de animação de progresso. FORCE_COLOR ou --color força a reativação da cor nos tubos que a renderizam. (#1281)
  • Os chamadores e a análise de impacto não subestimam mais silenciosamente uma função que chama o mesmo receptor muitas vezes. Quando um chamador continha vários sites de chamada para o mesmo receptor e um limite de lote de resolução interno os dividiu, a limpeza após o primeiro lote removeu as linhas pendentes dos sites posteriores antes mesmo de serem tentadas - suas bordas nunca foram criadas, deterministicamente, e quais bordas faltaram foram alteradas com alterações não relacionadas na contagem total de referências do projeto. A limpeza pós-passagem agora tem como alvo a linha exata do banco de dados de onde veio cada referência processada. Encontrado durante a validação da correção de chamada do operador em nlohmann/json, onde as 11 chamadas de write_cbor para to_char_type indexadas como 10. (#1269)
  • Chamadas de operador explícitas em C++ — a.operator+(b), p->operator+(b), a.operator[](3) e outras formas simbólicas — agora produzem uma borda calls para o método do operador, de modo que um operador invocado apenas por meio da sintaxe explícita não pareça mais desnecessário em chamadores e na análise de impacto. tree-sitter analisa esses sites de chamada com o nome do operador preso em um nó de erro (nunca como um acesso de membro normal), de modo que o alvo da chamada foi lido silenciosamente apenas como a variável do receptor; o nome do operador agora é recuperado do nó de erro e resolvido por meio de inferência do tipo receptor como qualquer outra chamada de membro - um operador com o mesmo nome em uma classe não relacionada nunca pode capturar a borda. Os usos do Infix (a + b, a[i]) precisam de inferência de tipo real e são rastreados separadamente. (#1247)
  • codegraph init e codegraph index não parecem mais travados depois que "Resolvendo referências" atinge 100%. O link de despacho dinâmico que é executado após a resolução (retornos de chamada, re-renderizações do React, ponteiros de função C e o resto) não tinha exibição de progresso, portanto, em repositórios onde demora um pouco - especialmente grandes bases de código C - a barra simplesmente ficou congelada em 100% até terminar. Esse trabalho agora mostra como sua própria fase de progresso "Vinculando despacho dinâmico", e a passagem mais pesada - vinculação de ponteiro de função C - também relata o progresso dentro da passagem, de modo que uma grande base de código C avança a barra suavemente em vez de estacioná-la em um número durante a maior parte da fase.
  • A indexação não imprime mais avisos repetidos "SQLite é um recurso experimental" que distorcem a exibição do progresso. O aviso vem do SQLite integrado do Node e é disparado uma vez por trabalhador de análise; agora está suprimido em todos os caminhos de lançamento.

codegraph v1.5.0

[1.5.0] - 2026-07-21

⚡ The Rust engine release — with near-instant sync

This release rebuilds CodeGraph's parsing engine as a native Rust kernel, overhauls the resolution pipeline around it, and makes the live graph effectively instant: a save now reaches the graph in well under a second, even on a 27,000-file repository. It is the largest performance upgrade in the project's history — and every graph is verified byte-for-byte identical to the previous engine.

  • Native Rust parsing for 20 languages — TypeScript, JavaScript (+TSX/JSX), Java, Python, Go, C, C++, Rust, C#, Ruby, PHP, Swift, Kotlin, Scala, Dart, R, Lua, and Luau now parse in a compiled Rust kernel (Metal and CUDA ride the C++ path). Platforms without a prebuilt binary, and individual files with syntax errors, fall back to the previous engine automatically — same graph either way, proven on repositories from small libraries to the Linux kernel.
  • Adaptive to your machine — CodeGraph sizes its parse workers, resolver pool, and caches from what the system actually has: real core counts (container/cgroup-aware, not the host's), honest available memory on macOS and Linux, and measured per-project resolution cost. A big workstation gets the full parallel pipeline; a 2-core VPS gets a pipeline tuned to finish reliably instead of running out of memory — the Linux kernel (70k files) indexes to completion on a 2-core, 6GB machine in under 12 minutes — down from 26 at the start of this cycle.
  • Resolution is dramatically faster across the board — adaptive parallel resolution, smarter method-candidate lookup, and memoized supertype/conformance walking. The Swift compiler repository (27k files, Swift + C++) went from over 3 minutes to about 100 seconds within this release cycle; Rust, Lua, and Java-family projects all see double-digit improvements.
  • Sync is now near-instant — a save reaches the graph in well under a second, even at compiler scale. The always-on watcher fires after a 300ms quiet window for lone saves (bursts of edits still coalesce), and hands the exact changed paths to sync instead of re-scanning the whole tree — measured save-to-fresh-graph work of ~0.3s on a 4,400-file Java project and ~0.4s on the 27,000-file Swift compiler repository, byte-identical to a full reconciliation.

Full details in the entries below.

New Features

  • Indexing TypeScript, TSX, JavaScript, JSX, Java, Python, Go, C, C++, Rust, C#, Ruby, PHP, Swift, Kotlin, Scala, Dart, R, Lua, and Luau projects is faster: parsing and symbol extraction now run in a native engine when a prebuilt binary is available for your platform (release bundles include one), producing exactly the same graph — verified byte-for-byte against the previous engine on real repositories, from small libraries up to vscode-, dubbo-, django-, git-, protobuf-, tokio-, rust-analyzer-, jellyfin-, rails-, symfony-, swift-nio-, kotlinx.coroutines-, ggplot2-, Kong-, Scala-3-compiler-, and Flutter-scale codebases (Lombok-generated members, C function-pointer tables, and Unreal-Engine-style macro-heavy headers included; CUDA and Metal sources ride the C++ path). The speedup is largest on resource-constrained machines like CI runners. No setup needed: platforms without the native binary, and individual files with syntax errors, automatically use the previous engine, and CODEGRAPH_KERNEL=0 turns the native path off entirely.
  • Reference resolution now runs in parallel on large projects. When a project has enough pending references to make it worthwhile (roughly 150k+, typical for big Java/Kotlin/Spring codebases), resolution fans out across worker threads while results are applied in the exact order the single-threaded path would have used — the graph comes out byte-for-byte identical, about twice as fast end-to-end on a 4,000-file Java project in our testing. Small projects keep the single-threaded path automatically (the fan-out costs more than it saves there). Set CODEGRAPH_NO_PARALLEL_RESOLVE=1 to disable, or CODEGRAPH_PARALLEL_RESOLVE_MIN=<count> to tune when it engages.
  • Indexing large projects got another sizeable speedup — about a quarter less wall-clock on the same 4,000-file Java project, with the graph still byte-for-byte identical. Two changes: the database no longer interleaves expensive checkpoint housekeeping into the middle of resolution on a fresh index (it's folded once at the end instead), and while one batch's results are being written out, the worker threads are already resolving the next batch instead of sitting idle.
  • The dynamic-dispatch analysis that runs at the end of indexing (callback, event, and framework wiring) now runs its passes in parallel on large projects, cutting that stage roughly in half there — and a pass that crashes now retries safely instead of failing the whole index, which also makes very large codebases that previously died in this stage more likely to index to completion. Graphs remain byte-for-byte identical.
  • On large projects, indexing writes its relationship data noticeably faster: secondary database indexes are set aside during the bulk of reference resolution and rebuilt once at the end, instead of being maintained row by row. Graphs remain byte-for-byte identical, and small projects are unaffected.
  • Very-large-codebase reliability: on multi-million-symbol projects, an analysis pass that fails on a worker thread is now skipped with a clear message instead of being retried in a way that could take down the whole index, and the end-of-indexing index rebuild no longer risks tripping the liveness watchdog on huge graphs. Validated end-to-end on the Linux kernel (70k files, 2M symbols, 6.4M relationships) — it now indexes to completion even on a 2-core machine.
  • Indexing is significantly faster — a fresh codegraph init on a medium TypeScript project takes about a third less wall-clock time, with the same graph produced byte-for-byte. The gains come from batching database writes, storing files on a dedicated writer thread, memoizing repeated import-resolution lookups, skipping per-row search-index maintenance during the bulk build (rebuilt once at the end), and — on completely fresh databases only — deferring disk durability until the index completes, since an interrupted first index is simply re-run. Set CODEGRAPH_NO_FAST_INIT=1 to keep full crash-durability during the initial build, or CODEGRAPH_NO_STORE_WORKER=1 to store on the main thread.
  • codegraph install and codegraph upgrade now offer CodeGraph Pro beta access after finishing — answer yes, type your email, and you join the same waitlist as the getcodegraph.com homepage form. Strictly opt-in and asked at most once per machine total: nothing is sent unless you say yes and enter an email, either answer is remembered so no later install or upgrade ever re-asks, and non-interactive runs (--yes, scripts, CI) never see the question.
  • Every release is now cryptographically verifiable: npm packages publish with npm provenance (the "Provenance" badge on npmjs.com, proving each version was built by this repository's release workflow from a specific commit), and the GitHub Release bundles carry signed build attestations you can check with gh attestation verify <file> -R colbymchenry/codegraph.
  • Indexing inside CPU- or memory-limited containers (Docker, CI runners) now sizes its worker pools from the container's actual allowance instead of the host machine's, and giant codebases no longer balloon temporary database files during indexing (previously tens of GB of transient disk on Linux-kernel-scale projects). Together these prevent out-of-memory and out-of-disk failures on constrained machines; set CODEGRAPH_RESOLVE_WORKERS to override the resolution worker count explicitly.
  • Indexing very large projects on multi-core machines got faster again: the parallel-resolution workers now periodically refresh their read-only database connections, which lets database housekeeping advance instead of silently building up a backlog behind long-lived readers — a backlog that was taxing the indexer's own writes. Graphs remain byte-for-byte identical; the win is largest at Linux-kernel scale on many-core machines.
  • Indexing on macOS now uses the machine's real memory headroom when sizing its parallel-resolution workers. macOS deliberately keeps RAM filled with reclaimable cache, so the previous free-memory reading came back tiny (~1GB on an otherwise idle machine) and silently halved the worker pool — a medium Java project's fresh index ran about 15–20% slower than the hardware allowed. Graphs remain byte-for-byte identical; the same fix also lets a memory-driven analysis cache engage fully on macOS for large C codebases.
  • Fresh indexing got a sizeable across-the-board speedup: during the initial build, the database's secondary lookup indexes are set aside and rebuilt once after parsing instead of being maintained row by row — the same proven trick the later linking phase already used, now applied to the whole parse lane — and the reference-resolution loop likewise stops maintaining lookup indexes it never reads, rebuilding them at the end when almost nothing is left in the table. A medium Java project's parse phase runs about 58% faster and its full fresh index about 19% faster end-to-end; a Linux-kernel-scale index that took ~15 minutes on an 8-core machine now completes in about 11, with the resolution phase alone dropping by a third. Graphs remain byte-for-byte identical, and incremental syncs are unaffected.
  • Saving a file now updates the graph almost immediately: the file watcher fires after a 300ms quiet window for one or two changed files (bursts still coalesce under the full debounce, and CODEGRAPH_WATCH_DEBOUNCE_MS remains the upper bound), and watcher-triggered syncs reconcile exactly the changed paths instead of stat-walking the entire repository. Directory deletions and event storms still run the full scan-diff, so nothing the events can't describe is ever missed. Measured: save-to-fresh-graph sync work drops to ~0.3s on a 4,400-file project and ~0.4s on a 27,000-file one, with resulting graphs byte-for-byte identical to a full reconciliation.
  • Indexing Swift and other protocol/interface-heavy codebases got dramatically faster: the conformance walk that checks whether a method lives on a receiver's supertypes (protocols, base classes, extensions) now remembers its answers for the duration of each resolution batch instead of re-querying the graph for every call site — on the Swift compiler repository (27k files) that walk ran nearly a million times per index. A fresh index of that repo drops from about 185 seconds to under 100, with the graph byte-for-byte identical. Method-candidate lookup also gained a per-name owner index, so overload-heavy names (init in Swift, execute in Java) no longer pay a full candidate scan per receiver type.
  • Resolving method calls through local variables (recv.method(), Lua's recv:method(), R's recv$method()) got much cheaper on repos where the same receiver is called over and over: the declaration scan that types the receiver now remembers what it has already scanned per scope instead of re-reading the same source lines for every call site, and the regex patterns it scans with are compiled once per receiver instead of per call. Kong's fresh index drops another 8% on top of the require-resolution fix (23% cumulative), with graphs byte-for-byte identical everywhere — including Java projects, where this same scan successfully types tens of thousands of receivers.
  • Indexing Lua and Luau projects got a sizeable speedup: resolving each require(...) no longer rescans the project's entire file list four times — a per-project filename index answers the same lookup instantly, cutting per-require resolution from about a millisecond to microseconds. A fresh index of Kong (1,870 Lua files) runs about 16% faster end-to-end, with the graph byte-for-byte identical. The same housekeeping also closes a latent staleness edge where COBOL copybook lookups could keep serving a cached file list after files changed.
  • Parallel reference resolution now engages adaptively instead of by a fixed project-size cutoff: the indexer measures the actual per-reference resolution rate on the first batch and spins up the worker pool mid-run whenever the remaining work justifies it. Languages whose references are expensive to resolve benefit most — Rust especially: a fresh index of tokio runs about 23% faster, with the graph byte-for-byte identical. Small projects and low-core machines (2-core CI runners) keep the single-threaded path exactly as before.
  • The dynamic-dispatch analysis at the end of indexing now skips passes that provably can't produce anything for the project at hand: React re-render bridging when no class has a render method, React Native and Expo cross-platform pairing when the required languages aren't present, and MyBatis mapper linking when there's no mapper XML. Previously each of these scanned the whole graph before coming up empty — on a 4,000-file Java project that was about 0.9 seconds of wasted analysis per fresh index. The interface-implementation bridging pass also got cheaper on real work: it no longer re-fetches a hub interface's method list once per implementer, and classes that extend or implement nothing are skipped before any per-class lookups. Graphs remain byte-for-byte identical.
  • Indexing large C and C++ codebases spends much less time in the function-pointer dispatch analysis (the pass that connects handler tables like a command table or an ops struct to their call sites): each source file is now read and prepared once instead of four times, files that can't contribute any dispatch wiring are skipped outright in the later linking steps, and on platforms with the native engine the per-file scanning itself now runs natively too. On a Linux-kernel-scale tree the pass runs about a third faster end-to-end, with graphs byte-for-byte identical; platforms without a native binary keep the same results on the previous path.

Fixes

  • TypeScript, TSX, and JavaScript files now parse with up-to-date grammars — modern syntax such as using declarations and import attributes no longer trips parse errors that could drop surrounding symbols. (The previously bundled grammars dated from 2023.)
  • Rust files also parse with an up-to-date grammar now (the previously bundled build dated from 2023), which additionally sharpens method-call attribution: calls through struct fields resolve with receiver context instead of falling back to ambiguous bare-name matching, removing a class of wrong call edges on common names like len and start.
  • Ruby files also parse with an up-to-date grammar now (the previously bundled build dated from early 2024), which fixes a misparse of safe-navigation operator-method calls (recv&.!= x) that had recorded the wrong callee name.
  • PHP files also parse with an up-to-date grammar now (the previously bundled build dated from 2023): files using modern PHP features — enum constants, PHP 8.4 property hooks, parenthesis-free new X()->method() chaining — no longer hit parse errors or misparses that dropped or garbled their symbols, so codebases like Symfony and Laravel index substantially more accurately.
  • Swift files also parse with an up-to-date grammar now (the previously bundled build dated from 2023): swift-testing #expect, #Preview-style macros, the package access modifier, and typed throws no longer produce parse errors that dropped surrounding symbols — server-side Swift projects like Vapor see the biggest recovery.
  • Dart's grammar is now bundled with CodeGraph itself instead of being resolved from a third-party package whose Dart build floated on an unpinned upstream reference — a routine dependency update can no longer silently change how Dart files parse.
  • Searching or exploring by field names now finds the code that defines them. A query made of object keys or API field names (profileInfo isTrialEligible quotaInfo billingMethod) used to return unrelated results while the defining files never appeared, because three retrieval steps each dropped multi-word camelCase terms: an internal case-comparison bug, a match step that only considered classes (never functions or methods), and exploration seeding that required exact symbol-name matches. All three are fixed — codegraph_explore with a bag of field names now surfaces the controllers and services that assemble those fields. (#1196)
  • codegraph.json's includeIgnored works again for the "folder of repos" layout: when one .gitignore rule covers a parent directory (/repos/) holding several embedded git repositories, opting in the individual repos ("includeIgnored": ["repos/a/"] — the exact spelling codegraph init's own hint suggests) previously matched nothing and indexed zero files, looping the same suggestion back at you. Both spellings now work — name the parent directory to opt in everything under it, or name individual repos to opt in just those — and the hint no longer re-suggests repos that are already configured. (#1295)
  • Method calls on literals (", ".join(...) in Python, "x".split(...) in JavaScript, and the like) no longer produce call edges to unrelated project functions that happen to share the builtin's name — a codebase with a function called join, get, or update could show phantom callers from every string-builtin use. Additionally, a function nested inside another function is now only matched as a call target from inside its container, since it isn't reachable from anywhere else. Blast-radius and affected-test results get cleaner on Python and JavaScript codebases especially. (#1230)
  • Go method calls through a struct field (target.conn.Exec(...)) no longer bind to unrelated same-named local methods when the field's type is external — conn *sql.DB calls were being attributed to a local interface that happened to declare Exec, fabricating internal dependencies. Chained field calls now resolve by inferring the field's declared type from the struct definition: in-project types (including unexported ones like chi's tree *node) gain correct, validated call edges that never existed before, and external types (standard library, third-party modules) are left unlinked instead of guessed. (#1276)
  • TypeScript/JavaScript method calls through an imported singleton (import { store } from './store'; store.notify()) now resolve to the class method instead of the exported constant, so codegraph callers sees cross-file callers of the method — previously only same-file calls were attributed and a method used everywhere could look unused. The same declaration-based type inference applies across the languages that share it (Python, Java, Kotlin, Go, and more), and a failed inference keeps the old edge rather than guessing. (#1292)
  • codegraph node <symbol> -f <file> now prints the symbol's source body. Pinning an ambiguous name to a specific file (the whole point of -f when many files define the same function) returned only the location and caller trail with no code. (#1284)
  • Deleting a whole directory is now picked up by watch mode: the files inside it are removed from the index on the next auto-sync instead of lingering as stale records until an unrelated edit happened to trigger one. Operating systems often report a directory deletion as a single event on the directory itself (with no per-file events for its contents), which the watcher previously discarded. (#1285)
  • codegraph sync now gets the same slow-disk fix that made full indexing fast in 1.4.0: database checkpointing is deferred for the whole incremental run instead of firing every few megabytes of writes. On mechanical drives and other high-latency storage, a small sync on a large index no longer stalls for minutes at near-zero CPU — the cost of a sync scales with what changed, not with the size of the existing index. The same CODEGRAPH_NO_WAL_DEFER=1 switch turns it off. (#1248)
  • C functions declared with a project-specific attribute macro in front of a typedef'd return type (SEC_ATTR UINT32 MyFunc(VOID) — common in embedded and kernel code) are now indexed under their real names. Previously the parser tripped over the unknown macro and stored the parameter list as the function name, leaving entries like "(VOID)" in the graph and making the real function unfindable. (#1211)
  • Macro-heavy C and C++ code indexes much more completely. Fifteen ubiquitous idioms that previously tripped the parser into error recovery — dropping symbols, garbling names, minting phantom entries, or losing the relationships between real ones — now parse cleanly: the #ifdef __cplusplus / extern "C" { compatibility guard in C headers, iterator macros in statement position (list_for_each_entry(pos, head, member) { … } and the whole Linux-kernel/git/jemalloc family — including calls that wrap across lines, like hlist_for_each_entry_rcu(…) with a lockdep_is_held argument), the Linux/sparse declaration annotations (static int __init foo(void), void __user *buf, container_of(p, struct T, m)), parameterized annotations (__free(kfree), __printf(4, 0), __counted_by(count)), per-CPU and work-queue declaration macros (static DEFINE_PER_CPU(struct T, name);, initialized forms included), bare type arguments to allocator and list macros (kzalloc_obj(struct T), list_entry(p, struct T, member)), va_arg with a qualified or pointer type, GNU named-variadic macro definitions (#define dbg(fmt, args...)), static notrace-style compiler markers, C23 auto declarations, trailing parameter annotations (int argc UNUSED, git's house style), namespace-management macros alone on a line (FMT_BEGIN_NAMESPACE, Qt's Q_OBJECT), and function attribute macros in front of C++ return types. On the Linux kernel this cuts files lost to parse errors on the core directories by nearly half and recovers thousands of call and reference relationships that error recovery silently dropped, with git and redis seeing smaller cuts of the same kind; graphs stay byte-for-byte identical between the native and fallback engines. A related fix stops the macro handling itself from corrupting #define lines that mention the same macro names, which removed a class of phantom parse errors in fmt-style headers.
  • C++ methods defined out-of-line inside a namespace (namespace sim { Output MyClass::Apply(...) { ... } }) now carry the namespace in their qualified name, matching their class. Fully-qualified call sites from other files (sim::MyClass::Apply(...)) resolve to the definition again, so codegraph callers and file impact no longer come up empty for this pattern. (#1291)
  • C++ methods defined out-of-line on a template class (template <typename T> T Box<T>::get() { ... }) no longer keep the template parameter list in their qualified name. They now index as Box::get — identical to an inline definition of the same method — so they link to their class and resolve from call sites again, and pathological multi-line template parameter lists can no longer blow the qualified name past filesystem name limits. (#1286)
  • Go route detection no longer misidentifies ordinary method calls that share HTTP verb names — cache.Put("key", value), store.Get("config", out), bus.Handle("user.created", handler) and the like were being indexed as HTTP routes, polluting route listings in cache-heavy codebases. A registration now has to look like one: its first argument must be a /-prefixed path (all routers) or a Go 1.22 "METHOD /path" pattern on Handle/HandleFunc, which now also extracts the method instead of listing the route as ANY. (#1259)
  • Progress output on Windows no longer mixes ASCII | rails with the Unicode │ ◆ ● frame around them. In terminals that render Unicode (Windows Terminal, VS Code, ConEmu/Cmder, JetBrains, Alacritty), the whole codegraph init / index / sync block now draws with matching box-drawing characters; unrecognized legacy consoles keep the safe all-ASCII output that avoids garbled characters. CODEGRAPH_ASCII=1 / CODEGRAPH_UNICODE=1 still override in either direction. (#398)
  • CLI output now honors the NO_COLOR convention and new --color / --no-color flags, and goes plain automatically when piped: commands like codegraph status, query, callers, and files no longer embed ANSI color codes when stdout isn't a terminal, and a piped codegraph init / index / sync prints simple per-phase lines instead of progress-animation control characters. FORCE_COLOR or --color forces color back on for pipes that render it. (#1281)
  • Callers and impact analysis no longer silently under-count a function that calls the same callee many times. When one caller contained several call sites to the same callee and an internal resolution batch boundary happened to split them, cleanup after the first batch removed the later sites' pending rows before they were ever attempted — their edges were never created, deterministically, and which edges went missing shifted with unrelated changes to the project's total reference count. Post-pass cleanup now targets the exact database row each processed reference came from. Found while validating the operator-call fix on nlohmann/json, where write_cbor's 11 calls to to_char_type indexed as 10. (#1269)
  • C++ explicit operator calls — a.operator+(b), p->operator+(b), a.operator[](3), and the other symbolic forms — now produce a calls edge to the operator method, so an operator invoked only through the explicit syntax no longer looks uncalled in callers and impact analysis. tree-sitter parses these call sites with the operator name stranded in an error node (never as a normal member access), so the call's target was silently read as just the receiver variable; the operator name is now recovered from the error node and resolved through receiver-type inference like any other member call — a same-named operator on an unrelated class can never capture the edge. Infix uses (a + b, a[i]) need real type inference and are tracked separately. (#1247)
  • codegraph init and codegraph index no longer look hung after "Resolving refs" reaches 100%. The dynamic-dispatch linking that runs after resolution (callbacks, React re-renders, C function pointers, and the rest) had no progress display, so on repos where it takes a while — large C codebases especially — the bar just sat frozen at 100% until it finished. That work now shows as its own "Linking dynamic dispatch" progress phase, and the heaviest pass — C function-pointer linking — additionally reports progress within the pass, so a large C codebase advances the bar smoothly instead of parking it on one number for the bulk of the phase.
  • Indexing no longer prints repeated "SQLite is an experimental feature" warnings that garbled the progress display. The warning comes from Node's built-in SQLite and fired once per parsing worker; it's now suppressed on every launch path.
