#gráfico de código v1.1.0

[1.1.0] - 23/06/2026

Novos recursos

  • Claude Code: um gancho de carregamento frontal opcional faz com que seu agente alcance o CodeGraph automaticamente. Quando você faz uma pergunta estrutural - "como X funciona", "o que chama Y", "rastrear o fluxo de A a B" - o CodeGraph injeta a origem relevante e os caminhos de chamada no prompt antecipadamente, para que o agente responda a partir do gráfico em vez de ficar procurando reconstruí-lo. Você é solicitado durante codegraph install (padrão sim; apenas código Claude, já que é o agente com ganchos de prompt), ele é removido por codegraph uninstall e codegraph upgrade o ativa para configurações existentes de Claude. É estritamente aditivo e degradável – prompts não estruturais e projetos não indexados são deixados de lado – e você pode desligá-lo a qualquer momento sem desinstalar, configurando CODEGRAPH_NO_PROMPT_HOOK=1.
  • Ações, mutações e getters da loja Vue agora são indexados como símbolos que você pode encontrar e ler. Quer sua loja seja Vuex (objetos mutations / actions em um módulo) ou Pinia — tanto o formulário de opções (defineStore({ actions: { … } })) quanto o formulário de configuração (defineStore('id', () => { … }), onde ações são funções locais) — cada ação, mutação e getter agora é um nó real. Portanto, codegraph search encontra login ou getSessionList, e codegraph_explore/codegraph_node mostra seu corpo e o que ele chama, em vez de "não encontrado" porque a função só existia como uma propriedade literal de objeto.
  • codegraph_explore agora conecta um componente Vue à ação de armazenamento Pinia que ele chama. Quando o código faz const store = useUserStore() e depois store.fetchUser(), essa chamada agora é vinculada à ação fetchUser no módulo de armazenamento - então "o que acontece quando esta visualização carrega seus dados?" traça do componente para o corpo da ação em vez de parar na linha store.fetchUser(). Funciona para ambos os estilos de loja Pinia (opções e configuração) e permanece preciso (um método integrado como store.$patch() ou um método não relacionado com o mesmo nome não está vinculado incorretamente).
  • codegraph_explore agora segue o envio de string Vuex. Uma chamada dispatch('user/login') ou commit('SET_TOKEN') - incluindo chaves 'module/action' com namespace - agora é vinculada à ação ou mutação que ela nomeia, resolvida para o módulo de armazenamento correto mesmo quando vários módulos compartilham um nome de ação (e sem serem enganados por um auxiliar api/ de mesmo nome). Então, "o que é executado quando isso é despachado?" rastreia da chamada para o manipulador de armazenamento e para as mutações que ele confirma. A forma canônica do módulo export default { namespaced, actions, mutations } do Vuex agora também está indexada, portanto, esses manipuladores são símbolos localizáveis.
  • codegraph_explore agora conecta fluxos de busca de dados React criados em RTK Query (createApi do Redux Toolkit). Um endpoint definido dentro de createApi({ endpoints }) e o gancho useGetXQuery / useUpdateYMutation que ele gera eram invisíveis para análise - então "o que este componente busca?" ou "onde o useGetThingQuery obtém seus dados?" sem saída, porque o gancho, o ponto final e o componente não tinham nada ligando-os. CodeGraph agora indexa cada endpoint e cada gancho gerado como símbolos reais e conecta o caminho component → useGetXQuery → getX → queryFn, para que o fluxo seja resolvido em uma chamada de exploração em vez de ler a fatia API manualmente. Os estilos de seta (endpoints: build => ({ … })) e método (endpoints(builder) { return { … } }) são reconhecidos, juntamente com a variante useLazyGetXQuery; ganchos escritos à mão com um nome semelhante são deixados intocados.
  • codegraph_explore agora segue o envio de tarefas Celery em Python. Uma chamada send_email.delay(...) ou send_email.apply_async(...) agora é vinculada à função @shared_task/@app.task que ela executa — normalmente definida em um módulo diferente (tasks.py) de onde é acionada (uma visualização ou serviço) — então "o que realmente acontece quando isso é despachado?" rastreia do site de chamada diretamente para o corpo da tarefa em vez de parar na linha .delay(). Ambos os dialetos decoradores são reconhecidos (@shared_task simples e a forma arg'd @app.task(bind=True, …)), incluindo o estilo de chamada tasks.invalidate_cache.apply_async() qualificado para módulo. Ele permanece preciso: um .delay() em algo que não é uma tarefa do Celery nunca é mal vinculado, portanto, um projeto que não usa o Celery não é afetado.
  • codegraph_explore agora segue eventos de aplicativos Spring em Java. Uma chamada publishEvent(new OrderShippedEvent(...)) agora é vinculada a cada @EventListener que lida com esse evento - geralmente em uma classe diferente - então "o que reage quando isso é publicado?" rastreia do editor diretamente para cada método de ouvinte, em vez de terminar em publishEvent(...). A ligação é por tipo de evento, e todos os estilos de listener comuns são reconhecidos: um @EventListener digitado em seu parâmetro, o formato @EventListener(SomeEvent.class), @TransactionalEventListener e o antigo implements ApplicationListener<SomeEvent>. Um evento se espalha para todos os seus ouvintes, e um aplicativo Spring simples, sem barramento de eventos, não é afetado.
  • codegraph_explore agora segue solicitação MediatR e envio de notificação em C#/.NET. Uma chamada _mediator.Send(command) ou _mediator.Publish(notification) agora é vinculada ao método Handle do IRequestHandler<> / INotificationHandler<> correspondente - geralmente em um arquivo diferente em um layout de Arquitetura Limpa - então "o que trata deste comando?" rastreia do controlador diretamente para o manipulador, em vez de parar na chamada do mediador. O tipo enviado é reconhecido seja construído em linha (Send(new GetFooQuery())), incorporado primeiro em um local (var cmd = new …; Send(cmd)) ou passado como um parâmetro e é correspondido por tipo - portanto, um MessagingCenter.Send(...) ou um DTO de mesmo nome que não é uma solicitação nunca é mal vinculado e um projeto sem MediatR não é afetado.
  • codegraph_explore agora segue o envio de trabalhos em segundo plano Sidekiq em Ruby. Uma chamada DestroyUserWorker.perform_async(id) (ou .perform_in / .perform_at) agora é vinculada ao método perform desse trabalhador - geralmente em app/workers/, longe do controlador ou modelo que o enfileira - então "o que é executado em segundo plano aqui?" rastreia do enfileiramento direto para o corpo do trabalho. Tanto o include Sidekiq::Job moderno quanto o Sidekiq::Worker mais antigo são reconhecidos, trabalhadores com namespace resolvem para a classe certa mesmo quando vários compartilham um nome (por exemplo, Comments::NotifyWorker vs Articles::NotifyWorker), e o perform_later do Rails ActiveJob - um mecanismo diferente - é intencionalmente deixado de lado.
  • codegraph_explore agora segue eventos Laravel em PHP. Uma chamada event(new OrderShipped($order)) agora é vinculada a cada ouvinte que a trata - o método handle() de cada ouvinte, geralmente uma classe app/Listeners/ separada - então "o que reage a este evento?" traços do despacho direto para os corpos do ouvinte. Os ouvintes são encontrados de ambas as maneiras que o Laravel os registra: por um handle(OrderShipped $event) digitado (autodescoberta, incluindo uma união handle(A|B $event) que escuta dois eventos) e pelo mapa protected $listen em seu EventServiceProvider (que também captura um ouvinte cujo handle() não tem dica de tipo). Um evento se espalha para todos os seus ouvintes e os trabalhos na fila – despachados via ::dispatch() em vez de event() – são corretamente deixados de fora.
  • CodeGraph agora entende métodos gerados pelo Lombok em Java. @Getter, @Setter, @Data, @Value e @Builder geram getters, setters, builder(), equals/hashCode/toString e o campo @Slf4j log em tempo de compilação, portanto, esses métodos nunca aparecem na fonte - e um user.getName(), User.builder() ou A chamada log.info(...) costumava não resolver nada, quebrando silenciosamente a análise da cadeia de chamadas (o agente concluiria que o método não existia e o reconstruiria manualmente). Esses membros agora são indexados a partir das anotações e campos, portanto, aparecem em codegraph search e codegraph_explore/codegraph_node, e os chamadores os rastreiam como qualquer método escrito à mão. Eles são marcados como gerados pelo Lombok, portanto são lidos como gerados, não escritos à mão; um método que você mesmo escreve nunca é substituído, campos estáticos não recebem acessador e uma classe sem Lombok não é afetada. Obrigado @git87663849. (#912)
  • codegraph_explore agora segue despacho de ponteiro de função C e C++. C faz polimorfismo com ponteiros de função: uma estrutura carrega um campo de ponteiro de função, funções concretas são registradas nela por meio de uma tabela (static struct cmd commands[] = {{"add", cmd_add}, …}), um inicializador designado (.handler = on_open) ou uma atribuição, e o código é despachado indiretamente (p->fn(argv)). Nada disso era visível para análise - a chamada indireta não resultava em nada, então o executor de comando do git parecia não ter chamado nada e as implementações de uma vtable não tinham chamadores. CodeGraph agora vincula o site de despacho aos manipuladores registrados, codificados pelo campo struct, então "o que é executado quando isso é despachado?" rastreia de p->fn(...) em cada função registrada para esse campo. Isso cobre o idioma da tabela de comandos (git, redis) e o idioma ops-struct/vtable (codificadores de conteúdo do curl, manipuladores de protocolo), incluindo o caso em que um slot de gancho genérico é reatribuído de um registro (h->func = found->fn). Ele permanece preciso — campos distintos de ponteiro de função não fazem link cruzado, um campo de dados simples nunca é tratado como um despacho e um projeto sem despacho de ponteiro de função não é afetado. (#932)
  • codegraph_explore agora segue ligações de rota GoFrame em Go. Os fios do roteador padrão do GoFrame são roteados de forma reflexiva: o caminho e o método residem em uma tag de estrutura g.Meta em um tipo de solicitação (g.Meta `path:"/user/sign-in" método:"post"`), the controller method that serves it is matched by that request type, and the two are joined at runtime by group.Bind(...) — so there was no path string and no edge from a route to its handler, and "where is /user/sign-in handled?" or "where are the routes bound to controllers?" could only be answered by reading. CodeGraph now indexes each g.Meta route as a real route node and links it to the controller method whose signature takes that request type, so a route resolves to its handler structurally in one codegraph_explore call. The link is by request type, not method name — so it's correct even when the two differ (a DeptSearchReq served by a List method); it tells apart the many identical request types a large app defines one-per-module (cash.ListReq vs order.ListReq) por pacote, incluindo módulos adicionais clonados; e uma rota cujo manipulador não está presente é deixada desvinculada em vez de adivinhada. (#747)
  • O servidor MCP agora funciona em configurações monorepos e multiprojeto. Antes, se você iniciasse o CodeGraph em algum lugar sem nenhum .codegraph/ próprio - na maioria das vezes uma raiz monorepo onde você indexava apenas serviços individuais - o servidor não expunha nenhuma ferramenta, então seu agente não poderia consultar o CodeGraph mesmo para os subprojetos que foram indexados. Agora as ferramentas estão sempre disponíveis: aponte uma consulta para qualquer projeto indexado com o argumento projectPath (seu caminho ou qualquer lugar dentro dele) e o CodeGraph responde a partir do índice desse projeto — para quantos projetos você quiser em uma sessão. Isso também significa que um projeto que você indexa após o servidor ser iniciado é selecionado sem reiniciar, onde antes as ferramentas permaneciam ocultas porque o servidor só verificava um índice uma vez na inicialização. Um projeto que realmente não possui índice ainda diz ao seu agente para usar suas ferramentas integradas (e que você pode executar codegraph init para habilitá-lo), portanto, o uso de um único projeto permanece inalterado. Obrigado @MaiLunJiye. (#964)
  • O gancho de carregamento frontal Claude agora encontra seus subprojetos indexados em um monorepo. O gancho UserPromptSubmit opcional que injeta o contexto do CodeGraph para questões estruturais anteriormente apenas procurava um índice no diretório de trabalho ou acima dele - portanto, se você abriu a raiz do monorepo, mas indexou pacotes individuais (packages/api, services/auth), ele não encontrou nada e permaneceu em silêncio exatamente onde era mais útil. Agora ele também analisa em subprojetos: um único subprojeto indexado obtém seu contexto carregado automaticamente e, com vários, o gancho carrega antecipadamente aquele que sua pergunta nomeia (e lista o resto para que o agente possa direcioná-los por projectPath). Os repositórios de projeto único não são afetados e a verificação é limitada e ignorada totalmente fora de uma raiz de espaço de trabalho reconhecível. (#964)
  • codegraph_explore agora apresenta o código correto em grandes projetos multicamadas. Quando você faz uma pergunta sobre o fluxo de back-end em um repositório que emparelha um servidor API com um grande front-end que espelha as mesmas palavras de domínio - digamos, uma interface de administração app/ instalada em um servidor api/ - o arquivo do lado do servidor que genuinamente corresponde a vários dos termos da sua consulta não é mais excluído dos resultados pela camada de front-end maior e mais interconectada. Um arquivo corroborado por dois ou mais termos de consulta distintos agora é mantido na resposta mesmo quando uma camada mais densa e não relacionada o excluiria, então "como o X lê os itens/trata a solicitação" retorna o serviço ou manipulador que faz o trabalho em vez de uma parede de visualizações de front-end. Os projetos de camada única não são afetados; configure CODEGRAPH_RANK_NO_MULTITERM=1 para reverter para a classificação anterior.
  • Análise de impacto e raio de explosão para TypeScript, JavaScript, Go, Python, Rust, Ruby, C, Java, C#, PHP, Scala, Kotlin, Swift, Dart e Pascal/Delphi agora entende os leitores de uma constante. Quando você altera uma constante de escopo de arquivo, nível de pacote, nível de módulo ou nível de classe - um objeto de configuração, uma tabela de pesquisa, uma constante compartilhada - os outros símbolos nesse arquivo que o lêem agora aparecem como afetados, onde antes eram invisíveis (o impacto apenas seguia chamadas, importações e herança, de modo que os consumidores de uma constante pareciam "nada depende disso"). Isso faz com que codegraph impact e a trilha de impacto em codegraph_explore/codegraph_node capturem a classe de mudança "mudar esta tabela, quebrar seus leitores". Está ativado por padrão e não adiciona nós ao seu gráfico; arquivos agrupados/minificados e nomes sombreados de forma ambígua são ignorados para manter os resultados precisos. Configure CODEGRAPH_VALUE_REFS=0 para desligá-lo.
  • Constantes e globais de escopo de arquivo C — escalares static const, tabelas de pesquisa de ponteiro/matriz e globais mutáveis ​​compartilhados — agora são reconhecidos como símbolos por si só. Anteriormente, eles não eram extraídos, portanto nunca apareceram em busca ou carregavam dependentes; agora eles aparecem em codegraph search e participam da análise de impacto (veja acima), portanto, a alteração de uma tabela de pesquisa C revela as funções do mesmo arquivo que a lêem.
  • Constantes Java static final, constantes C# const / static readonly, Scala object vals e Kotlin de nível superior / object / companion object vals agora são classificados como constantes em vez de campos genéricos, portanto, eles participam da análise de impacto do leitor constante acima - altere uma tabela public static final, uma const string, Scala object Config { val Timeout = … } ou Kotlin companion object { const val … } e os métodos que os leem agora aparecem como afetados. (As propriedades da instância Java final / C# readonly / Scala e Kotlin class por objeto permanecem inalteradas.) As constantes Kotlin anteriormente não eram indexadas como seus próprios símbolos, então agora também aparecem em codegraph search.
  • As constantes lets e static let de nível superior do Swift (incluindo aquelas com namespace em um enum/struct, o padrão Swift comum) agora são indexadas como constantes e participam da análise de impacto do leitor constante acima - altere um static let defaultRetryLimit ou um enum Constants { static let … } e o mesmo código de arquivo que o lê aparece como afetado. Propriedades computadas e lets por instância não são tratadas como constantes.
  • As constantes const/final de nível superior do Dart e as constantes de classe static const/static final agora são indexadas como constantes e participam da análise de impacto do leitor constante acima. Campos de instância, vars e locais não são tratados como constantes. (O código Dart gerado com os sufixos padrão .g.dart/.freezed.dart/.pb.dart já foi ignorado.)
  • Agora você pode ensinar ao CodeGraph sobre extensões de arquivo personalizadas. Solte um codegraph.json na raiz do repositório com um mapa extensions - { "extensions": { ".dota_lua": "lua", ".tpl": "php" } } - e os arquivos com essas extensões serão indexados no idioma que você nomear, em vez de serem ignorados silenciosamente porque a extensão não era um dos padrões integrados. Ele é ativado e confirmado junto com seu código para que toda a equipe o compartilhe, seus mapeamentos sejam colocados sobre os integrados e vença o conflito (você pode até apontar novamente um integrado, por exemplo, .h → cpp), e uma linguagem digitada ou uma configuração malformada é avisada e ignorada em vez de quebrar a indexação. Projetos sem codegraph.json se comportam exatamente como antes. (#906)

Correções

  • codegraph index e codegraph init não rastejam mais durante a fase "Resolver refs" em projetos grandes - mais dolorosamente aqueles que misturam um grande front-end e back-end, onde a fase pode se estender por vários minutos. Um pacote ou módulo importado em centenas ou milhares de arquivos (react, um pacote de UI compartilhado, Python logging / typing) estava sendo tratado como se cada uma dessas instruções de importação pudesse ser sua definição, então o resolvedor comparou cada importação com todas as outras - trabalho que cresce com o quadrado de quão amplamente um pacote é importado, e é por isso que ele explodiu apenas em repositórios grandes e com muitas importações. As importações agora são resolvidas diretamente para as definições para as quais realmente apontam, de modo que essas comparações redundantes desaparecem (a resolução de referência é dramaticamente mais rápida em repositórios grandes) e o gráfico não acumula mais os links sem sentido de importação para importação que o antigo substituto criava. (#915)
  • Os resultados da ferramenta MCP não aparecem mais como títulos superdimensionados em clients de renderização Markdown (como a extensão Claude Code VSCode). Os resultados usaram títulos Markdown (##/###) para coisas como o resumo de status, cada resultado de pesquisa e cada seção de arquivo em uma exploração, portanto, uma consulta normal preencheu a transcrição com linhas de fonte grande – pior com codegraph_search e codegraph_explore, onde o ruído cresceu com o número de resultados. Os cabeçalhos das seções agora são rótulos em negrito, que são renderizados no tamanho normal do texto, mantendo a mesma estrutura. A saída do terminal/CLI permanece inalterada. (#778)
  • Um servidor MCP apontado para um repositório muito grande (dezenas de milhares de arquivos) não trava mais na primeira chamada de ferramenta após um novo início. Na inicialização, o CodeGraph reconcilia seu índice com os arquivos atuais no disco e em um repositório enorme que a reconciliação pode ser executada por minutos enquanto bloqueia a primeira solicitação - tempo suficiente para que o servidor de segundo plano às vezes seja reiniciado à força no meio da verificação, de modo que a primeira consulta nunca mais voltou. A reconciliação agora ocorre à medida que é executada (mantendo o servidor responsivo em vez de fixá-lo), e a primeira chamada da ferramenta espera apenas brevemente antes de responder e deixar o restante terminar em segundo plano — para que você obtenha uma primeira resposta rápida e o índice ainda seja atualizado. Configure CODEGRAPH_CATCHUP_GATE_TIMEOUT_MS para ajustar quanto tempo a primeira chamada aguarda (padrão 3000 ms) ou =0 para sempre aguardar pela reconciliação completa. (#905)
  • codegraph install agora conecta seus agentes e para aí — ele não indexa mais o diretório atual. Construir o gráfico de um projeto é sempre o codegraph init (ou codegraph index) explícito, então você decide o que será indexado e quando, e as etapas serão as mesmas, independentemente de você ter instalado globalmente ou apenas para um projeto. Isso esclarece a confusão em que uma instalação local do projeto foi indexada silenciosamente, mas uma instalação global não, e onde os documentos e a ferramenta discordaram sobre se você ainda precisava executar o init. (#826)
  • Componentes React declarados com forwardRef, memo ou componentes estilizados/emoção (const Button = forwardRef(...), const Card = memo(...), const Box = styled.button\…`) are now recognized as components, so finding where they're used works. Before, they were indexed as plain constants, so codegraph callersand impact analysis reported "no callers found" even when the component was rendered across dozens of files — a dangerous false "safe to change" right before refactoring a shared component. Now every<Button/>` vincula o uso de volta ao componente, para que os chamadores e o raio de explosão estejam completos. Este é o estilo de declaração shadcn/ui padrão, portanto, para sistemas de design React típicos, toda a camada de UI não é mais invisível à análise de impacto. Obrigado @Arlandaren pelo relatório e @maxmilian pela causa raiz (#841).
  • As rotas React Router e Next.js definidas nos arquivos .tsx / .jsx agora são indexadas. Rotas escritas como JSX - arquivos de página <Route path="/users" element={<UsersPage/>}/>, createBrowserRouter([...]) e Next.js app//pages/ - estavam sendo totalmente ignoradas (apenas rotas que residiam em .ts/.js simples foram selecionadas), então "o que é renderizado neste caminho?" e o link rota → componente da página estavam faltando para a maioria dos aplicativos React. Agora essas rotas aparecem em codegraph search/codegraph_explore e se conectam ao componente que elas renderizam, assim como a rota de backend → links do manipulador em outras estruturas.
  • codegraph sync (e a sincronização automática do observador de arquivos por trás do uso sempre ativo / MCP) não elimina mais os chamadores de uma função quando você edita o arquivo em que a função reside. Reindexar um arquivo após uma edição - mesmo uma alteração apenas de docstring - estava cortando as bordas calls / references provenientes de outros arquivos inalterados (por exemplo, chamadores from pkg import mod; mod.fn() ou qualquer referência de arquivo cruzado), então codegraph callers/impact reportaria abruptamente "nenhum chamador" para uma função usada em toda a base de código, até a próxima reindexação completa. A sincronização agora preserva as bordas dos arquivos cruzados de entrada na reindexação, combinando-as novamente com o símbolo mesmo quando a edição mudou seu número de linha. Mais visível em grandes árvores de pacotes Python, mas se aplica a todos os idiomas. Obrigado @JosefAschauer. (#899)
  • codegraph index agora reconstrói o gráfico completo do zero, produzindo o mesmo resultado que um codegraph init novo em vez de reportar "0 nós, 0 arestas" e parecer que apagou seu índice. Anteriormente, a nova execução do index em um projeto inalterado ignorava todos os arquivos (seu conteúdo não havia mudado) e mostrava um resumo de aparência vazia; agora ele é limpo e reindexado para uma reconstrução completa e honesta sempre. Use codegraph sync para atualizações incrementais rápidas entre reconstruções completas. Obrigado @Arc-univer. (#874)
  • O inspetor de arquivos que sincroniza automaticamente o gráfico agora falha de forma limpa quando a visualização ao vivo não pode mais ser trusted, em vez de parecer saudável enquanto o índice fica obsoleto silenciosamente. Se o sistema operacional ficar sem recursos de observação de arquivos ou outro processo mantiver o bloqueio de gravação por muito mais tempo do que um salvamento normal, o CodeGraph agora desabilita a sincronização automática uma vez - com uma única mensagem clara informando para você executar codegraph sync (ou confiar nos ganchos de sincronização do git) para atualizar - em vez de tentar novamente para sempre ou repetir o mesmo erro em um loop. E embora a sincronização automática esteja desabilitada, as respostas da ferramenta CodeGraph (e codegraph status) agora dizem isso claramente, para que seu agente de IA saiba ler os arquivos diretamente, em vez de trusting um índice congelado. Isso é importante principalmente para sessões MCP/daemon de longa duração, que de outra forma poderiam continuar exibindo resultados obsoletos enquanto pareciam funcionar. Obrigado @thismilktea. (#876)
  • No Linux, atingir o limite de observação inotify do kernel em um projeto grande não deixa mais silenciosamente metade da árvore sem vigilância. CodeGraph agora informa uma vez - nomeando a configuração exata para aumentar (fs.inotify.max_user_watches, por exemplo, sudo sysctl fs.inotify.max_user_watches=1048576) - e continua observando ao vivo os diretórios que pode registrar enquanto codegraph sync (ou os ganchos de sincronização do git) cobre o resto. (#876)
  • Um servidor MCP de longa execução agora percebe quando uma árvore de trabalho git ganha seu próprio índice. Antes, se o servidor (ou daemon compartilhado) visse uma árvore de trabalho pela primeira vez antes de você executar codegraph init nela - então a pesquisa caminhava até o índice do checkout principal - ele fixava essa decisão para toda a vida: mesmo depois que a árvore de trabalho tinha seu próprio .codegraph/, cada consulta continuava atingindo o índice do checkout principal e cada resultado carregava um aviso falso "este índice pertence a uma árvore de trabalho git diferente", até você reiniciar o servidor. O CLI acertou, mas o servidor MCP não e a reindexação não ajudou. O servidor agora verifica novamente a qual índice um caminho pertence em cada chamada, de modo que o próprio índice da árvore de trabalho seja capturado — e o aviso obsoleto seja descartado — sem reinicialização. (#926)
  • Um servidor MCP de longa duração agora se recupera quando seu índice é excluído e reconstruído no mesmo caminho. Se .codegraph/ foi removido e recriado enquanto o servidor o mantinha aberto - mais facilmente recriando uma árvore de trabalho git no mesmo caminho, ou rm fazendo .codegraph/ e executando codegraph init novamente - o servidor continuava lendo o arquivo de banco de dados antigo e excluído e exibia um instantâneo congelado: símbolos renomeados ou removidos ainda eram exibidos como ativos, novos estavam faltando e codegraph sync não conseguia atualizá-lo - apenas reiniciar o servidor corrigia o problema. O servidor agora detecta que o arquivo de banco de dados foi trocado e reabre o arquivo ativo no local, para que os resultados permaneçam corretos sem reinicialização. (No Linux e macOS; o Windows não permite a exclusão de um arquivo aberto, portanto não é afetado.) (#925)
  • O servidor MCP agora abre e sincroniza automaticamente um projeto que reside dentro de uma pasta que um repositório git anexo ignora. Antes, se o diretório que você indexou estava dentro de um repositório maior que o ignorava, o daemon MCP compartilhado falhava ao abrir o projeto - seu log repetia Failed to open project … path should be a path.relative() d string, but got "./" - então o inspetor de arquivo nunca iniciava e o índice ficava obsoleto silenciosamente até que você executasse codegraph sync manualmente (definir CODEGRAPH_NO_DAEMON=1 era a única solução alternativa). O daemon agora abre o projeto e começa a observar conforme esperado. Mais visível com Codex no Windows, mas a causa não era específica da plataforma. (#936)
  • Uma árvore de trabalho git de um submódulo não é mais indexada como uma cópia duplicada do código desse submódulo. CodeGraph já ignora árvores de trabalho comuns (uma segunda visão funcional de um repositório que ele indexa), mas uma árvore de trabalho criada a partir de um submódulo - comum em monorepos que verificam submódulos em árvores de trabalho para trabalho de recursos paralelos - foi confundida com um repositório incorporado genuíno e varrido, duplicando cada símbolo que ele compartilhou com o checkout real do submódulo (um relatório tinha ~28% de seu índice como duplicados, inflando os resultados da consulta e o banco de dados). Essas árvores de trabalho do submódulo agora são reconhecidas e ignoradas, enquanto o próprio checkout do submódulo permanece indexado como código distinto. Obrigado @ charlesxu2026-ship-it. (#945)
  • Uma classe ou estrutura C++ anotada com uma macro de exportação/visibilidade — class MYLIB_EXPORT Foo : public Bar { … }, o padrão comum de exportação/visibilidade de DLL em cabeçalhos — não é mais indexada incorretamente como uma função que abrange todo o corpo da classe. Sem saber que a macro é uma macro, o analisador a leu como um tipo e toda a declaração como uma função, então a classe surgiu como um fantasma function que apareceu como um chamador falso em codegraph callers, codegraph impact e análise de raio de explosão e contagens de símbolos distorcidas. CodeGraph agora reconhece essa análise incorreta e descarta o nó falso. Obrigado @spwlyzx. (#946)
  • codegraph status não relata mais alterações fantasmas pendentes para arquivos que o CodeGraph mantém deliberadamente fora do índice - um arquivo rastreado dentro de um diretório de dependência confirmado (um vendor/ ou node_modules/ com check-in) ou um arquivo rastreado em um diretório .gitignored. Um índice completo os exclui corretamente, e o codegraph sync nunca os indexa, mas o rápido detector de alterações por trás do codegraph status sinalizou cada edição desse arquivo como "modificado" (e um novo como "adicionado") - portanto, a contagem de alterações pendentes nunca é apagada, não importa quantas vezes você sincronizou. A detecção de alterações agora aplica as mesmas regras de ignorar que o índice completo faz, então status concorda com sync, e as ferramentas construídas na detecção de alterações API do CodeGraph obtêm a mesma lista corrigida. (#766)
  • Arquivos alcançados por meio de um diretório com link simbólico que aponta para fora do seu projeto agora são indexados em vez de serem ignorados silenciosamente. Quando uma pasta em seu repositório é um link simbólico para um local fora da raiz do repositório - o layout padrão para jogos personalizados Dota 2 e projetos semelhantes vinculados ao SDK, onde game/ e content/ se vinculam à árvore do mecanismo - CodeGraph seguiu o link simbólico para descobrir esses arquivos, mas depois bloqueou cada um deles durante a leitura, registrando Path traversal blocked in batch reader e não indexando nada sob eles. O leitor agora concorda com a verificação do diretório e indexa esses arquivos. A proteção contra escapes de caminho ../ permanece inalterada, e a proteção que impede seu agente de receber conteúdo de arquivo de fora do repositório também permanece inalterada - apenas o caminho de leitura do próprio indexador segue esses links simbólicos no repositório. (#935)

codegraph v1.1.0

[1.1.0] - 2026-06-23

New Features

  • Claude Code: an optional front-load hook makes your agent reach for CodeGraph automatically. When you ask a structural question — "how does X work", "what calls Y", "trace the flow from A to B" — CodeGraph injects the relevant source and call paths into the prompt up front, so the agent answers from the graph instead of grepping around to rebuild it. You're asked during codegraph install (default yes; Claude Code only, since it's the agent with prompt hooks), it's removed by codegraph uninstall, and codegraph upgrade turns it on for existing Claude setups. It's strictly additive and degradable — non-structural prompts and un-indexed projects are left alone — and you can switch it off any time without uninstalling by setting CODEGRAPH_NO_PROMPT_HOOK=1.

  • Vue store actions, mutations, and getters are now indexed as symbols you can find and read. Whether your store is Vuex (mutations / actions objects in a module) or Pinia — both the options form (defineStore({ actions: { … } })) and the setup form (defineStore('id', () => { … }), where actions are local functions) — each action, mutation, and getter is now a real node. So codegraph search finds login or getSessionList, and codegraph_explore / codegraph_node show its body and what it calls, instead of "not found" because the function only existed as an object-literal property.

  • codegraph_explore now connects a Vue component to the Pinia store action it calls. When code does const store = useUserStore() and then store.fetchUser(), that call now links through to the fetchUser action in the store module — so "what happens when this view loads its data?" traces from the component into the action's body instead of stopping at the store.fetchUser() line. Works for both Pinia store styles (options and setup), and stays precise (a built-in like store.$patch() or an unrelated same-named method isn't mislinked).

  • codegraph_explore now follows Vuex string dispatch. A dispatch('user/login') or commit('SET_TOKEN') call — namespaced 'module/action' keys included — now links to the action or mutation it names, resolved to the correct store module even when several modules share an action name (and without being fooled by a same-named api/ helper). So "what runs when this dispatches?" traces from the call into the store handler and on to the mutations it commits. Vuex's canonical export default { namespaced, actions, mutations } module shape is now indexed too, so those handlers are findable symbols.

  • codegraph_explore now connects React data-fetching flows built on RTK Query (Redux Toolkit's createApi). An endpoint defined inside createApi({ endpoints }) and the useGetXQuery / useUpdateYMutation hook it generates were both invisible to analysis — so "what does this component fetch?" or "where does useGetThingQuery get its data?" dead-ended, because the hook, the endpoint, and the component had nothing linking them. CodeGraph now indexes each endpoint and each generated hook as real symbols and wires the path component → useGetXQuery → getX → queryFn, so the flow resolves in one explore call instead of reading the API slice by hand. Both the arrow (endpoints: build => ({ … })) and method (endpoints(builder) { return { … } }) styles are recognized, along with the useLazyGetXQuery variant; hand-written hooks of a similar name are left untouched.

  • codegraph_explore now follows Celery task dispatch in Python. A send_email.delay(...) or send_email.apply_async(...) call now links to the @shared_task / @app.task function it runs — typically defined in a different module (tasks.py) from where it's triggered (a view or service) — so "what actually happens when this is dispatched?" traces from the call site straight into the task body instead of stopping at the .delay() line. Both decorator dialects are recognized (bare @shared_task and the arg'd @app.task(bind=True, …) form), including the module-qualified tasks.invalidate_cache.apply_async() call style. It stays precise: a .delay() on something that isn't a Celery task is never mislinked, so a project that doesn't use Celery is unaffected.

  • codegraph_explore now follows Spring application events in Java. A publishEvent(new OrderShippedEvent(...)) call now links to every @EventListener that handles that event — usually in a different class — so "what reacts when this is published?" traces from the publisher straight into each listener method instead of dead-ending at publishEvent(...). The link is by event type, and all the common listener styles are recognized: a @EventListener typed on its parameter, the @EventListener(SomeEvent.class) form, @TransactionalEventListener, and the older implements ApplicationListener<SomeEvent>. One event fans out to all its listeners, and a plain Spring app with no event bus is unaffected.

  • codegraph_explore now follows MediatR request and notification dispatch in C#/.NET. A _mediator.Send(command) or _mediator.Publish(notification) call now links to the Handle method of the matching IRequestHandler<> / INotificationHandler<> — usually in a different file in a Clean Architecture layout — so "what handles this command?" traces from the controller straight into the handler instead of stopping at the mediator call. The sent type is recognized whether it's constructed inline (Send(new GetFooQuery())), built into a local first (var cmd = new …; Send(cmd)), or passed in as a parameter, and it's matched by type — so a MessagingCenter.Send(...) or a same-named DTO that isn't a request is never mislinked, and a project without MediatR is unaffected.

  • codegraph_explore now follows Sidekiq background-job dispatch in Ruby. A DestroyUserWorker.perform_async(id) (or .perform_in / .perform_at) call now links to that worker's perform method — usually in app/workers/ away from the controller or model that enqueues it — so "what runs in the background here?" traces from the enqueue straight into the job body. Both the modern include Sidekiq::Job and the older Sidekiq::Worker are recognized, namespaced workers resolve to the right class even when several share a name (e.g. Comments::NotifyWorker vs Articles::NotifyWorker), and Rails ActiveJob's perform_later — a different mechanism — is intentionally left alone.

  • codegraph_explore now follows Laravel events in PHP. An event(new OrderShipped($order)) call now links to every listener that handles it — each listener's handle() method, usually a separate app/Listeners/ class — so "what reacts to this event?" traces from the dispatch straight into the listener bodies. Listeners are found both ways Laravel registers them: by a typed handle(OrderShipped $event) (auto-discovery, including a handle(A|B $event) union that listens for two events) and by the protected $listen map in your EventServiceProvider (which also catches a listener whose handle() has no type-hint). One event fans out to all its listeners, and queued jobs — dispatched via ::dispatch() rather than event() — are correctly left out.

  • CodeGraph now understands Lombok-generated methods in Java. @Getter, @Setter, @Data, @Value, and @Builder generate getters, setters, builder(), equals/hashCode/toString, and the @Slf4j log field at compile time, so those methods never appear in the source — and a user.getName(), User.builder(), or log.info(...) call used to resolve to nothing, silently breaking call-chain analysis (the agent would conclude the method didn't exist and reconstruct it by hand). Those members are now indexed from the annotations and fields, so they appear in codegraph search and codegraph_explore/codegraph_node, and callers trace through them like any hand-written method. They're marked as Lombok-generated so they read as generated, not hand-written; a method you write yourself is never overridden, static fields get no accessor, and a class without Lombok is unaffected. Thanks @git87663849. (#912)

  • codegraph_explore now follows C and C++ function-pointer dispatch. C does polymorphism with function pointers: a struct carries a function-pointer field, concrete functions are registered into it through a table (static struct cmd commands[] = {{"add", cmd_add}, …}), a designated initializer (.handler = on_open), or an assignment, and the code dispatches indirectly (p->fn(argv)). None of that was visible to analysis — the indirect call resolved to nothing, so git's command runner looked like it called nothing and a vtable's implementations had no callers. CodeGraph now links the dispatch site to the registered handlers, keyed by the struct field, so "what runs when this dispatches?" traces from p->fn(...) into every function registered for that field. This covers the command-table idiom (git, redis) and the ops-struct/vtable idiom (curl's content-encoders, protocol handlers), including the case where a generic hook slot is reassigned from a registry (h->func = found->fn). It stays precise — distinct function-pointer fields don't cross-link, a plain data field is never treated as a dispatch, and a project without function-pointer dispatch is unaffected. (#932)

  • codegraph_explore now follows GoFrame route bindings in Go. GoFrame's standard router wires routes reflectively: the path and method live in a g.Meta struct tag on a request type (g.Meta `path:"/user/sign-in" method:"post"`), the controller method that serves it is matched by that request type, and the two are joined at runtime by group.Bind(...) — so there was no path string and no edge from a route to its handler, and "where is /user/sign-in handled?" or "where are the routes bound to controllers?" could only be answered by reading. CodeGraph now indexes each g.Meta route as a real route node and links it to the controller method whose signature takes that request type, so a route resolves to its handler structurally in one codegraph_explore call. The link is by request type, not method name — so it's correct even when the two differ (a DeptSearchReq served by a List method); it tells apart the many identical request types a large app defines one-per-module (cash.ListReq vs order.ListReq) by package, including cloned addon modules; and a route whose handler isn't present is left unlinked rather than guessed. (#747)

  • The MCP server now works in monorepos and multi-project setups. Before, if you started CodeGraph somewhere with no .codegraph/ of its own — most often a monorepo root where you only indexed individual services — the server exposed no tools at all, so your agent couldn't query CodeGraph even for the sub-projects that were indexed. Now the tools are always available: point a query at any indexed project with the projectPath argument (its path, or anywhere inside it) and CodeGraph answers from that project's index — for as many projects as you like in one session. It also means a project you index after the server started is picked up without restarting, where before the tools stayed hidden because the server only checked for an index once at launch. A project that genuinely has no index still cleanly tells your agent to use its built-in tools there (and that you can run codegraph init to enable it), so single-project use is unchanged. Thanks @MaiLunJiye. (#964)

  • The Claude front-load hook now finds your indexed sub-projects in a monorepo. The optional UserPromptSubmit hook that injects CodeGraph context for structural questions previously only looked for an index at or above your working directory — so if you opened the monorepo root but indexed individual packages (packages/api, services/auth), it found nothing and stayed silent exactly where it was most useful. It now also looks into sub-projects: a single indexed sub-project gets its context front-loaded automatically, and with several the hook front-loads the one your question names (and lists the rest so the agent can target them by projectPath). Single-project repos are unaffected, and the scan is bounded and skipped entirely outside a recognizable workspace root. (#964)

  • codegraph_explore now surfaces the right code in large multi-layer projects. When you ask a backend-flow question in a repo that pairs an API server with a big frontend that mirrors the same domain words — say an app/ admin UI sitting over an api/ server — the server-side file that genuinely matches several of your query's terms is no longer pushed out of the results by the larger, more interconnected frontend layer. A file corroborated by two or more distinct query terms is now kept in the answer even when a denser unrelated layer would otherwise crowd it out, so "how does X read items / handle the request" returns the service or handler that does the work instead of a wall of frontend views. Single-layer projects are unaffected; set CODEGRAPH_RANK_NO_MULTITERM=1 to revert to the previous ranking.

  • Impact and blast-radius analysis for TypeScript, JavaScript, Go, Python, Rust, Ruby, C, Java, C#, PHP, Scala, Kotlin, Swift, Dart, and Pascal/Delphi now understands the readers of a constant. When you change a file-scope, package-level, module-level, or class-level constant — a config object, a lookup table, a shared constant — the other symbols in that file that read it now show up as affected, where before they were invisible (impact only followed calls, imports, and inheritance, so a constant's consumers looked like "nothing depends on this"). This makes codegraph impact, and the impact trail in codegraph_explore/codegraph_node, catch the "change this table, break its readers" class of change. It's on by default and adds no nodes to your graph; bundled/minified files and ambiguously-shadowed names are skipped to keep results precise. Set CODEGRAPH_VALUE_REFS=0 to turn it off.

  • C file-scope constants and globals — static const scalars, pointer/array lookup tables, and shared mutable globals — are now recognized as symbols in their own right. They previously weren't extracted at all, so they never appeared in search or carried any dependents; now they show up in codegraph search and participate in impact analysis (see above), so changing a C lookup table surfaces the same-file functions that read it.

  • Java static final constants, C# const / static readonly constants, Scala object vals, and Kotlin top-level / object / companion object vals are now classified as constants rather than generic fields, so they participate in the constant-reader impact analysis above — change a public static final table, a const string, a Scala object Config { val Timeout = … }, or a Kotlin companion object { const val … } and the methods that read it now show up as affected. (Per-object Java final / C# readonly / Scala & Kotlin class instance properties are unchanged.) Kotlin constants were previously not indexed as their own symbols at all, so they now also appear in codegraph search.

  • Swift top-level lets and static let constants (including those namespaced in an enum/struct, the common Swift pattern) are now indexed as constants and participate in the constant-reader impact analysis above — change a static let defaultRetryLimit or an enum Constants { static let … } and the same-file code that reads it shows up as affected. Computed properties and per-instance lets are not treated as constants.

  • Dart top-level const/final and class static const/static final constants are now indexed as constants and participate in the constant-reader impact analysis above. Instance fields, vars, and locals are not treated as constants. (Generated Dart code with the standard .g.dart/.freezed.dart/.pb.dart suffixes is already skipped.)

  • You can now teach CodeGraph about custom file extensions. Drop a codegraph.json at your repo root with an extensions map — { "extensions": { ".dota_lua": "lua", ".tpl": "php" } } — and files with those extensions get indexed under the language you name, instead of being silently skipped because the extension wasn't one of the built-in defaults. It's opt-in and committed alongside your code so the whole team shares it, your mappings layer on top of the built-ins and win on conflict (you can even re-point a built-in, e.g. .h → cpp), and a typo'd language or a malformed config is warned about and skipped rather than breaking indexing. Projects without a codegraph.json behave exactly as before. (#906)

Fixes

  • codegraph index and codegraph init no longer crawl during the "Resolving refs" phase on large projects — most painfully ones that mix a big front-end and back-end, where the phase could stretch to many minutes. A package or module imported across hundreds or thousands of files (react, a shared UI package, Python logging / typing) was being treated as if every one of those import statements might be its definition, so the resolver compared each import against all the others — work that grows with the square of how widely a package is imported, which is why it blew up only on big, import-heavy repos. Imports now resolve straight to the definitions they actually point at, so those redundant comparisons are gone (reference resolution is dramatically faster on large repos), and the graph no longer accumulates the meaningless import-to-import links the old fallback created. (#915)
  • MCP tool results no longer show up as oversized headings in Markdown-rendering clients (such as the Claude Code VSCode extension). Results used Markdown headings (##/###) for things like the status summary, each search hit, and every file section in an exploration, so a normal query filled the transcript with large-font lines — worst with codegraph_search and codegraph_explore, where the noise grew with the number of results. Section headers are now bold labels, which render at normal text size while keeping the same structure. Terminal/CLI output is unchanged. (#778)
  • An MCP server pointed at a very large repository (tens of thousands of files) no longer hangs on the first tool call after a fresh start. On startup CodeGraph reconciles its index against the current files on disk, and on a huge repo that reconcile could run for minutes while blocking the very first request — long enough that the background server was sometimes force-restarted mid-scan, so the first query never came back at all. The reconcile now yields as it runs (keeping the server responsive instead of pinning it), and the first tool call waits only briefly for it before answering and letting the rest finish in the background — so you get a fast first response and the index still catches up. Set CODEGRAPH_CATCHUP_GATE_TIMEOUT_MS to tune how long that first call waits (default 3000ms), or =0 to always wait for the full reconcile. (#905)
  • codegraph install now wires up your agents and stops there — it no longer indexes the current directory. Building a project's graph is always the explicit codegraph init (or codegraph index), so you decide what gets indexed and when, and the steps are the same whether you installed globally or just for one project. This clears up the confusion where a project-local install silently indexed but a global one didn't, and where the docs and the tool disagreed about whether you still had to run init. (#826)
  • React components declared with forwardRef, memo, or styled-components / emotion (const Button = forwardRef(...), const Card = memo(...), const Box = styled.button\…`) are now recognized as components, so finding where they're used works. Before, they were indexed as plain constants, so codegraph callersand impact analysis reported "no callers found" even when the component was rendered across dozens of files — a dangerous false "safe to change" right before refactoring a shared component. Now every<Button/>` usage links back to the component, so callers and blast radius are complete. This is the standard shadcn/ui declaration style, so for typical React design systems the whole UI layer is no longer invisible to impact analysis. Thanks @Arlandaren for the report and @maxmilian for the root-cause. (#841)
  • React Router and Next.js routes defined in .tsx / .jsx files are now indexed. Routes written as JSX — <Route path="/users" element={<UsersPage/>}/>, createBrowserRouter([...]), and Next.js app//pages/ page files — were being skipped entirely (only routes that happened to live in plain .ts/.js were picked up), so "what renders at this path?" and the route → page-component link were missing for most React apps. Now those routes show up in codegraph search/codegraph_explore and connect to the component they render, just like the backend route → handler links on other frameworks.
  • codegraph sync (and the file-watcher auto-sync behind always-on / MCP use) no longer drops a function's callers when you edit the file that function lives in. Re-indexing a file after an edit — even a docstring-only change — was severing the calls / references edges coming from other, unchanged files (e.g. from pkg import mod; mod.fn() callers, or any cross-file reference), so codegraph callers / impact would abruptly report "no callers" for a function that's used throughout the codebase, until the next full re-index. Sync now preserves those incoming cross-file edges across the re-index, re-matching them to the symbol even when the edit shifted its line number. Most visible in large Python package trees, but it applies to every language. Thanks @JosefAschauer. (#899)
  • codegraph index now rebuilds the full graph from scratch, so it produces the same result as a fresh codegraph init instead of reporting "0 nodes, 0 edges" and looking like it wiped your index. Previously, re-running index on an unchanged project skipped every file (their contents hadn't changed) and showed an empty-looking summary; it now clears and re-indexes for an honest, complete rebuild every time. Use codegraph sync for fast incremental updates between full rebuilds. Thanks @Arc-univer. (#874)
  • The file watcher that auto-syncs the graph now fails cleanly when live watching can no longer be trusted, instead of looking healthy while the index quietly goes stale. If the operating system runs out of file-watch resources, or another process holds the write lock far longer than a normal save, CodeGraph now disables auto-sync once — with a single clear message telling you to run codegraph sync (or rely on the git sync hooks) to refresh — rather than retrying forever or repeating the same error on a loop. And while auto-sync is disabled, CodeGraph's tool responses (and codegraph status) now say so plainly, so your AI agent knows to read files directly instead of trusting a frozen index. This mostly matters for long-running MCP/daemon sessions, which could otherwise keep serving stale results while appearing to work. Thanks @thismilktea. (#876)
  • On Linux, hitting the kernel's inotify watch limit on a large project no longer silently leaves half the tree unwatched. CodeGraph now tells you once — naming the exact setting to raise (fs.inotify.max_user_watches, e.g. sudo sysctl fs.inotify.max_user_watches=1048576) — and keeps live-watching the directories it could register while codegraph sync (or the git sync hooks) covers the rest. (#876)
  • A long-running MCP server now notices when a git worktree gains its own index. Before, if the server (or shared daemon) first saw a worktree before you ran codegraph init in it — so the lookup walked up to the main checkout's index — it pinned that decision for its whole life: even after the worktree had its own .codegraph/, every query kept hitting the main checkout's index and every result carried a false "this index belongs to a different git working tree" warning, until you restarted the server. The CLI got it right but the MCP server didn't, and re-indexing didn't help. The server now re-checks which index a path belongs to on each call, so the worktree's own index is picked up — and the stale warning drops — without a restart. (#926)
  • A long-running MCP server now recovers when your index is deleted and rebuilt at the same path. If .codegraph/ was removed and recreated while the server held it open — most easily by recreating a git worktree at the same path, or rm-ing .codegraph/ and running codegraph init again — the server kept reading the old, deleted database file and served a frozen snapshot: renamed or removed symbols still showed as live, new ones were missing, and codegraph sync couldn't refresh it — only restarting the server fixed it. The server now detects that the database file was swapped out from under it and reopens the live one in place, so results stay correct without a restart. (On Linux and macOS; Windows doesn't allow deleting an open file, so it isn't affected.) (#925)
  • The MCP server now opens and auto-syncs a project that lives inside a folder an enclosing git repository ignores. Before, if the directory you indexed sat within a larger repo that gitignored it, the shared MCP daemon failed to open the project — its log repeated Failed to open project … path should be a path.relative() d string, but got "./" — so the file watcher never started and the index silently went stale until you ran codegraph sync by hand (setting CODEGRAPH_NO_DAEMON=1 was the only workaround). The daemon now opens the project and starts watching as expected. Most visible with Codex on Windows, but the cause wasn't platform-specific. (#936)
  • A git worktree of a submodule is no longer indexed as a duplicate copy of that submodule's code. CodeGraph already skips ordinary worktrees (a second working view of a repo it indexes), but a worktree created from a submodule — common in monorepos that check submodules out into worktrees for parallel feature work — was mistaken for a genuine embedded repo and swept in, duplicating every symbol it shared with the real submodule checkout (one report had ~28% of its index as duplicates, inflating both query results and the database). These submodule worktrees are now recognized and skipped, while the submodule's own checkout stays indexed as distinct code. Thanks @charlesxu2026-ship-it. (#945)
  • A C++ class or struct annotated with an export/visibility macro — class MYLIB_EXPORT Foo : public Bar { … }, the common DLL-export / visibility pattern in headers — is no longer mis-indexed as a function spanning the whole class body. Not knowing the macro is a macro, the parser read it as a type and the whole declaration as a function, so the class surfaced as a phantom function that showed up as a false caller in codegraph callers, codegraph impact, and blast-radius analysis, and skewed symbol counts. CodeGraph now recognizes this misparse and drops the bogus node. Thanks @spwlyzx. (#946)
  • codegraph status no longer reports phantom pending changes for files CodeGraph deliberately keeps out of the index — a tracked file inside a committed dependency dir (a checked-in vendor/ or node_modules/), or a tracked file under a .gitignored directory. A full index correctly excludes these, and codegraph sync never indexes them, but the fast change-detector behind codegraph status flagged every edit to such a file as "modified" (and a new one as "added") — so the pending-changes count never cleared no matter how many times you synced. Change detection now applies the same ignore rules the full index does, so status agrees with sync, and tools built on CodeGraph's change-detection API get the same corrected list. (#766)
  • Files reached through a symlinked directory that points outside your project now index instead of being silently skipped. When a folder in your repo is a symlink to a location outside the repo root — the standard layout for Dota 2 custom games and similar SDK-linked projects, where game/ and content/ link into the engine tree — CodeGraph followed the symlink to discover those files but then blocked every one of them while reading, logging Path traversal blocked in batch reader and indexing nothing under them. The reader now agrees with the directory scan and indexes those files. The guard against ../ path escapes is unchanged, and the protection that keeps your agent from being served file contents from outside the repo is also unchanged — only the indexer's own read path follows these in-repo symlinks. (#935)
