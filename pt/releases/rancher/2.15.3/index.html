Liberar v2.15.3

[!IMPORTANTE]

  • Se você estiver usando o AD FS (Serviço de Federação do Active Directory), a atualização para o Rancher v2.10.1 ou posterior poderá causar problemas de autenticação, exigindo intervenção manual. Esses problemas ocorrem porque a parte confiável Trust do AD FS não consegue obter um certificado de verificação de assinatura dos metadados. Para obter mais informações, consulte #48655. Esses problemas podem ser corrigidos por um dos dois métodos:

  • Atualizando as informações da Parte Confiante Trust dos metadados da federação (Parte Confiante Trust → Atualização dos Metadados da Federação…​).

  • Adicionar diretamente o certificado (Parte Confiável Trust → Propriedades → guia Assinatura → Adicionar → Selecionar o certificado).

Rancher v2.15.3 é o patch mais recente do Rancher. Este é um lançamento da versão comunitária que apresenta atualizações de manutenção e correções de bugs.

Para obter mais informações sobre novos recursos na versão secundária geral, consulte v2.15.0 release notes.

Correções de segurança para vulnerabilidades

Esta versão aborda os seguintes problemas de segurança:

Fazendeiro

  • Correção de uma vulnerabilidade de segurança no endpoint do metaproxy Rancher, onde a lista de permissões de destino era avaliada em um local que não impedia o encaminhamento de uma solicitação. Um usuário autenticado pode fazer com que o servidor Rancher envie solicitações a serviços internos que a lista de permissões pretende bloquear e receba as respostas. A lista de permissões agora é aplicada no manipulador de solicitações, que rejeita destinos não permitidos antes que qualquer conexão seja feita. Para obter mais informações, consulte CVE-2026-88809.
  • Corrigida uma vulnerabilidade de segurança na validação RBAC do Rancher onde o campo inheritedNamespacedRules de um GlobalRole não era verificado para escalonamento de privilégios. Um usuário com permissões delegadas para gerenciar funções globais e vinculações de funções globais poderia conceder permissões em clusters downstream que excediam as suas próprias. Os webhooks de admissão GlobalRole e GlobalRoleBinding agora validam este campo da mesma forma que os outros campos que carregam permissão. Para obter mais informações, consulte CVE-2026-88810.
  • Correção de uma vulnerabilidade de segurança no meta proxy do Rancher Manager, em que as próprias credenciais do Rancher do chamador não eram removidas de forma consistente das solicitações encaminhadas para hosts de provedores de nuvem de terceiros. A credencial de sessão de um usuário conectado poderia ser enviada a um provedor de nuvem durante o uso normal de visualizações de provisionamento, e um token Rancher de API client poderia ser enviado quando ele omitisse os cabeçalhos de seleção de credenciais do proxy. O proxy agora remove as credenciais do chamador em cada caminho de solicitação. Para obter mais informações, consulte CVE-2026-88811.
  • Corrigida uma vulnerabilidade de segurança no Rancher onde a verificação de autorização que protege o shell do cluster local não era aplicada a todas as rotas API que poderiam alcançá-lo. Qualquer usuário autenticado, incluindo aquele sem permissões no cluster local, poderia obter um shell pod sem privilégios no cluster de gerenciamento, quebrando o isolamento esperado do plano de gerenciamento. A verificação de autorização agora é aplicada de forma consistente para todos os formulários de solicitação. Para obter mais informações, consulte CVE-2026-104623.

Frota

  • Corrigida uma vulnerabilidade de escalonamento de privilégios no controlador de gerenciamento de agentes do Fleet, onde um objeto de cluster do Fleet criado por um usuário comum poderia fazer referência a credenciais administrativas para o cluster de gerenciamento do Rancher (local). Isso permitiu que um usuário autenticado contendo apenas a função global user padrão, sem permissões no cluster local, obtivesse cluster-admin no cluster de gerenciamento Rancher e, portanto, em todos os clusters gerenciados. O Fleet agora só aceita um segredo kubeconfig de outro namespace quando o segredo é rotulado para uso pelo namespace de referência e implanta agentes apenas no cluster de gerenciamento para seus próprios clusters de sistema. Para obter mais informações, consulte CVE-2026-94290.
  • Correção de uma vulnerabilidade de segurança no Fleet em que a identidade do cluster reivindicada durante o registro do cluster não estava vinculada ao token de registro usado para a solicitação. Um detentor de um token de registro de espaço de trabalho válido que conhecesse o identificador client de outro cluster poderia obter credenciais para o namespace de gerenciamento de frota desse cluster e interromper seu agente legítimo. O Fleet agora registra o token de registro com o qual um cluster está registrado e rejeita solicitações de registro que reivindicam a mesma identidade de cluster com um token diferente. Para obter mais informações, consulte CVE-2026-104615.

Para obter detalhes adicionais, consulte a página de Avisos de segurança e CVEs na documentação do Rancher ou no repositório do Rancher GitHub.

Quando uma variável de ambiente é removida, o Rancher agora limpa a origem e o valor do ambiente armazenado na inicialização. A configuração então reverte para seu valor padrão. Notas de instalação/atualização

Se você estiver instalando o Rancher pela primeira vez, seu ambiente deverá atender aos requisitos de instalação.

[!IMPORTANTE]

  • O Rancher agora exige que o cluster em que ele é executado tenha a Camada de agregação Kubernetes API habilitada. Isso ocorre porque o Rancher estende Kubernetes com APIs adicionais registrando seu próprio servidor de extensão API. Observe que todas as versões do Kubernetes suportadas nestas distribuições K8s das versões Rancher (RKE2/K3s) terão a camada de agregação configurada e habilitada por padrão.

  • Consulte a documentação do servidor de extensão API e #50400 para obter mais informações.

  • O motor Rancher Kubernetes (RKE/RKE1) atingiu o fim de sua vida útil em 31 de julho de 2025. As versões Rancher 2.12.0 e posteriores não suportam mais o provisionamento ou o gerenciamento de clusters RKE1 downstream. Recomendamos a replataforma de clusters RKE1 para RKE2 para garantir suporte contínuo e atualizações de segurança. Saiba mais sobre a transição aqui.

  • O Rancher agora tem uma verificação de validação de pré-atualização para recursos RKE1 que falha e lista os recursos RKE1, se presentes. Consulte #50286 para obter mais informações.

  • É crucial que você revise o espaço em disco disponível em seus nós e planeje adequadamente antes de atualizar para o Rancher v2.12.0 e posteriormente para evitar possíveis problemas de pressão de disco e de despejo de pod.

  • Para obter informações adicionais, consulte a documentação UI Server Side Pagination - Disk Space.

  • O Rancher agora tem uma opção de ativação chamada AUDIT_LOG_ENABLED para registros de auditoria API para uma instalação do Rancher.

  • Nas versões Rancher 2.11.x e anteriores, apenas o AUDIT_LEVEL poderia ser definido e o nível de log padrão (0) desabilitaria o log de auditoria. Nas versões Rancher 2.12.x e posteriores, o nível de log padrão (0) agora contém apenas a solicitação de log e os metadados de resposta e pode ser definido ao configurar AUDIT_LOG_ENABLED. Se estiver instalando ou atualizando via Helm, você pode ativar os logs de auditoria API e especificar o nível de log aplicando a seguinte configuração ao comando do Helm: --set auditLog.enabled=true --set auditLog.level=0. Consulte a documentação Ativando o log de auditoria API para registrar eventos do sistema e #48941.

Mudanças em artefatos de imagem

Os resumos de artefatos de imagem foram renomeados em Rancher v2.12.0, v2.11.4 e v2.10.8. Até essa mudança, arquivos de resumo de imagem separados para cada sistema operacional e arquitetura eram mantidos por motivos de compatibilidade. Com esta alteração, apenas um arquivo para cada sistema operacional deverá ser fornecido:

  • Os arquivos rancher-images-digests-linux-amd64.txt e rancher-images-digests-linux-arm64.txt devem ser renomeados para rancher-images-digests-linux.txt.

  • Os arquivos rancher-images-digests-windows-ltsc2019.txt e rancher-images-digests-windows-ltsc2022.txt devem ser renomeados para rancher-images-digests-windows.txt.

Requisitos de atualização

  • Criando backups: Crie um backup antes de atualizar o Rancher. Para reverter o Rancher após uma atualização, você deve primeiro fazer backup e restaurar o Rancher para a versão anterior do Rancher. Como o Rancher será restaurado para o mesmo estado de quando o backup foi criado, quaisquer alterações pós-atualização não serão incluídas após a restauração.

  • Requisitos da versão do Helm:

    • Para gerenciar o Rancher 2.12.x e posterior, você deve atualizar seu Helm client para a versão 3.18 ou mais recente.

    • Esta alteração é necessária para refletir a adição de suporte Kubernetes 1.33 nesta versão.

    • Atualmente, a Política de Suporte à Versão do Helm oficial determina que apenas o Helm 3.18 suporta o intervalo de versões Kubernetes adequado para o Rancher 2.12.

  • Requisitos CNI:

    • Para Kubernetes v1.19 e posterior, desative o firewalld, pois é incompatível com vários plug-ins CNI. Consulte #28840.

    • Ao atualizar ou instalar uma distribuição Linux que usa nf_tables como filtro de pacotes de back-end, como SLES 15, RHEL 8, Ubuntu 20.10, Debian 10 ou posterior, atualize para RKE v1.19.2 ou posterior para obter Flannel v0.13.0. Flanela v0.13.0 suporta nf_tables. Consulte Flanela #1317.

  • Requisitos para ambientes isolados:

    • Ao usar um proxy na frente de uma instância do Rancher sem ar, você deve passar parâmetros adicionais para NO_PROXY. Consulte a documentação e a edição #2725.

  • Ao instalar o Rancher com Docker em um ambiente air gap, você deve fornecer um arquivo registries.yaml customizado para o comando docker run, conforme mostrado na documentação do K3s. Se o registro tiver certificados, você também precisará fornecê-los. Consulte #28969.

rancher v2.15.3

Release v2.15.3

[!IMPORTANT]

  • If you are using Active Directory Federation Service (AD FS), upgrading to Rancher v2.10.1 or later may cause issues with authentication, requiring manual intervention. These issues are due to the AD FS Relying Party Trust not being able to pick up a signature verification certificate from the metadata. For more information, see #48655. These issues can be corrected by either of two methods:

    • Updating the Relying Party Trust information from federation metadata (Relying Party Trust → Update from Federation Metadata…​).

    • Directly adding the certificate (Relying Party Trust → Properties → Signature tab → Add → Select the certificate).

Rancher v2.15.3 is the latest patch release of Rancher. This is a Community version release that introduces maintenance updates and bug fixes.

For more information on new features in the general minor release, see the v2.15.0 release notes.

Security Fixes for Vulnerabilities

This release addresses the following security issues:

Rancher

  • Fixed a security vulnerability in the Rancher meta proxy endpoint where the destination allowlist was evaluated in a location that could not prevent a request from being forwarded. An authenticated user could cause the Rancher server to send requests to internal services that the allowlist is intended to block and receive the responses. The allowlist is now enforced in the request handler, which rejects disallowed destinations before any connection is made. For more information, see CVE-2026-88809.
  • Fixed a security vulnerability in Rancher's RBAC validation where the inheritedNamespacedRules field of a GlobalRole was not checked for privilege escalation. A user with delegated permissions to manage global roles and global role bindings could grant permissions in downstream clusters that exceeded their own. The GlobalRole and GlobalRoleBinding admission webhooks now validate this field in the same way as the other permission-carrying fields. For more information, refer to CVE-2026-88810.
  • Fixed a security vulnerability in the Rancher Manager meta proxy where the caller's own Rancher credentials were not consistently removed from requests forwarded to third-party cloud provider hosts. A signed-in user's session credential could be sent to a cloud provider during ordinary use of provisioning views, and an API client's Rancher token could be sent when it omitted the proxy's credential selection headers. The proxy now strips the caller's credentials on every request path. For more information, refer to CVE-2026-88811.
  • Fixed a security vulnerability in Rancher where the authorization check that protects the local cluster shell was not applied to every API route that could reach it. Any authenticated user, including one with no permissions on the local cluster, could obtain an unprivileged shell pod on the management cluster, breaking the expected isolation of the management plane. The authorization check is now enforced consistently for all request forms. For more information, see CVE-2026-104623.

Fleet

  • Fixed a privilege escalation vulnerability in Fleet's agent management controller, where a Fleet cluster object created by an ordinary user could reference administrative credentials for the Rancher management (local) cluster. This allowed an authenticated user holding only the default user global role, with no permissions on the local cluster, to gain cluster-admin on the Rancher management cluster and thereby on all managed clusters. Fleet now only accepts a kubeconfig secret from another namespace when the secret is labeled for use by the referencing namespace, and only deploys agents onto the management cluster for its own system clusters. For more information, refer to CVE-2026-94290.
  • Fixed a security vulnerability in Fleet where the cluster identity claimed during cluster registration was not bound to the registration token used for the request. A holder of a valid workspace registration token who knew another cluster's client identifier could obtain credentials for that cluster's Fleet management namespace and disrupt its legitimate agent. Fleet now records the registration token a cluster is registered with and rejects registration requests that claim the same cluster identity with a different token. For more information, refer to CVE-2026-104615.

For additional details, see the Security Advisories and CVEs page in Rancher's documentation or in Rancher's GitHub repository.

Rancher general

Major bug fixes

  • Fixed an issue where Rancher settings configured using environment variables retained stale values and the source: env attribute after the environment variable was removed. When an environment variable is removed, Rancher now clears the stored environment source and value on startup. The setting then reverts to its default value. See See #58075.

Cluster provisioning

Major bug fixes

  • Fixed an issue where imported clusters could become unavailable after upgrading Rancher if the cluster agent was redeployed before its registration token was migrated, leaving the agent with an empty token. See #58028.

  • Fixed an issue where provisioned clusters with S3 etcd snapshots could remain stuck during deletion. See #57506.

Install/Upgrade Notes

If you’re installing Rancher for the first time, your environment must fulfill the installation requirements.

[!IMPORTANT]

  • Rancher now requires the cluster it runs on to have the Kubernetes API Aggregation Layer enabled. This is because Rancher extends Kubernetes with additional APIs by registering its own extension API server. Please note that all versions of Kubernetes supported in this Rancher versions K8s distributions (RKE2/K3s) will have the aggregation layer configured and enabled by default.

    • Refer to the Extension API Server documentation and #50400 for more information.

  • Rancher Kubernetes Engine (RKE/RKE1) has reached end of life as of July 31, 2025. Rancher versions 2.12.0 and later no longer support provisioning or managing downstream RKE1 clusters. We recommend replatforming RKE1 clusters to RKE2 to ensure continued support and security updates. Learn more about the transition here.

    • Rancher now has a pre-upgrade validation check for RKE1 resources which fails and lists the RKE1 resources if present. Refer to #50286 for more information.

  • It is crucial that you review the available disk space on your nodes and plan accordingly before upgrading to Rancher v2.12.0 and later to avoid potential disk pressure and pod eviction issues.

    • For additional information, refer to the UI Server Side Pagination - Disk Space documentation.

  • Rancher now has an enablement option called AUDIT_LOG_ENABLED for API Audit Logs for a Rancher installation.

    • In Rancher versions 2.11.x and earlier, only the AUDIT_LEVEL could be set and the default log level (0) would disable the audit log. In Rancher versions 2.12.x and later, the default log level (0) now only contains the log request and response metadata, and can be set when configuring AUDIT_LOG_ENABLED. If installing or upgrading via Helm you can enable the API Audit Logs and specify the log level by applying the following setting to your Helm command: --set auditLog.enabled=true --set auditLog.level=0. See the Enabling the API Audit Log to Record System Events documentation and #48941.

Changes in Image Artifacts

Image artifact digests are renamed in Rancher v2.12.0, v2.11.4 and v2.10.8. Up until this change, separate image digests files for each operating system and architecture have been maintained for compatibility reasons. With this change, only one file for each operating system is to be provided:

  • The rancher-images-digests-linux-amd64.txt and rancher-images-digests-linux-arm64.txt files are to be renamed to rancher-images-digests-linux.txt.

  • The rancher-images-digests-windows-ltsc2019.txt and rancher-images-digests-windows-ltsc2022.txt files are to be renamed to rancher-images-digests-windows.txt.

Upgrade Requirements

  • Creating backups: Create a backup before you upgrade Rancher. To roll back Rancher after an upgrade, you must first back up and restore Rancher to the previous Rancher version. Because Rancher will be restored to the same state as when the backup was created, any changes post-upgrade will not be included after the restore.

  • Helm version requirements:

    • To manage Rancher 2.12.x and later, you must upgrade your Helm client to version 3.18 or newer.

    • This change is required to reflect the addition of Kubernetes 1.33 support with this release.

    • Currently, the official Helm Version Support Policy dictates that only Helm 3.18 supports the proper Kubernetes version range for Rancher 2.12.

  • CNI requirements:

    • For Kubernetes v1.19 and later, disable firewalld as it’s incompatible with various CNI plugins. See #28840.

    • When upgrading or installing a Linux distribution that uses nf_tables as the backend packet filter, such as SLES 15, RHEL 8, Ubuntu 20.10, Debian 10, or later, upgrade to RKE v1.19.2 or later to get Flannel v0.13.0. Flannel v0.13.0 supports nf_tables. See Flannel #1317.

  • Requirements for air-gapped environments:

    • When using a proxy in front of an air-gapped Rancher instance, you must pass additional parameters to NO_PROXY. See the documentation and issue #2725.

    • When installing Rancher with Docker in an air-gapped environment, you must supply a custom registries.yaml file to the docker run command, as shown in the K3s documentation. If the registry has certificates, then you’ll also need to supply those. See #28969.

In Rancher v2.6.0 and later, in the Apps & Marketplace UI, many Rancher Helm charts are named with a major version that starts with 100. This avoids simultaneous upstream changes and Rancher changes from causing conflicting version increments. This also complies with semantic versioning (SemVer), which is a requirement for Helm. You can see the upstream version number of a chart in the build metadata, for example: 100.0.0+up2.1.0. See #32294.

Long-standing Known Issues - Cluster Provisioning

  • Rancher v2.15.1:

    • Creating or editing v2prov clusters with native CAPI infrastructure providers from the UI can under some failure conditions leave unused infrastructure resources in the management cluster that must be cleaned up manually. See #55705.

  • Rancher v2.15.0:

    • Imported clusters cannot reconnect to Rancher if their registration token is rotated while they are disconnected and the grace period ends before they reconnect. The cluster agent logs 400 Bad Request with the response body cluster not found. As a workaround, re-run the registration command from the cluster Registration tab on the downstream cluster. To prevent the issue, increase the crt-default-grace-period-minutes setting to cover the expected downtime, or disable the crt-token-ttl-rotation feature flag. See #57078.

  • Not all cluster tools can be installed on a hardened cluster.

  • Rancher v2.8.1:

    • When you attempt to register a new etcd/controlplane node in a CAPR-managed cluster after a failed etcd snapshot restoration, the node can become stuck in a perpetual paused state, displaying the error message [ERROR] 000 received while downloading Rancher connection information. Sleeping for 5 seconds and trying again. As a workaround, you can unpause the cluster by running kubectl edit clusters.cluster clustername -n fleet-default and set spec.unpaused to false. See #43735.

Long-standing Known Issues - RKE2 Provisioning

  • Rancher v2.7.7:

    • Due to the backoff logic in various components, downstream provisioned K3s and RKE2 clusters may take longer to re-achieve Active status after a migration. If you see that a downstream cluster is still updating or in an error state immediately after a migration, please let it attempt to resolve itself. This might take up to an hour to complete. See #42834.

  • Rancher v2.7.6:

    • Provisioning RKE2/K3s clusters with added (not built-in) custom node drivers causes provisioning to fail. As a workaround, fix the added node drivers after activating. See #37074.

Long-standing Known Issues - K3s Provisioning

  • Rancher v2.7.6:

    • Provisioning RKE2/K3s clusters with added (not built-in) custom node drivers causes provisioning to fail. As a workaround, fix the added node drivers after activating. See #37074.

  • Rancher v2.7.2:

    • Clusters remain in an Updating state even when they contain nodes in an Error state. See #39164.

Long-standing Known Issues - Rancher App (Global UI)

  • Rancher v2.10.0:

    • After deleting a Namespace or Project in the Rancher UI, the Namespace or Project remains visible. As a workaround, refresh the page. See #12220.

  • Rancher v2.9.2:

    • Although system mode node pools must have at least one node, the Rancher UI allows a minimum node count of zero. Inputting a zero minimum node count through the UI can cause cluster creation to fail due to an invalid parameter error. To prevent this error from occurring, enter a minimum node count at least equal to the node count. See #11922.

  • Rancher v2.7.7:

    • When creating a cluster in the Rancher UI it does not allow the use of an underscore _ in the Cluster Name field. See #9416.

  • Rancher v2.6.4:

    • Deployment securityContext section is missing when a new workload is created. This prevents pods from starting when Pod Security Policy Support is enabled. See #4815.

Long-standing Known Issues - EKS

  • Rancher v2.7.0:

    • EKS clusters on Kubernetes v1.21 or below on Rancher v2.7 cannot be upgraded. See #39392.

Long-standing Known Issues - Authentication

  • Rancher v2.9.0:

    • There are some known issues with the OpenID Connect provider support:

      • When the generic OIDC auth provider is enabled, and you attempt to add auth provider users to a cluster or project, users are not populated in the dropdown search bar. This is expected behavior as the OIDC auth provider alone is not searchable. See #46104.

      • When the generic OIDC auth provider is enabled, auth provider users that are added to a cluster/project by their username are not able to access resources upon logging in. A user will only have access to resources upon login if the user is added by their userID. See #46105.

      • When the generic OIDC auth provider is enabled and an auth provider user in a nested group is logged into Rancher, the user will see the following error when they attempt to create a Project: projectroletemplatebindings.management.cattle.io is forbidden: User "u-gcxatwsnku" cannot create resource "projectroletemplatebindings" in API group "management.cattle.io" in the namespace "p-9t5pg". However, the project is still created. See #46106.

Long-standing Known Issues - Rancher Webhook

  • Rancher v2.7.2:

    • A webhook is installed in all downstream clusters. There are several issues that users may encounter with this functionality:

      • If you rollback from a version of Rancher v2.7.2 or later, to a Rancher version earlier than v2.7.2, the webhooks will remain in downstream clusters. Since the webhook is designed to be 1:1 compatible with specific versions of Rancher, this can cause unexpected behaviors to occur downstream. The Rancher team has developed a script which should be used after rollback is complete (meaning after a Rancher version earlier than v2.7.2 is running). This removes the webhook from affected downstream clusters. See #40816.

Long-standing Known Issues - Virtualization Management (Harvester)

  • Rancher v2.13.1:

    • When upgrading to Rancher v2.13.1 or higher while using Harvester v1.6.1, users may encounter an issue with their Load Balancers in downstream clusters using the Harvester Cloud Provider, and must perform the following workaround to instruct Calico to not use any of the IP/interface managed by kube-vip. See #9767.

  • Rancher v2.7.2:

    • If you’re using Rancher v2.7.2 with Harvester v1.1.1 clusters, you won’t be able to select the Harvester cloud provider when deploying or updating guest clusters. The Harvester release notes contain instructions on how to resolve this. See #3750.

Long-standing Known Issues - Backup/Restore

  • When migrating to a cluster with the Rancher Backup feature, the server-url cannot be changed to a different location. It must continue to use the same URL.

  • Rancher v2.13.0:

    • When performing a rollback from Rancher v2.13.0 to v2.12.3 using the backup and restore operator (BRO), the restore does not complete successfully. See #844. To work around this issue, you must scale down your Rancher deployment and uninstall the Webhook chart before performing the restore. For details, refer to this Knowledge Base article.

  • Rancher v2.7.7:

    • Due to the backoff logic in various components, downstream provisioned K3s and RKE2 clusters may take longer to re-achieve Active status after a migration. If you see that a downstream cluster is still updating or in an error state immediately after a migration, please let it attempt to resolve itself. This might take up to an hour to complete. See #42834.
