Destaques

Temos o prazer de anunciar o lançamento do PyTorch® 2.5! Esta versão apresenta um novo backend CuDNN para SDPA, permitindo acelerações por padrão para usuários de SDPA em H100s ou GPUs mais recentes. Além disso, a compilação regional de torch.compile oferece uma maneira de reduzir o tempo de inicialização a frio de torch.compile, permitindo que os usuários compilem um nn.Module repetido (por exemplo, uma camada de transformador em LLM) sem recompilações. Finalmente, o backend TorchInductor CPP oferece aceleração de desempenho sólida com inúmeras melhorias, como suporte FP16, wrapper CPP, modo AOT-Inductor e modo max-autotune. Esta versão é composta por 4.095 commits de 504 contribuidores desde PyTorch 2.4. Queremos agradecer sinceramente à nossa comunidade dedicada por suas contribuições. Como sempre, encorajamos você a experimentá-los e relatar quaisquer problemas à medida que melhoramos o 2.5. Mais informações sobre como começar a usar a série PyTorch 2 podem ser encontradas em nossa página Introdução. RECURSOS BETA

[Beta] Back-end CuDNN para SDPA

O backend cuDNN "Fused Flash Attention" foi lançado para torch.nn.functional.scaled_dot_product_attention. Nas GPUs NVIDIA H100, isso pode fornecer até 75% de aceleração em relação ao FlashAttentionV2. Essa aceleração é habilitada por padrão para todos os usuários de SDPA em GPUs H100 ou mais recentes.

[Beta] torch.compile compilação regional sem recompilações

Compilação regional sem recompilações, via torch._dynamo.config.inline_inbuilt_nn_modules cujo padrão é True em 2.5+. Esta opção permite aos usuários compilar um nn.Module repetido (por exemplo, uma camada de transformador em LLM) sem recompilações. Em comparação com a compilação do modelo completo, esta opção pode resultar em latências de compilação menores, com degradação de desempenho de 1% a 5% em comparação com a compilação do modelo completo. Veja o tutorial para mais informações.

[Beta] Otimização de back-end da CPU do TorchInductor

Este recurso avança a otimização de back-end da CPU do Inductor, incluindo geração de código de back-end CPP e fusões FX com kernels de CPU personalizados. O back-end da CPU do Inductor oferece suporte à vetorização de tipos de dados comuns e todas as operações do Inductor IR, junto com as formas estáticas e simbólicas. É compatível com os sistemas operacionais Linux e Windows e suporta o wrapper Python padrão, o wrapper CPP e o modo AOT-Inductor. Além disso, estende o modo max-autotune do modelo GEMM (prototipado em 2.5), oferecendo ganhos adicionais de desempenho. O back-end oferece suporte a várias fusões FX, chegando a kernels personalizados, como oneDNN para operações Linear/Conv e SDPA. O back-end da CPU Inductor atinge consistentemente aumentos de desempenho em três conjuntos de benchmark – TorchBench, Hugging Face e timms – superando o modo ansioso em 97.5% dos 193 modelos testados.

RECURSOS DO PROTÓTIPO

[Protótipo] FlexAttention

Introduzimos um API flexível que permite implementar vários mecanismos de atenção, como janela deslizante, máscara causal e PrefixLM com apenas algumas linhas de código PyTorch idiomático. Este API aproveita torch.compile para gerar um kernel FlashAttention fundido, que elimina a alocação extra de memória e atinge desempenho comparável a implementações manuscritas. Além disso, geramos automaticamente a passagem para trás usando o maquinário autograd do PyTorch. Além disso, nosso API pode tirar vantagem da dispersão na máscara de atenção, resultando em melhorias significativas em relação às implementações de atenção padrão. Para obter mais informações e exemplos, consulte a postagem oficial do blog e Attention Gym.

[Protótipo] Autograd compilado

O Autograd compilado é uma extensão da pilha PT2 que permite a captura de toda a passagem para trás. Ao contrário do gráfico reverso rastreado pelo despachante AOT, o rastreamento do Autograd Compilado é adiado até o tempo de execução regressiva, o que o torna impermeável às quebras do gráfico de passagem direta e permite registrar ganchos retroativos no gráfico. Consulte o tutorial para obter mais informações.

[Protótipo] Gravador de voo

O gravador de voo é uma nova ferramenta de depuração que ajuda a depurar trabalhos travados. A ferramenta funciona capturando continuamente informações sobre os coletivos enquanto eles funcionam. Ao detectar um trabalho travado, as informações podem ser usadas para identificar rapidamente classificações/máquinas com comportamento inadequado, juntamente com rastreamentos de pilha de código. Para obter mais informações, consulte o seguinte tutorial.

[Protótipo] Suporte Max-autotune na CPU com modelo GEMM

O modo Max-autotune para o back-end da CPU do Inductor em torch.compile traça o perfil de várias implementações de operações em tempo de compilação e seleciona a de melhor desempenho. Isto é particularmente benéfico para operações relacionadas ao GEMM, usando uma implementação GEMM baseada em modelo C++ como uma alternativa à abordagem baseada em ATen com bibliotecas oneDNN e MKL. Oferecemos suporte a FP32, BF16, FP16 e INT8 com fusões de epílogo para CPUs x86. Vimos uma aceleração de até 7% da média geográfica nos conjuntos de benchmark do dínamo e um aumento de até 20% na latência do próximo token para inferência LLM. Para mais informações consulte o tutorial.

[Protótipo] CPU TorchInductor no Windows

O back-end da CPU do indutor em torch.compile agora funciona no Windows. Atualmente, oferecemos suporte a MSVC (cl), clang (clang-cl) e compilador Intel (icx-cl) para indutor do Windows. Veja o tutorial para mais detalhes.

[Protótipo] Suporte FP16 no caminho da CPU para modo ansioso e back-end TorchInductor CPP

Float16 é um tipo de ponto flutuante reduzido comumente usado para melhoria de desempenho em inferência/treinamento de redes neurais. Desde esta versão, float16 para ansioso e TorchInductor é suportado no caminho da CPU.

[Protótipo] Extensão de dispositivo de carregamento automático

PyTorch agora oferece suporte ao carregamento automático para extensões de dispositivos fora da árvore, simplificando a integração ao eliminar a necessidade de importações manuais. Esse recurso, habilitado por meio do ponto de entrada torch.backends, simplifica o uso, garantindo o carregamento contínuo da extensão, ao mesmo tempo que permite que os usuários o desativem por meio de uma variável de ambiente, se necessário. Veja o tutorial para mais informações.

[Protótipo] Suporte aprimorado à GPU Intel

O aprimoramento do suporte às GPUs Intel agora está disponível para GPUs Intel® Data Center GPU Max Series e Intel® Client (processadores Intel® Core™ Ultra com gráficos Intel® Arc™ integrados e gráficos Intel® Arc™ para peças dGPU), o que facilita a aceleração de seus fluxos de trabalho de aprendizado de máquina em GPUs Intel na versão PyTorch 2.5. Também habilitamos o suporte inicial de PyTorch no Windows para GPUs Intel® Client nesta versão.

  • Matriz de suporte de back-end de hardware PyTorch expandida para incluir GPUs Intel Data Center e Client.  
  • A implementação de kernels SYCL* para aprimorar a cobertura e execução de operadores Aten em GPUs Intel para aumentar o desempenho no modo ansioso PyTorch.
  • Back-end aprimorado da GPU Intel do torch.compile para melhorar o desempenho de inferência e treinamento para uma ampla variedade de cargas de trabalho de aprendizado profundo.
    Esses recursos estão disponíveis por meio da visualização do PyTorch e das rodas PIP binárias noturnas. Para obter mais informações sobre o suporte à GPU Intel, consulte a documentação.

    # No basic option is passed in when creating a instance of ProcessGroup
pg: ProcessGroup = ProcessGroup(store, rank, group_size)
pg._set_default_backend(Backend.backend_type_map[backend])
# Users then need to create a backend option to create the comm backend (e.g., ProcessGroupNCCL)

  store, rank, group_size, pg_options

ONNX

As opções para torch.onnx.export (exceto os três primeiros argumentos) agora são apenas palavras-chave (#131501)

As opções podem ser fornecidas por palavras-chave apenas para permitir futuras adições e evolução do torch.onnx.export API. Exemplo:
Versão 2.4

torch.onnx.export(model, input, f, True, False)

Versão 2.5:

torch.onnx.export(model, input, f, export_params=True, verbose=False)

API torch.onnx._export interno obsoleto foi removido (133824)

torch.onnx._export é um API interno que não se destina ao consumo público. Use o torch.onnx.export público. Exemplo:
Versão 2.4

torch.onnx._export(...)

Versão 2.5:

torch.onnx.export(...)

A opção op_level_debug do torch.onnx.ExportOptions foi removida (#134961)

Esta opção, concebida para identificar discrepâncias entre operadores, revelou-se pouco fiável e foi eliminada. Em vez disso, use a opção torch.onnx.export(..., report=True, verify=True) para validar os modelos exportados.

A classe ONNXProgramSerializer foi removida (#135261)

O modelo ONNX em torch.onnx.ONNXProgram agora é mantido e serializado por ONNX IR.
Os formatos textproto, onnxtext e json são suportados por padrão ao chamar ONNXProgram.save() com uma extensão de arquivo correspondente.

A classe SymbolicContext foi removida (#132184)

A classe obsoleta torch.onnx.SymbolicContext foi removida. Funções simbólicas personalizadas (não dínamo) não podem mais usar ctx: torch.onnx.SymbolicContext como primeiro argumento.

O suporte para caffe2 foi removido (#129021)

  • Remova o manuseio do Caffe2 do onnx_unpack_quantized_weights (#129021)
  • Remover is_caffe2_aten_fallback em torch.onnx.symbolic_helper

Algumas classes de erros foram removidas

CheckerError e InvalidExportOptionsError são removidos. Os usuários sempre podem capturar RuntimeError para lidar com erros de exportação torch.onnx.

ONNX

O fornecimento de argumentos de palavra-chave do modelo para torch.onnx.export está obsoleto (#131501)

A capacidade de fornecer argumentos de palavras-chave do modelo como um dicionário final está obsoleta. Os usuários devem usar o parâmetro kwargs. Obsoleto:

torch.onnx.export(model, (arg1, arg2, {“kwarg1”: …}))

Futuro:

torch.onnx.export(model, (arg1, arg2), kwargs={“kwarg1”: …})

torch.onnx.OperatorExportTypes está obsoleto (#131501)

A capacidade de fornecer operator_export_type em torch.onnx.export() está obsoleta. Os gráficos ONNX exportados sempre usarão o domínio opset ONNX. As opções ONNX_FALLTHROUGH, ONNX_ATEN e ONNX_ATEN_FALLBACK não são mais suportadas. A classe OperatorExportTypes será removida em uma versão futura.

A opção training em torch.onnx.export está obsoleta

Defina o modo de treinamento do modelo antes de exportar. Obsoleto:

torch.onnx.export(model, inputs, path, training=torch.onnx.TrainingMode.EVAL)

Futuro:

model = model.eval()  
torch.onnx.export(model, inputs, path)

ONNX

A opção dynamo=True e nova lógica de exportação (#132530, #133743, #134304, #134782, #135378, #135399, #135786, #136162, #135134, #134976, #135367, #135418, #135591, #135520)

Apresentamos a opção dynamo=True no torch.onnx.export(). Isto é recomendado como um substituto para torch.onnx.dynamo_export começando em PyTorch 2.5. Versão 2.5:

onnx_program = torch.onnx.export(model, inputs, kwargs=kwargs, dynamo=True)  
# Use the external_data option to save weights as external data  
onnx_program.save(“model.onnx”, external_data=True)  
# To save without initializers  
onnx_program.save(“model.onnx”, include_initializers=False, keep_initializers_as_inputs=True)

torch.onnx.export(model, args, dynamo=True, report=True, verify=True) aproveita torch.export e ONNX IR para converter ExportedPrograms capturados em ONNX de forma eficiente e robusta. Este novo processo reduz o consumo de memória pela metade em comparação com dynamo_export no 2.4, preservando ao mesmo tempo o rico formato do tensor e informações de rastreamento de pilha no gráfico ONNX. Você pode aproveitar a opção report=True para obter um relatório de conversão em formato markdown para diagnosticar quaisquer problemas de conversão. Configure verify=True para verificar numericamente o modelo ONNX com ONNX Runtime. Ao usar external_data=True para salvar pesos de modelo como dados externos no arquivo .onnx, pesos maiores que 1 MB agora são alinhados em endereços de 64 KB. Isso permite que os tempos de execução mapeiem os pesos da memória para melhor eficiência da memória durante a inferência.

[NOTA]
A opção dynamo=True atualmente oferece suporte apenas ao opset 18 do ONNX. Versões futuras expandirão o suporte para opsets mais recentes. [NOTA]
A opção dynamo=True requer as versões mais recentes dos pacotes onnxscript e onnx.

Highlights

We are excited to announce the release of PyTorch® 2.5! This release features a new CuDNN backend for SDPA, enabling speedups by default for users of SDPA on H100s or newer GPUs. As well, regional compilation of torch.compile offers a way to reduce the cold start up time for torch.compile by allowing users to compile a repeated nn.Module (e.g. a transformer layer in LLM) without recompilations. Finally, TorchInductor CPP backend offers solid performance speedup with numerous enhancements like FP16 support, CPP wrapper, AOT-Inductor mode, and max-autotune mode. This release is composed of 4095 commits from 504 contributors since PyTorch 2.4. We want to sincerely thank our dedicated community for your contributions. As always, we encourage you to try these out and report any issues as we improve 2.5. More information about how to get started with the PyTorch 2-series can be found at our Getting Started page. As well, please check out our new ecosystem projects releases with TorchRec and TorchFix.

BETA FEATURES

[Beta] CuDNN backend for SDPA

The cuDNN "Fused Flash Attention" backend was landed for torch.nn.functional.scaled_dot_product_attention. On NVIDIA H100 GPUs this can provide up to 75% speed-up over FlashAttentionV2. This speedup is enabled by default for all users of SDPA on H100 or newer GPUs.

[Beta] torch.compile regional compilation without recompilations

Regional compilation without recompilations, via torch._dynamo.config.inline_inbuilt_nn_modules which default to True in 2.5+. This option allows users to compile a repeated nn.Module (e.g. a transformer layer in LLM) without recompilations. Compared to compiling the full model, this option can result in smaller compilation latencies with 1%-5% performance degradation compared to full model compilation.

See the tutorial for more information.

[Beta] TorchInductor CPU backend optimization

This feature advances Inductor’s CPU backend optimization, including CPP backend code generation and FX fusions with customized CPU kernels. The Inductor CPU backend supports vectorization of common data types and all Inductor IR operations, along with the static and symbolic shapes. It is compatible with both Linux and Windows OS and supports the default Python wrapper, the CPP wrapper, and AOT-Inductor mode.

Additionally, it extends the max-autotune mode of the GEMM template (prototyped in 2.5), offering further performance gains. The backend supports various FX fusions, lowering to customized kernels such as oneDNN for Linear/Conv operations and SDPA. The Inductor CPU backend consistently achieves performance speedups across three benchmark suites—TorchBench, Hugging Face, and timms—outperforming eager mode in 97.5% of the 193 models tested.

PROTOTYPE FEATURES

[Prototype] FlexAttention

We've introduced a flexible API that enables implementing various attention mechanisms such as Sliding Window, Causal Mask, and PrefixLM with just a few lines of idiomatic PyTorch code. This API leverages torch.compile to generate a fused FlashAttention kernel, which eliminates extra memory allocation and achieves performance comparable to handwritten implementations. Additionally, we automatically generate the backwards pass using PyTorch's autograd machinery. Furthermore, our API can take advantage of sparsity in the attention mask, resulting in significant improvements over standard attention implementations.

For more information and examples, please refer to the official blog post and Attention Gym.

[Prototype] Compiled Autograd

Compiled Autograd is an extension to the PT2 stack allowing the capture of the entire backward pass. Unlike the backward graph traced by AOT dispatcher, Compiled Autograd tracing is deferred until backward execution time, which makes it impervious to forward pass graph breaks, and allows it to record backward hooks into the graph.

Please refer to the tutorial for more information.

[Prototype] Flight Recorder

Flight recorder is a new debugging tool that helps debug stuck jobs. The tool works by continuously capturing information about collectives as they run. Upon detecting a stuck job, the information can be used to quickly identify misbehaving ranks/machines along with code stack traces.

For more information please refer to the following tutorial.

[Prototype] Max-autotune Support on CPU with GEMM Template

Max-autotune mode for the Inductor CPU backend in torch.compile profiles multiple implementations of operations at compile time and selects the best-performing one. This is particularly beneficial for GEMM-related operations, using a C++ template-based GEMM implementation as an alternative to the ATen-based approach with oneDNN and MKL libraries. We support FP32, BF16, FP16, and INT8 with epilogue fusions for x86 CPUs. We’ve seen up to 7% geomean speedup on the dynamo benchmark suites and up to 20% boost in next-token latency for LLM inference.

For more information please refer to the tutorial.

[Prototype] TorchInductor CPU on Windows

Inductor CPU backend in torch.compile now works on Windows. We support MSVC (cl), clang (clang-cl) and Intel compiler (icx-cl) for Windows inductor currently.

See the tutorial for more details.

[Prototype] FP16 support on CPU path for both eager mode and TorchInductor CPP backend

Float16 is a commonly used reduced floating point type for performance improvement in neural network inference/training. Since this release, float16 for both eager and TorchInductor is supported on the CPU path.

[Prototype] Autoload Device Extension

PyTorch now supports autoloading for out-of-tree device extensions, streamlining integration by eliminating the need for manual imports. This feature, enabled through the torch.backends entrypoint, simplifies usage by ensuring seamless extension loading, while allowing users to disable it via an environment variable if needed.

See the tutorial for more information.

[Prototype] Enhanced Intel GPU support

Intel GPUs support enhancement is now available for both Intel® Data Center GPU Max Series and Intel® Client GPUs (Intel® Core™ Ultra processors with built-in Intel® Arc™ graphics and Intel® Arc™ Graphics for dGPU parts), which is to make it easier to accelerate your Machine Learning workflows on Intel GPUs in PyTorch 2.5 release. We also enabled the initial support of PyTorch on Windows for Intel® Client GPUs in this release.

  • Expanded PyTorch hardware backend support matrix to include both Intel Data Center and Client GPUs.  
  • The implementation of SYCL* kernels to enhance coverage and execution of Aten operators on Intel GPUs to boost performance in PyTorch eager mode.
  • Enhanced Intel GPU backend of torch.compile to improve inference and training performance for a wide range of deep learning workloads.

These features are available through PyTorch preview and nightly binary PIP wheels. For more information regarding Intel GPU support, please refer to documentation.

ONNX

The dynamo=True option and new export logic (#132530, #133743, #134304, #134782, #135378, #135399, #135786, #136162, #135134, #134976, #135367, #135418, #135591, #135520)

We introduce the dynamo=True option in torch.onnx.export(). This is recommended as a replacement for torch.onnx.dynamo_export starting in PyTorch 2.5.

Version 2.5:

onnx_program = torch.onnx.export(model, inputs, kwargs=kwargs, dynamo=True)  
# Use the external_data option to save weights as external data  
onnx_program.save(“model.onnx”, external_data=True)  
# To save without initializers  
onnx_program.save(“model.onnx”, include_initializers=False, keep_initializers_as_inputs=True)

torch.onnx.export(model, args, dynamo=True, report=True, verify=True) leverages torch.export and ONNX IR to convert captured ExportedPrograms to ONNX efficiently and robustly. This new process reduces memory consumption by half compared to dynamo_export in 2.4, while preserving rich tensor shape and stack trace information in the ONNX graph. You can leverage the report=True option to obtain a conversion report in markdown format to diagnose any conversion issues. Set verify=True to verify the ONNX model numerically with ONNX Runtime.

When using external_data=True to save model weights as external data to the .onnx file, weights larger than 1 MB are now aligned at 64 KB addresses. This allows runtimes to memory-map weights for better memory efficiency during inference.

[NOTE]
The dynamo=True option currently supports only ONNX opset 18. Future releases will expand support to newer opsets.

[NOTE]
The dynamo=True option requires the latest versions of onnxscript and onnx packages.

  • The issue Avoid OpOverloadPacket.__getattr__ calls in inductor lowering resolves inefficiencies caused by excessive calls to __getattr__ during inductor lowering. By avoiding these calls, the patch prevents unnecessary exceptions that slow down compilation, improving overall performance. (#131348)
  • The issue Always realize sigmoid for CPU modifies the inductor backend to ensure that sigmoid is realized in CPU operations, similar to how exp is handled. This update improves performance by preventing repeated computation of exp in nested loops during inference tasks, particularly for models like LLaMA2. (#128339)
  • The issue bf16/fp16 gemm template computed with fp32 reintroduces the GEMM template for mixed-precision computation, allowing bf16 and fp16 values to be computed using fp32 precision in PyTorch's inductor backend. This enhances accuracy and stability for matrix multiplications involving lower precision data types. (#128472)
