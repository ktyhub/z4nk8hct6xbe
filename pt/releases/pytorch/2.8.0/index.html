### Um erro agora é gerado corretamente para a variante out de `tensordot` quando chamado com um tensor `requires_grad=True` (#150270)

## tocha.compile
### Especialização de uma forma de tensor com `mark_dynamic` aplicado agora com erros corretos (#152661)
Antes do 2.8, era possível que uma proteção com formato simbólico fosse incorretamente
omitido se a avaliação da forma simbólica foi previamente testada com guardas
suprimido (isso geralmente acontece dentro do próprio compilador). Isso foi corrigido
no 2.8 e normalmente apenas "faz a coisa certa" silenciosamente e adiciona o correto
guarda. No entanto, se a nova guarda fizer com que um tensor marcado com `mark_dynamic` se torne
especializado, isso pode resultar em erro. Uma solução alternativa é usar
`maybe_mark_dynamic` em vez de `mark_dynamic`.
Veja a discussão na edição #157921 para mais
contexto.
Versão 2.7.0
```python
import torch

embed = torch.randn(2, 8192)
x = torch.zeros(8192)

torch._dynamo.mark_dynamic(x, 0)

@torch.compile
def f(embedding_indices, x):
    added_tokens_mask = torch.where(x > 10000, 1, 0)
    ei = torch.narrow(embedding_indices, 1, 0, x.size(0))
    return ei.clone()

f(embed, x)

Versão 2.8.0

import torch

embed = torch.randn(2, 8192)
x = torch.zeros(8192)

torch._dynamo.maybe_mark_dynamic(x, 0)

@torch.compile
def f(embedding_indices, x):
    added_tokens_mask = torch.where(x > 10000, 1, 0)
    ei = torch.narrow(embedding_indices, 1, 0, x.size(0))
    return ei.clone()

f(embed, x)

Adicionada uma verificação de alias/mutação mais rigorosa para HigherOrderOperators (por exemplo, cond), que irá gerar erros explicitamente se o alias/mutação entre entradas e saídas não for suportado (#148953, #146658).

Para HigherOrderOperators afetados, adicione .clone() às saídas com alias para resolver isso. Versão 2.7.0

Construir front-end

Removido o include torch/types.h do Dispatcher.h (#149557)

Isso pode causar erros de construção no código C++ que depende implicitamente deste include (por exemplo, versões muito antigas do torchvision). Observe que Dispatcher.h não pertence como um include de torch/types.h e só estava presente como um hack de curto prazo para apaziguar torchvision. Se você encontrar erros de compilação do torchvision, por favor atualize para uma versão mais recente do torchvision para resolver isso.

O código NVTX3 foi movido de cmake/public/cuda.cmake para cmake/Dependencies.cmake (#151583)

Esta é uma mudança decisiva no BC para a interface do sistema de compilação. Projetos downstream que anteriormente obtiveram NVTX3 por meio de cmake/public/cuda.cmake (ou seja, chamando find_package(TORCH REQUIRED)) agora precisará configurar explicitamente o suporte NVTX3 na própria biblioteca (ou seja, usar USE_SYSTEM_NVTX=1). A mudança é para corrigir o comportamento interrompido onde os projetos downstream não conseguiam encontrar o NVTX3 devido à incompatibilidade do PROJECT_SOURCE_DIR. Versão 2.7.0:

  • Um projeto downstream usando -DUSE_SYSTEM_NVTX seria capaz de encontrar NVTX3 e torch::nvtx3 por meio da lógica cmake/public/cuda.cmake do PyTorch.
  • Um projeto downstream que NÃO usa -DUSE_SYSTEM_NVTX encontraria erros de construção com CUDA 12.8 ou superior. Versão 2.8.0:
  • Um projeto downstream usando -DUSE_SYSTEM_NVTX não será capaz de encontrar NVTX3 ou torch::nvtx3 por meio do cmake/public/cuda.cmake do PyTorch. O projeto downstream agora precisa encontrar explicitamente NVTX3 e torch::nvtx3 implementando a mesma lógica no cmake/Dependences.cmake do PyTorch.
  • Um projeto downstream que NÃO usa -DUSE_SYSTEM_NVTX continuará a construção sem NVTX, a menos que outra parte do processo de construção reative o NVTX.

Depreciações

O suporte MPS para MacOS Ventura será removido no 2.9

PyTorch 2.8 é a última versão que oferecerá suporte à aceleração de GPU no MacOS Ventura. No próximo versão (2.9), MacOS Sonoma (lançado em setembro de 2023) ou superior será necessário para usar o MPS back-end.

torch.ao.quantization está obsoleto e será removido em 2.10 (#153892)

Para migrar:

  • Quantização no modo ansioso (torch.ao.quantization.quantize, torch.ao.quantization.quantize_dynamic)
    • Quantização apenas de peso e dinâmica: use o modo ansioso torchao quantize_.
    • Quantização estática: use a quantização torchao PT2E.
  • Quantização em modo gráfico FX (torch.ao.quantization.quantize_fx.prepare_fx, torch.ao.quantization.quantize_fx.convert_fx): use quantização torchao PT2E (torchao.quantization.quantize_pt2e.prepare_pt2e, torchao.quantization.quantize_pt2e.convert_pt2e). Observe que a quantização PT2E foi migrada para torchao (https://github.com/pytorch/ao/tree/main/torchao/quantization/pt2e). Consulte https://github.com/pytorch/ao/issues/2259 e https://docs.pytorch.org/ao/main/quick_start.html#pytorch-2-export-quantization para obter mais detalhes.

A opção dynamo=False (padrão atual) para torch.onnx.export está obsoleta (#152478, #155580)

O padrão será dynamo=True começando em PyTorch 2.9. Recomendamos que você migre para usar a opção dynamo=True no torch.onnx.export. Este sinalizador torna torch.export.export o caminho de exportação padrão, substituindo TorchScript. Para manter o comportamento antigo, defina dynamo=False explicitamente. Recomendamos que você também experimente a opção fallback=True, que fará com que o exportador retorne ao caminho dynamo=False se houver erros.

Tracked Regressions

Windows wheel builds with CUDA 12.9.1 stack overflow during build (#156181)

Due to a bug introduced in CUDA 12.9.1, we are unable to complete full Windows wheel builds with this version, as compilation of torch.segment_reduce() crashes the build. Thus, we provide a wheel without torch.segment_reduce() included in order to sidestep the issue. If you need support for torch.segment_reduce(), please utilize a different version.

Backwards Incompatible Changes

CUDA Support

Removed support for Maxwell and Pascal architectures with CUDA 12.8 and 12.9 builds (#157517, #158478, #158744)

Due to binary size limitations, support for sm50 - sm60 architectures with CUDA 12.8 and 12.9 has been dropped for the 2.8.0 release. If you need support for these architectures, please utilize CUDA 12.6 instead.

torch.compile

Specialization of a tensor shape with mark_dynamic applied now correctly errors (#152661)

Prior to 2.8, it was possible for a guard on a symbolic shape to be incorrectly omitted if the symbolic shape evaluation was previously tested with guards suppressed (this often happens within the compiler itself). This has been fixed in 2.8 and usually will just silently "do the right thing" and add the correct guard. However, if the new guard causes a tensor marked with mark_dynamic to become specialized, this can result in an error. One workaround is to use maybe_mark_dynamic instead of mark_dynamic.

See the discussion in issue #157921 for more context.

Version 2.7.0

import torch

embed = torch.randn(2, 8192)
x = torch.zeros(8192)

torch._dynamo.mark_dynamic(x, 0)

@torch.compile
def f(embedding_indices, x):
    added_tokens_mask = torch.where(x > 10000, 1, 0)
    ei = torch.narrow(embedding_indices, 1, 0, x.size(0))
    return ei.clone()

f(embed, x)

Version 2.8.0

import torch

embed = torch.randn(2, 8192)
x = torch.zeros(8192)

torch._dynamo.maybe_mark_dynamic(x, 0)

@torch.compile
def f(embedding_indices, x):
    added_tokens_mask = torch.where(x > 10000, 1, 0)
    ei = torch.narrow(embedding_indices, 1, 0, x.size(0))
    return ei.clone()

f(embed, x)

NVTX3 code has been moved from cmake/public/cuda.cmake to cmake/Dependencies.cmake (#151583)

This is a BC-breaking change for the build system interface. Downstream projects that previously got NVTX3 through cmake/public/cuda.cmake (i.e.. calling find_package(TORCH REQUIRED)) will now need to explicitly configure NVTX3 support in the library itself (i.e. use USE_SYSTEM_NVTX=1). The change is to fix the broken behavior where downstream projects couldn't find NVTX3 anyway due to the PROJECT_SOURCE_DIR mismatch.

Version 2.7.0:

  • A downstream project using -DUSE_SYSTEM_NVTX would be able to find NVTX3 and torch::nvtx3 via PyTorch's cmake/public/cuda.cmake logic.
  • A downstream project NOT using -DUSE_SYSTEM_NVTX would encounter build errors with CUDA 12.8 or above.

Version 2.8.0:

  • A downstream project using -DUSE_SYSTEM_NVTX will not be able to find NVTX3 or torch::nvtx3 via PyTorch's cmake/public/cuda.cmake. The downstream project now needs to explicitly find NVTX3 and torch::nvtx3 by implementing the same logic in PyTorch's cmake/Dependences.cmake.
  • A downstream project NOT using -DUSE_SYSTEM_NVTX will proceed building without NVTX unless another part of the build process re-enables NVTX.
