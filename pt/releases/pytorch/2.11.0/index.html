## Interface Python
### `torch.hub.list()`, `torch.hub.load()` e `torch.hub.help()` agora padronizam o parâmetro `trust_repo` para `"check"` em vez de `None`. A opção `trust_repo=None` foi removida. (#174101)
Anteriormente, passar `trust_repo=None` (ou confiar no padrão) baixaria e executaria silenciosamente o código dos repositórios untrusted com apenas um aviso. Agora, o comportamento padrão do `"check"` solicitará ao usuário uma confirmação explícita antes de executar o código de repositórios que não estão na lista trusted.
Os usuários que passaram explicitamente por `trust_repo=None` devem atualizar seu código. Os usuários que já passaram por `trust_repo=True`, `trust_repo=False` ou `trust_repo="check"` não serão afetados.
Versão 2.10:
```python
# Default trust_repo=None — downloads with a warning
torch.hub.load("user/repo", "model")
# Explicit None — same behavior
torch.hub.load("user/repo", "model", trust_repo=None)

Versão 2.11:

# Default trust_repo="check" — prompts for confirmation if repo is not trusted
torch.hub.load("user/repo", "model")
# To skip the prompt, explicitly trust the repo
torch.hub.load("user/repo", "model", trust_repo=True)

tocha.nn

Adicionado suporte a janela deslizante para varlen_attn via window_size, tornando argumentos opcionais somente palavras-chave (#172238)

A assinatura de torch.nn.attention.varlen_attn mudou: um * (separador somente de palavras-chave) foi inserido antes dos argumentos opcionais. Anteriormente, argumentos opcionais como is_causal, return_aux e scale podiam ser passados ​​posicionalmente; eles agora devem ser passados ​​como argumentos de palavras-chave. Um novo argumento de palavra-chave window_size também foi adicionado.

# Before (2.10)
output = varlen_attn(query, key, value, cu_seq_q, cu_seq_k, max_q, max_k, True, None, 1.0)

# After (2.11) — pass as keyword argument
output = varlen_attn(query, key, value, cu_seq_q, cu_seq_k, max_q, max_k, window_size=(-1, 0), return_aux=None, scale=1.0)

Remover sinalizador is_causal de varlen_attn (#172245)

O parâmetro is_causal foi removido do torch.nn.attention.varlen_attn. A atenção causal agora é expressa através do parâmetro window_size: use window_size=(-1, 0) para mascaramento causal ou window_size=(W, 0) para atenção causal com uma janela deslizante de tamanho W. O padrão window_size=(-1, -1) corresponde à atenção total (não causal).

# Before (2.10)
output = varlen_attn(query, key, value, cu_seq_q, cu_seq_k, max_q, max_k, is_causal=True)

# After (2.11) — use window_size instead
output = varlen_attn(query, key, value, cu_seq_q, cu_seq_k, max_q, max_k, window_size=(-1, 0))

DebugInfoWriter agora homenageia $XDG_CACHE_HOME por seu diretório de cache em código C++, consistente com o lado Python. Anteriormente sempre usava ~/.cache/torch. (#168232)

Isso evita problemas em que $HOME não está configurado ou não pode ser gravado. Os usuários que dependiam do uso do ~/.cache/torch independentemente do $XDG_CACHE_HOME podem ver as informações de depuração gravadas em um local diferente. Versão 2.10:

Versão 2.11:

# C++ DebugInfoWriter now respects $XDG_CACHE_HOME/torch (same as Python code)

DeviceMesh agora armazena um registro de grupo de processos (_pg_registry) diretamente, permitindo que torch.compile rastreie através de get_group(). (#172272)

Isso pode quebrar o código que ignora init_process_group, carrega um DTensor salvo (construindo um DeviceMesh sem PGs) e posteriormente cria PGs separadamente - durante o tempo de execução de torch.compile a pesquisa de PG falhará. Os usuários devem garantir que os grupos de processos sejam inicializados antes de construir o DeviceMesh. Versão 2.10:

# PGs resolved via global _resolve_process_group at runtime
mesh = DeviceMesh(...)  # PGs could be created later

Versão 2.11:

dist.init_process_group(...)  # Must be called before creating mesh
mesh = DeviceMesh(...)

Distribuído (DTensor)

DTensor.to_local() para trás agora converte posicionamentos Partial em Replicate por padrão quando grad_placements não é fornecido. (#173454)

Anteriormente, chamar to_local() em um Partial DTensor preservaria o posicionamento de Partial no gradiente reverso, o que poderia produzir gradientes incorretos quando combinado com from_local(). Agora, a passagem para trás mapeia automaticamente os posicionamentos de avanço do Partial para os posicionamentos de gradiente do Replicate, correspondendo ao comportamento do from_local(). Os usuários que confiaram no comportamento anterior (onde to_local() preservou gradientes Partial para trás) podem ver diferentes valores de gradiente. Para garantir a correção, passe explicitamente grad_placements para to_local(). Versão 2.10:

# Partial placement preserved in backward — could produce incorrect gradients
local_tensor = partial_dtensor.to_local()

Versão 2.11:

# Partial → Replicate in backward by default (correct behavior)
local_tensor = partial_dtensor.to_local()
# Or explicitly specify grad_placements for full control:
local_tensor = partial_dtensor.to_local(grad_placements=[Replicate()])

_PhiloxState.seed e _PhiloxState.offset agora retornam torch.Tensor em vez de int (#173876)

A classe _PhiloxState interna do DTensor RNG mudou suas propriedades seed e offset para retornar tensores em vez de ints Python, e os setters agora esperam tensores. Isso torna o estado RNG compatível com o rastreamento PT2 (as chamadas .item() anteriores não eram compatíveis com tensores falsos). O código que lê diretamente _PhiloxState.seed ou _PhiloxState.offset e os trata como inteiros será quebrado. Chame .item() para obter o valor int. Ao definir, envolva o valor em um tensor. Versão 2.10:

from torch.distributed.tensor._random import _PhiloxState

philox = _PhiloxState(state)
seed: int = philox.seed          # returned int
philox.offset = 42               # accepted int

Versão 2.11:

from torch.distributed.tensor._random import _PhiloxState

philox = _PhiloxState(state)
seed: int = philox.seed.item()   # now returns Tensor; call .item() for int
philox.offset = torch.tensor([42], dtype=torch.int64)  # must pass Tensor

##ROCm

O suporte ao caffe2 foi totalmente removido do pré-processamento hipify do ROCm PyTorch. Isso é conhecido como comportamento "hipify v2". (#174087, #174300, #174388, #174499, #175098)

fundo hipify v1

Quando caffe2 e PyTorch eram projetos separados, as estratégias de suporte do ROCm eram diferentes. Para caffe2, todos os arquivos e classes seriam renomeados seguindo o padrão de CUDA para HIP, Cuda para Hip, cuda para hip e assim por diante. PyTorch não renomeou classes, mas criou novos arquivos seguindo o mesmo padrão de renomeação (por exemplo, aten/src/ATen/cuda/CUDABlas.h para aten/src/ATen/hip/HIPBlas.h). Como consequência, o caffe2 tinha um back-end de dispositivo distinto denominado "HIP" (renomeado de "CUDA"), enquanto o ROCm PyTorch se disfarça como o dispositivo "cuda" (torch.empty(1, device="cuda")). Depois que os projetos caffe2 e PyTorch foram mesclados, isso causou uma incompatibilidade entre o caffe2 que esperava usar um dispositivo "HIP" enquanto o PyTorch esperava um dispositivo "cuda". Para aliviar essa incompatibilidade, classes "Masquerading" foram criadas em aten/src/ATen/hip/impl.

  • HIPAllocatorMasqueradingAsCUDA.h -HIPCachingAllocatorMasqueradingAsCUDA.h
  • HIPGuardImplMasqueradingAsCUDA.h -HIPStreamMasqueradingAsCUDA.h Essas classes eram frequentemente utilizadas de forma transparente durante o pré-processamento hipify de arquivos de origem do ROCm PyTorch. Todos os arquivos em c10/ e caffe2/ foram modificados usando o comportamento de renomeação caffe2, enquanto todos os outros arquivos "PyTorch" usaram a outra estratégia. As classes Masquerading substituiriam sua contraparte CUDA durante o pré-processamento do hipify. Por exemplo, CUDAStream de c10/cuda/CUDAStream.h seria substituído por HIPStreamMasqueradingAsCUDA de aten/src/ATen/hip/impl/HIPStreamMasqueradingAsCUDA.h. Essas classes Masquerading chamam o código caffe2 subjacente e criam dispositivos "HIP", e o dispositivo seria redefinido para "cuda" pelas classes Masquerading.

novo comportamento do hipify v2

Hipify v2 (#174087, #174300, #174388, #174499, #175098) faz as seguintes alterações:

  • As classes "Masquerading" estão obsoletas. Retrabalhado para ser uma camada fina em torno das classes existentes, para compatibilidade com versões anteriores.
  • Não renomeie classes "CUDA" para "HIP". Renomeie apenas CUDA Runtime APIs. Os arquivos ainda são renomeados fora do lugar.
  • Remove soluções alternativas do caffe2 para dispositivos HIP versus dispositivos CUDA. Muito cuidado foi tomado para tornar essa alteração compatível com versões anteriores. Embora o PyTorch hoje seja construído de forma limpa usando o comportamento do hipify v2, projetos de extensão downstream do PyTorch que incluíam explicitamente cabeçalhos de mascaramento ou chamados de APIs de mascaramento podem ser afetados, resultando em compilações com falha. Por exemplo, antes da compatibilidade com versões anteriores ser realizada, o projeto xformers não conseguiu construir usando as alterações do hipify v2. A PR demonstra as mudanças que foram inicialmente necessárias para contornar as falhas de construção, mas tais mudanças não são mais necessárias depois que o comportamento de quebra de BC do hipify v2 foi melhorado.

tocha.exportação

torch.export.export_for_training foi removido (#171714)

O export_for_training estava anteriormente disponível como um API separado para exportar modelos enquanto preservava a semântica de treinamento. Esta função foi removida. Os usuários devem usar torch.export.export, que retorna o mesmo gráfico do export_for_training anterior.

ONNX

Remova a opção fallback do torch.onnx.export (#173189)

O parâmetro fallback foi removido do torch.onnx.export(). Anteriormente, quando fallback=True, o exportador voltaria automaticamente para o exportador legado baseado em TorchScript se o exportador dínamo falhasse. Este recurso foi removido porque era excessivamente complicado, exigia diferentes insumos, produzia modelos diferentes e ocultava erros do novo exportador. Migração: Remova fallback=True (ou fallback=False) de suas chamadas torch.onnx.export(). Se você precisar de um comportamento de fallback, implemente-o explicitamente em seu próprio código, capturando exceções e chamando o exportador legado separadamente.

# Before
torch.onnx.export(model, args, "model.onnx", dynamo=True, fallback=True)

# After
torch.onnx.export(model, args, "model.onnx", dynamo=True)

Remova a lógica de correspondência de sobrecarga do despachante ONNX (#165083)

O parâmetro custom_translation_table em torch.onnx.export() não aceita mais lista de funções para cada operação da tocha. Anteriormente, os usuários podiam passar uma lista de funções ONNX sobrecarregadas (por exemplo, uma para tensores flutuantes, outra para tensores bool), e o despachante selecionaria automaticamente a sobrecarga correta com base nos tipos de entrada. Essa lógica complexa de correspondência de tipo foi removida porque o torchlib não usa mais sobrecargas para a mesma versão do opset. O tipo de custom_translation_table mudou de dict[Callable, Callable | Sequence[Callable]] para dict[Callable, Callable]. Passar um Sequence como valor agora gera um TypeError. Migração: fornece uma única função por operador em vez de uma lista de sobrecargas. Se você precisar de um comportamento dependente do tipo, trate-o dentro de uma única função.

# Before
custom_translation_table = {
    torch.ops.aten.logical_and.default: [custom_impl_float, custom_impl_bool],
}

# After
custom_translation_table = {
    torch.ops.aten.logical_and.default: custom_impl,
}

O fluxo de quantização PT2E (torch.ao.quantization.pt2e e torch.ao.quantization.quantizer) foi removido do PyTorch e migrado para torchao. (#169151)

Backwards Incompatible Changes

Release Engineering

Volta (SM 7.0) GPU support removed from CUDA 12.8 and 12.9 binary builds (#172598)

Starting with PyTorch 2.11, the CUDA 12.8 and 12.9 pre-built binaries no longer include support for Volta GPUs (compute capability 7.0, e.g. V100). This change was necessary to enable updating to CuDNN 9.15.1, which is incompatible with Volta.

Users with Volta GPUs who need CUDA 12.8+ should use the CUDA 12.6 builds, which continue to include Volta support. Alternatively, build PyTorch from source with Volta included in TORCH_CUDA_ARCH_LIST.

Version 2.10:

# CUDA 12.8 builds supported Volta (SM 7.0)
pip install torch --index-url https://download.pytorch.org/whl/cu128
# Works on V100

Version 2.11:

# CUDA 12.8 builds no longer support Volta
# For V100 users, use CUDA 12.6 builds instead:
pip install torch --index-url https://download.pytorch.org/whl/cu126

PyPI wheels now ship with CUDA 13.0 instead of CUDA 12.x (#172663, announcement)

Starting with PyTorch 2.11, pip install torch on PyPI installs CUDA 13.0 wheels by default for both Linux x86_64 and Linux aarch64. Previously, PyPI wheels shipped with CUDA 12.x and only Linux x86_64 CUDA wheels were available on PyPI. Users whose systems have only CUDA 12.x drivers installed may encounter errors when running pip install torch without specifying an index URL.

Additionally, CUDA 13.0 only supports Turing (SM 7.5) and newer GPU architectures on Linux x86_64. Maxwell and Pascal GPUs are no longer supported under CUDA 13.0. Users with these older GPUs should use the CUDA 12.6 builds instead.

CUDA 12.6 and 12.8 binaries remain available via download.pytorch.org.

Version 2.10:

# PyPI wheel used CUDA 12.x
pip install torch

Version 2.11:

DTensor.to_local() backward now converts Partial placements to Replicate by default when grad_placements is not provided. (#173454)

Previously, calling to_local() on a Partial DTensor would preserve the Partial placement in the backward gradient, which could produce incorrect gradients when combined with from_local(). Now, the backward pass automatically maps Partial forward placements to Replicate gradient placements, matching the behavior of from_local().

Users who relied on the previous behavior (where to_local() backward preserved Partial gradients) may see different gradient values. To ensure correctness, explicitly pass grad_placements to to_local().

Version 2.10:

local_tensor = partial_dtensor.to_local()

Version 2.11:

# Or explicitly specify grad_placements for full control:
local_tensor = partial_dtensor.to_local(grad_placements=[Replicate()])

_PhiloxState.seed and _PhiloxState.offset now return torch.Tensor instead of int (#173876)

The DTensor RNG internal _PhiloxState class changed its seed and offset properties to return tensors instead of Python ints, and the setters now expect tensors. This makes the RNG state compatible with PT2 tracing (the previous .item() calls were not fake-tensor friendly).

Code that directly reads _PhiloxState.seed or _PhiloxState.offset and treats them as ints will break. Call .item() to get the int value. When setting, wrap the value in a tensor.

Version 2.10:

Version 2.11:

philox.offset = torch.tensor([42], dtype=torch.int64)  # must pass Tensor

ROCm

caffe2 support is fully removed from ROCm PyTorch's hipify preprocessing. This is known as "hipify v2" behavior. (#174087, #174300, #174388, #174499, #175098)

hipify v1 background

When caffe2 and PyTorch were separate projects, the ROCm support strategies were different. For caffe2, all files and classes would be renamed following the pattern of CUDA to HIP, Cuda to Hip, cuda to hip, and so on. PyTorch did not rename classes, but would create new files following the same renaming pattern (e.g., aten/src/ATen/cuda/CUDABlas.h to aten/src/ATen/hip/HIPBlas.h). As a consequence, caffe2 had a distinct device backend named "HIP" (renamed from "CUDA") while ROCm PyTorch masquerades as the "cuda" device (torch.empty(1, device="cuda")). Once caffe2 and PyTorch projects were merged, this caused a mismatch between caffe2 expecting to use a "HIP" device while PyTorch expecting a "cuda" device. To alleviate this mismatch, "Masquerading" classes were created under aten/src/ATen/hip/impl.

  • HIPAllocatorMasqueradingAsCUDA.h
  • HIPCachingAllocatorMasqueradingAsCUDA.h
  • HIPGuardImplMasqueradingAsCUDA.h
  • HIPStreamMasqueradingAsCUDA.h These classes were often transparently utilized during ROCm PyTorch's hipify preprocessing of source files. All files under c10/ and caffe2/ were hipified using the caffe2 renaming behavior, while all other "PyTorch" files used the other strategy. The Masquerading classes would replace their CUDA counterpart during hipify preprocessing. For example, c10/cuda/CUDAStream.h's CUDAStream would be replaced by aten/src/ATen/hip/impl/HIPStreamMasqueradingAsCUDA.h's HIPStreamMasqueradingAsCUDA. These Masquerading classes call the underlying caffe2 code and create "HIP" devices, and the device would be reset to "cuda" by the Masquerading classes.

hipify v2 new behavior

Hipify v2 (#174087, #174300, #174388, #174499, #175098) makes the following changes:

  • "Masquerading" classes are deprecated. Reworked to be thin shells around existing classes, for backward compatibility.
  • Do not rename "CUDA" classes to "HIP". Only rename CUDA Runtime APIs. Files are still renamed out of place.
  • Removes caffe2 work-arounds for HIP device versus CUDA device. Great care has been taken to make this change backwards compatible. Though PyTorch today builds cleanly using hipify v2 behavior, downstream PyTorch extension projects that explicitly included Masquerading headers or called Masquerading APIs could be affected, resulting in failed builds. As an example, before backwards compatibility was realized, the xformers project had failed to build using the hipify v2 changes. A PR demonstrates the changes that were initially necessary to work around the build failures, but such changes are no longer necessary after hipify v2 BC-breaking behavior was improved.

ONNX

Remove the fallback option from torch.onnx.export (#173189)

The fallback parameter has been removed from torch.onnx.export(). Previously, when fallback=True, the exporter would automatically fall back to the legacy TorchScript-based exporter if the dynamo exporter failed. This fallback was removed because it was overly complicated, required different inputs, produced different models, and hid errors from the new exporter.

Migration: Remove fallback=True (or fallback=False) from your torch.onnx.export() calls. If you need fallback behavior, implement it explicitly in your own code by catching exceptions and calling the legacy exporter separately.

# Before
torch.onnx.export(model, args, "model.onnx", dynamo=True, fallback=True)

# After
torch.onnx.export(model, args, "model.onnx", dynamo=True)

Remove overload matching logic from the ONNX dispatcher (#165083)

The custom_translation_table parameter in torch.onnx.export() no longer accepts a list of functions for each torch op. Previously, users could pass a list of overloaded ONNX functions (e.g., one for float tensors, another for bool tensors), and the dispatcher would automatically select the correct overload based on input types. This complex type-matching logic has been removed because torchlib no longer uses overloads for the same opset version.

The type of custom_translation_table changed from dict[Callable, Callable | Sequence[Callable]] to dict[Callable, Callable]. Passing a Sequence as a value now raises a TypeError.

Migration: Provide a single function per operator instead of a list of overloads. If you need type-dependent behavior, handle it inside the single function.

# Before
custom_translation_table = {
    torch.ops.aten.logical_and.default: [custom_impl_float, custom_impl_bool],
}

# After
custom_translation_table = {
    torch.ops.aten.logical_and.default: custom_impl,
}

  • The MAGMA backend for linear algebra operations is now deprecated and will be removed in a future release. Setting torch.backends.cuda.preferred_linalg_library("magma") or retrieving a previously-set MAGMA preference will now issue a deprecation warning. cuSOLVER remains the default backend. (#172823)

    Version 2.11:

  • torch.linalg.svd no longer dispatches to MAGMA. The MAGMA backend is deprecated and cuSOLVER is now used unconditionally, providing significant speedups (2x–400x depending on matrix size and batch dimensions). (#172824)
