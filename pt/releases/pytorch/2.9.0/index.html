Abaixo estão os release notes completos para este lançamento. # Alterações incompatíveis com versões anteriores ## A versão mínima do Python suportada agora é 3.10 (#162310) A versão mínima do Python necessária para PyTorch 2.9.0 é 3.10. Também temos 3.14 e 3.14t disponíveis como visualização nesta versão. ## Comportamento indefinido quando uma saída de um operador personalizado compartilha armazenamento com uma entrada Este é um lembrete de que as saídas dos operadores personalizados PyTorch (que são registrados usando os `torch.library` ou `TORCH_LIBRARY` APIs) não têm permissão para retornar tensores que compartilham armazenamento com tensores de entrada. A violação desta condição leva a um comportamento indefinido: às vezes o resultado será correto, às vezes será lixo. Depois de [#163227](https://github.com/pytorch/pytorch/pull/163227), os operadores personalizados que violaram essa condição que anteriormente retornava resultados corretos em `torch.compile` agora podem retornar resultados silenciosamente incorretos em `torch.compile`. Como isso está alterando o comportamento de um comportamento indefinido, não consideramos isso um bug, mas ainda o documentamos nesta seção como uma "mudança de comportamento potencialmente inesperada". Esta é uma das condições verificadas por [`torch.library.opcheck`](https://docs.pytorch.org/docs/stable/library.html#testing-custom-ops) e é mencionada no [Manual do Operador Personalizado](https://docs.google.com/document/d/1_W62p8WJOQQUzPsJYa7s701JXt0qf2OfLub2sbkHOaU/edit?tab=t.0#bookmark=id.4c0um7xkba6e) ### Mais detalhes As saídas dos operadores personalizados PyTorch não têm permissão para retornar tensores que compartilham armazenamento com tensores de entrada Por exemplo, os dois operadores personalizados a seguir não são operadores personalizados válidos: ```py @torch.library.custom_op("mylib::foo", mutates_args=()) def foo(x: torch.Tensor) -> torch.Tensor: # the result of `foo` must not directly be an input to foo. return x

@torch.library.custom_op("mylib::bar", mutates_args=()) def bar(x: torch.Tensor) -> torch.Tensor: # the result of bar must not be a view of an input of bar return x.view(-1)

A solução mais fácil é adicionar um `.clone()` extra às saídas:
```py
@torch.library.custom_op("mylib::foo", mutates_args=())
def foo(x: torch.Tensor) -> torch.Tensor:
    return x.clone()

@torch.library.custom_op("mylib::bar", mutates_args=())
def bar(x: torch.Tensor) -> torch.Tensor:
    return x.view(-1).clone()

Uma maneira comum de entrar nessa situação é um usuário querer criar um operador personalizado que às vezes altera a entrada no local e às vezes retorna um novo Tensor, como no exemplo a seguir.

@torch.library.custom_op("mylib::baz", mutates_args=["x"])
def baz(x: torch.Tensor) -> torch.Tensor:
    if inplace:
        x.sin_()
        return x
    else:
        return x.sin()

Este dinamismo não é suportado e leva a um comportamento indefinido. A solução alternativa é dividir o operador personalizado em dois operadores personalizados, um que sempre altera a entrada no local e outro que sempre retorna um novo Tensor.

@torch.library.custom_op("mylib::baz_outplace", mutates_args=())
def baz_outplace(x: torch.Tensor) -> torch.Tensor:
    return x.sin()

@torch.library.custom_op("mylib::baz_inplace", mutates_args=["x"])
def baz_inplace(x: torch.Tensor) -> torch.Tensor:
    x.sin_()

def baz(x):
    if inplace:
        baz_inplace(x)
        return x
    else:
        return baz_outplace(x)

Construir kernels metálicos do MacOS-14+ e remover toda a lógica específica pré-MacOS-14, requer MacOS-14+ daqui para frente (#159733, #159912)

PyTorch MPS é compatível apenas com MacOS-14 ou posterior. Se você precisar usar MPS no MacOS Ventura, evite atualizar para Python-3.9 ou superior

Atualize para DLPack 1.0 (#145000)

Esta atualização está fazendo as mesmas alterações radicais do BC que a versão DLPack. Os objetos em torch.utils.dlpack foram atualizados para refletir essas alterações, como DLDeviceType. Consulte o PR para obter detalhes sobre as alterações exatas e como atualizar seu código.

Levanta erros apropriados em torch.cat (#158249)

torch.cat agora aumenta ValueError, IndexError ou TypeError quando apropriado, em vez do RuntimeError genérico. Se o seu código estava detectando esses erros, você pode atualizar para capturar o novo tipo de erro.

Padrão para dynamo=True para exportador ONNX (#159646, #162726)

Anteriormente, torch.onnx.export(...) usava o exportador TorchScript herdado se nenhum argumento fosse fornecido. O exportador ONNX agora usa o pipeline torch.export.export mais recente por padrão (dynamo=True). Essa alteração melhora a fidelidade do gráfico e as exportações preparadas para o futuro, mas pode revelar erros de captura de gráfico que antes eram mascarados ou tratados de maneira diferente. Anteriormente na tocha 2.8.0:

# API calls the legacy exporter with dynamo=False
torch.onnx.export(...)

Agora na tocha 2.9.0:

# To preserve the original behavior
torch.onnx.export(..., dynamo=False)

# Export onnx model through torch.export.export
torch.onnx.export(...)

Recomendação: primeiro tente o novo padrão; só recue se você encontrar problemas de bloqueio e reportá-los ao upstream. Solução de longo prazo: corrija a causa raiz em vez de confiar no substituto ou no exportador TorchScript.

Desative as declarações de tempo de execução por padrão em Exportar em favor de uma função de proteção de forma (#160111, #161178, #161794)

Para habilitar declarações de tempo de execução, use export(..., prefer_deferred_runtime_asserts_over_guards=True). Também elimina o sinalizador allow_complex_guards_as_runtime_asserts, mesclando-o com a opção anterior. Além disso, exported_program.module() irá gerar uma chamada para um submódulo _guards_fn que irá executar verificações adicionais nas entradas. Os usuários que não desejam esse comportamento podem remover esta chamada do grafo ou fazer exported_program.module(check_guards=False) para evitar a geração.

Defina o opset padrão para 20 no ONNX (#158802)

O Opset 20 permite definições de operadores mais recentes. Se suas ferramentas ou tempo de execução downstream suportam apenas o opset 18, fixe-o explicitamente. Para os operadores ONNX mais recentes, você pode experimentar o opset 23. Anteriormente na tocha 2.8.0:

# opset_version=18
torch.onnx.export(...)

Agora na tocha 2.9.0:

# To preserve the original behavior
torch.onnx.export(..., opset_version=18)

# New: opset_version=20
torch.onnx.export(...)

# Use the latest supported opset: opset_version=23
torch.onnx.export(..., opset_version=23)

Solte draft_export no exportador API (#161454, #162225)

Remova o rascunho implícito do caminho do exportador padrão, obtendo um comportamento mais claro e falhas mais rápidas. O caro caminho de diagnóstico do torch.export.draft_export não é mais invocado automaticamente (o que pode levar horas em modelos grandes). Você ainda pode optar por diagnósticos profundos: Anteriormente na tocha 2.8.0:

# If both torch.export.export(..., strict=False) and
# torch.export.export(..., strict=True) fail to capture
# the model graph, torch.export.draft_export(...) will be triggered,
# and uses real tensor to trace/export the model.
#
# Inside export_to_onnx.py:
#  ... torch.onnx.export(..., dynamo=True)
python export_to_onnx.py

Agora na tocha 2.9.0:

# To trigger torch.export.draft_export once
# torch.export.export strict=False/True both
# fail:

TORCH_ONNX_ENABLE_DRAFT_EXPORT=True python export_to_onnx.py

Remova torch.onnx.dynamo_export e o backend de compilação da tocha onnxrt (#158130, #158258)

torch.onnx.dynamo_export é removido. Use torch.onnx.export. O back-end de compilação experimental ONNX Runtime (torch.compile(backend="onnxrt")) não é mais compatível.

Remover torch.onnx.enable_fake_mode (#161222)

O modo dynamo=True usa FakeTensors por padrão, o que economiza memória.

Alguns utilitários ONNX APIs voltados ao público para o exportador baseado em TorchScript agora são privados (#161323)

Os membros obsoletos em torch.onnx.verification foram removidos. As funções anteriormente privadas do torch.onnx.symbolic_opsets* não estarão mais acessíveis. Considere fazer uma cópia do código-fonte se precisar acessar qualquer função privada para compatibilidade com o exportador baseado em TorchScript.

Remover torch.onnx.symbolic_caffe2 (#157102)

O suporte para caffe2 no exportador ONNX foi encerrado e removido.

Remova o sinalizador /d2implyavx512upperregs que retarda a construção (#159431)

Otimizações AVX512 reintroduzidas para compilações do Windows VS2022 podem causar problemas com versões específicas do VS2022, consulte #145702

Adicione ScalarType à conversão de calço e stable::Tensor.scalar_type (#160557)

Antes, as extensões do usuário só podiam passar de forma abstrata dtypes ofuscados que apareciam como int32_ts. Agora, os usuários podem usar torch::headeronly::ScalarType com segurança em suas extensões para os principais tipos escalares. Este PR permite a estabilidade da ABI adicionando uma camada de tradução por meio do calço, de modo que, mesmo que os valores da enumeração ScalarType mudem no futuro, as extensões do usuário não precisam se preocupar. Essa alteração adiciona suporte ScalarType para extensões de usuário e é apenas uma quebra estreita de BC para dtypes impopulares: quint*s, qint*s, Bits*, dummy_uint*s, dummy_int*s, Float8_e8m0fnu e Float4_e2m1fn_x2 no caso de uso em que uma extensão recupera um dtype Tensor acima e o passa para aoti_torch_call_dispatcher.

Depreciações

Descontinuar parâmetro pin_memory_device em torch.utils.data.DataLoader (#158323)

Movemos a habilitação do pin_memory de volta para o BaseDataLoaderIter. Isso é necessário para StatefulDataloader que aproveitou BaseDataLoaderIter diretamente em vez do init da classe Dataloader

Descontinuar torch.export.export_for_training API em favor do equivalente torch.export.export API (#158203)

torch.export.export_for_training existe porque não conseguimos migrar usos internos de exportação para o IR final. Agora que concluímos a migração, descontinuamos e excluímos este API.

Backwards Incompatible Changes

Min supported Python version is now 3.10 (#162310)

The minimum version of Python required for PyTorch 2.9.0 is 3.10. We also have 3.14 and 3.14t available as preview with this release.

Undefined behavior when an output of a custom operator shares storage with an input

This is a reminder that outputs of PyTorch custom operators (that are registered using the torch.library or TORCH_LIBRARY APIs) are not allowed to return Tensors that share storage with input tensors. The violation of this condition leads to undefined behavior: sometimes the result will be correct, sometimes it will be garbage.

After #163227, custom operators that violated this condition that previously returned correct results under torch.compile may now return silently incorrect results under torch.compile. Because this is changing the behavior of undefined behavior, we do not consider this to be a bug, but we are still documenting it in this section as a "potentially unexpected behavior change".

This is one of the conditions checked for by torch.library.opcheck and is mentioned in The Custom Operators Manual

More details

Outputs of PyTorch custom operators are not allowed to return Tensors that share storage with input tensors

For example, the following two custom operators are not valid custom operators:

@torch.library.custom_op("mylib::foo", mutates_args=())
def foo(x: torch.Tensor) -> torch.Tensor:
    # the result of `foo` must not directly be an input to foo.
    return x

@torch.library.custom_op("mylib::bar", mutates_args=())
def bar(x: torch.Tensor) -> torch.Tensor:
    # the result of bar must not be a view of an input of bar
    return x.view(-1)

The easiest workaround is to add an extra .clone() to the outputs:

@torch.library.custom_op("mylib::foo", mutates_args=())
def foo(x: torch.Tensor) -> torch.Tensor:
    return x.clone()

@torch.library.custom_op("mylib::bar", mutates_args=())
def bar(x: torch.Tensor) -> torch.Tensor:
    return x.view(-1).clone()

A common way to get into this situation is for a user to want to create a custom operator that sometimes mutates the input in-place and sometimes returns a new Tensor, like in the following example.

@torch.library.custom_op("mylib::baz", mutates_args=["x"])
def baz(x: torch.Tensor) -> torch.Tensor:
    if inplace:
        x.sin_()
        return x
    else:
        return x.sin()

This dynamism is not supported and leads to undefined behavior. The workaround is to split the custom operator into two custom operators, one that always mutates the input in-place, and another that always returns a new Tensor.

@torch.library.custom_op("mylib::baz_outplace", mutates_args=())
def baz_outplace(x: torch.Tensor) -> torch.Tensor:
    return x.sin()

@torch.library.custom_op("mylib::baz_inplace", mutates_args=["x"])
def baz_inplace(x: torch.Tensor) -> torch.Tensor:
    x.sin_()

def baz(x):
    if inplace:
        baz_inplace(x)
        return x
    else:
        return baz_outplace(x)

Raise appropriate errors in torch.cat (#158249)

torch.cat now raises ValueError, IndexError or TypeError where appropriate instead of the generic RuntimeError. If you code was catching these errors, you can update to catch the new error type.

Default to dynamo=True for ONNX exporter (#159646, #162726)

Previously torch.onnx.export(...) used the legacy TorchScript exporter if no arguments were provied. The ONNX exporter now uses the newer torch.export.export pipeline by default (dynamo=True). This change improves graph fidelity and future-proofs exports, but may surface graph capture errors that were previously masked or handled differently.

Previously in torch 2.8.0:

# API calls the legacy exporter with dynamo=False
torch.onnx.export(...)

Now in torch 2.9.0:

# To preserve the original behavior
torch.onnx.export(..., dynamo=False)

# Export onnx model through torch.export.export
torch.onnx.export(...)

Recommendation: first try the new default; only fall back if you hit blocking issues and report them upstream. Long term solution: fix the root cause instead of relying on fallback or TorchScript exporter.

Switch off runtime asserts by default in Export in favor of a shape guards function (#160111, #161178, #161794)

To enable runtime asserts, use export(..., prefer_deferred_runtime_asserts_over_guards=True). Also kills the allow_complex_guards_as_runtime_asserts flag, merging it into the former option.

Additionally, exported_program.module() will generate a call to a _guards_fn submodule that will run additional checks on inputs. Users who do not want this behavior can either remove this call in the graph, or do exported_program.module(check_guards=False) to avoid the generation.

Set default opset to 20 in ONNX (#158802)

Opset 20 enables newer operator definitions. If your tooling or downstream runtime only supports opset 18, pin it explicitly. For the latest ONNX operators, you can experiment with opset 23.

Previously in torch 2.8.0:

# opset_version=18
torch.onnx.export(...)

Now in torch 2.9.0:

# To preserve the original behavior
torch.onnx.export(..., opset_version=18)

# New: opset_version=20
torch.onnx.export(...)

# Use the latest supported opset: opset_version=23
torch.onnx.export(..., opset_version=23)

Drop draft_export in exporter API (#161454, #162225)

Remove implicit draft tracing from the default exporter path, achieving clearer behaviour and faster failures. The expensive torch.export.draft_export diagnostic path is no longer auto-invoked (which could take hours on large models). You can still opt in for deep diagnostics:

Previously in torch 2.8.0:

# If both torch.export.export(..., strict=False) and
# torch.export.export(..., strict=True) fail to capture
# the model graph, torch.export.draft_export(...) will be triggered,
# and uses real tensor to trace/export the model.
#
# Inside export_to_onnx.py:
#  ... torch.onnx.export(..., dynamo=True)
python export_to_onnx.py

Now in torch 2.9.0:

# To trigger torch.export.draft_export once
# torch.export.export strict=False/True both
# fail:

TORCH_ONNX_ENABLE_DRAFT_EXPORT=True python export_to_onnx.py

Remove torch.onnx.dynamo_export and the onnxrt torch compile backend (#158130, #158258)

torch.onnx.dynamo_export is removed. Please use torch.onnx.export instead. The experimental ONNX Runtime compile backend (torch.compile(backend="onnxrt")) is no longer supported.

Remove torch.onnx.enable_fake_mode (#161222)

The dynamo=True mode uses FakeTensors by default which is memory efficient.

Some public facing ONNX utility APIs for the TorchScript based exporter are now private (#161323)

Deprecated members in torch.onnx.verification are removed. Previously private torch.onnx.symbolic_opsets* functions will no longer be accessible. Consider making a copy of the source code if you need to access any private functions for compatibility with the TorchScript based exporter.

Remove torch.onnx.symbolic_caffe2 (#157102)

Support for caffe2 in the ONNX exporter has ended and is removed.

Remove /d2implyavx512upperregs flag that slows build (#159431)

Re-introduced AVX512 optimizations for Windows VS2022 builds, may cause issues with specific versions of VS2022, see #145702

Add ScalarType to shim conversion and stable::Tensor.scalar_type (#160557)

Before, user extensions could only in abstract pass around obfuscated dtypes appearing as int32_ts. Now, users can confidently use torch::headeronly::ScalarType in their extensions for major scalar types. This PR enables ABI stability by adding a translation layer through the shim, so that even if the ScalarType enum values change in the future, user extensions need not fear.

This change adds ScalarType support for user extensions and is only narrowly BC breaking for unpopular dtypes: quint*s, qint*s, Bits*, dummy_uint*s, dummy_int*s, Float8_e8m0fnu, and Float4_e2m1fn_x2 in the use case where an extension retrieves a Tensor dtype of the above and passes it into aoti_torch_call_dispatcher.
