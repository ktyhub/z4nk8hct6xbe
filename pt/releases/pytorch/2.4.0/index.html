Destaques

Temos o prazer de anunciar o lançamento do PyTorch® 2.4! PyTorch 2.4 adiciona suporte para a versão mais recente do Python (3.12) para torch.compile. O congelamento do AOTInductor oferece aos desenvolvedores que executam o AOTInductor mais otimizações baseadas em desempenho, permitindo que o serialização de pesos MKLDNN. Além disso, um novo back-end de servidor TCPStore padrão utilizando libuv foi introduzido o que deve reduzir significativamente os tempos de inicialização para usuários que executam trabalhos em grande escala. Finalmente, um novo operador personalizado Python API torna mais fácil do que antes a integração de kernels personalizados em PyTorch, especialmente para torch.compile. Esta versão é composta por 3.661 commits e 475 contribuidores desde PyTorch 2.3. Queremos agradecer sinceramente aos nossos comunidade dedicada por suas contribuições. Como sempre, encorajamos você a experimentá-los e relatar quaisquer problemas à medida que melhorar 2.4. Mais informações sobre como começar a usar a série PyTorch 2 podem ser encontradas em nosso Página Introdução. <tabela>

Torch.as_strided é uma operação de visualização existente que pode ser usada de forma não composicional: ou seja, quando você chama x.as_strided(...), as_strided apenas considere o tamanho de armazenamento subjacente de x e ignore seu tamanho/passo/deslocamento de armazenamento atual ao criar uma nova visualização. Isso torna difícil funcionalizar com segurança mutações em visualizações de as_strided que são criadas de forma não composicional, portanto, nós os banimos em vez de arriscarmos problemas silenciosos de correção em torch.compile. Um exemplo de uso não composicional de as_strided seguido de mutação no qual iremos errar está abaixo. Você pode evitar esse problema reescrevendo seu uso de as_strided para que seja composicional (por exemplo: use um conjunto diferente de view ops em vez de as_strided, ou chame as_strided diretamente no tensor base em vez de uma visão existente dele). ```python @torch.compile def foo(a): e = a.diagonal() # as_strided is being called on an existing view (e), # making it non-compositional. mutations to f under torch.compile # are not allowed, as we cannot easily functionalize them safely f = e.as_strided((2,), (1,), 0) f.add_(1.0) return a ``` #### Agora verificamos esquemas de operações personalizadas no momento do registro (#124520) Anteriormente, você poderia registrar uma operação personalizada por meio do registro do operador APIs, mas fornecer a ela um esquema que continha tipos desconhecidos para o PyTorch Dispatcher. Este comportamento veio do TorchScript, onde tipos “desconhecidos” eram implicitamente tratados pelo interpretador TorchScript como variáveis de tipo. No entanto, chamar essa operação personalizada por meio do pytorch normal resultaria em um erro mais tarde. A partir do 2.4, geraremos um erro no momento do registro, quando você registrar pela primeira vez o operador personalizado. Você pode obter o comportamento antigo construindo o esquema com allow_typevars=true. ``` TORCH_LIBRARY(my_ns, m) { // this now raises an error at registration time: bar/baz are unknown types m.def("my_ns::foo(bar t) -> baz"); // you can get back the old behavior with the below flag m.def(torch::schema("my_ns::foo(bar t) -> baz", /*allow_typevars*/ true)); } ``` ### Interface do Autograd #### Excluir torch.autograd.function.traceable APIs (#122817) O torch.autograd.function.traceable(...) FullyShardedDataParallel v2 (FSDP2)

  • FSDP2 é uma nova implementação paralela de dados totalmente fragmentada que usa dim-0 por parâmetro baseado em DTensor fragmentação para maior flexibilidade (por exemplo, coleta total de tipo misto, sem restrições em require_grad) sem custo significativo para o desempenho. Veja o documento para mais detalhes e uma comparação com FSDP1 (#122888, #122907, #123142, #123362, #123491, #123857, #119302, #122908, #123953, #120952, #123988, #124293, #124318, #124319, #120256, #124513, #124955, #125191, #125269, #125394, #126070, #126267, #126305, #126166, #127585, #127776, #127832, #128138, #128117, #128242)

Pipeline

  • Paralelismo de pipeline distribuído PyTorch APIs foram upstreamados do Projeto PiPPy e estão disponíveis como protótipo em PyTorch 2.4. O pacote está em torch.distributed.pipelining e consiste em duas partes: um frontend dividido e um tempo de execução distribuído. O frontend de divisão pega o código do modelo como está, divide-o em “partições de modelo” e captura o relacionamento do fluxo de dados. O tempo de execução distribuído executa os estágios do pipeline em diferentes dispositivos em paralelo, lidando com coisas como divisão de microlotes, agendamento, comunicação e propagação de gradiente. Para mais informações consulte o documentação e tutorial (#126322, #124776, #125273, #125729, #125975, #126123, #126419, #126539, #126582, #126732, #126653, #127418, #127084, #127673, #127332, #127946, #128157, #128163, #127796, #128201, #128228, #128240, #128236, #128273, #128279, #128276, #128278, #127066)

  • torch.compile é compatível com Python 3.12.

  • Recurso experimental - Introduzimos um novo sinalizador experimental torch._dynamo.config.inline_inbuilt_nn_modules para permitir que torch.compile reutilize compilado artefatos em blocos repetidos nos modelos. Isso fornece outro ponto na compensação entre tempo de compilação e aceleração de desempenho. Ao mover torch.compile do modelo completo para um bloco repetido (por exemplo, mover torch.compile do LLM completo para um bloco Transformer repetido), agora podemos obter um tempo de compilação mais rápido com alguma queda no desempenho em comparação com o modelo completo. Planejamos tornar esse sinalizador padrão como True na versão 2.5.

Tracked Regressions

Subproc exception with torch.compile and onnxruntime-training

There is a reported issue (#131070) when using torch.compile if onnxruntime-training lib is installed. The issue will be fixed (#131194) in v2.4.1. It can be solved locally by setting the environment variable TORCHINDUCTOR_WORKER_START=fork before executing the script.

cu118 wheels will not work with pre-cuda12 drivers

It was also reported (#130684) that the new version of triton uses cuda features that are not compatible with pre-cuda12 drivers. In this case, the workaround is to set TRITON_PTXAS_PATH manually as follows (adapt the code according to the local installation path):

TRITON_PTXAS_PATH=/usr/local/lib/python3.10/site-packages/torch/bin/ptxas  python script.py

Backwards Incompatible Change

Python frontend

Default TreadPool size to number of physical cores (#125963)

Changed the default number of threads used for intra-op parallelism from the number of logical cores to the number of physical cores. This should reduce core oversubscribing when running CPU workload and improve performance. Previous behavior can be recovered by using torch.set_num_threads to set the number of threads to the desired value.

Fix torch.quasirandom.SobolEngine.draw default dtype handling (#126781)

The default dtype value has been changed from torch.float32 to the current default dtype as given by torch.get_default_dtype() to be consistent with other APIs.

Forbid subclassing torch._C._TensorBase directly (#125558)

This is an internal subclass that a user used to be able to create an object that is almost a Tensor in Python and was advertised as such in some tutorials. This is not allowed anymore to improve consistency and all users should subclass torch.Tensor directly.

Composability

Non-compositional usages of as_strided + mutation under torch.compile will raise an error (#122502)

The torch.compile flow involves functionalizing any mutations inside the region being compiled. Torch.as_strided is an existing view op that can be used non-compositionally: meaning when you call x.as_strided(...), as_strided will only consider the underlying storage size of x, and ignore its current size/stride/storage_offset when creating a new view. This makes it difficult to safely functionalize mutations on views of as_strided that are created non-compositionally, so we ban them rather than risking silent correctness issues under torch.compile.

An example of a non-compositional usage of as_strided followed by mutation that we will error on is below. You can avoid this issue by re-writing your usage of as_strided so that it is compositional (for example: either use a different set of view ops instead of as_strided, or call as_strided directly on the base tensor instead of an existing view of it).

@torch.compile
def foo(a):
    e = a.diagonal()
    # as_strided is being called on an existing view (e),
    # making it non-compositional. mutations to f under torch.compile
    # are not allowed, as we cannot easily functionalize them safely
    f = e.as_strided((2,), (1,), 0)
    f.add_(1.0)
    return a

We now verify schemas of custom ops at registration time (#124520)

Previously, you could register a custom op through the operator registration APIs, but give it a schema that contained types unknown to the PyTorch Dispatcher. This behavior came from TorchScript, where “unknown” types were implicitly treated by the TorchScript interpreter as type variables. However, calling such a custom op through regular pytorch would result in an error later. As of 2.4, we will raise an error at registration time, when you first register the custom operator. You can get the old behavior by constructing the schema with allow_typevars=true.

TORCH_LIBRARY(my_ns, m) {
  // this now raises an error at registration time: bar/baz are unknown types
  m.def("my_ns::foo(bar t) -> baz");
  // you can get back the old behavior with the below flag
  m.def(torch::schema("my_ns::foo(bar t) -> baz", /*allow_typevars*/ true));
}

Pipelining

  • PyTorch Distributed pipeline parallelism APIs were upstreamed from the PiPPy project and are available as a prototype release in PyTorch 2.4. The package is under torch.distributed.pipelining and consists of two parts: a splitting frontend and a distributed runtime. The splitting frontend takes your model code as-is, splits it up into “model partitions”, and captures the data-flow relationship. The distributed runtime executes the pipeline stages on different devices in parallel, handling things like micro-batch splitting, scheduling, communication, and gradient propagation. For more information please check out the documentation and tutorial (#126322, #124776, #125273, #125729, #125975, #126123, #126419, #126539, #126582, #126732, #126653, #127418, #127084, #127673, #127332, #127946, #128157, #128163, #127796, #128201, #128228, #128240, #128236, #128273, #128279, #128276, #128278, #127066)
