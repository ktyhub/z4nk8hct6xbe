Destaques

Temos o prazer de anunciar o lançamento do PyTorch® 2.6 (release notes)! Esta versão apresenta diversas melhorias para PT2: torch.compile agora pode ser usado com Python 3.13; novo botão relacionado ao desempenho torch.compiler.set_stance; vários aprimoramentos do AOTInductor. Além das melhorias no PT2, outro destaque é o suporte ao FP16 em CPUs X86. NOTA: A partir deste lançamento, não publicaremos no Conda, consulte [Anúncio] Descontinuando o canal Anaconda oficial do PyTorch para obter detalhes. Para esta versão, os binários experimentais do Linux fornecidos com CUDA 12.6.3 (assim como os binários Linux Aarch64, Linux ROCm 6.2.4 e Linux XPU) são construídos com CXX11_ABI=1 e estão usando a plataforma de construção Manylinux 2.28. Se você criar extensões PyTorch com extensões C++ ou CUDA personalizadas, atualize essas compilações para usar CXX_ABI=1 também e relate quaisquer problemas que estiver vendo. Para o próximo lançamento do PyTorch 2.7, planejamos mudar todas as compilações do Linux para Manylinux 2.28 e CXX11_ABI=1, consulte [RFC] PyTorch next wheel build platform: manylinux-2.28 para obter detalhes e discussão. Também nesta versão, como uma importante medida de melhoria de segurança, alteramos o valor padrão do parâmetro weights_only de torch.load. Esta é uma alteração que quebra a compatibilidade com versões anteriores. Consulte esta postagem no fórum para obter mais detalhes. Esta versão é composta por 3.892 commits de 520 contribuidores desde PyTorch 2.5. Queremos agradecer sinceramente à nossa comunidade dedicada por suas contribuições. Como sempre, encorajamos você a experimentá-los e relatar quaisquer problemas à medida que melhoramos o PyTorch. Uma das posturas, por exemplo, é “eager_on_recompile”, que instrui o PyTorch a codificar avidamente quando uma recompilação for necessária, reutilizando o código compilado em cache quando possível. Para obter mais informações, consulte a [documentação set_stance](https://pytorch.org/docs/2.6/generated/torch.compiler.set_stance.html#torch.compiler.set_stance) e o tutorial [Controle de compilação dinâmica com torch.compiler.set_stance](https://pytorch.org/tutorials/recipes/torch_compiler_set_stance_tutorial.html). **[Beta] torch.library.triton_op** `torch.library.triton_op` oferece uma maneira padrão de criar operadores personalizados que são apoiados por kernels triton definidos pelo usuário. Quando os usuários transformam kernels triton definidos pelo usuário em operadores personalizados, `torch.library.triton_op` permite que `torch.compile` espie a implementação, permitindo que `torch.compile` otimize o kernel triton dentro dele. Para obter mais informações, consulte a [documentação triton_op](https://pytorch.org/docs/2.6/library.html#torch.library.triton_op) e o tutorial [Usando Kernels Triton definidos pelo usuário com torch.compile](https://pytorch.org/tutorials/recipes/torch_compile_user_defined_triton_kernel_tutorial.html). **[Beta] suporte torch.compile para Python 3.13** Anteriormente, `torch.compile` suportava apenas Python até a versão 3.12. Os usuários agora podem otimizar modelos com `torch.compile` em Python 3.13. **[Beta] Nova embalagem APIs para AOTInductor** Um novo formato de pacote, “[arquivo PT2](https://docs.google.com/document/d/1RQ4cmywilnFUT1VE-4oTGxwXdc8vowCSZsrRgo3wFA8/edit?usp=sharing)”, foi introduzido. Este contém essencialmente um arquivo zip de todos os arquivos que precisam ser utilizados pelo AOTInductor e permite aos usuários enviar tudo o que for necessário para outros ambientes. Também há funcionalidade para empacotar vários modelos em um artefato e armazenar metadados adicionais dentro do pacote. Para obter mais detalhes, consulte o [Tutorial torch.export AOTInductor para tempo de execução Python] (https://pytorch.org/tutorials/recipes/torch_export_aoti_python.html) atualizado. **[Beta] AOTInductor: minificador** Se um usuário encontrar um erro ao usar AOTInductor APIs, o AOTInductor Minifier permite a criação de um nn.Module mínimo que reproduz o erro. Para obter mais informações, consulte a [documentação do AOTInductor Minifier] (https://pytorch.org/docs/2.6/torch.compiler_aot_inductor_minifier.html). **[Beta] AOTInductor: geração de código de modo compatível com ABI** O código do modelo gerado pelo AOTInductor depende das bibliotecas cpp do Pytorch. À medida que o Pytorch evolui rapidamente, é importante garantir que os modelos compilados anteriormente pelo AOTInductor possam continuar a ser executados nas versões mais recentes do Pytorch, ou seja, o AOTInductor é compatível com versões anteriores. Para garantir a compatibilidade com versões anteriores da interface binária do aplicativo (ABI), definimos cuidadosamente um conjunto de interfaces C estáveis ​​​​na libtorch e garantimos que o AOTInductor gere código que se refira apenas ao conjunto específico de APIs e nada mais na libtorch. Manteremos o conjunto de C APIs estável nas versões Pytorch e, assim, forneceremos garantias de compatibilidade com versões anteriores para modelos compilados pelo AOTInductor. **Suporte [Beta] FP16 para CPUs X86 (modos ansioso e indutor)** O tipo de dados Float16 é comumente usado para redução do uso de memória e computação mais rápida em inferência e treinamento de IA. CPUs como o recentemente lançado [Intel® Xeon® 6 com P-Cores](https://www.intel.com/content/www/us/en/products/details/processors/xeon/xeon6-p-cores.html) suportam o tipo de dados Float16 com acelerador nativo [AMX](https://www.intel.com/content/www/us/en/products/docs/accelerator-engines/advanced-matrix-extensions/overview.html). O suporte Float16 em CPUs X86 foi introduzido no PyTorch 2.5 como um recurso de protótipo e agora foi melhorado tanto para o modo ansioso quanto para o modo Torch.compile + Inductor, tornando-o um recurso de nível Beta com funcionalidade e desempenho verificados com um amplo escopo de cargas de trabalho. ### RECURSOS DO PROTÓTIPO **[Protótipo] Experiência de usuário PyTorch aprimorada em GPUs Intel** A experiência do usuário PyTorch em GPUs Intel é aprimorada ainda mais com etapas de instalação simplificadas, distribuição binária de lançamento do Windows e cobertura expandida de modelos de GPU suportados, incluindo os mais recentes gráficos discretos Intel® Arc™ Série B. Este novo recurso aproveita e amplia as capacidades atuais do modelo CPP para suportar variantes de atenção ampla (por exemplo: PageAttention, que é crítico para inferência de LLMs) com base no FlexAttention API existente e traz desempenho otimizado em CPUs x86. Com este recurso, é fácil utilizar o FlexAttention API para compor soluções de Atenção em plataformas de CPU e obter bom desempenho. **[Protótipo] Dim.AUTO** `Dim.AUTO` permite o uso de formas dinâmicas automáticas com `torch.export`. Os usuários podem exportar com `Dim.AUTO ` e “descobrir” o comportamento dinâmico de seus modelos, com intervalos mínimo/máximo, relações entre dimensões e comportamento estático/dinâmico sendo inferidos automaticamente. Esta é uma experiência mais amigável em comparação com a abordagem existente de Dims nomeados para especificar formas dinâmicas, que exige que o usuário compreenda completamente o comportamento dinâmico de seus modelos no momento da exportação. `Dim.AUTO` permite aos usuários escrever código genérico que não depende do modelo, aumentando a facilidade de uso para exportação com formas dinâmicas. Consulte [tutorial torch.export](https://pytorch.org/tutorials/intermediate/torch_export_tutorial.html#constraints-dynamic-shapes) para obter mais informações. **[Protótipo] Backends CUTLASS e CK GEMM/CONV para AOTInductor** O backend CUTLASS e CK adiciona opções de kernel para ajuste automático GEMM no Inductor. BETA FEATURES

[Beta] torch.compiler.set_stance

This feature enables the user to specify different behaviors (“stances”) that torch.compile can take between different invocations of compiled functions. One of the stances, for example, is

“eager_on_recompile”, that instructs PyTorch to code eagerly when a recompile is necessary, reusing cached compiled code when possible.

For more information please refer to the set_stance documentation and the Dynamic Compilation Control with torch.compiler.set_stance tutorial.

[Beta] torch.library.triton_op

torch.library.triton_op offers a standard way of creating custom operators that are backed by user-defined triton kernels.

When users turn user-defined triton kernels into custom operators, torch.library.triton_op allows torch.compile to peek into the implementation, enabling torch.compile to optimize the triton kernel inside it.

For more information please refer to the triton_op documentation and the Using User-Defined Triton Kernels with torch.compile tutorial.

[Beta] torch.compile support for Python 3.13

torch.compile previously only supported Python up to version 3.12. Users can now optimize models with torch.compile in Python 3.13.

[Beta] New packaging APIs for AOTInductor

A new package format, “PT2 archive”, has been introduced. This essentially contains a zipfile of all the files that need to be used by AOTInductor, and allows users to send everything needed to other environments. There is also functionality to package multiple models into one artifact, and to store additional metadata inside of the package.

For more details please see the updated torch.export AOTInductor Tutorial for Python runtime.

[Beta] AOTInductor: minifier

If a user encounters an error while using AOTInductor APIs, AOTInductor Minifier allows creation of a minimal nn.Module that reproduces the error.

For more information please see the AOTInductor Minifier documentation.

[Beta] AOTInductor: ABI-compatible mode code generation

AOTInductor-generated model code has dependency on Pytorch cpp libraries. As Pytorch evolves quickly, it’s important to make sure previously AOTInductor compiled models can continue to run on newer Pytorch versions, i.e. AOTInductor is backward compatible.

In order to guarantee application binary interface (ABI) backward compatibility, we have carefully defined a set of stable C interfaces in libtorch and make sure AOTInductor generates code that only refers to the specific set of APIs and nothing else in libtorch. We will keep the set of C APIs stable across Pytorch versions and thus provide backward compatibility guarantees for AOTInductor-compiled models.

[Beta] FP16 support for X86 CPUs (both eager and Inductor modes)

Float16 datatype is commonly used for reduced memory usage and faster computation in AI inference and training. CPUs like the recently launched Intel® Xeon® 6 with P-Cores support Float16 datatype with native accelerator AMX. Float16 support on X86 CPUs was introduced in PyTorch 2.5 as a prototype feature, and now it has been further improved for both eager mode and Torch.compile + Inductor mode, making it Beta level feature with both functionality and performance verified with a broad scope of workloads.

PROTOTYPE FEATURES

[Prototype] Improved PyTorch user experience on Intel GPUs

PyTorch user experience on Intel GPUs is further improved with simplified installation steps, Windows release binary distribution and expanded coverage of supported GPU models including the latest Intel® Arc™ B-Series discrete graphics. Application developers and researchers seeking to fine-tune, inference and develop with PyTorch models on Intel® Core™ Ultra AI PCs and Intel® Arc™ discrete graphics will now be able to directly install PyTorch with binary releases for Windows, Linux and Windows Subsystem for Linux 2.

  • Simplified Intel GPU software stack setup to enable one-click installation of the torch-xpu PIP wheels to run deep learning workloads in an out of the box fashion, eliminating the complexity of installing and activating Intel GPU development software bundles.
  • Windows binary releases for torch core, torchvision and torchaudio have been made available for Intel GPUs, and the supported GPU models have been expanded from Intel® Core™ Ultra Processors with Intel® Arc™ Graphics, Intel® Core™ Ultra Series 2 with Intel® Arc™ Graphics and Intel® Arc™ A-Series Graphics to the latest GPU hardware Intel® Arc™ B-Series graphics.
  • Further enhanced coverage of Aten operators on Intel GPUs with SYCL* kernels for smooth eager mode execution, as well as bug fixes and performance optimizations for torch.compile on Intel GPUs.

For more information regarding Intel GPU support, please refer to Getting Started Guide.

[Prototype] FlexAttention support on X86 CPU for LLMs

FlexAttention was initially introduced in PyTorch 2.5 to provide optimized implementations for Attention variants with a flexible API. In PyTorch 2.6, X86 CPU support for FlexAttention was added through TorchInductor CPP backend. This new feature leverages and extends current CPP template abilities to support broad attention variants (e.x.: PageAttention, which is critical for LLMs inference) based on the existing FlexAttention API, and brings optimized performance on x86 CPUs. With this feature, it’s easy to use FlexAttention API to compose Attention solutions on CPU platforms and achieve good performance.

[Prototype] Dim.AUTO

Dim.AUTO allows usage of automatic dynamic shapes with torch.export. Users can export with Dim.AUTO and “discover” the dynamic behavior of their models, with min/max ranges, relations between dimensions, and static/dynamic behavior being automatically inferred.

This is a more user-friendly experience compared to the existing named-Dims approach for specifying dynamic shapes, which requires the user to fully understand the dynamic behavior of their models at export time. Dim.AUTO allows users to write generic code that isn’t model-dependent, increasing ease-of-use for exporting with dynamic shapes.

Please see torch.export tutorial for more information.

[Prototype] CUTLASS and CK GEMM/CONV Backends for AOTInductor

The CUTLASS and CK backend adds kernel choices for GEMM autotuning in Inductor. This is now also available in AOTInductor which can run in C++ runtime environments. A major improvement to the two backends is improved compile-time speed by eliminating redundant kernel binary compilations and dynamic shapes support.

There is a known regression (#144152) that torch.device(0) makes CUDA init fail in subprocess since PyTorch 2.5.0. There was an attempt to fix the regressions, but it caused some complications and was reverted.

When this flag is set, instead of using the usual pickle module, torch.load uses a custom unpickler constrained to call only functions and classes needed for loading state dictionaries and basic types.
