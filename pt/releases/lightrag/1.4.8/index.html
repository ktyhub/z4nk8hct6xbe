LightRAG v1.4.8

Importar notas

  1. Introduziu uma consulta de dados brutos API /query/data, permitindo que os desenvolvedores recuperem dados brutos completos recuperados pelo LightRAG para processamento refinado.
  2. Otimizou o sistema para lidar com eficiência com centenas de documentos e centenas de milhares de dez relacionamentos em um trabalho em lote, resolvendo o atraso da interface do usuário e melhorando a estabilidade geral do sistema.
  3. Eliminar entidades com nomes numéricos curtos que impactem negativamente o desempenho e os resultados da consulta; eliminando nomes contendo apenas dois dígitos, nomes com menos de seis caracteres e nomes misturados com dígitos e pontos, como 1.1, 12.3, 1.2.3 etc.
  4. Melhora significativamente a quantidade e a qualidade da extração de entidades e relações para modelos de parâmetros menores, levando a uma melhoria substancial no desempenho da consulta
  5. Otimizou a engenharia imediata para os modelos Qwen3-30B-A3B-Instruct e gpt-oss-120b, incorporando tolerância a falhas direcionada para saídas do modelo.
  6. Implementação da configuração max tokens e tempreture para evitar loop de saída excessivamente longo ou interminável durante a fase de extração de relacionamento de entidade para respostas de Large Language Model (LLM).
# Increased temperature values may mitigate infinite inference loops in certain LLM, such as Qwen3-30B.
OPENAI_LLM_TEMPERATURE=0.9

# For vLLM/SGLang doployed models, or most of OpenAI compatible API provider
OPENAI_LLM_MAX_TOKENS=9000

# For Ollama Deployed Modeles
OLLAMA_LLM_NUM_PREDICT=9000

# For OpenAI o1-mini or newer modles
OPENAI_LLM_MAX_COMPLETION_TOKENS=9000

O objetivo de definir o parâmetro max tokens é truncar a saída do LLM antes que o tempo limite ocorra, evitando assim falhas na extração de documentos. Isso aborda problemas em que certos blocos de texto (por exemplo, tabelas ou citações) contendo inúmeras entidades e relacionamentos podem levar a resultados de loop excessivamente longos ou até mesmo intermináveis ​​dos LLMs. Essa configuração é particularmente crucial para modelos de parâmetros menores implantados localmente. O valor máximo dos tokens pode ser calculado por esta fórmula: LLM_TIMEOUT * llm_output_tokens/second (ou seja, 9000 = 180s * 50 tokens/s)

LightRAG v1.4.8

Highlights

  • Raw-data retrieval API — New query_data() and /query/data expose complete recalled raw data as a structured response, enabling custom reranking, citation handling, and post-processing instead of relying solely on generated answers (PRs #2036, #2100).
  • Stronger small-model extraction — Reworked prompts, parser robustness, prompt caching, and fault tolerance improve entity/relation extraction with smaller local models. Validate extraction on a representative corpus after upgrading, since graph contents—and therefore query results—will change (PRs #2051, #2072, #2076, #2093).
  • Bounded extraction output — Configure provider-appropriate token limits: OPENAI_LLM_MAX_TOKENS, OPENAI_LLM_MAX_COMPLETION_TOKENS for o1-mini/newer models, or OLLAMA_LLM_NUM_PREDICT. This truncates runaway table/citation extraction before request timeouts; size limits as LLM_TIMEOUT × output tokens/sec (e.g. 9000 = 180s × 50). Higher OPENAI_LLM_TEMPERATURE, such as 0.9, may help with looping models like Qwen3-30B.
  • Stricter entity-name filtering — Extraction now drops two-digit numeric names, names shorter than six characters, and dotted numeric labels such as 1.1 and 1.2.3. This reduces noise and graph size, but can remove meaningful identifiers; audit affected labels and expect leaner graphs after re-extraction.
  • Batch scale and operational stability — Processing is optimized for hundreds of documents and hundreds of thousands of entity relationships. Vector-database retries, a Gunicorn timeout increase from 210s to 300s, and clearer error context reduce partial failures. Pipeline status history is capped at the latest 1,000 entries, so persist it separately if you need a complete audit trail (PRs #2055, #2064, #2078).
  • Breaking changes — None announced.

Import Notes

  1. Introduced a raw data query API /query/data, enabling developers to retrieve complete raw data recalled by LightRAG for fine-grained processing.
  2. Optimized the system to efficiently handle hundreds of documents and hundreds of thousands of ten-relationships in one batch job, resolving UI lag and enhancing overall system stability.
  3. Drop entities with short numeric names that negatively impact performance and query results; dropping names containing only two digits, names shorter than six characters, and names mixed with digits and dots, like 1.1, 12.3, 1.2.3 etc.
  4. Significantly improves the quantity and quality of entity and relation extraction for smaller parameter models, leading to a substantial improvement in query performance
  5. Optimized the prompt engineering for Qwen3-30B-A3B-Instruct and gpt-oss-120b models, incorporating targeted fault tolerance for model outputs.
  6. Implemented max tokens and tempreture configuration to prevent excessively long or endless output loop during the entity relationship extraction phase for Large Language Model (LLM) responses.
# Increased temperature values may mitigate infinite inference loops in certain LLM, such as Qwen3-30B.
OPENAI_LLM_TEMPERATURE=0.9

# For vLLM/SGLang doployed models, or most of OpenAI compatible API provider
OPENAI_LLM_MAX_TOKENS=9000

# For Ollama Deployed Modeles
OLLAMA_LLM_NUM_PREDICT=9000

# For OpenAI o1-mini or newer modles
OPENAI_LLM_MAX_COMPLETION_TOKENS=9000

The purpose of setting max tokens parameter is to truncate LLM output before timeouts occur, thereby preventing document extraction failures. This addresses issues where certain text blocks (e.g., tables or citations) containing numerous entities and relationships can lead to overly long or even endless loop outputs from LLMs. This setting is particularly crucial for locally deployed, smaller-parameter models. Max tokens value can be calculated by this formula: LLM_TIMEOUT * llm_output_tokens/second (i.e. 9000 = 180s * 50 tokens/s)
