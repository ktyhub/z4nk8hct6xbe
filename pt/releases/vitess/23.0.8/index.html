#vitess v23.0.8

Lançamento do Vitess v23.0.8

Resumo

Valores sql_mode não suportados são rejeitados

VTGgate

O VTGate já rejeitou instruções SET sql_mode = ... que habilitam um modo que o analisador Vitess não suporta (ANSI_QUOTES, NO_BACKSLASH_ESCAPES, PIPES_AS_CONCAT, REAL_AS_FLOAT). A verificação comparou os nomes dos modos textualmente e pode ser ignorada. O VTGate agora implementa a semântica de atribuição sql_mode do MySQL 8.x e valida cada atribuição em relação a eles:

  • A configuração de um modo não suportado é rejeitada mesmo quando o MySQL subjacente já roda com esse modo, ou seja, quando o SET não alteraria o valor. Tais declarações foram bem-sucedidas anteriormente, embora o VTGate não analise consultas nesses modos. O modo de combinação ANSI também é rejeitado, pois habilita ANSI_QUOTES, PIPES_AS_CONCAT e REAL_AS_FLOAT.
  • IGNORE_SPACE e HIGH_NOT_PRECEDENCE agora também são rejeitados. Eles são os dois modos restantes que alteram a forma como o texto SQL é interpretado. O analisador Vitess não os respeita, então o VTGate analisaria as consultas de maneira diferente das promessas do sql_mode da sessão.
  • Nomes de modos desconhecidos e valores numéricos inválidos falham com os próprios erros do MySQL: ER_WRONG_VALUE_FOR_VAR (1231) e ER_UNSUPPORTED_SQL_MODE (3899) para os bits de modos removidos em MySQL 8.0.
  • Os valores numéricos são decodificados em relação à máscara de bits sql_mode do MySQL. Por exemplo, SET sql_mode = 1048576 relata que NO_BACKSLASH_ESCAPES não é compatível. Valores numéricos válidos são aceitos.
  • Os valores constantes são validados no momento do planejamento, sem ida e volta do fragmento. Isso inclui expressões constantes como CONCAT sobre literais e também se aplica quando --enable-system-settings está desabilitado. Expressões não constantes são validadas em tempo de execução, uma vez conhecido seu valor.

VTTablet

VTTablet aplica a mesma validação em seus próprios pontos de entrada e retorna os mesmos erros: configurações de conexão, no pool de configurações e em conexões reservadas e instruções SET sql_mode de escopo de sessão. Isso cobre clients que ignoram a validação do VTGate, como VTGates que ainda não foram atualizados e clients que se comunicam diretamente com o serviço de consulta. As dicas do otimizador SET_VAR são encaminhadas para MySQL inalteradas. Cada conexão MySQL que Vitess cria agora remove os modos que alteram a forma como o texto SQL é interpretado da sessão sql_mode que ele herda do valor global do servidor. Todos os outros modos, como os modos estritos e os modos de data zero, são mantidos. Isso se aplica a todos os componentes: serviço de consulta, rastreamento de esquema, pulsações, gerenciamento de replicação, DDL online, VReplication e VDiff e conexões com servidores MySQL externos. O sql_mode global não foi alterado.

Impacto

  • Clients que executam SET sql_mode com um modo não suportado, incluindo ANSI, IGNORE_SPACE e HIGH_NOT_PRECEDENCE, agora recebem um erro. Isso também acontece quando o SET corresponde ao sql_mode atual do backend. Clients que definem nomes de modo MySQL também rejeitariam e receberiam um erro.
  • Durante uma atualização contínua, os VTTablets normalmente são atualizados antes dos VTGates. Uma sessão que define um sql_mode agora rejeitado por meio de um VTGate que ainda não foi atualizado começa a receber erros de VTTablets atualizados.
  • Um backend cujo sql_mode global inclui um desses modos o mantém, mas as sessões Vitess não o herdam mais. Consulte #20883 para obter detalhes.

Tabela ACL: chamadores com todas as funções em todas as tabelas podem executar instruções cujas tabelas não podem ser determinadas

v23.0.7 começou a negar, sob ACL de tabela estrita (--queryserver-config-strict-table-acl), instruções cujas tabelas vttablet não pode determinar (DO, CALL, REPAIR, OPTIMIZE, LOAD DATA e um CREATE TABLE que o analisador do vttablet não pode analisar completamente) para cada chamador fora da ACL isenta (--queryserver-config-acl-exempt-acl); consulte GHSA-w6mx-2f8x-pqf4. Um chamador que é um leitor, um escritor e um administrador em um grupo de tabelas que cobre todas as tabelas ("table_names_or_prefixes": ["%"]) ocupa todas as funções em qualquer tabela que tal instrução possa tocar, então DO, REPAIR, OPTIMIZE e um CREATE TABLE parcialmente analisado agora são executados para ele. CALL e LOAD DATA permanecem negados mesmo assim, pois um procedimento SQL SECURITY DEFINER é executado com os privilégios de seu definidor e LOAD DATA INFILE lê arquivos no servidor, nenhum dos quais a tabela ACL concede; emita-os como chamadores na ACL isenta. Essas verificações são contadas sob o rótulo undetermined-table-set TableName, em TableACLDenied ou em TableACLAllowed para um chamador com todas as funções em todas as mesas. Com simulação (--queryserver-config-enable-table-acl-dry-run), apenas as instruções que a verificação negaria o incremento TableACLPseudoDenied. Consulte #21349 para obter detalhes.

Conjuntos de caracteres de conexão restritos

--db-charset, e os outros locais onde um conjunto de caracteres de conexão MySQL está configurado, não aceitam mais sjis, cp932, gb18030, gbk, big5, ucs2, utf16, utf16le ou utf32, seja fornecido como um conjunto de caracteres ou como um de seus agrupamentos. Um tablet configurado com um deles falha ao iniciar, o VTGate recusa um SET de character_set_client, character_set_connection, character_set_results ou collation_connection para um deles, ou para um nome que não seja um conjunto de caracteres ou agrupamento, que costumava responder com OK e ignorar, e VTTablet recusa uma configuração ou instrução SET que mudaria a conexão de uma sessão para um deles. Um client ainda pode solicitar um deles no aperto de mão: o VTGate lê suas instruções byte por byte, como faz a conexão do tablet com MySQL, portanto, eles não podem sair de um literal. O Vitess analisa e escapa o texto SQL byte por byte e, nesses conjuntos de caracteres, o segundo byte de um caractere pode ser uma barra invertida ou uma aspa invertida, portanto, o texto neles foi mal analisado ou corrompido em seu caminho pelo Vitess. Use utf8mb4 como conjunto de caracteres de conexão. Tabelas e colunas ainda podem ser declaradas com qualquer um desses conjuntos de caracteres; MySQL converte entre eles e o conjunto de caracteres de conexão. Isso corrige GHSA-c28j-qmfx-4gxp. Consulte #21392 e #21465 para obter detalhes.

Charset e nomes de agrupamento são citados quando regenerados

Um nome de conjunto de caracteres, agrupamento, mecanismo, espaço de tabela ou analisador de texto completo agora é decodificado quando analisado e escrito de volta como um único token quando Vitess regenera a instrução: simples quando é um conjunto de caracteres, agrupamento, mecanismo, tipo de índice ou nome de analisador conhecido, caso contrário, entre aspas invertidas. Consequências visíveis ao usuário:

  • Um nome entre aspas é normalizado. COLLATE 'utf8_bin' regenera como COLLATE utf8_bin — as grafias entre aspas e sem aspas significam o mesmo nome, e a forma decodificada é o que é armazenado. Qualquer coisa que compare a forma impressa dessas declarações byte por byte verá a nova ortografia.
  • Apenas nomes conhecidos permanecem vazios. Um conjunto de caracteres ou nome de agrupamento de qualquer versão MySQL ou MariaDB, um mecanismo de armazenamento conhecido como InnoDB ou memory, os tipos de índice BTREE, HASH e RTREE, os analisadores ngram e mecab e os espaços de tabela innodb_system e innodb_file_per_table são gravados de volta à medida que são foram soletrados. Qualquer outro nome é entre aspas: TABLESPACE ts regenera como TABLESPACE `ts` , and so does an engine Vitess does not know or a keyword used as a name. WITH PARSER accepts only a plain identifier, so a known name that is a keyword is quoted there: WITH PARSER `memory` keeps its quoting where ENGINE memory does not. binary is still bare where the grammar has a BINARY alternative, except directly before the BINARY attribute: CHARACTER SET 'binary' BINARY regenerates as CHARACTER SET `binário` BINARY.
  • COLLATE binary em uma expressão é citado. expr COLLATE binary regenera como expr COLLATE `binary` , because MySQL's expression COLLATE only accepts binary quoted. Column, table and database COLLATE binária and CHARACTER SET binário permanece vazio.
  • Um nome vazio de conjunto de caracteres, agrupamento, mecanismo ou espaço de tabela de partição é rejeitado. CHARACTER SET '' e COLLATE '' em uma coluna, uma tabela, ALTER TABLE ... CONVERT TO, CAST/CONVERT, CONVERT ... USING, CHAR ... USING, SELECT ... INTO OUTFILE e uma expressão, ENGINE '' em uma tabela ou partição e uma partição TABLESPACE '' não analisa mais. Um nome vazio nessas posições é indistinguível da cláusula ausente, portanto, ele teria sido previamente descartado ou mutilado e uma declaração rejeitada por MySQL poderia ter se tornado válida e diferente. Instruções não DDL obtêm o erro diretamente; O DDL retorna para uma análise parcial, então o próprio texto do client é encaminhado e MySQL o rejeita. SET NAMES ... COLLATE '' e SET CHARACTER SET ... COLLATE '', que costumavam analisar e descartar o agrupamento, agora também são erros de análise; MySQL rejeita ambos. CREATE/ALTER DATABASE ... CHARACTER SET '' e COLLATE '' permanecem inalterados: eles ainda analisam e são gravados como ''.
  • ENCRYPTION requer um valor entre aspas. CREATE/ALTER DATABASE ... ENCRYPTION N não analisa mais completamente, correspondendo a MySQL, que aceita apenas 'Y' ou 'N' como uma string entre aspas. Tal declaração agora recorre a uma análise parcial, em vez de ser regenerada em uma grafia que MySQL recusaria. Isso corrige GHSA-j8pc-mcwq-qrg6. Consulte #21435 para obter detalhes.

Os modos VTAdmin VExplain que executam a instrução requerem a ação execute

O VExplain API do VTAdmin foi autorizado com a ação get, mas VEXPLAIN QUERIES, ALL e TRACE executam a instrução que explicam, portanto, um ator autorizado apenas a ler poderia alterar os dados por meio dela (GHSA-c2r8-grjp-w8c2). Esses modos agora exigem a nova ação execute no recurso VExplain; PLAN e KEYS, que planejam apenas a declaração, ainda exigem apenas get. Para esses modos, o VTAdmin também aceita apenas um SELECT sem INTO, sequencia os próximos valores ou funções de bloqueio de aconselhamento e os executa em uma transação somente leitura que é sempre revertida. A página VExplain na UI da web agora tem como padrão PLAN. Migração: concede a ação execute em VExplain aos atores que deverão rodar VEXPLAIN QUERIES, ALL ou TRACE. As regras que concedem todas as ações (*) e --no-rbac já incluem. Impacto: um ator com apenas get em VExplain recebe um erro unauthorized de VEXPLAIN QUERIES, ALL e TRACE. Consulte #21396 para obter detalhes.

vitess v23.0.8

Release of Vitess v23.0.8

Summary

Unsupported sql_mode values are rejected

VTGate

VTGate already rejected SET sql_mode = ... statements that enable a mode the Vitess parser does not support (ANSI_QUOTES, NO_BACKSLASH_ESCAPES, PIPES_AS_CONCAT, REAL_AS_FLOAT). The check compared mode names textually and could be bypassed. VTGate now implements MySQL 8.x's sql_mode assignment semantics and validates every assignment against them:

  • Setting an unsupported mode is rejected even when the underlying MySQL already runs with that mode, that is, when the SET would not change the value. Such statements previously succeeded, even though VTGate does not parse queries under these modes. The combination mode ANSI is rejected as well, because it enables ANSI_QUOTES, PIPES_AS_CONCAT, and REAL_AS_FLOAT.
  • IGNORE_SPACE and HIGH_NOT_PRECEDENCE are now also rejected. They are the two remaining modes that change how SQL text is interpreted. The Vitess parser does not honor them, so VTGate would parse queries differently than the session's sql_mode promises.
  • Unknown mode names and invalid numeric values fail with MySQL's own errors: ER_WRONG_VALUE_FOR_VAR (1231), and ER_UNSUPPORTED_SQL_MODE (3899) for the bits of modes removed in MySQL 8.0.
  • Numeric values decode against MySQL's sql_mode bitmask. For example, SET sql_mode = 1048576 reports that NO_BACKSLASH_ESCAPES is unsupported. Valid numeric values are accepted.
  • Constant values are validated at planning time, with no shard round trip. This includes constant expressions such as CONCAT over literals, and it also applies when --enable-system-settings is disabled. Non-constant expressions are validated at execution time, once their value is known.

VTTablet

VTTablet applies the same validation at its own entry points and returns the same errors: connection settings, on the settings pool and on reserved connections, and session-scope SET sql_mode statements. This covers clients that bypass VTGate's validation, such as VTGates that are not upgraded yet and clients that talk to the query service directly. SET_VAR optimizer hints are forwarded to MySQL unchanged.

Every MySQL connection Vitess creates now strips the modes that change how SQL text is interpreted from the session sql_mode it inherits from the server's global value. All other modes, such as the strict modes and the zero-date modes, are kept. This applies to every component: query serving, schema tracking, heartbeats, replication management, Online DDL, VReplication and VDiff, and connections to external MySQL servers. The global sql_mode is not changed.

Impact

  • Clients that run SET sql_mode with an unsupported mode, including ANSI, IGNORE_SPACE and HIGH_NOT_PRECEDENCE, now receive an error. This also happens when the SET matches the backend's current sql_mode. Clients that set mode names MySQL would itself reject receive an error as well.
  • During a rolling upgrade, VTTablets are typically upgraded before VTGates. A session that sets a now-rejected sql_mode through a VTGate that is not upgraded yet starts receiving errors from upgraded VTTablets.
  • A backend whose global sql_mode includes one of these modes keeps it, but Vitess sessions no longer inherit it.

See #20883 for details.

Table ACL: callers with every role on every table may run statements whose tables cannot be determined

v23.0.7 began denying, under strict table ACL (--queryserver-config-strict-table-acl), statements whose tables vttablet cannot determine (DO, CALL, REPAIR, OPTIMIZE, LOAD DATA, and a CREATE TABLE that vttablet's parser cannot fully parse) for every caller outside the exempt ACL (--queryserver-config-acl-exempt-acl); see GHSA-w6mx-2f8x-pqf4. A caller that is a reader, a writer and an admin in a table group covering every table ("table_names_or_prefixes": ["%"]) holds every role on any table such a statement could touch, so DO, REPAIR, OPTIMIZE and a partially parsed CREATE TABLE now run for it. CALL and LOAD DATA remain denied even then, since a SQL SECURITY DEFINER procedure runs with its definer's privileges and LOAD DATA INFILE reads files on the server, neither of which table ACL grants; issue them as a caller in the exempt ACL.

These checks are counted under the undetermined-table-set TableName label, in TableACLDenied, or in TableACLAllowed for a caller with every role on every table. With dry-run (--queryserver-config-enable-table-acl-dry-run), only the statements the check would deny increment TableACLPseudoDenied.

See #21349 for details.

Connection character sets restricted

--db-charset, and the other places a MySQL connection character set is configured, no longer accept sjis, cp932, gb18030, gbk, big5, ucs2, utf16, utf16le or utf32, whether given as a character set or as one of its collations. A tablet configured with one of them fails to start, VTGate refuses a SET of character_set_client, character_set_connection, character_set_results or collation_connection to one of them, or to a name that is not a character set or collation, which it used to answer with OK and ignore, and VTTablet refuses a setting or SET statement that would switch a session's connection to one of them. A client may still ask for one of them at the handshake: VTGate reads its statements byte by byte, as the tablet's connection to MySQL does, so they cannot break out of a literal.

Vitess parses and escapes SQL text byte by byte, and in these character sets the second byte of a character can be a backslash or a back quote, so text in them was misparsed or corrupted on its way through Vitess. Use utf8mb4 as the connection character set instead. Tables and columns can still be declared with any of these character sets; MySQL converts between them and the connection character set.

This fixes GHSA-c28j-qmfx-4gxp.

See #21392 and #21465 for details.

Charset and collation names are quoted when regenerated

A charset, collation, engine, tablespace or full-text parser name is now decoded when parsed, and written back as a single token when Vitess regenerates the statement: bare when it is a known charset, collation, engine, index type or parser name, back-quoted otherwise.

User-visible consequences:

  • A quoted name is normalized. COLLATE 'utf8_bin' regenerates as COLLATE utf8_bin — the quoted and unquoted spellings mean the same name, and the decoded form is what is stored. Anything comparing the printed form of these statements byte for byte sees the new spelling.
  • Only known names stay bare. A charset or collation name of any MySQL or MariaDB version, a known storage engine such as InnoDB or memory, the BTREE, HASH and RTREE index types, the ngram and mecab parsers, and the innodb_system and innodb_file_per_table tablespaces are written back as they were spelled. Any other name is back-quoted: TABLESPACE ts regenerates as TABLESPACE `ts` , and so does an engine Vitess does not know or a keyword used as a name. WITH PARSER accepts only a plain identifier, so a known name that is a keyword is quoted there: WITH PARSER `memory` keeps its quoting where ENGINE memory does not. binary is still bare where the grammar has a BINARY alternative, except directly before the BINARY attribute: CHARACTER SET 'binary' BINARY regenerates as CHARACTER SET `binary` BINARY.
  • COLLATE binary in an expression is quoted. expr COLLATE binary regenerates as expr COLLATE `binary` , because MySQL's expression COLLATE only accepts binary quoted. Column, table and database COLLATE binary and CHARACTER SET binary stay bare.
  • An empty charset, collation, engine or partition tablespace name is rejected. CHARACTER SET '' and COLLATE '' on a column, a table, ALTER TABLE ... CONVERT TO, CAST/CONVERT, CONVERT ... USING, CHAR ... USING, SELECT ... INTO OUTFILE and an expression, ENGINE '' on a table or a partition, and a partition's TABLESPACE '' no longer parse. An empty name in these positions is indistinguishable from the clause being absent, so it would previously have been dropped or mangled and a statement MySQL rejects could have become a valid, different one. Non-DDL statements get the error directly; DDL falls back to a partial parse, so the client's own text is forwarded and MySQL rejects it. SET NAMES ... COLLATE '' and SET CHARACTER SET ... COLLATE '', which used to parse and discard the collation, are now parse errors too; MySQL rejects both. CREATE/ALTER DATABASE ... CHARACTER SET '' and COLLATE '' are unchanged: they still parse and are written back as ''.
  • ENCRYPTION requires a quoted value. CREATE/ALTER DATABASE ... ENCRYPTION N no longer fully parses, matching MySQL, which only accepts 'Y' or 'N' as a quoted string. Such a statement now falls back to a partial parse rather than being regenerated into a spelling MySQL would refuse.

This fixes GHSA-j8pc-mcwq-qrg6.

See #21435 for details.

VTAdmin VExplain modes that run the statement require the execute action

VTAdmin's VExplain API was authorized with the get action, but VEXPLAIN QUERIES, ALL and TRACE run the statement they explain, so an actor allowed only to read could change data through it (GHSA-c2r8-grjp-w8c2). Those modes now require the new execute action on the VExplain resource; PLAN and KEYS, which only plan the statement, still require only get. For those modes VTAdmin also accepts only a SELECT without INTO, sequence next-values or advisory lock functions, and runs them in a read-only transaction that is always rolled back. The VExplain page in the web UI now defaults to PLAN.

Migration: grant the execute action on VExplain to the actors that should run VEXPLAIN QUERIES, ALL or TRACE. Rules that grant all actions (*) and --no-rbac already include it.

Impact: an actor with only get on VExplain gets an unauthorized error from VEXPLAIN QUERIES, ALL and TRACE.

See #21396 for details.

Security fixes

  • Fixes GHSA-73pp-99vw-h5g8: SQL injection through VStream LastPK values. See #21377.
  • Fixes GHSA-92cc-q2h6-m2vr: SQL injection through convert_tz() arguments in a VStream filter. See #21377.
  • Fixes GHSA-8w3p-4xg5-rm9w: SQL injection through table names in Online DDL statements. See #21381.
  • Fixes GHSA-x56j-8c72-5xgg: SQL injection through the caller ID in query annotations (--queryserver-config-annotate-queries). See #21369.
  • Fixes GHSA-m282-7w35-g77m: SQL injection through a global SET variable name. See #21390.
  • Fixes GHSA-9248-hccp-qf8f: SQL injection through DATE, TIME and TIMESTAMP literals. See #21389.
  • Fixes GHSA-9rx3-8pwm-c228: SQL injection through a session variable value carried in a SET_VAR hint. See #21388.
  • Fixes GHSA-pfg5-ppc7-ff45: SQL hidden from parsing and table ACL checks in a trailing comment. See #21387.
  • Fixes GHSA-xf67-9r78-xv82: SQL injection through malformed numeric bind variables. See #21386.
  • Fixes GHSA-3fr2-mqr5-r5x5: VTAdmin API routes that change cluster state accepted cross-site GET requests. See #21397.
  • Fixes GHSA-78h7-x6qm-xpr8: VTAdmin's ReloadSchemaShard did not check RBAC. See #21394.
