druida druida-0.6.105

Atualizando

Ao atualizar o Druid sem tempo de inatividade, é altamente recomendável atualizar os nós históricos e os nós em tempo real antes de atualizar a camada do corretor. As alterações nas consultas normalmente são compatíveis com uma versão antiga do corretor e uma nova versão do nó histórico, mas não vice-versa. Nosso processo de atualização contínua recomendado é:

  1. serviço de indexação/nós em tempo real
  2. nós históricos (com uma espera entre cada nó, o tempo de espera corresponde ao tempo que leva para um nó histórico reiniciar e carregar todos os segmentos armazenados em cache localmente)
  3. Nós do corretor
  4. nós coordenadores

Release Notes

  • Os nós históricos agora podem usar e manter um cache local (desativado por padrão). Esse cache pode ser baseado em heap ou memcached. Isso permite que os nós históricos mesclem os resultados localmente e reduz grande parte da pressão de memória observada nos corretores enquanto extraem um grande número de resultados do cache. O preenchimento do cache agora também é feito de maneira assíncrona.
  • Nó roteador experimental. Estamos experimentando um nó roteador totalmente assíncrono que pode rotear consultas para diferentes corretores, dependendo da consulta real. Atualmente, o nó roteador toma decisões sobre com qual intermediário conversar com base nas regras do nó coordenador. Nosso objetivo é, em algum momento, fundir a lógica do roteador e do corretor e avançar para corretores hierárquicos.
  • Otimização pós-agregação. Otimizamos os cálculos de agregações de postagens (anteriormente, as agregações de postagens eram calculadas mais do que o necessário). Em alguns benchmarks iniciais, isso pode levar a uma melhoria de 20% a 30% nas consultas que envolvem agregações de postagens.
  • Suporte hyperUnique em groupBys. Corrigimos um problema relatado em que groupBys relatava resultados incorretos ao usar métricas complexas (especialmente hyperUnique).
  • Suporte a funções de extração de dimensão em groupBy
  • Threads persistentes e persist-n-merge agora não bloqueiam mais uns aos outros durante a ingestão em tempo real. Adicionamos um parâmetro para limitar a ingestão em tempo real há alguns meses, e o que vimos é que taxas de ingestão muito altas que levam a um grande número de persistências intermediárias podem ser bloqueadas enquanto aguardamos a conclusão de uma operação de transferência. Este comportamento foi agora melhorado. Agora você também pode definir maxPendingPersists no encanador.
  • Otimizações de desempenho hyperUnique: agregações aproximadamente 30-50% mais rápidas

Outras coisas diversas

  • Corrigir estouro de número inteiro em partições baseadas em hash
  • Suporte para objetos JSON arbitrários no contexto de consulta
  • Os registros de solicitação agora incluem estatísticas de tempo de consulta
  • Suporte Hadoop 2.3 por padrão
  • Atualização para o Jetty 9
  • Não requer conexões de banco de dados válidas para teste
  • Lidar com NaN / Infinity retornados por nós de computação
  • melhor relatório de erros para casos em que o ChainedExecutionQueryRunner lança NPEs

Extensões:

  • O armazenamento HDFS agora deve funcionar melhor com Cloudera CDH4
  • Armazenamento S3: as ACLs de objeto agora são consistentemente padronizadas como "controle total do proprietário do bucket"

druid druid-0.6.105

Updating

When updating Druid with no downtime, we highly recommend updating historical nodes and real-time nodes before updating the broker layer. Changes in queries are typically compatible with an old broker version and a new historical node version, but not vice versa. Our recommended rolling update process is:

  1. indexing service/real-time nodes
  2. historical nodes (with a wait in between each node, the wait time corresponds to how long it takes for a historical node to restart and load all locally cached segments)
  3. broker nodes
  4. coordinator nodes

Release Notes

  • Historical nodes can now use and maintain a local cache (disabled by default). This cache can either be heap based or memcached. This allows historical nodes to merge results locally and reduces much of the memory pressure seen on brokers while pulling a large number of results from the cache. Populating the cache is also now done in an asynchronous manner.
  • Experimental router node. We’ve been experimenting with a fully asynchronous router node that can route queries to different brokers depending on the actual query. Currently, the router node makes decisions about which broker to talk to based on rules from the coordinator node. It is our goal to at some point merge the router and broker logic and move towards hierarchical brokers.
  • Post aggregation optimization. We’ve optimized calculations of post aggregations (previously post aggs were being calculated more than necessary). In some initial benchmarks, this can lead to 20%-30% improvement in queries that involve post aggregations.
  • Support hyperUnique in groupBys. We’ve fixed a reported problem where groupBys would report incorrect results when using complex metrics (especially hyperUnique).
  • Support dimension extraction functions in groupBy
  • Persist and persist-n-merge threads now no longer block each other during real-time ingestion. We added a parameter for throttling real-time ingestion a few months ago, and what we’ve seen is that very high ingestion rates that lead to a high number of intermediate persists can be blocked while waiting for a hand-off operation to complete. This behavior has now been improved. You are also now able to set maxPendingPersists in the plumber.
  • hyperUnique performance optimizations: ~30-50% faster aggregations

Miscellaneous other things

  • Fix integer overflow in hash based partitions
  • Support for arbitrary JSON objects in query context
  • Request logs now include query timing statistics
  • Hadoop 2.3 support by default
  • Update to Jetty 9
  • Do not require valid database connections for testing
  • Gracefully handle NaN / Infinity returned by compute nodes
  • better error reporting for cases where the ChainedExecutionQueryRunner throws NPEs

Extensions:

  • HDFS Storage should now work better with Cloudera CDH4
  • S3 Storage: object ACLs now consistently default to "bucket owner full control"
