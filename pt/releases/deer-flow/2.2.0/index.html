DeerFlow 2.2.0

DeerFlow 2.2 transforma o equipamento de superagente 2.1 em uma plataforma de nível de implantação com foco em operar em escala e delegar com trust: programado tarefas se transformam em fluxos de trabalho orientados por objetivos com execução justa de vários proprietários, todos subsistema de canais de IM para fluxos de trabalho é executado em vários gateways casos, a plataforma de extensão fornece plug-ins full-stack, conhecimento a recuperação torna-se independente do provedor com citações e modelos verificáveis, memória e canais ganham gerenciamento de nível de produção - reforçado por falhas fechadas padrões, criptografia de credenciais em repouso e uploads e caminhos muito mais rígidos camada.

Este lançamento encerra o marco 2.2.0 com 1.068 PRs mesclados desde o lançamento do 2.1.0.

⚠️ Mudanças importantes

  • Desenvolvedor local vincula loopback — make dev / make start não escuta mais todas as interfaces; as portas 2026/8001/3000 e /setup permanecem fora de LAN/VPN. Definir BIND_HOST=0.0.0.0 em .env para expor a pilha e observe que os valores nginx seria interpretado incorretamente (0, 1.2.3, IPv6 entre colchetes) agora são rejeitados antes qualquer serviço é interrompido. ([#6587], [#6635])
  • As credenciais armazenadas são criptografadas em repouso — um novo ambiente somente DEER_FLOW_CREDENTIALS_KEY (Fernet, separado por vírgula para rotação) protege Credenciais de canal de mensagens instantâneas e tokens de atualização MCP OAuth; multi-instância implantações com channel_connections ou OAuth com token de atualização se recusam a comece sem ele. As credenciais do bot de mensagens instantâneas são transferidas do texto simples channels/runtime-config.json no channel_runtime_configs compartilhado tabela – os bots existentes são importados uma vez na primeira inicialização e um downgrade deve entre novamente nos bots configurados pela UI. ([#6611], [#7207], [#6988])
  • A porta multiprocesso é mais rigorosa — GATEWAY_WORKERS > 1 (ou deployment.multi_instance: true ou WEB_CONCURRENCY) agora requer o Ponte de fluxo Redis; a ponte de memória não inicia mais o multiprocesso. O nova seção channels.leader_lease deve permanecer habilitada quando um IM não GitHub canal está configurado. ([#6328], [#6746], [#6252])
  • Alteração de contratos do agendador — Erros /api/scheduled-tasks* retornam um envelope {"detail": {"code", "message", "params"}} estruturado (leia detail.message); um novo scheduler.max_concurrent_runs_per_user (padrão 2) limita as execuções programadas simultâneas de um proprietário; Os avisos de mensagens instantâneas são honestos, localizado e enviado no máximo uma vez por ocorrência; Parede once ignorada por DST os tempos são rejeitados com 422. ([#6378], [#6393], [#7281])
  • Cascatas de exclusão de threads — excluir um thread agora também remove suas execuções, executar eventos e feedback, para que os tópicos excluídos não possam mais ser lidos ou herdado por IDs de thread recriados. ([#5535])
  • O histórico vinculado ao modelo permanece apenas anexado - carga útil write_file substituída elisão torna-se opcional (tool_output.elide_superseded_writes, padrão false) porque elision reescreveu segmentos de solicitação anteriores e invalidou caches de prompt do provedor; habilidade allowed-tools é apenas metadados de compatibilidade e não oculta mais ou bloqueia ferramentas. ([#7319], [#7455], [#6935])
  • A autorização de ferramentas abrange ferramentas de middleware — modo de plano write_todos e ferramentas de middleware de extensão agora passam pela autorização da Camada 1 como qualquer outra ferramenta; implantações com uma política tools explícita que as omitiu param vinculando-os. ([#6105])
  • Padrões de segurança com falha fechada — delegado web_fetch/web_capture back-ends (Browserless, Crawl4AI, Firecrawl, fastCRW) selecionam seu URL base e recusar loopback/padrões privados até serem confirmados; o guarda SSRF recusa a gama CGNAT 100.64.0.0/10 (redes de cauda necessitam allow_private_addresses: true); IM allowed_users análise com falha fechada em Slack, DingTalk, QQ e Telegram (uma lista inválida agora nega a todos em vez de permitir silenciosamente); mensagens externas system/developer são rejeitado com 400; verificações de permissão agora cobrem rotas que anteriormente tinham apenas autenticação e USER.md tem escopo por usuário. ([#6531], [#6202], [#6230], [#6742], [#6730], [#5651], [#4989])
  • Uploads e caminhos são rigorosos — Nomes de dispositivos reservados do Windows (incluindo sobrescrito COM¹–COM³ e CONIN$/CONOUT$) são rejeitados uploads, gravações em sandbox e arquivos de habilidades; uploads com o mesmo nome reivindicam o próximo Sufixo _N em vez de truncar; companheiros Markdown convertidos nunca substitua um arquivo existente; anexos rejeitados são registrados em skipped_files e success significam pelo menos um arquivo armazenado; esboço/visualização registros com carimbos de data/hora ausentes são rejeitados — reenvie para restaurar a conversão. ([#6102], [#6148], [#6279], [#6149], [#7388], [#7054], [#7165], [#6165])
  • O menu de barra do compositor foi reduzido — / agora lista apenas as barras integradas /goal e /compact; selecione habilidades como referências @ in-line. ([#6154])
  • Formas API apertam — corpos de execução malformados retornam 422/400 em vez de 500; Os endpoints wait retornam um envelope de erro compatível com SDK para conclusão execuções falhadas; um filtro event_types vazio explícito não corresponde a nada; digitado currículo falha fechado (503) para RunStores que não podem persistir na identidade da solicitação; As conexões MCP do editor web tornam-se por usuário; URIs SQLite file: são rejeitado; campos de configuração inteiros rejeitam booleanos YAML; Modelos da família gpt-6 o padrão é as Respostas API; --print/--json saída 1 em erro LLM substituto. deer-flow v2.2.0

DeerFlow 2.2.0

DeerFlow 2.2 turns the 2.1 super-agent harness into a deployment-grade platform with a focus on operating at scale and delegating with trust: scheduled tasks grow into goal-driven workflows with fair multi-owner execution, every subsystem from IM channels to workflows runs across multiple Gateway instances, the extension platform ships full-stack plugins, knowledge retrieval becomes provider-independent with verifiable citations, and models, memory and channels gain production-grade management — hardened by fail-closed defaults, at-rest credential encryption, and a much stricter uploads and paths layer.

This release closes the 2.2.0 milestone with 1068 merged PRs since the 2.1.0 release.

📖 Full notes: CHANGELOG.md · 中文版

⚠️ Breaking changes

  • Local dev binds loopback — make dev / make start no longer listen on all interfaces; ports 2026/8001/3000 and /setup stay off LAN/VPN. Set BIND_HOST=0.0.0.0 in .env to expose the stack, and note that values nginx would misread (0, 1.2.3, bracketed IPv6) are now rejected before any service stops. ([#6587], [#6635])
  • Stored credentials are encrypted at rest — a new env-only DEER_FLOW_CREDENTIALS_KEY (Fernet, comma-separated for rotation) protects IM channel credentials and MCP OAuth refresh tokens; multi-instance deployments with channel_connections or refresh-token OAuth refuse to start without it. IM bot credentials move from plaintext channels/runtime-config.json into the shared channel_runtime_configs table — existing bots are imported once on first start, and a downgrade must re-enter UI-configured bots. ([#6611], [#7207], [#6988])
  • The multi-process gate is stricter — GATEWAY_WORKERS > 1 (or deployment.multi_instance: true, or WEB_CONCURRENCY) now requires the Redis stream bridge; the memory bridge no longer starts multi-process. The new channels.leader_lease section must stay enabled when a non-GitHub IM channel is configured. ([#6328], [#6746], [#6252])
  • Scheduler contracts change — /api/scheduled-tasks* errors return a structured {"detail": {"code", "message", "params"}} envelope (read detail.message); a new scheduler.max_concurrent_runs_per_user (default 2) caps one owner's concurrent scheduled runs; IM notices are honest, localized, and sent at most once per occurrence; DST-skipped once wall times are rejected with 422. ([#6378], [#6393], [#7281])
  • Thread deletion cascades — deleting a thread now also removes its runs, run events and feedback, so deleted threads can no longer be read or inherited by recreated thread ids. ([#5535])
  • Model-bound history stays append-only — superseded write_file payload elision becomes opt-in (tool_output.elide_superseded_writes, default false) because elision rewrote earlier request segments and invalidated provider prompt caches; skill allowed-tools is compatibility metadata only and no longer hides or blocks tools. ([#7319], [#7455], [#6935])
  • Tool authorization covers middleware tools — plan-mode write_todos and extension middleware tools now pass Layer-1 authorization like any other tool; deployments with an explicit tools policy that omitted them stop binding them. ([#6105])
