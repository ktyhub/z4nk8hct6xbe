[!AVISO] Os submódulos do trl.experimental.async_grpo desapareceram. from trl.experimental.async_grpo.async_grpo_config import AsyncGRPOConfig e importações de async_rollout_worker, packing, vllm_client ou weight_transfer nesse pacote não funcionam mais. Importe o treinador de trl, o loop de implementação de trl.trainer.async_grpo_trainer e o vLLM client de trl.generation.async_vllm_client (renomeado AsyncVLLMClient). from trl.experimental.async_grpo import AsyncGRPOConfig, AsyncGRPOTrainer ainda funciona, com FutureWarning, até v2.0.0.

:mortar_board: AsyncGRPOTrainer agora é um treinador estável

AsyncGRPOTrainer roda GRPO com geração desacoplada do treinamento. Um trabalhador de implementação em um processo em segundo plano transmite conclusões de um servidor vLLM, pontua-as e coloca-as na fila, enquanto o loop de treinamento extrai da fila e atualiza o modelo. As atualizações de geração e gradiente se sobrepõem em vez de se alternarem, e o treinador envia seus novos pesos para o servidor por meio de NCCL a cada etapa do weight_sync_steps. No v1.17 ele residia no trl.experimental.async_grpo: sete arquivos, três maneiras de geração em lote e vinculada, dois argumentos de construtor para troca de internos e nomes de métricas que não correspondiam aos do GRPO. Este ciclo limpou isso em cerca de 40 PRs, rastreados em renomeações de configuração https://github.com/huggingface/trl/issues/7841:, um tempo limite em vez de três, um modo de lote, geração mantida em max_staleness, nomes de métricas do GRPO e verificações de inicialização, um loop de implementação público e o layout de dois arquivos que todo treinador estável possui. Então https://github.com/huggingface/trl/pull/8288 mudou-o para o pacote de nível superior.

# Before
from trl.experimental.async_grpo import AsyncGRPOConfig, AsyncGRPOTrainer

# Now
from trl import AsyncGRPOConfig, AsyncGRPOTrainer

O caminho antigo ainda funciona e emite um FutureWarning (remoção em v2.0.0). O ponto de extensão do loop de implementação fica próximo ao treinador, from trl.trainer.async_grpo_trainer import AsyncRolloutLoop, Rollout, e não é exportado do trl. O chicote OpenEnv/Harbour permanece experimental, como HarnessAsyncGRPOTrainer em trl.experimental.async_grpo.openenv_harness. Os nomes das métricas registradas ainda podem mudar entre as versões. Início rápido, em docs. Instale com pip install trl[vllm,kernels,math_verify] e inicie o servidor vLLM na GPU 0:

CUDA_VISIBLE_DEVICES=0 VLLM_SERVER_DEV_MODE=1 vllm serve Qwen/Qwen3.5-2B \
    --weight-transfer-config '{"backend": "nccl"}' \
    --logprobs-mode processed_logprobs \
    --api-server-count 8 \
    --max-model-len 4096

Então treine na GPU 1 com CUDA_VISIBLE_DEVICES=1 python train_async_grpo.py:

# train_async_grpo.py
from datasets import load_dataset
from trl import AsyncGRPOTrainer
from trl.rewards import accuracy_reward

if __name__ == "__main__":  # the rollout worker is a spawned process that re-imports this script
    dataset = load_dataset("trl-lib/DeepMath-103K", split="train")

    trainer = AsyncGRPOTrainer(
        model="Qwen/Qwen3.5-2B",
        reward_funcs=accuracy_reward,
        train_dataset=dataset,
    )
    trainer.train()

Este exemplo exato é executado de ponta a ponta. É uma verificação de sanidade, não uma comparação de aceleração: | | | | --- | --- | | Modelo/dados/recompensa | Qwen/Qwen3.5-2B, trl-lib/DeepMath-103K, accuracy_reward | | Ferragens | 2x B200: vLLM em uma GPU, o treinador na outra | | Configuração | padrão AsyncGRPOConfig: pesos fp32 com autocast bf16, 8 gerações por prompt, até 2.048 tokens de conclusão, token_budget lido de --max-model-len 4096 | | Tempo de passo | ~7 s/passo, após ~5 min de aquecimento | | Rendimento | ~7 mil tokens treinados/s | | Lacuna de log-prob do instrutor vs vLLM | 0.007 para 0.02 | O que o treinador cobre, tudo documentado na página do treinador:

  • Embalagem de árvore: cada linha de microlote é um prefixo trie, portanto, um prompt compartilhado pelas implementações de um grupo, ou o histórico repetido a cada turno de uma implementação multiturno, é encaminhado uma vez. Híbridos DeltaNet fechados (Qwen3.5, Qwen3.6, Qwen3-Next) são suportados.
  • Treinamento de agentes: tools, environment_factory e implementações multivoltas.
  • Centramento de pontuação com amostragem de importância mascarada como objetivo padrão (score_centering=True). score_centering=False fornece a objetiva clipped do GRPO com a mesma proporção mascarada.
  • Filtragem de grupo com vantagem zero: grupos cujas recompensas são todas iguais são descartados antes de custarem para frente e para trás, e sua parcela é registrada como frac_zero_std_groups.
  • Renormalização top-k / top-p: com top_p ou min_p, defina top_k > 0 e o treinador normaliza seus log-probs sobre o conjunto candidato vLLM amostrado.
  • Sincronização do adaptador LoRA: inicie o vLLM com --enable-lora e cada sincronização de peso envia apenas o adaptador (cerca de 160 MB em r=32) em vez de pesos mesclados.
  • Loops de implementação personalizados: subclasse AsyncRolloutLoop, substitua filter_prompt, generate_one, generate_one_turn, compute_advantages, setup ou close e defina-o como loop_cls em uma subclasse de treinador. O construtor do treinador não muda.
  • Métricas com guias de leitura: cada métrica registrada tem uma definição de uma linha, além de guias para saber se uma execução é vinculada à geração ou ao treinador e se está saturando ou amostrando duplicatas.
  • Treinamento somente de texto de pontos de verificação VLM (Qwen3.5, Qwen3.6, Qwen3-VL), com a torre de visão congelada. :boom: O que isso muda para você. Outro

O modo de servidor GRPO agora é renormalizado no conjunto de candidatos do vLLM. Com top_p, min_p ou saídas estruturadas, os log-probs do vLLM são normalizados nos tokens restantes após a filtragem. O modo Colocate já tratou disso. No modo servidor, o treinador normalizou todo o vocabulário, então o GRPO alertou que a taxa de amostragem de importância era tendenciosa ou recusou resultados estruturados. Um servidor vLLM (>= 0.28) iniciado com --return-sampling-mask agora retorna o conjunto candidato de cada token amostrado, VLLMClient.generate(return_sampling_mask=True) o lê e GRPO o ativa quando o servidor relata o sinalizador. Com Qwen2.5-0.5B-Instruct, top_k=10 e um servidor vLLM 0.32, a proporção permanece entre 0.85 e 1.27 para saídas estruturadas e top_p=0.9, onde era de 1e-13 a 1e-31 para saídas estruturadas sem o conjunto de candidatos. trl vllm-serve não adiciona o sinalizador por padrão, pois o servidor rejeita todas as solicitações com top_k=0 ou temperature=0. Por @albertvillanova em https://github.com/huggingface/trl/pull/8235 Perda de UDPO para preferências ruidosas. DPOTrainer obtém loss_type="udpo", a perda imparcial de DPO normalizada de Alinhamento imparcial para modelos de linguagem grande com preferências ruidosas. Ele corrige rótulos de preferência invertidos com probabilidade ε, lidos de label_smoothing em [0.0, 0.5) e, ao contrário de "robust", permanece imparcial quando ε é superestimado.

from trl import DPOConfig

training_args = DPOConfig(loss_type="udpo", label_smoothing=0.4)

Correções

Vários deles mudam o que uma corrida treina. O primeiro precisa de ação nos modelos que você já salvou. Modelos MoE salvos por SFTTrainer v1.7.0 para v1.17.1 computam logits do roteador a cada encaminhamento, inferência incluída. SFT escreveu output_router_logits=True e router_aux_loss_coef na configuração do modelo e os salvou, então modelos MoE ajustados continuaram retornando seus logits de roteador, e um coef substituído transportado para o próximo ajuste fino. Assim como GRPO, RLOO, DPO e KTO, o SFT agora deixa a configuração em paz. Porém, ele mantém a configuração com a qual o modelo foi carregado, portanto, um modelo salvo por uma dessas versões mantém o sinalizador mesmo após outro ajuste fino. Para redefini-lo, configure-o novamente para False e salve novamente:

model = AutoModelForCausalLM.from_pretrained("path/to/model")
model.config.output_router_logits = False  # model.config.text_config.output_router_logits for a VLM
model.save_pretrained("path/to/model")

Por @qgallouedec em https://github.com/huggingface/trl/pull/8103 Os gradientes CISPO eram 5x muito pequenos por padrão. Features

[!WARNING] The submodules of trl.experimental.async_grpo are gone. from trl.experimental.async_grpo.async_grpo_config import AsyncGRPOConfig, and imports from async_rollout_worker, packing, vllm_client or weight_transfer in that package, no longer work. Import the trainer from trl, the rollout loop from trl.trainer.async_grpo_trainer, and the vLLM client from trl.generation.async_vllm_client (renamed AsyncVLLMClient). from trl.experimental.async_grpo import AsyncGRPOConfig, AsyncGRPOTrainer still works, with a FutureWarning, until v2.0.0.

:mortar_board: AsyncGRPOTrainer is now a stable trainer

AsyncGRPOTrainer runs GRPO with generation decoupled from training. A rollout worker in a background process streams completions from a vLLM server, scores them and queues them, while the training loop pulls from the queue and updates the model. Generation and gradient updates overlap instead of alternating, and the trainer sends its new weights to the server over NCCL every weight_sync_steps steps.

In v1.17 it lived in trl.experimental.async_grpo: seven files, three ways to batch and bound generation, two constructor arguments for swapping out internals, and metric names that didn't match GRPO's. This cycle cleaned that up in about 40 PRs, tracked in https://github.com/huggingface/trl/issues/7841: config renames, one timeout instead of three, one batching mode, generation held to max_staleness, GRPO's metric names and init checks, a public rollout loop, and the two-file layout every stable trainer has. Then https://github.com/huggingface/trl/pull/8288 moved it to the top-level package.

# Before
from trl.experimental.async_grpo import AsyncGRPOConfig, AsyncGRPOTrainer

# Now
from trl import AsyncGRPOConfig, AsyncGRPOTrainer

The old path still works and emits a FutureWarning (removal in v2.0.0). The rollout loop extension point lives next to the trainer, from trl.trainer.async_grpo_trainer import AsyncRolloutLoop, Rollout, and isn't exported from trl. The OpenEnv / Harbor harness stays experimental, as HarnessAsyncGRPOTrainer in trl.experimental.async_grpo.openenv_harness. Logged metric names can still change between releases.

Quick start, from the docs. Install with pip install trl[vllm,kernels,math_verify], then start the vLLM server on GPU 0:

CUDA_VISIBLE_DEVICES=0 VLLM_SERVER_DEV_MODE=1 vllm serve Qwen/Qwen3.5-2B \
    --weight-transfer-config '{"backend": "nccl"}' \
    --logprobs-mode processed_logprobs \
    --api-server-count 8 \
    --max-model-len 4096

Then train on GPU 1 with CUDA_VISIBLE_DEVICES=1 python train_async_grpo.py:

# train_async_grpo.py
from datasets import load_dataset
from trl import AsyncGRPOTrainer
from trl.rewards import accuracy_reward

if __name__ == "__main__":  # the rollout worker is a spawned process that re-imports this script
    dataset = load_dataset("trl-lib/DeepMath-103K", split="train")

    trainer = AsyncGRPOTrainer(
        model="Qwen/Qwen3.5-2B",
        reward_funcs=accuracy_reward,
        train_dataset=dataset,
    )
    trainer.train()

What the trainer covers, all documented on the trainer page:

  • Tree packing: each micro-batch row is a prefix trie, so a prompt shared by a group's rollouts, or the history repeated by every turn of a multi-turn rollout, is forwarded once. Gated DeltaNet hybrids (Qwen3.5, Qwen3.6, Qwen3-Next) are supported.
  • Agent training: tools, environment_factory and multi-turn rollouts.
  • Score centering with masked importance sampling as the default objective (score_centering=True). score_centering=False gives GRPO's clipped objective with the same masked ratio.
  • Zero-advantage group filtering: groups whose rewards are all equal are dropped before they cost a forward and backward, and their share is logged as frac_zero_std_groups.
  • Top-k / top-p renormalization: with top_p or min_p, set top_k > 0 and the trainer normalizes its log-probs over the candidate set vLLM sampled from.
  • LoRA adapter sync: start vLLM with --enable-lora and each weight sync sends only the adapter (about 160 MB at r=32) instead of merged weights.
  • Custom rollout loops: subclass AsyncRolloutLoop, override filter_prompt, generate_one, generate_one_turn, compute_advantages, setup or close, and set it as loop_cls on a trainer subclass. The trainer's constructor doesn't change.
  • Metrics with reading guides: every logged metric has a one-line definition, plus guides for whether a run is generation-bound or trainer-bound and whether it is saturating or sampling duplicates.
  • Text-only training of VLM checkpoints (Qwen3.5, Qwen3.6, Qwen3-VL), with the vision tower frozen.

:boom: What this changes for you. If you used the experimental AsyncGRPOTrainer in v1.17, the breaking changes all landed before the promotion, so they don't have to happen after it. AsyncDistillationTrainer (still experimental) got the same constructor removals, config renames, timeout merge, batching and staleness changes and metric conventions in the same PRs.

Constructor arguments:

  • weight_transfer= is removed. Weight sync is built from the config: NCCL through vLLM's weight-transfer API, or adapter sync for LoRA. The server is a plain vllm serve.
  • rollout_worker= is removed. To change how rollouts are produced, subclass AsyncRolloutLoop and set loop_cls (see above).
  • For OpenEnv / Harbor, HarnessAsyncGRPOTrainer replaces building a HarnessRolloutWorker yourself and passing it as rollout_worker=.

Behavior to check after upgrading:

  • Readiness used to wait 240 s and a request 600 s. Both now wait up to vllm_server_timeout (1800 s).
  • max_concurrent_rollouts no longer derives from per_device_train_batch_size. With OpenEnv / Harbor, the environment server's MAX_CONCURRENT_ENVS must be at least max_concurrent_rollouts + 1: raise it, or lower max_concurrent_rollouts. The Harbor example's --max-inflight flag is now --max-concurrent-rollouts.
  • rollout/backpressure_s used to measure time waiting on a full queue. It now measures time waiting on the staleness limit.

Metrics: where AsyncGRPO and GRPO log the same quantity, AsyncGRPO now mostly uses the GRPO name. The async-only metrics keep their namespaces (rollout/, sample/, batch/, perf/, tools/, env/), with one meaning per suffix: _count is a count over the logging window, _s a duration, _per_s a rate, _frac a fraction. Dashboards and scripts that read the old names need the new ones.

Other

GRPO server mode now renormalizes over vLLM's candidate set. With top_p, min_p or structured outputs, vLLM's log-probs are normalized over the tokens left after filtering. Colocate mode already handled this. In server mode the trainer normalized over the whole vocabulary, so GRPO warned that the importance sampling ratio was biased, or refused structured outputs. A vLLM server (>= 0.28) started with --return-sampling-mask now returns the candidate set of each sampled token, VLLMClient.generate(return_sampling_mask=True) reads it, and GRPO turns it on when the server reports the flag. With Qwen2.5-0.5B-Instruct, top_k=10 and a vLLM 0.32 server, the ratio stays between 0.85 and 1.27 for structured outputs and top_p=0.9, where it was 1e-13 to 1e-31 for structured outputs without the candidate set. trl vllm-serve doesn't add the flag by default, since the server then rejects every request with top_k=0 or temperature=0. By @albertvillanova in https://github.com/huggingface/trl/pull/8235

UDPO loss for noisy preferences. DPOTrainer gets loss_type="udpo", the normalized Unbiased DPO loss from Unbiased Alignment for Large Language Models with Noisy Preferences. It corrects for preference labels flipped with probability ε, read from label_smoothing in [0.0, 0.5), and unlike "robust" it stays unbiased when ε is overestimated.

from trl import DPOConfig

training_args = DPOConfig(loss_type="udpo", label_smoothing=0.4)

By @cswjl in https://github.com/huggingface/trl/pull/8211

Privileged-context distillation in GOLD. The teacher sees per-example extra context while the student keeps its original prompt, and both score the same completion tokens. Turn it on with use_privileged_context=True, and set privileged_context_column and teacher_prompt_template as needed. It supports text, off-policy (lmbda=0) standard JSD distillation only. See the GOLD docs. By @eshwanthkartitr in https://github.com/huggingface/trl/pull/6437

MXFP4 and FP8 checkpoints load dequantized. Fixes

Several of these change what a run trains on. The first one needs action on models you already saved.

MoE models saved by SFTTrainer v1.7.0 to v1.17.1 compute router logits at every forward, inference included. SFT wrote output_router_logits=True and router_aux_loss_coef into the model config and saved them, so fine-tuned MoE models kept returning their router logits, and an overridden coef carried over to the next fine-tune. Like GRPO, RLOO, DPO and KTO, SFT now leaves the config alone. It keeps the config the model was loaded with, though, so a model saved by one of these versions keeps the flag even after another fine-tune. To reset it, set it back to False and save again:

model = AutoModelForCausalLM.from_pretrained("path/to/model")
model.config.output_router_logits = False  # model.config.text_config.output_router_logits for a VLM
model.save_pretrained("path/to/model")

By @qgallouedec in https://github.com/huggingface/trl/pull/8103

CISPO gradients were 5x too small by default. CISPO clips the importance weight itself, but an unset epsilon_high fell back to epsilon=0.2, so every on-policy weight was clipped to 0.2. With loss_type="cispo", an unset epsilon_high now defaults to 5.0, the value the docstring already recommended. On the repro, grad_norm goes from 0.0539 to 0.2693 and cispo_clip_ratio from 0.375 to 0. By @qgallouedec in https://github.com/huggingface/trl/pull/7917

Assistant-only loss trained tokens the generation prompt already ends with. Several training templates put the turn opener or the pre-filled thinking block inside {% generation %}, so SFT trained tokens the model never generates. The rendered text doesn't change, only the mask: Qwen3 (#8072), GLM-4-MoE (#8122), DeepSeek-R1/V3 and R1-Distill (#8060), Nemotron 3 (#8217), gpt-oss (#8219), Muse Glimmer (#8221), and the Qwen3.6 and Qwen3.8 revisions shipped since 2026-11-07, which bring their own markers (#8199, #8187). The DeepSeek-R1/V3 training template also dropped the reasoning of assistant turns from the target (#8061). All by @albertvillanova.

AsyncGRPO and AsyncDistillation reused prefix-cache KV computed by older weights. Each weight sync pauses vLLM without clearing its prefix cache, so a prefix shared by many prompts (system prompt, few-shot examples, tool schemas) kept the KV of the weights that first served it for the whole run. Rollout requests are now salted by model version. On a Qwen3.5-35B-A3B LoRA run with a ~2.4k-token shared prefix, mean train reward over steps 11-20 went from 0.726 to 0.781. By @AmineDiro in https://github.com/huggingface/trl/pull/8300

GKD divided its loss by the length of answers it threw away. On-policy and seq_kd steps counted num_items_in_batch on the dataset labels, then replaced them with generated completions. On the repro, num_items_in_batch goes from 172 to 16, the number of tokens the loss sums over. By @qgallouedec in https://github.com/huggingface/trl/pull/7925

One rejected token vetoed a whole VESPO sequence. With loss_type="vespo" and vllm_importance_sampling_mode="token_mask", a token outside the ratio bounds got a ratio of 0, whose clamped log collapsed the sequence weight to ~0, while the token itself kept its gradient. Rejected tokens are now dropped from both the sequence weight and the loss. By @yusufozdil in https://github.com/huggingface/trl/pull/8108

GRPO configurations that trained nothing without an error now raise:

  • repetition_penalty with the vLLM importance sampling correction: vLLM applies the penalty to the log-probs it returns, so the ratio dropped to ~1e-28 and the gradient to 0. By @qgallouedec in https://github.com/huggingface/trl/pull/7915
  • Structured outputs with the importance sampling correction now need top_k > 0: the ratio fell to about 1e-17. By @albertvillanova in https://github.com/huggingface/trl/pull/8145
  • PEFT training separate copies of tied embeddings with vLLM: vLLM >= 0.29 raised during the weight sync, and older versions silently generated from weights the trainer didn't have. By @albertvillanova in https://github.com/huggingface/trl/pull/8144
