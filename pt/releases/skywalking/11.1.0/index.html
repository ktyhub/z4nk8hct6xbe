Métricas e topologia de rastreamentos OTLP

Os aplicativos instrumentados com o OpenTelemetry SDKs não precisam mais de um agente SkyWalking para painéis de serviço, topologia e pesquisa de rastreamento. OAP armazena rastreamentos OTLP à medida que chegam, e a nova linguagem de análise de rastreamento (TAL) transforma cada extensão em métricas de serviço, instância e endpoint, uma topologia e painéis para bancos de dados, caches e filas de mensagens que os serviços chamam. Leia OpenTelemetry Traces in SkyWalking para um início rápido com um comando na Loja de Astronomia OpenTelemetry.

O arquivo em sslTrustCAPath agora é monitorado e uma alteração reconstrói o canal gRPC para que a nova CA entre em vigor sem reiniciar o OAP. Anteriormente, a CA só era relida depois que o certificado em uso já havia causado falhas nas solicitações, o que significava que uma rotação era paga com uma interrupção. O canal substituto é criado antes do antigo ser lançado, portanto, uma reconstrução com falha deixa o canal atual em serviço; solicitações já em andamento terminam no canal antigo. A integridade da substituição não é verificada antes da troca - um canal gRPC se conecta lentamente - portanto, a rotação para uma CA que não valida o servidor interrompe o tráfego até que o material válido seja gravado de volta; o documento de armazenamento descreve o procedimento de sobreposição antigo + novo que evita isso. Observe que a substituição seleciona novamente um endereço de targets, para que o OAP possa se conectar a um nó diferente após uma rotação.

O registro agora é cópia na gravação. O log de falhas no mesmo loop de varredura agora também nomeia o monitor que falhou em vez de imprimir um gourp = vazio.

Applications instrumented with the OpenTelemetry SDKs no longer need a SkyWalking agent for service dashboards, topology and trace search.   • Fix the OTLP/HTTP JSON trace endpoint reading the hex traceId, spanId and parentSpanId the OTLP/JSON encoding specifies as base64, the protobuf JSON mapping. The bodies parsed without an error into ids of the wrong length, so a trace exported as JSON matched neither the ids its SDK logged nor the same trace exported over gRPC or OTLP/HTTP protobuf.
  • Fix the heatmap query failing on a meter histogram whose bucket bounds exceed an int, such as the 9223372036854775807 key MAL gives an OTel histogram's +Inf bucket: the bucket keys are read as longs.
  • Cut the slow statements a LAL SlowSQL output writes, as the default mysql-slowsql, pgsql-slowsql and redis-slowsql rules do, to the 2000 characters of the top_n_database_statement column, as the agent path already cuts them to maxSlowSQLLength. A longer statement was refused by a strict SQL store, and stored whole on Elasticsearch and BanyanDB; it is now cut there too.
  • Fix a UI template update on BanyanDB leaving a disabled template disabled. PUT /ui-management/templates wrote only the configuration there, while on ElasticSearch and JDBC it replaces the whole record and enables it. An update is the only way to bring a disabled template back on those two stores, where adding refuses an existing id; the BanyanDB update now writes the whole record too, so the same call works on every storage.
  • Fix the Elasticsearch storage reading metrics from the wrong daily indices when dayStep and superDatasetDayStep differ. The top N query, the labeled metrics read without an entity, the entity listing of a metric and the tag autocomplete query located their indices with superDatasetDayStep, though metrics are written to indices rolled by dayStep, and Elasticsearch ignores the missing indices, so these queries returned nothing or only part of the range. They now use dayStep.
  • Read the Kubernetes and Istio metadata used by Envoy ALS k8s-mesh, the eBPF access log, MAL retagByK8sMeta and the MAL process names from the API server in the background, one read at a time in each of two lanes, one for the reads MAL waits for and one for the rest, instead of on the thread analyzing the data. A slow or unreachable API server held one gRPC handler thread, with the batch it was analyzing, per access log stream until it answered, which could exhaust OAP's memory. Envoy ALS and the eBPF access log no longer wait: an IP seen for the first time is analyzed as unknown while it is read, and is found by the later lookups; an eBPF connection resolves its unknown addresses again on its later messages. MAL queues the reads of a retagByK8sMeta's pods first and waits for them up to the new core.default.malMetadataReadTimeout in all (2 seconds by default, under the OpenTelemetry Collector's 5-second export timeout). The reads waiting at once are of distinct keys, and the new core.default.k8sMetadataReadQueueSize (als=<size>,mal=<size>, no limit by default) can limit them per lane, with the refused reads summarized at WARN. Lookup reads are sent without the Kubernetes client's retries, so a failing read holds the reads queued behind it for one attempt instead of up to ten retries with backoff, and the HTTP and TCP access log analyzers share their lookups. The API calls are the same as before, and are made only for what the lookups use: data is read again when used core.default.k8sMetadataRefreshPeriod (3 minutes) after it was written and dropped core.default.k8sMetadataCacheTime after its last write (als=21,mal=21 minutes by default, per cache); finding nothing is read again when used core.default.k8sMetadataNotFoundRetryPeriod (1 minute) later, and the endpoints or services read are read again for a pod not in them once that old, as the pod may be new; a failed read, such as for a 403 or the API server not answering, is retried when used the refresh period later, and keeps the data read before. Failed reads are logged as one ERROR summary a minute after the first failure and then every five minutes instead of a line per failure, and a resource the API server does not serve, such as ServiceEntries without Istio, is not logged. ServiceEntry hostname resolution failures are summarized at WARN, and a failing resolution retries with a growing backoff instead of immediately once three attempts failed. ServiceEntries are read through the shared Kubernetes client instead of a new client per read.
  • Fix the Elasticsearch Zipkin trace search listing the daily indices of every day since 1970 when the query starts at or before the epoch, as a lookback equal to endTs makes it. With the default day step of 1 that is over 20,000 index names, which can exceed the request line Elasticsearch accepts. The search now uses the whole zipkin_span index family in that case, as its time filter already did. Queries with a usual lookback are not affected.
  • Fix Elasticsearch reads of a metric a peer OAP reinstalls without a schema change, such as a bundled MAL rule restored after the runtime rule overriding it is deleted. The peer kept the index it had registered for the runtime rule. This only matters with logicSharding enabled and when the two rules use different functions, since the function decides the index there; with the default merged indices every metric stays in metrics-all.
  • Build the dated Elasticsearch index names in one place, IndexNames, with the day step decided once per physical table from its models, replacing TimeSeriesUtils and TimeRangeIndexNameGenerator. Apart from the fixes above, index names are unchanged.
  • Fix a service instance dropping out of the instance list queried with a time range when a record carrying an older minute updates it, such as the segment of a request that started minutes earlier arriving after the instance's heartbeat. InstanceTraffic took the last_ping of the last record written instead of keeping the latest one, as EndpointTraffic now does.
  • Fix eBPF access-log timestamps losing all sub-second precision. NodeInfo.parseTimestamp truncated the nanosecond-since-boot offset to whole seconds and also dropped bootTime.nanos before converting to millis, so short mesh HTTP latency (end - start) was quantized to 0 or 1000ms depending on whether the request crossed a whole-second boundary, and minute buckets could land in the wrong minute near minute boundaries. The conversion is now Instant.ofEpochSecond(bootSeconds, bootNanos).plusNanos(offset).toEpochMilli(), the same Instant-plus-nanos style Envoy ALS uses for wall time.
  • Fix the Envoy ALS sidecar internal request and response latencies dropping whole seconds: only the nanos part of each protobuf Duration was read. The internal response latency is now left out of the internal latency metrics when the access log lacks the upstream or downstream timing it is computed from, such as when Envoy answers an upstream timeout with its own 504, instead of counting the whole wait or going negative.
  • Sync the Envoy access log proto, envoy/data/accesslog/v3/accesslog.proto, with Envoy v1.40.0, adding the envoy/annotations/deprecation.proto it imports. With it, the Envoy ALS sidecar internal latencies leave out what the access log cannot measure instead of counting it: the internal request latency of an HTTP request Envoy retried or hedged, or of a TCP connection that took more than one connect attempt (upstream_request_attempt_count above 1), as Envoy measures the upstream timings from the start of the downstream request or connection, so the time to the first upstream byte can include the earlier attempts and the delays between them; and the internal response latency when the response details are set to anything but via_upstream, as for Envoy's own 504 of a timeout during a retry backoff, which can carry an earlier attempt's upstream timing, and, conservatively, for an upstream response that a later reset or timeout ended. The adapters report such a latency as -1, and the *_sidecar_internal_req_latency_nanos and *_sidecar_internal_resp_latency_nanos metrics in mesh.oal filter it out with filter(... >= 0). A customized mesh.oal needs the same filters, or the -1 values are averaged in.
  • Fix OAL >, >=, < and <= filters on a long or double source field, and == on a long one, failing to compile when they compare it with a number, such as filter(sideCar.internalRequestLatencyNanos >= 0). The generated code passed the number as an int, and the comparison matchers have no match(long, int) or match(double, int) overload, as Javassist does not widen an argument. The number is now written in the field's type, 0L or 0.0; filters on int fields, which already worked, generate the same code.
  • Add ZIPKIN to the GenAI evaluation record's traceRef.type, for spans received by receiver-zipkin and OTLP spans converted with otlpTraceStorage: zipkin, so the type names the store holding the judged span: SKYWALKING_NATIVE, OTLP for OTLP spans stored natively, or ZIPKIN. Zipkin and OTLP spans are both addressed by span ID, and one OAP can hold both, so an OTLP reference alone could not tell a client which store to read the trace from. The type is decided when the span is received, so records written under different otlpTraceStorage settings each name their own store.
  • Fix the Zabbix receiver dropping the sub-second part of agent sample times. Each agent data item carries clock (Unix seconds) and ns (nanoseconds within that second), but the sample time used only clock * 1000; it is now clock * 1000 + ns / 1_000_000. The sub-second precision can affect values produced by custom Zabbix rules using MAL rate, irate or increase; results from the bundled Zabbix rules and the assignment of samples to minute buckets are unchanged.
  • Fix expired records never being dropped on receipt. RecordStreamProcessor decoded a record's second-precision time bucket as a minute bucket, which put the record's time far in the future, so no record was ever treated as expired. It also compared the record's age against recordDataTTL converted to microseconds instead of milliseconds.
  • Fix Kong and APISIX latency percentiles being about 1000 times too high. Kong's kong_kong_latency_ms, kong_request_latency_ms and kong_upstream_latency_ms, and APISIX's apisix_http_latency, are already millisecond histograms, but the rules called .histogram() with no unit, which treats each le bucket as seconds and multiplies it by 1000 before histogram_percentile stores that scaled bucket as the percentile. A 100ms request was shown as 100 seconds. The Kong service, instance and endpoint rules and the APISIX rules now call histogram("le", TimeUnit.MILLISECONDS).
  • Fix the service topology drawing a service as a different one when its name equals a network address alias. The topology query renamed any call's destination whose name was an alias address, a real service included, so an OTLP service frontend was drawn as agent::frontend once an agent had registered the host frontend for agent::frontend. It now folds only a destination that is not a registered service, such as an address an agent or a TAL rule could not resolve yet, so those calls still fold onto the callee once its alias lands, and a self-call whose alias names another service, which a caller dialing its downstream by its own service name records until the downstream's alias lands.
  • Add receiver-otel.otlpServiceGroupKeys (SW_OTEL_RECEIVER_OTLP_SERVICE_GROUP) to group OTLP services in the group::name convention: the first of the listed resource attributes a resource carries, such as service.namespace or k8s.namespace.name, groups cart as shop::cart in the trace analysis, the stored spans and the OTLP logs, while the resource attributes stay as sent. The trace analyzer's alias is keyed by the caller, so cart:7070 dialed by shop::frontend reaches shop::cart and dialed by outlet::frontend reaches outlet::cart, even with one application deployed in both groups. TraceQL search lists the grouped service as each span's service.name and a trace fetched by id carries it as its resource's service.name, and the OTLP span listeners (SpanListener.onOTLPSpan / onNativeOTLPSpan, which gain a serviceName parameter) name it too. This changes the SpanListener SPI: an implementation that overrides the old four-argument onOTLPSpan / onNativeOTLPSpan must move to the new signature, or it is no longer called. Empty, the default, groups nothing.
  • Fix pprof task log records using seconds for a duration that is in minutes. PprofServiceHandler.recordPprofTaskLog used TimeUnit.SECONDS.toMillis(task.getDuration()) for the record timestamp and time bucket, while the GraphQL API, PprofTaskCommand and overlap checks treat duration as minutes. The log now uses TimeUnit.MINUTES, the same as profile task logs, so the record TTL stays aligned with the task.
  • Fix Kafka broker request_queue_time_ms, remote_time_ms, response_queue_time_ms and response_send_time_ms reporting observation rate instead of latency. Those rules used histogram *_count.rate, so under load the chart showed requests per second while the metric names and Kafka's *TimeMs histograms are millisecond latency. The Prometheus JMX exporter kafka-2_0_0.yml does not expose *_sum for these histograms, so the rules now use the exported quantile="0.50" gauge.
  • Fix Kafka broker throughput and topic metrics. meter_kafka_broker_topic_bytesin_per_second read kafka_server_brokertopicmetrics_bytesout_total, so per-topic inbound traffic matched outbound; it now reads bytesin_total. The Prometheus JMX exporter exports Kafka's BrokerTopicMetrics message, byte and request meters per topic and again as the all-topics total without a topic label, so meter_kafka_broker_messages_per_second, meter_kafka_broker_bytes_in_per_second and meter_kafka_broker_bytes_out_per_second summed both and reported twice the real rate, and every meter_kafka_broker_topic_* metric carried an extra topic="" series holding the broker total, which the Topic Rates chart drew as an extra line. Broker rules now read only the all-topics total and topic rules only the per-topic series. meter_kafka_broker_network_processor_avg_idle_percent applied rate to Kafka's idle-ratio gauge, so it reported how fast the idle percentage changed; it now reports the idle percentage. Values stored before the upgrade keep the old numbers, so these charts step at the upgrade.
  • Fix RabbitMQ node singleblock allocator meters reading multiblock carriers. meter_rabbitmq_node_allocated_singleblock_used / _unused copied kind=mbcs, so the Singleblock charts matched Multiblock; they now use kind=sbcs, and _unused subtracts the used blocks size from the carriers size, as RabbitMQ's Erlang memory allocators dashboard does, instead of reporting the whole carriers size. Values stored before the upgrade keep the old numbers, so these charts step at the upgrade.
  • Fix PostgreSQL temporary-files rate reading temp bytes. meter_pg_temporary_files_rate / meter_pg_instance_temporary_files_rate used pg_stat_database_temp_bytes, so the Temporary Files / s charts showed byte throughput; they now use pg_stat_database_temp_files, and no chart shows the temporary-file byte throughput. Values stored before the upgrade keep the old numbers, so these charts step at the upgrade.
  • Fix Zabbix agent filesystem usage percentage reading inode usage. meter_vm_filesystem_percentage used vfs.fs.inode pused, so the File System Mountpoint Usage chart showed inode occupancy; it now uses the agent's vfs.fs.size[/,pused], the space usage df and the Telegraf VM rule report, which leaves the space reserved for root out (the OTEL VM rule counts that space as used, so it reads higher on the same disk). Add vfs.fs.size[/,pused] to the required item keys, and drop unused vfs.fs.inode[/,pused] and the duplicate vm.memory.size[pavailable]. Values stored before the upgrade keep the old numbers, so this chart steps at the upgrade.
  • AI agent conversations read a tool call as its arguments, as the AI Sessionizer does (apache/skywalking-ai-sessionizer#94). A step on one part of a record reads that part alone. A tool call that shares a record with the agent's text read as that text, and now reads as its arguments. A queued command reads as the prompt inside its own part, never as text another part of the record holds.
  • Add the OTLP_MESH layer for the spans of service mesh sidecars that report over OTLP, such as Istio's Envoy. No shipped TAL rule analyzes it, so the sidecars' spans are stored and searchable ({resource.service.layer="OTLP_MESH"} in TraceQL) but not analyzed.
  • The OTLP service catalog keeps each service's service.layer, UNDEFINED when absent or unregistered, in the otlp_service_layer column, and the stored span carries the same value. A TraceQL q on resource.service.layer alone lists the services from the catalog.
  • Write a network address alias only when its mapping changes, or once per five minutes to keep it in the alias cache's ten-minute reload window; a changed mapping is written at the next flush. The alias's last_update_time_bucket is the minute OAP received it rather than the span's time, so an agent's clock skew or a late segment cannot leave a changed alias outside the cache reload. NetworkAddressAlias#combine used to rewrite every alias at every persistence period, about 140 writes an hour for a stable alias, now about twelve.
  • Fix RabbitMQ node multiblock and multiblock-pool unused meters reporting whole carriers size. meter_rabbitmq_node_allocated_multiblock_unused / _multiblock_pool_unused now subtract the used blocks size from the carriers size, matching the singleblock unused formula and RabbitMQ's Erlang memory allocators dashboard. Values stored before the upgrade keep the old numbers, so these charts step at the upgrade.
  • Fix RabbitMQ node publisher count using channels minus channel consumers. meter_rabbitmq_node_publisher_total computed rabbitmq_channels - rabbitmq_channel_consumers, which counts channels without a consumer rather than publishers: a basic.get polling channel counted as a publisher, a channel that both publishes and consumes did not, and a channel with several consumers drove the value below zero, stored as 0. It now reads rabbitmq_global_publishers, which RabbitMQ counts correctly from 3.10.11 and 3.11.3. Values stored before the upgrade keep the old numbers, so this chart steps at the upgrade.
  • Fix MySQL connection-errors-for-max-connections reading a mistyped exporter label. meter_mysql_connection_errors_max_connections / meter_mysql_instance_connection_errors_max_connections filtered error=max_connection, while mysqld_exporter exposes Connection_errors_max_connections as error=max_connections, so live scrapes never matched and the chart stayed empty; the filter now uses max_connections.
  • Add server clusters, server-clusters.yml and its dynamic configuration item core.default.serverClusters, to show a message broker, a database or a cache that clients reach at more than one address as one service. An address listed under a cluster's members or aliases, or a list of addresses, such as a Kafka client's bootstrap servers, whose every element is listed under one cluster in any order, is renamed to the cluster by the native trace analysis where no network alias maps the address, and by the OpenTelemetry trace analysis through the new TAL function findServerClusterName, which the shipped tal/otlp-general.yaml calls for brokers, databases and caches. A cluster may declare the scheme its clients write before an address, as written, such as pulsar://, and kinds, names of the user's choosing that a custom TAL rule may pass as findServerClusterName(address, kind) to match only the clusters of that kind; the native trace analysis and the shipped TAL rules do not use kinds. The file is empty by default, so nothing is renamed until a cluster is listed.
  • Bump dependencies to clear CVE alerts on shipped OAP jars: jackson 2.18.8 → 2.18.12, guava 32.0.1-jre → 33.7.2-jre, micrometer 1.14.4 → 1.16.8, log4j 2.25.4 → 2.25.5, freemarker 2.3.31 → 2.3.35 and postgresql 42.7.11 → 42.7.14. Micrometer 1.14.x has no open-source fix, and Armeria 1.34.2 is built against micrometer 1.16.0, which the old pin downgraded.
  • Bump dependencies to clear CVEs on shipped OAP jars that Dependabot does not see, because their versions come from a BOM or a transitive dependency: netty 4.2.15.Final → 4.2.19.Final (with netty-tcnative-boringssl-static 2.0.77.Final → 2.0.84.Final, the version netty 4.2.19.Final is built with), and, pulled in by kafka-clients, lz4-java 1.10.1 → 1.11.4 and snappy-java 1.1.10.5 → 1.1.10.12.
  • Add HTTP alarm hook delivery self-observability metrics, alarm_http_delivery_total, alarm_http_delivery_status_total and alarm_http_delivery_latency_seconds, on telemetry.prometheus, labeled by hook_type and by result or status_class. result names why a delivery failed (auth_failed, rate_limited, rejected, server_error, token_error, timeout, io_error, interrupted) and reads the error code DingTalk, WeCom, Feishu and WeLink return in a 2xx body, so such a refused message is now logged as a failure instead of passing as delivered. A WeLink access-token response without a token now skips the messages of that webhook URL instead of sending them with an empty token. The otel-rules/oap.yaml rules add meter_oap_instance_alarm_http_delivery_count, meter_oap_instance_alarm_http_delivery_status_count and meter_oap_instance_alarm_http_delivery_latency_percentile to the OAP self-observability layer, and the OAP Grafana dashboards chart the raw series.
