codebase-memory-mcp v0.12.0

#v0.12.0

Conheça o CBM Lens e um gráfico de código que lê sua documentação.

v0.12.0 é o maior lançamento de codebase-memory-mcp até agora: 231 solicitações pull mescladas desde v0.11.0, 40 delas da comunidade.

Quatro manchetes definem isso.

  1. CBM Lens Beta: o gráfico de código, para humanos. Até agora, o poder do gráfico alcançava as pessoas apenas por meio de seus agentes. Lens é nossa nova interface humana. Ele traz o gráfico de conhecimento do código diretamente para você. Ele vem dentro do binário que você já executa e escuta apenas em loopback. Ele coloca a fonte, o gráfico, a arquitetura, a cobertura do índice e um assistente local do navegador lado a lado, e cada fato que mostra diz de onde vem. O Lens foi construído com base no trabalho de @BernhardJackiewicz, que agora se junta ao projeto como proprietário.

  2. A documentação se junta ao gráfico. Até agora o gráfico parava onde o código parava. Agora, comentários de documentos, documentos Markdown, reStructuredText, AsciiDoc e PDF, registros de decisão de arquitetura, diagramas e especificações OpenAPI fazem parte disso. Cada um está vinculado às funções, tipos e arquivos de que fala. Um agente agora pode percorrer sua documentação e chegar ao código exato que uma página descreve, e voltar de uma função para cada página que a explica. Você também pode, no Lens. A vinculação é estrita por design: uma referência se torna uma aresta somente quando nomeia exatamente uma definição. As famílias de links que ainda não ultrapassaram sua barra de precisão são contadas e relatadas, nunca adivinhadas no gráfico.

  3. CI inteligente: o gráfico seleciona os testes. detect_changes agora pode dizer quais testes uma mudança pode afetar. Ele semeia o gráfico do diff, percorre tudo que depende do código alterado e nomeia os testes no final desses caminhos, cada um com seu motivo. Quando a evidência está faltando ou é duvidosa, ele responde “executa tudo” e diz o porquê; nunca se estreita silenciosamente. O próprio CI do codebase-memory-mcp é o primeiro usuário: as solicitações pull executam apenas as pistas de teste que suas alterações tocam, e a seleção de teste do gráfico é executada ao lado de cada PR.

  4. Infraestrutura como código no gráfico. Manifestos Kubernetes, gráficos Helm, CD Flux e Argo, arquivos Compose, Dockerfiles e os scripts, Makefiles e trabalhos de CI que os implantam agora estão vinculados. Um Serviço pode ser acompanhado através de sua carga de trabalho, sua imagem e seu arquivo Docker até o programa que o contêiner executa.

O gráfico do código também ficou mais nítido:

  • Typedefs, macros e enumeradores C obtêm identidades próprias.
  • Lançamentos de processos tornam-se bordas SPAWNS.
  • Correções de resolução abrangem C#, C++, TypeScript, Python, PHP, Rust e Go.

Atualizando? O primeiro índice de cada projeto existente após a atualização é uma reconstrução completa, uma vez. Os detalhes estão em notas de atualização. Algumas identidades e padrões também mudaram; consulte [Alterações significativas](#mudanças significativas).

Lente CBM Beta (#2068)

As ferramentas MCP são a interface do agente com o gráfico. CBM Lens Beta é seu: nossa tentativa de levar o poder do gráfico de conhecimento de código aos humanos. Ele substitui a UI gráfica anterior e está integrado ao binário:

codebase-memory-mcp --ui=true --port=9749
  • Explorar: segue o arquivo atual ou a fonte marcada, com suas dependências diretas e um resumo do impacto no nível do arquivo a partir do gráfico e da evidência local do Git.
  • Galaxy: pesquise nós, arquivos e pastas e, em seguida, expanda relacionamentos de entrada ou saída por profundidade e tipo de borda.
  • Arquitetura: o mapa do repositório, rotas, pontos de acesso, estrutura e comportamento do sistema.
  • Cobertura e sistema: o que o índice perdeu e por quê, além de status do daemon, índices, diagnósticos e configuração do MCP.
  • ADR: editar o documento de decisão do projeto no navegador, compartilhado com manage_adr.
  • Adicionar índice do projeto (Alt+P): escolha um repositório local, nomeie-o e acompanhe o progresso do daemon.
  • Bate-papo local: pergunte sobre o código que você selecionou. A inferência é executada no seu navegador. Os pesos do modelo não são agrupados; eles são baixados do Hugging Face somente quando você ativa um modelo.
  • Evidência de tempo de execução: os caminhos de chamada enviados por meio do ingest_traces são armazenados e o Lens marca os saltos que realmente foram executados.

O Lens funciona em loopback, mantém os arquivos de origem somente leitura e os nomes de onde vem cada fato. Os erros de front-end são registrados no servidor, portanto, um relatório de bug pode incluí-los.

CBM Lens é baseado no trabalho de @BernhardJackiewicz na superfície de leitura CBM, contribuído com a concordância do autor (design e rastreamento em #1964). @BernhardJackiewicz agora possui o subsistema UI. Obrigado, @BernhardJackiewicz. Este lançamento seria muito diferente sem o seu trabalho.

Smart CI: o gráfico escolhe os testes (#2458)

Executar todos os testes para todas as alterações é lento e caro. Uma regra escrita à mão sobre quais testes devem ser ignorados é suposição. Nesta versão, o gráfico decide.

  • Teste o impacto do gráfico. detect_changes com scope: "tests":

    • fixa a mudança, da base de mesclagem para HEAD;
    • semeia o gráfico a partir dos pedaços alterados;
    • percorre tudo o que depende deles, através de chamadas, referências, leituras e rotas, e através de inclusões de cabeçalho e suas macros.

    Os testes, suítes e pontos de entrada dos executores no final desses caminhos são a resposta, cada um com a forma como ela foi alcançada.

  • Nunca é uma falha silenciosa. Evidências ausentes ou duvidosas nunca restringem a seleção. Uma mudança não analisável, um teste não mapeado ou um executor de teste alcançado main transforma a resposta em "executar tudo", com o motivo nomeado.

  • Parâmetros de caminhada para cada repositório. detect_changes leva edge_types, fixpoint e via. Qualquer projeto pode solicitar o fechamento completo da dependência de entrada de uma mudança e ver o caminho para cada ocorrência.

  • Pacotes de equipe. codebase-memory-mcp test-impact publish|select empacota um gráfico congelado de commit e seu mapa de cobertura por teste como um pacote. A seleção de uma solicitação pull começa a partir do pacote de sua base de mesclagem, em vez de indexar do zero.

  • Dogfooded. As próprias solicitações pull do codebase-memory-mcp executam apenas as pistas de teste que suas alterações tocam; simulações e liberações ainda executam tudo. A seleção de teste do gráfico também é executada como uma sombra somente de relatório em cada PR. Isso cria o registro que precisamos antes de restringir as execuções de teste por padrão.

Hoje o modelo de teste conhece o próprio executor de teste C do codebase-memory-mcp. Para outros executores de testes, scope: "tests" responde "executar tudo" até que suas convenções sejam mapeadas. Os parâmetros de caminhada funcionam em qualquer lugar.

Infraestrutura como código no gráfico (#2597, #2643, #2644)

As peças de um gráfico de infraestrutura já existiam antes; agora eles acorrentam. Medimos em 17 repositórios de infraestrutura de código aberto, desde kubespray e cluster-api até opentelemetry-demo. Neles, um serviço pode ser orientado até o código que seu contêiner executa:

Service → Deployment → Image → Dockerfile → main()
                     └ the container's environment variables
  • Kubernetes:
    • Todo documento manifesto é um objeto com identidade estável.
    • Os objetos se vinculam aos ConfigMaps, Secrets, ServiceAccounts e volumes que eles nomeiam, e às suas referências Flux, Argo CD, Cluster API e cert-manager.
    • Um serviço é vinculado aos pods que todo o seu seletor seleciona.
  • Helm: os manifestos modelados também se tornam objetos, os modelos de gráfico são vinculados aos modelos nomeados que eles incluem e as dependências do gráfico file:// são resolvidas.
  • Implantar cadeias: As bordas DEPLOYS vêm de:
    • Flux Kustomizations e HelmReleases e aplicações Argo CD;
    • kubectl apply, kustomize build e helm install|upgrade|template em scripts e Makefiles;
    • Terraform helm_release e instaladores Go que usam o Helm SDK.
  • Construir e executar:
    • Os arquivos Docker dependem das imagens a partir das quais são construídos e o SPAWNS vincula cada um ao que seu contêiner executa.
    • Um novo rótulo Image une cargas de trabalho, serviços de composição e comandos de construção ao arquivo Docker que constrói a imagem.
    • Scripts e trabalhos de CI (GitHub Actions, Prow) vinculam-se aos scripts e programas que executam e make TARGET à sua regra.
  • Ambiente, sem valores: cada variável que um contêiner define torna-se o próprio EnvVar desse contêiner. Os valores nunca são armazenados e o material secreto nunca chega ao gráfico.
  • Ferramentas: trace_path ganha os modos run, deploy e topology; search_graph filtra a infraestrutura por tipo e namespace.
  • Correções ao longo do caminho:
    • Um comentário antes de um manifesto não o oculta mais.
    • Foram encontrados arquivos Kustomization sem extensão.
    • Os arquivos OpenTofu .tofu e .tfvars são indexados.
    • As bordas da rota HANDLES não dependem mais da ordem dos trabalhadores (convés: 6.424 → 44, os falsos desapareceram).
  • Verificado de forma independente: um leitor independente verificou cada camada em todos os 17 repositórios. O recall e a precisão foram de 100% no osciloscópio fechado.
  • Kustomize, Terraform e Ansible juntam-se à cadeia (#2643, #2644):
    • Patches Kustomize, variantes helmCharts e namePrefix/nameSuffix vinculam-se aos objetos que eles alteram ou implantam (OVERRIDE, DEPLOYS).
    • As variáveis ​​de ambiente de um container chegam ao código dentro da própria imagem que as lê (CONFIGURES). Cargas de trabalho e serviços Compose CONNECTS_TO o Serviço seus endereços de ambiente, e curl/wget em scripts, Makefiles e CI fazem HTTP_CALLS para Rotas.
  • Terraform, OpenTofu e Terragrunt: var., local., module., data. e referências de recursos vinculam-se ao bloco que os declara; módulos locais são IMPORTS, arquivos .tfvars OVERRIDE suas variáveis ​​e Terragrunt include/dependency estão vinculados. Os recursos kubernetes_* tornam-se os mesmos objetos que os manifestos.
    • Ansible: playbooks, arquivos de tarefas e links de funções por IMPORTS; tarefas e manipuladores são funções, notify chama os manipuladores que nomeia e kube/k8s tarefas DEPLOYS o modelo que eles aplicam.
    • Os gráficos externos do Helm são identificados pela URL que os publica: um nó compartilhado por gráfico publicado entre projetos. Um gráfico sem uma URL declarada permanece por projeto, e uma URL que contém um token ou credenciais nunca se torna parte de um nó.
    • As chaves de configuração TOML e INI vinculam-se ao código apenas pelo nome exato e dentro do componente do arquivo de configuração, o que remove bordas CONFIGURES coincidentes.
    • Uma amostra verificada manualmente das novas arestas estava 849 de 850 corretas.

Um gráfico de código mais nítido

C e C++

  • Typedefs e macros (#2543):

    • Typedefs tornam-se nós e agregados typedef struct/enum {…} X; anônimos são nomeados de acordo com seu typedef.
    • Um #define NAME não substitui mais a função ou tipo denominado NAME; as macros obtêm sua própria identidade <module>.<NAME>#macro.
    • As funções por trás de uma macro líder desconhecida mantêm seu nome real.
    • Medido: redis ganhou 573 nós Type e curl 193; funções anteriormente perdidas para uma macro de mesmo nome foram restauradas (45 em redis, 41 em curl).

  • Acesso de membro (#2458): a.b e a->b vinculam o campo do tipo real do objeto. Quando o tipo é desconhecido, eles vinculam apenas um nome de membro que exatamente uma estrutura carrega. Neste projeto, a parcela de usos de campo C que chegam a uma estrutura cujo arquivo realmente nomeia aumentou de 58.1% para 97.6%.

  • Definições condicionais (#2458): um nó por definição que existe uma vez por ramificação #if, tag de construção #[cfg] ou Go, com o intervalo de cada variante mantido em uma propriedade variants. Definições dentro de blocos condicionais agora são extraídas para C++, C#, Objective-C, Elixir, Fortran e Haskell.

  • Variantes de plataforma (#2630): uma função C/C++ definida uma vez por arquivo ou diretório de plataforma (src/unix/fs.c e src/win/fs.c, arch/x86/... e arch/arm64/...) mantém um nó por arquivo em seu próprio caminho, para que cada implementação seja localizável por seu caminho. As variantes compartilham uma propriedade variant_key, e o Smart CI trata uma alteração em qualquer variante como atingindo os testes de todas elas.

  • Uma definição por site em C/C++ pesado em macro (#2626, #2629): onde a análise bruta e a macro-expandida discordavam sobre o escopo ou a ortografia de uma definição, ambas as cópias costumavam chegar ao gráfico (por exemplo, bitonic<int64_t, AVX2> e bitonic < int64_t , AVX2 >). Cada definição agora é um nó com uma ortografia: em dotnet/runtime as definições duplicadas caem de 545 grupos em v0.11.0 para 185.

  • Chamadas entre arquivos (#2466):

    • As chamadas Class::member são resolvidas em arquivos, incluindo X::instance()->m() e auto w = Widget::create(); w->m().
    • qBittorrent ganhou 489 bordas CALLS corretas.

  • Macros de exportação (#2005): definições de tipo ocultas atrás de macros de exportação são recuperadas (obrigado @XIYBHK).

  • Tipos de retorno (#2274): o tipo de retorno de uma função da família C mantém seu ponteiro e qualificadores.

  • Definições agrupadas em macro (#2450): void FNAME(first)(void) e void Cls::__API_HOOK(Spawn)() são nomeados após o argumento da macro (first, Spawn). Cada definição que uma macro wrapper gera é usada para compartilhar um único nó (#946, #1957). Em vários idiomas (#2458, #2227)

  • Bordas SPAWNS. subprocess.run, exec.Command, child_process.spawn, posix_spawn, Process.Start, Command::new e seus parentes em cerca de 30 idiomas agora apontam para um nó Process com o nome do programa. Anteriormente, essas bordas eram adivinhadas do CALLS.

  • Sem suposições de nomes entre idiomas. Uma correspondência somente de nome nunca vincula um símbolo definido em outro idioma, e linguagens de configuração (Makefile, CMake, YAML) não se vinculam mais ao código.

  • Importações Bash são os arquivos originados por um script, e não todos os comandos que ele executa.

  • Um arquivo e uma pasta com a mesma raiz permanecem (#2624). genproto.sh próximo a genproto/ costumava compartilhar um nome qualificado, e o Módulo do arquivo foi descartado junto com as bordas apontando para ele. A pasta agora está escrita proj.pkg.genproto/; onde o diretório é um pacote Java ou Go, a pasta mantém seu nome e o Módulo do arquivo passa a ser proj.pkg.genproto#sh. Os nomes dos símbolos não mudam. Em 17 repositórios de infraestrutura, 27 módulos perdidos → 0.

Idioma por idioma

  • C#:
    • Tipos com o mesmo nome vinculados por namespace declarado, using e aliases: dotnet/runtime ganhou 8.338 arestas CALLS (#2347).

Desempenho e memória

  • Indexação mais rápida em todos os aspectos. Em dez repositórios de benchmark, um por linguagem LSP, um índice completo desta versão supera o v0.11.0 em todos os lugares. Medianas de três execuções em um Apple M5 Pro:

    | Repositório | v0.11.0 | v0.12.0 | Alterar | |---|---|---|---| | Perl | 7.0s | 1.1s | −84% | | PHP | 7.4s | 1.7s | −77% | | Rust | 8.0s | 1.9s | −76% | | C | 9.2s | 3.0s | −67% | | Vá | 45.2s | 18.6s | −59% | | Kotlin | 11.0s | 4.7s | −57% | | Python (django) | 11.9s | 6.0s | −50% | | TypeScript | 33.9s | 21.6s | −36% | | C# | 132.0s | 120.8s | −8% | | Java | 76.0s | 72.0s | −5 % |

    O pico de memória é menor em nove dos dez, e cada repositório produziu o mesmo gráfico em cada execução.

  • O kernel Linux, tempo de indexação com e sem a passagem de documentação. Documentação no gráfico adiciona uma nova etapa de indexação: cada seção de documentação é pontuada em relação ao código para encontrar as funções e arquivos de que se trata. Ele é executado por padrão para índices completos (o modo padrão) e não para índices moderate ou fast; doc_candidates liga ou desliga em qualquer modo.

    | Kernel Linux, índice completo | v0.11.0 | v0.12.0 | |---|---|---| | gráfico de código apenas | 236 s, pico 21.3 GB | 225 s, pico 14.3 GB | | gráfico de código + passagem de documentação (padrão) | n/a | 396s |

    Em repositórios abaixo de cerca de 100.000 funções, a documentação custa cerca de um segundo ou menos.

  • As ferramentas de consulta respondem rapidamente, em todas as plataformas (#2642). No macOS e no Linux, cada resposta é idêntica em bytes a antes; apenas o tempo mudou.

    • search_code verifica os arquivos indexados em processo, em vez de usar grep ou PowerShell. No Django, uma pesquisa padrão caiu de 908 ms para 355 ms e uma ampla de 3.8 s para 0.7 s. No Windows on Arm, a pesquisa caiu de 1.6-3.4 s para 0.2-0.5 s; nos executores Arm do GitHub, a varredura do PowerShell precisou de até 31 s por chamada, contra um limite de varredura de 30 s. O Windows agora também corresponde exatamente ao macOS e ao Linux (consulte [Alterações recentes](#mudanças recentes)).
    • query_graph classifica, desduplica e agrupa em O(n log n) em vez de O(n²). Nos 29.000 métodos do Django, WITH ... ORDER BY caiu de 41 s para 62 ms, RETURN ... ORDER BY de 2.2 s para 50 ms e WITH DISTINCT de 18 s para 56 ms.
    • As ferramentas de leitura executam suas pesquisas de gráfico em uma transação de leitura SQLite, renovada a cada 100 ms, em vez de bloquear o arquivo de banco de dados uma vez por pesquisa. Um gráfico inteiro count(*) caiu de 508 ms para 184 ms, e no Windows, onde os bloqueios de arquivos custam mais, de 2.9 s para 0.39 s.
    • Em um gráfico em escala de kernel (o kernel Linux: 8.5 milhões de nós, 16.9 milhões de arestas):
      • trace_path e os filtros de grau do search_graph percorrem um índice de adjacência na memória, construído uma vez por versão do índice (1.2-1.5 s no kernel) e cobrado no orçamento de memória; um inativo é liberado após 10 minutos. trace_path de schedule caiu de 7.5 s para 22 ms, uma busca de hub de 4.2 s para 0.17 s.
      • query_graph transmite suas linhas em vez de manter todas as correspondências na memória. Um gráfico inteiro count(*) costumava atingir o pico em 24.9 GB e parar no limite de tempo de consulta; agora ele responde em 11 segundos em 289 MB.
      • get_architecture caiu de 9 s para 0.9 s, e uma busca de nome exato ou prefixado de 1.1 s para 14 ms.
      • search_code caiu de 11.8 s para 3.4 s.
    • A reindexação de um repositório inalterado não copia mais primeiro o banco de dados inteiro. No kernel que pegou 18.4 se gravou 19 GB; agora leva 2.4 s e não grava nada (django 841 ms a 539 ms).
    • list_projects solicita ao git apenas o branch que ele mostra: duas chamadas git por projeto em vez de sete (94 ms a 40 ms com um projeto, e a economia aumenta a cada projeto).

  • Inicialização mais rápida em cada invocação. SHA-256 agora é executado em instruções ARMv8 SHA2 e x86 SHA-NI. O início da sessão do caminho do gancho caiu de 1.448 s para 0.376 s no Apple arm64, com resumos idênticos (#2575).

  • Muito menos rotatividade de disco em atualizações incrementais. Uma edição de uma linha em um índice Django de 294 MB gravou 5.2 GiB no SQLite WAL; agora escreve 0.52 GiB (#2469).

  • Um orçamento de memória que respeita a máquina.

    • O orçamento agora é dimensionado a partir da memória livre, não apenas da RAM total: um índice do kernel em um host ocupado de 48 GB termina em vez de esgotá-lo.
    • O derramamento no disco nunca começa abaixo de 10 GB livres.
    • Os arquivos derramados desaparecem mesmo se o processo for eliminado (POSIX).
    • Bancos de dados temporários órfãos de cada projeto são recuperados (#2233).

  • Alocação mais enxuta. No corpus Go, as alocações caíram de 245.5 M para 134.8 M, com a saída do gráfico inalterada (#2233).

  • ** Menor consumo de memória do macOS. ** Trabalhadores de índice no macOS retornam memória eliminada para que o consumo de memória do sistema operacional caia, com um gráfico de bytes idênticos (#2581).

    • Superfícies LSP decodificadas em tempo linear (#2288, obrigado @JosephStarobinets).

Confiabilidade

  • Índices grandes não são mais corrompidos. O gravador SQLite em massa pode finalizar um nível de árvore B com uma página interior vazia em gráficos grandes com chaves longas; O SQLite então relatou o banco de dados como malformado. Corrigido (#2330).
  • Banco de dados de configurações (#2650):
    • Correção de uma corrida de inicialização no banco de dados de configurações: daemon start --port, --ui=true --port e outros comandos poderiam falhar com "o daemon não aceitou a configuração da UI" ou "não foi possível carregar as configurações de tempo de execução salvas" enquanto outro processo estava gravando as configurações. Eles agora esperam que a gravação termine e iniciar o daemon não reescreve mais as configurações de UI inalteradas.
    • Corrigida uma lacuna de recuperação: depois que um processo era encerrado no meio de uma gravação de configurações, todos os comandos posteriores falhavam com "não foi possível carregar as configurações de tempo de execução salvas" até que o banco de dados de configurações fosse reparado manualmente. A inicialização agora reverte a gravação interrompida e continua.
  • Menos bugs de simultaneidade e perda de dados:
    • As primeiras leituras simultâneas de um banco de dados ocioso não correm mais (#2561).
    • Uma publicação atômica com falha registra o motivo (#2259, retirado do trabalho por @junk151516).
    • Um indexador que sai sem responder é nomeado (#2494).
    • Os IDs de borda permanecem únicos após uma fase paralela. Um contador de ID reduzido distribuiu alguns deles duas vezes, o que excluir um nó poderia se transformar em uma referência pendente (#2607).
  • Chega de Git redirecionado. Os próprios comandos Git do cbm ignoram variáveis ​​de redirecionamento de repositório (GIT_DIR, GIT_WORK_TREE,…) herdadas de ganchos e terminais de editor (#2341).
  • Correções de segurança de memória:
    • uma leitura não inicializada no scanner gramatical WIT, revelada por MemorySanitizer (#2596)
    • uma leitura de um byte não escrito no texto da seção reST (#2583)
    • um vazamento trace_path (#2425)
    • um vazamento quando um padrão Cypher MATCH falha na análise (#2603)
    • um argumento de chamada muito longo excedeu seu buffer de formatação de 512 bytes e uma sintaxe profundamente aninhada poderia esgotar a pilha; ambos os caminhantes agora são limitados e iterativos (#2478)

codebase-memory-mcp v0.12.0

v0.12.0

Meet CBM Lens, and a code graph that reads your documentation.

v0.12.0 is the biggest release of codebase-memory-mcp yet: 231 merged pull requests since v0.11.0, 40 of them from the community.

Four headlines define it.

  1. CBM Lens Beta: the code graph, for humans. Until now the graph's power reached people only through their agents. Lens is our new human interface. It brings the code knowledge graph to you directly. It ships inside the binary you already run and listens on loopback only. It puts source, the graph, the architecture, index coverage and a browser-local assistant side by side, and every fact it shows says where it comes from. Lens is built on the work of @BernhardJackiewicz, who now joins the project to own it.

  2. Documentation joins the graph. Until now the graph stopped where the code stopped. Now doc comments, Markdown, reStructuredText, AsciiDoc and PDF documents, architecture decision records, diagrams and OpenAPI specs are part of it. Each is linked to the functions, types and files it talks about. An agent can now traverse your documentation and land on the exact code a page describes, and walk from a function back to every page that explains it. So can you, in Lens. Linking is strict by design: a reference becomes an edge only when it names exactly one definition. Link families that have not yet cleared their accuracy bar are counted and reported, never guessed into the graph.

  3. Smart CI: the graph picks the tests. detect_changes can now say which tests a change can affect. It seeds the graph from the diff, walks everything that depends on the changed code, and names the tests at the end of those paths, each with its reason. When the evidence is missing or doubtful, it answers "run everything" and says why; it never narrows silently. codebase-memory-mcp's own CI is the first user: pull requests run only the test lanes their change touches, and the graph's test selection runs beside every PR.

  4. Infrastructure as code in the graph. Kubernetes manifests, Helm charts, Flux and Argo CD, Compose files, Dockerfiles and the scripts, Makefiles and CI jobs that deploy them now link up. A Service can be followed through its workload, its image and its Dockerfile to the program the container runs.

The code graph itself got sharper too:

  • C typedefs, macros and enumerators get identities of their own.
  • Process launches become SPAWNS edges.
  • Resolution fixes cover C#, C++, TypeScript, Python, PHP, Rust and Go.

Upgrading? The first index of each existing project after the upgrade is a full rebuild, once. Details are in Upgrade notes. A few identities and defaults also changed; see Breaking changes.

Documentation in the graph

Doc-comment links (#2550, #2593)

  • C# <see cref>, <seealso cref>, <exception cref> and <inheritdoc cref> bind by the compiler's own lookup rules, including MSBuild global usings evaluated from your project files (#2550).
  • Go doc links, Javadoc and KDoc tags ({@link}, @see, @throws, {@value}, @sample), Rust intra-doc links, Perl POD L<>, TypeScript/JavaScript {@link}, PHPDoc @see and Doxygen @ref/@see follow the same rule (#2593).
  • Each of the 17 doc-comment link families that ship in #2593 passed a blind audit on repositories never used to build it (bar: Wilson 95% lower bound ≥ 0.90).
  • Families still below the bar resolve but stay out of the graph, for example TS/JS {@linkcode} and @see, diagram links and OpenAPI operationId links.
  • index_status gains a doc_links block: the MENTIONS count, plus unresolved references counted by reason (missing, ambiguous, external, …). Pass diagnostics='full' for samples.

Documents (#2551)

  • Markdown: sections link to the code they name through links, bare paths, and code spans holding paths or qualified names. A line range such as #L3-L9 binds the innermost definition that holds it. A bare name is never an edge.
  • reStructuredText / Sphinx: a Section per title, with links from roles (:class:, :meth: …), object directives, autodoc, literalinclude and inline literals. Python names resolve the way Sphinx imports them. conf.py is read as text, never executed.
  • AsciiDoc / Antora: sections link through include:: directives and tag regions.
  • PDF: every page becomes a Section whose text is searchable, linked to the paths, file names and qualified names it mentions. The extractor is dependency-free and built for untrusted input: 44,070 seeded mutant PDFs ran under ASan and UBSan with zero findings. Encrypted documents are reported as such.
  • ADRs: detected in Markdown and reST. Their facts come from front matter, header fields or the Status section.
  • Markdown file-to-file references also become REFERENCES_FILE edges, so documentation hubs show up in fan-in queries (#1832, thanks @cdeust).

Complete doc comments (#2459). Multi-line // and /// runs, docs above attributes and exports, field and enum-member docs, Go package comments and Perl POD are now captured in full, with no 500-byte cut. Full-doc capture on real corpora:

| Language | Before | After | |---|---|---| | Go | 35% | 99.999% | | C# | 10% | 99.8% | | Rust | 7% | 99.9% | | Java | 74% | 99.99% | | TypeScript | 42% | 100% |

Doc-section candidates (#2574). Documentation often explains a function without naming it. For those sections, get_code_snippet now lists possibly_about candidates (on a section) and possibly_described_in candidates (on a function). Each candidate carries a probability judged on blind samples. They are leads for an agent to verify, not edges: at best about half are right, and the tool says so. get_file_outline lists the sections that are likely about a file.

Diagrams and OpenAPI (#2593)

  • Supported formats:
    • Mermaid: flowchart, sequence, class, ER, state, C4, architecture
    • PlantUML, Graphviz DOT and D2
    • draw.io: plain, compressed and .drawio.svg
    • Excalidraw: .excalidraw, .excalidraw.json and .excalidraw.svg
  • Embedded or standalone: diagrams are read in Markdown fences, reST directives (.. mermaid::, .. uml::, .. graphviz::), Asciidoctor diagram blocks and diagram files of their own. .drawio.svg and .excalidraw.svg files are no longer skipped as images.
  • Labels, not syntax: a Markdown section that embeds a diagram keeps the diagram's labels in its searchable text instead of its syntax (-->, participant).
  • OpenAPI and Swagger: openapi.json, swagger.json and any YAML or JSON file whose root declares openapi/swagger contribute one Route per operation. The spec's route and the route your code registers meet in one node.

Smart CI: the graph picks the tests (#2458)

Running every test for every change is slow and expensive. A hand-written rule for which tests to skip is guesswork. In this release, the graph decides.

  • Test impact from the graph. detect_changes with scope: "tests":

    • pins the change, from the merge base to HEAD;
    • seeds the graph from the changed hunks;
    • walks everything that depends on them, over calls, references, reads and routes, and through header includes and their macros.

    The tests, suites and runner entry points at the end of those paths are the answer, each with how it was reached.

  • Never a silent miss. Missing or doubtful evidence never narrows the selection. An unparseable change, an unmapped test, or a reached test-runner main turns the answer into "run everything", with the reason named.

  • Walk parameters for every repository. detect_changes takes edge_types, fixpoint and via. Any project can ask for the full inbound dependency closure of a change and see the path to each hit.

  • Team bundles. codebase-memory-mcp test-impact publish|select packages a commit's frozen graph and its per-test coverage map as a bundle. A pull request's selection then starts from the bundle of its merge base instead of indexing from scratch.

  • Dogfooded. codebase-memory-mcp's own pull requests run only the test lanes their change touches; dry runs and releases still run everything. The graph's test selection also runs as a report-only shadow on every PR. That builds the record we need before it narrows test runs by default.

Today the test model knows codebase-memory-mcp's own C test runner. For other test runners, scope: "tests" answers "run everything" until their conventions are mapped. The walk parameters work everywhere.

Infrastructure as code in the graph (#2597, #2643, #2644)

The pieces of an infrastructure graph existed before; now they chain. We measured on 17 open-source infrastructure repositories, from kubespray and cluster-api to opentelemetry-demo. On them, a Service can be walked to the code its container runs:

Service → Deployment → Image → Dockerfile → main()
                     └ the container's environment variables
  • Kubernetes:
    • Every manifest document is an object with a stable identity.
    • Objects link to the ConfigMaps, Secrets, ServiceAccounts and volumes they name, and to their Flux, Argo CD, Cluster API and cert-manager references.
    • A Service links to the pods its whole selector selects.
  • Helm: templated manifests become objects too, chart templates link to the named templates they include, and file:// chart dependencies resolve.
  • Deploy chains: DEPLOYS edges come from:
    • Flux Kustomizations and HelmReleases, and Argo CD Applications;
    • kubectl apply, kustomize build and helm install|upgrade|template in scripts and Makefiles;
    • Terraform helm_release, and Go installers that use the Helm SDK.
  • Build and run:
    • Dockerfiles depend on the images they build from, and SPAWNS links each to what its container runs.
    • A new Image label joins workloads, Compose services and build commands to the Dockerfile that builds the image.
    • Scripts and CI jobs (GitHub Actions, Prow) link to the scripts and programs they run, and make TARGET to its rule.
  • Environment, without values: each variable a container sets becomes that container's own EnvVar. Values are never stored, and secret material never reaches the graph.
  • Tools: trace_path gains the modes run, deploy and topology; search_graph filters infrastructure by kind and namespace.
  • Fixes along the way:
    • A comment before a manifest no longer hides it.
    • Extensionless Kustomization files are found.
    • OpenTofu .tofu and .tfvars files are indexed.
    • Route HANDLES edges no longer depend on worker order (deckhouse: 6,424 → 44, the false ones gone).
  • Checked independently: an independent reader checked every layer on all 17 repositories. Recall and precision were 100% on the gated scope.
  • Kustomize, Terraform and Ansible join the chain (#2643, #2644):
    • Kustomize patches, helmCharts and namePrefix/nameSuffix variants link to the objects they change or deploy (OVERRIDE, DEPLOYS).
    • A container's environment variables reach the code inside its own image that reads them (CONFIGURES). Workloads and Compose services CONNECTS_TO the Service their environment addresses, and curl/wget in scripts, Makefiles and CI make HTTP_CALLS to Routes.
    • Terraform, OpenTofu and Terragrunt: var., local., module., data. and resource references link to the block that declares them; local modules are IMPORTS, .tfvars files OVERRIDE their variables, and Terragrunt include/dependency are linked. kubernetes_* resources become the same objects as manifests.
    • Ansible: playbooks, task files and roles link by IMPORTS; tasks and handlers are functions, notify calls the handlers it names, and kube/k8s tasks DEPLOYS the template they apply.
    • External Helm charts are identified by the URL that publishes them: one shared node per published chart across projects. A chart without a stated URL stays per project, and a URL carrying a token or credentials never becomes part of a node.
    • TOML and INI config keys link to code only by exact name and inside the config file's component, which removes coincidental CONFIGURES edges.
    • A hand-checked sample of the new edges was 849 of 850 correct.

A sharper code graph

C and C++

  • Typedefs and macros (#2543):
    • Typedefs become nodes, and anonymous typedef struct/enum {…} X; aggregates are named after their typedef.
    • A #define NAME no longer replaces the function or type called NAME; macros get their own <module>.<NAME>#macro identity.
    • Functions behind an unknown leading macro keep their real name.
    • Measured: redis gained 573 Type nodes and curl 193; functions previously lost to a same-named macro were restored (45 on redis, 41 on curl).
  • Member access (#2458): a.b and a->b bind the field of the object's actual type. When the type is unknown, they bind only a member name exactly one struct carries. On this project, the share of C field uses that land on a struct the file actually names rose from 58.1% to 97.6%.
  • Conditional definitions (#2458): one node per definition that exists once per #if branch, #[cfg] or Go build tag, with every variant's span kept in a variants property. Definitions inside conditional blocks are now extracted for C++, C#, Objective-C, Elixir, Fortran and Haskell.
  • Platform variants (#2630): a C/C++ function defined once per platform file or directory (src/unix/fs.c and src/win/fs.c, arch/x86/... and arch/arm64/...) keeps one node per file under its own path, so every implementation is findable by its path. The variants share a variant_key property, and Smart CI treats a change in any variant as reaching the tests of all of them.
  • One definition per site in macro-heavy C/C++ (#2626, #2629): where the raw and the macro-expanded parse disagreed about a definition's scope or spelling, both copies used to land in the graph (e.g. bitonic<int64_t, AVX2> and bitonic < int64_t , AVX2 >). Each definition is now one node with one spelling: on dotnet/runtime the duplicate definitions drop from 545 groups in v0.11.0 to 185.
  • Calls across files (#2466):
    • Class::member calls resolve across files, including X::instance()->m() and auto w = Widget::create(); w->m().
    • qBittorrent gained 489 correct CALLS edges.
  • Export macros (#2005): type definitions hidden behind export macros are recovered (thanks @XIYBHK).
  • Return types (#2274): a C-family function's return type keeps its pointer and qualifiers.
  • Macro-wrapped definitions (#2450): void FNAME(first)(void) and void Cls::__API_HOOK(Spawn)() are named after the macro's argument (first, Spawn). Every definition one wrapper macro generates used to share a single node (#946, #1957).

Across languages (#2458, #2227)

  • SPAWNS edges. subprocess.run, exec.Command, child_process.spawn, posix_spawn, Process.Start, Command::new and their kin in about 30 languages now point to a Process node named after the program. Previously these were guessed CALLS edges.
  • No cross-language name guesses. A name-only match never binds a symbol defined in another language, and config languages (Makefile, CMake, YAML) no longer bind into code.
  • Bash imports are the files a script sources, not every command it runs.
  • A file and a folder with the same stem both stay (#2624). genproto.sh next to genproto/ used to share one qualified name, and the file's Module was dropped together with the edges pointing at it. The folder is now spelled proj.pkg.genproto/; where the directory is a Java or Go package, the folder keeps its name and the file's Module becomes proj.pkg.genproto#sh. Symbol names do not change. On 17 infrastructure repositories, 27 lost Modules → 0.

Performance and memory

  • Faster indexing across the board. On ten benchmark repositories, one per LSP language, a full index of this release beats v0.11.0 everywhere. Medians of three runs on an Apple M5 Pro:

    | Repository | v0.11.0 | v0.12.0 | Change | |---|---|---|---| | Perl | 7.0 s | 1.1 s | −84 % | | PHP | 7.4 s | 1.7 s | −77 % | | Rust | 8.0 s | 1.9 s | −76 % | | C | 9.2 s | 3.0 s | −67 % | | Go | 45.2 s | 18.6 s | −59 % | | Kotlin | 11.0 s | 4.7 s | −57 % | | Python (django) | 11.9 s | 6.0 s | −50 % | | TypeScript | 33.9 s | 21.6 s | −36 % | | C# | 132.0 s | 120.8 s | −8 % | | Java | 76.0 s | 72.0 s | −5 % |

    Peak memory is lower on nine of the ten, and every repository produced the same graph on every run.

  • The Linux kernel, indexing time with and without the documentation pass. Documentation in the graph adds one new indexing step: every documentation section is scored against the code to find the functions and files it is about. It runs by default for full indexes (the default mode) and not for moderate or fast ones; doc_candidates switches it on or off for any mode.

    | Linux kernel, full index | v0.11.0 | v0.12.0 | |---|---|---| | code graph only | 236 s, 21.3 GB peak | 225 s, 14.3 GB peak | | code graph + documentation pass (default) | n/a | 396 s |

    On repositories below about 100,000 functions the documentation pass costs about a second or less.

  • Query tools answer fast, on every platform (#2642). On macOS and Linux every response is byte-identical to before; only the time changed.

    • search_code scans the indexed files in process instead of through grep or PowerShell. On django a default search fell from 908 ms to 355 ms and a wide one from 3.8 s to 0.7 s. On Windows on Arm a search fell from 1.6-3.4 s to 0.2-0.5 s; on GitHub's Arm runners the PowerShell scan had needed up to 31 s per call, against a 30 s scan limit. Windows now also matches exactly like macOS and Linux (see Breaking changes).
    • query_graph sorts, deduplicates and groups in O(n log n) instead of O(n²). Over django's 29,000 methods, WITH ... ORDER BY fell from 41 s to 62 ms, RETURN ... ORDER BY from 2.2 s to 50 ms and WITH DISTINCT from 18 s to 56 ms.
    • Read tools run their graph lookups in one SQLite read transaction, renewed every 100 ms, instead of locking the database file once per lookup. A whole-graph count(*) fell from 508 ms to 184 ms, and on Windows, where file locks cost more, from 2.9 s to 0.39 s.
    • On a kernel-scale graph (the Linux kernel: 8.5 million nodes, 16.9 million edges):
      • trace_path and the degree filters of search_graph walk an in-memory adjacency index, built once per index version (1.2-1.5 s on the kernel) and charged to the memory budget; an idle one is released after 10 minutes. trace_path from schedule fell from 7.5 s to 22 ms, a hub search from 4.2 s to 0.17 s.
      • query_graph streams its rows instead of holding every match in memory. A whole-graph count(*) used to peak at 24.9 GB and stop at the query time limit; it now answers in 11 s within 289 MB.
      • get_architecture fell from 9 s to 0.9 s, and an exact or prefix name search from 1.1 s to 14 ms.
      • search_code fell from 11.8 s to 3.4 s.
    • Re-indexing an unchanged repository no longer copies the whole database first. On the kernel that took 18.4 s and wrote 19 GB; it now takes 2.4 s and writes nothing (django 841 ms to 539 ms).
    • list_projects asks git only for the branch it shows: two git calls per project instead of seven (94 ms to 40 ms with one project, and the saving grows with every project).

  • Faster startup on every invocation. SHA-256 now runs on ARMv8 SHA2 and x86 SHA-NI instructions. The hook path's session start dropped from 1.448 s to 0.376 s on Apple arm64, with identical digests (#2575).

  • Far less disk churn on incremental updates. A one-line edit on a 294 MB django index wrote 5.2 GiB to the SQLite WAL; it now writes 0.52 GiB (#2469).

  • A memory budget that respects the machine.

    • The budget is now sized from free memory, not just total RAM: a kernel index on a busy 48 GB host finishes instead of exhausting it.
    • Spilling to disk never starts below 10 GB free.
    • Spill files disappear even if the process is killed (POSIX).
    • Orphaned staging databases of every project are reclaimed (#2233).

  • Leaner allocation. On the Go corpus, allocations fell from 245.5 M to 134.8 M, with graph output unchanged (#2233).

  • Lower macOS memory footprint. Index workers on macOS return purged memory so the footprint the OS charges falls, with a byte-identical graph (#2581).

  • Algorithmic fixes:

    • LSP surfaces decode in linear time (#2288, thanks @JosephStarobinets).
    • Python scope-chain lookups are collapsed into one pass (#2252, from work by Andrew Hundt).
    • Doc-section scoring is exact and cheaper (#2582).
    • Repeated resolver work is bounded without truncating large files. A file that reaches the bound is reported as incomplete instead of silently partial (#2522, #1527).
    • Python submodule probes and class and wildcard scans no longer walk the whole registry (#2532, #2535).

Reliability

  • Large indexes no longer corrupt. The bulk SQLite writer could end a B-tree level with an empty interior page on large graphs with long keys; SQLite then reported the database as malformed. Fixed (#2330).
  • Settings database (#2650):

Upgrade notes

  • One full rebuild per project. This release changes how C macros, enumerators and fields are identified. It also adds the documentation layer and the infrastructure graph, which moves the index format from 1 to 2. An index written by v0.11.0 or earlier is therefore rebuilt in full, once, the next time it is indexed (#2543, #2550, #2551, #2574, #2597, #2643).
    • Until then, the old graph keeps answering, and index_status points out that the index predates doc links.
    • On a large repository, plan for the time of a first index.
    • Your project's ADR document carries over.
    • Coming from v0.10.x? The index-format boundary introduced in v0.11.0 (#1104) is covered by the same single rebuild.
  • Terraform and Ansible edits re-index in full. A changed Terraform or Ansible file takes a full re-index instead of an incremental one, so cross-file edges never go stale (#2643).
  • Re-run cross-repo linking. A rebuild drops CROSS_* edges and their status together, so run index_repository(mode="cross-repo-intelligence") again for linked projects.
  • Indexes cover more files. PDF, AsciiDoc, diagram files, OpenAPI specs, .NET project files and Sphinx .txt sources are now read, and the documentation layer adds its own tables. Documentation-heavy repositories get larger indexes.
  • Very large repositories: the documentation pass and doc_candidates. Scoring the doc-section candidates (#2574) is the largest extra indexing cost on very large repositories. It runs by default for full indexes and not for moderate or fast ones. On the Linux kernel it adds about three minutes; on repositories below about 100,000 functions, about a second or less. codebase-memory-mcp config set doc_candidates false turns it off for every mode (true turns it on for every mode), and index_repository(doc_candidates: ...) does the same for one index. The code graph is unchanged either way; only the possibly_about / possibly_described_in leads are left out. With it off, the kernel indexes faster than with v0.11.0 (#2610, #2628).
  • Watcher scope, stated precisely. The background watcher follows the project each open MCP session is rooted in. A repository indexed from the CLI or from another project's session is not watched. Nothing changed here, but index_status now says so (#2348).
  • New opt-in settings (all off by default):
    • watch_non_git
    • index_max_files
    • index_max_source_mb
    • CBM_STARTUP_TIMEOUT_MS
    • CBM_WALK_MAX_NODES (restores a node cap on the AST walk if you want one)
  • The previous graph UI is replaced by CBM Lens Beta. It is still started with --ui=true.

    • C member accesses on names several structs share no longer bind to an arbitrary field.
    • SEMANTICALLY_RELATED admission and scores are recalibrated.
  • search_code on Windows matches like macOS and Linux. It used PowerShell Select-String, which matched case-insensitively, used .NET regex syntax and read files containing NUL bytes as text. Now every platform matches case-sensitively, uses extended regular expressions and skips binary files, so the same query gives the same answer on every OS (#2642).
  • uninstall -y keeps project indexes. Add --delete-indexes to remove them (#2517).
  • detect_changes default base. It now compares against origin/HEAD (then main, master, upstream) instead of always main (#2496).
  • Stricter inputs:
    • Cypher rejects a non-numeric SKIP/LIMIT that it used to silently ignore (#2002).
    • Regular expressions that would compile too large are refused (#2475).
    • search_code caps context at 200 lines (#2474).
