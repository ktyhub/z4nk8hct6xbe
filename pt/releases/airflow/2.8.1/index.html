#fluxo de ar 2.8.1

Mudanças Significativas

Versão de destino para o pacote pendulum de dependência principal definido como 3 (#36281).

O suporte para o pêndulo 2.1.2 será mantido por um tempo, provavelmente até a próxima versão do Airflow. É aconselhável atualizar o código do usuário para usar o pêndulo 3 o mais rápido possível.

As especificações de embalagem Airflow seguem os modernos padrões de embalagem Python (#36537).

Padronizamos a configuração de dependência do Airflow para seguir o desenvolvimento mais recente no pacote Python por usando pyproject.toml. O Airflow agora está em conformidade com os PEPs aceitos: *PEP-440 Version Identification and Dependency Specification <https://www.python.org/dev/peps/pep-0440/>__ *PEP-517 A build-system independent format for source trees <https://www.python.org/dev/peps/pep-0517/>__ *PEP-518 Specifying Minimum Build System Requirements for Python Projects <https://www.python.org/dev/peps/pep-0518/>__ *PEP-561 Distributing and Packaging Type Information <https://www.python.org/dev/peps/pep-0561/>__ *PEP-621 Storing project metadata in pyproject.toml <https://www.python.org/dev/peps/pep-0621/>__ *PEP-660 Editable installs for pyproject.toml based builds (wheel based) <https://www.python.org/dev/peps/pep-0660/>__ *PEP-685 Comparison of extra names for optional distribution dependencies <https://www.python.org/dev/peps/pep-0685/>__ Também implementamos suporte a vários arquivos de licença provenientes do Draft, ainda não aceito (mas suportado pelo hatchling) PEP: *PEP 639 Improving License Clarity with Better Package Metadata <https://peps.python.org/pep-0639/>__ Isso quase não tem impacto perceptível nos usuários se eles estiverem usando embalagens Python modernas e ferramentas de desenvolvimento, geralmente falando, o Airflow deve se comportar como antes ao instalá-lo a partir do PyPI e deve ser muito mais fácil de instalar para fins de desenvolvimento usando pip install -e ".[devel]". As diferenças do lado do usuário são:

  • Extras de fluxo de ar agora recebem extras normalizados para - (following PEP-685) instead of _ and . (como acontecia antes em alguns extras). Quando você instala o fluxo de ar com tais extras (por exemplo dbt.core ou all_dbs) you should use - instead of _ and .. Na maioria das ferramentas modernas isso funcionará de maneira compatível com versões anteriores, mas em algumas versões antigas dessas ferramentas você pode precisar substitua _ and . with -. Você também pode receber avisos de que o extra que você está instalando não existe - mas normalmente este aviso é inofensivo e o extra é instalado de qualquer maneira. É, no entanto, recomendado mudar para usar - nos extras da sua dependência especificações para todos os extras do Airflow.
  • O pacote de fluxo de ar lançado não contém extras devel, devel-*, doc and doc-gen. Esses extras estão disponíveis apenas quando você instala o Airflow a partir de fontes no modo --editable. Isto é porque esses extras são usados apenas para fins de desenvolvimento e construção de documentação e não são necessários ao instalar o Airflow para uso em produção. Essas dependências tinham comportamento não especificado e variado para pacotes lançados de qualquer maneira e você não deveria usá-los em pacotes lançados.
  • Os extras all and all-* nem sempre funcionavam corretamente ao instalar o Airflow usando restrições porque também foram considerados dependências apenas de desenvolvimento. Com esta mudança, essas dependências são agora lidando corretamente com as restrições e eles serão instalados corretamente com as restrições, puxando o conjunto certo de provedores e dependências quando restrições são usadas.

A dependência do Graphviz agora é opcional, não obrigatória (#36647).

A dependência graphviz tem sido problemática porque o Airflow exigia dependência - especialmente para Instalações baseadas em ARM. Os pacotes Graphviz requerem bibliotecas binárias do Graphviz - o que já é um limitação, mas eles também exigem a instalação de ligações graphviz Python para serem construídas e instaladas. Isto não funciona para instalações antigas do Linux, mas - mais importante - quando você tenta instalar Bibliotecas Graphviz para Python 3.8, 3.9 para MacBooks ARM M1, os pacotes falham na instalação porque A compilação de ligações Python para M1 só pode funcionar para Python 3.10+. Tecnicamente, esta não é uma mudança significativa - os CLIs para renderizar os DAGs ainda estão lá e SE você já tiver o graphviz instalado, ele continuará funcionando como antes. O único problema quando não funciona é onde você não tem o graphviz instalado ele gerará um erro e informará que você precisa dele. O Graphviz continuará instalado para a maioria dos usuários:

  • a imagem do Airflow ainda conterá a biblioteca graphviz, porque é adicionado lá como extra
  • quando a versão anterior do Airflow já estiver instalada, então a biblioteca graphviz já está instalada lá e o Airflow irá continuar trabalhando como antes A única mudança será uma nova instalação da nova versão do Airflow do zero, onde o graphviz será precisa ser especificado como extra ou instalado separadamente para ativar a opção de renderização DAG.

airflow 2.8.1

Highlights

  • Dependency lifecycle — Core now targets Pendulum 3 (#36281) while temporarily retaining 2.1.2 support; migrate date/time code before the next feature release. MSSQL support is announced to end in Airflow 2.9.0, with migration-script hints added (#36509).
  • Modern packaging, with extra-name changes — The Hatchling/pyproject.toml migration (#36537) simplifies editable installs and fixes constraint handling for all/all-* extras. Normalize extras from _ and . to - (dbt.core → dbt-core, all_dbs → all-dbs); devel* and doc* extras are now available only for source editable installs.
  • Graphviz becomes optional — Removing the mandatory Python binding (#36647) avoids ARM and older-runtime build failures. The official image and existing installations retain Graphviz, but fresh minimal installs must add the extra or install it separately to render DAGs.
  • Failures and schedule semantics are corrected — The scheduler now exits nonzero on exceptions (#36800), and dag test raises when a DagRun fails (#36517), improving CI and process supervision. EventsTimetable no longer schedules past events with catchup=False (#36134), while timezone-naive datetimes are no longer serialized as UTC-aware values (#36379).
  • Serialization and authorization hardening — With enable_xcom_pickling=False, Airflow no longer deserializes pickle payloads (#36255). Access fixes cover DAG-code reads, variable access, and anonymous DAG-run API requests (#36257, #36396, #36275); retest custom roles and public-role configurations.
  • Task-mapping compatibility — multiple_outputs inference now correctly handles TypedDict and typing.Union on Python 3.10+ (#36652, #36728), reducing surprises for decorated tasks returning structured mappings.
  • Breaking changes — None formally announced; packaging extras and fresh-install Graphviz behavior still warrant migration checks.

Significant Changes

Target version for core dependency pendulum package set to 3 (#36281).

Support for pendulum 2.1.2 will be saved for a while, presumably until the next feature version of Airflow. It is advised to upgrade user code to use pendulum 3 as soon as possible.

Airflow packaging specification follows modern Python packaging standards (#36537).

We standardized Airflow dependency configuration to follow latest development in Python packaging by using pyproject.toml. Airflow is now compliant with those accepted PEPs:

  • PEP-440 Version Identification and Dependency Specification <https://www.python.org/dev/peps/pep-0440/>__
  • PEP-517 A build-system independent format for source trees <https://www.python.org/dev/peps/pep-0517/>__
  • PEP-518 Specifying Minimum Build System Requirements for Python Projects <https://www.python.org/dev/peps/pep-0518/>__
  • PEP-561 Distributing and Packaging Type Information <https://www.python.org/dev/peps/pep-0561/>__
  • PEP-621 Storing project metadata in pyproject.toml <https://www.python.org/dev/peps/pep-0621/>__
  • PEP-660 Editable installs for pyproject.toml based builds (wheel based) <https://www.python.org/dev/peps/pep-0660/>__
  • PEP-685 Comparison of extra names for optional distribution dependencies <https://www.python.org/dev/peps/pep-0685/>__

Also we implement multiple license files support coming from Draft, not yet accepted (but supported by hatchling) PEP:

  • PEP 639 Improving License Clarity with Better Package Metadata <https://peps.python.org/pep-0639/>__

This has almost no noticeable impact on users if they are using modern Python packaging and development tools, generally speaking Airflow should behave as it did before when installing it from PyPI and it should be much easier to install it for development purposes using pip install -e ".[devel]".

The differences from the user side are:

  • Airflow extras now get extras normalized to - (following PEP-685) instead of _ and . (as it was before in some extras). When you install airflow with such extras (for example dbt.core or all_dbs) you should use - instead of _ and ..

In most modern tools this will work in backwards-compatible way, but in some old version of those tools you might need to replace _ and . with -. You can also get warnings that the extra you are installing does not exist - but usually this warning is harmless and the extra is installed anyway. It is, however, recommended to change to use - in extras in your dependency specifications for all Airflow extras.

  • Released airflow package does not contain devel, devel-*, doc and doc-gen extras. Those extras are only available when you install Airflow from sources in --editable mode. This is because those extras are only used for development and documentation building purposes and are not needed when you install Airflow for production use. Those dependencies had unspecified and varying behaviour for released packages anyway and you were not supposed to use them in released packages.

  • The all and all-* extras were not always working correctly when installing Airflow using constraints because they were also considered as development-only dependencies. With this change, those dependencies are now properly handling constraints and they will install properly with constraints, pulling the right set of providers and dependencies when constraints are used.

Graphviz dependency is now an optional one, not required one (#36647).

The graphviz dependency has been problematic as Airflow required dependency - especially for ARM-based installations. Graphviz packages require binary graphviz libraries - which is already a limitation, but they also require to install graphviz Python bindings to be build and installed. This does not work for older Linux installation but - more importantly - when you try to install Graphviz libraries for Python 3.8, 3.9 for ARM M1 MacBooks, the packages fail to install because Python bindings compilation for M1 can only work for Python 3.10+.

This is not a breaking change technically - the CLIs to render the DAGs is still there and IF you already have graphviz installed, it will continue working as it did before. The only problem when it does not work is where you do not have graphviz installed it will raise an error and inform that you need it.

Graphviz will remain to be installed for most users:

  • the Airflow Image will still contain graphviz library, because it is added there as extra
  • when previous version of Airflow has been installed already, then graphviz library is already installed there and Airflow will continue working as it did

The only change will be a new installation of new version of Airflow from the scratch, where graphviz will need to be specified as extra or installed separately in order to enable DAG rendering option.
