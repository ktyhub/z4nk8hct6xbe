Mudanças Significativas

Particionamento de ativos

O recurso principal do Airflow 3.2.0 é o particionamento de ativos – uma grande evolução do reconhecimento de dados agendamento. Em vez de acionar Dags com base em um ativo inteiro, agora você pode agendar downstream processamento baseado em partições específicas de dados. Somente a fatia relevante dos dados aciona o downstream trabalho, tornando a orquestração de pipeline muito mais eficiente e precisa.

Isso é importante ao trabalhar com data lakes particionados – caminhos S3 particionados por data, tabela Hive partições, partições de tabela do BigQuery ou qualquer outro armazenamento de dados particionado. Anteriormente, qualquer atualização para um ativo acionou todos os Dags downstream, independentemente de qual partição foi alterada. Agora só o certo o trabalho é acionado no momento certo.

Para instruções de uso detalhadas, consulte :doc:/authoring-and-scheduling/assets.

Implantações multiequipe

O Airflow 3.2 apresenta suporte multiequipe, permitindo que as organizações executem várias equipes isoladas em uma única implantação do Airflow. Cada equipe pode ter seus próprios Dags, conexões, variáveis, pools e executores, permitindo um verdadeiro isolamento de recursos e permissões sem exigir instâncias separadas do Airflow por equipe.

Isto é particularmente valioso para equipes de plataforma que atendem diversas equipes de engenharia ou ciência de dados a partir de infraestrutura compartilhada, ao mesmo tempo em que mantêm limites fortes entre os recursos e o acesso das equipes.

Para instruções de uso detalhadas, consulte :doc:/core-concepts/multi-team.

.. aviso::

As implantações multiequipe são experimentais no 3.2.0 e podem mudar em versões futuras com base em feedback do usuário.

Suporte de retorno de chamada síncrono para alertas de prazo

Alertas de prazo agora suportam retornos de chamada síncronos via SyncCallback, além do existente AsyncCallback assíncrono. Retornos de chamada síncronos são executados pelo executor (em vez de o acionador) e pode, opcionalmente, direcionar um executor específico através do parâmetro executor.

Um Dag também pode definir vários Alertas de Prazo passando uma lista para o parâmetro deadline, e cada alerta pode usar qualquer tipo de retorno de chamada.

.. aviso::

Os Alertas de Prazo são experimentais no 3.2.0 e podem mudar em versões futuras com base em feedback do usuário. Retornos de chamada de prazo síncrono (SyncCallback) atualmente não suporta conexões armazenadas no banco de dados de metadados do Airflow.

Para instruções de uso detalhadas, consulte :doc:/howto/deadline-alerts.

Melhorias e desempenho da interface do usuário

  • Virtualização de visualização em grade: A visualização Grid agora usa virtualização – apenas as linhas visíveis são renderizadas no DOM. Isso melhora drasticamente o desempenho ao visualizar Dags com um grande número de execuções de tarefas, reduzindo o tempo de renderização e o uso de memória para Dags complexos. (#60241)

  • Gerenciamento XCom na UI: Agora você pode adicionar, editar e excluir valores XCom diretamente da IU do Airflow. Isso torna muito mais fácil depurar e gerenciar o estado do XCom durante o desenvolvimento e as operações diárias sem a necessidade de comandos CLI. (#58921)

  • Histórico de detalhes do HITL: A interface de aprovação Human-in-the-Loop agora inclui uma visualização completa do histórico, permitindo que operadores e revisores vejam a trilha de auditoria completa de aprovações e rejeições para qualquer tarefa. (#56760, #55952)

  • Melhorias no gráfico de Gantt:

    • Todas as tentativas de tarefas exibidas: o gráfico de Gantt agora mostra todas as tentativas, não apenas as mais recentes

  • Nomes de exibição de tarefas em Gantt: task_display_name mostrado para melhor legibilidade (#61438)

    • Datas ISO em Gantt: formato de data consistente entre navegadores (#61250)
    • Corrigida falha de data e hora nula: o gráfico de Gantt não trava mais em tarefas com campos de data e hora nulos

Nova flag --only-idle para o agendador CLI

O sinalizador airflow scheduler command has a new --only-idle que só conta é executado quando o agendador está ocioso. Isso ajuda os usuários a executar o agendador uma vez e processar todos os Dags e tarefas em fila. Requer e complementa o sinalizador --num-runs para que seja possível definir um valor pequeno em vez de adivinhar quantas iterações o agendador precisa.

Substitua solicitações de resumo de TI por execução por um único fluxo NDJSON

As visualizações de grade, gráfico, gantt e detalhes da tarefa agora buscam a instância da tarefa resumos por meio de uma única solicitação HTTP de streaming (GET /ui/grid/ti_summaries/{dag_id}?run_ids=...) em vez de uma solicitação por corrida. O servidor emite uma linha JSON por execução assim que a tarefa dessa execução as instâncias estão prontas, então as colunas aparecem progressivamente, em vez de todas de uma vez.

O que mudou:

  • GET /ui/grid/ti_summaries/{dag_id}?run_ids=... agora é o único endpoint para resumos de TI, retornando um fluxo application/x-ndjson onde cada line é um objeto GridTISummaries serializado para uma execução.
  • O antigo endpoint de execução única GET /ui/grid/ti_summaries/{dag_id}/{run_id} foi removido.
  • A estrutura Dag serializada é carregada uma vez e compartilhada em todas as execuções que compartilham o mesmo dag_version_id, evitando desserialização redundante.
  • Todas as visualizações da UI (grade, gráfico, gantt, instância de tarefa, instância de tarefa mapeada, grupo instância de tarefa) use o endpoint de fluxo, passando um ou mais run_ids.

Registro estruturado do JSON para todas as saídas do servidor API

A nova seção json_logs option under the [logging] torna o Airflow produzir toda a sua saída como JSON delimitado por nova linha (logs estruturados) em vez de logs formatados legíveis por humanos. Isso cobre o servidor API (gunicorn/uvicorn), incluindo logs de acesso, avisos e exceções não tratadas.

Nem todos os componentes suportam isso ainda — notavelmente airflow celery worker mas qualquer saída não JSON quando json_logs estiver habilitado será tratada como um bug. (#63365)

Remover metaclasse legada do OTel Trace e wrappers de rastreador compartilhados

As interfaces e funções localizadas em airflow.traces foram código interno que forneceu uma maneira padrão de gerenciar spans em código de fluxo de ar interno. Eles não foram concebidos como código voltado para o usuário e nunca foram documentados. Eles não são mais necessários, então nós remova-os em 3.2. (#63452)

Mover importações de exceção em nível de tarefa para a tarefa SDK

O Airflow agora origina exceções voltadas para tarefas (AirflowSkipException, TaskDeferred, etc.) de airflow.sdk.exceptions. airflow.exceptions ainda expõe as mesmas exceções, mas elas são proxies que emitem DeprecatedImportWarning para que os autores do Dag possam migrar antes que o shim seja removido.

O que mudou:

  • O código de tempo de execução agora aumenta consistentemente as versões SDK de exceções em nível de tarefa.
  • A tarefa SDK redefine essas classes para que os trabalhadores não dependam mais de airflow-core em tempo de execução.
  • airflow.providers.common.compat.sdk centraliza as importações de compatibilidade para provedores.

Mudanças de comportamento:

  • Sensores e outros auxiliares que validam a entrada do usuário agora geram ValueError (em vez de Os argumentos AirflowException) when poke_interval/ timeout são inválidos.
  • A importação de nomes de exceção obsoletos de airflow.exceptions registra um aviso direcionando os usuários para o caminho de importação do SDK.

Exceções agora fornecidas por airflow.sdk.exceptions:

  • AirflowException and AirflowNotFoundException
  • AirflowRescheduleException and AirflowSensorTimeout
  • AirflowSkipException, AirflowFailException, AirflowTaskTimeout, AirflowTaskTerminated
  • TaskDeferred, TaskDeferralTimeout, TaskDeferralError
  • DagRunTriggerException and DownstreamTasksSkipped
  • AirflowDagCycleException and AirflowInactiveAssetInInletOrOutletException
  • ParamValidationError, DuplicateTaskIdFound, TaskAlreadyInTaskGroup, TaskNotFound, XComNotFound
  • AirflowOptionalProviderFeatureException

Compatibilidade com versões anteriores:

  • Dags/operadores existentes que ainda importam de airflow.exceptions continuam funcionando, embora eles registram avisos.
  • Os provedores podem contar com airflow.providers.common.compat.sdk para manter um caminho de importação que funcione em todas as versões suportadas do Airflow.

Migração:

  • Atualize operadores, sensores e extensões personalizados para importar classes de exceção airflow.sdk.exceptions (ou do shim de compatibilidade do provedor).
  • Ajuste o código de validação personalizado para esperar ValueError para argumentos de sensor inválidos, se anteriormente capturado AirflowException.

Suporta valores de multiplicadores numéricos para o parâmetro retry_exponencial_backoff

O retry_exponential_backoff parameter now accepts numeric values to specify custom exponential backoff multipliers for task retries. Previously, this parameter only accepted boolean values (True or False), with True using a hardcoded multiplier of 2.0.

Novo comportamento:

  • Valores numéricos (por exemplo, 2.0, 3.5) especificam diretamente o multiplicador de espera exponencial
  • retry_exponential_backoff=2.0 dobra o atraso entre cada nova tentativa
  • retry_exponential_backoff=0 or False disables exponential backoff (uses fixed retry_delay)

Compatibilidade com versões anteriores:

Dags existentes que usam valores booleanos continuam funcionando:

  • retry_exponential_backoff=True → converted to 2.0 (mantém o comportamento original)
  • retry_exponential_backoff=False → converted to 0.0 (sem espera exponencial)

Alterações no API:

O esquema REST API para retry_exponential_backoff has changed from type: boolean to type: number. API clients devem usar valores numéricos (valores booleanos serão rejeitados).

Migração:

Embora os valores booleanos em Python Dags sejam convertidos automaticamente para compatibilidade com versões anteriores, recomendamos a atualização para valores numéricos explícitos para maior clareza:

  • Alterar retry_exponential_backoff=True → retry_exponential_backoff=2.0
  • Alterar retry_exponential_backoff=False → retry_exponential_backoff=0

Mover a lógica de serialização/desserialização (serde) para a tarefa SDK

O Airflow agora obtém lógica serde de airflow.sdk.serde em vez de airflow.serialization.serde. Serializer modules have moved from airflow.serialization.serializers.* para airflow.sdk.serde.serializers.*. The old import paths still work but emit DeprecatedImportWarning para orientar a migração. A camada de compatibilidade com versões anteriores será removida no Airflow 4.

O que mudou:

  • Código de serialização/desserialização movido do pacote airflow-core to task-sdk
  • Módulos serializadores movidos de airflow.serialization.serializers.* to airflow.sdk.serde.serializers.*
  • Novos serializadores devem ser adicionados ao namespace airflow.sdk.serde.serializers.*

Alterações na interface do código:

  • Importar serializadores de airflow.sdk.serde.serializers.* instead of airflow.serialization.serializers.*
  • Importar funções de serialização de airflow.sdk.serde instead of airflow.serialization.serde

Compatibilidade com versões anteriores:

  • Os serializadores existentes importados de airflow.serialization.serializers.* continuam funcionando com avisos de descontinuação
  • Todos os serializadores existentes (builtin, datetime, pandas, numpy, etc.) estão disponíveis no novo local

Migração:

  • Para serializadores personalizados existentes: atualize as importações para usar airflow.sdk.serde.serializers.*
  • Para novos serializadores: Adicione-os a airflow.sdk.serde.serializers.* namespace (e.g., create task-sdk/src/airflow/sdk/serde/serializers/your_serializer.py)

Métodos removidos de PriorityWeightStrategy

Na classe (experimental) PriorityWeightStrategy, functions serialize() e deserialize() nunca foram usados em lugar nenhum e foram removidos. Eles não deve ser confiável no código do usuário. (#59780)

Métodos removidos de TaskInstance

Na classe TaskInstance, functions run(), render_templates(), get_template_context(), e membros privados relacionados a eles foram removido. A classe é considerada interna desde 3.0 e não deve ser confiável no código do usuário. (#59780, #59835)

Novo comportamento:

  • DagBag now uses Path.relative_to para comportamento consistente entre plataformas.
  • FileLoadStat now has two additional nullable fields: bundle_path and bundle_name.

Compatibilidade com versões anteriores:

FileLoadStat will no longer produce paths beginning with / com o significado de "em relação à pasta dags". Esta é uma alteração significativa para qualquer código personalizado que execute manipulações de caminho baseadas em string dependendo desse comportamento. Remover --conn-id option from airflow connections list

O comando redundante --conn-id option has been removed from the airflow connections list CLI. Use airflow connections get em vez disso. (#59855)

Adicionar substituição render_template_as_native_obj em nível de operador

Os operadores agora podem substituir a configuração render_template_as_native_obj no nível Dag, permitindo controle refinado sobre se os modelos são renderizados como Python nativo tipos ou strings por tarefa. Defina render_template_as_native_obj=True ou False on any operator to override the Dag setting, or leave as None (padrão) para herdar do Dag.

Adicionar suporte gunicorn para servidor API com trabalhador com tempo de inatividade zero recycling

O servidor API agora suporta gunicorn como um servidor alternativo com reinicializações contínuas de trabalhadores para evitar o acúmulo de memória em processos de longa execução.

Principais benefícios:

  • Trabalhador contínuo reiniciado: Novos trabalhadores aparecem e passam nos exames de saúde antes dos trabalhadores antigos são eliminados, garantindo tempo de inatividade zero durante a reciclagem do trabalhador.

  • Compartilhamento de memória: Gunicorn usa pré-carregamento + fork, para que os trabalhadores compartilhem memória via copiar na gravação. Isso reduz significativamente o uso total de memória em comparação com o uvicorn modo multiprocesso onde cada trabalhador carrega tudo de forma independente.

  • Manipulação correta do sinal FIFO: o SIGTTOU do Gunicorn mata o trabalhador mais velho (FIFO), não o mais novo (LIFO), que é correto para reinicializações contínuas.

Configuração:

.. bloco de código :: ini

[api]
# Use gunicórnio em vez de uvicórnio
tipo_servidor=gunicórnio

# Habilita reinicializações contínuas do trabalhador a cada 12 horas
trabalhador_refresh_interval = 43200

#Reiniciar os trabalhadores um de cada vez
trabalhador_refresh_batch_size = 1

Ou através de variáveis de ambiente:

.. bloco de código :: bash

exportar AIRFLOW__API__SERVER_TYPE=gunicórnio
exportar FLUXO DE AR__API__WORKER_REFRESH_INTERVAL=43200

Requisitos:

Instale o extra gunicorn: pip install 'apache-airflow-core[gunicorn]'

Nota sobre uvicórnio (padrão):

O modo uvicorn padrão não suporta reinicializações contínuas do trabalhador porque:

  1. Com trabalhadores = 1, não há processo mestre para enviar sinais
  2. SIGTTOU do uvicorn mata o trabalhador mais novo (LIFO), anulando os propósitos de reinicialização contínua
  3. Cada trabalhador uvicórnio carrega tudo de forma independente, sem compartilhamento de memória

Se você precisar de reciclagem de trabalhador ou implantação de vários trabalhadores com eficiência de memória, use gunicorn. (#60921)

Melhor desempenho de limpeza de campos de instância de tarefa renderizada para Dags com muitas tarefas mapeadas (~42x mais rápido)

A configuração max_num_rendered_ti_fields_per_task is renamed to num_dag_runs_to_retain_rendered_fields (o nome antigo ainda funciona com aviso de descontinuação).

A retenção agora é baseada nas N execuções de dag mais recentes, em vez das N execuções de tarefas mais recentes, o que pode resultar em menos registros retidos para tarefas condicionais/esparsas. (#60951)

As permissões de preenchimento do AuthManager agora são gerenciadas pelo requires_access_dag on the DagAccessEntity.Run

A interface is_authorized_backfill of the BaseAuthManager foi removida. Core não chamará mais este método e seus a implementação da contraparte do provedor será marcada como obsoleta. As permissões para operações de preenchimento agora são verificadas em relação à permissão DagAccessEntity.Run usando o existente Decorador requires_access_dag. Em outras palavras, se um usuário tiver permissão para executar um Dag, ele poderá realizar operações de preenchimento nele.

Atualize suas políticas de segurança para garantir que os usuários que precisam realizar operações de preenchimento tenham as permissões DagAccessEntity.Run apropriadas. (Usuários ter as permissões de Backfill sem ter as de DagRun não poderá mais realizar operações de backfill sem nenhuma atualização)

airflow 3.2.0

📦 PyPI: https://pypi.org/project/apache-airflow/3.2.0/ 📚 Docs: https://airflow.apache.org/docs/apache-airflow/3.2.0/ 🛠 Release Notes: https://airflow.apache.org/docs/apache-airflow/3.2.0/release_notes.html 🐳 Docker Image: "docker pull apache/airflow:3.2.0" 🚏 Constraints: https://github.com/apache/airflow/tree/constraints-3.2.0

Significant Changes

Asset Partitioning

The headline feature of Airflow 3.2.0 is asset partitioning — a major evolution of data-aware scheduling. Instead of triggering Dags based on an entire asset, you can now schedule downstream processing based on specific partitions of data. Only the relevant slice of data triggers downstream work, making pipeline orchestration far more efficient and precise.

This matters when working with partitioned data lakes — date-partitioned S3 paths, Hive table partitions, BigQuery table partitions, or any other partitioned data store. Previously, any update to an asset triggered all downstream Dags regardless of which partition changed. Now only the right work gets triggered at the right time.

For detailed usage instructions, see :doc:/authoring-and-scheduling/assets.

Multi-Team Deployments

Airflow 3.2 introduces multi-team support, allowing organizations to run multiple isolated teams within a single Airflow deployment. Each team can have its own Dags, connections, variables, pools, and executors— enabling true resource and permission isolation without requiring separate Airflow instances per team.

This is particularly valuable for platform teams that serve multiple data engineering or data science teams from shared infrastructure, while maintaining strong boundaries between teams' resources and access.

For detailed usage instructions, see :doc:/core-concepts/multi-team.

.. warning::

Multi-Team Deployments are experimental in 3.2.0 and may change in future versions based on user feedback.

Synchronous callback support for Deadline Alerts

Deadline Alerts now support synchronous callbacks via SyncCallback in addition to the existing asynchronous AsyncCallback. Synchronous callbacks are executed by the executor (rather than the triggerer), and can optionally target a specific executor via the executor parameter.

A Dag can also define multiple Deadline Alerts by passing a list to the deadline parameter, and each alert can use either callback type.

.. warning::

Deadline Alerts are experimental in 3.2.0 and may change in future versions based on user feedback. Synchronous deadline callbacks (SyncCallback) do not currently support Connections stored in the Airflow metadata database.

For detailed usage instructions, see :doc:/howto/deadline-alerts.

UI Enhancements & Performance

  • Grid View Virtualization: The Grid view now uses virtualization -- only visible rows are rendered to the DOM. This dramatically improves performance when viewing Dags with large numbers of task runs, reducing render time and memory usage for complex Dags. (#60241)

  • XCom Management in the UI: You can now add, edit, and delete XCom values directly from the Airflow UI. This makes it much easier to debug and manage XCom state during development and day-to-day operations without needing CLI commands. (#58921)

  • HITL Detail History: The Human-in-the-Loop approval interface now includes a full history view, letting operators and reviewers see the complete audit trail of approvals and rejections for any task. (#56760, #55952)

  • Gantt Chart Improvements:

    • All task tries displayed: Gantt chart now shows every attempt, not just the latest
    • Task display names in Gantt: task_display_name shown for better readability (#61438)
    • ISO dates in Gantt: Cross-browser consistent date format (#61250)
    • Fixed null datetime crash: Gantt chart no longer crashes on tasks with null datetime fields

New --only-idle flag for the scheduler CLI

The airflow scheduler command has a new --only-idle flag that only counts runs when the scheduler is idle. This helps users run the scheduler once and process all triggered Dags and queued tasks. It requires and complements the --num-runs flag so one can set a small value instead of guessing how many iterations the scheduler needs.

Replace per-run TI summary requests with a single NDJSON stream

The grid, graph, gantt, and task-detail views now fetch task-instance summaries through a single streaming HTTP request (GET /ui/grid/ti_summaries/{dag_id}?run_ids=...) instead of one request per run. The server emits one JSON line per run as soon as that run's task instances are ready, so columns appear progressively rather than all at once.

What changed:

  • GET /ui/grid/ti_summaries/{dag_id}?run_ids=... is now the sole endpoint for TI summaries, returning an application/x-ndjson stream where each line is a serialized GridTISummaries object for one run.
  • The old single-run endpoint GET /ui/grid/ti_summaries/{dag_id}/{run_id} has been removed.
  • The serialized Dag structure is loaded once and shared across all runs that share the same dag_version_id, avoiding redundant deserialization.
  • All UI views (grid, graph, gantt, task instance, mapped task instance, group task instance) use the stream endpoint, passing one or more run_ids.

Structured JSON logging for all API server output

The new json_logs option under the [logging] section makes Airflow produce all its output as newline-delimited JSON (structured logs) instead of human-readable formatted logs. This covers the API server (gunicorn/uvicorn), including access logs, warnings, and unhandled exceptions.

Not all components support this yet — notably airflow celery worker but any non-JSON output when json_logs is enabled will be treated as a bug. (#63365)

Remove legacy OTel Trace metaclass and shared tracer wrappers

The interfaces and functions located in airflow.traces were internal code that provided a standard way to manage spans in internal Airflow code. They were not intended as user-facing code and were never documented. They are no longer needed so we remove them in 3.2. (#63452)

Move task-level exception imports into the Task SDK

Airflow now sources task-facing exceptions (AirflowSkipException, TaskDeferred, etc.) from airflow.sdk.exceptions. airflow.exceptions still exposes the same exceptions, but they are proxies that emit DeprecatedImportWarning so Dag authors can migrate before the shim is removed.

What changed:

  • Runtime code now consistently raises the SDK versions of task-level exceptions.
  • The Task SDK redefines these classes so workers no longer depend on airflow-core at runtime.
  • airflow.providers.common.compat.sdk centralizes compatibility imports for providers.

Behaviour changes:

  • Sensors and other helpers that validate user input now raise ValueError (instead of AirflowException) when poke_interval/ timeout arguments are invalid.
  • Importing deprecated exception names from airflow.exceptions logs a warning directing users to the SDK import path.

Exceptions now provided by airflow.sdk.exceptions:

  • AirflowException and AirflowNotFoundException
  • AirflowRescheduleException and AirflowSensorTimeout
  • AirflowSkipException, AirflowFailException, AirflowTaskTimeout, AirflowTaskTerminated
  • TaskDeferred, TaskDeferralTimeout, TaskDeferralError

Support numeric multiplier values for retry_exponential_backoff parameter

The retry_exponential_backoff parameter now accepts numeric values to specify custom exponential backoff multipliers for task retries. Previously, this parameter only accepted boolean values (True or False), with True using a hardcoded multiplier of 2.0.

New behavior:

  • Numeric values (e.g., 2.0, 3.5) directly specify the exponential backoff multiplier
  • retry_exponential_backoff=2.0 doubles the delay between each retry attempt
  • retry_exponential_backoff=0 or False disables exponential backoff (uses fixed retry_delay)

Backwards compatibility:

Existing Dags using boolean values continue to work:

  • retry_exponential_backoff=True → converted to 2.0 (maintains original behavior)
  • retry_exponential_backoff=False → converted to 0.0 (no exponential backoff)

API changes:

The REST API schema for retry_exponential_backoff has changed from type: boolean to type: number. API clients must use numeric values (boolean values will be rejected).

Migration:

While boolean values in Python Dags are automatically converted for backwards compatibility, we recommend updating to explicit numeric values for clarity:

  • Change retry_exponential_backoff=True → retry_exponential_backoff=2.0
  • Change retry_exponential_backoff=False → retry_exponential_backoff=0

What changed:

  • Serialization/deserialization code moved from airflow-core to task-sdk package
  • Serializer modules moved from airflow.serialization.serializers.* to airflow.sdk.serde.serializers.*
  • New serializers should be added to airflow.sdk.serde.serializers.* namespace

Code interface changes:

  • Import serializers from airflow.sdk.serde.serializers.* instead of airflow.serialization.serializers.*
  • Import serialization functions from airflow.sdk.serde instead of airflow.serialization.serde

Backward compatibility:

Add gunicorn support for API server with zero-downtime worker recycling

The API server now supports gunicorn as an alternative server with rolling worker restarts to prevent memory accumulation in long-running processes.

Key Benefits:

  • Rolling worker restarts: New workers spawn and pass health checks before old workers are killed, ensuring zero downtime during worker recycling.

  • Memory sharing: Gunicorn uses preload + fork, so workers share memory via copy-on-write. This significantly reduces total memory usage compared to uvicorn's multiprocess mode where each worker loads everything independently.

  • Correct FIFO signal handling: Gunicorn's SIGTTOU kills the oldest worker (FIFO), not the newest (LIFO), which is correct for rolling restarts.

Configuration:

.. code-block:: ini

[api]
# Use gunicorn instead of uvicorn
server_type = gunicorn

# Enable rolling worker restarts every 12 hours
worker_refresh_interval = 43200

# Restart workers one at a time
worker_refresh_batch_size = 1

Or via environment variables:

.. code-block:: bash

export AIRFLOW__API__SERVER_TYPE=gunicorn
export AIRFLOW__API__WORKER_REFRESH_INTERVAL=43200

Requirements:

Install the gunicorn extra: pip install 'apache-airflow-core[gunicorn]'

Note on uvicorn (default):

The default uvicorn mode does not support rolling worker restarts because:

  1. With workers=1, there is no master process to send signals to
  2. uvicorn's SIGTTOU kills the newest worker (LIFO), defeating rolling restart purposes
  3. Each uvicorn worker loads everything independently with no memory sharing

If you need worker recycling or memory-efficient multi-worker deployment, use gunicorn. (#60921)
