#fluxo de ar 2.8.2

Mudanças Significativas

A flag allowed_deserialization_classes agora segue um padrão glob (#36147).

Por exemplo, se alguém quiser adicionar a classe airflow.tests.custom_class ao Lista allowed_deserialization_classes, isso pode ser feito escrevendo a classe completa nome (airflow.tests.custom_class) ou um padrão como os usados ​​em glob pesquisa (por exemplo, airflow.*, airflow.tests.*). Se você usa atualmente um caminho regexp personalizado, certifique-se de reescrevê-lo como um padrão glob. Alternativamente, se você ainda deseja combiná-lo como um padrão regexp, adicione-o sob o novo liste allowed_deserialization_classes_regexp em vez disso.

As permissões audit_logs foram atualizadas para maior segurança (#37501).

Isso foi feito de acordo com a política de que não queremos usuários como Viewer, Ops, e outros usuários além do Admin tenham acesso ao audit_logs. A intenção por trás esta alteração visa restringir usuários com menos permissões de visualizar detalhes do usuário como nome, e-mail etc. dos audit_logs quando não são permitidos. O impacto desta alteração é que os usuários existentes com direitos que não sejam de administrador não poderão para visualizar ou acessar os audit_logs, tanto na guia Navegar quanto na execução do DAG.

AirflowTimeoutError is no longer except by default through Exception (#35653).

O AirflowTimeoutError is now inheriting BaseException em vez de AirflowException->Exception. Veja https://docs.python.org/3/library/exceptions.html#exception-hierarchy Isso evita que o código capture Exception acidentalmente pegando AirflowTimeoutError e continuando a correr. AirflowTimeoutError é uma intenção explícita de cancelar a tarefa e não deve ser pego nas tentativas de tratar o erro e retornar algum valor padrão. Capturando AirflowTimeoutError is still possible by explicitly except AirflowTimeoutError or BaseException. Isso é desencorajado, pois pode permitir que o código continue em execução mesmo depois tais solicitações de cancelamento. Código que anteriormente dependia da realização de uma limpeza rigorosa em todas as situações depois de capturar blocos Exception is advised to use finally ou gerenciadores de contexto. Para realizar apenas a limpeza e depois automaticamente re-aumentar a exceção. Veja considerações semelhantes sobre a captura de KeyboardInterrupt em https://docs.python.org/3/library/exceptions.html#KeyboardInterrupt

airflow 2.8.2

Significant Changes

The allowed_deserialization_classes flag now follows a glob pattern (#36147).

For example if one wants to add the class airflow.tests.custom_class to the allowed_deserialization_classes list, it can be done by writing the full class name (airflow.tests.custom_class) or a pattern such as the ones used in glob search (e.g., airflow.*, airflow.tests.*).

If you currently use a custom regexp path make sure to rewrite it as a glob pattern.

Alternatively, if you still wish to match it as a regexp pattern, add it under the new list allowed_deserialization_classes_regexp instead.

The audit_logs permissions have been updated for heightened security (#37501).

This was done under the policy that we do not want users like Viewer, Ops, and other users apart from Admin to have access to audit_logs. The intention behind this change is to restrict users with less permissions from viewing user details like First Name, Email etc. from the audit_logs when they are not permitted to.

The impact of this change is that the existing users with non admin rights won't be able to view or access the audit_logs, both from the Browse tab or from the DAG run.

AirflowTimeoutError is no longer except by default through Exception (#35653).

The AirflowTimeoutError is now inheriting BaseException instead of AirflowException->Exception. See https://docs.python.org/3/library/exceptions.html#exception-hierarchy

This prevents code catching Exception from accidentally catching AirflowTimeoutError and continuing to run. AirflowTimeoutError is an explicit intent to cancel the task, and should not be caught in attempts to handle the error and return some default value.

Catching AirflowTimeoutError is still possible by explicitly excepting AirflowTimeoutError or BaseException. This is discouraged, as it may allow the code to continue running even after such cancellation requests. Code that previously depended on performing strict cleanup in every situation after catching Exception is advised to use finally blocks or context managers. To perform only the cleanup and then automatically re-raise the exception. See similar considerations about catching KeyboardInterrupt in https://docs.python.org/3/library/exceptions.html#KeyboardInterrupt
