Destaques do lançamento <a id="v2100-release-highlights"></a>

Gerenciamento de segredos <a id="v2100-highlight-secrets-management"></a>

Mantenha as credenciais do coletor fora dos arquivos de configuração de texto simples. O Netdata agora permite referenciar segredos nas configurações do coletor em vez de armazená-los diretamente. Senhas, tokens e chaves API são resolvidos em tempo de execução a partir da fonte que você escolher.

Resolvedores

A Netdata fornece quatro tipos de resolvedores, desde simples até de nível empresarial:

| Resolvedor | Sintaxe | Melhor para | |:-------------------------|:-----------------------------------|:----------------------------------------------------------------------------------------------------------| | Variável de ambiente | ${env:VAR_NAME} | Segredos já injetados no ambiente de serviço Netdata | | Arquivo | ${file:/absolute/path} | Segredos armazenados em arquivos locais no disco (Segredos Docker, Segredos Kubernetes montados como volumes) | | Comando | ${cmd:/absolute/path args} | Segredos retornados por um comando local trusted (por exemplo, 1Password CLI, scripts personalizados) | | Loja secreta | ${store:<kind>:<name>:<operand>} | Segredos gerenciados centralmente em provedores de nuvem ou Vault |

Back-ends de Secretstore suportados

Para organizações que gerenciam segredos centralmente, o Netdata se integra a quatro back-ends de armazenamento secreto:

| Back-end | Tipo | Formato do operando | Modos de autenticação | |:--------------------------------------------------------------------------------------------------------------------------------------------------|:-----------|:---------------------------|:-------------------------------------------------------------------------------------| | Gerenciador de segredos da AWS | aws-sm | secret-name[#key] | Credenciais de ambiente, função de tarefa ECS, perfil de instância EC2 | | Cofre de Chaves do Azure | azure-kv | vault-name/secret-name | Entidade de serviço, identidade gerenciada, cadeia de credenciais padrão | | Gerenciador secreto do Google | gcp-sm | project/secret[/version] | Servidor de metadados, arquivo de conta de serviço | | Cofre HashiCorp | vault | path#key | Token, arquivo de token |

Configure secretstores por meio da Netdata Dynamic Configuration UI (Collectors → go.d → SecretStores) ou por meio de arquivos de configuração em /etc/netdata/go.d/ss/.

Exemplo

Um coletor MySQL referenciando sua senha do HashiCorp Vault:

# /etc/netdata/go.d/mysql.conf
jobs:
  - name: mysql_prod
    dsn: "netdata:${store:vault:vault_prod:secret/data/netdata/mysql#password}@tcp(127.0.0.1:3306)/"

Você pode misturar tipos de resolvedores livremente. Por exemplo, leia o nome de usuário de uma variável de ambiente e a senha de um secretstore no mesmo valor de configuração:

jobs:
  - name: mysql_prod
    dsn: "${env:MYSQL_USER}:${store:vault:vault_prod:secret/data/netdata/mysql#password}@tcp(127.0.0.1:3306)/"

Como funciona

  • Os segredos são resolvidos sempre que um trabalho do coletor é iniciado ou reiniciado.
  • A atualização de um secretstore reinicia automaticamente os trabalhos do coletor que o utilizam para que eles obtenham novas credenciais.
  • Os próprios valores de configuração do Secretstore também suportam os resolvedores ${env:...}, ${file:...} e ${cmd:...}, portanto, as credenciais de back-end também não precisam ser armazenadas em texto simples.

[!TIP] Para configuração detalhada, guias de autenticação específicos de backend e solução de problemas, consulte a documentação de gerenciamento de segredos.

Coletor de plug-ins Nagios <a id="v2100-highlight-nagios-plugins"></a>

Execute plug-ins compatíveis com Nagios e scripts personalizados diretamente dentro do Netdata com o novo coletor de plug-ins Nagios. Qualquer executável que siga o formato de saída do plugin Nagios funciona imediatamente: plugins Nagios empacotados, scripts de shell personalizados ou binários compilados.

O que você ganha

| Recurso | Detalhes | |:------------------------------------------------|:---------------------------------------------------------------------------------------------------------------------------------------------| | Verifique o monitoramento do estado | Rastreia os estados OK, AVISO, CRÍTICO e DESCONHECIDO do código de saída do processo | | Gráficos automáticos de dados de desempenho | Os valores dos dados de desempenho do Nagios são analisados ​​e mapeados automaticamente | | Alertas com base em limites | Quando o perfdata inclui limites de aviso/críticos, o Netdata deriva um gráfico de estado de limite (ok/aviso/crítico) e cria alertas integrados | | Métricas de execução | Mede a duração da execução, o tempo de CPU e o uso de memória de cada verificação | | Agendamento estilo Nagios | Intervalos de verificação configuráveis, intervalos de repetição, tentativas máximas de verificação e períodos de tempo | | Lógica de estado suave/hard | Resultados não OK são repetidos em retry_interval até max_check_attempts antes de acionar alertas, evitando falsos alarmes de falhas transitórias |

Alertas integrados

O coletor vem com quatro alertas de estoque:

| Alerta | Aciona quando | |:-----------------------------------------------------|:-------------------------------------------------| | nagios_job_execution_state_warn | Um cheque está no estado difícil WARNING | | nagios_job_execution_state_crit | Um cheque está em estado crítico CRÍTICO | | nagios_job_perfdata_threshold_state_warn | Uma métrica perfdata excede seu limite de aviso | | nagios_job_perfdata_threshold_state_crit | Uma métrica perfdata excede seu limite crítico |

Todos os alertas de estoque suprimem estados de repetição suave. Os alertas disparam somente após as falhas consecutivas configuradas do max_check_attempts.

Exemplo

# /usr/local/lib/netdata/checks/check_api.sh
#!/bin/sh
resp=$(curl -s -o /dev/null -w "%{http_code} %{time_total}" --max-time 5 "$1" 2>/dev/null)
code=$(echo "$resp" | cut -d' ' -f1)
time=$(echo "$resp" | cut -d' ' -f2)

[ "$code" -ge 500 ] && echo "CRITICAL - HTTP $code | response_time=${time}s;~:2;~:5" && exit 2
[ "$code" -ne 200 ] && echo "WARNING - HTTP $code | response_time=${time}s;~:2;~:5" && exit 1
echo "OK - HTTP $code | response_time=${time}s;~:2;~:5"
exit 0

# /etc/netdata/scripts.d/nagios.conf
jobs:
  - name: api_health
    plugin: /bin/sh
    args: ["/usr/local/lib/netdata/checks/check_api.sh", "http://localhost:8080/health"]
    check_interval: 1m
    retry_interval: 15s
    max_check_attempts: 3

Isso produz gráficos de estado de verificação, métricas de execução e, como o script emite perfdata com limites (response_time com aviso >2s/crit >5s), um gráfico de tempo de resposta automático com um gráfico de estado de limite e alertas integrados.

[!TIP] Para obter o guia de configuração completo, instruções passo a passo sobre scripts personalizados e configuração do período de tempo, consulte a [documentação do coletor de plug-ins do Nagios] (https://learn.netdata.cloud/docs/collecting-metrics/collectors/synthetic-testing/nagios-plugins).

Coletor do Azure Monitor <a id="v2100-highlight-azure-monitor"></a>

Monitore toda a sua infraestrutura do Azure a partir da Netdata com o novo coletor Azure Monitor. Ele coleta métricas de plataforma do Azure Monitor Metrics API com descoberta automática de recursos: aponte-o para suas assinaturas e encontre seus recursos, combine-os com perfis integrados (conjuntos pré-configurados de métricas) e comece a coletar métricas.

[!IMPORTANTE] Este é um recurso alfa. O formato de configuração pode mudar nas próximas versões.

O que você ganha

| Recurso | Detalhes | |:---------------------------------|:-------------------------------------------------------------------------------------------------------------| | 38 perfis de serviço integrados | Mais de 1.300 métricas em computação, bancos de dados, redes, armazenamento, IA/ML, análises, contêineres e muito mais | | Descoberta automática | Descobre recursos por meio do Azure Resource Graph e permite perfis correspondentes sem configuração por recurso | | Assinatura múltipla | Monitore recursos em várias assinaturas do Azure em um único trabalho de coletor | | Escopo de descoberta flexível | Restrinja a descoberta por grupos de recursos, regiões ou tags ou use uma consulta KQL personalizada do Azure Resource Graph | | Alertas integrados | Alertas pré-configurados para condições críticas de recursos do Azure | | Configuração da IU | Configurar por meio da UI de configuração dinâmica do Netdata sem edição de arquivo |

Secrets Management <a id="v2100-highlight-secrets-management"></a>

Keep collector credentials out of plain-text configuration files. Netdata now lets you reference secrets in collector configurations instead of storing them directly. Passwords, tokens, and API keys are resolved at runtime from the source you choose.

Resolvers

Netdata provides four resolver types, from simple to enterprise-grade:

| Resolver | Syntax | Best For | |:-------------------------|:-----------------------------------|:----------------------------------------------------------------------------------------------| | Environment variable | ${env:VAR_NAME} | Secrets already injected into the Netdata service environment | | File | ${file:/absolute/path} | Secrets stored in local files on disk (Docker Secrets, Kubernetes Secrets mounted as volumes) | | Command | ${cmd:/absolute/path args} | Secrets returned by a trusted local command (e.g., 1Password CLI, custom scripts) | | Secretstore | ${store:<kind>:<name>:<operand>} | Secrets managed centrally in cloud providers or Vault |

Supported Secretstore Backends

For organizations managing secrets centrally, Netdata integrates with four secretstore backends:

| Backend | Kind | Operand Format | Authentication Modes | |:------------------------------------------------------------------------------------------------------------------------------------|:-----------|:---------------------------|:--------------------------------------------------------------| | AWS Secrets Manager | aws-sm | secret-name[#key] | Environment credentials, ECS task role, EC2 instance profile | | Azure Key Vault | azure-kv | vault-name/secret-name | Service principal, Managed identity, Default credential chain | | Google Secret Manager | gcp-sm | project/secret[/version] | Metadata server, Service account file | | HashiCorp Vault | vault | path#key | Token, Token file |

Configure secretstores through the Netdata Dynamic Configuration UI (Collectors → go.d → SecretStores) or via configuration files under /etc/netdata/go.d/ss/.

Example

A MySQL collector referencing its password from HashiCorp Vault:

# /etc/netdata/go.d/mysql.conf
jobs:
  - name: mysql_prod
    dsn: "netdata:${store:vault:vault_prod:secret/data/netdata/mysql#password}@tcp(127.0.0.1:3306)/"

You can mix resolver types freely. For example, read the username from an environment variable and the password from a secretstore in the same config value:

jobs:
  - name: mysql_prod
    dsn: "${env:MYSQL_USER}:${store:vault:vault_prod:secret/data/netdata/mysql#password}@tcp(127.0.0.1:3306)/"

How It Works

  • Secrets are resolved each time a collector job starts or restarts.
  • Updating a secretstore automatically restarts collector jobs that use it so they pick up new credentials.
  • Secretstore configuration values themselves also support ${env:...}, ${file:...}, and ${cmd:...} resolvers, so backend credentials don't need to be stored in plain text either.

[!TIP] For detailed setup, backend-specific authentication guides, and troubleshooting, see the Secrets Management documentation.

Nagios Plugins Collector <a id="v2100-highlight-nagios-plugins"></a>

Run Nagios-compatible plugins and custom scripts directly inside Netdata with the new Nagios Plugins collector. Any executable that follows the Nagios plugin output format works out of the box: packaged Nagios plugins, custom shell scripts, or compiled binaries.

What You Get

| Feature | Details | |:--------------------------------------|:----------------------------------------------------------------------------------------------------------------------------------------------| | Check State Monitoring | Tracks OK, WARNING, CRITICAL, and UNKNOWN states from the process exit code | | Automatic Performance Data Charts | Nagios performance data values are parsed and charted automatically | | Threshold-Based Alerting | When perfdata includes warning/critical thresholds, Netdata derives a threshold state chart (ok/warning/critical) and creates built-in alerts | | Execution Metrics | Measures run duration, CPU time, and memory usage of each check | | Nagios-Style Scheduling | Configurable check intervals, retry intervals, max check attempts, and time periods | | Soft/Hard State Logic | Non-OK results retry at retry_interval up to max_check_attempts before triggering alerts, preventing false alarms from transient failures |

Built-in Alerts

The collector ships with four stock alerts:

| Alert | Triggers When | |:-------------------------------------------|:-------------------------------------------------| | nagios_job_execution_state_warn | A check is in WARNING hard state | | nagios_job_execution_state_crit | A check is in CRITICAL hard state | | nagios_job_perfdata_threshold_state_warn | A perfdata metric exceeds its warning threshold | | nagios_job_perfdata_threshold_state_crit | A perfdata metric exceeds its critical threshold |

All stock alerts suppress soft retry states. Alerts fire only after the configured max_check_attempts consecutive failures.

Example

# /usr/local/lib/netdata/checks/check_api.sh
#!/bin/sh
resp=$(curl -s -o /dev/null -w "%{http_code} %{time_total}" --max-time 5 "$1" 2>/dev/null)
code=$(echo "$resp" | cut -d' ' -f1)
time=$(echo "$resp" | cut -d' ' -f2)

[ "$code" -ge 500 ] && echo "CRITICAL - HTTP $code | response_time=${time}s;~:2;~:5" && exit 2
[ "$code" -ne 200 ] && echo "WARNING - HTTP $code | response_time=${time}s;~:2;~:5" && exit 1
echo "OK - HTTP $code | response_time=${time}s;~:2;~:5"
exit 0

# /etc/netdata/scripts.d/nagios.conf
jobs:
  - name: api_health
    plugin: /bin/sh
    args: ["/usr/local/lib/netdata/checks/check_api.sh", "http://localhost:8080/health"]
    check_interval: 1m
    retry_interval: 15s
    max_check_attempts: 3

This produces check state charts, execution metrics, and because the script emits perfdata with thresholds (response_time with warn >2s / crit >5s), an automatic response time chart with a threshold state chart and built-in alerts.

[!TIP] For the full setup guide, custom scripts walkthrough, and time period configuration, see the Nagios Plugins collector documentation.

Monitor your entire Azure infrastructure from Netdata with the new Azure Monitor collector. It collects platform metrics from the Azure Monitor Metrics API with automatic resource discovery: point it at your subscriptions, and it finds your resources, matches them to built-in profiles (preconfigured sets of metrics), and starts collecting metrics.

Support options <a id="v2100-support-options"></a>

As we grow, we stay committed to providing the best support ever seen from an open-source solution. Should you encounter an issue with any of the changes made in this release or any feature in the Netdata Agent, feel free to contact us through one of the following channels:
