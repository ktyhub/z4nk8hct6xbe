DeepTutor v1.3.0

DeepTutor v1.3.0 Release Note

Date de sortie : 2026.04.27

Faits saillants

Index de la base de connaissances versionnés et flux de travail de réindexation

Les bases de connaissances conservent désormais les index vectoriels par configuration d'intégration au lieu de traiter un répertoire llamaindex_storage/ comme la vérité entière. Chaque nouvelle version de l'index enregistre une signature et des métadonnées intégrées, de sorte que le changement de modèle n'a plus besoin d'écraser l'index précédent, et le retour en arrière peut réutiliser une version prête lorsque la signature correspond.

  • Disposition de stockage versionnée — les nouveaux index sont écrits sous forme de répertoires plats version-N/ avec meta.json ; Les anciennes dispositions racine et imbriquées llamaindex_storage restent lisibles pour les installations existantes.
  • Lectures et écritures prenant en compte l'intégration — La recherche RAG, les ajouts de documents, les statistiques du gestionnaire et les chemins de suppression/nettoyage résolvent désormais le stockage via la signature d'intégration active. Si aucune version prête ne correspond au modèle d'intégration actuel, la récupération renvoie un signal needs_reindex clair au lieu d'échouer plus tard avec une erreur de stockage opaque.
  • Réindexation en arrière-plan API — POST /api/v1/knowledge/{kb_name}/reindex reconstruit une base de connaissances par rapport à la configuration d'intégration active, diffuse les journaux via le canal de tâches existant et renvoie noop: true lorsqu'un index prêt correspondant existe déjà.
  • L'état de l'index est apparu dans l'interface utilisateur — Les résumés de la base de connaissances incluent désormais les métadonnées de la version d'index, l'état de correspondance active, l'intégration des indicateurs de non-concordance, la progression et la préparation à la réindexation afin que l'interface puisse expliquer pourquoi une base de connaissances doit être reconstruite.

Reconstruction de la page de gestion des connaissances

La page Connaissances a été divisée d'un écran monolithique en un espace de travail principal-détails ciblé pour les opérations quotidiennes de la base de connaissances.

  • Onglets de détail dédiés à la base de connaissances — Les fichiers, l'ajout de documents, les versions d'index et les paramètres sont désormais présentés dans des sections distinctes avec un en-tête compact affichant le fournisseur, le modèle d'intégration, l'état par défaut, l'heure de mise à jour et l'état des tâches en cours.
  • Navigateur de fichiers bruts et aperçu en ligne — le nouvel onglet Fichiers répertorie les documents du répertoire KB raw/ et les ouvre dans un volet d'aperçu en ligne, réutilisant le pipeline d'aperçu du chat pour les PDF, les images, les Markdown, le code/texte et les téléchargements de secours. La liste des fichiers peut être réduite pour récupérer de l'espace d'aperçu.
  • Réindexer les contrôles et les journaux — la section Indexer les versions affiche les versions actives, obsolètes, héritées et inactives, avec une action de réindexation one-click et des journaux de processus en direct pour les tâches de reconstruction.
  • Hooks de progression et d'historique — useKnowledgeBases, useKnowledgeProgress et useKnowledgeHistory fusionnent l'état du serveur avec la progression WebSocket/SSE en direct, actualisent automatiquement le travail actif et gardent visibles les résultats récents de création/téléchargement/réindexation.

Intégration du runtime, de la couverture des fournisseurs et de la découverte des dimensions

La pile d'intégration a été resserrée autour du comportement spécifique au fournisseur au lieu de supposer que chaque service se comporte comme le point de terminaison par défaut d'OpenAI.

  • Plus de valeur par défaut 3072 codée en dur — la dimension d'intégration commence désormais comme inconnue/vide et est automatiquement remplie à partir de la réponse du fournisseur après un test de connexion réussi. La sonde de test évite délibérément d'envoyer dimensions afin de mesurer la longueur du vecteur natif du modèle avant toute troncature de Matryoshka.
  • Sémantique complète des URL des points de terminaison — Les adaptateurs d'intégration basés sur httpx traitent désormais les URL EMBEDDING_HOST/catalogue comme le point de terminaison exact à appeler, tandis que le nouvel adaptateur openai_sdk conserve le comportement de l'URL de base /v1 de style SDK. .env.example documente des exemples concrets de points de terminaison pour OpenAI, Cohere, Jina, Ollama, SiliconFlow et Aliyun DashScope.
  • Nouveaux adaptateurs et liaisons d'intégration — ajout de la prise en charge officielle de l'intégration OpenAI SDK, des intégrations multimodales natives Aliyun DashScope, des préréglages SiliconFlow, des profils OpenRouter/OpenAI-SDK personnalisés, des limites de lots du fournisseur, des indicateurs de fournisseur multimodal et des solutions de secours de clé API par fournisseur.
  • Demandes d'intégration multimodales — EmbeddingRequest accepte désormais le contents structuré plus DashScope enable_fusion ; Cohere v2, Jina, les passerelles compatibles OpenAI et DashScope gèrent les charges utiles multimodales via leurs propres règles d'adaptateur.
  • Meilleures erreurs de fournisseur — les échecs d'intégration préservent désormais le statut du fournisseur, le corps, le modèle et le contexte de l'URL, avec une gestion plus claire des réponses 4xx et des réponses de passerelle non JSON/HTML.

Flux de raisonnement LLM et robustesse de l'attachement à la vision

Les traces de raisonnement et les pièces jointes d'images circulent désormais via davantage de chemins de fournisseur avec moins de surprises spécifiques au fournisseur.

  • Deltas de raisonnement — on_reasoning_delta est câblé via le contrat du fournisseur LLM de base, le streaming compatible OpenAI, le streaming Azure SDK, les chemins anthropiques et l'analyse des réponses OpenAI. La sortie de streaming encapsule le texte de raisonnement dans <think>...</think> avant la reprise du contenu normal.
  • Paramètres de raisonnement DeepSeek — Les modèles de modèle de raisonnement DeepSeek peuvent injecter automatiquement un effort de raisonnement élevé lorsque l'appelant n'en a pas spécifié, correspondant aux fournisseurs qui nécessitent un passage explicite à la sortie de réflexion de surface.
  • Drapeaux de capacité d'URL de vision : les capacités du fournisseur/modèle distinguent désormais "prend en charge la vision" de "accepte les URL d'image". Les modèles de vision Moonshot/Kimi et les adaptateurs de style Anthropic forcent les URL de pièces jointes locales en base64 en ligne lorsque cela est possible.
  • Résolution d'URL de pièce jointe locale — Les URL d'image /api/attachments/... peuvent être résolues via le magasin de pièces jointes et envoyées en base64 aux fournisseurs qui rejettent le formulaire d'URL distante ; les URL externes non résolues sont comptées comme des entrées d'image supprimées au lieu de prétendre silencieusement qu'elles ont été envoyées.

Space Hub, tags de compétences et UX de la bibliothèque personnelle

Les artefacts d'apprentissage personnel ont été rassemblés dans une nouvelle zone Espace dans la barre latérale.

  • Navigation spatiale — /space redirige vers /space/notebooks et les nouveaux groupes de mini-nav Carnets, Banque de questions, Compétences et Mémoire avec un style d'en-tête de section partagé.
  • Section Carnets — les carnets peuvent être créés, supprimés, recherchés, ouverts et inspectés avec des aperçus d'enregistrement rendus. Les sorties TutorBot, chat, recherche et Co-Writer enregistrées reçoivent des badges distincts et peuvent renvoyer à la session de discussion d'origine lorsque les métadonnées sont disponibles.
  • Section Banque de questions — les entrées du quiz peuvent être filtrées par toutes/marquées/incorrectes uniquement, regroupées par catégories, renommées, supprimées des catégories, mises en favoris, supprimées et rouvertes dans leur contexte source.
  • Section Mémoire — la page Mémoire se déplace dans l'espace avec les modes d'édition/aperçu pour le résumé et le profil, la sauvegarde manuelle, l'actualisation de la session, les actions claires, l'état des modifications non enregistrées et les commentaires localisés.
  • Section Compétences — Les compétences créées par les utilisateurs prennent désormais en charge les balises dans le frontmatter ainsi qu'un vocabulaire .tags.json. Le API ajoute une liste de balises/créer/renommer/supprimer des points de terminaison, et l'interface utilisateur peut filtrer par balise, gérer les balises, renommer les compétences et modifier les affectations de balises tout en préservant le flux de travail SKILL.md existant.

Couches de dépendance, débogage de TutorBot et démarrage de Windows

L'histoire de l'installation a été réorganisée autour des extras de pyproject, avec des fichiers d'exigences conservés comme miroirs pour les environnements Docker/CI. Cela rend également la configuration de TutorBot et le débogage des canaux moins ambigus : le moteur d'agent, les SDK du canal, les dépendances natives de Matrix et les importations du fournisseur de serveur principal résident désormais dans des couches clairement séparées.

  • Hiérarchie des extras — .[cli] inclut désormais RAG, l'analyse de documents et le fournisseur intégré SDK ; .[server] s'appuie sur CLI avec FastAPI/uvicorn ; Capacités facultatives des couches .[tutorbot], .[matrix], .[math-animator], .[dev] et .[all] explicitement.
  • ** Limite de dépendance de TutorBot ** — requirements/tutorbot.txt reflète désormais .[tutorbot], dépend de server.txt et conserve les dépendances de canal/agent telles que cron, MCP, Telegram, Feishu/Lark, DingTalk, Slack, QQ, Socket.IO, chaussettes et les outils de pack de messages dans la couche TutorBot au lieu de les mélanger dans l'installation de base.
  • Répartition du canal Matrix — La prise en charge de Matrix/Element a ses propres .[matrix] supplémentaires et requirements/matrix.txt, avec matrix-nio[e2e], des assistants de désinfection Markdown et des notes de configuration explicites libolm pour les dépendances de chiffrement natif.
  • Correction de dépendance d'exécution (#391) — loguru et json-repair ont été déplacés dans la couche de dépendance du serveur car les importations principales du fournisseur en ont besoin avant que TutorBot ne soit impliqué. Cela corrige les installations de serveur propres qui plantaient auparavant sur des modules manquants.
  • Robuste du lanceur Windows (#391, #398) — scripts/start_web.py lit désormais la sortie du sous-processus backend/frontend au format UTF-8 avec remplacement, évitant ainsi UnicodeDecodeError sur les paramètres régionaux Windows tels que GBK.
  • Docs et astuces CLI — Les messages d'erreur README, README chinois, CLI README et CLI pointent désormais les utilisateurs vers pip install -e ".[cli]" / pip install -e ".[server]" au lieu des anciennes commandes axées sur les exigences. Un nouveau requirements/matrix.txt reflète le supplément Matrix et documente le prérequis natif du libolm.

Corrections de bugs

  • Diagnostics de téléchargement/création de connaissances (#392, #405) — Les tâches d'initialisation, de téléchargement et de réindexation de la base de connaissances propagent désormais les détails des échecs et empilent les traces via les journaux de tâches ; l'interface utilisateur peut afficher des erreurs plus riches au lieu de sembler ne rien faire lorsque l'ingestion en arrière-plan échoue.
  • Validation du nom de la base de connaissances — Les chemins de création HTTP et CLI rejettent désormais les caractères de type chemin ou réservés par une URL tout en préservant les noms compatibles Unicode, empêchant ainsi les dossiers de la base de connaissances non valides et les itinéraires dangereux.
  • Découverte de documents insensibles à la casse — L'analyse du répertoire KB et la collecte de documents CLI utilisent désormais le routeur de fichiers partagés, de sorte que les extensions en majuscules telles que .PDF et .MD sont acceptées de manière cohérente.
  • Noms de fichiers de documents plus sûrs — les noms de fichiers téléchargés sont normalisés, les fragments de chemin sont supprimés et les extensions sont en minuscules avant la validation et le stockage.
  • Sécurité du traitement des fichiers bruts — Les points de terminaison des fichiers bruts de la Ko résolvent les chemins strictement sous le répertoire raw/ et rejettent les tentatives de traversée.
  • Superposition de l'environnement du catalogue de modèles — Les valeurs .env ne sont synchronisées dans le catalogue que tant qu'il semble intact, évitant ainsi les écrasements accidentels une fois que les utilisateurs disposent de plusieurs profils personnalisés.
  • Research reporting fallback (#404) — l'avertissement de repli JSON de l'agent déclarant utilise désormais une chaîne f afin que les enregistreurs qui n'appliquent pas le formatage % incluent toujours le titre de la section proprement.

DeepTutor v1.3.0

DeepTutor v1.3.0 Release Notes

Release Date: 2026.04.27

Highlights

Versioned Knowledge Base Indexes and Re-index Workflow

Knowledge bases now keep vector indexes per embedding configuration instead of treating one llamaindex_storage/ directory as the whole truth. Each new index version records an embedding signature and metadata, so switching models no longer has to overwrite the previous index, and switching back can reuse a ready version when the signature matches.

  • Versioned storage layout — new indexes are written as flat version-N/ directories with meta.json; legacy root and nested llamaindex_storage layouts remain readable for existing installs.
  • Embedding-aware reads and writes — RAG search, document additions, manager statistics, and delete/cleanup paths now resolve storage through the active embedding signature. If no ready version matches the current embedding model, retrieval returns a clear needs_reindex signal instead of failing later with an opaque storage error.
  • Background re-index API — POST /api/v1/knowledge/{kb_name}/reindex rebuilds a KB against the active embedding configuration, streams logs through the existing task channel, and returns noop: true when a matching ready index already exists.
  • Index status surfaced to the UI — KB summaries now include index-version metadata, active-match state, embedding mismatch flags, progress, and re-index readiness so the frontend can explain why a KB needs rebuilding.

Knowledge Management Page Rebuild

The Knowledge page has been split from a monolithic screen into a focused master-detail workspace for day-to-day KB operations.

  • Dedicated KB detail tabs — Files, Add documents, Index versions, and Settings now live as separate sections with a compact header showing provider, embedding model, default status, update time, and live task status.
  • Raw file browser and inline preview — the new Files tab lists documents from the KB raw/ directory and opens them in an inline preview pane, reusing the chat preview pipeline for PDFs, images, Markdown, code/text, and fallback downloads. The file list can collapse to reclaim preview space.
  • Re-index controls and logs — the Index versions section shows active, stale, legacy, and inactive versions, with a one-click Re-index action and live process logs for rebuild tasks.
  • Progress and history hooks — useKnowledgeBases, useKnowledgeProgress, and useKnowledgeHistory merge server state with live WebSocket/SSE progress, auto-refresh active work, and keep recent create/upload/re-index outcomes visible.

Embedding Runtime, Provider Coverage, and Dimension Discovery

The embedding stack was tightened around provider-specific behavior instead of assuming every service behaves like OpenAI's default endpoint.

  • No more hard-coded 3072 default — embedding dimension now starts as unknown/empty and is auto-filled from the provider response after a successful test connection. The test probe deliberately avoids sending dimensions so it measures the model's native vector length before any Matryoshka truncation.
  • Full endpoint URL semantics — httpx-based embedding adapters now treat EMBEDDING_HOST / catalog URLs as the exact endpoint to call, while the new openai_sdk adapter keeps SDK-style /v1 base URL behavior. .env.example documents concrete endpoint examples for OpenAI, Cohere, Jina, Ollama, SiliconFlow, and Aliyun DashScope.
  • New embedding adapters and bindings — added official OpenAI SDK embedding support, Aliyun DashScope native multimodal embeddings, SiliconFlow presets, OpenRouter/custom OpenAI-SDK profiles, provider batch limits, multimodal provider flags, and per-provider API-key fallbacks.
  • Multimodal embedding requests — EmbeddingRequest now accepts structured contents plus DashScope enable_fusion; Cohere v2, Jina, OpenAI-compatible gateways, and DashScope handle multimodal payloads through their own adapter rules.
  • Better provider errors — embedding failures now preserve provider status, body, model, and URL context, with clearer handling for 4xx responses and non-JSON/HTML gateway replies.

LLM Reasoning Streams and Vision Attachment Robustness

Reasoning traces and image attachments now flow through more provider paths with less provider-specific surprise.

  • Reasoning deltas — on_reasoning_delta is wired through the base LLM provider contract, OpenAI-compatible streaming, Azure SDK streaming, Anthropic paths, and OpenAI Responses parsing. Streaming output wraps reasoning text in <think>...</think> before normal content resumes.
  • DeepSeek reasoning defaults — DeepSeek reasoning model patterns can auto-inject a high reasoning effort when the caller has not specified one, matching providers that require an explicit switch to surface thinking output.
  • Vision URL capability flags — provider/model capabilities now distinguish "supports vision" from "accepts image URLs." Moonshot/Kimi vision models and Anthropic-style adapters force local attachment URLs into inline base64 when possible.
  • Local attachment URL resolution — /api/attachments/... image URLs can be resolved back through the attachment store and sent as base64 to providers that reject remote URL form; unresolved external URLs are counted as dropped image inputs instead of silently pretending they were sent.

Space Hub, Skills Tags, and Personal Library UX

Personal learning artifacts have been gathered under a new Space area in the sidebar.

  • Space navigation — /space redirects to /space/notebooks and the new mini-nav groups Notebooks, Question Bank, Skills, and Memory with a shared section header style.
  • Notebooks section — notebooks can be created, deleted, searched, opened, and inspected with rendered record previews. Saved TutorBot, chat, research, and Co-Writer outputs receive distinct badges and can link back to the original chat session when metadata is available.
  • Question Bank section — quiz entries can be filtered by all/bookmarked/wrong-only, grouped with categories, renamed, removed from categories, bookmarked, deleted, and opened back in their source context.
  • Memory section — the Memory page moves into Space with edit/preview modes for summary and profile, manual save, refresh-from-session, clear actions, unsaved-change status, and localized feedback.
  • Skills section — user-authored skills now support tags in frontmatter plus a .tags.json vocabulary. The API adds tag list/create/rename/delete endpoints, and the UI can filter by tag, manage tags, rename skills, and edit tag assignments while preserving the existing SKILL.md workflow.

Dependency Layers, TutorBot Debugging, and Windows Startup

The install story has been reorganized around pyproject extras, with requirements files kept as mirrors for Docker/CI environments. This also makes TutorBot setup and channel debugging less ambiguous: the agent engine, channel SDKs, Matrix native dependencies, and core server provider imports now live in clearly separated layers.

  • Extras hierarchy — .[cli] now includes RAG, document parsing, and built-in provider SDKs; .[server] builds on CLI with FastAPI/uvicorn; .[tutorbot], .[matrix], .[math-animator], .[dev], and .[all] layer optional capabilities explicitly.
  • TutorBot dependency boundary — requirements/tutorbot.txt now mirrors .[tutorbot], depends on server.txt, and keeps channel/agent dependencies such as cron, MCP, Telegram, Feishu/Lark, DingTalk, Slack, QQ, Socket.IO, socks, and message-pack tooling in the TutorBot layer instead of mixing them into the base install.
  • Matrix channel split-out — Matrix / Element support has its own .[matrix] extra and requirements/matrix.txt, with matrix-nio[e2e], Markdown sanitization helpers, and explicit libolm setup notes for native encryption dependencies.
  • Runtime dependency fix (#391) — loguru and json-repair moved into the server dependency layer because provider-core imports need them before TutorBot is involved. This fixes clean server installs that previously crashed on missing modules.
  • Windows launcher robustness (#391, #398) — scripts/start_web.py now reads backend/frontend subprocess output as UTF-8 with replacement, avoiding UnicodeDecodeError on Windows locales such as GBK.
  • Docs and CLI hints — README, Chinese README, CLI README, and CLI error messages now point users to pip install -e ".[cli]" / pip install -e ".[server]" instead of older requirements-first commands. A new requirements/matrix.txt mirrors the Matrix extra and documents the native libolm prerequisite.

Bug Fixes

  • Knowledge upload/create diagnostics (#392, #405) — KB initialization, upload, and re-index tasks now propagate failure details and stack traces through task logs; the UI can show richer errors instead of appearing to do nothing when background ingestion fails.
  • KB name validation — HTTP and CLI creation paths now reject path-like or URL-reserved characters while preserving Unicode-friendly names, preventing invalid KB folders and unsafe routes.
  • Case-insensitive document discovery — KB directory scanning and CLI document collection now use the shared file router, so uppercase extensions such as .PDF and .MD are accepted consistently.
  • Safer document filenames — uploaded filenames are normalized, path fragments are stripped, and extensions are lowercased before validation and storage.
  • Raw file serving safety — KB raw-file endpoints resolve paths strictly under the raw/ directory and reject traversal attempts.
  • Model catalog environment overlay — .env values are only synced into the catalog while it still looks pristine, avoiding accidental overwrites once users have multiple custom profiles.
  • Research reporting fallback (#404) — the reporting agent's JSON-fallback warning now uses an f-string so loggers that do not apply % formatting still include the section title cleanly.

Test Suite Expansion

  • Knowledge/RAG — new coverage for KB naming, index-version allocation and read priority, legacy-to-flat storage compatibility, LlamaIndex storage layout, raw directory initialization, case-insensitive file routing, KB deletion, and API upload edge cases.
  • Embedding/config — new tests cover dimension auto-fill from test probes, catalog .env overlay behavior, DashScope and OpenAI SDK adapters, Qwen3 send_dimensions, URL transparency, non-JSON provider responses, and multimodal embedding requests.
  • LLM/multimodal — new tests validate reasoning/vision capability behavior and local attachment URL conversion for providers that require inline base64 images.
  • CLI and validation — CLI KB collection and document validator tests cover uppercase extensions, Chinese filenames, and Windows-style path stripping.

Community Contributions

  • @jonathanzhan1975 — Fix Windows server startup and missing server runtime dependencies affecting clean Web/TutorBot installs (#391)
  • @kagura-agent — Clean up reporting-agent fallback logging for JSON parse failures (#404)

Recent open discussions after v1.2.5 also shaped this release window, especially KB upload/create failures (#392, #405), TutorBot Agent restart/state reports (#385), Windows startup reports (#398), dependency-installation pain (#402), JSON robustness feedback (#400), and the next wave of Space/Memory/project organization requests (#397, #401, #403).
