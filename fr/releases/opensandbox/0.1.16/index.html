OpenSandbox python/sandbox/v0.1.16

Quoi de neuf

✨Caractéristiques

  • Transport HTTP résilient — Les clients asynchrones et synchronisés partagent désormais un transport de nouvelle tentative configurable avec intervalle d'attente, gigue, gestion de Retry-After, délais d'attente par tentative, un délai global et des rappels de nouvelle tentative. Les tentatives sont activées par défaut pour les requêtes idempotentes sur HTTP 429, 502 et 503 ; les appelants qui nécessitent le comportement d'échec rapide précédent peuvent utiliser RetryPolicy.disabled(). Les transports fournis par l'utilisateur restent intacts et les requêtes SSE en streaming contournent la relecture. #1372
  • Hooks de cycle de vie Sandbox — Sandbox.create et SandboxSync.create acceptent désormais preStart en option et les hooks de cycle de vie périodiques, avec des modèles Python stables et une validation alignée sur le serveur. Les plages de délais d'expiration du hook font autorité sur le serveur. #1588 #1605
  • Exécutions en arrière-plan dans des sessions isolées — Les sessions isolées peuvent démarrer un travail détaché et interroger son état et sa sortie combinée incrémentielle. Les exécutions actives en arrière-plan suspendent la collecte inactive ; les espaces de travail en lecture seule rejettent l'exécution en arrière-plan car ils ne peuvent pas conserver les journaux d'exécution. #1456
  • Allocation d'exécution et visibilité du renforcement — Les réponses du bac à sable peuvent exposer des résumés d'allocation de pool confirmés, tandis que les fonctionnalités isolées incluent le mode d'initialisation exécuté et l'état de la couche de renforcement. Ces champs sont additifs et restent absents lorsque le serveur ne peut pas confirmer l'état correspondant. #1481 #1474
  • Contre-pression de capacité du pool — Les serveurs de cycle de vie compatibles peuvent désormais afficher la capacité épuisée du pool Kubernetes en tant que HTTP 429 avec KUBERNETES::POOL_CAPACITY_EXHAUSTED et Retry-After, au lieu de signaler éventuellement un délai d'attente de préparation générique. La création du sandbox reste non idempotente et n'est pas automatiquement rejouée sur ce statut. #1581

⚡Performances

  • Démarrage plus rapide du sandbox — La création, la connexion et la reprise du sandbox asynchrone résolvent simultanément les points de terminaison d'exécution et de sortie, réduisant ainsi les deux recherches de gestion API à une seule attente parallèle. La propagation des échecs et la sémantique de création de nettoyage restent inchangées. #1531
  • Nettoyage de pool parallèle limité — La version inactive du bac à sable utilise la concurrence limitée tout en préservant le nettoyage au mieux et le comportement public hérité. Le nettoyage mesuré de 100 bacs à sable dans le PR est passé d'environ 8.3 secondes à 0.8 secondes. #1475

🐛 Corrections de bugs

  • Analyse SSE conforme aux normes — Les flux de commandes et d'exécution isolés utilisent désormais un cadrage spécifique à SSE, préservant les séparateurs Unicode à l'intérieur des chaînes JSON tout en restant compatible avec les anciennes trames nues JSON. #1444
  • Achèvement fiable des commandes en arrière-plan — Les flux de commandes en arrière-plan s'arrêtent après execution_complete, empêchant ainsi les faux échecs de RemoteProtocolError lorsque le homologue se ferme avant le terminateur HTTP final. Le comportement du streaming au premier plan est inchangé. #1532
  • Correction de la course au cache des points de terminaison — L'exécution d'une récupération de point de terminaison plus ancienne ne supprime plus une récupération en vol de remplacement plus récente dans les clients asynchrones ou synchronisés. #1567
  • Erreurs API plus utiles — Les corps de réponse non structurés 4xx et 5xx sont inclus dans les messages d'exception et restent disponibles sous forme d'octets bruts response_body. Les réponses HTTP 429 utilisent SandboxRateLimitException et exposent retry_after analysé lorsqu'il est présent. #1496 #1372
  • Diagnostics de préparation au nettoyeur : les messages d'expiration du délai de préparation conservent la synchronisation, le contexte de connexion et la dernière erreur de vérification de l'état sans suggérer des correctifs réseau spécifiques au déploiement qui peuvent ne pas s'appliquer. #1493

📦 Divers

  • Modèles de cycle de vie régénérés, remplacement de la version de secours du package par 0.1.16 et alignement des chaînes d'agent utilisateur asynchrones et synchronisées par défaut avec la version. #1622 #1623

OpenSandbox python/sandbox/v0.1.16

What's New

✨ Features

  • Resilient HTTP transport — Async and sync clients now share a configurable retry transport with backoff, jitter, Retry-After handling, per-attempt timeouts, an overall deadline, and retry callbacks. Retries are enabled by default for idempotent requests on HTTP 429, 502, and 503; callers that require the previous fast-fail behavior can use RetryPolicy.disabled(). User-supplied transports remain untouched, and streaming SSE requests bypass replay. #1372
  • Sandbox lifecycle hooks — Sandbox.create and SandboxSync.create now accept optional preStart and periodic lifecycle hooks, with stable Python models and server-aligned validation. Hook timeout ranges remain server-authoritative. #1588 #1605
  • Background runs in isolated sessions — Isolated sessions can start detached work and poll its status and incremental combined output. Active background runs suspend idle collection; read-only workspaces reject background execution because they cannot persist run logs. #1456
  • Runtime allocation and hardening visibility — Sandbox responses can expose confirmed Pool allocation summaries, while isolated capabilities include execd init mode and hardening-layer state. These fields are additive and remain absent when the server cannot confirm the corresponding state. #1481 #1474
  • Pool capacity back-pressure — Compatible lifecycle servers can now surface exhausted Kubernetes Pool capacity as HTTP 429 with KUBERNETES::POOL_CAPACITY_EXHAUSTED and Retry-After, instead of eventually reporting a generic readiness timeout. Sandbox creation remains non-idempotent and is not automatically replayed on this status. #1581

⚡ Performance

  • Faster sandbox startup — Async sandbox creation, connection, and resume resolve execd and egress endpoints concurrently, reducing the two management API lookups to one parallel wait. Failure propagation and create cleanup semantics remain unchanged. #1531
  • Bounded parallel Pool cleanup — Idle sandbox release uses bounded concurrency while preserving best-effort cleanup and legacy public behavior. The measured 100-sandbox cleanup in the PR dropped from about 8.3 seconds to 0.8 seconds. #1475

🐛 Bug Fixes

  • Standards-compliant SSE parsing — Command and isolated execution streams now use SSE-specific framing, preserving Unicode separators inside JSON strings while remaining compatible with legacy bare-JSON frames. #1444
  • Reliable background command completion — Background command streams stop after execution_complete, preventing false RemoteProtocolError failures when the peer closes before the final HTTP terminator. Foreground streaming behavior is unchanged. #1532
  • Endpoint cache race fix — Completing an older endpoint fetch no longer removes a newer replacement inflight fetch in async or sync clients. #1567
  • More useful API errors — Unstructured 4xx and 5xx response bodies are included in exception messages and remain available as raw response_body bytes. HTTP 429 responses use SandboxRateLimitException and expose parsed retry_after when present. #1496 #1372
  • Cleaner readiness diagnostics — Readiness timeout messages retain timing, connection context, and the last health-check error without suggesting deployment-specific network fixes that may not apply. #1493

📦 Misc

  • Regenerated lifecycle models, bumped the package fallback version to 0.1.16, and aligned async and sync default User-Agent strings with the release. #1622 #1623
