Vingt-huit jours et 280 pull request. Le travail s'est déroulé sur trois fronts : exploiter une flotte, l'alimenter en modèles provenant de sources privées et réparer les backends dont vous dépendez. 🚀 Nouvelles fonctionnalités et améliorations majeures

📊 Tableau de bord des opérations de flotte

La page Nœuds était une liste plate de cartes par nœud. Il vous montrait ce qui était enregistré mais pas ce que faisait le cluster, et chaque action du cycle de vie concernait un nœud à la fois.

La réécriture est un tableau de bord des opérations de flotte avec deux onglets et un interrogeur récapitulatif partagé.

ClusterOverview se trouve en haut. Une bande de santé segmente les nœuds en comptes sains, épuisants et attentifs. Les jauges de capacité affichent la VRAM, la RAM, le CPU et le disque, chacun indiquant le nombre de travailleurs qui ne signalent pas cette métrique, de sorte que le nombre est honnête plutôt que moyenné sur les nœuds de reporting. Une file d'attente d'attention filtre les nœuds en attente d'approbation, hors ligne/malsains, VRAM faible, RAM faible et disque faible, faisant apparaître les nœuds qui nécessitent une action sans compter deux fois le total global. NodeFleetTable est triable, regroupable (par étiquette ou type) et paginé à 50 lignes par page, avec une sélection de cases à cocher qui persiste dans les filtres et les pages. Bulk Drain, Resume et Remove s’exécutent avec une concurrence limitée (limite 8), de sorte qu’une flotte avec des milliers d’enregistrements est utilisable. Colonnes : pilule d'état, adresse, capacité (VRAM + RAM), CPU, charge de travail et rythme cardiaque. Un bouton Approuver apparaît sur les nœuds en attente.

Onglet Modèles en cours d'exécution. Une vue à l'échelle du parc des réplicas chargés sur des travailleurs sains, regroupés par modèle : nom du modèle, nombre de réplicas, nombre de nœuds, demandes en cours, types de backend et dernière utilisation. L'arrêt par modèle arrête tous les placements via POST /backend/shutdown {model}, qui déclenche désormais le déchargeur à distance même lorsqu'un processus local existe et déduplique les nœuds avant d'envoyer des messages d'arrêt.

Inspecteurs. Un NodeInspector coulissant affiche l'état de santé, les étiquettes, les barres de ressources, le processeur, le nombre de modèles chargés, les backends (chargés paresseux) et en cours, avec les actions Approuver/Vider/Reprendre. Un ModelInspector affiche le placement des réplicas regroupés par nœud, avec des noms de nœuds clickable qui explorent un NodeInspector.

Les travailleurs signalent désormais cpu_logical_cores, cpu_usage_percent et cpu_load_1 lors de l'enregistrement et du battement de cœur. Le tableau de bord affiche la capacité et l'utilisation du processeur, avec des cœurs inactifs dérivés comme cpu_logical_cores * (1 - cpu_usage_percent / 100).

Les transitions du cycle de vie sont désormais atomiques. MarkDraining inverse le statut et supprime les enregistrements de modèle en une seule transaction plutôt que dans le cadre d'opérations distinctes qui pourraient s'entrelacer avec SetNodeModel. ResumeNode est conditionnel : drainage vers sain uniquement, empêchant l'écrasement de l'approbation en attente ou des changements d'état simultanés. Les points de terminaison HTTP renvoient les numéros 404 (introuvable) et 409 (conflit de statut) au lieu d'un 500 générique.

🔑 Fichier d'informations d'identification pour les sources privées

Les backends, les modèles et les index de galerie peuvent vivre derrière des registres OCI privés, des serveurs HTTP internes ou des dépôts GitHub privés. Avant cela, chaque chemin de téléchargement disposait de son propre mécanisme d'authentification ad hoc et les jetons étaient dispersés entre les variables d'environnement.

Un fichier credentials.yaml, chargé par --credentials-file / LOCALAI_CREDENTIALS_FILE, les authentifie tous. Il s'agit d'une liste de règles YAML de niveau supérieur. Chaque règle a un préfixe d'URL match et exactement un type d'authentification : de base (username + password / password_env / password_file), porteur (bearer / bearer_env / bearer_file) ou en-tête personnalisé (header.name + header.value / header.value_env / header.value_file). Exactement une des formes simples, _env ou _file par secret ; Les clés inconnues sont des erreurs, donc un pasword_env mal orthographié échoue bruyamment.

Les registres OCI (images backend, modèles oci:// et ollama://, recherche de résumé, reprise de plage, vérification de cosign) consultent d'abord le magasin, puis authn.DefaultKeychain (configuration docker). Les téléchargements HTTP, les galeries et les URI github: s'authentifient via un http.RoundTripper qui place les informations d'identification sur un clone de la requête. net/http reconstruit chaque saut de redirection à partir des en-têtes d'origine, de sorte qu'une redirection vers un autre hôte ne transporte jamais les informations d'identification. Un identifiant fourni par l'appelant (par exemple HF_TOKEN) est prioritaire : le transport laisse seul un en-tête Authorization existant. Les secrets sont lus au moment de l'utilisation, pas au moment du chargement, donc un montage secret du K8 pivoté prend effet sans redémarrage. Credential et Store implémentent String, GoString et LogValue, donc aucun verbe fmt ou appel slog, y compris lorsqu'ils sont imbriqués dans des champs non exportés, ne peut imprimer du matériel secret. Les informations d'identification vont uniquement à https ou à http lorsque la règle définit allow_insecure. Les chaînes de correspondance contenant user:token@, ? (où les URL signées contiennent des jetons) ou # sont rejetées au chargement. Les erreurs de décodage YAML sont supprimées : les valeurs scalaires citées (souvent secrètes) sont supprimées, ne conservant que les numéros de ligne et le libellé de l'analyseur.

🔗 PR : #12028

📏 Commande local-ai benchmark CLI

Une commande de référence pour les modèles de texte configurés, répondant « à quelle vitesse ce modèle est-il sur ce matériel » sans quitter le terminal.

local-ai benchmark MODEL [MODEL ...] envoie des requêtes POST /v1/chat/completions sans streaming à temperature:0 avec --runs configurable (par défaut 3), --warmup (par défaut 1), --max-tokens (par défaut 128) et --timeout (par défaut 5m). Il rapporte la latence minimale, moyenne et maximale et les jetons d'achèvement de bout en bout/s par modèle.

La métrique de débit est sum(completion_tokens) / sum(latencies) sur les exécutions mesurées. Il s'agit de nil/N/A si un échantillon omet completion_tokens dans l'utilisation de la réponse, ou si la latence totale est nulle. La commande ne mesure pas la vitesse ou le temps de décodage uniquement jusqu'au premier jeton ; il s'agit d'un benchmark client de bout en bout couvrant le transport HTTP, la mise en file d'attente, le traitement des invites, la génération et l'analyse.

Le HTTP client refuse les redirections par défaut, donc un point de terminaison mal configuré derrière une redirection ne réussit pas silencieusement. La clé API est supprimée des messages d'erreur et les erreurs de transport brutes sont masquées sous la forme HTTP request failed pour éviter l'écho des informations d'identification. Le rapport complet est mis en mémoire tampon dans un bytes.Buffer et écrit uniquement via le io.Copy une fois que tous les modèles ont réussi, de sorte qu'un échec ne laisse aucune sortie partielle. La gestion du signal annule la requête active sur SIGINT/SIGTERM.

La sortie est une table par défaut ou --json pour les données structurées avec une latence par échantillon et un nombre de jetons nullables. La clé API n'est pas incluse dans le JSON. Pour comparer les backends, configurez des alias de modèle distincts par backend et transmettez ces noms d'alias.

🔗 PR : #12020

🔧 Fusion vllm-cpp LoRA au moment du chargement

Les champs de configuration lora_adapters et lora_scales sont des champs LocalAI standard qui répertorient les fichiers de poids de l'adaptateur LoRA et les multiplicateurs de force par adaptateur. Le backend vidéo vllm-cpp les consomme désormais pour la première fois, fusionnant les deltas LoRA en poids DiT (transformateur de diffusion) à la charge du moteur.

buildLoraExtras convertit les champs de configuration en paires clé-valeur lora_path / lora_strength indexées. Le premier adaptateur n'a pas de suffixe ; les suivants obtiennent _2, _3, etc. Si le singulier lora_adapter est défini, il est ajouté comme premier adaptateur avant la liste plurielle. Les chemins d'accès relatifs à l'adaptateur sont joints au chemin du modèle ; des chemins absolus traversent. La force est par défaut 1.0 lorsqu'aucune échelle n'est fournie.

Les paires sont emballées via la couture extras ABI v18 et remises à vllmVideoEngineLoad. Le ResolveDitLoraSpecs de vllm.cpp fusionne les deltas LoRA dans les poids DiT en charge. Un chemin générique dessert à la fois LTX2.5 et MiniMax-H3, puisque le moteur détecte automatiquement la famille DiT à partir du point de contrôle.

Les adaptateurs sont toujours chargés ; il n'y a pas d'activation par demande dans ce chemin. LoRA activé par l'invite d'exécution (<lora:name:strength> de style punica) est hors de portée et suivi séparément.

🔗 PR : #12082

🌍 Variables d'environnement par modèle

Une carte env: sur la configuration du modèle injecte des variables dans l'environnement de processus backend. Le cas d'utilisation principal consiste à épingler CUDA_VISIBLE_DEVICES par modèle pour contrôler le placement du GPU, mais il s'applique à tout backend qui lit les variables d'environnement.

name: vllm-model
backend: vllm
env:
  CUDA_VISIBLE_DEVICES: "0,1"
  VLLM_CACHE_DIR: "/tmp/vllm_cache"

La carte est fournie via la couche de génération de processus commune dans pkg/model/process.go, de sorte que chaque backend gRPC en hérite sans câblage par backend. Les variables de modèle sont ajoutées en dernier, après l'environnement de base, elles remplacent donc les variables système héritées du même nom. L’interface utilisateur affiche une carte clé/valeur modifiable.

Les variables de modèle ne prennent effet que lorsqu'un modèle génère son propre processus backend, et non lorsqu'il réutilise un processus supervisé par un travailleur. Il n'y a pas de liste d'autorisation ou de liste de blocage : les configurations de modèle constituent une limite d'opérateur trust, cohérente avec la posture générale de LocalAI.

🔗 PR : #10721

💬template.system_messages_after_first

Les frameworks d'agent ajoutent légitimement des instructions système au milieu d'une conversation : une invite de paramètre d'outil avant un appel, une invite d'ajustement après un résultat. La famille Qwen3.x de modèles de tokenizer génère Jinja Exception: System message must be at the beginning pour tout message de rôle système après le premier tour, renvoyant HTTP 500. Le chat simple semble sain ; chaque tâche d'agent échoue.

template.system_messages_after_first contrôle ce qui arrive aux messages de rôle système qui apparaissent après le bloc système principal contigu :

  • "merge" regroupe les messages système tardifs dans le premier message système avec un séparateur \n\n, les laissant tomber de leur position d'origine.
  • "user" réécrit chaque message système tardif en place dans le rôle user, en conservant sa position et son contenu.
  • unset (par défaut) passe sans changement ; le modèle de tokenizer décide.

La normalisation s'exécute dans ChatEndpoint après stripEmptySystemMessages et avant l'injection du modèle de tokenizer system_prompt, de sorte que le modèle Jinja ne voit jamais de message système déplacé. Il ne touche que les requêtes dont la configuration du modèle est activée, le comportement par défaut reste donc inchangé.

"user" est le mode recommandé pour les charges de travail des agents : l'instruction reste là où le framework l'a placée et le modèle la suit.

🔗 PR : #11906

🧠context_size dans /v1/models/capabilities

Le point de terminaison des capacités remplit désormais entry.ContextSize avec backend.EffectiveContextSize(cfg) lorsque le résultat est positif. Clients peut lire la fenêtre de contexte efficace de chaque modèle pour budgétiser les jetons, tronquer les invites et l'historique et éviter d'envoyer plus de contexte que ce que le modèle accepte, sans avoir à sonder la configuration du modèle hors bande.

🔗 PR : #12083

🕵️ Replay de l'inscription en face

Le registre de reconnaissance faciale 1:N obtient un chemin de relecture. FaceRegisterRequest accepte désormais un Embedding (vecteur pré-calculé) et RegisteredAt (horodatage d'origine), de sorte qu'un client qui a précédemment extrait une intégration via /v1/face/embed peut rejouer directement le vecteur, le nom, les étiquettes et l'horodatage enregistrés, en ignorant entièrement le décodage de l'image et l'appel d'inférence FaceEmbed.

Le magasin dérive un ID déterministe à partir des octets d'intégration et de l'espace de noms du magasin via uuid.NewSHA1, donc la relecture du même vecteur après un redémarrage ou sur une autre réplique renvoie le même ID sans créer de doublons. Le serveur ne conserve pas le registre lui-même ; clients doit conserver et relire les enregistrements pour restaurer le registre après un redémarrage.

🔗 PR : #11908

🎯 Basculer le mode de mise au point

Le mode Focus (qui réduit la barre latérale globale de l'application et affine l'en-tête une fois qu'une conversation contient au moins un message, avec Esc les restaurant temporairement) existait déjà en tant que comportement de session uniquement. Cela ajoute une bascule de désinscription persistante dans le tiroir des paramètres de discussion, soutenue par localStorage sous localai_chat_focus_mode. Il est activé par défaut ; avec la bascule désactivée, la mise en page complète reste même dans une conversation active.

LocalAI v4.10.0

Highlights

  • Fleet operations replace flat node monitoring — The Nodes page now provides cluster health, capacity, replica placement, and bulk Drain/Resume/Remove actions with bounded concurrency (#12046). Lifecycle transitions are atomic, while endpoints now return meaningful 404/409 responses; automation should handle these instead of expecting generic 500s.
  • Private-source authentication is centralized and rotatable — Configure credentials.yaml through --credentials-file or LOCALAI_CREDENTIALS_FILE for OCI registries, galleries, HTTP downloads, and github: sources. _env and _file secrets are read at use time, allowing rotated Kubernetes mounts without restart; cross-host redirects do not receive credentials. Validate rules before upgrading because unknown keys and inline URL credentials are rejected.
  • CLI benchmarking supports repeatable performance checks — local-ai benchmark MODEL ... measures end-to-end min/mean/max latency and completion tokens/sec, with configurable warmup, runs, and token limits. Table and JSON output support CI integration; redirects are blocked, API keys are redacted, and reports are emitted only after every requested model succeeds.
  • Model integration and prompt handling become more explicit — /v1/models/capabilities now exposes context_size for client-side token budgeting. Set template.system_messages_after_first to merge or user when agent frameworks append system turns that break Qwen3.x templates. The vllm-cpp video backend also fuses configured LoRA adapters into LTX2.5 and MiniMax-H3 weights at load time; adapters are always loaded rather than activated per request.
  • Security and platform fixes reduce deployment risk — Dependency updates patch CVE-2026-69192, CVE-2026-46680, CVE-2026-53488, and GHSA-qwww-vcr4-c8h2. The go-m1cpu v0.2.2 bump also resolves the Apple M5 startup SIGSEGV.
  • Compatibility — No breaking changes.

LocalAI 4.10.0 is out!

Twenty-eight days and 280 pull requests. The work landed on three fronts: operating a fleet, feeding it models from private sources, and fixing the backends you depend on. A fleet operations dashboard replaces the flat node list with cluster-wide health, capacity, running models, and bulk lifecycle actions. A credentials file lets one credentials.yaml authenticate OCI registries, galleries and direct downloads without scattering tokens across environment variables. And local-ai benchmark measures end-to-end latency and throughput from the CLI.

The ds4 backend had four fixes that together make it reliable on CUDA: the kernels now build for the target architecture, abandoned inference is cancelled, generation boundaries are enforced, and prefilled reasoning is separated from content. Distributed mode gained seven stabilisation fixes across staging, liveness, virtual models and the control-plane database. Four CVEs were patched, enable_thinking=false is now honoured across every text backend, and Apple M5 no longer SIGSEGVs at startup.

Highlights:

  • 📊 Fleet operations dashboard - a real-time cluster overview replacing the flat node list. Aggregate health bands, capacity gauges for VRAM/RAM/CPU/disk, a running-models tab showing replica placement across workers, bulk drain/resume/remove with bounded concurrency, and a slide-out node inspector. Workers now report CPU telemetry at registration and heartbeat.
  • 🔑 Credentials file for private sources - one credentials.yaml authenticates OCI registries, galleries, HTTP downloads and github: URIs. Supports basic auth, bearer tokens and custom headers, with secrets read at use time so rotated K8s secret mounts take effect without restart, and full masking in logs and error messages.
  • 📏 local-ai benchmark CLI command - measures end-to-end latency and throughput against configured text models. Reports min/mean/max latency and completion tokens/sec across warmup and measured runs, with table and JSON output, redirect blocking, and API-key redaction.
  • 🔧 vllm-cpp LoRA fusion at load time - lora_adapters and lora_scales are now consumed by the vllm-cpp video engine, fusing LoRA deltas into DiT weights at engine load. Works for both LTX2.5 and MiniMax-H3 through one generic path.
  • 🌍 Environment variables per model - an env: map in model config injects variables into the backend process environment, so CUDA_VISIBLE_DEVICES or VLLM_CACHE_DIR can be pinned per model without wrapping the backend in a script.
  • 💬 template.system_messages_after_first - agent frameworks that append system instructions mid-conversation no longer crash Qwen3.x models. Late system turns can be merged into the leading system message or forwarded as user turns.
  • 🧠 context_size in /v1/models/capabilities - clients can now read each model's effective context window to budget tokens and truncate prompts without probing the model config out-of-band.
  • 🛡️ Four CVEs patched - ip-address 10.3.1 (CVE-2026-69192), containerd 1.7.32 and 1.7.33 (CVE-2026-46680, CVE-2026-53488), and react-router (GHSA-qwww-vcr4-c8h2).
  • 🍎 Apple M5 SIGSEGV fixed - go-m1cpu bumped to v0.2.2, fixing a segmentation fault on Apple M5 hardware at startup.

Plus a focus mode toggle in chat settings, face enrollment replay for the 1:N registry, a ROCm build of stablediffusion-ggml, in-place editing of distributed scheduling rules, OCI layer download resumption, and 140 new gallery entries.

📊 Fleet operations dashboard

The Nodes page was a flat list of per-node cards. It showed you what was registered but not what the cluster was doing, and every lifecycle action was one node at a time.

The rewrite is a fleet operations dashboard with two tabs and a shared summary poller.

ClusterOverview sits at the top. A health band segments nodes into healthy, draining and attention counts. Capacity gauges show VRAM, RAM, CPU and disk, each reporting how many workers do not report that metric so the number is honest rather than averaged over reporting nodes. An attention queue filters for pending approval, offline/unhealthy, low VRAM, low RAM and low disk, surfacing nodes that need action without double-counting the headline total.

NodeFleetTable is sortable, groupable (by label or type) and paginated at 50 rows per page, with checkbox selection that persists across filters and pages. Bulk Drain, Resume and Remove run with bounded concurrency (limit 8) so a fleet with thousands of registrations is usable. Columns: status pill, address, capacity (VRAM + RAM), CPU, workload and heartbeat. An Approve button appears on pending nodes.

Running models tab. A fleet-wide view of loaded replicas on healthy workers, grouped by model: model name, replica count, node count, in-flight requests, backend types and last used. Per-model Stop shuts down all placements through POST /backend/shutdown {model}, which now fires the remote unloader even when a local process exists, and deduplicates nodes before sending stop messages.

Inspectors. A slide-out NodeInspector shows health, labels, resource bars, CPU, loaded model count, backends (lazy-loaded) and in-flight, with Approve/Drain/Resume actions. A ModelInspector shows replica placement grouped by node, with clickable node names that drill into a NodeInspector.

🔑 Credentials file for private sources

Backends, models and gallery indexes can live behind private OCI registries, internal HTTP servers or private GitHub repos. Before this, each download path had its own ad-hoc auth mechanism, and tokens were scattered across environment variables.

One credentials.yaml file, loaded by --credentials-file / LOCALAI_CREDENTIALS_FILE, authenticates them all. It is a top-level YAML list of rules. Each rule has a match URL prefix and exactly one auth type: basic (username + password / password_env / password_file), bearer (bearer / bearer_env / bearer_file), or custom header (header.name + header.value / header.value_env / header.value_file). Exactly one of the plain, _env or _file form per secret; unknown keys are errors so a misspelled pasword_env fails loudly.

OCI registries (backend images, oci:// and ollama:// models, digest lookup, Range resume, cosign verify) consult the store first, then authn.DefaultKeychain (docker config). HTTP downloads, galleries and github: URIs authenticate through an http.RoundTripper that puts the credential on a clone of the request. net/http rebuilds each redirect hop from the original headers, so a redirect to another host never carries the credential. A caller-supplied credential (e.g. HF_TOKEN) takes precedence: the transport leaves an existing Authorization header alone.

Secrets are read at use time, not load time, so a rotated K8s secret mount takes effect without restart. Credential and Store implement String, GoString and LogValue, so no fmt verb or slog call, including when nested in unexported fields, can print secret material. Credentials go only to https, or to http when the rule sets allow_insecure. Match strings containing user:token@, ? (where signed URLs carry tokens) or # are rejected at load. YAML decode errors are redacted: quoted scalar values (often secrets) are stripped, keeping only line numbers and parser wording.

🔗 PRs: #12028

📏 local-ai benchmark CLI command

A benchmark command for configured text models, answering "how fast is this model on this hardware" without leaving the terminal.

local-ai benchmark MODEL [MODEL ...] sends non-streaming POST /v1/chat/completions requests at temperature:0 with configurable --runs (default 3), --warmup (default 1), --max-tokens (default 128) and --timeout (default 5m). It reports min, mean and max latency and end-to-end completion tokens/sec per model.

The throughput metric is sum(completion_tokens) / sum(latencies) across measured runs. It is nil/N/A if any sample omits completion_tokens from the response usage, or if total latency is zero. The command does not measure decode-only speed or time to first token; it is an end-to-end client benchmark covering HTTP transport, queueing, prompt processing, generation and parse.

The HTTP client refuses redirects by default, so a misconfigured endpoint behind a redirect does not silently succeed. The API key is redacted from error messages, and raw transport errors are masked as HTTP request failed to avoid credential echo. The full report is buffered in a bytes.Buffer and only written via io.Copy after all models succeed, so a failure leaves no partial output. Signal handling cancels the active request on SIGINT/SIGTERM.

Output is a table by default or --json for structured data with per-sample latency and nullable token counts. The API key is not included in the JSON. To compare backends, configure separate model aliases per backend and pass those alias names.

🔗 PRs: #12020

🔧 vllm-cpp LoRA fusion at load time

The lora_adapters and lora_scales config fields are standard LocalAI fields that list LoRA adapter weight files and per-adapter strength multipliers. The vllm-cpp video backend now consumes them for the first time, fusing LoRA deltas into DiT (diffusion Transformer) weights at engine load.

buildLoraExtras converts the config fields into indexed lora_path / lora_strength key-value pairs. The first adapter is unsuffixed; subsequent ones get _2, _3, etc. If the singular lora_adapter is set, it is prepended as the first adapter before the plural list. Relative adapter paths are joined to the model path; absolute paths pass through. Strength defaults to 1.0 when no scale is provided.

The pairs are packed via the ABI v18 extras seam and handed to vllmVideoEngineLoad. vllm.cpp's ResolveDitLoraSpecs fuses the LoRA deltas into the DiT weights at load. One generic path serves both LTX2.5 and MiniMax-H3, since the engine auto-detects the DiT family from the checkpoint.

Adapters are always loaded; there is no per-request activation in this path. Runtime prompt-activated LoRA (punica-style <lora:name:strength>) is out of scope and tracked separately.

🔗 PRs: #12082

🌍 Environment variables per model

An env: map on the model config injects variables into the backend process environment. The primary use case is pinning CUDA_VISIBLE_DEVICES per model to control GPU placement, but it applies to any backend that reads environment variables.

name: vllm-model
backend: vllm
env:
  CUDA_VISIBLE_DEVICES: "0,1"
  VLLM_CACHE_DIR: "/tmp/vllm_cache"

The map is delivered through the common process-spawning layer in pkg/model/process.go, so every gRPC backend inherits it with no per-backend wiring. Model vars are appended last, after the base env, so they override same-named inherited system vars. The UI renders an editable key/value map.

Model vars take effect only when a model spawns its own backend process, not when it reuses a worker-supervised one. There is no allowlist or blocklist: model configs are an operator trust boundary, consistent with LocalAI's general posture.

🔗 PRs: #10721

💬 template.system_messages_after_first

Agent frameworks legitimately append system instructions mid-conversation: a tool-parameter prompt before a call, an adjustment prompt after a result. The Qwen3.x family of tokenizer templates raises Jinja Exception: System message must be at the beginning for any system-role message after the first turn, returning HTTP 500. Plain chat looks healthy; every agent task fails.

template.system_messages_after_first controls what happens to system-role messages that appear after the contiguous leading system block:

  • "merge" folds late system messages into the first system message with a \n\n separator, dropping them from their original position.
  • "user" rewrites each late system message in place to role user, keeping its position and content.
  • unset (default) passes through unchanged; the tokenizer template decides.

The normalization runs in ChatEndpoint after stripEmptySystemMessages and before tokenizer-template system_prompt injection, so the Jinja template never sees an out-of-place system message. It only touches requests whose model config opts in, so default behavior is unchanged.

"user" is the recommended mode for agent workloads: the instruction stays where the framework placed it, and the model follows it.
