<!-- Release note générés à l'aide de la configuration dans .github/release.yml à v2.15.3 -->

[!AVERTISSEMENT] Changement radical : les webhooks vers les adresses internes sont bloqués par défaut

Le correctif pour GHSA-2phj-cp9f-qq6w bloque la livraison du webhook et de Slack vers des adresses privées, de bouclage, de lien local et autres adresses non publiques. Cela inclut les noms d'hôtes qui les résolvent, tels que *.svc.cluster.local. Après la mise à niveau, les webhooks existants vers les points de terminaison internes ne parviennent pas à être livrés et les nouveaux sont rejetés.

Pour les autoriser à nouveau, définissez la désinscription sur core et jobservice :

  • harbor.yml : network.allow_private_network_access: true, puis ./prepare et redémarrer
  • Helm : ajoutez {name: HARBOR_ALLOW_PRIVATE_NETWORK_ACCESS, value: "true"} à core.extraEnvVars et jobservice.extraEnvVars

Cela désactive complètement la protection. Utilisez-le uniquement si vous trust tous les administrateurs du projet et bloquez 169.254.169.254 au niveau du réseau.

[!AVERTISSEMENT] Modification révolutionnaire : la signature d'images non signées échoue lorsque le contenu trust est appliqué

Le correctif pour GHSA-wrw5-gmvj-gf23 supprime l'exemption basée sur l'agent utilisateur qui permettait à cosign et notation d'extraire des images non signées. Dans les projets qui autorisent uniquement les images signées, cosign sign et notation sign sur une nouvelle image non signée échouent désormais avec 412 Precondition Failed. Les images qui possèdent déjà une signature ne sont pas affectées.

Pour autoriser à nouveau la signature de clients, définissez CONTENT_TRUST_LEGACY_SIGNER_PULL_ENABLED=true sur core. La valeur doit être exactement true.

  • Helm : ajoutez-le à core.extraEnvVars
  • Installations harbor.yml : il n'y a pas d'option harbor.yml. Ajoutez-le à common/config/core/env et redémarrez. La réexécution de ./prepare écrase ce fichier.

L'exemption trust concerne toujours le User-Agent du client, mais uniquement pour les utilisateurs ou robots ayant une autorisation push sur le projet. Les projets qui bloquent les images vulnérables n'ont pas de droit de non-participation : un client signataire ne peut plus extraire une image bloquée par la politique de vulnérabilité.

[!AVERTISSEMENT] Problème connu : échec de la réplication push pour des registres spécifiques tels qu'AWS ECR (régression GHSA-wjpm-hv5w-gxr6)

Le correctif de sécurité pour GHSA-wjpm-hv5w-gxr6 a strictement validé les en-têtes d'emplacement de téléchargement par rapport au point de terminaison de registre configuré de manière statique (c.url). Étant donné que l'adaptateur AWS ECR configure le point de terminaison du plan de contrôle API (https://api.ecr.<region>.amazonaws.com) tandis que les demandes sont réécrites sur l'hôte du plan de données (<account>.dkr.ecr.<region>.amazonaws.com), l'en-tête Location de la réponse ECR est rejeté en tant que cible d'origine croisée.

Solution de contournement/résolution :

Un correctif a été fourni dans le PR #24113 et sera publié dans la prochaine version du correctif. Si votre environnement dépend de la réplication push, nous vous recommandons de reporter la mise à niveau jusqu'à la prochaine version du correctif ou d'appliquer le correctif directement.

<!-- Release notes generated using configuration in .github/release.yml at v2.15.3 -->

[!WARNING] Breaking change: webhooks to internal addresses are blocked by default

The fix for GHSA-2phj-cp9f-qq6w blocks webhook and Slack delivery to private, loopback, link-local and other non-public addresses. That includes hostnames that resolve to them, such as *.svc.cluster.local. After you upgrade, existing webhooks to internal endpoints fail to deliver, and new ones are rejected.

To allow them again, set the opt-out on both core and jobservice:

  • harbor.yml: network.allow_private_network_access: true, then ./prepare and restart
  • Helm: add {name: HARBOR_ALLOW_PRIVATE_NETWORK_ACCESS, value: "true"} to both core.extraEnvVars and jobservice.extraEnvVars

This disables the protection entirely. Only use it if you trust all project admins, and block 169.254.169.254 at the network level.

[!WARNING] Breaking change: signing unsigned images fails when content trust is enforced

The fix for GHSA-wrw5-gmvj-gf23 removes the User-Agent based exemption that let cosign and notation pull unsigned images. In projects that only allow signed images, cosign sign and notation sign on a new, unsigned image now fail with 412 Precondition Failed. Images that already have a signature are not affected.

To allow signing clients again, set CONTENT_TRUST_LEGACY_SIGNER_PULL_ENABLED=true on core. The value must be exactly true.

  • Helm: add it to core.extraEnvVars
  • harbor.yml installs: there is no harbor.yml option. Add it to common/config/core/env and restart. Re-running ./prepare overwrites that file.

The exemption still trusts the client's User-Agent, but only for users or robots with push permission on the project. Projects that block vulnerable images have no opt-out: a signing client can no longer pull an image that the vulnerability policy blocks.

[!WARNING] Known Issue: Push Replication Fails for Specific Registries such as AWS ECR (GHSA-wjpm-hv5w-gxr6 Regression)

The security fix for GHSA-wjpm-hv5w-gxr6 strictly validated upload Location headers against the statically configured registry endpoint (c.url). Because the AWS ECR adapter configures the API control-plane endpoint (https://api.ecr.<region>.amazonaws.com) while requests are rewritten to the data-plane host (<account>.dkr.ecr.<region>.amazonaws.com), ECR's response Location header is rejected as a cross-origin target.

Workaround / Resolution:

A fix has been provided in PR #24113 and will be released in the upcoming patch release. If your environment depends on push replication, we recommend postponing the upgrade until the next patch release or applying the patch directly.
