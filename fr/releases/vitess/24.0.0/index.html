<a id="major-changes"/>Modifications majeures</a>

<a id="new-support"/>Nouveau support</a>

<a id="window-function-pushdown"/>Déroulage des fonctions de fenêtre pour les espaces de clés partitionnés</a>

Cette version introduit une optimisation qui permet aux fonctions de fenêtre d'être transférées vers des partitions individuelles lorsqu'elles sont partitionnées par une colonne correspondant à un vindex unique. Auparavant, toutes les requêtes de fonction de fenêtre nécessitaient un routage sur une seule partition, ce qui limitait leur applicabilité sur les tables partitionnées. Avec ce changement, les requêtes dans lesquelles la clause PARTITION BY s'aligne sur un vindex unique peuvent désormais être repoussées et exécutées sur chaque partition. Pour des exemples et plus de détails, consultez la documentation.

<a id="view-routing-rules"/>Afficher les règles de routage</a>

Vitess prend désormais en charge les règles de routage pour les vues et peut être appliqué de la même manière que les tables avec vtctldclient ApplyRoutingRules. Lorsqu'une règle de routage de vues est active, VTGate réécrit les requêtes qui font référence à la vue source pour utiliser à la place la définition de la vue cible. Par exemple, étant donné cette règle de routage :

{
  "rules": [
    {
      "from_table": "source_ks.my_view",
      "to_tables": ["target_ks.my_view"]
    }
  ]
}

Et cette définition de vue :

CREATE VIEW target_ks.my_view AS SELECT id, name FROM user;

Une requête comme SELECT * FROM source_ks.my_view serait réécrite en interne comme :

SELECT * FROM (SELECT id, name FROM target_ks.user) AS my_view;

Les règles de routage des vues nécessitent que le suivi de schéma surveille les vues, ce qui signifie que VTGate doit être démarré avec l'indicateur --enable-views et VTTablet avec l'indicateur --queryserver-enable-views. La vue cible doit exister dans l'espace de clés spécifié pour que la règle de routage fonctionne correctement. Pour plus de détails, consultez la [documentation sur les règles de routage de schéma] (https://vitess.io/docs/24.0/reference/features/schema-routing-rules/).

<a id="tablet-targeting"/>Ciblage des tablettes via l'instruction USE</a>

VTGate prend désormais en charge le routage des requêtes vers une tablette spécifique par alias à l'aide d'une syntaxe d'instruction USE étendue :

USE keyspace:shard@tablet_type|tablet_alias;

Par exemple, pour cibler une réplique de tablette spécifique :

USE commerce:-80@replica|zone1-0000000100;

Une fois définies, toutes les requêtes suivantes de la session sont acheminées vers la tablette spécifiée jusqu'à ce qu'elles soient effacées par une instruction USE keyspace ou USE keyspace@tablet_type standard. Ceci est utile pour le débogage, la surveillance par tablette, le réchauffement du cache et d'autres tâches opérationnelles où le ciblage d'une tablette spécifique est requis. Remarque : Une partition doit être spécifiée lors de l'utilisation du ciblage sur tablette. Comme le ciblage de fragments, cela contourne le routage basé sur vindex, donc à utiliser avec précaution.

<a id="vtgate-binlog-dump"/>Prise en charge du streaming Binlog</a>

VTGate prend désormais en charge le streaming de journaux binaires basé sur GTID via deux protocoles :

  • Protocole MySQL : les utilisateurs Clients peuvent se connecter à l'aide de la commande standard du protocole de réplication MySQL COM_BINLOG_DUMP_GTID : aucun adaptateur spécial compatible VStream ni accès direct MySQL n'est requis.
  • gRPC : le nouveau RPC de streaming BinlogDumpGTID dans vtgateservice fournit un accès natif gRPC pour les clients personnalisés sans la dépendance du protocole MySQL. Remarque : Seul le streaming basé sur GTID est pris en charge. Le streaming basé sur un fichier/position n'est pas disponible via COM_BINLOG_DUMP ou COM_BINLOG_DUMP_GTID et renvoie une erreur. Cette fonctionnalité est désactivée par défaut. Activez-le avec --enable-binlog-dump. Nouveaux drapeaux :
  • --enable-binlog-dump : active la prise en charge du vidage du journal binaire. Sans cet indicateur, les demandes de vidage du journal binaire renvoient une erreur.
  • --binlog-dump-authorized-users : liste d'utilisateurs séparés par des virgules autorisés à exécuter des opérations de vidage de binlog, ou % pour autoriser tous les utilisateurs. Exigences : Lors du lancement d'une connexion de vidage de journal binaire, clients doit spécifier :
  • Un nom de fichier vide
  • Une position de fichier (filepos) de 4
  • Un poste GTID Pour gRPC clients, spécifiez l'espace de clés, la partition et éventuellement le type de tablette ou l'alias de tablette directement dans le BinlogDumpGTIDRequest. Limites :
  • Chaque flux fonctionne sur une seule tablette : aucune agrégation de données entre les partitions.
  • Pas de basculement automatique : si la tablette ciblée devient indisponible, le flux échoue et le client doit se reconnecter à une autre tablette.
  • Non compatible avec les opérations MoveTables ou Reshard. Utilisez le VStream API pour ces cas d'utilisation.

<a id="structured-logging"/>Journalisation structurée</a>

Vitess utilise désormais la journalisation structurée JSON par défaut. La sortie du journal est émise sous la forme JSON vers stderr. Pour configurer le niveau de journalisation minimum, transmettez --log-level (l'un des debug, info, warn, error ; info par défaut). Pour un format lisible par l’homme avec détection automatique des couleurs, passez --log-format=text. Pour revenir au backend glog précédent, transmettez --log-structured=false. glog est obsolète depuis la v24 et sera supprimé dans la v25.

<a id="breaking-changes"/>Modifications récentes</a>

<a id="vttablet-external-decompressor-manifest"/>Le décompresseur externe ne lit plus le MANIFEST de sauvegarde par défaut</a>

La commande de décompresseur externe stockée dans le fichier MANIFEST d'une sauvegarde n'est plus utilisée par défaut au moment de la restauration. Auparavant, lorsqu'aucun indicateur --external-decompressor n'était fourni, VTTablet revenait à la commande spécifiée dans MANIFEST. Cela présentait un risque de sécurité : un attaquant disposant d'un accès en écriture au stockage de sauvegarde pourrait modifier le MANIFEST pour exécuter des commandes arbitraires sur la tablette. À partir de la version 24, le décompresseur basé sur MANIFEST est ignoré, sauf si vous l'acceptez explicitement avec le nouvel indicateur --external-decompressor-use-manifest. Si vous comptez sur ce comportement, ajoutez l'indicateur à votre configuration VTTablet, mais soyez conscient des implications en matière de sécurité. Voir #19460 pour plus de détails.

<a id="minor-changes"/>Modifications mineures</a>

<a id="minor-changes-vreplication"/>VRéplication</a>

<a id="vreplication-shards-flag-start-stop"/>Drapeau --shards pour le démarrage et l'arrêt de MoveTables/Reshard</a>

Les commandes start et stop pour les workflows MoveTables et Reshard prennent désormais en charge l'indicateur --shards, permettant aux utilisateurs de démarrer ou d'arrêter des workflows sur un sous-ensemble spécifique de partitions plutôt que sur toutes les partitions à la fois. Exemple d'utilisation :

# Start workflow on specific shards only
vtctldclient MoveTables --target-keyspace customer --workflow commerce2customer start --shards="-80,80-"

# Stop workflow on specific shards only
vtctldclient Reshard --target-keyspace customer --workflow cust2cust stop --shards="80-"

<a id="vreplication-tablet-error-retry"/>Réessai automatique de la tablette en cas d'erreurs spécifiques à la tablette</a>

Les workflows VReplication réessayent désormais automatiquement avec différentes tablettes lorsqu'ils rencontrent des erreurs spécifiques à la tablette. Auparavant, les flux de travail sans préférence de cellule étaient par défaut basés sur la cellule locale et pouvaient rester bloqués indéfiniment en réessayant la même tablette défaillante. Lorsqu'une tablette rencontre des erreurs telles que la purge du journal binaire (erreur MySQL 1236 ou 1789) ou des incompatibilités d'ensembles GTID, VReplication ajoute cette tablette à une liste d'ignorés et essaie d'autres tablettes dans toutes les cellules. Une fois que toutes les tablettes correspondantes ont été essayées, la liste des éléments ignorés est effacée et le flux de travail recommence à zéro. Ceci est particulièrement utile dans les déploiements multicellulaires où une tablette dans la cellule locale peut ne pas disposer des journaux binaires requis, mais les tablettes dans d'autres cellules les ont toujours.

<a id="minor-changes-vtgate"/>VTGate</a>

<a id="vtgate-removed-grpc-send-session-in-streaming"/>indicateur --grpc-send-session-in-streaming supprimé</a>

Le drapeau VTGate --grpc-send-session-in-streaming a été supprimé. Cet indicateur était obsolète dans la v22 via #17907 et est par défaut true. La session est désormais toujours envoyée en tant que dernier paquet dans la réponse en streaming pour les RPC StreamExecute et StreamExecuteMulti. Ce comportement est requis pour prendre en charge les transactions en streaming et ne peut pas être désactivé. Impact : supprimez toute utilisation de l'indicateur --grpc-send-session-in-streaming des scripts de démarrage ou de la configuration de VTGate.

<a id="vtgate-new-default-legacy-replication-lag-algorithm"/>Nouvelle valeur par défaut pour l'indicateur --legacy-replication-lag-algorithm</a>

L'indicateur VTGate --legacy-replication-lag-algorithm est désormais par défaut false, désactivant l'approche héritée de gestion du décalage de réplication par défaut. Au lieu de cela, un algorithme plus simple basé uniquement sur un faible décalage, un décalage élevé et un nombre minimum de tablettes est utilisé, qui s'est avéré plus stable dans de nombreux environnements de production. Une explication détaillée des deux approches [est expliquée dans ce commentaire de code] (https://github.com/vitessio/vitess/blob/main/go/vt/discovery/replicationlag.go#L125-L149). Dans la version 25, cet indicateur deviendra obsolète et dans la version suivante, il sera supprimé. En attendant, le comportement hérité peut être utilisé en définissant --legacy-replication-lag-algorithm=true. Cette dépréciation est suivie dans https://github.com/vitessio/vitess/issues/18914.

<a id="vtgate-session-balancer-mode"/>Nouveau mode "session" pour le flag --vtgate-balancer-mode</a>

Le drapeau VTGate --vtgate-balancer-mode prend désormais en charge un nouveau mode « session » en plus des modes « cellule », « préférence-cellule » et « aléatoire » existants. Le mode Session achemine chaque session de manière cohérente vers la même tablette pendant toute la durée de la session. Pour activer le mode session, définissez le drapeau au démarrage de VTGate :

--vtgate-balancer-mode=session

<a id="minor-changes-query-serving"/>Servage des requêtes</a>

<a id="query-serving-json-extract-dynamic-args"/>JSON_EXTRACT prend désormais en charge les arguments de chemin dynamique</a>

La fonction JSON_EXTRACT prend désormais en charge les arguments de chemin dynamique tels que les variables de liaison ou les résultats d'autres appels de fonction. Auparavant, JSON_EXTRACT fonctionnait uniquement avec des chaînes littérales statiques pour les arguments de chemin. La gestion NULL correspond désormais au comportement de MySQL. La fonction renvoie NULL lorsque l'argument du document ou du chemin est NULL. Les arguments de chemin statique sont toujours optimisés, même lorsqu'ils sont mélangés à des arguments dynamiques, de sorte que les requêtes existantes ne subiront aucune régression des performances.

<a id="minor-changes-vttablet"/>VTTablet</a>

<a id="vttablet-init-tablet-type-lookup"/>Nouveau indicateur expérimental --init-tablet-type-lookup</a>

Le nouvel indicateur expérimental --init-tablet-type-lookup pour VTTablet permet aux tablettes de restaurer automatiquement leur type de tablette précédent au redémarrage en recherchant l'enregistrement de topologie existant, plutôt que de toujours utiliser la valeur statique --init-tablet-type. Lorsqu'elle est activée, la tablette utilise son alias pour rechercher le type de tablette dans l'enregistrement de topologie existant au redémarrage. Cela permet aux tablettes de conserver leurs rôles modifiés (par exemple, RDONLY/DRAINED) lors des redémarrages sans reconfiguration manuelle. Si elle est désactivée ou si aucun enregistrement de topologie n'existe, la valeur standard --init-tablet-type sera utilisée à la place. Remarque : Les déploiements gérés par l'opérateur Vitess ne conservent généralement pas les enregistrements de tablette correspondants dans le topo lors des remplacements de pods, cette fonctionnalité aura donc un effet plus limité dans ces environnements.

<a id="vttablet-querythrottler-metrics"/>Mesures d'observabilité de QueryThrottler</a>

VTTablet expose désormais de nouvelles métriques pour suivre le comportement de QueryThrottler. Quatre nouvelles métriques ont été ajoutées :

  • QueryThrottlerRequests : nombre total de requêtes évaluées par le régulateur de requêtes
  • QueryThrottlerThrottled : nombre de requêtes limitées
  • QueryThrottlerTotalLatencyNs : temps total nécessaire à chaque requête pour la limitation des requêtes, y compris l'évaluation, les vérifications de métriques et autres frais généraux (en nanosecondes)
  • QueryThrottlerEvaluateLatencyNs : temps nécessaire pour prendre la décision de limitation (en nanosecondes) Toutes les métriques incluent des étiquettes pour Strategy, Workload et Priority. La métrique QueryThrottlerThrottled comporte des étiquettes supplémentaires pour MetricName, MetricValue et DryRun afin d'identifier quelle métrique a déclenché la limitation et si elle s'est produite en mode d'exécution à sec. Ces métriques permettent de surveiller les modèles de limitation, d'identifier les charges de travail qui sont limitées, de mesurer la surcharge de performances et de valider le comportement en mode d'exécution à sec avant les modifications de configuration.

<a id="vttablet-querythrottler-config-watch"/>Mises à jour de la configuration basée sur les événements de QueryThrottler</a>

La configuration de QueryThrottler est désormais propagée et stockée dans l'enregistrement SrvKeyspace au sein du serveur de topologie et gérée à l'aide d'outils de topologie standard. Auparavant, les tablettes recherchaient les modifications de configuration toutes les 60 secondes. Les tablettes utilisent désormais des surveillances basées sur les événements (WatchSrvKeyspace) pour recevoir des mises à jour immédiatement lorsque la configuration de limitation des requêtes change. Toutes les tablettes d'un espace de clés voient les modifications de configuration à peu près au même moment, et les modifications du serveur de topologie sont versionnées et vérifiables. Cette modification remplace l'ancien chargeur de configuration basé sur des fichiers par une structure de configuration définie par protobuf et stockée dans la topologie. La nouvelle configuration comprend des champs pour activer/désactiver la limitation, sélectionner la stratégie de limitation et configurer des règles spécifiques à la stratégie.

<a id="vttablet-conn-pool-waiter-cap"/>Casquette de serveur de pool de connexion pour tablette</a>

VTTablet permet désormais aux utilisateurs de définir une limite sur le nombre de requêtes en attente d'obtention d'une connexion depuis le pool de connexions, par exemple les pools de connexions de requêtes, de flux et de transactions. Les limites sont définies avec les indicateurs suivants : *--queryserver-config-query-pool-waiter-cap *--queryserver-config-stream-pool-waiter-cap *--queryserver-config-txpool-waiter-cap Tous les éléments ci-dessus ont une valeur par défaut de 0, ce qui signifie aucune limite, préservant ainsi le comportement de la version précédente.

<a id="minor-changes-tracing"/>Traçage</a>

<a id="tracing-opentelemetry"/>Prise en charge du traçage OpenTelemetry</a>

Vitess prend désormais en charge OpenTelemetry comme backend de traçage. Pour l'utiliser, définissez --tracer opentelemetry sur n'importe quel binaire Vitess. Les traces sont exportées via OTLP/gRPC, configurable avec les indicateurs suivants :

  • --otel-endpoint : point final du collecteur OpenTelemetry. Si elle est vide, la variable d'environnement OTEL_EXPORTER_OTLP_ENDPOINT est utilisée ; si cela n'est pas non plus défini, l'OTel SDK est par défaut localhost:4317.
  • --otel-insecure (false par défaut) : utiliser une connexion non sécurisée au collecteur.
  • --tracing-sampling-rate (0.1 par défaut) : taux d'échantillonnage pour les traces (partagé entre tous les backends de traçage). Tout backend compatible OTLP (Jaeger v1.35+, Grafana Tempo, Datadog Agent, etc.) peut recevoir ces traces.

<a id="tracing-opentracing-deprecation"/>Obsolescence des backends de traçage basés sur OpenTracing</a>

Les backends de traçage suivants sont obsolètes à partir de la version 24 et seront supprimés dans la version 25 :

  • opentracing-jaeger — Utilise la bibliothèque Jaeger client-go, qui a été archivée. Le projet Jaeger recommande de migrer vers OpenTelemetry. Les utilisateurs doivent migrer vers --tracer opentelemetry avec un point de terminaison Jaeger compatible OTLP (v1.35+).
  • opentracing-datadog — Utilise le pont OpenTracing dans dd-trace-go. Les utilisateurs doivent migrer vers --tracer opentelemetry avec le point de terminaison d’ingestion OTLP de l’agent Datadog. Les options --tracer opentracing-jaeger et --tracer opentracing-datadog continuent de fonctionner dans la version 24 mais enregistreront un avertissement de dépréciation au démarrage. Les indicateurs spécifiques à Jaeger suivants sont également obsolètes et seront supprimés dans la v25 : ---jaeger-agent-host ---tracing-sampling-type Migration : remplacez --tracer opentracing-jaeger par --tracer opentelemetry et --jaeger-agent-host host:port par --otel-endpoint host:4317. Assurez-vous que votre déploiement Jaeger accepte OTLP (Jaeger v1.35+ écoute sur le port 4317 par défaut).

<a id="minor-changes-vtorc"/>VTORc</a>

<a id="vtorc-cell-flag"/>Nouveau drapeau --cell</a>

VTOrc prend désormais en charge un indicateur --cell qui spécifie dans quelle cellule Vitess le processus VTOrc s'exécute. L'indicateur est facultatif dans la v24 mais sera requis dans la v25+, similaire à l'indicateur --cell de VTGate. Lorsqu'il est fourni, VTOrc valide que la cellule existe dans le service de topologie au démarrage. Sans l'indicateur, VTOrc enregistre un avertissement concernant l'exigence d'indicateur v25+. Cela permet une future validation des problèmes entre cellules, où VTOrc pourra demander à une autre cellule de valider les problèmes détectés avant de prendre des mesures de récupération. L'indicateur est actuellement validé mais n'est pas encore utilisé dans la logique de récupération VTOrc. Remarque : Si vous exécutez VTOrc dans un déploiement multicellulaire, commencez dès maintenant à utiliser l'indicateur --cell pour vous préparer à l'exigence v25.

<a id="vtorc-ordered-recovery-semi-sync"/>Exécution de récupération ordonnée et déploiement de semi-synchronisation</a>

VTOrc exécute désormais les récupérations par fragment avec un ordre défini, plutôt que par tablette de manière isolée. Les problèmes qui ont des dépendances d'ordre (par exemple, une configuration semi-synchronisée) sont d'abord exécutés en série, tandis que les problèmes indépendants sont exécutés simultanément. Cela garantit que les récupérations dépendantes se produisent dans le bon ordre au sein d’une partition. La principale amélioration destinée aux utilisateurs concerne les déploiements semi-synchronisés : VTOrc garantit désormais que la semi-synchronisation est activée sur les réplicas avant de mettre à jour le principal. Auparavant, l'activation de la semi-synchronisation sur le serveur principal avant qu'un nombre suffisant de réplicas ne soient prêts pouvait bloquer les écritures pendant que le serveur principal attendait des accusés de réception semi-synchronisés qu'aucun réplica n'était prêt à envoyer. Voir #19427 pour plus de détails.

<a id="vtorc-deprecated-metric-removed"/>Métrique VTOrc obsolète supprimée</a>

La métrique DiscoverInstanceTimings a été supprimée de VTORc dans la v24. Cette métrique est obsolète dans la version v23. Migration : utilisez plutôt DiscoveryInstanceTimings, qui fournit les mêmes informations de synchronisation pour les actions de découverte d'instance (Backend, Instance, Autre). Impact : Les tableaux de bord de surveillance ou les systèmes d'alerte utilisant DiscoverInstanceTimings doivent être mis à jour pour utiliser DiscoveryInstanceTimings.

<a id="vtorc-snapshot-topology-deprecation"/>Obsolescence de la fonctionnalité Snapshot Topology</a>

La fonctionnalité Snapshot Topology de VTORc, qui est activée en définissant --snapshot-topology-interval sur une valeur non nulle, est obsolète à partir de la v24 et la logique est prévue pour être supprimée dans la v25. Le manque de fonctionnalités pour lire les instantanés créés par cette fonctionnalité, associé à la nature en mémoire du backend de VTOrc, signifie que cette logique a une utilité limitée. Cette dépréciation est expliquée et suivie en détail dans https://github.com/vitessio/vitess/issues/18691. Migration : supprimez le flag VTOrc --snapshot-topology-interval avant la v25. Impact : VTOrc ne peut plus créer d'instantanés de la topologie dans sa base de données principale.

<a id="vtorc-replication-analysis-api-removed"/>Point de terminaison /api/replication-analysis obsolète supprimé</a>

Le point de terminaison /api/replication-analysis a été supprimé de VTORc dans la version 24. Utilisez plutôt le /api/detection-analysis, qui offre les mêmes fonctionnalités. Migration : mettez à jour tous les scripts, systèmes de surveillance ou automatisations qui appellent /api/replication-analysis pour utiliser /api/detection-analysis à la place. Le point de terminaison de remplacement accepte les mêmes paramètres de requête (keyspace, shard) et renvoie le même format de réponse JSON. Impact : les requêtes HTTP adressées à /api/replication-analysis renverront une erreur 404 Not Found.

<a id="minor-changes-metrics"/>Métriques</a>

<a id="metrics-extended-go-runtime"/>Métriques d'exécution Go étendues via Prometheus</a>

Vitess expose désormais l'ensemble complet des métriques d'exécution Go via Prometheus. Le Prometheus GoCollector par défaut n'expose que trois runtime/metrics (/gc/gogc:percent, /gc/gomemlimit:bytes, /sched/gomaxprocs:threads) plus l'ancien ensemble go_memstats_*. À partir de la v24, tous les composants Vitess exposent environ 150 métriques supplémentaires du package runtime/metrics de Go. Les nouvelles statistiques incluent :

  • Histogrammes d'allocation de tas
  • Comptages de cycles GC et histogrammes de pause
  • Pannes de classe de mémoire
  • Pannes d'état Goroutine
  • Histogrammes de latence du planificateur
  • Répartitions du temps CPU par classe (utilisateur, GC, récupération, inactif) Une nouvelle jauge go_info_ext est également ajoutée avec les étiquettes compiler, GOARCH et GOOS, fournissant des informations étendues sur l'environnement de construction au-delà de la métrique standard go_info. Composants concernés : vtgate, vttablet, vtctld, vtorc, vtbackup, mysqlctld Aucune configuration requise — les métriques apparaissent automatiquement sur le point de terminaison /metrics pour tous les composants utilisant le backend Prometheus.

<a id="minor-changes-backup-restore"/>Sauvegarde et restauration</a>

<a id="mysql-clone-support"/>Prise en charge de MySQL CLONE pour le provisionnement de réplicas</a>

VTTablet et VTBackup prennent désormais en charge l'utilisation du [plug-in CLONE] natif de MySQL (https://dev.mysql.com/doc/refman/en/clone-plugin.html) pour provisionner de nouvelles répliques en copiant les données directement à partir d'une tablette donatrice sur le réseau. La copie de données au niveau physique est nettement plus rapide que la sauvegarde et la restauration logiques, en particulier pour les grands ensembles de données. Nécessite les tables MySQL 8.0.17+ et InnoDB uniquement. Nouveaux drapeaux : | Drapeau | Descriptif | |------|-------------| | --mysql-clone-enabled | Activez le plugin MySQL CLONE et créez l'utilisateur clone lors de l'initialisation de MySQL. Obligatoire pour toutes les tablettes qui participeront aux opérations CLONE. | | --clone-from-primary | Clonez les données de la tablette principale du fragment au lieu de restaurer à partir d'une sauvegarde. Mutuellement exclusif avec --clone-from-tablet. | | --clone-from-tablet | Clonez les données d'une tablette spécifique par alias (par exemple, zone1-123) au lieu de restaurer à partir d'une sauvegarde. Mutuellement exclusif avec --clone-from-primary. | | --restore-with-clone | Utilisez MySQL CLONE pour la phase de restauration au lieu de restaurer à partir d'une sauvegarde. Nécessite soit --clone-from-primary, soit --clone-from-tablet. | | --clone-restart-wait-timeout | Délai d'attente pour le redémarrage du MySQL une fois CLONE REMOTE terminé. Par défaut : 5 minutes. | Cloner la configuration utilisateur : | Drapeau | Descriptif | |------|-------------| | --db-clone-user | Nom d'utilisateur MySQL pour les opérations CLONE (authentification du donateur). | | --db-clone-password | Mot de passe de l'utilisateur CLONE. | | --db-clone-use-ssl | Utilisez SSL lors de la connexion au donateur pour les opérations CLONE. | Exemple d'utilisation : Cloner à partir du fragment principal du fragment :

vttablet \
  --mysql-clone-enabled \
  --restore-with-clone \
  --clone-from-primary \
  ...

Cloner depuis une tablette spécifique :

vtbackup \
  --mysql-clone-enabled \
  --restore-with-clone \
  --clone-from-tablet=zone1-0000000100 \
  ...

Remarque : Toutes les tablettes participant aux opérations CLONE (donneurs et receveurs) doivent avoir --mysql-clone-enabled défini lors de l'initialisation de MySQL pour garantir que le plug-in CLONE est chargé et que l'utilisateur clone existe.

<a id="restore-hook-backup-engine-env"/>Améliorations de la restauration du Hook</a>

Couverture étendue du hook : le hook vttablet_restore_done se déclenche désormais lorsque les restaurations sont déclenchées via vtctldclient RestoreFromBackup. Auparavant, ce hook ne s'exécutait que lors des opérations de démarrage ou de clonage de la tablette. Nouvelle variable d'environnement : le hook définit désormais TM_RESTORE_DATA_BACKUP_ENGINE pour indiquer quel moteur de sauvegarde a été utilisé. La valeur provient du champ BackupMethod du manifeste de sauvegarde. TM_RESTORE_DATA_BACKUP_ENGINE n'est défini que lorsqu'une restauration lit à partir d'une sauvegarde réelle, pas pour les restaurations basées sur le clonage ou lorsqu'aucune sauvegarde n'est utilisée. Les scripts Hook peuvent l'utiliser pour effectuer des actions spécifiques au moteur selon que la restauration a utilisé builtin, xtrabackup ou un autre moteur.

<a id="major-changes"/>Major Changes</a>

<a id="new-support"/>New Support</a>

<a id="window-function-pushdown"/>Window function pushdown for sharded keyspaces</a>

This release introduces an optimization that allows window functions to be pushed down to individual shards when they are partitioned by a column that matches a unique vindex.

Previously, all window function queries required single-shard routing, which limited their applicability on sharded tables. With this change, queries where the PARTITION BY clause aligns with a unique vindex can now be pushed down and executed on each shard.

For examples and more details, see the documentation.

<a id="view-routing-rules"/>View Routing Rules</a>

Vitess now supports routing rules for views, and can be applied the same as tables with vtctldclient ApplyRoutingRules. When a view routing rule is active, VTGate rewrites queries that reference the source view to use the target view's definition instead. For example, given this routing rule:

{
  "rules": [
    {
      "from_table": "source_ks.my_view",
      "to_tables": ["target_ks.my_view"]
    }
  ]
}

And this view definition:

CREATE VIEW target_ks.my_view AS SELECT id, name FROM user;

A query like SELECT * FROM source_ks.my_view would be internally rewritten to:

SELECT * FROM (SELECT id, name FROM target_ks.user) AS my_view;

View routing rules require the schema tracker to monitor views, which means VTGate must be started with the --enable-views flag and VTTablet with the --queryserver-enable-views flag. The target view must exist in the specified keyspace for the routing rule to function correctly. For more details, see the Schema Routing Rules documentation.

<a id="tablet-targeting"/>Tablet targeting via USE statement</a>

VTGate now supports routing queries to a specific tablet by alias using an extended USE statement syntax:

USE keyspace:shard@tablet_type|tablet_alias;

For example, to target a specific replica tablet:

USE commerce:-80@replica|zone1-0000000100;

Once set, all subsequent queries in the session route to the specified tablet until cleared with a standard USE keyspace or USE keyspace@tablet_type statement. This is useful for debugging, per-tablet monitoring, cache warming, and other operational tasks where targeting a specific tablet is required.

Note: A shard must be specified when using tablet targeting. Like shard targeting, this bypasses vindex-based routing, so use with care.

<a id="vtgate-binlog-dump"/>Binlog Streaming Support</a>

VTGate now supports GTID-based binlog streaming through two protocols:

  • MySQL protocol: Clients can connect using the standard MySQL COM_BINLOG_DUMP_GTID replication protocol command—no special VStream-aware adapters or direct MySQL access required.
  • gRPC: The new BinlogDumpGTID streaming RPC in vtgateservice provides native gRPC access for custom clients without the MySQL protocol dependency.

Note: Only GTID-based streaming is supported. File/position-based streaming is not available through either COM_BINLOG_DUMP or COM_BINLOG_DUMP_GTID and returns an error.

This feature is disabled by default. Enable it with --enable-binlog-dump.

New flags:

  • --enable-binlog-dump: Enables binlog dump support. Without this flag, binlog dump requests return an error.
  • --binlog-dump-authorized-users: Comma-separated list of users authorized to execute binlog dump operations, or % to allow all users.

Requirements:

When initiating a binlog dump connection, clients must specify:

  • An empty filename
  • A file position (filepos) of 4
  • A GTID position

For gRPC clients, specify the keyspace, shard, and optionally the tablet type or tablet alias directly in the BinlogDumpGTIDRequest.

Limitations:

  • Each stream operates on a single tablet—no data aggregation across shards.
  • No automatic failover—if the targeted tablet becomes unavailable, the stream fails and the client must reconnect to a different tablet.
  • Not compatible with MoveTables or Reshard operations. Use the VStream API for those use cases.

<a id="structured-logging"/>Structured logging</a>

Vitess now uses structured JSON logging by default. Log output is emitted as JSON to stderr. To configure the minimum log level, pass --log-level (one of debug, info, warn, error; default info). For a human-readable format with automatic color detection, pass --log-format=text. To revert to the previous glog backend, pass --log-structured=false.

glog is deprecated as of v24 and will be removed in v25.

<a id="breaking-changes"/>Breaking Changes</a>

<a id="vttablet-external-decompressor-manifest"/>External Decompressor No Longer Read from Backup MANIFEST by Default</a>

The external decompressor command stored in a backup's MANIFEST file is no longer used at restore time by default. Previously, when no --external-decompressor flag was provided, VTTablet would fall back to the command specified in the MANIFEST. This posed a security risk: an attacker with write access to backup storage could modify the MANIFEST to execute arbitrary commands on the tablet.

Starting in v24, the MANIFEST-based decompressor is ignored unless you explicitly opt in with the new --external-decompressor-use-manifest flag. If you rely on this behavior, add the flag to your VTTablet configuration, but be aware of the security implications.

See #19460 for details.

<a id="minor-changes"/>Minor Changes</a>

<a id="minor-changes-vreplication"/>VReplication</a>

<a id="vreplication-shards-flag-start-stop"/>--shards flag for MoveTables/Reshard start and stop</a>

The start and stop commands for MoveTables and Reshard workflows now support the --shards flag, allowing users to start or stop workflows on a specific subset of shards rather than all shards at once.

Example usage:

# Start workflow on specific shards only
vtctldclient MoveTables --target-keyspace customer --workflow commerce2customer start --shards="-80,80-"

# Stop workflow on specific shards only
vtctldclient Reshard --target-keyspace customer --workflow cust2cust stop --shards="80-"

<a id="vreplication-tablet-error-retry"/>Automatic tablet retry for tablet-specific errors</a>

VReplication workflows now automatically retry with different tablets when encountering tablet-specific errors. Previously, workflows without a cell preference would default to the local cell and could get stuck retrying the same failing tablet indefinitely.

When a tablet encounters errors like binary log purging (MySQL error 1236 or 1789) or GTID set mismatches, VReplication adds that tablet to an ignore list and tries other tablets across all cells. Once all matching tablets have been tried, the ignore list is cleared and the workflow retries from scratch.

This is particularly useful in multi-cell deployments where a tablet in the local cell may lack the required binary logs, but tablets in other cells still have them.

<a id="minor-changes-vtgate"/>VTGate</a>

<a id="vtgate-removed-grpc-send-session-in-streaming"/>Removed --grpc-send-session-in-streaming flag</a>

The VTGate flag --grpc-send-session-in-streaming has been removed. This flag was deprecated in v22 via #17907 and defaulted to true.

The session is now always sent as the last packet in the streaming response for StreamExecute and StreamExecuteMulti RPCs. This behavior is required to support transactions in streaming and cannot be disabled.

Impact: Remove any usage of the --grpc-send-session-in-streaming flag from VTGate startup scripts or configuration.

<a id="vtgate-new-default-legacy-replication-lag-algorithm"/>New default for --legacy-replication-lag-algorithm flag</a>

The VTGate flag --legacy-replication-lag-algorithm now defaults to false, disabling the legacy approach to handling replication lag by default.

Instead, a simpler algorithm purely based on low lag, high lag and minimum number of tablets is used, which has proven to be more stable in many production environments. A detailed explanation of the two approaches is explained in this code comment.

In v25 this flag will become deprecated and in the following release it will be removed. In the meantime, the legacy behaviour can be used by setting --legacy-replication-lag-algorithm=true. This deprecation is tracked in https://github.com/vitessio/vitess/issues/18914.

<a id="vtgate-session-balancer-mode"/>New "session" mode for --vtgate-balancer-mode flag</a>

The VTGate flag --vtgate-balancer-mode now supports a new "session" mode in addition to the existing "cell", "prefer-cell", and "random" modes. Session mode routes each session consistently to the same tablet for the session's duration.

To enable session mode, set the flag when starting VTGate:

--vtgate-balancer-mode=session

<a id="minor-changes-query-serving"/>Query Serving</a>

<a id="query-serving-json-extract-dynamic-args"/>JSON_EXTRACT now supports dynamic path arguments</a>

The JSON_EXTRACT function now supports dynamic path arguments like bind variables or results from other function calls. Previously, JSON_EXTRACT only worked with static string literals for path arguments.

NULL handling now matches MySQL behavior. The function returns NULL when either the document or path argument is NULL.

Static path arguments are still optimized, even when mixed with dynamic arguments, so existing queries won't see any performance regression.

<a id="minor-changes-vttablet"/>VTTablet</a>

<a id="vttablet-init-tablet-type-lookup"/>New Experimental flag --init-tablet-type-lookup</a>

The new experimental flag --init-tablet-type-lookup for VTTablet allows tablets to automatically restore their previous tablet type on restart by looking up the existing topology record, rather than always using the static --init-tablet-type value.

When enabled, the tablet uses its alias to look up the tablet type from the existing topology record on restart. This allows tablets to maintain their changed roles (e.g., RDONLY/DRAINED) across restarts without manual reconfiguration. If disabled or if no topology record exists, the standard --init-tablet-type value will be used instead.

Note: Vitess Operator–managed deployments generally do not keep matching tablet records in the topo across pod replacements, so this feature will have a more limited effect in those environments.

<a id="vttablet-querythrottler-metrics"/>QueryThrottler Observability Metrics</a>

VTTablet now exposes new metrics to track QueryThrottler behavior.

Four new metrics have been added:

  • QueryThrottlerRequests: Total number of requests evaluated by the query throttler
  • QueryThrottlerThrottled: Number of requests that were throttled
  • QueryThrottlerTotalLatencyNs: Total time each request takes in query throttling, including evaluation, metric checks, and other overhead (in nanoseconds)
  • QueryThrottlerEvaluateLatencyNs: Time taken to make the throttling decision (in nanoseconds)

All metrics include labels for Strategy, Workload, and Priority. The QueryThrottlerThrottled metric has additional labels for MetricName, MetricValue, and DryRun to identify which metric triggered the throttling and whether it occurred in dry-run mode.

These metrics help monitor throttling patterns, identify which workloads are throttled, measure performance overhead, and validate behavior in dry-run mode before configuration changes.

<a id="vttablet-querythrottler-config-watch"/>QueryThrottler Event-Driven Configuration Updates</a>

QueryThrottler configuration is now propagated to and stored in the SrvKeyspace record within the topology server and managed using standard topology tools. Previously, tablets polled for configuration changes every 60 seconds. Tablets now use event-driven watches (WatchSrvKeyspace) to receive updates immediately when the query throttling configuration changes. All tablets in a keyspace see configuration changes at roughly the same time, and topology server changes are versioned and auditable.

This change replaces the previous file-based configuration loader with a protobuf-defined configuration structure stored in the topology. The new configuration includes fields for enabling/disabling throttling, selecting the throttling strategy, and configuring strategy-specific rules.

<a id="vttablet-conn-pool-waiter-cap"/>Tablet Connection Pool Waiter Cap</a>

VTTablet now allows users to set a limit on the number of requests waiting to get a connection from the connection pool, for the query, stream, and transaction connection pools. The limits are set with the following flags:

  • --queryserver-config-query-pool-waiter-cap
  • --queryserver-config-stream-pool-waiter-cap
  • --queryserver-config-txpool-waiter-cap

All of the above have a default value of 0, meaning no limit, thus preserving the behavior of the previous version.

<a id="minor-changes-tracing"/>Tracing</a>

<a id="tracing-opentelemetry"/>OpenTelemetry tracing support</a>

Vitess now supports OpenTelemetry as a tracing backend. To use it, set --tracer opentelemetry on any Vitess binary. Traces are exported via OTLP/gRPC, configurable with the following flags:

  • --otel-endpoint: OpenTelemetry collector endpoint. If empty, the OTEL_EXPORTER_OTLP_ENDPOINT env var is used; if that is also unset, the OTel SDK defaults to localhost:4317.
  • --otel-insecure (default false): use insecure connection to the collector.
  • --tracing-sampling-rate (default 0.1): sampling rate for traces (shared across all tracing backends).

Any OTLP-compatible backend (Jaeger v1.35+, Grafana Tempo, Datadog Agent, etc.) can receive these traces.

<a id="tracing-opentracing-deprecation"/>Deprecation of OpenTracing-based tracing backends</a>

The following tracing backends are deprecated as of v24 and will be removed in v25:

  • opentracing-jaeger — Uses the Jaeger client-go library, which has been archived. The Jaeger project recommends migrating to OpenTelemetry. Users should migrate to --tracer opentelemetry with an OTLP-compatible Jaeger endpoint (v1.35+).
  • opentracing-datadog — Uses the OpenTracing bridge in dd-trace-go. Users should migrate to --tracer opentelemetry with the Datadog Agent's OTLP ingestion endpoint.

The --tracer opentracing-jaeger and --tracer opentracing-datadog options continue to work in v24 but will log a deprecation warning at startup. The following Jaeger-specific flags are also deprecated and will be removed in v25:

  • --jaeger-agent-host
  • --tracing-sampling-type

Migration: Replace --tracer opentracing-jaeger with --tracer opentelemetry and --jaeger-agent-host host:port with --otel-endpoint host:4317. Ensure your Jaeger deployment accepts OTLP (Jaeger v1.35+ listens on port 4317 by default).

<a id="minor-changes-vtorc"/>VTOrc</a>

<a id="vtorc-cell-flag"/>New --cell Flag</a>

VTOrc now supports a --cell flag that specifies which Vitess cell the VTOrc process is running in. The flag is optional in v24 but will be required in v25+, similar to VTGate's --cell flag.

When provided, VTOrc validates that the cell exists in the topology service on startup. Without the flag, VTOrc logs a warning about the v25+ flag requirement.

This enables future cross-cell problem validation, where VTOrc will be able to ask another cell to validate detected problems before taking recovery actions. The flag is currently validated but not yet used in VTOrc recovery logic.

Note: If you're running VTOrc in a multi-cell deployment, start using the --cell flag now to prepare for the v25 requirement.

<a id="vtorc-ordered-recovery-semi-sync"/>Ordered Recovery Execution and Semi-Sync Rollout</a>

VTOrc now executes recoveries per-shard with a defined ordering, rather than per-tablet in isolation. Problems that have ordering dependencies (e.g., semi-sync configuration) are executed serially first, while independent problems are executed concurrently. This ensures that dependent recoveries happen in the correct sequence within a shard.

The main user-facing improvement is for semi-sync rollouts: VTOrc now ensures replicas have semi-sync enabled before updating the primary. Previously, enabling semi-sync on the primary before enough replicas were ready could stall writes while the primary waited for semi-sync acknowledgements that no replica was prepared to send.

See #19427 for details.

<a id="vtorc-deprecated-metric-removed"/>Deprecated VTOrc Metric Removed</a>

The DiscoverInstanceTimings metric has been removed from VTOrc in v24. This metric was deprecated in v23.

Migration: Use DiscoveryInstanceTimings instead, which provides the same timing information for instance discovery actions (Backend, Instance, Other).

Impact: Monitoring dashboards or alerting systems using DiscoverInstanceTimings must be updated to use DiscoveryInstanceTimings.

<a id="vtorc-snapshot-topology-deprecation"/>Deprecation of Snapshot Topology feature</a>

VTOrc's Snapshot Topology feature, which is enabled by setting --snapshot-topology-interval to a non-zero-value is deprecated as of v24 and the logic is planned for removal in v25.

The lack of facilities to read the snapshots created by this feature coupled with the in-memory nature of VTOrc's backend means this logic has limited usefulness. This deprecation is explained and tracked in detail in https://github.com/vitessio/vitess/issues/18691.

Migration: remove the VTOrc flag --snapshot-topology-interval before v25.

Impact: VTOrc can no longer create snapshots of the topology in it's backend database.

<a id="vtorc-replication-analysis-api-removed"/>Deprecated /api/replication-analysis Endpoint Removed</a>

The /api/replication-analysis endpoint has been removed from VTOrc in v24. Use /api/detection-analysis instead, which provides the same functionality.

Migration: Update any scripts, monitoring systems, or automation that calls /api/replication-analysis to use /api/detection-analysis instead. The replacement endpoint accepts the same query parameters (keyspace, shard) and returns the same JSON response format.

Impact: HTTP requests to /api/replication-analysis will return a 404 Not Found error.

<a id="minor-changes-metrics"/>Metrics</a>

<a id="metrics-extended-go-runtime"/>Extended Go Runtime Metrics via Prometheus</a>

Vitess now exposes the full set of Go runtime metrics via Prometheus. The default Prometheus GoCollector only exposes three runtime/metrics (/gc/gogc:percent, /gc/gomemlimit:bytes, /sched/gomaxprocs:threads) plus the legacy go_memstats_* set. Starting in v24, all Vitess components expose approximately 150 additional metrics from Go's runtime/metrics package.

New metrics include:

  • Heap allocation histograms
  • GC cycle counts and pause histograms
  • Memory class breakdowns
  • Goroutine state breakdowns
  • Scheduler latency histograms
  • CPU time breakdowns by class (user, GC, scavenge, idle)

A new go_info_ext gauge is also added with compiler, GOARCH, and GOOS labels, providing extended build environment information beyond the standard go_info metric.

Affected components: vtgate, vttablet, vtctld, vtorc, vtbackup, mysqlctld

No configuration required — the metrics appear automatically on the /metrics endpoint for all components using the Prometheus backend.

<a id="minor-changes-backup-restore"/>Backup and Restore</a>

<a id="mysql-clone-support"/>MySQL CLONE Support for Replica Provisioning</a>

VTTablet and VTBackup now support using MySQL's native CLONE plugin to provision new replicas by copying data directly from a donor tablet over the network. Physical-level data copying is significantly faster than logical backup and restore, especially for large datasets. Requires MySQL 8.0.17+ and InnoDB-only tables.

New Flags:

| Flag | Description | |------|-------------| | --mysql-clone-enabled | Enable the MySQL CLONE plugin and create the clone user during MySQL initialization. Required for all tablets that will participate in CLONE operations. | | --clone-from-primary | Clone data from the shard's primary tablet instead of restoring from backup. Mutually exclusive with --clone-from-tablet. | | --clone-from-tablet | Clone data from a specific tablet by alias (e.g., zone1-123) instead of restoring from backup. Mutually exclusive with --clone-from-primary. | | --restore-with-clone | Use MySQL CLONE for the restore phase instead of restoring from backup. Requires either --clone-from-primary or --clone-from-tablet. | | --clone-restart-wait-timeout | Timeout for waiting for MySQL to restart after CLONE REMOTE completes. Default: 5 minutes. |

Clone User Configuration:

| Flag | Description | |------|-------------| | --db-clone-user | MySQL username for CLONE operations (donor authentication). | | --db-clone-password | Password for the CLONE user. | | --db-clone-use-ssl | Use SSL when connecting to the donor for CLONE operations. |

Example Usage:

Clone from the shard's primary:

vttablet \
  --mysql-clone-enabled \
  --restore-with-clone \
  --clone-from-primary \
  ...

Clone from a specific tablet:

vtbackup \
  --mysql-clone-enabled \
  --restore-with-clone \
  --clone-from-tablet=zone1-0000000100 \
  ...

Note: All tablets participating in CLONE operations (both donors and recipients) must have --mysql-clone-enabled set during MySQL initialization to ensure the CLONE plugin is loaded and the clone user exists.

<a id="restore-hook-backup-engine-env"/>Restore Hook Improvements</a>

Extended Hook Coverage: The vttablet_restore_done hook now fires when restores are triggered via vtctldclient RestoreFromBackup. Previously, this hook only ran during tablet startup or clone operations.

New Environment Variable: The hook now sets TM_RESTORE_DATA_BACKUP_ENGINE to indicate which backup engine was used. The value comes from the backup manifest's BackupMethod field.

TM_RESTORE_DATA_BACKUP_ENGINE is only set when a restore reads from an actual backup—not for clone-based restores or when no backup is used. Hook scripts can use this to perform engine-specific actions based on whether the restore used builtin, xtrabackup, or another engine.
