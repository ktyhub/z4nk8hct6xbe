#vitesse v24.0.5

Sortie du Vitess v24.0.5

Résumé

Les valeurs sql_mode non prises en charge sont rejetées

VTGate

VTGate a déjà rejeté les instructions SET sql_mode = ... qui activent un mode que l'analyseur Vitess ne prend pas en charge (ANSI_QUOTES, NO_BACKSLASH_ESCAPES, PIPES_AS_CONCAT, REAL_AS_FLOAT). La vérification comparait les noms de mode textuellement et pouvait être contournée. VTGate implémente désormais la sémantique d'affectation sql_mode de MySQL 8.x et valide chaque affectation par rapport à elle :

  • La définition d'un mode non pris en charge est rejetée même lorsque le MySQL sous-jacent fonctionne déjà avec ce mode, c'est-à-dire lorsque le SET ne modifie pas la valeur. De telles déclarations réussissaient auparavant, même si VTGate n'analyse pas les requêtes dans ces modes. Le mode combiné ANSI est également rejeté car il active ANSI_QUOTES, PIPES_AS_CONCAT et REAL_AS_FLOAT.
  • IGNORE_SPACE et HIGH_NOT_PRECEDENCE sont désormais également rejetés. Ce sont les deux modes restants qui modifient la façon dont le texte SQL est interprété. L'analyseur Vitess ne les honore pas, donc VTGate analyserait les requêtes différemment des promesses sql_mode de la session.
  • Les noms de mode inconnus et les valeurs numériques invalides échouent avec les propres erreurs de MySQL : ER_WRONG_VALUE_FOR_VAR (1231) et ER_UNSUPPORTED_SQL_MODE (3899) pour les bits de modes supprimés dans MySQL 8.0.
  • Les valeurs numériques sont décodées par rapport au masque de bits sql_mode du MySQL. Par exemple, SET sql_mode = 1048576 signale que NO_BACKSLASH_ESCAPES n'est pas pris en charge. Les valeurs numériques valides sont acceptées.
  • Les valeurs constantes sont validées au moment de la planification, sans aller-retour de fragment. Cela inclut les expressions constantes telles que CONCAT sur les littéraux, et s'applique également lorsque --enable-system-settings est désactivé. Les expressions non constantes sont validées au moment de l'exécution, une fois leur valeur connue.

VTTablette

VTTablet applique la même validation à ses propres points d'entrée et renvoie les mêmes erreurs : paramètres de connexion, sur le pool de paramètres et sur les connexions réservées, et instructions SET sql_mode à l'échelle de la session. Cela couvre les clients qui contournent la validation de VTGate, tels que les VTGates qui ne sont pas encore mis à niveau et les clients qui communiquent directement avec le service de requête. Les conseils de l'optimiseur SET_VAR sont transmis au MySQL sans modification. Chaque connexion MySQL créée par Vitess supprime désormais les modes qui modifient la façon dont le texte SQL est interprété à partir de la session sql_mode dont il hérite de la valeur globale du serveur. Tous les autres modes, comme les modes stricts et les modes zéro date, sont conservés. Cela s'applique à chaque composant : service de requêtes, suivi de schéma, pulsations, gestion de la réplication, DDL en ligne, VReplication et VDiff, et connexions aux serveurs MySQL externes. Le sql_mode global n'est pas modifié.

Impact

  • Les Clients qui exécutent SET sql_mode avec un mode non pris en charge, notamment ANSI, IGNORE_SPACE et HIGH_NOT_PRECEDENCE, reçoivent désormais une erreur. Cela se produit également lorsque le SET correspond au sql_mode actuel du backend. Les Clients qui définissent des noms de mode MySQL rejetteraient également la réception d'une erreur.
  • Lors d'une mise à niveau continue, les VTTablets sont généralement mis à niveau avant les VTGates. Une session qui définit un sql_mode désormais rejeté via un VTGate qui n'est pas encore mis à niveau commence à recevoir des erreurs des VTTablets mis à niveau.
  • Un backend dont le sql_mode global inclut un de ces modes le conserve, mais les sessions Vitess n'en héritent plus. Voir #20883 pour plus de détails.

Table ACL : les appelants avec chaque rôle sur chaque table peuvent exécuter des instructions dont les tables ne peuvent pas être déterminées

v24.0.4 a commencé à refuser, sous une ACL de table stricte (--queryserver-config-strict-table-acl), les instructions dont les tables vttablet ne peuvent pas déterminer (DO, CALL, REPAIR, OPTIMIZE, LOAD DATA et un CREATE TABLE que l'analyseur de vttablet ne peut pas analyser complètement) pour chaque appelant en dehors de l'ACL exemptée (--queryserver-config-acl-exempt-acl) ; voir GHSA-w6mx-2f8x-pqf4. Un appelant qui est un lecteur, un écrivain et un administrateur dans un groupe de tables couvrant chaque table ("table_names_or_prefixes": ["%"]) détient tous les rôles sur n'importe quelle table qu'une telle instruction pourrait toucher, donc DO, REPAIR, OPTIMIZE et un CREATE TABLE partiellement analysé s'exécutent maintenant pour cela. CALL et LOAD DATA restent même alors refusés, puisqu'une procédure SQL SECURITY DEFINER s'exécute avec les privilèges de son définisseur et LOAD DATA INFILE lit les fichiers sur le serveur, ce que l'ACL de table n'accorde pas ; émettez-les en tant qu’appelant dans l’ACL exemptée. Ces chèques sont comptés sous le label undetermined-table-set TableName, en TableACLDenied, ou en TableACLAllowed pour un appelant avec chaque rôle sur chaque table. Avec l'exécution à sec (--queryserver-config-enable-table-acl-dry-run), seules les instructions pour lesquelles la vérification refuserait l'incrémentation de TableACLPseudoDenied. Voir #21349 pour plus de détails.

Jeux de caractères de connexion restreints

--db-charset, et les autres endroits où un jeu de caractères de connexion MySQL est configuré, n'acceptent plus sjis, cp932, gb18030, gbk, big5, ucs2, utf16, utf16le ou utf32, qu'ils soient donnés comme jeu de caractères ou comme l'un de ses classements. Une tablette configurée avec l'un d'eux ne démarre pas, VTGate refuse un SET de character_set_client, character_set_connection, character_set_results ou collation_connection à l'un d'eux, ou à un nom qui n'est pas un jeu de caractères ou un classement, auquel il répondait par OK et ignorait, et VTTablet refuse un paramètre ou une instruction SET qui basculerait la connexion d'une session vers l'un d'eux. Un client peut toujours en demander un lors de la poignée de main : VTGate lit ses instructions octet par octet, comme le fait la connexion de la tablette à MySQL, afin qu'elles ne puissent pas sortir d'un littéral. Vitess analyse et échappe le texte SQL octet par octet, et dans ces jeux de caractères, le deuxième octet d'un caractère peut être une barre oblique inverse ou une citation inverse, de sorte que le texte qu'ils contiennent a été mal analysé ou corrompu lors de son passage dans Vitess. Utilisez plutôt utf8mb4 comme jeu de caractères de connexion. Les tables et les colonnes peuvent toujours être déclarées avec n'importe lequel de ces jeux de caractères ; MySQL convertit entre eux et le jeu de caractères de connexion. Cela corrige GHSA-c28j-qmfx-4gxp. Voir #21392 et #21465 pour plus de détails.

Les noms des jeux de caractères et des classements sont cités lors de la régénération

Un nom de jeu de caractères, de classement, de moteur, d'espace de table ou d'analyseur de texte intégral est désormais décodé lors de l'analyse, et réécrit sous la forme d'un seul jeton lorsque Vitess régénère l'instruction : nu lorsqu'il s'agit d'un jeu de caractères, d'un classement, d'un moteur, d'un type d'index ou d'un nom d'analyseur connu, sinon cité en arrière. Conséquences visibles par l'utilisateur :

  • Un nom entre guillemets est normalisé. COLLATE 'utf8_bin' se régénère en COLLATE utf8_bin — les orthographes entre guillemets et sans guillemets signifient le même nom, et la forme décodée est ce qui est stocké. Tout ce qui compare la forme imprimée de ces instructions octet par octet voit la nouvelle orthographe.
  • Seuls les noms connus restent intacts. Un nom de jeu de caractères ou de classement de n'importe quelle version de MySQL ou MariaDB, un moteur de stockage connu tel que InnoDB ou memory, les types d'index BTREE, HASH et RTREE, les analyseurs ngram et mecab et les espaces de table innodb_system et innodb_file_per_table sont réécrits tels qu'ils étaient. orthographié. Tout autre nom est cité en arrière : TABLESPACE ts se régénère sous la forme TABLESPACE `ts` , and so does an engine Vitess does not know or a keyword used as a name. WITH PARSER accepts only a plain identifier, so a known name that is a keyword is quoted there: WITH PARSER `memory` keeps its quoting where ENGINE memory does not. binary is still bare where the grammar has a BINARY alternative, except directly before the BINARY attribute: CHARACTER SET 'binaire' BINARY regenerates as CHARACTER SET `binary` BINARY.
  • COLLATE binary dans une expression est cité. expr COLLATE binary se régénère alors que expr COLLATE `binary` , because MySQL's expression COLLATE only accepts binary quoted. Column, table and database COLLATE binaire and CHARACTER SET binaire reste nu.
  • Un nom de jeu de caractères, de classement, de moteur ou de tablespace de partition vide est rejeté. CHARACTER SET '' et COLLATE '' sur une colonne, une table, ALTER TABLE ... CONVERT TO, CAST/CONVERT, CONVERT ... USING, CHAR ... USING, SELECT ... INTO OUTFILE et une expression, ENGINE '' sur une table ou une partition, et TABLESPACE '' d'une partition n'analyse plus. Un nom vide dans ces positions est impossible à distinguer de l'absence de la clause, donc il aurait déjà été supprimé ou mutilé et une instruction rejetée par MySQL aurait pu devenir une instruction valide et différente. Les instructions non-DDL obtiennent directement l'erreur ; DDL revient à une analyse partielle, donc le propre texte du client est transmis et MySQL le rejette. SET NAMES ... COLLATE '' et SET CHARACTER SET ... COLLATE '', qui analysaient et supprimaient le classement, sont désormais également des erreurs d'analyse ; MySQL rejette les deux. CREATE/ALTER DATABASE ... CHARACTER SET '' et COLLATE '' sont inchangés : ils sont toujours analysés et sont réécrits sous la forme ''.
  • ENCRYPTION nécessite une valeur entre guillemets. CREATE/ALTER DATABASE ... ENCRYPTION N n'analyse plus complètement, correspondant à MySQL, qui n'accepte que 'Y' ou 'N' comme chaîne entre guillemets. Une telle déclaration revient désormais à une analyse partielle plutôt que d'être régénérée dans une orthographe que MySQL refuserait. Cela corrige GHSA-j8pc-mcwq-qrg6. Voir #21435 pour plus de détails.

Les modes VTAdmin VExplain qui exécutent l'instruction nécessitent l'action execute

VExplain API de VTAdmin a été autorisé avec l'action get, mais VEXPLAIN QUERIES, ALL et TRACE exécutent l'instruction qu'ils expliquent, donc un acteur autorisé uniquement à lire peut modifier les données via celle-ci (GHSA-c2r8-grjp-w8c2). Ces modes nécessitent désormais la nouvelle action execute sur la ressource VExplain ; PLAN et KEYS, qui planifient uniquement l'instruction, ne nécessitent toujours que get. Pour ces modes, VTAdmin accepte également uniquement un SELECT sans INTO, séquence les valeurs suivantes ou les fonctions de verrouillage consultatif, et les exécute dans une transaction en lecture seule qui est toujours annulée. La page VExplain de l'interface utilisateur Web est désormais par défaut PLAN. Migration : accordez l'action execute sur VExplain aux acteurs qui doivent exécuter VEXPLAIN QUERIES, ALL ou TRACE. Les règles qui accordent toutes les actions (*) et --no-rbac l'incluent déjà. Impact : un acteur avec seulement get sur VExplain obtient une erreur unauthorized de VEXPLAIN QUERIES, ALL et TRACE. Voir #21396 pour plus de détails.

vitess v24.0.5

Release of Vitess v24.0.5

Summary

Unsupported sql_mode values are rejected

VTGate

VTGate already rejected SET sql_mode = ... statements that enable a mode the Vitess parser does not support (ANSI_QUOTES, NO_BACKSLASH_ESCAPES, PIPES_AS_CONCAT, REAL_AS_FLOAT). The check compared mode names textually and could be bypassed. VTGate now implements MySQL 8.x's sql_mode assignment semantics and validates every assignment against them:

  • Setting an unsupported mode is rejected even when the underlying MySQL already runs with that mode, that is, when the SET would not change the value. Such statements previously succeeded, even though VTGate does not parse queries under these modes. The combination mode ANSI is rejected as well, because it enables ANSI_QUOTES, PIPES_AS_CONCAT, and REAL_AS_FLOAT.
  • IGNORE_SPACE and HIGH_NOT_PRECEDENCE are now also rejected. They are the two remaining modes that change how SQL text is interpreted. The Vitess parser does not honor them, so VTGate would parse queries differently than the session's sql_mode promises.
  • Unknown mode names and invalid numeric values fail with MySQL's own errors: ER_WRONG_VALUE_FOR_VAR (1231), and ER_UNSUPPORTED_SQL_MODE (3899) for the bits of modes removed in MySQL 8.0.
  • Numeric values decode against MySQL's sql_mode bitmask. For example, SET sql_mode = 1048576 reports that NO_BACKSLASH_ESCAPES is unsupported. Valid numeric values are accepted.
  • Constant values are validated at planning time, with no shard round trip. This includes constant expressions such as CONCAT over literals, and it also applies when --enable-system-settings is disabled. Non-constant expressions are validated at execution time, once their value is known.

VTTablet

VTTablet applies the same validation at its own entry points and returns the same errors: connection settings, on the settings pool and on reserved connections, and session-scope SET sql_mode statements. This covers clients that bypass VTGate's validation, such as VTGates that are not upgraded yet and clients that talk to the query service directly. SET_VAR optimizer hints are forwarded to MySQL unchanged.

Every MySQL connection Vitess creates now strips the modes that change how SQL text is interpreted from the session sql_mode it inherits from the server's global value. All other modes, such as the strict modes and the zero-date modes, are kept. This applies to every component: query serving, schema tracking, heartbeats, replication management, Online DDL, VReplication and VDiff, and connections to external MySQL servers. The global sql_mode is not changed.

Impact

  • Clients that run SET sql_mode with an unsupported mode, including ANSI, IGNORE_SPACE and HIGH_NOT_PRECEDENCE, now receive an error. This also happens when the SET matches the backend's current sql_mode. Clients that set mode names MySQL would itself reject receive an error as well.
  • During a rolling upgrade, VTTablets are typically upgraded before VTGates. A session that sets a now-rejected sql_mode through a VTGate that is not upgraded yet starts receiving errors from upgraded VTTablets.
  • A backend whose global sql_mode includes one of these modes keeps it, but Vitess sessions no longer inherit it.

See #20883 for details.

Table ACL: callers with every role on every table may run statements whose tables cannot be determined

v24.0.4 began denying, under strict table ACL (--queryserver-config-strict-table-acl), statements whose tables vttablet cannot determine (DO, CALL, REPAIR, OPTIMIZE, LOAD DATA, and a CREATE TABLE that vttablet's parser cannot fully parse) for every caller outside the exempt ACL (--queryserver-config-acl-exempt-acl); see GHSA-w6mx-2f8x-pqf4. A caller that is a reader, a writer and an admin in a table group covering every table ("table_names_or_prefixes": ["%"]) holds every role on any table such a statement could touch, so DO, REPAIR, OPTIMIZE and a partially parsed CREATE TABLE now run for it. CALL and LOAD DATA remain denied even then, since a SQL SECURITY DEFINER procedure runs with its definer's privileges and LOAD DATA INFILE reads files on the server, neither of which table ACL grants; issue them as a caller in the exempt ACL.

These checks are counted under the undetermined-table-set TableName label, in TableACLDenied, or in TableACLAllowed for a caller with every role on every table. With dry-run (--queryserver-config-enable-table-acl-dry-run), only the statements the check would deny increment TableACLPseudoDenied.

See #21349 for details.

Connection character sets restricted

--db-charset, and the other places a MySQL connection character set is configured, no longer accept sjis, cp932, gb18030, gbk, big5, ucs2, utf16, utf16le or utf32, whether given as a character set or as one of its collations. A tablet configured with one of them fails to start, VTGate refuses a SET of character_set_client, character_set_connection, character_set_results or collation_connection to one of them, or to a name that is not a character set or collation, which it used to answer with OK and ignore, and VTTablet refuses a setting or SET statement that would switch a session's connection to one of them. A client may still ask for one of them at the handshake: VTGate reads its statements byte by byte, as the tablet's connection to MySQL does, so they cannot break out of a literal.

Vitess parses and escapes SQL text byte by byte, and in these character sets the second byte of a character can be a backslash or a back quote, so text in them was misparsed or corrupted on its way through Vitess. Use utf8mb4 as the connection character set instead. Tables and columns can still be declared with any of these character sets; MySQL converts between them and the connection character set.

This fixes GHSA-c28j-qmfx-4gxp.

See #21392 and #21465 for details.

Charset and collation names are quoted when regenerated

A charset, collation, engine, tablespace or full-text parser name is now decoded when parsed, and written back as a single token when Vitess regenerates the statement: bare when it is a known charset, collation, engine, index type or parser name, back-quoted otherwise.

User-visible consequences:

  • A quoted name is normalized. COLLATE 'utf8_bin' regenerates as COLLATE utf8_bin — the quoted and unquoted spellings mean the same name, and the decoded form is what is stored. Anything comparing the printed form of these statements byte for byte sees the new spelling.
  • Only known names stay bare. A charset or collation name of any MySQL or MariaDB version, a known storage engine such as InnoDB or memory, the BTREE, HASH and RTREE index types, the ngram and mecab parsers, and the innodb_system and innodb_file_per_table tablespaces are written back as they were spelled. Any other name is back-quoted: TABLESPACE ts regenerates as TABLESPACE `ts` , and so does an engine Vitess does not know or a keyword used as a name. WITH PARSER accepts only a plain identifier, so a known name that is a keyword is quoted there: WITH PARSER `memory` keeps its quoting where ENGINE memory does not. binary is still bare where the grammar has a BINARY alternative, except directly before the BINARY attribute: CHARACTER SET 'binary' BINARY regenerates as CHARACTER SET `binary` BINARY.
  • COLLATE binary in an expression is quoted. expr COLLATE binary regenerates as expr COLLATE `binary` , because MySQL's expression COLLATE only accepts binary quoted. Column, table and database COLLATE binary and CHARACTER SET binary stay bare.
  • An empty charset, collation, engine or partition tablespace name is rejected. CHARACTER SET '' and COLLATE '' on a column, a table, ALTER TABLE ... CONVERT TO, CAST/CONVERT, CONVERT ... USING, CHAR ... USING, SELECT ... INTO OUTFILE and an expression, ENGINE '' on a table or a partition, and a partition's TABLESPACE '' no longer parse. An empty name in these positions is indistinguishable from the clause being absent, so it would previously have been dropped or mangled and a statement MySQL rejects could have become a valid, different one. Non-DDL statements get the error directly; DDL falls back to a partial parse, so the client's own text is forwarded and MySQL rejects it. SET NAMES ... COLLATE '' and SET CHARACTER SET ... COLLATE '', which used to parse and discard the collation, are now parse errors too; MySQL rejects both. CREATE/ALTER DATABASE ... CHARACTER SET '' and COLLATE '' are unchanged: they still parse and are written back as ''.
  • ENCRYPTION requires a quoted value. CREATE/ALTER DATABASE ... ENCRYPTION N no longer fully parses, matching MySQL, which only accepts 'Y' or 'N' as a quoted string. Such a statement now falls back to a partial parse rather than being regenerated into a spelling MySQL would refuse.

This fixes GHSA-j8pc-mcwq-qrg6.

See #21435 for details.

VTAdmin VExplain modes that run the statement require the execute action

VTAdmin's VExplain API was authorized with the get action, but VEXPLAIN QUERIES, ALL and TRACE run the statement they explain, so an actor allowed only to read could change data through it (GHSA-c2r8-grjp-w8c2). Those modes now require the new execute action on the VExplain resource; PLAN and KEYS, which only plan the statement, still require only get. For those modes VTAdmin also accepts only a SELECT without INTO, sequence next-values or advisory lock functions, and runs them in a read-only transaction that is always rolled back. The VExplain page in the web UI now defaults to PLAN.

Migration: grant the execute action on VExplain to the actors that should run VEXPLAIN QUERIES, ALL or TRACE. Rules that grant all actions (*) and --no-rbac already include it.

Impact: an actor with only get on VExplain gets an unauthorized error from VEXPLAIN QUERIES, ALL and TRACE.

See #21396 for details.

Security fixes

  • Fixes GHSA-73pp-99vw-h5g8: SQL injection through VStream LastPK values. See #21377.
  • Fixes GHSA-92cc-q2h6-m2vr: SQL injection through convert_tz() arguments in a VStream filter. See #21377.
  • Fixes GHSA-8w3p-4xg5-rm9w: SQL injection through table names in Online DDL statements. See #21381.
  • Fixes GHSA-x56j-8c72-5xgg: SQL injection through the caller ID in query annotations (--queryserver-config-annotate-queries). See #21369.
  • Fixes GHSA-m282-7w35-g77m: SQL injection through a global SET variable name. See #21390.
  • Fixes GHSA-9248-hccp-qf8f: SQL injection through DATE, TIME and TIMESTAMP literals. See #21389.
  • Fixes GHSA-9rx3-8pwm-c228: SQL injection through a session variable value carried in a SET_VAR hint. See #21388.
  • Fixes GHSA-pfg5-ppc7-ff45: SQL hidden from parsing and table ACL checks in a trailing comment. See #21387.
  • Fixes GHSA-xf67-9r78-xv82: SQL injection through malformed numeric bind variables. See #21386.
  • Fixes GHSA-3fr2-mqr5-r5x5: VTAdmin API routes that change cluster state accepted cross-site GET requests. See #21397.
  • Fixes GHSA-78h7-x6qm-xpr8: VTAdmin's ReloadSchemaShard did not check RBAC. See #21394.
