Points forts de la version <a id="v2100-release-highlights"></a>

Gestion des secrets <a id="v2100-highlight-secrets-management"></a>

Conservez les informations d’identification du collecteur hors des fichiers de configuration en texte brut. Netdata vous permet désormais de référencer des secrets dans les configurations du collecteur au lieu de les stocker directement. Les mots de passe, jetons et clés API sont résolus au moment de l'exécution à partir de la source que vous choisissez.

Résolveurs

Netdata propose quatre types de résolveurs, du simple au niveau entreprise :

| Résolveur | Syntaxe | Idéal pour | |:---------------|:-------------------------------------------------|:----------------------------------------------------------------------------------------------------------------------| | Variable d'environnement | ${env:VAR_NAME} | Secrets déjà injectés dans l'environnement de service Netdata | | Fichier | ${file:/absolute/path} | Secrets stockés dans des fichiers locaux sur le disque (Docker Secrets, Kubernetes Secrets montés en volumes) | | Commande | ${cmd:/absolute/path args} | Secrets renvoyés par une commande locale trusted (par exemple, 1Password CLI, scripts personnalisés) | | Boutique secrète | ${store:<kind>:<name>:<operand>} | Secrets gérés de manière centralisée dans les fournisseurs de cloud ou dans Vault |

Backends Secretstore pris en charge

Pour les organisations gérant les secrets de manière centralisée, Netdata s'intègre à quatre backends secretstore :

| Back-end | Genre | Format de l'opérande | Modes d'authentification | |:-------------------------------------------------------------------------------------------------------------------------|:-------------------------|:-----------------------------------------|:----------------------------------------------------------------------------| | Gestionnaire de secrets AWS | aws-sm | secret-name[#key] | Identifiants d'environnement, rôle de tâche ECS, profil d'instance EC2 | | Coffre de clés Azure | azure-kv | vault-name/secret-name | Principal de service, identité gérée, chaîne d'informations d'identification par défaut | | Gestionnaire de secrets Google | gcp-sm | project/secret[/version] | Serveur de métadonnées, fichier de compte de service | | Coffre-fort HashiCorp | vault | path#key | Jeton, fichier de jeton |

Configurez les magasins de secrets via l'interface utilisateur de configuration dynamique Netdata (Collectors → go.d → SecretStores) ou via des fichiers de configuration sous /etc/netdata/go.d/ss/.

Exemple

Un collecteur MySQL référençant son mot de passe depuis HashiCorp Vault :

# /etc/netdata/go.d/mysql.conf
jobs:
  - name: mysql_prod
    dsn: "netdata:${store:vault:vault_prod:secret/data/netdata/mysql#password}@tcp(127.0.0.1:3306)/"

Vous pouvez mélanger librement les types de résolveurs. Par exemple, lisez le nom d'utilisateur d'une variable d'environnement et le mot de passe d'un secretstore dans la même valeur de configuration :

jobs:
  - name: mysql_prod
    dsn: "${env:MYSQL_USER}:${store:vault:vault_prod:secret/data/netdata/mysql#password}@tcp(127.0.0.1:3306)/"

Comment ça marche

  • Les secrets sont résolus à chaque démarrage ou redémarrage d'une tâche de collecteur.
  • La mise à jour d'un magasin de secrets redémarre automatiquement les tâches de collecteur qui l'utilisent afin qu'elles récupèrent de nouvelles informations d'identification.
  • Les valeurs de configuration Secretstore elles-mêmes prennent également en charge les résolveurs ${env:...}, ${file:...} et ${cmd:...}, de sorte que les informations d'identification du backend n'ont pas non plus besoin d'être stockées en texte brut.

[!ASTUCE] Pour une configuration détaillée, des guides d'authentification spécifiques au back-end et le dépannage, consultez la [documentation de Secrets Management] (https://learn.netdata.cloud/docs/collecting-metrics/secrets-management).

Collecteur de plugins Nagios <a id="v2100-highlight-nagios-plugins"></a>

Exécutez des [plugins compatibles Nagios] (https://www.nagios-plugins.org/) et des scripts personnalisés directement dans Netdata avec le nouveau [collecteur de plugins Nagios] (https://learn.netdata.cloud/docs/collecting-metrics/collectors/synthetic-testing/nagios-plugins). Tout exécutable qui suit le [format de sortie du plugin Nagios] (https://nagios-plugins.org/doc/guidelines.html) fonctionne immédiatement : plugins Nagios packagés, scripts shell personnalisés ou binaires compilés.

Ce que vous obtenez

| Fonctionnalité | Détails | |:--------------------------------------|:------------------------------------------------------------------------------------------------------------------------------------------------------------| | Vérifier la surveillance de l'état | Suit les états OK, AVERTISSEMENT, CRITIQUE et INCONNU à partir du code de sortie du processus | | Graphiques de données de performances automatiques | Les valeurs des données de performances Nagios sont analysées et représentées automatiquement | | Alertes basées sur un seuil | Lorsque perfdata inclut des seuils d'avertissement/critique, Netdata dérive un graphique d'état de seuil (ok/avertissement/critique) et crée des alertes intégrées | | Mesures d'exécution | Mesure la durée d'exécution, le temps CPU et l'utilisation de la mémoire de chaque vérification | | Planification de style Nagios | Intervalles de vérification configurables, intervalles de nouvelle tentative, nombre maximal de tentatives de vérification et périodes de temps | | Logique d'état doux/dur | Les résultats non OK réessayent à retry_interval jusqu'à max_check_attempts avant de déclencher des alertes, évitant ainsi les fausses alarmes dues à des défaillances transitoires |

Alertes intégrées

Le collecteur est livré avec quatre alertes de stock :

| Alerte | Déclenche quand | |:------------------------------------------|:-------------------------------------------------| | nagios_job_execution_state_warn | Un contrôle est à l'état dur AVERTISSEMENT | | nagios_job_execution_state_crit | Un chèque est dans un état critique CRITIQUE | | nagios_job_perfdata_threshold_state_warn | Une métrique perfdata dépasse son seuil d'avertissement | | nagios_job_perfdata_threshold_state_crit | Une métrique perfdata dépasse son seuil critique |

Toutes les alertes de stock suppriment les états de nouvelle tentative logicielle. Les alertes se déclenchent uniquement après les échecs consécutifs configurés du max_check_attempts.

Exemple

# /usr/local/lib/netdata/checks/check_api.sh
#!/bin/sh
resp=$(curl -s -o /dev/null -w "%{http_code} %{time_total}" --max-time 5 "$1" 2>/dev/null)
code=$(echo "$resp" | cut -d' ' -f1)
time=$(echo "$resp" | cut -d' ' -f2)

[ "$code" -ge 500 ] && echo "CRITICAL - HTTP $code | response_time=${time}s;~:2;~:5" && exit 2
[ "$code" -ne 200 ] && echo "WARNING - HTTP $code | response_time=${time}s;~:2;~:5" && exit 1
echo "OK - HTTP $code | response_time=${time}s;~:2;~:5"
exit 0

# /etc/netdata/scripts.d/nagios.conf
jobs:
  - name: api_health
    plugin: /bin/sh
    args: ["/usr/local/lib/netdata/checks/check_api.sh", "http://localhost:8080/health"]
    check_interval: 1m
    retry_interval: 15s
    max_check_attempts: 3

Cela produit des graphiques d'état de vérification, des métriques d'exécution et, comme le script émet des données de performances avec des seuils (response_time avec avertissement > 2 s / critique > 5 s), un graphique de temps de réponse automatique avec un graphique d'état de seuil et des alertes intégrées.

[!ASTUCE] Pour le guide de configuration complet, la procédure pas à pas des scripts personnalisés et la configuration des périodes de temps, consultez la [documentation du collecteur de plugins Nagios] (https://learn.netdata.cloud/docs/collecting-metrics/collectors/synthetic-testing/nagios-plugins).

Collecteur Azure Monitor <a id="v2100-highlight-azure-monitor"></a>

Surveillez l’intégralité de votre infrastructure Azure depuis Netdata avec le nouveau Collecteur Azure Monitor. Il collecte les métriques de plate-forme à partir d'Azure Monitor Metrics API avec découverte automatique des ressources : pointez-le vers vos abonnements, et il trouve vos ressources, les associe aux profils intégrés (ensembles de métriques préconfigurés) et commence à collecter des métriques.

[!IMPORTANT] Il s'agit d'une fonctionnalité alpha. Le format de configuration peut changer dans les prochaines versions.

Secrets Management <a id="v2100-highlight-secrets-management"></a>

Keep collector credentials out of plain-text configuration files. Netdata now lets you reference secrets in collector configurations instead of storing them directly. Passwords, tokens, and API keys are resolved at runtime from the source you choose.

Resolvers

Netdata provides four resolver types, from simple to enterprise-grade:

| Resolver | Syntax | Best For | |:-------------------------|:-----------------------------------|:----------------------------------------------------------------------------------------------| | Environment variable | ${env:VAR_NAME} | Secrets already injected into the Netdata service environment | | File | ${file:/absolute/path} | Secrets stored in local files on disk (Docker Secrets, Kubernetes Secrets mounted as volumes) | | Command | ${cmd:/absolute/path args} | Secrets returned by a trusted local command (e.g., 1Password CLI, custom scripts) | | Secretstore | ${store:<kind>:<name>:<operand>} | Secrets managed centrally in cloud providers or Vault |

Supported Secretstore Backends

For organizations managing secrets centrally, Netdata integrates with four secretstore backends:

| Backend | Kind | Operand Format | Authentication Modes | |:------------------------------------------------------------------------------------------------------------------------------------|:-----------|:---------------------------|:--------------------------------------------------------------| | AWS Secrets Manager | aws-sm | secret-name[#key] | Environment credentials, ECS task role, EC2 instance profile | | Azure Key Vault | azure-kv | vault-name/secret-name | Service principal, Managed identity, Default credential chain | | Google Secret Manager | gcp-sm | project/secret[/version] | Metadata server, Service account file | | HashiCorp Vault | vault | path#key | Token, Token file |

Configure secretstores through the Netdata Dynamic Configuration UI (Collectors → go.d → SecretStores) or via configuration files under /etc/netdata/go.d/ss/.

Example

A MySQL collector referencing its password from HashiCorp Vault:

# /etc/netdata/go.d/mysql.conf
jobs:
  - name: mysql_prod
    dsn: "netdata:${store:vault:vault_prod:secret/data/netdata/mysql#password}@tcp(127.0.0.1:3306)/"

You can mix resolver types freely. For example, read the username from an environment variable and the password from a secretstore in the same config value:

jobs:
  - name: mysql_prod
    dsn: "${env:MYSQL_USER}:${store:vault:vault_prod:secret/data/netdata/mysql#password}@tcp(127.0.0.1:3306)/"

How It Works

  • Secrets are resolved each time a collector job starts or restarts.
  • Updating a secretstore automatically restarts collector jobs that use it so they pick up new credentials.
  • Secretstore configuration values themselves also support ${env:...}, ${file:...}, and ${cmd:...} resolvers, so backend credentials don't need to be stored in plain text either.

[!TIP] For detailed setup, backend-specific authentication guides, and troubleshooting, see the Secrets Management documentation.

Nagios Plugins Collector <a id="v2100-highlight-nagios-plugins"></a>

Run Nagios-compatible plugins and custom scripts directly inside Netdata with the new Nagios Plugins collector. Any executable that follows the Nagios plugin output format works out of the box: packaged Nagios plugins, custom shell scripts, or compiled binaries.

What You Get

| Feature | Details | |:--------------------------------------|:----------------------------------------------------------------------------------------------------------------------------------------------| | Check State Monitoring | Tracks OK, WARNING, CRITICAL, and UNKNOWN states from the process exit code | | Automatic Performance Data Charts | Nagios performance data values are parsed and charted automatically | | Threshold-Based Alerting | When perfdata includes warning/critical thresholds, Netdata derives a threshold state chart (ok/warning/critical) and creates built-in alerts | | Execution Metrics | Measures run duration, CPU time, and memory usage of each check | | Nagios-Style Scheduling | Configurable check intervals, retry intervals, max check attempts, and time periods | | Soft/Hard State Logic | Non-OK results retry at retry_interval up to max_check_attempts before triggering alerts, preventing false alarms from transient failures |

Built-in Alerts

The collector ships with four stock alerts:

| Alert | Triggers When | |:-------------------------------------------|:-------------------------------------------------| | nagios_job_execution_state_warn | A check is in WARNING hard state | | nagios_job_execution_state_crit | A check is in CRITICAL hard state | | nagios_job_perfdata_threshold_state_warn | A perfdata metric exceeds its warning threshold | | nagios_job_perfdata_threshold_state_crit | A perfdata metric exceeds its critical threshold |

All stock alerts suppress soft retry states. Alerts fire only after the configured max_check_attempts consecutive failures.

Example

# /usr/local/lib/netdata/checks/check_api.sh
#!/bin/sh
resp=$(curl -s -o /dev/null -w "%{http_code} %{time_total}" --max-time 5 "$1" 2>/dev/null)
code=$(echo "$resp" | cut -d' ' -f1)
time=$(echo "$resp" | cut -d' ' -f2)

[ "$code" -ge 500 ] && echo "CRITICAL - HTTP $code | response_time=${time}s;~:2;~:5" && exit 2
[ "$code" -ne 200 ] && echo "WARNING - HTTP $code | response_time=${time}s;~:2;~:5" && exit 1
echo "OK - HTTP $code | response_time=${time}s;~:2;~:5"
exit 0

# /etc/netdata/scripts.d/nagios.conf
jobs:
  - name: api_health
    plugin: /bin/sh
    args: ["/usr/local/lib/netdata/checks/check_api.sh", "http://localhost:8080/health"]
    check_interval: 1m
    retry_interval: 15s
    max_check_attempts: 3

This produces check state charts, execution metrics, and because the script emits perfdata with thresholds (response_time with warn >2s / crit >5s), an automatic response time chart with a threshold state chart and built-in alerts.

[!TIP] For the full setup guide, custom scripts walkthrough, and time period configuration, see the Nagios Plugins collector documentation.
