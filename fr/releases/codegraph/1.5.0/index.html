codegraphe v1.5.0

[1.5.0] - 2026-07-21

⚡ La version du moteur Rust — avec une synchronisation quasi instantanée

Cette version reconstruit le moteur d'analyse de CodeGraph en tant que noyau natif Rust, révise le pipeline de résolution qui l'entoure et rend le graphique en direct effectivement instantané : une sauvegarde atteint désormais le graphique en moins d'une seconde, même sur un référentiel de 27 000 fichiers. Il s'agit de la plus grande mise à niveau de performances de l'histoire du projet, et chaque graphique est vérifié octet par octet, à l'identique du moteur précédent.

  • Analyse native Rust pour 20 langues — TypeScript, JavaScript (+TSX/JSX), Java, Python, Go, C, C++, Rust, C#, Ruby, PHP, Swift, Kotlin, Scala, Dart, R, Lua et Luau analysent désormais dans un noyau Rust compilé (Metal et CUDA utilisent le chemin C++). Les plates-formes sans binaire prédéfini et les fichiers individuels comportant des erreurs de syntaxe reviennent automatiquement au moteur précédent - même graphique dans les deux cas, éprouvé sur les référentiels allant des petites bibliothèques au noyau Linux.
  • Adaptatif à votre machine — CodeGraph dimensionne ses analyseurs, son pool de résolveurs et ses caches à partir de ce que le système possède réellement : nombre de cœurs réels (conteneur/groupe de contrôle, pas celui de l'hôte), mémoire disponible honnête sur macOS et Linux et coût de résolution mesuré par projet. Un grand poste de travail bénéficie du pipeline parallèle complet ; un VPS à 2 cœurs obtient un pipeline réglé pour se terminer de manière fiable au lieu de manquer de mémoire – le noyau Linux (70 000 fichiers) indexe jusqu'à la fin sur une machine à 2 cœurs de 6 Go en moins de 12 minutes – contre 26 au début de ce cycle.
  • La résolution est considérablement plus rapide dans tous les domaines : résolution parallèle adaptative, recherche de méthode-candidat plus intelligente et marche de supertype/conformité mémorisée. Le référentiel du compilateur Swift (27 000 fichiers, Swift + C++) est passé de plus de 3 minutes à environ 100 secondes au cours de ce cycle de publication ; Les projets Rust, Lua et Java connaissent tous des améliorations à deux chiffres.
  • La synchronisation est désormais quasi instantanée : une sauvegarde atteint le graphique en moins d'une seconde, même à l'échelle du compilateur. L'observateur permanent se déclenche après une fenêtre silencieuse de 300 ms pour les sauvegardes isolées (des rafales de modifications continuent de fusionner) et transmet les chemins modifiés exacts à synchroniser au lieu de réanalyser l'ensemble de l'arborescence - travail de sauvegarde sur un nouveau graphique mesuré d'environ 0,3 s sur un projet Java de 4 400 fichiers et d'environ 0,4 s sur le référentiel du compilateur Swift de 27 000 fichiers, octet identique à une réconciliation complète. Tous les détails dans les entrées ci-dessous.

Nouvelles fonctionnalités

  • L'indexation des projets TypeScript, TSX, JavaScript, JSX, Java, Python, Go, C, C++, Rust, C#, Ruby, PHP, Swift, Kotlin, Scala, Dart, R, Lua et Luau est plus rapide : l'analyse et l'extraction de symboles s'exécutent désormais dans un moteur natif lorsqu'un binaire prédéfini est disponible pour votre plate-forme (les bundles de versions en incluent un), produisant exactement le même graphique - vérifié octet par octet par rapport au moteur précédent sur des référentiels réels, des petites bibliothèques jusqu'à vscode-, dubbo-, django-, git-, protobuf-, tokio-, rust-analyzer-, jellyfin-, rails-, symfony-, swift-nio-, kotlinx.coroutines-, ggplot2-, Kong-, Scala-3-compiler- et Flutter-scale bases de code (membres générés par Lombok, tables de pointeurs de fonctions C et en-têtes macro-lourds de style Unreal-Engine inclus ; les sources CUDA et Metal empruntent le chemin C++). L'accélération est la plus importante sur les machines aux ressources limitées telles que les exécuteurs CI. Aucune configuration nécessaire : les plates-formes sans binaire natif et les fichiers individuels comportant des erreurs de syntaxe utilisent automatiquement le moteur précédent et CODEGRAPH_KERNEL=0 désactive complètement le chemin natif.
  • La résolution de référence s'exécute désormais en parallèle sur les grands projets. Lorsqu'un projet a suffisamment de références en attente pour qu'il en vaille la peine (environ 150 000+, typique des grandes bases de code Java/Kotlin/Spring), la résolution se propage à travers les threads de travail tandis que les résultats sont appliqués dans l'ordre exact que le chemin à thread unique aurait utilisé - le graphique est identique octet par octet, environ deux fois plus rapide de bout en bout sur un projet Java de 4 000 fichiers lors de nos tests. Les petits projets conservent automatiquement le chemin à thread unique (la diffusion coûte plus cher qu'elle n'y économise). Réglez CODEGRAPH_NO_PARALLEL_RESOLVE=1 pour désactiver ou CODEGRAPH_PARALLEL_RESOLVE_MIN=<count> pour régler lorsqu'il s'enclenche.
  • L'indexation des grands projets a encore bénéficié d'une accélération considérable : environ un quart d'horloge en moins sur le même projet Java de 4 000 fichiers, le graphique étant toujours identique octet par octet. Deux changements : la base de données n'entrelace plus la maintenance coûteuse des points de contrôle au milieu de la résolution sur un nouvel index (elle est pliée une fois à la fin), et pendant que les résultats d'un lot sont écrits, les threads de travail résolvent déjà le lot suivant au lieu de rester inactifs.
  • L'analyse de répartition dynamique qui s'exécute à la fin de l'indexation (câblage de rappel, d'événement et de framework) exécute désormais ses passes en parallèle sur les grands projets, réduisant cette étape environ de moitié là-bas - et une passe qui plante réessaye désormais en toute sécurité au lieu d'échouer l'ensemble de l'index, ce qui rend également les bases de code très volumineuses qui étaient auparavant mortes à cette étape plus susceptibles d'être indexées jusqu'à la fin. Les graphiques restent identiques octet par octet.
  • Sur les grands projets, l'indexation écrit ses données relationnelles sensiblement plus rapidement : les index des bases de données secondaires sont mis de côté pendant la majeure partie de la résolution des références et reconstruits une fois à la fin, au lieu d'être conservés ligne par ligne. Les graphiques restent identiques octet par octet et les petits projets ne sont pas affectés.
  • Fiabilité d'une très grande base de code : sur les projets de plusieurs millions de symboles, une passe d'analyse qui échoue sur un thread de travail est désormais ignorée avec un message clair au lieu d'être réessayée d'une manière qui pourrait supprimer l'intégralité de l'index, et la reconstruction de l'index de fin d'indexation ne risque plus de déclencher le chien de garde d'activité sur des graphiques énormes. Validé de bout en bout sur le noyau Linux (70 000 fichiers, 2 millions de symboles, 6,4 millions de relations) — il s'indexe désormais jusqu'à la fin, même sur une machine à 2 cœurs.
  • L'indexation est nettement plus rapide : un nouveau codegraph init sur un projet moyen TypeScript prend environ un tiers de temps d'horloge en moins, avec le même graphique produit octet par octet. Les gains proviennent du traitement par lots des écritures de base de données, du stockage des fichiers sur un thread d'écriture dédié, de la mémorisation des recherches répétées de résolution d'importation, de l'absence de maintenance de l'index de recherche par ligne pendant la construction en bloc (reconstruite une fois à la fin) et, sur des bases de données entièrement nouvelles uniquement, du report de la durabilité du disque jusqu'à la fin de l'index, puisqu'un premier index interrompu est simplement réexécuté. Définissez CODEGRAPH_NO_FAST_INIT=1 pour conserver une durabilité totale en cas de crash lors de la construction initiale, ou CODEGRAPH_NO_STORE_WORKER=1 pour stocker sur le thread principal.
  • codegraph install et codegraph upgrade offrent désormais un accès bêta à CodeGraph Pro une fois terminé — répondez oui, saisissez votre e-mail et vous rejoignez la même liste d'attente que le formulaire de la page d'accueil getcodegraph.com. Strictement opt-in et demandé au plus une fois par machine totale : rien n'est envoyé à moins que vous ne disiez oui et que vous saisissiez un e-mail, l'une ou l'autre des réponses est mémorisée, donc aucune installation ou mise à niveau ultérieure ne vous demandera de nouveau, et les exécutions non interactives (--yes, scripts, CI) ne voient jamais la question.
  • Chaque version est désormais vérifiable cryptographiquement : les packages npm sont publiés avec la provenance npm (le badge "Provenance" sur npmjs.com, prouvant que chaque version a été construite par le workflow de publication de ce référentiel à partir d'un commit spécifique), et les bundles de version GitHub portent des attestations de construction signées que vous pouvez vérifier avec gh attestation verify <file> -R colbymchenry/codegraph.
  • L'indexation dans des conteneurs limités en CPU ou en mémoire (Docker, exécuteurs CI) dimensionne désormais ses pools de travailleurs à partir de l'allocation réelle du conteneur au lieu de celle de la machine hôte, et les bases de code géantes ne gonflent plus les fichiers de base de données temporaires lors de l'indexation (auparavant, des dizaines de Go de disque transitoire sur les projets à l'échelle du noyau Linux). Ensemble, ces éléments évitent les pannes de mémoire et de disque insuffisantes sur les machines contraintes ; définissez CODEGRAPH_RESOLVE_WORKERS pour remplacer explicitement le nombre de travailleurs de résolution.
  • L'indexation de très gros projets sur des machines multicœurs est à nouveau plus rapide : les travailleurs à résolution parallèle actualisent désormais périodiquement leurs connexions à la base de données en lecture seule, ce qui permet de progresser dans la maintenance de la base de données au lieu de créer silencieusement un retard derrière les lecteurs de longue durée - un retard qui mettait à rude épreuve les propres écritures de l'indexeur. Les graphiques restent identiques octet par octet ; la victoire est la plus importante à l'échelle du noyau Linux sur les machines multicœurs.
  • L'indexation sur macOS utilise désormais la véritable marge de mémoire de la machine lors du dimensionnement de ses travailleurs à résolution parallèle. macOS conserve délibérément la RAM remplie de cache récupérable, de sorte que la lecture précédente de la mémoire libre est revenue minuscule (~ 1 Go sur une machine par ailleurs inactive) et a silencieusement réduit de moitié le pool de tâches - le nouvel index d'un projet Java moyen fonctionnait environ 15 à 20 % plus lentement que le matériel autorisé. Les graphiques restent identiques octet par octet ; le même correctif permet également à un cache d'analyse basé sur la mémoire de s'activer pleinement sur macOS pour les grandes bases de code C.
  • La nouvelle indexation a obtenu une accélération générale considérable : lors de la construction initiale, les index de recherche secondaires de la base de données sont mis de côté et reconstruits une fois après l'analyse au lieu d'être conservés ligne par ligne - la même astuce éprouvée que la phase de liaison ultérieure a déjà utilisée, maintenant appliquée à l'ensemble de la voie d'analyse - et la boucle de résolution de référence arrête également de maintenir les index de recherche qu'elle ne lit jamais, les reconstruisant à la fin lorsqu'il ne reste presque plus rien dans la table. La phase d'analyse d'un projet Java moyen s'exécute environ 58 % plus rapidement et son nouvel index complet environ 19 % plus rapide de bout en bout ; un index à l'échelle du noyau Linux qui prenait environ 15 minutes sur une machine à 8 cœurs se termine désormais en 11 environ, la phase de résolution à elle seule diminuant d'un tiers. Les graphiques restent identiques octet par octet et les synchronisations incrémentielles ne sont pas affectées.
  • L'enregistrement d'un fichier met désormais à jour le graphique presque immédiatement : l'observateur de fichiers se déclenche après une fenêtre silencieuse de 300 ms pour un ou deux fichiers modifiés (les rafales fusionnent toujours sous le rebond complet, et CODEGRAPH_WATCH_DEBOUNCE_MS reste la limite supérieure), et les synchronisations déclenchées par l'observateur réconcilient exactement les chemins modifiés au lieu de parcourir l'ensemble du référentiel. Les suppressions de répertoires et les tempêtes d'événements exécutent toujours l'analyse complète, de sorte que rien que les événements ne peuvent décrire n'est jamais manqué. Mesuré : le travail de synchronisation de sauvegarde sur un nouveau graphique tombe à environ 0,3 s sur un projet de 4 400 fichiers et à environ 0,4 s sur un projet de 27 000 fichiers, avec des graphiques résultants octet par octet identiques à une réconciliation complète.
  • L'indexation de Swift et d'autres bases de code gourmandes en protocoles/interfaces est devenue considérablement plus rapide : le parcours de conformité qui vérifie si une méthode réside sur les supertypes d'un récepteur (protocoles, classes de base, extensions) se souvient désormais de ses réponses pendant la durée de chaque lot de résolution au lieu de réinterroger le graphique pour chaque site d'appel - sur le référentiel du compilateur Swift (27 000 fichiers) qui a été exécuté près d'un million de fois par index. Un nouvel index de ce référentiel passe d'environ 185 secondes à moins de 100, le graphique octet par octet étant identique. La recherche de méthode candidate a également obtenu un index de propriétaire par nom, de sorte que les noms lourds de surcharge (init dans Swift, execute dans Java) ne paient plus une analyse complète de candidat par type de récepteur.
  • La résolution des appels de méthode via des variables locales (recv.method(), recv:method() de Lua, recv$method() de R) est devenue beaucoup moins chère sur les dépôts où le même récepteur est appelé encore et encore : l'analyse de déclaration qui tape le récepteur se souvient désormais de ce qu'il a déjà analysé par portée au lieu de relire les mêmes lignes source pour chaque site d'appel, et les modèles d'expression régulière avec lesquels il analyse sont compilés une fois par récepteur au lieu de par appel. Le nouvel index de Kong chute encore de 8 % en plus du correctif de résolution requise (23 % cumulés), avec des graphiques octet par octet identiques partout, y compris dans les projets Java, où cette même analyse réussit à saisir des dizaines de milliers de récepteurs.
  • L'indexation des projets Lua et Luau a été considérablement accélérée : la résolution de chaque require(...) ne réanalyse plus quatre fois la liste complète des fichiers du projet — un index de nom de fichier par projet répond instantanément à la même recherche, réduisant la résolution par besoin d'environ une milliseconde à des microsecondes. Un nouvel index de Kong (1 870 fichiers Lua) s'exécute environ 16 % plus rapidement de bout en bout, avec le graphique octet par octet identique. Le même entretien ferme également un bord d'obsolescence latent où les recherches de copybook COBOL pourraient continuer à servir une liste de fichiers mis en cache après la modification des fichiers.
  • La résolution de référence parallèle s'engage désormais de manière adaptative plutôt que par un seuil de taille de projet fixe : l'indexeur mesure le taux de résolution réel par référence sur le premier lot et fait tourner le pool de travailleurs à mi-exécution chaque fois que le travail restant le justifie. Les langages dont la résolution est coûteuse à résoudre en bénéficient le plus – Rust en particulier : un nouvel index de tokio s'exécute environ 23 % plus rapidement, avec le graphique octet par octet identique. Les petits projets et les machines low-core (exécuteurs CI à 2 cœurs) conservent le chemin monothread exactement comme avant.
  • L'analyse de répartition dynamique à la fin de l'indexation ignore désormais les passes qui ne peuvent manifestement rien produire pour le projet en cours : pont de re-rendu React lorsqu'aucune classe n'a de méthode render, couplage multiplateforme React Native et Expo lorsque les langages requis ne sont pas présents et liaison du mappeur MyBatis lorsqu'il n'y a pas de mappeur XML. Auparavant, chacun d'eux analysait l'intégralité du graphique avant de se retrouver vide – sur un projet Java de 4 000 fichiers, ce qui représentait environ 0.9 secondes d'analyse perdues par nouvel index. La passe de pontage d'implémentation d'interface est également devenue moins chère sur le travail réel : elle ne récupère plus la liste de méthodes d'une interface hub une fois par implémenteur, et les classes qui étendent ou n'implémentent rien sont ignorées avant toute recherche par classe. Les graphiques restent identiques octet par octet.
  • L'indexation de grandes bases de code C et C++ passe beaucoup moins de temps dans l'analyse de répartition du pointeur de fonction (la passe qui connecte les tables de gestionnaires comme une table de commandes ou une structure d'opérations à leurs sites d'appel) : chaque fichier source est désormais lu et préparé une fois au lieu de quatre fois, les fichiers qui ne peuvent contribuer à aucun câblage de répartition sont carrément ignorés dans les étapes de liaison ultérieures, et sur les plates-formes avec le moteur natif, l'analyse par fichier elle-même s'exécute désormais également de manière native. Sur une arborescence à l'échelle du noyau Linux, la passe s'exécute environ un tiers plus rapidement de bout en bout, avec des graphiques octet par octet identiques ; les plates-formes sans binaire natif conservent les mêmes résultats sur le chemin précédent.

Correctifs

  • Les fichiers TypeScript, TSX et JavaScript sont désormais analysés avec des grammaires à jour — la syntaxe moderne telle que les déclarations using et les attributs d'importation ne déclenche plus les erreurs d'analyse qui pourraient supprimer les symboles environnants. (Les grammaires précédemment regroupées dataient de 2023.)
  • Les fichiers Rust sont également analysés avec une grammaire à jour (la version précédemment fournie datait de 2023), ce qui affine en outre l'attribution des appels de méthode : les appels via les champs de structure sont résolus avec le contexte du récepteur au lieu de revenir à une correspondance ambiguë de noms nus, supprimant une classe de bords d'appels erronés sur des noms communs comme len et start.
  • Les fichiers Ruby sont également analysés avec une grammaire à jour (la version précédemment fournie datait de début 2024), qui corrige une erreur d'analyse des appels de méthode d'opérateur de navigation sécurisée (recv&.!= x) qui avaient enregistré le mauvais nom d'appelé.
  • Les fichiers PHP sont également analysés avec une grammaire à jour maintenant (la version précédemment fournie datait de 2023) : les fichiers utilisant des fonctionnalités PHP modernes - constantes d'énumération, hooks de propriété PHP 8.4, chaînage new X()->method() sans parenthèses - ne rencontrent plus d'erreurs d'analyse ou d'erreurs d'analyse qui ont laissé tomber ou tronqué leurs symboles, donc les bases de code comme Symfony et Laravel indexent beaucoup plus précisément.
  • Les fichiers Swift sont également analysés avec une grammaire à jour (la version précédemment fournie datait de 2023) : les tests rapides de #expect, les macros de style #Preview, le modificateur d'accès package et le throws tapé ne produisent plus d'erreurs d'analyse qui ont laissé tomber les symboles environnants - les projets Swift côté serveur comme Vapor voient la plus grande récupération.
  • La grammaire de Dart est désormais fournie avec CodeGraph lui-même au lieu d'être résolue à partir d'un package tiers dont la version Dart flottait sur une référence en amont non épinglée - une mise à jour de routine des dépendances ne peut plus modifier silencieusement la façon dont les fichiers Dart sont analysés.
  • La recherche ou l'exploration par nom de champ permet désormais de trouver le code qui les définit. Une requête composée de clés d'objet ou de noms de champs API (profileInfo isTrialEligible quotaInfo billingMethod) utilisée pour renvoyer des résultats sans rapport alors que les fichiers de définition n'apparaissaient jamais, car trois étapes de récupération supprimaient chacune des termes camelCase multi-mots : un bug de comparaison de cas interne, une étape de correspondance qui ne prenait en compte que les classes (jamais de fonctions ou de méthodes) et un amorçage d'exploration qui nécessitait des correspondances exactes de nom de symbole. Tous les trois sont corrigés : codegraph_explore avec un ensemble de noms de champs fait désormais apparaître les contrôleurs et les services qui assemblent ces champs. (#1196)
  • Le includeIgnored de codegraph.json fonctionne à nouveau pour la disposition "dossier de dépôts": lorsqu'une règle .gitignore couvre un répertoire parent (/repos/) contenant plusieurs référentiels git intégrés, l'option des dépôts individuels ("includeIgnored": ["repos/a/"] - l'orthographe exacte suggérée par le propre indice de codegraph init) ne correspondait auparavant à rien et n'indexait aucun fichier, vous renvoyant la même suggestion. Les deux orthographes fonctionnent désormais : nommez le répertoire parent pour activer tout ce qu'il contient, ou nommez les dépôts individuels pour activer uniquement ceux-ci - et l'indice ne suggère plus les dépôts déjà configurés. (#1295)
  • Les appels de méthode sur les littéraux (", ".join(...) dans Python, "x".split(...) dans JavaScript, et autres) ne produisent plus de bords d'appel vers des fonctions de projet non liées qui partagent le nom de la fonction intégrée - une base de code avec une fonction appelée join, get ou update pourrait afficher des appelants fantômes pour chaque utilisation de chaîne intégrée. De plus, une fonction imbriquée dans une autre fonction ne correspond désormais qu'à une cible d'appel depuis l'intérieur de son conteneur, car elle n'est accessible nulle part ailleurs. Les résultats du rayon d'explosion et des tests affectés deviennent plus nets sur les bases de code Python et JavaScript en particulier. (#1230)
  • Les appels de méthode Go via un champ de structure (target.conn.Exec(...)) ne se lient plus à des méthodes locales du même nom non liées lorsque le type du champ est externe — les appels conn *sql.DB étaient attribués à une interface locale qui déclarait Exec, fabriquant des dépendances internes. Les appels de champ chaînés sont désormais résolus en déduisant le type déclaré du champ à partir de la définition de la structure : les types dans le projet (y compris ceux non exportés comme le tree *node de chi) obtiennent des bords d'appel corrects et validés qui n'ont jamais existé auparavant, et les types externes (bibliothèque standard, modules tiers) ne sont pas liés au lieu d'être devinés. (#1276)
  • Les appels de méthode TypeScript/JavaScript via un singleton importé (import { store } from './store'; store.notify()) sont désormais résolus en méthode de classe au lieu de la constante exportée, donc codegraph callers voit les appelants inter-fichiers de la méthode — auparavant, seuls les appels du même fichier étaient attribués et une méthode utilisée partout pouvait sembler inutilisée. La même inférence de type basée sur une déclaration s'applique dans tous les langages qui la partagent (Python, Java, Kotlin, Go, etc.), et une inférence échouée conserve l'ancien avantage plutôt que de deviner. (#1292)
  • codegraph node <symbol> -f <file> imprime désormais le corps source du symbole. Épingler un nom ambigu à un fichier spécifique (tout l'intérêt de -f lorsque de nombreux fichiers définissent la même fonction) renvoyait uniquement l'emplacement et la piste de l'appelant sans code. (#1284)
  • La suppression d'un répertoire entier est désormais prise en charge par le mode surveillance : les fichiers qu'il contient sont supprimés de l'index lors de la prochaine synchronisation automatique au lieu de rester en tant qu'enregistrements obsolètes jusqu'à ce qu'une modification sans rapport en déclenche une. Les systèmes d'exploitation signalent souvent une suppression de répertoire comme un événement unique sur le répertoire lui-même (sans aucun événement par fichier pour son contenu), que l'observateur a précédemment ignoré. (#1285)
  • codegraph sync bénéficie désormais du même correctif de disque lent qui a rendu l'indexation complète rapide dans 1.4.0 : le point de contrôle de la base de données est différé pour toute l'exécution incrémentielle au lieu de se déclencher tous les quelques mégaoctets d'écritures. Sur les disques mécaniques et autres stockages à latence élevée, une petite synchronisation sur un index volumineux ne se bloque plus pendant des minutes avec un processeur proche de zéro : le coût d'une synchronisation évolue en fonction de ce qui a changé, et non en fonction de la taille de l'index existant. Le même interrupteur CODEGRAPH_NO_WAL_DEFER=1 l'éteint. (#1248)
  • Les fonctions C déclarées avec une macro d'attribut spécifique au projet devant un type de retour typedef (SEC_ATTR UINT32 MyFunc(VOID) — courant dans le code embarqué et dans le noyau) sont désormais indexées sous leurs vrais noms. Auparavant, l'analyseur trébuchait sur la macro inconnue et stockait la liste de paramètres comme nom de fonction, laissant des entrées comme "(VOID)" dans le graphique et rendant la fonction réelle introuvable. (#1211)
  • Les codes C et C++ riches en macros indexent beaucoup plus complètement. Quinze idiomes omniprésents qui déclenchaient auparavant l'analyseur en récupération d'erreur - suppression de symboles, confusion de noms, création d'entrées fantômes ou perte des relations entre les vraies - sont désormais analysés proprement : la protection de compatibilité #ifdef __cplusplus / extern "C" { dans les en-têtes C, les macros d'itérateur en position d'instruction (list_for_each_entry(pos, head, member) { … } et toute la famille Linux-kernel/git/jemalloc - y compris les appels qui s'étendent sur plusieurs lignes, comme hlist_for_each_entry_rcu(…) avec un argument lockdep_is_held), les annotations de déclaration Linux/sparse (static int __init foo(void), void __user *buf, container_of(p, struct T, m)), les annotations paramétrées (__free(kfree), __printf(4, 0), __counted_by(count)), les macros de déclaration par CPU et par file d'attente de travail (static DEFINE_PER_CPU(struct T, name);, formulaires initialisés inclus), les arguments de type nu pour les macros d'allocation et de liste (kzalloc_obj(struct T), list_entry(p, struct T, member)), va_arg avec un type qualifié ou pointeur, définitions de macros variadiques nommées GNU (#define dbg(fmt, args...)), marqueurs de compilateur de style static notrace, déclarations C23 auto, annotations de paramètres de fin (int argc UNUSED, style maison de git), macros de gestion d'espace de noms seules sur une ligne (FMT_BEGIN_NAMESPACE, Q_OBJECT de Qt) et macros d'attributs de fonction dans devant les types de retour C++. Sur le noyau Linux, cela réduit de près de moitié les fichiers perdus lors de l'analyse des erreurs dans les répertoires principaux et récupère des milliers de relations d'appel et de référence que la récupération d'erreur a silencieusement abandonnées, git et redis voyant des coupes plus petites du même type ; les graphiques restent identiques octet par octet entre les moteurs natifs et de secours. Un correctif associé empêche la gestion des macros elle-même de corrompre les lignes #define qui mentionnent les mêmes noms de macro, ce qui a supprimé une classe d'erreurs d'analyse fantôme dans les en-têtes de style fmt.
  • Les méthodes C++ définies hors ligne dans un espace de noms (namespace sim { Output MyClass::Apply(...) { ... } }) portent désormais l'espace de noms dans leur nom qualifié, correspondant à leur classe. Les sites d'appels pleinement qualifiés provenant d'autres fichiers (sim::MyClass::Apply(...)) sont à nouveau résolus selon la définition, donc codegraph callers et l'impact sur le fichier ne sont plus vides pour ce modèle. (#1291)
  • Les méthodes C++ définies hors ligne sur une classe modèle (template <typename T> T Box<T>::get() { ... }) ne conservent plus la liste des paramètres du modèle dans leur nom qualifié. Ils sont désormais indexés sous la forme Box::get – identique à une définition en ligne de la même méthode – afin qu'ils soient liés à leur classe et résolus à nouveau à partir des sites d'appel, et les listes de paramètres de modèle multilignes pathologiques ne peuvent plus faire dépasser le nom qualifié au-delà des limites de nom du système de fichiers. (#1286)
  • La détection de route Go n'identifie plus à tort les appels de méthode ordinaires partageant des noms de verbes HTTP : cache.Put("key", value), store.Get("config", out), bus.Handle("user.created", handler) et autres étaient indexés en tant que routes HTTP, polluant les listes de routes dans des bases de code lourdes en cache. Une inscription doit désormais ressembler à une telle : son premier argument doit être un chemin préfixé par / (tous les routeurs) ou un modèle Go 1.22 "METHOD /path" sur Handle/HandleFunc, qui extrait désormais également la méthode au lieu de lister la route comme ANY. (#1259)
  • La sortie Progress sous Windows ne mélange plus les rails ASCII | avec le cadre Unicode │ ◆ ● qui les entoure. Dans les terminaux qui affichent Unicode (Windows Terminal, VS Code, ConEmu/Cmder, JetBrains, Alacritty), l'ensemble du bloc codegraph init / index / sync est désormais dessiné avec des caractères de dessin de boîte correspondants ; les anciennes consoles non reconnues conservent la sortie sécurisée entièrement ASCII qui évite les caractères tronqués. CODEGRAPH_ASCII=1 / CODEGRAPH_UNICODE=1 sont toujours prioritaires dans les deux sens. (#398)
  • La sortie CLI respecte désormais la convention NO_COLOR et les nouveaux indicateurs --color / --no-color, et s'affiche automatiquement lorsqu'elle est redirigée : les commandes comme codegraph status, query, callers et files n'intègrent plus les codes de couleur ANSI lorsque la sortie standard n'est pas un terminal, et un codegraph init / index redirigé / sync imprime des lignes simples par phase au lieu de caractères de contrôle d'animation de progression. FORCE_COLOR ou --color force le rétablissement de la couleur pour les tuyaux qui la restituent. (#1281)
  • Les appelants et l'analyse d'impact ne sous-estiment plus silencieusement une fonction qui appelle plusieurs fois le même appelé. Lorsqu'un appelant contenait plusieurs sites d'appel au même appelé et qu'une limite de lot de résolution interne les divisait, le nettoyage après le premier lot supprimait les lignes en attente des sites ultérieurs avant même qu'elles ne soient tentées - leurs bords n'ont jamais été créés, de manière déterministe, et les bords manquants ont été décalés avec des modifications sans rapport avec le nombre total de références du projet. Le nettoyage après passage cible désormais la ligne exacte de la base de données d’où provient chaque référence traitée. Trouvé lors de la validation du correctif d'appel de l'opérateur sur nlohmann/json, où les 11 appels de write_cbor à to_char_type étaient indexés à 10. (#1269)
  • Les appels d'opérateur explicites C++ — a.operator+(b), p->operator+(b), a.operator[](3) et les autres formes symboliques — produisent désormais un avantage calls dans la méthode d'opérateur, de sorte qu'un opérateur invoqué uniquement via la syntaxe explicite ne semble plus ignoré dans les appelants et l'analyse d'impact. tree-sitter analyse ces sites d'appel avec le nom de l'opérateur bloqué dans un nœud d'erreur (jamais en tant qu'accès membre normal), de sorte que la cible de l'appel a été lue silencieusement comme simplement la variable du récepteur ; le nom de l'opérateur est maintenant récupéré à partir du nœud d'erreur et résolu via une inférence de type récepteur comme tout autre appel de membre - un opérateur du même nom sur une classe non liée ne pourra jamais capturer le bord. Les utilisations d'Infix (a + b, a[i]) nécessitent une inférence de type réel et sont suivies séparément. (#1247)
  • codegraph init et codegraph index ne semblent plus bloqués une fois que « Résolution des références » atteint 100 %. La liaison de répartition dynamique qui s'exécute après la résolution (rappels, rendus React, pointeurs de fonction C et le reste) n'avait aucun affichage de progression, donc sur les dépôts où cela prend un certain temps - en particulier les grandes bases de code C - la barre est restée gelée à 100% jusqu'à ce qu'elle soit terminée. Ce travail apparaît désormais comme sa propre phase de progression « Liaison dynamique de répartition », et la passe la plus lourde – liaison fonction C-pointeur – rapporte en outre la progression au sein de la passe, de sorte qu'une grande base de code C fait avancer la barre en douceur au lieu de la garer sur un numéro pendant la majeure partie de la phase.
  • L'indexation n'imprime plus les avertissements répétés "SQLite est une fonctionnalité expérimentale" qui tronquaient l'affichage de la progression. L'avertissement provient du SQLite intégré de Node et est déclenché une fois par travailleur d'analyse ; il est désormais supprimé sur chaque chemin de lancement.

codegraph v1.5.0

[1.5.0] - 2026-07-21

⚡ The Rust engine release — with near-instant sync

This release rebuilds CodeGraph's parsing engine as a native Rust kernel, overhauls the resolution pipeline around it, and makes the live graph effectively instant: a save now reaches the graph in well under a second, even on a 27,000-file repository. It is the largest performance upgrade in the project's history — and every graph is verified byte-for-byte identical to the previous engine.

  • Native Rust parsing for 20 languages — TypeScript, JavaScript (+TSX/JSX), Java, Python, Go, C, C++, Rust, C#, Ruby, PHP, Swift, Kotlin, Scala, Dart, R, Lua, and Luau now parse in a compiled Rust kernel (Metal and CUDA ride the C++ path). Platforms without a prebuilt binary, and individual files with syntax errors, fall back to the previous engine automatically — same graph either way, proven on repositories from small libraries to the Linux kernel.
  • Adaptive to your machine — CodeGraph sizes its parse workers, resolver pool, and caches from what the system actually has: real core counts (container/cgroup-aware, not the host's), honest available memory on macOS and Linux, and measured per-project resolution cost. A big workstation gets the full parallel pipeline; a 2-core VPS gets a pipeline tuned to finish reliably instead of running out of memory — the Linux kernel (70k files) indexes to completion on a 2-core, 6GB machine in under 12 minutes — down from 26 at the start of this cycle.
  • Resolution is dramatically faster across the board — adaptive parallel resolution, smarter method-candidate lookup, and memoized supertype/conformance walking. The Swift compiler repository (27k files, Swift + C++) went from over 3 minutes to about 100 seconds within this release cycle; Rust, Lua, and Java-family projects all see double-digit improvements.
  • Sync is now near-instant — a save reaches the graph in well under a second, even at compiler scale. The always-on watcher fires after a 300ms quiet window for lone saves (bursts of edits still coalesce), and hands the exact changed paths to sync instead of re-scanning the whole tree — measured save-to-fresh-graph work of ~0.3s on a 4,400-file Java project and ~0.4s on the 27,000-file Swift compiler repository, byte-identical to a full reconciliation.

Full details in the entries below.

New Features

  • Indexing TypeScript, TSX, JavaScript, JSX, Java, Python, Go, C, C++, Rust, C#, Ruby, PHP, Swift, Kotlin, Scala, Dart, R, Lua, and Luau projects is faster: parsing and symbol extraction now run in a native engine when a prebuilt binary is available for your platform (release bundles include one), producing exactly the same graph — verified byte-for-byte against the previous engine on real repositories, from small libraries up to vscode-, dubbo-, django-, git-, protobuf-, tokio-, rust-analyzer-, jellyfin-, rails-, symfony-, swift-nio-, kotlinx.coroutines-, ggplot2-, Kong-, Scala-3-compiler-, and Flutter-scale codebases (Lombok-generated members, C function-pointer tables, and Unreal-Engine-style macro-heavy headers included; CUDA and Metal sources ride the C++ path). The speedup is largest on resource-constrained machines like CI runners. No setup needed: platforms without the native binary, and individual files with syntax errors, automatically use the previous engine, and CODEGRAPH_KERNEL=0 turns the native path off entirely.
  • Reference resolution now runs in parallel on large projects. When a project has enough pending references to make it worthwhile (roughly 150k+, typical for big Java/Kotlin/Spring codebases), resolution fans out across worker threads while results are applied in the exact order the single-threaded path would have used — the graph comes out byte-for-byte identical, about twice as fast end-to-end on a 4,000-file Java project in our testing. Small projects keep the single-threaded path automatically (the fan-out costs more than it saves there). Set CODEGRAPH_NO_PARALLEL_RESOLVE=1 to disable, or CODEGRAPH_PARALLEL_RESOLVE_MIN=<count> to tune when it engages.
  • Indexing large projects got another sizeable speedup — about a quarter less wall-clock on the same 4,000-file Java project, with the graph still byte-for-byte identical. Two changes: the database no longer interleaves expensive checkpoint housekeeping into the middle of resolution on a fresh index (it's folded once at the end instead), and while one batch's results are being written out, the worker threads are already resolving the next batch instead of sitting idle.
  • The dynamic-dispatch analysis that runs at the end of indexing (callback, event, and framework wiring) now runs its passes in parallel on large projects, cutting that stage roughly in half there — and a pass that crashes now retries safely instead of failing the whole index, which also makes very large codebases that previously died in this stage more likely to index to completion. Graphs remain byte-for-byte identical.
  • On large projects, indexing writes its relationship data noticeably faster: secondary database indexes are set aside during the bulk of reference resolution and rebuilt once at the end, instead of being maintained row by row. Graphs remain byte-for-byte identical, and small projects are unaffected.
  • Very-large-codebase reliability: on multi-million-symbol projects, an analysis pass that fails on a worker thread is now skipped with a clear message instead of being retried in a way that could take down the whole index, and the end-of-indexing index rebuild no longer risks tripping the liveness watchdog on huge graphs. Validated end-to-end on the Linux kernel (70k files, 2M symbols, 6.4M relationships) — it now indexes to completion even on a 2-core machine.
  • Indexing is significantly faster — a fresh codegraph init on a medium TypeScript project takes about a third less wall-clock time, with the same graph produced byte-for-byte. The gains come from batching database writes, storing files on a dedicated writer thread, memoizing repeated import-resolution lookups, skipping per-row search-index maintenance during the bulk build (rebuilt once at the end), and — on completely fresh databases only — deferring disk durability until the index completes, since an interrupted first index is simply re-run. Set CODEGRAPH_NO_FAST_INIT=1 to keep full crash-durability during the initial build, or CODEGRAPH_NO_STORE_WORKER=1 to store on the main thread.
  • codegraph install and codegraph upgrade now offer CodeGraph Pro beta access after finishing — answer yes, type your email, and you join the same waitlist as the getcodegraph.com homepage form. Strictly opt-in and asked at most once per machine total: nothing is sent unless you say yes and enter an email, either answer is remembered so no later install or upgrade ever re-asks, and non-interactive runs (--yes, scripts, CI) never see the question.
  • Every release is now cryptographically verifiable: npm packages publish with npm provenance (the "Provenance" badge on npmjs.com, proving each version was built by this repository's release workflow from a specific commit), and the GitHub Release bundles carry signed build attestations you can check with gh attestation verify <file> -R colbymchenry/codegraph.
  • Indexing inside CPU- or memory-limited containers (Docker, CI runners) now sizes its worker pools from the container's actual allowance instead of the host machine's, and giant codebases no longer balloon temporary database files during indexing (previously tens of GB of transient disk on Linux-kernel-scale projects). Together these prevent out-of-memory and out-of-disk failures on constrained machines; set CODEGRAPH_RESOLVE_WORKERS to override the resolution worker count explicitly.
  • Indexing very large projects on multi-core machines got faster again: the parallel-resolution workers now periodically refresh their read-only database connections, which lets database housekeeping advance instead of silently building up a backlog behind long-lived readers — a backlog that was taxing the indexer's own writes. Graphs remain byte-for-byte identical; the win is largest at Linux-kernel scale on many-core machines.
  • Indexing on macOS now uses the machine's real memory headroom when sizing its parallel-resolution workers. macOS deliberately keeps RAM filled with reclaimable cache, so the previous free-memory reading came back tiny (~1GB on an otherwise idle machine) and silently halved the worker pool — a medium Java project's fresh index ran about 15–20% slower than the hardware allowed. Graphs remain byte-for-byte identical; the same fix also lets a memory-driven analysis cache engage fully on macOS for large C codebases.
  • Fresh indexing got a sizeable across-the-board speedup: during the initial build, the database's secondary lookup indexes are set aside and rebuilt once after parsing instead of being maintained row by row — the same proven trick the later linking phase already used, now applied to the whole parse lane — and the reference-resolution loop likewise stops maintaining lookup indexes it never reads, rebuilding them at the end when almost nothing is left in the table. A medium Java project's parse phase runs about 58% faster and its full fresh index about 19% faster end-to-end; a Linux-kernel-scale index that took ~15 minutes on an 8-core machine now completes in about 11, with the resolution phase alone dropping by a third. Graphs remain byte-for-byte identical, and incremental syncs are unaffected.
  • Saving a file now updates the graph almost immediately: the file watcher fires after a 300ms quiet window for one or two changed files (bursts still coalesce under the full debounce, and CODEGRAPH_WATCH_DEBOUNCE_MS remains the upper bound), and watcher-triggered syncs reconcile exactly the changed paths instead of stat-walking the entire repository. Directory deletions and event storms still run the full scan-diff, so nothing the events can't describe is ever missed. Measured: save-to-fresh-graph sync work drops to ~0.3s on a 4,400-file project and ~0.4s on a 27,000-file one, with resulting graphs byte-for-byte identical to a full reconciliation.
  • Indexing Swift and other protocol/interface-heavy codebases got dramatically faster: the conformance walk that checks whether a method lives on a receiver's supertypes (protocols, base classes, extensions) now remembers its answers for the duration of each resolution batch instead of re-querying the graph for every call site — on the Swift compiler repository (27k files) that walk ran nearly a million times per index. A fresh index of that repo drops from about 185 seconds to under 100, with the graph byte-for-byte identical. Method-candidate lookup also gained a per-name owner index, so overload-heavy names (init in Swift, execute in Java) no longer pay a full candidate scan per receiver type.
  • Resolving method calls through local variables (recv.method(), Lua's recv:method(), R's recv$method()) got much cheaper on repos where the same receiver is called over and over: the declaration scan that types the receiver now remembers what it has already scanned per scope instead of re-reading the same source lines for every call site, and the regex patterns it scans with are compiled once per receiver instead of per call. Kong's fresh index drops another 8% on top of the require-resolution fix (23% cumulative), with graphs byte-for-byte identical everywhere — including Java projects, where this same scan successfully types tens of thousands of receivers.
  • Indexing Lua and Luau projects got a sizeable speedup: resolving each require(...) no longer rescans the project's entire file list four times — a per-project filename index answers the same lookup instantly, cutting per-require resolution from about a millisecond to microseconds. A fresh index of Kong (1,870 Lua files) runs about 16% faster end-to-end, with the graph byte-for-byte identical. The same housekeeping also closes a latent staleness edge where COBOL copybook lookups could keep serving a cached file list after files changed.
  • Parallel reference resolution now engages adaptively instead of by a fixed project-size cutoff: the indexer measures the actual per-reference resolution rate on the first batch and spins up the worker pool mid-run whenever the remaining work justifies it. Languages whose references are expensive to resolve benefit most — Rust especially: a fresh index of tokio runs about 23% faster, with the graph byte-for-byte identical. Small projects and low-core machines (2-core CI runners) keep the single-threaded path exactly as before.
  • The dynamic-dispatch analysis at the end of indexing now skips passes that provably can't produce anything for the project at hand: React re-render bridging when no class has a render method, React Native and Expo cross-platform pairing when the required languages aren't present, and MyBatis mapper linking when there's no mapper XML. Previously each of these scanned the whole graph before coming up empty — on a 4,000-file Java project that was about 0.9 seconds of wasted analysis per fresh index. The interface-implementation bridging pass also got cheaper on real work: it no longer re-fetches a hub interface's method list once per implementer, and classes that extend or implement nothing are skipped before any per-class lookups. Graphs remain byte-for-byte identical.
  • Indexing large C and C++ codebases spends much less time in the function-pointer dispatch analysis (the pass that connects handler tables like a command table or an ops struct to their call sites): each source file is now read and prepared once instead of four times, files that can't contribute any dispatch wiring are skipped outright in the later linking steps, and on platforms with the native engine the per-file scanning itself now runs natively too. On a Linux-kernel-scale tree the pass runs about a third faster end-to-end, with graphs byte-for-byte identical; platforms without a native binary keep the same results on the previous path.

Fixes

  • TypeScript, TSX, and JavaScript files now parse with up-to-date grammars — modern syntax such as using declarations and import attributes no longer trips parse errors that could drop surrounding symbols. (The previously bundled grammars dated from 2023.)
  • Rust files also parse with an up-to-date grammar now (the previously bundled build dated from 2023), which additionally sharpens method-call attribution: calls through struct fields resolve with receiver context instead of falling back to ambiguous bare-name matching, removing a class of wrong call edges on common names like len and start.
  • Ruby files also parse with an up-to-date grammar now (the previously bundled build dated from early 2024), which fixes a misparse of safe-navigation operator-method calls (recv&.!= x) that had recorded the wrong callee name.
  • PHP files also parse with an up-to-date grammar now (the previously bundled build dated from 2023): files using modern PHP features — enum constants, PHP 8.4 property hooks, parenthesis-free new X()->method() chaining — no longer hit parse errors or misparses that dropped or garbled their symbols, so codebases like Symfony and Laravel index substantially more accurately.
  • Swift files also parse with an up-to-date grammar now (the previously bundled build dated from 2023): swift-testing #expect, #Preview-style macros, the package access modifier, and typed throws no longer produce parse errors that dropped surrounding symbols — server-side Swift projects like Vapor see the biggest recovery.
  • Dart's grammar is now bundled with CodeGraph itself instead of being resolved from a third-party package whose Dart build floated on an unpinned upstream reference — a routine dependency update can no longer silently change how Dart files parse.
  • Searching or exploring by field names now finds the code that defines them. A query made of object keys or API field names (profileInfo isTrialEligible quotaInfo billingMethod) used to return unrelated results while the defining files never appeared, because three retrieval steps each dropped multi-word camelCase terms: an internal case-comparison bug, a match step that only considered classes (never functions or methods), and exploration seeding that required exact symbol-name matches. All three are fixed — codegraph_explore with a bag of field names now surfaces the controllers and services that assemble those fields. (#1196)
  • codegraph.json's includeIgnored works again for the "folder of repos" layout: when one .gitignore rule covers a parent directory (/repos/) holding several embedded git repositories, opting in the individual repos ("includeIgnored": ["repos/a/"] — the exact spelling codegraph init's own hint suggests) previously matched nothing and indexed zero files, looping the same suggestion back at you. Both spellings now work — name the parent directory to opt in everything under it, or name individual repos to opt in just those — and the hint no longer re-suggests repos that are already configured. (#1295)
  • Method calls on literals (", ".join(...) in Python, "x".split(...) in JavaScript, and the like) no longer produce call edges to unrelated project functions that happen to share the builtin's name — a codebase with a function called join, get, or update could show phantom callers from every string-builtin use. Additionally, a function nested inside another function is now only matched as a call target from inside its container, since it isn't reachable from anywhere else. Blast-radius and affected-test results get cleaner on Python and JavaScript codebases especially. (#1230)
  • Go method calls through a struct field (target.conn.Exec(...)) no longer bind to unrelated same-named local methods when the field's type is external — conn *sql.DB calls were being attributed to a local interface that happened to declare Exec, fabricating internal dependencies. Chained field calls now resolve by inferring the field's declared type from the struct definition: in-project types (including unexported ones like chi's tree *node) gain correct, validated call edges that never existed before, and external types (standard library, third-party modules) are left unlinked instead of guessed. (#1276)
  • TypeScript/JavaScript method calls through an imported singleton (import { store } from './store'; store.notify()) now resolve to the class method instead of the exported constant, so codegraph callers sees cross-file callers of the method — previously only same-file calls were attributed and a method used everywhere could look unused. The same declaration-based type inference applies across the languages that share it (Python, Java, Kotlin, Go, and more), and a failed inference keeps the old edge rather than guessing. (#1292)
  • codegraph node <symbol> -f <file> now prints the symbol's source body. Pinning an ambiguous name to a specific file (the whole point of -f when many files define the same function) returned only the location and caller trail with no code. (#1284)
  • Deleting a whole directory is now picked up by watch mode: the files inside it are removed from the index on the next auto-sync instead of lingering as stale records until an unrelated edit happened to trigger one. Operating systems often report a directory deletion as a single event on the directory itself (with no per-file events for its contents), which the watcher previously discarded. (#1285)
  • codegraph sync now gets the same slow-disk fix that made full indexing fast in 1.4.0: database checkpointing is deferred for the whole incremental run instead of firing every few megabytes of writes. On mechanical drives and other high-latency storage, a small sync on a large index no longer stalls for minutes at near-zero CPU — the cost of a sync scales with what changed, not with the size of the existing index. The same CODEGRAPH_NO_WAL_DEFER=1 switch turns it off. (#1248)
  • C functions declared with a project-specific attribute macro in front of a typedef'd return type (SEC_ATTR UINT32 MyFunc(VOID) — common in embedded and kernel code) are now indexed under their real names. Previously the parser tripped over the unknown macro and stored the parameter list as the function name, leaving entries like "(VOID)" in the graph and making the real function unfindable. (#1211)
  • Macro-heavy C and C++ code indexes much more completely. Fifteen ubiquitous idioms that previously tripped the parser into error recovery — dropping symbols, garbling names, minting phantom entries, or losing the relationships between real ones — now parse cleanly: the #ifdef __cplusplus / extern "C" { compatibility guard in C headers, iterator macros in statement position (list_for_each_entry(pos, head, member) { … } and the whole Linux-kernel/git/jemalloc family — including calls that wrap across lines, like hlist_for_each_entry_rcu(…) with a lockdep_is_held argument), the Linux/sparse declaration annotations (static int __init foo(void), void __user *buf, container_of(p, struct T, m)), parameterized annotations (__free(kfree), __printf(4, 0), __counted_by(count)), per-CPU and work-queue declaration macros (static DEFINE_PER_CPU(struct T, name);, initialized forms included), bare type arguments to allocator and list macros (kzalloc_obj(struct T), list_entry(p, struct T, member)), va_arg with a qualified or pointer type, GNU named-variadic macro definitions (#define dbg(fmt, args...)), static notrace-style compiler markers, C23 auto declarations, trailing parameter annotations (int argc UNUSED, git's house style), namespace-management macros alone on a line (FMT_BEGIN_NAMESPACE, Qt's Q_OBJECT), and function attribute macros in front of C++ return types. On the Linux kernel this cuts files lost to parse errors on the core directories by nearly half and recovers thousands of call and reference relationships that error recovery silently dropped, with git and redis seeing smaller cuts of the same kind; graphs stay byte-for-byte identical between the native and fallback engines. A related fix stops the macro handling itself from corrupting #define lines that mention the same macro names, which removed a class of phantom parse errors in fmt-style headers.
  • C++ methods defined out-of-line inside a namespace (namespace sim { Output MyClass::Apply(...) { ... } }) now carry the namespace in their qualified name, matching their class. Fully-qualified call sites from other files (sim::MyClass::Apply(...)) resolve to the definition again, so codegraph callers and file impact no longer come up empty for this pattern. (#1291)
  • C++ methods defined out-of-line on a template class (template <typename T> T Box<T>::get() { ... }) no longer keep the template parameter list in their qualified name. They now index as Box::get — identical to an inline definition of the same method — so they link to their class and resolve from call sites again, and pathological multi-line template parameter lists can no longer blow the qualified name past filesystem name limits. (#1286)
  • Go route detection no longer misidentifies ordinary method calls that share HTTP verb names — cache.Put("key", value), store.Get("config", out), bus.Handle("user.created", handler) and the like were being indexed as HTTP routes, polluting route listings in cache-heavy codebases. A registration now has to look like one: its first argument must be a /-prefixed path (all routers) or a Go 1.22 "METHOD /path" pattern on Handle/HandleFunc, which now also extracts the method instead of listing the route as ANY. (#1259)
  • Progress output on Windows no longer mixes ASCII | rails with the Unicode │ ◆ ● frame around them. In terminals that render Unicode (Windows Terminal, VS Code, ConEmu/Cmder, JetBrains, Alacritty), the whole codegraph init / index / sync block now draws with matching box-drawing characters; unrecognized legacy consoles keep the safe all-ASCII output that avoids garbled characters. CODEGRAPH_ASCII=1 / CODEGRAPH_UNICODE=1 still override in either direction. (#398)
  • CLI output now honors the NO_COLOR convention and new --color / --no-color flags, and goes plain automatically when piped: commands like codegraph status, query, callers, and files no longer embed ANSI color codes when stdout isn't a terminal, and a piped codegraph init / index / sync prints simple per-phase lines instead of progress-animation control characters. FORCE_COLOR or --color forces color back on for pipes that render it. (#1281)
  • Callers and impact analysis no longer silently under-count a function that calls the same callee many times. When one caller contained several call sites to the same callee and an internal resolution batch boundary happened to split them, cleanup after the first batch removed the later sites' pending rows before they were ever attempted — their edges were never created, deterministically, and which edges went missing shifted with unrelated changes to the project's total reference count. Post-pass cleanup now targets the exact database row each processed reference came from. Found while validating the operator-call fix on nlohmann/json, where write_cbor's 11 calls to to_char_type indexed as 10. (#1269)
  • C++ explicit operator calls — a.operator+(b), p->operator+(b), a.operator[](3), and the other symbolic forms — now produce a calls edge to the operator method, so an operator invoked only through the explicit syntax no longer looks uncalled in callers and impact analysis. tree-sitter parses these call sites with the operator name stranded in an error node (never as a normal member access), so the call's target was silently read as just the receiver variable; the operator name is now recovered from the error node and resolved through receiver-type inference like any other member call — a same-named operator on an unrelated class can never capture the edge. Infix uses (a + b, a[i]) need real type inference and are tracked separately. (#1247)
  • codegraph init and codegraph index no longer look hung after "Resolving refs" reaches 100%. The dynamic-dispatch linking that runs after resolution (callbacks, React re-renders, C function pointers, and the rest) had no progress display, so on repos where it takes a while — large C codebases especially — the bar just sat frozen at 100% until it finished. That work now shows as its own "Linking dynamic dispatch" progress phase, and the heaviest pass — C function-pointer linking — additionally reports progress within the pass, so a large C codebase advances the bar smoothly instead of parking it on one number for the bulk of the phase.
  • Indexing no longer prints repeated "SQLite is an experimental feature" warnings that garbled the progress display. The warning comes from Node's built-in SQLite and fired once per parsing worker; it's now suppressed on every launch path.
