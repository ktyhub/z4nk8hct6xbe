codegraphe v1.1.0

[1.1.0] - 2026-06-23

Nouvelles fonctionnalités

  • Claude Code : un crochet de chargement frontal en option permet à votre agent d'accéder automatiquement à CodeGraph. Lorsque vous posez une question structurelle : « comment fonctionne X », « qu'est-ce qui appelle Y », « tracez le flux de A à B » - CodeGraph injecte la source appropriée et les chemins d'appel dans l'invite dès le départ, de sorte que l'agent répond à partir du graphique au lieu de chercher à le reconstruire. Vous êtes invité pendant codegraph install (oui par défaut ; code Claude uniquement, puisqu'il s'agit de l'agent avec des hooks d'invite), il est supprimé par codegraph uninstall et codegraph upgrade l'active pour les configurations Claude existantes. Il est strictement additif et dégradable (les invites non structurelles et les projets non indexés sont laissés seuls) et vous pouvez le désactiver à tout moment sans le désinstaller en configurant CODEGRAPH_NO_PROMPT_HOOK=1.
  • Les actions, mutations et getters de Vue Store sont désormais indexés sous forme de symboles que vous pouvez trouver et lire. Que votre boutique soit Vuex (objets mutations / actions dans un module) ou Pinia — à la fois le formulaire d'options (defineStore({ actions: { … } })) et le formulaire de configuration (defineStore('id', () => { … }), où les actions sont des fonctions locales) — chaque action, mutation et getter est désormais un véritable nœud. Ainsi, codegraph search trouve login ou getSessionList, et codegraph_explore / codegraph_node affiche son corps et ce qu'il appelle, au lieu de "introuvable", car la fonction n'existait qu'en tant que propriété littérale d'objet.
  • codegraph_explore connecte désormais un composant Vue à l'action de magasin Pinia qu'il appelle. Lorsque le code exécute const store = useUserStore() puis store.fetchUser(), cet appel est désormais lié à l'action fetchUser dans le module de magasin - alors "que se passe-t-il lorsque cette vue charge ses données ?" traces du composant dans le corps de l'action au lieu de s'arrêter à la ligne store.fetchUser(). Fonctionne pour les deux styles de magasin Pinia (options et configuration) et reste précis (une méthode intégrée comme store.$patch() ou une méthode du même nom sans rapport n'est pas mal liée).
  • codegraph_explore suit désormais l'envoi de chaînes Vuex. Un appel dispatch('user/login') ou commit('SET_TOKEN') - clés 'module/action' avec espace de noms incluses - est désormais lié à l'action ou à la mutation qu'il nomme, résolu vers le module de magasin correct même lorsque plusieurs modules partagent un nom d'action (et sans être trompé par un assistant api/ du même nom). Alors « qu'est-ce qui s'exécute lorsque cela est envoyé ? » traces depuis l'appel vers le gestionnaire de magasin et jusqu'aux mutations qu'il commet. La forme canonique du module export default { namespaced, actions, mutations } de Vuex est désormais également indexée, de sorte que ces gestionnaires sont des symboles trouvables.
  • codegraph_explore connecte désormais les flux de récupération de données React construits sur RTK Query (createApi de Redux Toolkit). Un point de terminaison défini dans createApi({ endpoints }) et le hook useGetXQuery / useUpdateYMutation qu'il génère étaient tous deux invisibles à l'analyse - alors "que récupère ce composant ?" ou "Où le useGetThingQuery obtient-il ses données ?" dans une impasse, car le hook, le point final et le composant n'avaient rien qui les liait. CodeGraph indexe désormais chaque point de terminaison et chaque hook généré en tant que symboles réels et câble le chemin component → useGetXQuery → getX → queryFn, de sorte que le flux se résout en un seul appel d'exploration au lieu de lire la tranche API à la main. Les styles de flèche (endpoints: build => ({ … })) et de méthode (endpoints(builder) { return { … } }) sont reconnus, ainsi que la variante useLazyGetXQuery ; les crochets manuscrits d’un nom similaire sont laissés intacts.
  • codegraph_explore suit désormais la répartition des tâches Céleri dans Python. Un appel send_email.delay(...) ou send_email.apply_async(...) est désormais lié à la fonction @shared_task / @app.task qu'il exécute - généralement définie dans un module différent (tasks.py) à partir duquel il est déclenché (une vue ou un service) - donc "que se passe-t-il réellement lorsque cela est distribué ?" les traces du site d'appel directement dans le corps de la tâche au lieu de s'arrêter à la ligne .delay(). Les deux dialectes de décorateur sont reconnus (@shared_task nu et la forme argumentée @app.task(bind=True, …)), y compris le style d'appel tasks.invalidate_cache.apply_async() qualifié par le module. Cela reste précis : un .delay() sur quelque chose qui n'est pas une tâche Celery n'est jamais mal lié, donc un projet qui n'utilise pas Celery n'est pas affecté.
  • codegraph_explore suit désormais les événements d'application Spring en Java. Un appel publishEvent(new OrderShippedEvent(...)) est désormais lié à chaque @EventListener qui gère cet événement – ​​généralement dans une classe différente – alors « qu'est-ce qui réagit lorsque cela est publié ? des traces de l'éditeur directement dans chaque méthode d'écoute au lieu d'une impasse à publishEvent(...). Le lien se fait par type d'événement, et tous les styles d'écoute courants sont reconnus : un @EventListener tapé sur son paramètre, la forme @EventListener(SomeEvent.class), @TransactionalEventListener, et l'ancien implements ApplicationListener<SomeEvent>. Un événement se diffuse à tous ses auditeurs, et une application Spring simple sans bus d'événements n'est pas affectée.
  • codegraph_explore suit désormais l'envoi des requêtes et des notifications MediatR en C#/.NET. Un appel _mediator.Send(command) ou _mediator.Publish(notification) est désormais lié à la méthode Handle du IRequestHandler<> / INotificationHandler<> correspondant — généralement dans un fichier différent dans une mise en page Clean Architecture — donc « qu'est-ce qui gère cette commande ? les traces du contrôleur directement dans le gestionnaire au lieu de s'arrêter à l'appel du médiateur. Le type envoyé est reconnu, qu'il soit construit en ligne (Send(new GetFooQuery())), intégré dans un premier local (var cmd = new …; Send(cmd)) ou transmis en tant que paramètre, et il correspond par type - donc un MessagingCenter.Send(...) ou un DTO du même nom qui n'est pas une requête n'est jamais mal lié, et un projet sans MediatR n'est pas affecté.
  • codegraph_explore suit désormais la répartition des tâches en arrière-plan Sidekiq dans Ruby. Un appel DestroyUserWorker.perform_async(id) (ou .perform_in / .perform_at) est désormais lié à la méthode perform de ce travailleur - généralement dans app/workers/, loin du contrôleur ou du modèle qui le met en file d'attente - donc "qu'est-ce qui s'exécute en arrière-plan ici ?" traces de la mise en file d'attente directement dans le corps du travail. Le include Sidekiq::Job moderne et l'ancien Sidekiq::Worker sont reconnus, les travailleurs à espace de noms se résolvent dans la bonne classe même lorsque plusieurs partagent un nom (par exemple Comments::NotifyWorker vs Articles::NotifyWorker), et le perform_later de Rails ActiveJob - un mécanisme différent - est intentionnellement laissé seul.
  • codegraph_explore suit désormais les événements Laravel en PHP. Un appel event(new OrderShipped($order)) est désormais lié à chaque écouteur qui le gère – la méthode handle() de chaque écouteur, généralement une classe app/Listeners/ distincte – donc « qu'est-ce qui réagit à cet événement ? des traces depuis l'envoi jusque dans les corps des auditeurs. Les auditeurs sont trouvés des deux manières par Laravel les enregistre : par un handle(OrderShipped $event) typé (découverte automatique, y compris une union handle(A|B $event) qui écoute deux événements) et par la carte protected $listen dans votre EventServiceProvider (qui attrape également un auditeur dont handle() n'a pas d'indice de type). Un événement est diffusé à tous ses auditeurs, et les tâches en file d'attente – distribuées via ::dispatch() plutôt que event() – sont correctement laissées de côté.
  • CodeGraph comprend désormais les méthodes générées par Lombok en Java. @Getter, @Setter, @Data, @Value et @Builder génèrent des getters, des setters, builder(), equals/hashCode/toString et le champ @Slf4j log au moment de la compilation, de sorte que ces méthodes n'apparaissent jamais dans la source - et un user.getName(), User.builder() ou L'appel log.info(...) était utilisé pour résoudre le problème, interrompant silencieusement l'analyse de la chaîne d'appels (l'agent concluait que la méthode n'existait pas et la reconstruisait à la main). Ces membres sont désormais indexés à partir des annotations et des champs, ils apparaissent donc dans codegraph search et codegraph_explore/codegraph_node, et les appelants les parcourent comme n'importe quelle méthode écrite à la main. Ils sont marqués comme générés par Lombok, ils sont donc lus comme générés et non écrits à la main ; une méthode que vous écrivez vous-même n'est jamais remplacée, les champs statiques n'ont aucun accesseur et une classe sans Lombok n'est pas affectée. Merci @git87663849. (#912)
  • codegraph_explore suit désormais la distribution des pointeurs de fonctions C et C++. C fait du polymorphisme avec des pointeurs de fonction : une structure porte un champ de pointeur de fonction, des fonctions concrètes y sont enregistrées via une table (static struct cmd commands[] = {{"add", cmd_add}, …}), un initialiseur désigné (.handler = on_open) ou une affectation, et le code est distribué indirectement (p->fn(argv)). Rien de tout cela n'était visible à l'analyse - l'appel indirect n'a abouti à rien, donc le programme d'exécution de commandes de git semblait ne rien appeler et les implémentations d'une table virtuelle n'avaient aucun appelant. CodeGraph relie désormais le site de répartition aux gestionnaires enregistrés, saisis par le champ struct, donc « qu'est-ce qui s'exécute lors de la répartition ? » traces de p->fn(...) dans chaque fonction enregistrée pour ce champ. Cela couvre l'idiome de table de commandes (git, redis) et l'idiome ops-struct/vtable (encodeurs de contenu de curl, gestionnaires de protocole), y compris le cas où un emplacement de hook générique est réaffecté à partir d'un registre (h->func = found->fn). Cela reste précis : les champs de pointeur de fonction distincts ne se lient pas, un champ de données simple n'est jamais traité comme une répartition et un projet sans répartition de pointeur de fonction n'est pas affecté. (#932)
  • codegraph_explore suit désormais les liaisons de route GoFrame dans Go. Les câbles de routeur standard de GoFrame acheminent de manière réfléchie : le chemin et la méthode se trouvent dans une balise de structure g.Meta sur un type de requête (g.Meta `path:"/user/sign-in" method:"post"`), the controller method that serves it is matched by that request type, and the two are joined at runtime by group.Bind(...) — so there was no path string and no edge from a route to its handler, and "where is /user/sign-in handled?" or "where are the routes bound to controllers?" could only be answered by reading. CodeGraph now indexes each g.Meta route as a real route node and links it to the controller method whose signature takes that request type, so a route resolves to its handler structurally in one codegraph_explore call. The link is by request type, not method name — so it's correct even when the two differ (a DeptSearchReq served by a List method); it tells apart the many identical request types a large app defines one-per-module (cash.ListReq vs order.ListReq) par package, y compris les modules complémentaires clonés ; et une route dont le gestionnaire n'est pas présent n'est pas liée plutôt que devinée. (#747)
  • Le serveur MCP fonctionne désormais dans des configurations monorepos et multi-projets. Avant, si vous démarriez CodeGraph quelque part sans .codegraph/ propre - le plus souvent une racine monorepo où vous indexiez uniquement des services individuels - le serveur n'exposait aucun outil, de sorte que votre agent ne pouvait pas interroger CodeGraph même pour les sous-projets qui étaient indexés. Désormais, les outils sont toujours disponibles : pointez une requête sur n'importe quel projet indexé avec l'argument projectPath (son chemin ou n'importe où à l'intérieur) et les réponses CodeGraph à partir de l'index de ce projet - pour autant de projets que vous le souhaitez en une seule session. Cela signifie également qu'un projet que vous indexez après le démarrage du serveur est récupéré sans redémarrage, alors qu'avant les outils restaient cachés car le serveur ne vérifiait un index qu'une seule fois au lancement. Un projet qui n'a véritablement pas d'index indique toujours clairement à votre agent d'y utiliser ses outils intégrés (et que vous pouvez exécuter codegraph init pour l'activer), de sorte que l'utilisation d'un seul projet reste inchangée. Merci @MaiLunJiye. (#964)
  • Le hook de chargement frontal Claude trouve désormais vos sous-projets indexés dans un monorepo. Le hook facultatif UserPromptSubmit qui injecte le contexte CodeGraph pour les questions structurelles ne recherchait auparavant qu'un index au niveau ou au-dessus de votre répertoire de travail - donc si vous ouvriez la racine monorepo mais indexiez des packages individuels (packages/api, services/auth), il ne trouvait rien et restait silencieux exactement là où c'était le plus utile. Il examine désormais également dans les sous-projets : un seul sous-projet indexé obtient automatiquement son contexte chargé en premier, et avec plusieurs hooks, il charge en premier celui que votre question nomme (et répertorie le reste afin que l'agent puisse les cibler par projectPath). Les dépôts pour un seul projet ne sont pas affectés et l'analyse est limitée et entièrement ignorée en dehors d'une racine d'espace de travail reconnaissable. (#964)
  • codegraph_explore fait désormais apparaître le bon code dans les grands projets multicouches. Lorsque vous posez une question de flux back-end dans un dépôt qui associe un serveur API à une grande interface qui reflète les mêmes mots de domaine (par exemple, une interface utilisateur d'administration app/ située sur un serveur api/), le fichier côté serveur qui correspond véritablement à plusieurs des termes de votre requête n'est plus exclu des résultats par la couche frontale plus grande et plus interconnectée. Un fichier corroboré par deux ou plusieurs termes de requête distincts est désormais conservé dans la réponse même lorsqu'une couche non liée plus dense l'évincerait autrement, donc "comment X lit les éléments/gère la demande" renvoie le service ou le gestionnaire qui effectue le travail au lieu d'un mur de vues frontales. Les projets à couche unique ne sont pas affectés ; réglez CODEGRAPH_RANK_NO_MULTITERM=1 pour revenir au classement précédent.
  • L'analyse d'impact et de rayon d'explosion pour TypeScript, JavaScript, Go, Python, Rust, Ruby, C, Java, C#, PHP, Scala, Kotlin, Swift, Dart et Pascal/Delphi comprend désormais les lecteurs d'une constante. Lorsque vous modifiez une constante au niveau d'un fichier, d'un package, d'un module ou d'une classe - un objet de configuration, une table de recherche, une constante partagée - les autres symboles de ce fichier qui le lisent apparaissent désormais comme affectés, alors qu'avant ils étaient invisibles (impact uniquement sur les appels suivis, les importations et l'héritage, de sorte que les consommateurs d'une constante ressemblaient à "rien ne dépend de cela"). Cela fait que codegraph impact, et la piste d'impact dans codegraph_explore/codegraph_node, attrapent la classe de changement « changer cette table, briser ses lecteurs ». Il est activé par défaut et n'ajoute aucun nœud à votre graphique ; les fichiers regroupés/minifiés et les noms ambigus sont ignorés pour garantir la précision des résultats. Réglez le CODEGRAPH_VALUE_REFS=0 pour l'éteindre.
  • Les constantes et globales de portée de fichier C (scalaires static const, tables de recherche de pointeur/tableau et globales mutables partagées) sont désormais reconnues comme des symboles à part entière. Auparavant, ils n'étaient pas du tout extraits, ils n'apparaissaient donc jamais lors des recherches et ne transportaient aucune personne à charge ; maintenant, ils apparaissent dans codegraph search et participent à l'analyse d'impact (voir ci-dessus), donc la modification d'une table de recherche C fait apparaître les fonctions du même fichier qui la lisent.
  • Les constantes Java static final, les constantes C# const / static readonly, les valeurs Scala object et les valeurs Kotlin de niveau supérieur / object / companion object val sont désormais classées comme constantes plutôt que comme champs génériques. Elles participent donc à l'analyse d'impact du lecteur de constante ci-dessus - modifiez une table public static final, un const string, un Scala object Config { val Timeout = … } ou un Kotlin companion object { const val … } et les méthodes qui le lisent apparaissent désormais comme affectées. (Les propriétés des instances Java final / C# readonly / Scala & Kotlin class par objet sont inchangées.) Les constantes Kotlin n'étaient auparavant pas du tout indexées en tant que leurs propres symboles, elles apparaissent donc désormais également dans codegraph search.
  • Les constantes Swift let et static let de niveau supérieur (y compris celles placées dans un espace de noms enum/struct, le modèle Swift commun) sont désormais indexées en tant que constantes et participent à l'analyse d'impact du lecteur constant ci-dessus - modifiez un static let defaultRetryLimit ou un enum Constants { static let … } et le même code de fichier qui le lit apparaît comme affecté. Les propriétés calculées et les let par instance ne sont pas traités comme des constantes.
  • Les constantes Dart de niveau supérieur const/final et de classe static const/static final sont désormais indexées en tant que constantes et participent à l'analyse d'impact des lecteurs constants ci-dessus. Les champs d'instance, les var et les valeurs locales ne sont pas traités comme des constantes. (Le code Dart généré avec les suffixes standard .g.dart/.freezed.dart/.pb.dart est déjà ignoré.)
  • Vous pouvez désormais enseigner à CodeGraph les extensions de fichiers personnalisées. Déposez un codegraph.json à la racine de votre dépôt avec une carte extensions — { "extensions": { ".dota_lua": "lua", ".tpl": "php" } } — et les fichiers avec ces extensions seront indexés sous la langue que vous nommez, au lieu d'être ignorés silencieusement car l'extension ne faisait pas partie des valeurs par défaut intégrées. Il est opt-in et validé avec votre code afin que toute l'équipe le partage, vos mappages se superposent aux éléments intégrés et gagnent en cas de conflit (vous pouvez même rediriger un élément intégré, par exemple .h → cpp), et une langue typée ou une configuration mal formée est avertie et ignorée plutôt que d'interrompre l'indexation. Les projets sans codegraph.json se comportent exactement comme avant. (#906)

Correctifs

  • codegraph index et codegraph init n'explorent plus pendant la phase de "Résolution des références" sur les grands projets - le plus péniblement étant ceux qui mélangent un gros front-end et un gros back-end, où la phase peut s'étendre sur plusieurs minutes. Un package ou un module importé dans des centaines ou des milliers de fichiers (react, un package d'interface utilisateur partagé, Python logging / typing) était traité comme si chacune de ces instructions d'importation pouvait être sa définition, de sorte que le résolveur comparait chaque importation à toutes les autres - un travail qui grandit avec le carré de l'ampleur de l'importation d'un package, c'est pourquoi il n'a explosé que sur les dépôts volumineux et lourds en importations. Les importations sont désormais résolues directement vers les définitions sur lesquelles elles pointent réellement, de sorte que ces comparaisons redondantes ont disparu (la résolution des références est considérablement plus rapide sur les dépôts volumineux) et le graphique n'accumule plus les liens d'importation à importation dénués de sens créés par l'ancienne solution de secours. (#915)
  • Les résultats de l'outil MCP n'apparaissent plus sous forme de titres surdimensionnés dans les clients à rendu Markdown (comme l'extension Claude Code VSCode). Les résultats utilisaient des en-têtes Markdown (##/###) pour des éléments tels que le résumé de l'état, chaque résultat de recherche et chaque section de fichier d'une exploration. Une requête normale remplissait donc la transcription avec des lignes à gros caractères - pire avec codegraph_search et codegraph_explore, où le bruit augmentait avec le nombre de résultats. Les en-têtes de section sont désormais des étiquettes en gras, qui s'affichent à la taille de texte normale tout en conservant la même structure. La sortie du terminal/CLI est inchangée. (#778)
  • Un serveur MCP pointé sur un dépôt très volumineux (des dizaines de milliers de fichiers) ne se bloque plus au premier appel de l'outil après un nouveau démarrage. Au démarrage, CodeGraph rapproche son index avec les fichiers actuels sur le disque, et sur un énorme dépôt, cette réconciliation pourrait s'exécuter pendant des minutes tout en bloquant la toute première requête - suffisamment longtemps pour que le serveur d'arrière-plan soit parfois redémarré de force en cours d'analyse, de sorte que la première requête n'est jamais revenue du tout. La réconciliation donne désormais un résultat au fur et à mesure de son exécution (en gardant le serveur réactif au lieu de l'épingler), et le premier appel d'outil n'attend que brièvement avant de répondre et de laisser le reste se terminer en arrière-plan - vous obtenez ainsi une première réponse rapide et l'index rattrape toujours son retard. Réglez CODEGRAPH_CATCHUP_GATE_TIMEOUT_MS pour régler la durée d'attente du premier appel (3 000 ms par défaut) ou =0 pour toujours attendre la réconciliation complète. (#905)
  • codegraph install connecte désormais vos agents et s'arrête là — il n'indexe plus le répertoire courant. Construire le graphique d'un projet est toujours le codegraph init explicite (ou codegraph index), vous décidez donc ce qui sera indexé et quand, et les étapes sont les mêmes, que vous ayez installé globalement ou juste pour un projet. Cela dissipe la confusion dans laquelle une installation locale du projet était indexée silencieusement mais pas une installation globale, et où la documentation et l'outil n'étaient pas d'accord sur la question de savoir si vous deviez toujours exécuter init. (#826)
  • Les composants React déclarés avec forwardRef, memo ou des composants stylisés / émotion (const Button = forwardRef(...), const Card = memo(...), const Box = styled.button\…`) are now recognized as components, so finding where they're used works. Before, they were indexed as plain constants, so codegraph callersand impact analysis reported "no callers found" even when the component was rendered across dozens of files — a dangerous false "safe to change" right before refactoring a shared component. Now every<Button/>` renvoient au composant, de sorte que les appelants et le rayon d'explosion sont complets. Il s'agit du style de déclaration shadcn/ui standard, donc pour les systèmes de conception React typiques, le toute la couche d'interface utilisateur n'est plus invisible pour l'analyse d'impact. Merci @Arlandaren pour le rapport et @maxmilian pour la cause première (#841).
  • Les routes React Router et Next.js définies dans les fichiers .tsx / .jsx sont désormais indexées. Les routes écrites en JSX — fichiers de page <Route path="/users" element={<UsersPage/>}/>, createBrowserRouter([...]) et Next.js app//pages/ — étaient entièrement ignorées (seules les routes qui se trouvaient dans la plaine .ts/.js ont été récupérées), donc « qu'est-ce qui s'affiche sur ce chemin ? et le lien itinéraire → composant de page manquait pour la plupart des applications React. Désormais, ces routes apparaissent dans codegraph search/codegraph_explore et se connectent au composant qu'elles restituent, tout comme la route backend → les liens du gestionnaire sur d'autres frameworks.
  • codegraph sync (et la synchronisation automatique de l'observateur de fichiers derrière l'utilisation permanente / MCP) ne supprime plus les appelants d'une fonction lorsque vous modifiez le fichier dans lequel réside la fonction. La réindexation d'un fichier après une modification - même une modification de docstring uniquement - coupait les bords calls / references provenant d'autres fichiers inchangés (par exemple, les appelants from pkg import mod; mod.fn(), ou toute référence croisée de fichiers), donc codegraph callers / impact signalerait brusquement "aucun appelant" pour une fonction utilisée dans toute la base de code, jusqu'à la prochaine réindexation complète. La synchronisation préserve désormais les bords croisés entrants lors de la réindexation, en les faisant correspondre au symbole même lorsque la modification a décalé son numéro de ligne. Plus visible dans les grandes arborescences de packages Python, mais il s'applique à toutes les langues. Merci @JosefAschauer. (#899)
  • codegraph index reconstruit désormais le graphique complet à partir de zéro, il produit donc le même résultat qu'un nouveau codegraph init au lieu de signaler "0 nœuds, 0 bords" et de donner l'impression qu'il a effacé votre index. Auparavant, la réexécution de index sur un projet inchangé ignorait tous les fichiers (leur contenu n'avait pas changé) et affichait un résumé vide ; il efface et réindexe désormais pour une reconstruction honnête et complète à chaque fois. Utilisez codegraph sync pour des mises à jour incrémentielles rapides entre les reconstructions complètes. Merci @Arc-univers. (#874)
  • L'observateur de fichiers qui synchronise automatiquement le graphique échoue désormais proprement lorsque la visualisation en direct ne peut plus être effectuée par trust, au lieu de paraître sain tandis que l'index devient progressivement obsolète. Si le système d'exploitation manque de ressources de surveillance des fichiers ou si un autre processus maintient le verrou en écriture beaucoup plus longtemps qu'une sauvegarde normale, CodeGraph désactive désormais la synchronisation automatique une fois - avec un seul message clair vous indiquant d'exécuter codegraph sync (ou de compter sur les hooks de synchronisation git) pour actualiser - plutôt que de réessayer indéfiniment ou de répéter la même erreur en boucle. Et bien que la synchronisation automatique soit désactivée, les réponses de l'outil CodeGraph (et codegraph status) le disent désormais clairement, afin que votre agent IA sache qu'il doit lire les fichiers directement au lieu de trusting un index gelé. Cela est principalement important pour les sessions MCP/démon de longue durée, qui pourraient autrement continuer à fournir des résultats obsolètes tout en semblant fonctionner. Merci @thismilktea. (#876)
  • Sous Linux, atteindre la limite de surveillance inotify du noyau sur un grand projet ne laisse plus silencieusement la moitié de l'arborescence sans surveillance. CodeGraph vous l'indique désormais une fois - en nommant le paramètre exact à augmenter (fs.inotify.max_user_watches, par exemple sudo sysctl fs.inotify.max_user_watches=1048576) - et continue de surveiller en direct les répertoires qu'il pourrait enregistrer pendant que codegraph sync (ou les hooks de synchronisation git) couvre le reste. (#876)
  • Un serveur MCP de longue durée remarque désormais lorsqu'un arbre de travail git obtient son propre index. Avant, si le serveur (ou le démon partagé) voyait pour la première fois un arbre de travail avant d'y exécuter codegraph init - de sorte que la recherche remontait jusqu'à l'index de la caisse principale - il épinglait cette décision pour toute sa vie : même après que l'arbre de travail avait son propre .codegraph/, chaque requête continuait d'atteindre l'index de la caisse principale et chaque résultat comportait un faux avertissement "cet index appartient à un arbre de travail git différent", jusqu'à ce que vous redémarriez le serveur. Le CLI a bien fait les choses, mais pas le serveur MCP et la réindexation n'a pas aidé. Le serveur revérifie désormais à quel index appartient un chemin à chaque appel, de sorte que le propre index de l'arbre de travail est récupéré - et l'avertissement obsolète est supprimé - sans redémarrage. (#926)
  • Un serveur MCP de longue durée récupère désormais lorsque votre index est supprimé et reconstruit sur le même chemin. Si .codegraph/ a été supprimé et recréé alors que le serveur le maintenait ouvert - le plus facilement en recréant un arbre de travail git sur le même chemin, ou en exécutant .codegraph/ avec .codegraph/ et en exécutant à nouveau codegraph init - le serveur a continué à lire l'ancien fichier de base de données supprimé et a servi un instantané gelé : les symboles renommés ou supprimés étaient toujours affichés comme étant actifs, de nouveaux manquaient et codegraph sync ne pouvait pas l'actualiser - il suffisait de redémarrer le serveur. je l'ai réparé. Le serveur détecte maintenant que le fichier de base de données a été remplacé et rouvre le fichier actif en place, de sorte que les résultats restent corrects sans redémarrage. (Sous Linux et macOS ; Windows n'autorise pas la suppression d'un fichier ouvert, il n'est donc pas affecté.) (#925)
  • Le serveur MCP ouvre et synchronise désormais automatiquement un projet qui se trouve dans un dossier ignoré par un référentiel git englobant. Auparavant, si le répertoire que vous indexiez se trouvait dans un référentiel plus grand qui l'ignorait, le démon MCP partagé ne parvenait pas à ouvrir le projet - son journal répétait Failed to open project … path should be a path.relative() d string, but got "./" - de sorte que l'observateur de fichiers ne démarrait jamais et l'index devenait obsolète jusqu'à ce que vous exécutiez codegraph sync à la main (la configuration de CODEGRAPH_NO_DAEMON=1 était la seule solution de contournement). Le démon ouvre maintenant le projet et commence à regarder comme prévu. Le plus visible avec Codex sous Windows, mais la cause n'était pas spécifique à la plate-forme. (#936)
  • Un arbre de travail git d'un sous-module n'est plus indexé comme une copie du code de ce sous-module. CodeGraph ignore déjà les arbres de travail ordinaires (une deuxième vue fonctionnelle d'un dépôt qu'il indexe), mais un arbre de travail créé à partir d'un sous-module - courant dans les monorepos qui vérifient les sous-modules dans les arbres de travail pour le travail de fonctionnalités parallèles - a été confondu avec un véritable dépôt intégré et balayé, dupliquant chaque symbole qu'il partageait avec la véritable extraction du sous-module (un rapport avait ~ 28% de son index en double, gonflant à la fois les résultats de la requête et la base de données). Ces arbres de travail de sous-module sont désormais reconnus et ignorés, tandis que la propre extraction du sous-module reste indexée en tant que code distinct. Merci @ charlesxu2026-ship-it. (#945)
  • Une classe ou une structure C++ annotée avec une macro d'exportation/visibilité — class MYLIB_EXPORT Foo : public Bar { … }, le modèle commun d'exportation/visibilité de DLL dans les en-têtes — n'est plus mal indexée en tant que fonction couvrant l'ensemble du corps de la classe. Ne sachant pas que la macro est une macro, l'analyseur l'a lu comme un type et la déclaration entière comme une fonction, de sorte que la classe est apparue comme un fantôme function qui s'est présenté comme un faux appelant dans codegraph callers, codegraph impact et l'analyse du rayon de souffle, et un nombre de symboles biaisé. CodeGraph reconnaît maintenant cette erreur d'analyse et supprime le faux nœud. Merci @spwlyzx. (#946)
  • codegraph status ne signale plus les modifications fantômes en attente pour les fichiers que CodeGraph garde délibérément en dehors de l'index - un fichier suivi dans un répertoire de dépendance validé (un vendor/ ou node_modules/ archivé), ou un fichier suivi dans un répertoire .gitignored. Un index complet les exclut correctement, et codegraph sync ne les indexe jamais, mais le détecteur de changements rapide derrière codegraph status a signalé chaque modification d'un tel fichier comme "modifié" (et un nouveau comme "ajouté") - de sorte que le nombre de modifications en attente n'a jamais été effacé, quel que soit le nombre de fois que vous avez synchronisé. La détection des modifications applique désormais les mêmes règles d'ignorance que l'index complet, donc status est d'accord avec sync, et les outils basés sur la détection de modifications de CodeGraph API obtiennent la même liste corrigée. (#766)
  • Les fichiers accessibles via un répertoire lié symboliquement qui pointe en dehors de votre projet sont désormais indexés au lieu d'être ignorés silencieusement. Lorsqu'un dossier de votre dépôt est un lien symbolique vers un emplacement en dehors de la racine du dépôt - la disposition standard pour les jeux personnalisés Dota 2 et les projets similaires liés à SDK, où game/ et content/ sont liés dans l'arborescence du moteur - CodeGraph a suivi le lien symbolique pour découvrir ces fichiers, mais a ensuite bloqué chacun d'entre eux lors de la lecture, en enregistrant Path traversal blocked in batch reader et en n'indexant rien sous eux. Le lecteur accepte maintenant l'analyse du répertoire et indexe ces fichiers. La protection contre les échappements de chemin ../ est inchangée, et la protection qui empêche votre agent de recevoir le contenu des fichiers depuis l'extérieur du dépôt est également inchangée : seul le chemin de lecture de l'indexeur suit ces liens symboliques dans le dépôt. (#935)

codegraph v1.1.0

[1.1.0] - 2026-06-23

New Features

  • Claude Code: an optional front-load hook makes your agent reach for CodeGraph automatically. When you ask a structural question — "how does X work", "what calls Y", "trace the flow from A to B" — CodeGraph injects the relevant source and call paths into the prompt up front, so the agent answers from the graph instead of grepping around to rebuild it. You're asked during codegraph install (default yes; Claude Code only, since it's the agent with prompt hooks), it's removed by codegraph uninstall, and codegraph upgrade turns it on for existing Claude setups. It's strictly additive and degradable — non-structural prompts and un-indexed projects are left alone — and you can switch it off any time without uninstalling by setting CODEGRAPH_NO_PROMPT_HOOK=1.

  • Vue store actions, mutations, and getters are now indexed as symbols you can find and read. Whether your store is Vuex (mutations / actions objects in a module) or Pinia — both the options form (defineStore({ actions: { … } })) and the setup form (defineStore('id', () => { … }), where actions are local functions) — each action, mutation, and getter is now a real node. So codegraph search finds login or getSessionList, and codegraph_explore / codegraph_node show its body and what it calls, instead of "not found" because the function only existed as an object-literal property.

  • codegraph_explore now connects a Vue component to the Pinia store action it calls. When code does const store = useUserStore() and then store.fetchUser(), that call now links through to the fetchUser action in the store module — so "what happens when this view loads its data?" traces from the component into the action's body instead of stopping at the store.fetchUser() line. Works for both Pinia store styles (options and setup), and stays precise (a built-in like store.$patch() or an unrelated same-named method isn't mislinked).

  • codegraph_explore now follows Vuex string dispatch. A dispatch('user/login') or commit('SET_TOKEN') call — namespaced 'module/action' keys included — now links to the action or mutation it names, resolved to the correct store module even when several modules share an action name (and without being fooled by a same-named api/ helper). So "what runs when this dispatches?" traces from the call into the store handler and on to the mutations it commits. Vuex's canonical export default { namespaced, actions, mutations } module shape is now indexed too, so those handlers are findable symbols.

  • codegraph_explore now connects React data-fetching flows built on RTK Query (Redux Toolkit's createApi). An endpoint defined inside createApi({ endpoints }) and the useGetXQuery / useUpdateYMutation hook it generates were both invisible to analysis — so "what does this component fetch?" or "where does useGetThingQuery get its data?" dead-ended, because the hook, the endpoint, and the component had nothing linking them. CodeGraph now indexes each endpoint and each generated hook as real symbols and wires the path component → useGetXQuery → getX → queryFn, so the flow resolves in one explore call instead of reading the API slice by hand. Both the arrow (endpoints: build => ({ … })) and method (endpoints(builder) { return { … } }) styles are recognized, along with the useLazyGetXQuery variant; hand-written hooks of a similar name are left untouched.

  • codegraph_explore now follows Celery task dispatch in Python. A send_email.delay(...) or send_email.apply_async(...) call now links to the @shared_task / @app.task function it runs — typically defined in a different module (tasks.py) from where it's triggered (a view or service) — so "what actually happens when this is dispatched?" traces from the call site straight into the task body instead of stopping at the .delay() line. Both decorator dialects are recognized (bare @shared_task and the arg'd @app.task(bind=True, …) form), including the module-qualified tasks.invalidate_cache.apply_async() call style. It stays precise: a .delay() on something that isn't a Celery task is never mislinked, so a project that doesn't use Celery is unaffected.

  • codegraph_explore now follows Spring application events in Java. A publishEvent(new OrderShippedEvent(...)) call now links to every @EventListener that handles that event — usually in a different class — so "what reacts when this is published?" traces from the publisher straight into each listener method instead of dead-ending at publishEvent(...). The link is by event type, and all the common listener styles are recognized: a @EventListener typed on its parameter, the @EventListener(SomeEvent.class) form, @TransactionalEventListener, and the older implements ApplicationListener<SomeEvent>. One event fans out to all its listeners, and a plain Spring app with no event bus is unaffected.

  • codegraph_explore now follows MediatR request and notification dispatch in C#/.NET. A _mediator.Send(command) or _mediator.Publish(notification) call now links to the Handle method of the matching IRequestHandler<> / INotificationHandler<> — usually in a different file in a Clean Architecture layout — so "what handles this command?" traces from the controller straight into the handler instead of stopping at the mediator call. The sent type is recognized whether it's constructed inline (Send(new GetFooQuery())), built into a local first (var cmd = new …; Send(cmd)), or passed in as a parameter, and it's matched by type — so a MessagingCenter.Send(...) or a same-named DTO that isn't a request is never mislinked, and a project without MediatR is unaffected.

  • codegraph_explore now follows Sidekiq background-job dispatch in Ruby. A DestroyUserWorker.perform_async(id) (or .perform_in / .perform_at) call now links to that worker's perform method — usually in app/workers/ away from the controller or model that enqueues it — so "what runs in the background here?" traces from the enqueue straight into the job body. Both the modern include Sidekiq::Job and the older Sidekiq::Worker are recognized, namespaced workers resolve to the right class even when several share a name (e.g. Comments::NotifyWorker vs Articles::NotifyWorker), and Rails ActiveJob's perform_later — a different mechanism — is intentionally left alone.

  • codegraph_explore now follows Laravel events in PHP. An event(new OrderShipped($order)) call now links to every listener that handles it — each listener's handle() method, usually a separate app/Listeners/ class — so "what reacts to this event?" traces from the dispatch straight into the listener bodies. Listeners are found both ways Laravel registers them: by a typed handle(OrderShipped $event) (auto-discovery, including a handle(A|B $event) union that listens for two events) and by the protected $listen map in your EventServiceProvider (which also catches a listener whose handle() has no type-hint). One event fans out to all its listeners, and queued jobs — dispatched via ::dispatch() rather than event() — are correctly left out.

  • CodeGraph now understands Lombok-generated methods in Java. @Getter, @Setter, @Data, @Value, and @Builder generate getters, setters, builder(), equals/hashCode/toString, and the @Slf4j log field at compile time, so those methods never appear in the source — and a user.getName(), User.builder(), or log.info(...) call used to resolve to nothing, silently breaking call-chain analysis (the agent would conclude the method didn't exist and reconstruct it by hand). Those members are now indexed from the annotations and fields, so they appear in codegraph search and codegraph_explore/codegraph_node, and callers trace through them like any hand-written method. They're marked as Lombok-generated so they read as generated, not hand-written; a method you write yourself is never overridden, static fields get no accessor, and a class without Lombok is unaffected. Thanks @git87663849. (#912)

  • codegraph_explore now follows C and C++ function-pointer dispatch. C does polymorphism with function pointers: a struct carries a function-pointer field, concrete functions are registered into it through a table (static struct cmd commands[] = {{"add", cmd_add}, …}), a designated initializer (.handler = on_open), or an assignment, and the code dispatches indirectly (p->fn(argv)). None of that was visible to analysis — the indirect call resolved to nothing, so git's command runner looked like it called nothing and a vtable's implementations had no callers. CodeGraph now links the dispatch site to the registered handlers, keyed by the struct field, so "what runs when this dispatches?" traces from p->fn(...) into every function registered for that field. This covers the command-table idiom (git, redis) and the ops-struct/vtable idiom (curl's content-encoders, protocol handlers), including the case where a generic hook slot is reassigned from a registry (h->func = found->fn). It stays precise — distinct function-pointer fields don't cross-link, a plain data field is never treated as a dispatch, and a project without function-pointer dispatch is unaffected. (#932)

  • codegraph_explore now follows GoFrame route bindings in Go. GoFrame's standard router wires routes reflectively: the path and method live in a g.Meta struct tag on a request type (g.Meta `path:"/user/sign-in" method:"post"`), the controller method that serves it is matched by that request type, and the two are joined at runtime by group.Bind(...) — so there was no path string and no edge from a route to its handler, and "where is /user/sign-in handled?" or "where are the routes bound to controllers?" could only be answered by reading. CodeGraph now indexes each g.Meta route as a real route node and links it to the controller method whose signature takes that request type, so a route resolves to its handler structurally in one codegraph_explore call. The link is by request type, not method name — so it's correct even when the two differ (a DeptSearchReq served by a List method); it tells apart the many identical request types a large app defines one-per-module (cash.ListReq vs order.ListReq) by package, including cloned addon modules; and a route whose handler isn't present is left unlinked rather than guessed. (#747)

  • The MCP server now works in monorepos and multi-project setups. Before, if you started CodeGraph somewhere with no .codegraph/ of its own — most often a monorepo root where you only indexed individual services — the server exposed no tools at all, so your agent couldn't query CodeGraph even for the sub-projects that were indexed. Now the tools are always available: point a query at any indexed project with the projectPath argument (its path, or anywhere inside it) and CodeGraph answers from that project's index — for as many projects as you like in one session. It also means a project you index after the server started is picked up without restarting, where before the tools stayed hidden because the server only checked for an index once at launch. A project that genuinely has no index still cleanly tells your agent to use its built-in tools there (and that you can run codegraph init to enable it), so single-project use is unchanged. Thanks @MaiLunJiye. (#964)

  • The Claude front-load hook now finds your indexed sub-projects in a monorepo. The optional UserPromptSubmit hook that injects CodeGraph context for structural questions previously only looked for an index at or above your working directory — so if you opened the monorepo root but indexed individual packages (packages/api, services/auth), it found nothing and stayed silent exactly where it was most useful. It now also looks into sub-projects: a single indexed sub-project gets its context front-loaded automatically, and with several the hook front-loads the one your question names (and lists the rest so the agent can target them by projectPath). Single-project repos are unaffected, and the scan is bounded and skipped entirely outside a recognizable workspace root. (#964)

  • codegraph_explore now surfaces the right code in large multi-layer projects. When you ask a backend-flow question in a repo that pairs an API server with a big frontend that mirrors the same domain words — say an app/ admin UI sitting over an api/ server — the server-side file that genuinely matches several of your query's terms is no longer pushed out of the results by the larger, more interconnected frontend layer. A file corroborated by two or more distinct query terms is now kept in the answer even when a denser unrelated layer would otherwise crowd it out, so "how does X read items / handle the request" returns the service or handler that does the work instead of a wall of frontend views. Single-layer projects are unaffected; set CODEGRAPH_RANK_NO_MULTITERM=1 to revert to the previous ranking.

  • Impact and blast-radius analysis for TypeScript, JavaScript, Go, Python, Rust, Ruby, C, Java, C#, PHP, Scala, Kotlin, Swift, Dart, and Pascal/Delphi now understands the readers of a constant. When you change a file-scope, package-level, module-level, or class-level constant — a config object, a lookup table, a shared constant — the other symbols in that file that read it now show up as affected, where before they were invisible (impact only followed calls, imports, and inheritance, so a constant's consumers looked like "nothing depends on this"). This makes codegraph impact, and the impact trail in codegraph_explore/codegraph_node, catch the "change this table, break its readers" class of change. It's on by default and adds no nodes to your graph; bundled/minified files and ambiguously-shadowed names are skipped to keep results precise. Set CODEGRAPH_VALUE_REFS=0 to turn it off.

  • C file-scope constants and globals — static const scalars, pointer/array lookup tables, and shared mutable globals — are now recognized as symbols in their own right. They previously weren't extracted at all, so they never appeared in search or carried any dependents; now they show up in codegraph search and participate in impact analysis (see above), so changing a C lookup table surfaces the same-file functions that read it.

  • Java static final constants, C# const / static readonly constants, Scala object vals, and Kotlin top-level / object / companion object vals are now classified as constants rather than generic fields, so they participate in the constant-reader impact analysis above — change a public static final table, a const string, a Scala object Config { val Timeout = … }, or a Kotlin companion object { const val … } and the methods that read it now show up as affected. (Per-object Java final / C# readonly / Scala & Kotlin class instance properties are unchanged.) Kotlin constants were previously not indexed as their own symbols at all, so they now also appear in codegraph search.

  • Swift top-level lets and static let constants (including those namespaced in an enum/struct, the common Swift pattern) are now indexed as constants and participate in the constant-reader impact analysis above — change a static let defaultRetryLimit or an enum Constants { static let … } and the same-file code that reads it shows up as affected. Computed properties and per-instance lets are not treated as constants.

  • Dart top-level const/final and class static const/static final constants are now indexed as constants and participate in the constant-reader impact analysis above. Instance fields, vars, and locals are not treated as constants. (Generated Dart code with the standard .g.dart/.freezed.dart/.pb.dart suffixes is already skipped.)

  • You can now teach CodeGraph about custom file extensions. Drop a codegraph.json at your repo root with an extensions map — { "extensions": { ".dota_lua": "lua", ".tpl": "php" } } — and files with those extensions get indexed under the language you name, instead of being silently skipped because the extension wasn't one of the built-in defaults. It's opt-in and committed alongside your code so the whole team shares it, your mappings layer on top of the built-ins and win on conflict (you can even re-point a built-in, e.g. .h → cpp), and a typo'd language or a malformed config is warned about and skipped rather than breaking indexing. Projects without a codegraph.json behave exactly as before. (#906)

Fixes

  • codegraph index and codegraph init no longer crawl during the "Resolving refs" phase on large projects — most painfully ones that mix a big front-end and back-end, where the phase could stretch to many minutes. A package or module imported across hundreds or thousands of files (react, a shared UI package, Python logging / typing) was being treated as if every one of those import statements might be its definition, so the resolver compared each import against all the others — work that grows with the square of how widely a package is imported, which is why it blew up only on big, import-heavy repos. Imports now resolve straight to the definitions they actually point at, so those redundant comparisons are gone (reference resolution is dramatically faster on large repos), and the graph no longer accumulates the meaningless import-to-import links the old fallback created. (#915)
  • MCP tool results no longer show up as oversized headings in Markdown-rendering clients (such as the Claude Code VSCode extension). Results used Markdown headings (##/###) for things like the status summary, each search hit, and every file section in an exploration, so a normal query filled the transcript with large-font lines — worst with codegraph_search and codegraph_explore, where the noise grew with the number of results. Section headers are now bold labels, which render at normal text size while keeping the same structure. Terminal/CLI output is unchanged. (#778)
  • An MCP server pointed at a very large repository (tens of thousands of files) no longer hangs on the first tool call after a fresh start. On startup CodeGraph reconciles its index against the current files on disk, and on a huge repo that reconcile could run for minutes while blocking the very first request — long enough that the background server was sometimes force-restarted mid-scan, so the first query never came back at all. The reconcile now yields as it runs (keeping the server responsive instead of pinning it), and the first tool call waits only briefly for it before answering and letting the rest finish in the background — so you get a fast first response and the index still catches up. Set CODEGRAPH_CATCHUP_GATE_TIMEOUT_MS to tune how long that first call waits (default 3000ms), or =0 to always wait for the full reconcile. (#905)
  • codegraph install now wires up your agents and stops there — it no longer indexes the current directory. Building a project's graph is always the explicit codegraph init (or codegraph index), so you decide what gets indexed and when, and the steps are the same whether you installed globally or just for one project. This clears up the confusion where a project-local install silently indexed but a global one didn't, and where the docs and the tool disagreed about whether you still had to run init. (#826)
  • React components declared with forwardRef, memo, or styled-components / emotion (const Button = forwardRef(...), const Card = memo(...), const Box = styled.button\…`) are now recognized as components, so finding where they're used works. Before, they were indexed as plain constants, so codegraph callersand impact analysis reported "no callers found" even when the component was rendered across dozens of files — a dangerous false "safe to change" right before refactoring a shared component. Now every<Button/>` usage links back to the component, so callers and blast radius are complete. This is the standard shadcn/ui declaration style, so for typical React design systems the whole UI layer is no longer invisible to impact analysis. Thanks @Arlandaren for the report and @maxmilian for the root-cause. (#841)
  • React Router and Next.js routes defined in .tsx / .jsx files are now indexed. Routes written as JSX — <Route path="/users" element={<UsersPage/>}/>, createBrowserRouter([...]), and Next.js app//pages/ page files — were being skipped entirely (only routes that happened to live in plain .ts/.js were picked up), so "what renders at this path?" and the route → page-component link were missing for most React apps. Now those routes show up in codegraph search/codegraph_explore and connect to the component they render, just like the backend route → handler links on other frameworks.
  • codegraph sync (and the file-watcher auto-sync behind always-on / MCP use) no longer drops a function's callers when you edit the file that function lives in. Re-indexing a file after an edit — even a docstring-only change — was severing the calls / references edges coming from other, unchanged files (e.g. from pkg import mod; mod.fn() callers, or any cross-file reference), so codegraph callers / impact would abruptly report "no callers" for a function that's used throughout the codebase, until the next full re-index. Sync now preserves those incoming cross-file edges across the re-index, re-matching them to the symbol even when the edit shifted its line number. Most visible in large Python package trees, but it applies to every language. Thanks @JosefAschauer. (#899)
  • codegraph index now rebuilds the full graph from scratch, so it produces the same result as a fresh codegraph init instead of reporting "0 nodes, 0 edges" and looking like it wiped your index. Previously, re-running index on an unchanged project skipped every file (their contents hadn't changed) and showed an empty-looking summary; it now clears and re-indexes for an honest, complete rebuild every time. Use codegraph sync for fast incremental updates between full rebuilds. Thanks @Arc-univer. (#874)
  • The file watcher that auto-syncs the graph now fails cleanly when live watching can no longer be trusted, instead of looking healthy while the index quietly goes stale. If the operating system runs out of file-watch resources, or another process holds the write lock far longer than a normal save, CodeGraph now disables auto-sync once — with a single clear message telling you to run codegraph sync (or rely on the git sync hooks) to refresh — rather than retrying forever or repeating the same error on a loop. And while auto-sync is disabled, CodeGraph's tool responses (and codegraph status) now say so plainly, so your AI agent knows to read files directly instead of trusting a frozen index. This mostly matters for long-running MCP/daemon sessions, which could otherwise keep serving stale results while appearing to work. Thanks @thismilktea. (#876)
  • On Linux, hitting the kernel's inotify watch limit on a large project no longer silently leaves half the tree unwatched. CodeGraph now tells you once — naming the exact setting to raise (fs.inotify.max_user_watches, e.g. sudo sysctl fs.inotify.max_user_watches=1048576) — and keeps live-watching the directories it could register while codegraph sync (or the git sync hooks) covers the rest. (#876)
  • A long-running MCP server now notices when a git worktree gains its own index. Before, if the server (or shared daemon) first saw a worktree before you ran codegraph init in it — so the lookup walked up to the main checkout's index — it pinned that decision for its whole life: even after the worktree had its own .codegraph/, every query kept hitting the main checkout's index and every result carried a false "this index belongs to a different git working tree" warning, until you restarted the server. The CLI got it right but the MCP server didn't, and re-indexing didn't help. The server now re-checks which index a path belongs to on each call, so the worktree's own index is picked up — and the stale warning drops — without a restart. (#926)
  • A long-running MCP server now recovers when your index is deleted and rebuilt at the same path. If .codegraph/ was removed and recreated while the server held it open — most easily by recreating a git worktree at the same path, or rm-ing .codegraph/ and running codegraph init again — the server kept reading the old, deleted database file and served a frozen snapshot: renamed or removed symbols still showed as live, new ones were missing, and codegraph sync couldn't refresh it — only restarting the server fixed it. The server now detects that the database file was swapped out from under it and reopens the live one in place, so results stay correct without a restart. (On Linux and macOS; Windows doesn't allow deleting an open file, so it isn't affected.) (#925)
  • The MCP server now opens and auto-syncs a project that lives inside a folder an enclosing git repository ignores. Before, if the directory you indexed sat within a larger repo that gitignored it, the shared MCP daemon failed to open the project — its log repeated Failed to open project … path should be a path.relative() d string, but got "./" — so the file watcher never started and the index silently went stale until you ran codegraph sync by hand (setting CODEGRAPH_NO_DAEMON=1 was the only workaround). The daemon now opens the project and starts watching as expected. Most visible with Codex on Windows, but the cause wasn't platform-specific. (#936)
  • A git worktree of a submodule is no longer indexed as a duplicate copy of that submodule's code. CodeGraph already skips ordinary worktrees (a second working view of a repo it indexes), but a worktree created from a submodule — common in monorepos that check submodules out into worktrees for parallel feature work — was mistaken for a genuine embedded repo and swept in, duplicating every symbol it shared with the real submodule checkout (one report had ~28% of its index as duplicates, inflating both query results and the database). These submodule worktrees are now recognized and skipped, while the submodule's own checkout stays indexed as distinct code. Thanks @charlesxu2026-ship-it. (#945)
  • A C++ class or struct annotated with an export/visibility macro — class MYLIB_EXPORT Foo : public Bar { … }, the common DLL-export / visibility pattern in headers — is no longer mis-indexed as a function spanning the whole class body. Not knowing the macro is a macro, the parser read it as a type and the whole declaration as a function, so the class surfaced as a phantom function that showed up as a false caller in codegraph callers, codegraph impact, and blast-radius analysis, and skewed symbol counts. CodeGraph now recognizes this misparse and drops the bogus node. Thanks @spwlyzx. (#946)
  • codegraph status no longer reports phantom pending changes for files CodeGraph deliberately keeps out of the index — a tracked file inside a committed dependency dir (a checked-in vendor/ or node_modules/), or a tracked file under a .gitignored directory. A full index correctly excludes these, and codegraph sync never indexes them, but the fast change-detector behind codegraph status flagged every edit to such a file as "modified" (and a new one as "added") — so the pending-changes count never cleared no matter how many times you synced. Change detection now applies the same ignore rules the full index does, so status agrees with sync, and tools built on CodeGraph's change-detection API get the same corrected list. (#766)
  • Files reached through a symlinked directory that points outside your project now index instead of being silently skipped. When a folder in your repo is a symlink to a location outside the repo root — the standard layout for Dota 2 custom games and similar SDK-linked projects, where game/ and content/ link into the engine tree — CodeGraph followed the symlink to discover those files but then blocked every one of them while reading, logging Path traversal blocked in batch reader and indexing nothing under them. The reader now agrees with the directory scan and indexes those files. The guard against ../ path escapes is unchanged, and the protection that keeps your agent from being served file contents from outside the repo is also unchanged — only the indexer's own read path follows these in-repo symlinks. (#935)
