codegraphe v1.2.0

[1.2.0] - 2026-07-02

Nouvelles fonctionnalités

  • Les appels de méthode effectués via une variable locale sont désormais résolus en méthode dans de nombreuses autres langues. Lorsque le code exécute const logger = new Logger(); logger.log(); (ou l'équivalent), CodeGraph déduit le type de la variable locale à partir de sa déclaration ou de son initialiseur et lie l'appel à la bonne méthode — de sorte que ces appels apparaissent désormais dans les appelants, les traces d'impact/rayon d'explosion et de flux codegraph_explore au lieu d'être supprimés. Auparavant, seul le C++ gérait cela ; il couvre désormais également TypeScript, JavaScript, Python, Java, C#, Kotlin, Swift, Go, Rust, Dart, Scala et PHP. (#1108)
  • Les appels de méthode Ruby effectués sur un récepteur (logger.log) enregistrent désormais un front dans la méthode. Auparavant, l'indexeur Ruby ne conservait que le récepteur et ignorait le nom de la méthode, de sorte qu'une méthode appelée via une variable ou un objet n'avait aucun appelant enregistré et manquait dans les traces d'impact/rayon d'explosion et de flux ; combiné à l'inférence de type de variable locale ci-dessus, logger = Logger.new; logger.log est désormais lié à Logger#log. Les appels à une méthode de classe (Foo.bar) et à la construction d'objets (Foo.new) sont également toujours enregistrés. (#1110)
  • La même résolution d'appel de méthode à variable locale s'étend désormais à Lua, Luau, R et Pascal/Delphi. Une méthode invoquée via un local — Lua/Luau local lg = Logger.new(); lg:log(), R lg <- Logger$new(); lg$log() ou Pascal var lg: TLogger; ... lg.Log — est désormais liée à la bonne méthode au lieu d'être supprimée. (#1112)

Correctifs

  • L'indexation d'un projet volumineux n'est plus interrompue en cours de route par le message "Le thread principal ne répond pas - tuant le processus coincé". Le chien de garde qui arrête un index véritablement bloqué confondait un travail lent mais normal avec un blocage : sur un gros dépôt, la liaison des références et les relations entre fichiers peuvent légitimement s'exécuter pendant un certain temps, et ce travail cède désormais régulièrement afin que le chien de garde puisse distinguer de réels progrès d'un véritable blocage. Les projets qui auparavant ne parvenaient pas à terminer codegraph init / codegraph index (et devaient revenir à CODEGRAPH_NO_WATCHDOG=1) se terminent désormais normalement, tandis qu'un processus véritablement bloqué est toujours bloqué. Merci @zmcrazy, @YoungLiao et @GeeLab-Mob pour les rapports. (#1091)
  • Sous Windows, une fenêtre de console ne clignote plus brièvement lorsque CodeGraph s'exécute en tant que serveur MCP en arrière-plan. Lorsque le lanceur npm a démarré le runtime fourni – ce qui se produit chaque fois qu'un éditeur démarre le serveur ou se reconnecte après l'inactivité du démon – et pendant son étape d'auto-réparation qui extrait un paquet de plate-forme manquant, Windows affiche une fenêtre de console noire (conhost) pendant un moment. Les deux se lancent désormais cachés, ce qui correspond au comportement du démon ; l'étape d'ouverture du navigateur de codegraph login a été renforcée de la même manière. Merci @luoyerr pour le rapport et l'analyse des causes profondes. (#1092)
  • Les déclarations avancées C++ n'éclipsent plus la véritable définition de classe. Une déclaration directe class Foo; – courante dans les grandes bases de code C++ et Unreal Engine, où une classe très utilisée est déclarée en avant dans des dizaines d'en-têtes – était indexée comme son propre nœud de classe à chaque fois qu'elle apparaissait. Ainsi, l'exploration de cette classe renvoyait principalement des sites de déclaration avancée, et pouvait même en choisir un comme représentant du rayon de souffle, enterrant ainsi la définition réelle et ses membres et appelants. Les déclarations directes sans corps sont désormais ignorées pour C et C++, exactement comme l'étaient déjà les structures et les énumérations déclarées en avant, de sorte que seule la définition réelle est indexée. Les langages dans lesquels une classe sans corps constitue une définition complète (comme class Empty et Scala de Kotlin) ne sont pas affectés. Merci @luoyxy pour le rapport et l'analyse des causes profondes. (#1093)
  • Les méthodes C++ qui renvoient une référence et les opérateurs de conversion définis par l'utilisateur sont désormais indexés sous leurs noms corrects. Un getter en ligne comme const FGameplayTagContainer& GetActiveTags() const – partout dans les en-têtes Unreal Engine – a été indexé comme & GetActiveTags() const au lieu de GetActiveTags, et un opérateur de conversion comme operator EALSMovementState() const a conservé son () const final au lieu de lire operator EALSMovementState. Dans les deux cas, le nom tronqué signifiait que vous ne pouviez pas trouver le symbole par son nom et que ses appelants n'étaient pas liés. Les deux se lisent désormais proprement, correspondant à la façon dont les méthodes de retour de pointeur et de retour de valeur fonctionnaient déjà. (#1096)
  • Les fonctions C++ écrites avec une macro de spécificateur en ligne avant le type de retour sont désormais correctement indexées. Dans Unreal Engine, les assistants en ligne s'écrivent généralement FORCEINLINE FString GetEnumerationToString(...) ; la macro FORCEINLINE a obligé l'analyseur à lire le type de retour dans le cadre du nom de la fonction (FString GetEnumerationToString au lieu de GetEnumerationToString) et à perdre le type de retour réel, de sorte que la fonction n'a pas pu être trouvée par son nom et ses appelants n'étaient pas liés. CodeGraph reconnaît désormais les macros en ligne Unreal standard (FORCEINLINE, FORCENOINLINE, FORCEINLINE_DEBUGGABLE), de sorte que le nom et le type de retour sont capturés. (#1100)
  • La même récupération de nom de fonction couvre désormais les macros en ligne des bibliothèques C++ tierces courantes, et pas seulement Unreal Engine — y compris pugixml (PUGI__FN, PUGIXML_FUNCTION), Godot (_FORCE_INLINE_), Boost (BOOST_FORCEINLINE) et générique ALWAYS_INLINE/FORCE_INLINE. Les fonctions agrémentées de ceux-ci sont désormais répertoriées sous leurs vrais noms. Sur un grand projet Unreal vendant ces bibliothèques, cela a nettoyé la grande majorité des confusions restantes dans les noms de fonctions. (#1101)
  • Les noms de fonctions C++ sont désormais récupérés même lorsqu'ils sont décorés avec une macro que CodeGraph ne connaît pas spécifiquement. Une fonction écrite SOME_LIBRARY_MACRO ReturnType doWork(...) avait auparavant la macro ou le type de retour absorbé dans son nom chaque fois que la macro n'était pas reconnue par CodeGraph ; désormais, le vrai nom (doWork) est récupéré quelle que soit la macro, il est donc trouvable et le lien de ses appelants — aucune configuration par bibliothèque n'est nécessaire. La liste des macros reconnues a également été élargie (Qt, Folly, Abseil, LLVM, V8, Eigen, rapidjson) afin que celles-ci capturent en plus le type de retour. Cela nettoie uniquement un nom déjà tronqué et est limité au C et au C++, de sorte que les noms ordinaires – et les langages comme Kotlin et Scala où les identifiants peuvent légitimement contenir des espaces – ne sont pas affectés. (#1102)
  • L'ensemble des bibliothèques C++ dont les macros sont reconnues pour une récupération complète de type retour a été étendu bien au-delà d'Unreal Engine - couvrant désormais Mozilla, Protobuf, {fmt}, nlohmann/json, GLM, Bullet, Skia, OpenCV, EASTL, Cocos2d-x, GLib, SQLite et les conventions d'appel Windows courantes (donc HRESULT WINAPI CreateThing(...) indexe comme CreateThing renvoyant HRESULT). Les fonctions des bibliothèques qui ne figurent pas sur la liste voient toujours leur nom récupéré automatiquement ; être répertorié récupère en outre le type de retour. (#1103)
  • Les résultats de parcours graphique et de rayon d'explosion ne suppriment plus ou ne comptent plus les relations dans une poignée de cas extrêmes. Lorsqu'un symbole pouvait être atteint par plusieurs chemins, une requête d'impact/rayon de souffle pouvait laisser de côté une dépendance directe entre deux symboles déjà liés d'une autre manière ; séparément, le parcours graphique de niveau inférieur utilisé par la bibliothèque API pourrait conserver une seule relation parmi plusieurs entre la même paire de symboles (par exemple un symbole qui en appelle et en référence un autre), compter deux fois un appelant atteint via deux sites d'appel différents, ou renvoyer légèrement plus de résultats que la limite de taille demandée sur un symbole très hautement connecté. Celles-ci étaient anciennes et pour la plupart masquées par une déduplication ultérieure, de sorte que les résultats des requêtes quotidiennes n'étaient en grande partie pas affectés, mais la traversée renvoie désormais l'ensemble complet et correctement délimité. Merci @inth3shadows pour les rapports précis et tracés individuellement. (#1086, #1087, #1088, #1089, #1090)
  • Les appels de méthode aux classes du même nom dans différents fichiers sont désormais résolus selon la bonne définition. Si deux fichiers déclaraient chacun, disons, une classe Logger avec sa propre méthode log(), un appel pourrait être lié à la définition qui aurait été indexée en premier - donc un appel dans un fichier pointait à tort sur la classe dans un autre, mélangeant les appelants et le rayon d'explosion de cette méthode. Cela affectait les appels écrits sous la forme obj.log(), Logger.log() et Logger::log() dans de nombreux langages, notamment C++, Python, TypeScript, Java, C# et Rust. Lorsqu'un nom de méthode est ambigu, CodeGraph préfère désormais la définition dans le fichier appelant lui-même - la cible correcte dans le cas courant - tandis que Java/Kotlin appelle qu'un import déjà épinglé à un autre fichier n'est pas affecté. Merci @inth3shadows pour la reproduction minimale et l'analyse des causes profondes. (#1079)

codegraph v1.2.0

[1.2.0] - 2026-07-02

New Features

  • Method calls made through a local variable now resolve to the method in many more languages. When code does const logger = new Logger(); logger.log(); (or the equivalent), CodeGraph infers the local variable's type from its declaration or initializer and links the call to the right method — so these calls now show up in callers, impact/blast-radius, and codegraph_explore flow traces instead of being dropped. Previously only C++ handled this; it now also covers TypeScript, JavaScript, Python, Java, C#, Kotlin, Swift, Go, Rust, Dart, Scala, and PHP. (#1108)
  • Ruby method calls made on a receiver (logger.log) now record an edge to the method. Previously the Ruby indexer kept only the receiver and discarded the method name, so a method called through a variable or object had no recorded callers and was missing from impact/blast-radius and flow traces; combined with the local-variable type inference above, logger = Logger.new; logger.log now links to Logger#log. Calls to a class method (Foo.bar) and object construction (Foo.new) are still recorded too. (#1110)
  • The same local-variable method-call resolution now extends to Lua, Luau, R, and Pascal/Delphi. A method invoked through a local — Lua/Luau local lg = Logger.new(); lg:log(), R lg <- Logger$new(); lg$log(), or Pascal var lg: TLogger; ... lg.Log — now links to the right method instead of being dropped. (#1112)

Fixes

  • Indexing a large project no longer gets killed partway through with a "Main thread unresponsive — killing the wedged process" message. The safety watchdog that stops a genuinely stuck index was mistaking slow-but-normal work for a hang: on a big repo, linking up references and cross-file relationships can legitimately run for a while, and that work now regularly yields so the watchdog can tell real progress from a true stall. Projects that previously failed to finish codegraph init / codegraph index (and had to fall back to CODEGRAPH_NO_WATCHDOG=1) now complete normally, while a genuinely hung process is still caught. Thanks @zmcrazy, @YoungLiao, and @GeeLab-Mob for the reports. (#1091)
  • On Windows, a console window no longer briefly flashes when CodeGraph runs as a background MCP server. When the npm launcher started the bundled runtime — which happens every time an editor starts the server or reconnects after the daemon idles out — and during its self-heal step that extracts a missing platform bundle, Windows would pop up a black console (conhost) window for a moment. Both now launch hidden, matching how the daemon already behaved; the browser-open step of codegraph login was hardened the same way. Thanks @luoyerr for the report and root-cause analysis. (#1092)
  • C++ forward declarations no longer crowd out the real class definition. A class Foo; forward declaration — common in large C++ and Unreal Engine codebases, where a heavily used class is forward-declared across dozens of headers — was indexed as its own class node every time it appeared. So exploring that class returned mostly forward-declaration sites, and could even pick one of them as the representative for blast-radius, burying the actual definition and its members and callers. Bodiless forward declarations are now skipped for C and C++, exactly as forward-declared structs and enums already were, so only the real definition is indexed. Languages where a class with no body is a complete definition — such as Kotlin's class Empty and Scala — are unaffected. Thanks @luoyxy for the report and root-cause analysis. (#1093)
  • C++ methods that return a reference, and user-defined conversion operators, are now indexed under their correct names. An inline getter like const FGameplayTagContainer& GetActiveTags() const — everywhere in Unreal Engine headers — was indexed as & GetActiveTags() const instead of GetActiveTags, and a conversion operator like operator EALSMovementState() const kept its trailing () const instead of reading operator EALSMovementState. In both cases the garbled name meant you couldn't find the symbol by name and its callers weren't linked. Both now read cleanly, matching how pointer-returning and value-returning methods already worked. (#1096)
  • C++ functions written with an inline-specifier macro before the return type are now indexed correctly. In Unreal Engine, inline helpers are commonly written FORCEINLINE FString GetEnumerationToString(...); the FORCEINLINE macro made the parser read the return type as part of the function's name (FString GetEnumerationToString instead of GetEnumerationToString) and lose the real return type, so the function couldn't be found by name and its callers weren't linked. CodeGraph now recognizes the standard Unreal inline macros (FORCEINLINE, FORCENOINLINE, FORCEINLINE_DEBUGGABLE), so both the name and the return type are captured. (#1100)
  • The same function-name recovery now covers inline macros from common third-party C++ libraries, not just Unreal Engine — including pugixml (PUGI__FN, PUGIXML_FUNCTION), Godot (_FORCE_INLINE_), Boost (BOOST_FORCEINLINE), and generic ALWAYS_INLINE / FORCE_INLINE. Functions decorated with these are now indexed under their real names. On a large Unreal project vendoring these libraries this cleaned up the large majority of remaining function-name garbling. (#1101)
  • C++ function names are now recovered even when decorated with a macro CodeGraph doesn't specifically know about. A function written SOME_LIBRARY_MACRO ReturnType doWork(...) previously had the macro or return type absorbed into its name whenever the macro wasn't one CodeGraph recognized; now the real name (doWork) is recovered regardless of the macro, so it's findable and its callers link — no per-library configuration needed. The recognized-macro list was also broadened (Qt, Folly, Abseil, LLVM, V8, Eigen, rapidjson) so those additionally capture the return type. This only ever cleans up an already-garbled name and is limited to C and C++, so ordinary names — and languages like Kotlin and Scala where identifiers can legitimately contain spaces — are unaffected. (#1102)
  • The set of C++ libraries whose macros are recognized for full return-type recovery was expanded well beyond Unreal Engine — now spanning Mozilla, Protobuf, {fmt}, nlohmann/json, GLM, Bullet, Skia, OpenCV, EASTL, Cocos2d-x, GLib, SQLite, and the common Windows calling conventions (so HRESULT WINAPI CreateThing(...) indexes as CreateThing returning HRESULT). Functions from libraries not on the list still get their name recovered automatically; being listed additionally recovers the return type. (#1103)
  • Graph traversal and blast-radius results no longer drop or miscount relationships in a handful of edge cases. When a symbol could be reached by more than one path, an impact/blast-radius query could leave out a direct dependency between two symbols that were already linked another way; separately, the lower-level graph traversal used by the library API could keep only one of several relationships between the same pair of symbols (for example a symbol that both calls and references another), count a caller reached through two different call sites twice, or return slightly more results than the requested size limit on a very highly-connected symbol. These were long-standing and mostly masked by later de-duplication, so day-to-day query results were largely unaffected, but the traversal now returns the complete, correctly-bounded set. Thanks @inth3shadows for the precise, individually-traced reports. (#1086, #1087, #1088, #1089, #1090)
  • Method calls to same-named classes in different files now resolve to the right definition. If two files each declared, say, a Logger class with its own log() method, a call could be linked to whichever definition happened to be indexed first — so a call in one file wrongly pointed at the class in another, mixing up that method's callers and blast radius. This affected calls written as obj.log(), Logger.log(), and Logger::log() across many languages, including C++, Python, TypeScript, Java, C#, and Rust. When a method name is ambiguous, CodeGraph now prefers the definition in the calling file itself — the correct target in the common case — while Java/Kotlin calls that an import already pins to another file are unaffected. Thanks @inth3shadows for the minimal repro and root-cause analysis. (#1079)
