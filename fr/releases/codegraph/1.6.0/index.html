codegraphe v1.6.0

[1.6.0] - 2026-08-26

Faits saillants

  • GitHub Copilot est désormais pris en charge — codegraph install le configure dans VS Code, le Copilot CLI et les IDE JetBrains, à côté des agents qu'il connaissait déjà.
  • Configuré en une seule commande — codegraph install --yes --init connecte vos agents et indexe votre projet sans invite, idéal pour un nouveau conteneur ou CI.
  • De meilleures réponses pour votre agent — codegraph_explore ne répète plus le code qu'il vous a déjà montré, ramène toujours les fichiers et les symboles que vous avez demandés par leur nom et consacre son espace au code qui répond réellement à la question plutôt qu'aux sosies, aux fichiers générés et aux cales de type.
  • Votre graphique reste correct pendant que vous continuez à coder : un index de longue durée ne dérive plus d'un nouveau, et les modifications apportées à codegraph.json (comme exclude) s'appliquent immédiatement sans redémarrage.
  • Plus de plantages ou de blocages silencieux : les fichiers C/C++ profondément imbriqués, les projets Swift Vapor et les gros lots de synchronisation qui interrompaient ou bloquaient l'indexation se terminent désormais proprement.
  • Une fuite d'espace disque est corrigée — une session interrompue de force pourrait laisser le journal d'écriture anticipée de la base de données croître sans limite (des dizaines de gigaoctets ont été signalés) ; le journal restant est maintenant replié dans l'index et coupé automatiquement à la prochaine ouverture du projet. L'index lui-même n'a pas de limite de taille.
  • Fonctionne à partir d'un espace de travail ou d'une racine monorepo — le serveur MCP trouve votre projet indexé lorsqu'il est lancé à partir d'un dossier situé au-dessus de celui-ci, et l'indique clairement lorsqu'il n'en trouve pas.
  • Graphiques de code plus précis pour les projets TypeScript, Rust, Erlang, C/C++ et Python — voir la liste complète ci-dessous.
  • Également nouveau : configuration du Codex par projet (codegraph install --location=local), un paramètre deprioritize pour empêcher les dossiers d'assistance de surpasser votre vrai code, la commande codegraph context et les statistiques d'utilisation qui restent désormais entièrement sur les propres serveurs de CodeGraph. Après la mise à niveau, exécutez codegraph index une fois dans chaque projet afin que votre graphique existant récupère ces correctifs — codegraph status vous rappelle quand cela est nécessaire.

Nouvelles fonctionnalités

  • GitHub Copilot est désormais un agent pris en charge : codegraph install peut configurer Copilot Chat dans VS Code (copilot-vscode), le GitHub Copilot CLI (copilot-cli) et le plugin Copilot dans les IDE JetBrains (copilot-jetbrains). Les surfaces Copilot installées sont détectées automatiquement comme tous les autres agents, les entrées de serveur MCP existantes dans leurs fichiers de configuration sont préservées et codegraph uninstall inverse proprement la configuration. Redémarrez VS Code ou votre IDE JetBrains après l'installation pour que Copilot récupère le serveur.
  • codegraph install --init connecte vos agents et crée l'index du projet actuel en une seule commande, et codegraph init --yes s'exécute sans aucune invite — de sorte qu'un nouveau conteneur ou une nouvelle tâche CI peut amorcer CodeGraph avec une seule ligne non interactive (codegraph install --yes --init). Le programme d'installation n'indexe toujours rien à moins que vous ne le demandiez avec l'indicateur, et le refus de sécurité habituel pour un répertoire personnel ou la racine d'un système de fichiers s'applique. (#1578)
  • Le Codex CLI peut désormais être configuré par projet au lieu de seulement à l'échelle de l'utilisateur : codegraph install --location=local écrit ./.codex/config.toml et le bloc CodeGraph dans le AGENTS.md de votre projet, donc CodeGraph est connecté à ce référentiel uniquement plutôt qu'à chaque session Codex sur la machine. codegraph uninstall --location=local l'inverse et l'installation globale reste intacte dans les deux cas. Le Codex n'applique la configuration d'un projet qu'une fois que vous avez marqué le projet trusted, donc le programme d'installation le dit après une installation locale. Merci @maxmilian. (#1531)
  • Un nouveau paramètre deprioritize dans codegraph.json empêche les chemins que vous nommez de surpasser votre code produit dans la recherche et les réponses codegraph_explore, sans rien supprimer de l'index. Il prend des modèles de style gitignore, tout comme exclude, mais est uniquement de classement : les arbres de script d'assistance, la sortie générée ou les répertoires complémentaires facultatifs dont les noms de symboles génériques (usage, run, status) évinceraient autrement le code qui répond réellement à une requête reste entièrement indexé et trouvable - et une requête qui cible véritablement un tel arbre le renvoie toujours. Merci @maxmilian. (#982)
  • codegraph_explore ne renvoie plus la source déjà renvoyée plus tôt dans la même conversation. Un fichier qu'il vous a déjà montré revient sous la forme d'un court pointeur - le chemin, les symboles et la plage de lignes exacte, avec la confirmation que le fichier n'a pas changé depuis - et l'espace libéré est consacré au code que vous n'avez pas encore vu, donc un appel de suivi couvre un nouveau terrain au lieu de répéter le dernier. Si un fichier a été modifié entre-temps, sa source est toujours affichée à nouveau dans son intégralité. Réglez CODEGRAPH_EXPLORE_DEDUP=0 pour désactiver cette fonction.
  • Lorsqu'un agent se connecte via MCP, CodeGraph indique désormais d'emblée qu'il indexe plus de 30 langues (TypeScript/JavaScript, Python, Go, Rust, Java, C#, C/C++, PHP, Ruby, Swift, Kotlin, etc.) afin que les agents ne supposent plus qu'une langue n'est pas prise en charge et ignorent le graphique. (#671)
  • La télémétrie d'utilisation anonyme est désormais entièrement stockée sur la propre infrastructure propriétaire de CodeGraph : aucun fournisseur d'analyse tiers n'en reçoit et le point de terminaison qui la reçoit ne fait aucune demande sortante. Les événements individuels sont supprimés après 90 jours, ne laissant que les totaux quotidiens anonymes. Rien dans ce qui est collecté n'a changé, votre adresse IP n'est toujours jamais lue ou stockée, et chaque interrupteur fonctionne exactement comme avant (codegraph telemetry off, CODEGRAPH_TELEMETRY=0, DO_NOT_TRACK=1). TELEMETRY.md reste la liste complète champ par champ.

Correctifs

Meilleures réponses de codegraph_explore

  • Nommer un fichier par son chemin dans une requête codegraph_explore fonctionne désormais de manière fiable : le chemin est résolu par rapport à l'index et ce fichier a la garantie d'une place en haut de la réponse. Auparavant, le chemin était divisé en fragments - des segments d'itinéraire entre parenthèses comme le [id] de SvelteKit rendaient la situation pire - et des morceaux comme page ou runs correspondaient à tous les fichiers frères, de sorte que le fichier que vous avez réellement nommé pouvait être complètement exclu de la réponse. Un chemin qui ne correspond à aucun fichier indexé est désormais appelé au lieu d'être ignoré en silence.
  • Nommer un fichier kebab-case sans son extension dans une requête codegraph_explore — background-image-table plutôt que background-image-table.tsx, la façon dont les chemins d'importation et la prose l'épelent — renvoie désormais également ce fichier exact. Auparavant, le nom était divisé au niveau des traits d'union, et dans une interface en forme de kebab, ces morceaux (background, image, table) sont parmi les mots les plus courants dans la base de code, donc des fichiers frères et sœurs similaires remplissaient la réponse alors que le fichier nommé n'apparaissait jamais. Les mots avec trait d'union qui ne nomment pas un fichier indexé, comme « appel croisé » ou « non bloquant », sont laissés seuls.
  • Les questions codegraph_explore formulées de manière claire trouvent désormais le code camelCase : une requête telle que "défilement automatique vers le bas" peut atteindre une fonction nommée scrollFeedToBottom, car les mots de la requête sont comparés aux mots à l'intérieur des identifiants, pas seulement aux noms entiers.
  • Les variables et les constantes comptent désormais lorsque codegraph_explore sélectionne ses symboles de départ, donc l'état conservé dans des variables simples — les variables de style $state dans Svelte, par exemple — n'est plus négligé.
  • codegraph_explore concentre désormais sa réponse sur le code qui répond réellement à votre question au lieu de la répartir dans des fichiers qui partagent simplement un mot avec lui, de sorte qu'une plus grande partie de la réponse arrive en un seul appel. Merci @LeDuyViet pour les mesures détaillées et la reproduction. (#1500)
  • Les fichiers faiblement liés à votre question reviennent désormais sous la forme d'un nom, d'un symbole et d'un numéro de ligne au lieu de dépenser la réponse sur leur source - nommez-en un dans un suivi codegraph_explore pour le récupérer dans son intégralité. (#1500)
  • Une couche CRUD ou protobuf générée n'évince plus le code écrit à la main qui se trouve à côté : les fichiers générés sont désormais reconnus par la bannière de style // Code generated by … DO NOT EDIT. écrite en haut du fichier, et non seulement par un nom de fichier qui semble généré. Réindexez après la mise à niveau pour récupérer la nouvelle détection. (#1500)
  • Les fichiers de test et de spécifications dans le répertoire test/ ou spec/ de niveau supérieur d'un référentiel sont désormais reconnus comme tels, ils ne prennent donc plus de place dans le code que vous avez demandé. (#1500)
  • Les fichiers de déclaration de type générés qui s'annoncent avec une bannière « Généré par… en exécutant… » (le worker-configuration.d.ts de Cloudflare Wrangler est le plus courant) sont désormais reconnus comme générés. Auparavant, un fichier comme celui-ci pouvait prendre la majeure partie d'une réponse codegraph_explore sur seulement quelques mots courants, repoussant entièrement le code écrit à la main que vous aviez demandé de la réponse. Réindexez après la mise à niveau pour récupérer la nouvelle détection.
  • Un fichier de déclaration de type écrit à la main — un .d.ts ambiant de cales globales, de typages vendus, d'augmentation de module — ne prend plus en charge une réponse codegraph_explore sur le fonctionnement de quelque chose. Des fichiers comme ceux-ci déclarent des noms communs (Body, Message, ImageMetadata) et rien d'autre, de sorte qu'une question formulée clairement pourrait en correspondre suffisamment pour qu'elle se classe en première position et exclue le gestionnaire réel de la réponse. Ils sont désormais moins bien classés pour les questions sur le comportement et sont toujours répertoriés par nom afin qu'un appel de suivi les récupère. Demander un type par son nom renvoie toujours sa déclaration en premier, et un module de types partagés n'affecte pas le reste de vos importations de code.
  • Lorsque vous nommez un symbole dans une requête codegraph_explore, sa définition revient désormais réellement. Deux cas l'avaient déjà perdu. Si les symboles que vous avez nommés ne s'appellent pas les uns les autres (les fonctions frères au sein de la même usine ou du même module en sont l'exemple quotidien) CodeGraph a arrêté de les traiter comme des symboles que vous aviez demandés et a répondu avec ce qui se trouvait en haut de leur fichier à la place ; sur un fichier de 1 400 lignes, cela signifiait qu'une interface QueuedMessage de même tige sur la ligne 70 revenait alors que la fonction queueMessage sur la ligne 1087 ne le faisait pas. Et lorsqu'une réponse devait être découpée pour s'adapter, elle était découpée du bas du fichier vers le bas, de sorte qu'un symbole situé à la fin d'un long fichier était toujours la première chose coupée. Le découpage protège désormais les définitions que vous avez nommées où qu'elles se trouvent dans le fichier.
  • Un fichier construit autour d'une très longue fonction ne prend plus la réponse entière du codegraph_explore pour lui-même – ou en disparaît. Auparavant, un tel fichier était affiché dans son intégralité, quelle que soit sa taille, ce qui occupait de l'espace à chaque fichier nécessaire, et lorsque la fonction était plus grande que la réponse entière, le fichier était supprimé sans un mot. Ces fichiers reviennent désormais sous la forme d'une fenêtre délimitée sur des lignes entières - la signature et le haut du corps, plus le site d'appel lorsque le chemin d'appel le traverse - le reste étant à un suivi de codegraph_explore.
  • codegraph_explore ne laisse plus le premier fichier d'une réponse occuper l'espace réservé aux fichiers en dessous, donc le reste de la réponse arrive quand même. Auparavant, un gros fichier situé en haut de la page pouvait tranquillement utiliser tout ce qui restait, et les fichiers classés en dessous – chacun déjà jugé suffisamment pertinent pour être inclus – étaient supprimés sans aucune source ; sur une question, une seule sur six a été incluse dans la réponse. Chaque fichier conserve désormais ce qui lui a été donné, et une question qui concerne réellement un fichier se concentre toujours sur ce fichier.
  • Lorsqu'une réponse codegraph_explore atteint sa limite de taille, elle supprime désormais les notes de fin plutôt que la source entière d'un fichier. Auparavant, le dernier fichier était coupé alors que couper uniquement les notes aurait suffi, donc un fichier qui avait déjà été lu, classé et rendu était jeté au dernier moment. Sur une gamme de projets réels, cela renvoie un fichier supplémentaire et jusqu'à 20 % de source en plus par appel.
  • Chaque fichier que codegraph_explore décide d'inclure arrive maintenant. Un fichier affiché dans son intégralité pouvait toujours occuper de l'espace réservé aux fichiers situés en dessous - le correctif ci-dessus couvrait les fichiers affichés sous forme d'extraits mais pas les fichiers affichés dans leur intégralité - et la comptabilité de la taille de la réponse sous-estimait l'en-tête de chaque fichier, de sorte que la réponse dépassait sa limite et un fichier entièrement préparé était supprimé à la fin. Un fichier qui ne rentre plus dans son intégralité est désormais affiché sous forme d'extraits au lieu de disparaître, et celui qui dépasse un peu est coupé pour s'adapter plutôt que supprimé.
  • La liste des fichiers qu'une réponse n'a pas pu couvrir — les pointeurs « explorer ces noms pour trouver leur source » — n'est plus jetée lorsque la réponse est pleine. Il est maintenant budgétisé et ajusté pour s'adapter, de sorte qu'une réponse complète vous indique toujours ce qu'elle a laissé de côté et quels noms demander ensuite, au lieu de se terminer sans aucune indication.
  • Lorsqu'une réponse codegraph_explore affiche un fichier sous forme d'extraits, un extrait volumineux qui ne correspondait plus a été entièrement supprimé au lieu d'être raccourci. Si le premier extrait du fichier s'avérait trivial – un bloc d'importation, une aide sur une ligne à côté du code sur lequel vous posiez la question – l'extrait contenant la réponse réelle était celui jeté, et le fichier revenait avec un quart de l'espace qui lui avait été attribué. Sur des projets réels, cela signifiait que le fichier le mieux classé ne livrait qu'une fraction de sa part tandis qu'un fichier beaucoup moins pertinent prenait le reste. Les extraits sont désormais raccourcis pour s'adapter, méthode entière par méthode entière, et supprimés uniquement lorsque ce qui reste est trop petit pour contenir quoi que ce soit de lisible.
  • La section de rayon d'explosion du codegraph_explore signalait "aucun test de couverture trouvé" chaque fois qu'aucun test n'appelait directement un symbole - qualifiant faussement les assistants qui testent l'exercice via leurs appelants de non testés (environ 40 % des symboles signalés dans un échantillon mesuré). La vérification suit désormais les chaînes d'appelants jusqu'à 3 sauts et signale la couverture indirecte comme « testée via les appelants » ; lorsque rien n'est trouvé, il indique exactement ce qui a été vérifié au lieu d'un avertissement inconditionnel. Merci @inth3shadows d'avoir mesuré le taux de faux positifs. (#1475)
  • Lorsqu'un fichier était modifié sur le disque après sa dernière synchronisation d'index, codegraph_node et codegraph_explore pouvaient renvoyer le code d'un symbole différent sous le nom demandé (octets du fichier actuel coupés à des positions de ligne obsolètes) tout en le présentant comme une source textuelle digne de trust. Cela a touché plus durement les projets interrogés via projectPath (par exemple, les sous-projets d'un monorepo), qui n'ont pas d'observateur de fichiers en direct pour signaler les modifications en attente. Les deux outils vérifient désormais chaque fichier par rapport à l'index avant d'afficher le code découpé : un fichier obsolète est soit affiché dans son intégralité avec sa source actuelle complète, soit son code est masqué avec une notification claire "modifié sur le disque" - jamais servi comme une mauvaise tranche. Une nouvelle réindexation rétablit automatiquement la sortie normale. Merci @inth3shadows pour le rapport détaillé et les passes de vérification. (#1474)

Trouver votre projet, les mises à jour en direct et le CLI

  • Le serveur MCP trouve désormais votre projet lorsqu'il est lancé à partir d'un dossier d'espace de travail situé au-dessus de lui : si le répertoire de lancement n'a pas d'index propre mais qu'exactement un projet indexé se trouve en dessous (un conteneur de dépôt, un espace de travail d'agent, une racine monorepo), ce projet devient le projet par défaut de la session - surveillance des fichiers en direct et démon partagé inclus - au lieu que chaque appel d'outil échoue jusqu'à ce qu'un projectPath ou un --path soit fourni. Merci @nakisen. (#1606)
  • Lorsqu'aucun projet ne peut être résolu, le serveur MCP l'indique désormais au lieu de démarrer silencieusement : une ligne de journal de démarrage nomme le répertoire dans lequel il a recherché et les appels d'outils répertorient les sous-projets indexés qu'il peut voir à proximité afin que vous puissiez en transmettre un comme projectPath. Auparavant, le serveur semblait sain de l'extérieur alors que chaque outil n'avait discrètement aucun projet auquel répondre. Merci @nakisen. (#1607)
  • La modification d'un exclude ou d'un include de codegraph.json (ou d'un .gitignore) pendant que le serveur MCP est en cours d'exécution prend désormais effet immédiatement. Auparavant, l'observateur de fichiers en cours d'exécution conservait la portée qu'il avait au démarrage, de sorte qu'un fichier nouvellement exclu était supprimé par codegraph sync, puis discrètement ré-ajouté par l'observateur quelques secondes plus tard - ce qui donnait l'impression que exclude ne fonctionnait pas du tout - jusqu'à ce que le serveur soit redémarré. Un changement de portée actualise désormais l'observateur et déclenche une réconciliation complète, et un fichier modifié que l'observateur doit synchroniser est d'abord revérifié par rapport à la portée actuelle, de sorte que le CLI et le serveur en direct ne peuvent plus être en désaccord sur ce qui appartient à l'index. Merci @K1nG11. (#1590)
  • codegraph status voit désormais les nouveaux fichiers dans de tout nouveaux répertoires. Git signale un répertoire entièrement non suivi sous la forme d'une seule entrée réduite, de sorte que les fichiers sources créés ici – un frontend/ fraîchement échafaudé, par exemple – étaient absents du rapport des modifications en attente, qui pourrait prétendre que tout était à jour alors que ces fichiers n'avaient pas encore été indexés. Merci @maxmilian. (#1213)
  • La commande codegraph context <task> documentée dans l'aide de CLI existe désormais réellement — elle crée un pack de contexte prêt à injecter pour une tâche (symboles pertinents, leurs relations et code) dans markdown ou JSON, restaurant le contrat sur lequel s'appuient les intégrations externes comme Memorix (--path, --format json, --max-nodes, --no-code). (#1611)
  • Sous Windows, le hook d'invite Claude Code écrit par codegraph install échouait avec "command not found" lorsque les hooks s'exécutaient via Git Bash, qui a besoin de l'extension .cmd pour trouver le lanceur. Le programme d'installation écrit maintenant la commande adaptée à la plate-forme et la réexécution de codegraph install (ou codegraph upgrade) répare une installation existante en place. (#1466)
  • La recherche d'un symbole par son nom ne lit plus l'intégralité du graphique. Chaque recherche effectuait un passage complet sur tous les symboles indexés pour chaque mot que vous avez tapé, et une question qui nommait plusieurs symboles effectuait deux passages supplémentaires par nom, y compris pour un mot qui ne correspond à rien, ce qui est le cas courant. Le coût a donc augmenté avec la taille du projet, et il a été payé à nouveau pour chaque message lorsque le hook d'invite est activé. Ces recherches passent désormais par l'index des noms. Les résultats sont identiques ; seul le temps de les obtenir change, et il n'évolue plus avec le projet. Merci @maxmilian.

Fiabilité de l'indexation et utilisation du disque

  • L'indexation ne fait plus planter l'ensemble du processus - une erreur de segmentation sans message ni index partiel - sur un fichier C/C++ (ou tout autre) avec une imbrication extrêmement profonde, comme les tests de stress de l'analyseur dans les suites de tests clang et gcc ou un corpus fuzzer. Un tel fichier est maintenant transmis à l'analyseur de secours et enregistré avec un avertissement d'analyse pendant que le reste du référentiel est indexé normalement. Merci @apollo600 pour le diagnostic exact. (#1581)
  • L'indexation ne se bloque plus sur un projet Swift Vapor contenant un appel avec une longue liste d'arguments. Un seul appel de style .get(...) avec de nombreux arguments étiquetés et aucun gestionnaire use: (ce que produisent les générateurs de requêtes générées par la forme) pourrait bloquer indéfiniment codegraph index, codegraph sync et le serveur MCP. La détection d'itinéraire gère désormais ces fichiers en millisecondes, et chaque forme d'itinéraire précédemment reconnue est toujours analysée exactement comme avant. Merci @maxmilian. (#1544) (Rapide)
  • La synchronisation d'un grand lot de fichiers modifiés ne plante plus avec "Taille maximale de la pile d'appels dépassée" en cours de route. Le crash a interrompu la résolution de référence une fois que les symboles des fichiers étaient déjà stockés, laissant le graphique avec beaucoup moins de connexions qu'un nouvel index n'en aurait - et il a frappé exactement les scénarios qui réanalysent plusieurs fichiers à la fois, y compris la réparation automatique ci-dessus. Merci @netbrah d'avoir identifié l'échec. (#1558)
  • Un indice de longue durée ne s'éloigne plus de ce que produirait un nouveau codegraph index. Lorsqu'un fichier gagnait ou perdait un symbole, les références à ce nom dans les fichiers que la synchronisation n'avait jamais touchés pointaient toujours vers la définition qui était correcte avant le changement, et - parce que rien ne distinguait deux définitions du même nom - le gagnant pouvait se résumer à l'ordre dans lequel les fichiers étaient écrits, ce qui diffère entre un index complet et une synchronisation. Sur le propre référentiel de ce projet, la relecture de 80 commits via sync a laissé 5.7 % de connexions erronées ; il est maintenant de 1.3%, et la moitié des mauvaises réponses toujours affirmées diminue de 99.7%. Étant donné que les bords d'appel sont ce que suivent les questions de flux et ce par quoi codegraph_explore classe les fichiers, cela dégrade discrètement les réponses comme un index vieilli, sans rien pour l'indiquer. La vitesse de synchronisation reste inchangée et une modification qui modifie uniquement le corps d'une fonction ne génère aucun travail supplémentaire. Configurez CODEGRAPH_NO_REBIND=1 pour vous désinscrire.
  • Correction d'une régression v1.5.0 où un fichier parfaitement valide pouvait être enregistré en permanence comme ayant 0 symbole, sans qu'aucune erreur ne soit signalée. Lorsque la première tentative d'analyse d'un fichier était interrompue (un crash ou un délai d'attente du processeur d'analyse, probablement sur des machines lentes ou très chargées), la nouvelle tentative automatique stockait un résultat vide pour n'importe quelle langue sur le chemin d'extraction natif, de sorte que les fonctions et les classes du fichier disparaissaient silencieusement de la recherche, des appelants et de l'impact jusqu'à la prochaine modification du fichier. Les nouvelles tentatives stockent désormais les vrais symboles du fichier, et un fichier déjà enregistré sans symbole est détecté et réparé automatiquement lors de la prochaine synchronisation ou réindexation après la mise à niveau. Merci @Baiae pour le rapport. (#1541)
  • Un processus CodeGraph qui est tué de force - par le chien de garde du processus bloqué, un crash ou le système d'exploitation - ne laisse plus le journal d'écriture anticipée de la base de données derrière lui pour croître sans limite. Auparavant, chaque session supprimée empilait plus de données dans le même fichier journal et rien ne les réduisait, ce qui, sur les machines où les sessions étaient régulièrement interrompues, pouvait tranquillement consommer des dizaines de gigaoctets de disque. La taille restante du journal est désormais limitée (64 Mo par défaut ; CODEGRAPH_WAL_HEAL_MB la modifie), et tout reste surdimensionné est replié dans l'index et rogné automatiquement à la prochaine ouverture du projet. Cela limite uniquement le journal — l'index lui-même n'a pas de limite de taille et le journal d'un grand référentiel peut toujours croître proportionnellement à son index pendant sa construction. Merci @tiendungdev pour le rapport Windows exceptionnel qui a cerné cela. (#1431)
  • Le chien de garde du serveur d'arrière-plan ne tue plus un serveur sain qui attend juste sur un disque lent : comme le fait déjà l'indexation, il vérifie désormais si les fichiers de la base de données progressent toujours avant de conclure que le processus est bloqué. Moins de suppressions intempestives signifie également moins de journaux d’écriture anticipée restants. (#1431)
  • codegraph status affiche désormais la taille du journal d'écriture anticipée à côté de la taille de la base de données et avertit lorsque les sessions interrompues l'ont laissé surdimensionné, et chaque ligne du journal du serveur en arrière-plan porte désormais un horodatage afin que les suppressions et les redémarrages puissent être placés à temps. (#1431)
  • Un démon en arrière-plan laissé par un kill par manque de mémoire ou par un kill forcé ne peut plus bloquer chaque session future lorsque le système d'exploitation réutilise son ID de processus : la gestion du démon vérifie désormais qu'un processus enregistré est bien un démon CodeGraph avant de le trust le signaler ou de le signaler, et codegraph unlock efface les artefacts du démon obsolètes ainsi que le verrou d'indexation. Merci @hcg1023 pour le rapport et @danusha2345 pour le correctif. (#1553)
  • Lorsque l'indexation doit revenir à l'analyse d'un fichier avec ses lignes de commentaires supprimées (une récupération de dernier recours après des pannes répétées de l'analyseur), le fichier est désormais signalé par un avertissement visible au lieu d'être signalé comme correctement indexé. Le résultat récupéré peut être incomplet et le succès du rapport fait qu'un nouvel index est en désaccord discret avec une réanalyse ultérieure du même fichier inchangé. Merci @jeremypetz pour la comptabilité précise des symboles init-versus-sync qui a exposé cela. (#1565)
  • Les en-têtes C/C++ de données uniquement proches de la limite de taille de fichier ne retiennent plus un analyseur pendant plusieurs minutes avant d'expirer ; le budget d'analyse par défaut des fichiers volumineux est désormais limité, tandis qu'un délai d'attente plus long explicitement configuré est toujours respecté. (#1555)
  • La réouverture d'un index après un crash lors d'un chargement groupé restaure désormais chaque index de base de données supprimé, et une synchronisation de récupération réussie marque l'index comme terminé au lieu de le laisser définitivement marqué comme interrompu. (#1556)
  • Les fichiers ignorés parce qu'ils sont trop volumineux ou échouent à plusieurs reprises à être analysés sont désormais enregistrés avec la raison, de sorte que les fichiers rejetés inchangés ne sont plus couverts par redis et réessayés à chaque vérification d'état et synchronisation - et une analyse ultérieure réussie d'un tel fichier remplace l'enregistrement par ses vrais symboles. Merci @netbrah pour l'analyse exceptionnelle des échecs derrière ce lot, et @danusha2345 pour les correctifs. (#1557)
  • L'analyse du pointeur de fonction C/C++ limite désormais ses caches de modèles compilés, de sorte que les très grands référentiels ne peuvent plus épuiser l'espace de code d'expression régulière du moteur JavaScript lors de l'indexation. (#1559)
  • L'analyse du rendu JSX s'exécute désormais uniquement sur les fichiers de la famille JavaScript, de sorte que les chaînes d'apparence JSX en C/C++ (ou tout autre langage) ne créent plus de bords d'appel impossibles — dans les projets en C pur et dans les monorepos en langage mixte. (#1560)

Précision du langage et du framework

  • Les appels aux méthodes d'une constante littérale objet exportée — export const api = { call() { … } } utilisé comme espace de noms de module, une manière courante d'organiser une surface TypeScript API — sont désormais résolus en méthode, à la fois dans le fichier de définition et via les importations. Auparavant, un tel appel n'était lié à rien (ou à la constante elle-même), donc codegraph callers et l'analyse d'impact n'ont signalé aucun appelant pour les méthodes appelées de partout. Réindexez après la mise à niveau pour récupérer les bords. Merci @IAliceBobI pour le rapport précis et la cause profonde. (#1573)
  • Les alias d'importation définis dans une configuration TypeScript partagée sont désormais récupérés. Les monorepos de style Nx conservent chaque alias @scope/... dans un tsconfig.base.json dont la racine tsconfig.json hérite uniquement via extends. CodeGraph n'a donc trouvé aucun alias et chaque importation entre packages s'est basée sur la correspondance sur le nom seul - ce qui attache discrètement les résultats à des symboles non liés qui partagent un nom, exactement là où un monorepo a besoin de codegraph_impact et codegraph_callers. c'est vrai. Les chaînes de plusieurs configurations profondes, une configuration héritée d'un package dans node_modules et un baseUrl déclaré dans une configuration héritée sont toutes suivies désormais, et un tsconfig.base.json est lu directement lorsque la racine tsconfig.json n'est qu'un shell de références de projet ou n'est pas là du tout. Réindexez après la mise à niveau. Merci @maxmilian. (#1534)
  • Les méthodes implémentées dans un bloc impl générique ou paramétré à vie (impl<T> Source for BufSource<T>, impl<'a> Iterator for Parents<'a>) sont désormais enregistrées sous le type d'implémentation au lieu du trait. Auparavant, une telle méthode ne pouvait pas être trouvée par son type - "qui appelle BufSource::read" n'avait pas de réponse - et elle entrait en collision avec la propre déclaration du trait, qui pouvait même inventer un bord de graphe d'appel à partir d'un corps impl ne contenant aucun appel. Les implicites sur une référence (impl Trait for &Foo) et sur un type qualifié de module (impl Trait for m::Foo) sont également attribués à leur type. Réindexez après la mise à niveau. Merci @Dshuishui. (#1588) (Rust)
  • Un appel de méthode sur un champ struct — self.inner.run() avec inner: Inner — est désormais résolu en méthode sur le type déclaré du champ. Auparavant, l'appel était réduit au nom de la méthode nue et correspondait à la méthode du même nom la plus proche, qui était souvent la méthode appelante elle-même, enregistrant une récursion qui n'est pas dans la source (quelques centaines de ces auto-bords dans ripgrep seul), ou une méthode d'un type sans rapport. Les références et les champs Box/Rc/Arc sont parcourus, tout comme les propres appels de méthode de Rust ; un champ dont le type est externe (un type std ou tiers), un paramètre générique ou un conteneur comme Option/Vec est laissé non résolu plutôt que deviné. Réindexez après la mise à niveau. Merci @Dshuishui. (#1585) (Rust)
  • Les fonctions Erlang qui partagent un nom mais diffèrent par leur arité sont désormais des symboles séparés avec la propre identité module:fun/arity du langage, de sorte que le f/1 quotidien qui délègue à f/2 s'affiche comme un véritable bord d'appel au lieu d'une boucle automatique, chaque arité conserve son propre -spec et sa propre étendue source, -export([f/1]) marque exactement cette arité comme publique et demande à codegraph_explore un symbole comme Erlang. l'épelle - cowboy_req:header/3 - renvoie cette définition. Réindexez les projets Erlang après la mise à niveau. Merci @Dshuishui. (#1610) (Erlang)
  • La répartition du comportement Erlang ne compte plus mal l'arité d'un site d'appel lorsqu'un argument est un littéral binaire comme <<1,2,3>> — les virgules à l'intérieur étaient comptées comme séparateurs d'arguments, ce qui supprimait silencieusement (ou pouvait mal lier) le bord de répartition au rappel de comportement. (#1358) (Erlang)
  • Un en-tête C++ .h dont la seule construction C++ est un type dérivé simple — struct Derived : Base sans macro d'exportation, mot clé class ou section d'accès — est désormais reconnu comme C++ (auparavant, seule la forme de macro d'exportation l'était). Un tel en-tête était lu comme C, donc la structure dérivée disparaissait de l'index et une fonction fantôme nommée d'après le type de base apparaissait à sa place. La vérification couvre désormais également l'intégralité du fichier plutôt que ses premiers kilo-octets, de sorte qu'un long préambule compatible C ne cache plus le signal. Réindexez après la mise à niveau pour récupérer les en-têtes concernés. Merci @Jaysenpeng. (#1592)
  • Les unions C, C++, Objective-C et Rust sont désormais indexées en tant que nœuds union de première classe. Une déclaration union ne produisait auparavant aucun symbole, elle n'apparaissait donc jamais dans la recherche ou dans codegraph_explore, et tout ce qui y était attaché disparaissait avec elle - dans Rust, chaque impl SomeTrait for MyUnion perdait son avantage, les méthodes de cet impl étaient laissées pointer vers un type que le graphe ne contenait pas, et demander quels types implémentaient un trait ignorait discrètement celles de l'union. Une table de répartition en forme d'union en C résout désormais ses pointeurs de fonction comme une table de répartition en forme de structure. Un typedef union { … } Name; en C conserve le nom du typedef et n'est plus confondu avec un alias de type simple. Merci @ctype-lab. Réindexez après la mise à niveau pour récupérer les syndicats dans les projets existants. (#1515)
  • Classes Python utilisées comme valeurs — return SomeSerializer à partir d'une méthode d'usine, alias handler = SomeClass, dictionnaires et listes de registre et classes passées en arguments — produisent désormais des arêtes de référence dans le graphique. Auparavant, ces idiomes étaient invisibles, donc sur les projets Django et Django REST Framework, demander les appelants d'un sérialiseur ou l'impact de sa modification manquait les vues qui l'utilisent réellement. Réindexez après la mise à niveau pour récupérer les nouveaux bords. (#1478)
  • Les importations SAP HANA .xsjs / .xsjslib sont désormais résolues dans tous les fichiers : un import { x } from './helpers' sans extension dans un fichier .xsjs trouve helpers.xsjslib, donc le bord d'appel inter-fichiers est créé et codegraph_callers / codegraph_impact le voit. Auparavant, le chemin d'importation n'aboutissait à rien et l'appel revenait à la correspondance du même nom, ce qui pouvait lier le bord à un fichier sans rapport qui exportait le même symbole. Complète le support d'extraction .xsjs / .xsjslib. Merci @maxmilian. (#556)

codegraph v1.6.0

[1.6.0] - 2026-08-26

Highlights

  • GitHub Copilot is now supported — codegraph install sets it up in VS Code, the Copilot CLI, and JetBrains IDEs, next to the agents it already knew.
  • Set up in one command — codegraph install --yes --init wires up your agents and indexes your project with no prompts, ideal for a fresh container or CI.
  • Better answers for your agent — codegraph_explore no longer repeats code it already showed you, always brings back the files and symbols you asked for by name, and spends its space on the code that actually answers the question rather than look-alikes, generated files, and type shims.
  • Your graph stays right as you keep coding — a long-running index no longer drifts from a fresh one, and edits to codegraph.json (such as exclude) apply immediately without a restart.
  • No more silent crashes or hangs — deeply nested C/C++ files, Swift Vapor projects, and large sync batches that used to kill or stall indexing now finish cleanly.
  • A disk-space leak is fixed — a force-killed session could leave the database's write-ahead log behind to grow without bound (tens of gigabytes was reported); the leftover log is now folded back into the index and trimmed automatically the next time the project opens. The index itself has no size limit.
  • Works from a workspace or monorepo root — the MCP server finds your indexed project when launched from a folder above it, and says so clearly when it can't find one.
  • More accurate code graphs for TypeScript, Rust, Erlang, C/C++, and Python projects — see the full list below.
  • Also new: per-project Codex setup (codegraph install --location=local), a deprioritize setting to keep helper folders from outranking your real code, the codegraph context command, and usage stats that now stay entirely on CodeGraph's own servers.

After upgrading, run codegraph index once in each project so your existing graph picks up these fixes — codegraph status reminds you when it's needed.

New Features

  • GitHub Copilot is now a supported agent: codegraph install can configure Copilot Chat in VS Code (copilot-vscode), the GitHub Copilot CLI (copilot-cli), and the Copilot plugin in JetBrains IDEs (copilot-jetbrains). Installed Copilot surfaces are auto-detected like every other agent, existing MCP server entries in their config files are preserved, and codegraph uninstall reverses the setup cleanly. Restart VS Code or your JetBrains IDE after installing so Copilot picks up the server.

  • codegraph install --init wires up your agents and builds the current project's index in one command, and codegraph init --yes runs without any prompts — so a fresh container or CI job can bootstrap CodeGraph with a single non-interactive line (codegraph install --yes --init). The installer still never indexes anything unless you ask for it with the flag, and the usual safety refusal for a home directory or filesystem root applies. (#1578)

  • Codex CLI can now be set up per project instead of only user-wide: codegraph install --location=local writes ./.codex/config.toml and the CodeGraph block in your project's AGENTS.md, so CodeGraph is wired into that repo only rather than every Codex session on the machine. codegraph uninstall --location=local reverses it, and the global install is untouched either way. Codex only applies a project's config once you've marked the project trusted, so the installer says so after a local install. Thanks @maxmilian. (#1531)

  • A new deprioritize setting in codegraph.json keeps the paths you name from outranking your product code in search and codegraph_explore answers, without removing anything from the index. It takes gitignore-style patterns just like exclude, but is ranking-only: helper-script trees, generated output, or optional add-on directories whose generic symbol names (usage, run, status) would otherwise crowd out the code that actually answers a query stay fully indexed and findable — and a query that genuinely targets such a tree still returns it. Thanks @maxmilian. (#982)

  • codegraph_explore no longer re-sends source it already returned earlier in the same conversation. A file it has already shown you comes back as a short pointer — the path, the symbols and the exact line range, with confirmation that the file hasn't changed since — and the space that frees is spent on code you haven't seen yet, so a follow-up call covers new ground instead of repeating the last one. If a file was edited in between, its source is always shown again in full. Set CODEGRAPH_EXPLORE_DEDUP=0 to turn this off.

  • When an agent connects over MCP, CodeGraph now states up front that it indexes 30+ languages — TypeScript/JavaScript, Python, Go, Rust, Java, C#, C/C++, PHP, Ruby, Swift, Kotlin, and more — so agents no longer assume a language isn't supported and skip the graph. (#671)

  • Anonymous usage telemetry is now stored entirely on CodeGraph's own first-party infrastructure — no third-party analytics vendor receives any of it, and the endpoint that receives it makes no outbound requests at all. Individual events are deleted after 90 days, leaving only anonymous daily totals. Nothing about what is collected changed, your IP address is still never read or stored, and every off-switch works exactly as before (codegraph telemetry off, CODEGRAPH_TELEMETRY=0, DO_NOT_TRACK=1). TELEMETRY.md remains the complete field-by-field list.

Fixes

Better answers from codegraph_explore

  • Naming a file by its path in a codegraph_explore query now works reliably: the path is resolved against the index and that file is guaranteed a place at the top of the answer. Previously the path was broken into fragments — bracketed route segments like SvelteKit's [id] made this worst — and pieces like page or runs matched every sibling file, so the file you actually named could be crowded out of the answer entirely. A path that doesn't match any indexed file is now called out instead of silently ignored.

  • Naming a kebab-case file without its extension in a codegraph_explore query — background-image-table rather than background-image-table.tsx, the way import paths and prose spell it — now returns that exact file too. Previously the name was split at the hyphens, and in a kebab-cased frontend those pieces (background, image, table) are among the most common words in the codebase, so look-alike sibling files filled the answer while the named file never appeared. Hyphenated words that don't name an indexed file, like "cross-call" or "non-blocking", are left alone.

  • Plainly-worded codegraph_explore questions now find camelCase code: a query like "auto-scroll to bottom" can reach a function named scrollFeedToBottom, because query words are matched against the words inside identifiers, not just whole names.

  • Variables and constants now count when codegraph_explore picks its starting symbols, so state held in plain variables — $state-style variables in Svelte, for example — no longer gets overlooked.

  • codegraph_explore now concentrates its answer on the code that actually answers your question instead of spreading it across files that merely share a word with it, so more of the answer arrives in a single call. Thanks @LeDuyViet for the detailed measurements and reproduction. (#1500)

  • Files only weakly related to your question now come back as a name, symbol and line number instead of spending the answer on their source — name one of them in a follow-up codegraph_explore to get it back in full. (#1500)

  • A generated CRUD or protobuf layer no longer crowds out the hand-written code sitting beside it: generated files are now recognized by the // Code generated by … DO NOT EDIT. style banner written at the top of the file, not just by a filename that looks generated. Re-index after upgrading to pick up the new detection. (#1500)

  • Test and spec files in a repository's top-level test/ or spec/ directory are now recognized as such, so they no longer take room from the code you asked about. (#1500)

  • Generated type-declaration files that announce themselves with a "Generated by … by running …" banner — Cloudflare Wrangler's worker-configuration.d.ts is the common one — are now recognized as generated. Previously a file like that could take most of a codegraph_explore answer on nothing more than a few common words, pushing the hand-written code you asked about out of the response entirely. Re-index after upgrading to pick up the new detection.

  • A hand-written type-declaration file — an ambient .d.ts of global shims, vendored typings, module augmentation — no longer takes over a codegraph_explore answer about how something works. Files like these declare common names (Body, Message, ImageMetadata) and nothing else, so a plainly-worded question could match one strongly enough that it ranked first and crowded the actual handler out of the answer. They are now ranked lower for questions about behaviour, and are still listed by name so one follow-up call fetches them. Asking about a type by name still returns its declaration first, and a shared types module the rest of your code imports is unaffected.

  • When you name a symbol in a codegraph_explore query, its definition now actually comes back. Two cases previously lost it. If the symbols you named don't call one another — sibling functions inside the same factory or module are the everyday example — CodeGraph stopped treating them as symbols you had asked for, and answered with whatever sat at the top of their file instead; on one 1,400-line file that meant a same-stem QueuedMessage interface on line 70 came back while the queueMessage function on line 1087 did not. And when an answer had to be trimmed to fit, it was trimmed from the bottom of the file down, so a symbol near the end of a long file was always the first thing cut. Trimming now protects the definitions you named wherever they sit in the file.

  • A file built around one very long function no longer takes the whole codegraph_explore answer for itself — or disappears from it. Previously such a file was shown in full however big it was, which used up the room every file after it needed, and when the function was larger than the entire response the file was dropped without a word. These files now come back as a bounded window on whole lines — the signature and the top of the body, plus the call site when the call path runs through it — with the rest one follow-up codegraph_explore away.

  • codegraph_explore no longer lets the first file in an answer spend the room set aside for the files below it, so the rest of the answer still arrives. Previously a large file near the top could quietly use up everything left, and the files ranked under it — each already judged relevant enough to include — were dropped with no source at all; on one question only one of six made it into the answer. Every file now keeps what it was given, and a question that really is about one file still concentrates on that file.

  • When a codegraph_explore answer runs right up against its size limit, it now drops the trailing notes rather than a whole file's source. Previously the last file was cut even though trimming the notes alone would have fit, so a file that had already been read, ranked and rendered was thrown away at the last moment. Across a range of real projects this returns one more file and up to 20% more source per call.

  • Every file codegraph_explore decides to include now actually arrives. A file shown in full could still spend room set aside for files below it — the fix above covered files shown as excerpts but not files shown whole — and the answer's own size bookkeeping under-counted each file's heading, so the answer ran past its limit and a fully prepared file was discarded at the end. A file that no longer fits whole is now shown as excerpts instead of vanishing, and one that overshoots by a little is trimmed to fit rather than dropped.

  • The list of files an answer could not cover — the "explore these names for their source" pointers — is no longer thrown away when the answer is full. It is now budgeted for and trimmed to fit, so a full answer still tells you what it left out and which names to ask for next, instead of ending with no pointers at all.

  • When a codegraph_explore answer shows a file as excerpts, a large excerpt that no longer fit was dropped entirely instead of being shortened. If the file's first excerpt happened to be a trivial one — an import block, a one-line helper next to the code you asked about — the excerpt carrying the actual answer was the one thrown away, and the file came back with a quarter of the room it had been given. On real projects that meant the top-ranked file delivered a fraction of its share while a far less relevant file took the rest. Excerpts are now shortened to fit, whole method by whole method, and only dropped when what is left is too small to hold anything readable.

  • The blast-radius section of codegraph_explore flagged "no covering tests found" whenever no test called a symbol directly — falsely branding helpers that tests exercise through their callers as untested (about 40% of flagged symbols in a measured sample). The check now follows caller chains up to 3 hops and reports indirect coverage as "tested via callers"; when nothing is found it states exactly what was checked instead of an unconditional warning. Thanks @inth3shadows for measuring the false-positive rate. (#1475)

  • When a file changed on disk after its last index sync, codegraph_node and codegraph_explore could return a different symbol's code under the requested name — current file bytes cut at outdated line positions — while presenting it as verbatim, trustworthy source. This hit hardest on projects queried through projectPath (for example, sub-projects of a monorepo), which have no live file watcher to flag pending edits. Both tools now verify each file against the index before showing sliced code: an out-of-date file is either shown whole with its full current source, or its code is withheld with a clear "changed on disk" notice — never served as a wrong slice. A fresh re-index restores normal output automatically. Thanks @inth3shadows for the thorough report and verification passes. (#1474)

Finding your project, live updates, and the CLI

  • The MCP server now finds your project when it's launched from a workspace folder above it: if the launch directory has no index of its own but exactly one indexed project sits below it (a repo container, an agent workspace, a monorepo root), that project becomes the session's default — live file watching and the shared daemon included — instead of every tool call failing until a projectPath or --path is supplied. Thanks @nakisen. (#1606)

  • When no project can be resolved at all, the MCP server now says so instead of starting silently: a startup log line names the directory it searched, and tool calls list the indexed sub-projects it can see nearby so you can pass one as projectPath. Previously the server looked healthy from the outside while every tool quietly had no project to answer from. Thanks @nakisen. (#1607)

  • Editing codegraph.json's exclude or include (or a .gitignore) while the MCP server is running now takes effect immediately. Previously the running file watcher kept the scope it had when it started, so a newly excluded file was removed by codegraph sync and then quietly re-added by the watcher seconds later — which looked like exclude not working at all — until the server was restarted. A scope change now refreshes the watcher and triggers a full reconcile, and a changed file the watcher hands to sync is re-checked against the current scope first, so the CLI and the live server can no longer disagree about what belongs in the index. Thanks @K1nG11. (#1590)

  • codegraph status now sees new files inside brand-new directories. Git reports an entirely-untracked directory as a single collapsed entry, so source files created there — a freshly scaffolded frontend/, for example — were missing from the pending-changes report, which could claim everything was up to date while those files had not yet been indexed. Thanks @maxmilian. (#1213)

  • The codegraph context <task> command documented in the CLI help now actually exists — it builds a ready-to-inject context pack for a task (relevant symbols, their relationships, and code) in markdown or JSON, restoring the contract external integrations like Memorix rely on (--path, --format json, --max-nodes, --no-code). (#1611)

  • On Windows, the Claude Code prompt hook written by codegraph install failed with "command not found" when hooks run through Git Bash, which needs the .cmd extension to find the launcher. The installer now writes the platform-correct command, and re-running codegraph install (or codegraph upgrade) repairs an existing install in place. (#1466)

  • Looking a symbol up by name no longer reads the whole graph. Every search made one full pass over all indexed symbols for each word you typed, and a question that named several symbols made two more passes per name — including for a word that matches nothing, which is the common case. The cost therefore grew with the size of the project, and it was paid again on every message when the prompt hook is enabled. These lookups now go through the name index instead. Results are identical; only the time to get them changes, and it no longer grows with the project. Thanks @maxmilian.

Indexing reliability and disk usage

  • Indexing no longer crashes the whole process — a segmentation fault with no message and no partial index — on a C/C++ (or any other) file with extremely deep nesting, such as the parser stress-test fixtures in the clang and gcc test suites or a fuzzer corpus. Such a file is now handed to the fallback parser and recorded with a parse warning while the rest of the repository indexes normally. Thanks @apollo600 for the exact diagnosis. (#1581)

  • Indexing no longer hangs on a Swift Vapor project containing a call with a long argument list. A single .get(...)-style call with many labeled arguments and no use: handler — the shape generated request builders produce — could stall codegraph index, codegraph sync, and the MCP server indefinitely. Route detection now handles such files in milliseconds, and every previously-recognized route shape still parses exactly as before. Thanks @maxmilian. (#1544) (Swift)

  • Syncing a large batch of changed files no longer crashes with "Maximum call stack size exceeded" partway through. The crash aborted reference resolution after the files' symbols were already stored, leaving the graph with far fewer connections than a fresh index would have — and it hit exactly the scenarios that re-parse many files at once, including the automatic repair above. Thanks @netbrah for pinpointing the failure. (#1558)

  • A long-lived index no longer drifts away from what a fresh codegraph index would produce. When a file gained or lost a symbol, references to that name in files the sync never touched kept pointing at the definition that was correct before the change, and — because nothing distinguished two same-named definitions — the winner could come down to the order files happened to be written, which differs between a full index and a sync. On this project's own repository, replaying 80 commits through sync left 5.7% of connections wrong; it is now 1.3%, and the wrong-answers-still-being-asserted half drops by 99.7%. Since call edges are what flow questions follow and what codegraph_explore ranks files by, this quietly degraded answers as an index aged, with nothing to indicate it. Syncing is unchanged in speed, and an edit that only changes a function's body does no extra work at all. Set CODEGRAPH_NO_REBIND=1 to opt out.

  • Fixed a v1.5.0 regression where a perfectly valid file could be permanently recorded as having 0 symbols, with no error reported. When a file's first parse attempt was interrupted — a parsing worker crash or timeout, most likely on slow or heavily loaded machines — the automatic retry stored an empty result for any language on the native extraction path, so the file's functions and classes silently vanished from search, callers, and impact until the file was next edited. Retries now store the file's real symbols, and a file already recorded as symbol-free is detected and repaired automatically by the next sync or re-index after upgrading. Thanks @Baiae for the report. (#1541)

  • A CodeGraph process that gets force-killed — by the stuck-process watchdog, a crash, or the OS — no longer leaves the database's write-ahead log behind to grow without bound. Previously each killed session stacked more data onto the same log file and nothing ever shrank it, which on machines where sessions were killed regularly could quietly eat tens of gigabytes of disk. The log's resting size is now bounded (64 MB by default; CODEGRAPH_WAL_HEAL_MB changes it), and any oversized leftover is folded back into the index and trimmed automatically the next time the project is opened. This bounds only the log — the index itself has no size limit, and a large repository's log is still allowed to grow in proportion to its index while it is being built. Thanks @tiendungdev for the exceptional Windows report that pinned this down. (#1431)

  • The background server's watchdog no longer kills a healthy server that is just waiting on a slow disk: like indexing already does, it now checks whether the database files are still making progress before concluding the process is stuck. Fewer spurious kills also means fewer leftover write-ahead logs. (#1431)

  • codegraph status now shows the write-ahead log's size next to the database size and warns when killed sessions have left it oversized, and every line in the background server's log now carries a timestamp so kills and restarts can be placed in time. (#1431)

  • A background daemon left behind by an out-of-memory kill or force-kill can no longer block every future session when the operating system reuses its process ID: daemon management now verifies a recorded process is really a CodeGraph daemon before trusting or signaling it, and codegraph unlock clears stale daemon artifacts as well as the indexing lock. Thanks @hcg1023 for the report and @danusha2345 for the fix. (#1553)

  • When indexing has to fall back to parsing a file with its comment lines stripped — a last-resort recovery after repeated parser crashes — the file is now flagged with a visible warning instead of being reported as cleanly indexed. The recovered result can be incomplete, and reporting success made a fresh index quietly disagree with a later re-parse of the same unchanged file. Thanks @jeremypetz for the precise init-versus-sync symbol accounting that exposed this. (#1565)

  • Data-only C/C++ headers near the file-size limit no longer hold a parser worker for several minutes before timing out; the default large-file parse budget is now bounded, while an explicitly configured larger timeout is still honored. (#1555)

  • Reopening an index after a crash during bulk loading now restores every dropped database index, and a successful recovery sync marks the index complete instead of leaving it permanently flagged as interrupted. (#1556)

  • Files skipped because they are too large or repeatedly fail to parse are now recorded with the reason, so unchanged rejected files are no longer rediscovered and retried on every status check and sync — and a later successful parse of such a file replaces the record with its real symbols. Thanks @netbrah for the exceptional failure analysis behind this batch, and @danusha2345 for the fixes. (#1557)

  • C/C++ function-pointer analysis now bounds its compiled-pattern caches, so very large repositories can no longer exhaust the JavaScript engine's regular-expression code space during indexing. (#1559)

  • JSX rendering analysis now runs only on JavaScript-family files, so JSX-looking strings in C/C++ (or any other language) no longer create impossible call edges — in pure-C projects and in mixed-language monorepos alike. (#1560)

Language and framework accuracy

  • Calls to the methods of an exported object-literal constant — export const api = { call() { … } } used as a module's namespace, a common way to organize a TypeScript API surface — now resolve to the method, both in the defining file and through imports. Previously such a call linked to nothing (or to the constant itself), so codegraph callers and impact analysis reported zero callers for methods that are called from everywhere. Re-index after upgrading to pick up the edges. Thanks @IAliceBobI for the precise report and root-cause. (#1573)

  • Import aliases defined in a shared TypeScript config are now picked up. Nx-style monorepos keep every @scope/... alias in a tsconfig.base.json that the root tsconfig.json only inherits through extends, so CodeGraph found no aliases at all and every cross-package import fell back to matching on name alone — which quietly attaches results to unrelated symbols that happen to share a name, exactly where a monorepo needs codegraph_impact and codegraph_callers to be right. Chains several configs deep, a config inherited from a package in node_modules, and a baseUrl declared in an inherited config are all followed now, and a tsconfig.base.json is read directly when the root tsconfig.json is only a project-references shell or isn't there at all. Re-index after upgrading. Thanks @maxmilian. (#1534)

  • Methods implemented in a generic or lifetime-parameterized impl block (impl<T> Source for BufSource<T>, impl<'a> Iterator for Parents<'a>) are now recorded under the implementing type instead of the trait. Previously such a method could not be found by its type — "who calls BufSource::read" had no answer — and it collided with the trait's own declaration, which could even invent a call-graph edge out of an impl body that contains no call at all. Impls on a reference (impl Trait for &Foo) and on a module-qualified type (impl Trait for m::Foo) are attributed to their type too. Re-index after upgrading. Thanks @Dshuishui. (#1588) (Rust)

  • A method call on a struct field — self.inner.run() with inner: Inner — now resolves to the method on the field's declared type. Previously the call was reduced to the bare method name and matched whichever same-named method was nearest, which was often the calling method itself, recording recursion that isn't in the source (a few hundred such self-edges in ripgrep alone), or a method of an unrelated type. References and Box/Rc/Arc fields are looked through, as Rust's own method calls are; a field whose type is external (a std or third-party type), a generic parameter, or a container like Option/Vec is left unresolved rather than guessed. Re-index after upgrading. Thanks @Dshuishui. (#1585) (Rust)

  • Erlang functions that share a name but differ in arity are now separate symbols with the language's own module:fun/arity identity, so the everyday f/1 delegating to f/2 shows as a real call edge instead of a self-loop, each arity keeps its own -spec and source span, -export([f/1]) marks exactly that arity as public, and asking codegraph_explore for a symbol the way Erlang spells it — cowboy_req:header/3 — returns that definition. Re-index Erlang projects after upgrading. Thanks @Dshuishui. (#1610) (Erlang)

  • Erlang behaviour dispatch no longer miscounts a call site's arity when an argument is a binary literal like <<1,2,3>> — the commas inside were counted as argument separators, which silently dropped (or could mislink) the dispatch edge to the behaviour callback. (#1358) (Erlang)

  • A C++ .h header whose only C++ construct is a plain derived type — struct Derived : Base with no export macro, class keyword, or access section — is now recognized as C++ (previously only the export-macro form was). Such a header was read as C, so the derived struct vanished from the index and a phantom function named after the base type appeared in its place. The check now also covers the whole file rather than its first few kilobytes, so a long C-compatible preamble no longer hides the signal. Re-index after upgrading to pick up affected headers. Thanks @Jaysenpeng. (#1592)

  • C, C++, Objective-C and Rust unions are now indexed as first-class union nodes. A union declaration previously produced no symbol at all, so it never appeared in search or codegraph_explore, and anything attached to it disappeared with it — in Rust, every impl SomeTrait for MyUnion lost its edge, the methods from that impl were left pointing at a type the graph did not contain, and asking which types implement a trait quietly skipped the union ones. A union-shaped dispatch table in C now resolves its function pointers like a struct-shaped one. A typedef union { … } Name; in C keeps the typedef's name and is no longer mistaken for a plain type alias. Thanks @ctype-lab. Re-index after upgrading to pick up unions in existing projects. (#1515)

  • Python classes used as values — return SomeSerializer from a factory method, handler = SomeClass aliases, registry dicts and lists, and classes passed as arguments — now produce reference edges in the graph. Previously these idioms were invisible, so on Django and Django REST Framework projects, asking for a serializer's callers or the impact of editing it missed the views that actually use it. Re-index after upgrading to pick up the new edges. (#1478)

  • SAP HANA .xsjs / .xsjslib imports now resolve across files: an extensionless import { x } from './helpers' in a .xsjs file finds helpers.xsjslib, so the cross-file call edge is created and codegraph_callers / codegraph_impact see it. Previously the import path resolved to nothing and the call fell back to same-name matching, which could bind the edge to an unrelated file that happened to export the same symbol. Complements the .xsjs / .xsjslib extraction support. Thanks @maxmilian. (#556)
