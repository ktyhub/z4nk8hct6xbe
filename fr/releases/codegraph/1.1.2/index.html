codegraphe v1.1.2

[1.1.2] - 2026-06-28

Nouvelles fonctionnalités

  • Vous pouvez désormais exclure les répertoires validés de l'index avec une liste exclude dans codegraph.json — même lorsqu'ils sont suivis par git. .gitignore ne peut pas supprimer un répertoire déjà suivi par Git, donc un thème vendu ou SDK qui est archivé dans votre dépôt (un thème Metronic engagé sous static/, une bibliothèque de fournisseur fournie) n'avait aucun moyen pris en charge d'être tenu à l'écart - cela ne faisait que gonfler le graphique et ralentir l'indexation. Ajoutez une racine codegraph.json avec, par exemple, { "exclude": ["static/", "**/vendor/**"] } et ces chemins sont ignorés lors de l'indexation, de la synchronisation et de la surveillance des fichiers, sur les projets git et non-git. Les modèles sont de style gitignore et comparés aux chemins relatifs à la racine du dépôt. Cela complète le includeIgnored existant (son opposé - opt in aux dépôts intégrés gitignored). (#999)
  • CodeGraph suit désormais les commandes C/C++ qui sont distribuées via des tables de pointeurs de fonctions créées par des macros, de sorte que les fonctions de gestionnaire qu'elles atteignent ne sont plus des impasses dans le graphique. De nombreux projets C enregistrent un gestionnaire dans le champ de pointeur de fonction d'une structure via une macro et une table générée - redis est le cas classique : chaque commande (getCommand, decrbyCommand, …) est câblée dans le champ proc de la structure de commande par une table MAKE_CMD(…) qui réside dans un fichier #include-d généré, puis invoquée sous le nom c->cmd->proc(c). CodeGraph lit désormais ces tables créées par des macros, y compris celles dont le type de structure est lui-même un alias de macro, dont la table se trouve dans un fichier #include-d qui n'est jamais indexé seul, ou qui sont enveloppées dans une compilation conditionnelle (#ifdef) et définies en ligne avec la structure. Il reconnaît les champs de pointeur de fonction déclarés via un typedef de fonction et suit le récepteur – un accès chaîné (c->cmd->proc) ou un indice de tableau via une table de portée de fichier ((cmdnames[i].cmd_func)(…)) – à travers les types de champs. Il suit également la distribution via un simple tableau de pointeurs de fonction sans aucun wrapper de structure - le modèle opcode/handler-table courant dans les interpréteurs et les émulateurs, où une table comme opcodes[op](…) invoque l'une des nombreuses fonctions de gestionnaire enregistrées par index - reliant le répartiteur à chaque gestionnaire du tableau. Le résultat : demander les appelants ou le rayon d'explosion d'un gestionnaire de commandes trouve désormais le répartiteur qui l'atteint. Pour redis, call apparaît comme appelant de chaque commande ; pour SQLite, les fonctions SQL intégrées enregistrées via FUNCTION(...) sont liées à l'endroit où elles sont invoquées ; pour Vim, chaque :ex et les commandes en mode normal sont liées depuis le répartiteur. (#991, prolongeant le #932)
  • CodeGraph n'expire plus lorsque plusieurs agents l'interrogent en même temps. Le serveur d'arrière-plan partagé qui dessert toutes vos sessions d'éditeur et d'agent exécutait chaque requête sur un seul thread, donc une rafale de requêtes simultanées - par exemple un essaim de sous-agents explorant ensemble un grand monorepo - se mettaient en file d'attente les unes derrière les autres et, tandis que les plus lourdes s'exécutaient, gelaient la connexion de sorte que les réponses terminées ne pouvaient même pas être renvoyées jusqu'à ce que tout le lot soit épuisé. Au-delà d'une poignée d'appelants simultanés qui apparaissaient régulièrement sous forme de délais d'attente de demande MCP. Le serveur partagé répond désormais aux requêtes sur un pool de threads de travail, de sorte que les requêtes simultanées s'exécutent en parallèle et que la connexion reste réactive tout le temps ; lorsqu'il est véritablement saturé, un appel renvoie une brève note « occupé, réessayez sous peu » (pas une erreur) au lieu de dépasser le délai d'attente de votre client. Le pool s'adapte à votre machine (environ un travailleur par cœur, en laissant un pour la coordination) et une seule session d'éditeur n'est pas affectée (pas de pool, pas de surcharge). Définissez CODEGRAPH_QUERY_POOL_SIZE pour choisir un nombre spécifique de nœuds de calcul ou 0 pour revenir aux requêtes en cours de processus à thread unique.
  • L'indexation analyse désormais les fichiers sur plusieurs cœurs de processeur au lieu d'un seul, donc la construction du graphique d'un projet - codegraph index, le premier index d'un projet et la réindexation en arrière-plan après les modifications - est plus rapide sur les machines multicœurs, notamment sur les bases de code volumineuses ou lourdes à analyser. Le graphique qu'il produit est identique à avant et la réindexation reste déterministe : l'analyse s'exécute en parallèle, mais les résultats sont toujours validés dans un ordre fixe, de sorte que le même projet produit toujours le même graphique. CodeGraph dimensionne automatiquement le pool en fonction de votre machine (laissant un noyau libre pour tout le reste) ; définissez CODEGRAPH_PARSE_WORKERS pour choisir un nombre spécifique de travailleurs d'analyse, ou CODEGRAPH_PARSE_WORKERS=1 pour restaurer le comportement monocœur précédent. La mémoire maximale reste inchangée : les travailleurs récupèrent la mémoire de l'analyseur de manière indépendante, de sorte qu'elle n'augmente pas avec le nombre de cœurs. (#1015, #320)
  • Lorsque le serveur MCP de CodeGraph s'exécute sans projet par défaut propre — démarré en dehors de tout référentiel (par exemple derrière une passerelle MCP) ou à une racine monorepo dont les index résident dans des sous-projets — il marque désormais projectPath comme argument obligatoire à chaque appel d'outil. Avant, projectPath était toujours facultatif, donc un agent parlant à un tel serveur l'omettait souvent, obtenait des instructions pour le transmettre et ne réessayait pas de manière fiable - vous deviez le pousser manuellement à chaque fois. Désormais, l'exigence fait partie de la définition de l'outil que l'agent voit, elle fournit donc le chemin d'accès au projet sur lequel il travaille pour la première fois. Lorsque le serveur a un projet par défaut – le cas normal, lancé dans votre dépôt – projectPath reste facultatif et un appel sans celui-ci revient à ce projet exactement comme avant. Merci @wauxhall pour le rapport. (#993)
  • Les outils MCP de CodeGraph fonctionnent désormais en mode Demande du curseur (et tout autre client qui n'autorise que les outils en lecture seule). Chaque outil CodeGraph lit simplement votre code indexé - il ne modifie jamais votre espace de travail - mais il ne l'a pas annoncé, donc le mode Demander du curseur a bloqué chaque appel avec "vous êtes en mode demande et ne pouvez pas exécuter d'outils non en lecture seule", et vous avez dû passer en mode Agent pour utiliser CodeGraph. CodeGraph déclare désormais tous ses outils en lecture seule à l'aide des annotations standard de l'outil MCP, donc Cursor (et clients similaires) les autorise dans des contextes en lecture seule. Rien dans le comportement des outils ne change. Merci @CDsouza315 pour le rapport. (#1018)

Correctifs

  • Un codegraph index ou un codegraph init qui devient orphelin ou coincé s'arrête désormais tout seul au lieu d'épingler un cœur de processeur pour toujours. Si vous supprimiez la commande (ou le terminal/agent qui l'avait lancée), le processus d'indexation sous-jacent continuait à s'exécuter en arrière-plan - le parent ne pouvait pas transmettre le signal - et un index véritablement bloqué ne le surveillait pas non plus, puisque les chiens de garde d'auto-récupération étaient connectés uniquement au serveur MCP en arrière-plan. Les deux lacunes sont comblées : l'indexation s'arrête désormais automatiquement lorsque son parent disparaît, et un thread principal qui cesse de progresser est tué afin qu'il ne puisse pas se bloquer indéfiniment. Désactivez-vous avec CODEGRAPH_NO_WATCHDOG=1 (vivabilité) ou CODEGRAPH_PPID_POLL_MS=0 (détection d'orphelins), correspondant au serveur. (#999)
  • L'indexation ne se bloque plus au niveau de « Résolution des références » sur un dépôt qui valide un grand thème JavaScript/TypeScript ou SDK. Un thème d'administration vendu (Metronic est le cas classique - ~ 1 300 fichiers .js validés) redéclare les mêmes noms de méthodes (init, update, render, destroy, …) sur des centaines de widgets et la résolution utilisée pour évaluer chaque définition du même nom contre chaque appel - un travail qui augmente avec le carré du nombre de fois qu'un nom est répété. Sur un tel dépôt, il a épinglé un cœur de processeur pendant 15 à 30 minutes et n'a effectivement jamais terminé. La résolution permet désormais de deviner quand un nom est défini plus de fois que n'importe quelle base de code réelle n'en répète un (le seuil est généreux - les projets normaux dépassent bien en dessous et ne sont absolument pas affectés), car aucune heuristique de proximité ne peut de toute façon choisir la seule véritable cible parmi des milliers. L'indexation qui était auparavant calée s'effectue désormais en quelques secondes et la résolution précise (importations, noms qualifiés, correspondances de noms de classe) reste inchangée. Il s'agit de la même classe de ralentissement que le correctif de nom d'importation 1.1.0, désormais fermé pour les noms de méthodes/symboles répétés. Ajustez la coupure avec CODEGRAPH_AMBIGUOUS_NAME_CEILING si jamais vous en avez besoin. Merci @DANOX2 pour le rapport détaillé et la repro. (#999)
  • Le hook d'invite de chargement frontal de Claude Code se déclenche désormais pour les invites non anglaises. Le hook facultatif qui injecte le contexte CodeGraph pour les questions structurelles ne reconnaissait que les mots-clés anglais, donc une question structurelle écrite en chinois – ou dans toute langue non latine – n'injectait rien silencieusement : le hook semblait ne pas être câblé malgré une configuration correcte, sans erreur pour expliquer pourquoi. La porte est désormais sensible à la langue. Il reconnaît les mots-clés structurels chinois (如何/流程/调用/依赖/实现/架构…) et, dans n'importe quelle langue, une invite qui nomme un véritable symbole de code de votre projet, tel que getUserId, article_publish, user.login ou parseToken() (le nom est vérifié par rapport à l'index, donc un mot ordinaire qui ressemble simplement à du code ne le déclenche pas). Les invites non structurelles (« corrigez cette faute de frappe », dans n'importe quelle langue) restent inopérantes comme avant, donc rien ne se déclenche là où il n'y a pas de réponse structurelle à donner. Merci @whinc pour le rapport détaillé et la repro. (#994)
  • Le serveur de synchronisation automatique en arrière-plan démarre désormais pour les projets conservés sur un disque externe ExFAT ou FAT (et certains montages réseau). Ces systèmes de fichiers ne prennent pas en charge les opérations sur lesquelles le serveur s'appuie pour coordonner et écouter localement, il a donc échoué immédiatement et a réenregistré la même erreur à chaque nouvelle tentative - l'indexation en arrière-plan était interrompue, vous avez donc dû exécuter codegraph sync manuellement après les modifications. (Les outils MCP, le hook d'invite et le manuel codegraph index/sync n'ont pas été affectés, puisqu'aucun d'entre eux n'a besoin du serveur.) Le serveur contourne désormais automatiquement ces limitations - en revenant à une méthode de coordination différente et en déplaçant son socket local vers le répertoire temporaire de votre système - de sorte que l'indexation en arrière-plan y fonctionne exactement comme partout ailleurs, sans aucune configuration nécessaire. Vérifié de bout en bout sur de vrais systèmes de fichiers à disque amovible sous macOS, Linux et Windows. Merci @zengwenliang416 pour le rapport détaillé. (#997)
  • Si vous utilisez CodeGraph comme bibliothèque, l'assistant QueryBuilder.deleteResolvedReferences() ne renvoie plus "trop de variables SQL" lorsqu'on lui remet une très grande liste d'identifiants - il a émis une requête illimitée, donc une liste plus longue que la limite de paramètres de SQLite a interrompu l'appel. Il divise désormais le travail en lots comme toutes les autres requêtes groupées du API. La propre résolution d'indexation et de référence de CodeGraph n'a jamais appelé cette méthode (ils utilisent un chemin différent, déjà par lots), de sorte que le serveur CLI et MCP n'ont pas été affectés. Merci @inth3shadows pour l'analyse statique. (#1001)
  • Les propriétés calculées Swift sont désormais indexées, vous pouvez donc les rechercher. Une propriété calculée - un var isCloudProxy: Bool { … } lu partout dans une base de code, un var body: some View { … } d'une vue SwiftUI, une exigence var title: String { get } d'un protocole - n'a produit aucun symbole, donc codegraph query et codegraph_explore ont répondu "Aucun résultat trouvé" pour cela, et un agent qui trust donne un résultat vide conclurait à tort que la propriété n'existe pas. Les propriétés calculées (et les exigences en matière de propriétés de protocole) sont désormais des symboles graphiques que vous pouvez trouver et explorer comme n'importe quoi d'autre. Le getter d'une propriété calculée est également lu comme son corps, de sorte que le body d'une vue SwiftUI est lié aux sous-vues et aux assistants qu'elle construit, ce qui rend le flux de rendu d'une vue traçable à travers la propriété. Les propriétés stockées étaient déjà indexées ; cela comble l’écart de propriété calculée. Merci @monochrome3694 pour le rapport précis et la repro. (#1020)

codegraph v1.1.2

[1.1.2] - 2026-06-28

New Features

  • You can now exclude committed directories from the index with an exclude list in codegraph.json — even when they're git-tracked. .gitignore can't drop a directory git already tracks, so a vendored theme or SDK that's checked into your repo (a committed Metronic theme under static/, a bundled vendor library) had no supported way to be kept out — it just bloated the graph and slowed indexing. Add a root codegraph.json with, e.g., { "exclude": ["static/", "**/vendor/**"] } and those paths are skipped on indexing, sync, and file-watching, on both git and non-git projects. Patterns are gitignore-style and matched against repo-root-relative paths. This complements the existing includeIgnored (its opposite — opt in to gitignored embedded repos). (#999)
  • CodeGraph now follows C/C++ commands that are dispatched through macro-built function-pointer tables, so the handler functions they reach are no longer dead-ends in the graph. Many C projects register a handler into a struct's function-pointer field through a macro and a generated table — redis is the classic case: every command (getCommand, decrbyCommand, …) is wired into the command struct's proc field by a MAKE_CMD(…) table that lives in a generated, #include-d file, then invoked as c->cmd->proc(c). CodeGraph now reads those macro-built tables — including ones whose struct type is itself a macro alias, whose table sits in an #include-d file that is never indexed on its own, or that are wrapped in conditional compilation (#ifdef) and defined inline with the struct. It recognizes function-pointer fields declared through a function typedef, and follows the receiver — a chained access (c->cmd->proc) or an array subscript through a file-scope table ((cmdnames[i].cmd_func)(…)) — across field types. It also follows dispatch through a bare array of function pointers with no struct wrapper at all — the opcode/handler-table pattern common in interpreters and emulators, where a table like opcodes[op](…) invokes one of many registered handler functions by index — linking the dispatcher to every handler in the array. The upshot: asking for the callers or blast radius of a command handler now finds the dispatcher that reaches it. For redis, call shows up as a caller of every command; for SQLite, the builtin SQL functions registered through FUNCTION(...) link to where they're invoked; for Vim, every :ex and normal-mode command links from the dispatcher. (#991, extending #932)
  • CodeGraph no longer times out when many agents query it at once. The shared background server that serves all your editor and agent sessions used to run every query on a single thread, so a burst of concurrent requests — for example a swarm of subagents exploring a large monorepo together — queued up behind one another and, while the heavy ones ran, froze the connection so finished answers couldn't even be sent back until the whole batch drained. Past a handful of simultaneous callers that routinely surfaced as MCP request timeouts. The shared server now answers queries across a pool of worker threads, so concurrent requests run in parallel and the connection stays responsive the whole time; when it's genuinely saturated a call returns a brief "busy, retry shortly" note (not an error) instead of hanging past your client's timeout. The pool sizes itself to your machine — roughly one worker per core, leaving one for coordination — and a single editor session is unaffected (no pool, no overhead). Set CODEGRAPH_QUERY_POOL_SIZE to choose a specific number of workers, or 0 to revert to single-threaded in-process queries.
  • Indexing now parses files across multiple CPU cores instead of one, so building a project's graph — codegraph index, the first index of a project, and the background re-index after changes — is faster on multi-core machines, most noticeably on large or parse-heavy codebases. The graph it produces is identical to before and re-indexing stays deterministic: parsing runs in parallel, but results are still committed in a fixed order, so the same project always yields the same graph. CodeGraph sizes the pool to your machine automatically (leaving a core free for everything else); set CODEGRAPH_PARSE_WORKERS to choose a specific number of parse workers, or CODEGRAPH_PARSE_WORKERS=1 to restore the previous single-core behavior. Peak memory is unchanged — workers reclaim parser memory independently, so it doesn't grow with the number of cores. (#1015, #320)
  • When CodeGraph's MCP server runs with no default project of its own — started outside any repository (for example behind an MCP gateway), or at a monorepo root whose indexes live in sub-projects — it now marks projectPath as a required argument on every tool call. Before, projectPath was always optional, so an agent talking to such a server would often omit it, get back guidance to pass it, and not reliably retry — you had to nudge it by hand every time. Now the requirement is part of the tool definition the agent sees, so it supplies the path to the project it's working on the first time. When the server does have a default project — the normal case, launched inside your repo — projectPath stays optional and a call without it falls back to that project exactly as before. Thanks @wauxhall for the report. (#993)
  • CodeGraph's MCP tools now work in Cursor's Ask mode (and any other client that only permits read-only tools). Every CodeGraph tool just reads your indexed code — it never changes your workspace — but it didn't advertise that, so Cursor's Ask mode blocked every call with "you are in ask mode and cannot run non read-only tools," and you had to switch to Agent mode to use CodeGraph at all. CodeGraph now declares all its tools read-only using the standard MCP tool annotations, so Cursor (and similar clients) allow them in read-only contexts. Nothing about how the tools behave changes. Thanks @CDsouza315 for the report. (#1018)

Fixes

  • A codegraph index or codegraph init that gets orphaned or wedged now stops itself instead of pinning a CPU core forever. If you killed the command (or the terminal/agent that launched it), the underlying indexer process used to keep running in the background — the parent couldn't pass the signal along — and a genuinely stuck index had nothing watching it either, since the self-recovery watchdogs were wired only into the background MCP server. Both gaps are closed: indexing now self-terminates when its parent goes away, and a main thread that stops making progress is killed so it can't hang indefinitely. Opt out with CODEGRAPH_NO_WATCHDOG=1 (liveness) or CODEGRAPH_PPID_POLL_MS=0 (orphan detection), matching the server. (#999)
  • Indexing no longer hangs at "Resolving refs" on a repo that commits a large JavaScript/TypeScript theme or SDK. A vendored admin theme (Metronic is the classic case — ~1,300 committed .js files) re-declares the same method names (init, update, render, destroy, …) on hundreds of widgets, and resolution used to score every same-named definition against every call — work that grows with the square of how many times a name repeats. On such a repo it pinned a CPU core for 15–30 minutes and effectively never finished. Resolution now declines to guess when a name is defined more times than any real codebase ever repeats one (the cutoff is generous — normal projects top out far below it and are completely unaffected), since no proximity heuristic can pick the one true target among thousands anyway. Indexing that previously wedged now completes in seconds, and precise resolution (imports, qualified names, class-name matches) is unchanged. This is the same class of slowdown as the 1.1.0 import-name fix, now closed for repeated method/symbol names. Tune the cutoff with CODEGRAPH_AMBIGUOUS_NAME_CEILING if you ever need to. Thanks @DANOX2 for the detailed report and repro. (#999)
  • Claude Code's front-load prompt hook now fires for non-English prompts. The optional hook that injects CodeGraph context for structural questions only recognized English keywords, so a structural question written in Chinese — or any non-Latin-script language — silently injected nothing: the hook looked like it wasn't wired up despite a correct setup, with no error to explain why. The gate is now language-aware. It recognizes Chinese structural keywords (如何/流程/调用/依赖/实现/架构…), and — in any language — a prompt that names a real code symbol from your project, such as getUserId, article_publish, user.login, or parseToken() (the name is checked against the index, so an ordinary word that merely looks like code doesn't trigger it). Non-structural prompts ("fix this typo", in any language) stay a no-op as before, so nothing fires where there's no structural answer to give. Thanks @whinc for the detailed report and repro. (#994)
  • The background auto-sync server now starts for projects kept on an ExFAT or FAT external drive (and some network mounts). Those filesystems don't support the operations the server relies on to coordinate and to listen locally, so it failed immediately and re-logged the same error on every retry — background indexing was broken, so you had to run codegraph sync by hand after changes. (The MCP tools, the prompt hook, and manual codegraph index/sync were unaffected, since none of them need the server.) The server now works around those limitations automatically — falling back to a different coordination method and relocating its local socket to your system temp directory — so background indexing works there exactly like anywhere else, with no configuration needed. Verified end-to-end on real removable-drive filesystems on macOS, Linux, and Windows. Thanks @zengwenliang416 for the detailed report. (#997)
  • If you use CodeGraph as a library, the QueryBuilder.deleteResolvedReferences() helper no longer throws "too many SQL variables" when handed a very large list of ids — it issued one unbounded query, so a list longer than SQLite's parameter limit aborted the call. It now splits the work into batches like every other bulk query in the API. CodeGraph's own indexing and reference resolution never called this method (they use a different, already-batched path), so the CLI and MCP server were unaffected. Thanks @inth3shadows for the static analysis. (#1001)
  • Swift computed properties are now indexed, so you can search for them. A computed property — a var isCloudProxy: Bool { … } read all over a codebase, a SwiftUI view's var body: some View { … }, a protocol's var title: String { get } requirement — produced no symbol at all, so codegraph query and codegraph_explore answered "No results found" for it, and an agent that trusts an empty result would wrongly conclude the property doesn't exist. Computed properties (and protocol property requirements) are now graph symbols you can find and explore like anything else. A computed property's getter is also read as its body, so a SwiftUI view's body links to the subviews and helpers it builds — making a view's render flow traceable through the property. Stored properties were already indexed; this closes the computed-property gap. Thanks @monochrome3694 for the precise report and repro. (#1020)
