druide druide-0.19.0

Apache Druid 0.19.0 contient environ 200 nouvelles fonctionnalités, corrections de bugs, améliorations des performances, améliorations de la documentation et couverture de tests supplémentaire de 51 contributeurs. Reportez-vous à la [liste complète des modifications] (https://github.com/apache/druid/compare/0.18.1...0.19.0) et à [tout ce qui est associé au jalon] (https://github.com/apache/druid/milestone/38) pour plus de détails.

<a name="19-new-features" href="#19-new-features">#</a> Nouvelles fonctionnalités

<a name="19-vectorize-default" href="#19-vectorize-default">#</a> Moteurs de requêtes vectorisées GroupBy et Timeseries activés par défaut

Les [moteurs de requêtes vectorisés] (https://github.com/apache/druid/issues/7093) pour les requêtes GroupBy et Timeseries ont été introduits dans Druid 0.16, en tant que fonctionnalité opt-in. Depuis, nous avons testé ces moteurs de manière approfondie et pensons que le moment est venu pour ces améliorations de trouver un public plus large. Notez que l'intégralité du moteur de requête n'est pas vectorisée pour le moment, mais ce changement fait en sorte que toute requête éligible à la vectorisation le fasse. Cette fonctionnalité peut toujours être désactivée si vous rencontrez des problèmes en définissant druid.query.vectorize sur false. https://github.com/apache/druid/pull/10065

<a name="19-avro" href="#19-avro">#</a> Prise en charge native par lots de Druid pour les fichiers conteneurs d'objets Apache Avro

Nouveau dans Druid 0.19.0, l'indexation par lots native prend désormais en charge les fichiers codés [Apache Avro Object Container Format] (https://avro.apache.org/docs/current/spec.html#Object+Container+Files), permettant l'ingestion par lots de données Avro sans avoir besoin d'un cluster Hadoop externe. Consultez les documents pour plus de détails https://github.com/apache/druid/pull/9671

<a name="19-sql-input-source" href="#19-sql-input-source">#</a> Mise à jour de la prise en charge native des lots Druid pour les bases de données SQL

Un « SqlInputSource » a été ajouté dans Druid 0.19.0 pour fonctionner avec les nouvelles spécifications natives d'ingestion par lots introduites pour la première fois dans Druid 0.17, dépréciant ainsi [SqlFirehose] (https://druid.apache.org/docs/0.19.0/ingestion/native-batch.html#sqlfirehose). Comme « SqlFirehose », il prend actuellement en charge MySQL et PostgreSQL, en utilisant le pilote de ces extensions. Il s'agit d'une tâche d'ingestion de niveau relativement bas, et l'opérateur doit veiller à s'assurer manuellement que les données correctes sont ingérées, soit en élaborant des requêtes spécialement pour garantir qu'aucune donnée en double n'est ingérée pour les ajouts, soit en s'assurant que l'ensemble des données est demandé pour être remplacé lors de l'écrasement. Voir [les documents] (https://druid.apache.org/docs/0.19.0/ingestion/native-batch.md#sql-input-source) pour plus de détails opérationnels. https://github.com/apache/druid/pull/9449

<a name="19-ranger" href="#19-ranger">#</a> Autorisation basée sur Apache Ranger

Une nouvelle extension dans Druid 0.19.0 ajoute un autorisateur qui implémente le contrôle d'accès pour Druid, soutenu par [Apache Ranger] (https://ranger.apache.org/). Veuillez consulter [la documentation de l'extension]((https://druid.apache.org/docs/0.19.0/development/extensions-core/druid-ranger-security.html) et Authentification et autorisation pour plus d'informations sur les fonctionnalités de base fournies par cette extension. https://github.com/apache/druid/pull/9579

<a name="19-aliyun-oss" href="#19-aliyun-oss">#</a> Prise en charge du service de stockage d'objets Alibaba

Une nouvelle extension « contrib » a été ajoutée pour [Alibaba Cloud Object Storage Service (OSS)] (https://www.alibabacloud.com/product/oss) afin de fournir à la fois un stockage approfondi et une utilisation en tant que source d'entrée d'ingestion par lots. Puisqu'il s'agit d'une extension 'contrib', elle ne sera pas empaquetée par défaut dans la distribution binaire, veuillez consulter extensions de communauté pour plus de détails sur la façon de l'utiliser dans votre cluster. https://github.com/apache/druid/pull/9898

<a name="19-gce-autoscale" href="#19-gce-autoscale">#</a> Autoscaling du nœud de calcul d'ingestion pour Google Compute Engine

Une autre extension « contrib » nouvelle dans 0.19.0 a été ajoutée pour prendre en charge la mise à l'échelle automatique des travailleurs d'ingestion, ce qui permet à un Druid Overlord de provisionner ou de mettre fin à des instances de travail (MiddleManagers ou Indexers) chaque fois qu'il y a des tâches en attente ou des travailleurs inactifs, pour Google Compute Engine. Contrairement à l'extension d'autoscaling d'ingestion d'Amazon Web Services, qui provisionne et met fin aux instances directement sans utiliser de groupe Auto Scaling, l'autoscaler GCE utilise des [groupes d'instances gérés] (https://cloud.google.com/compute/docs/instance-groups#managed_instance_groups) pour s'aligner plus étroitement sur la manière dont les opérateurs sont susceptibles de provisionner leurs clusters dans GCE. Comme les autres extensions « contrib », elle ne sera pas empaquetée par défaut dans la distribution binaire, veuillez consulter extensions de communauté pour plus de détails sur la façon de l'utiliser dans votre cluster. https://github.com/apache/druid/pull/8987

<a name="19-regexp-like" href="#19-regexp-like">#</a> REGEXP_LIKE

Une nouvelle fonction REGEXP_LIKE a été ajoutée à Druid SQL et aux expressions natives, qui se comporte de manière similaire à LIKE, sauf en utilisant des expressions régulières pour le modèle. https://github.com/apache/druid/pull/9893

<a name="19-web-lookup" href="#19-web-lookup">#</a> Améliorations de la gestion des recherches dans la console Web

Druid 0.19, également console Web, inclut également des améliorations utiles de l'interface de gestion des tables de recherche. La création et la modification des recherches se font désormais avec un formulaire pour accepter les entrées de l'utilisateur, plutôt qu'avec un éditeur de texte brut pour saisir la spécification JSON. <img width="682" alt="Capture d'écran 02/04/2020 à 1 h 14 h 38" src="https://user-images.githubusercontent.com/37322608/78221645-fa2b5080-7480-11ea-9824-c74e121575f3.png"> De plus, clicliquer sur l'icône en forme de loupe à côté d'une recherche permettra désormais d'afficher les 5 000 premières valeurs de cette recherche. <img width="1129" alt="Capture d'écran 20/03/2020 à 15 h 09 24" src="https://user-images.githubusercontent.com/37322608/77206532-cd5c5e00-6abc-11ea-9ea0-0680fa5de8cb.png"> https://github.com/apache/druid/pull/9549 https://github.com/apache/druid/pull/9587

<a name="19-datasource-loadstatus" href="#19-datasource-loadstatus">#</a> Nouveau coordinateur par source de données 'loadstatus' API

Un coordinateur API peut faciliter la détermination si les derniers segments publiés sont disponibles pour l'interrogation. Ceci est similaire au coordinateur existant « loadstatus » API, mais est spécifique à la source de données, peut spécifier un intervalle et peut éventuellement actualiser en direct l'instantané du magasin de métadonnées pour obtenir les dernières informations à jour. Notez que les opérateurs doivent toujours faire preuve de prudence lorsqu'ils utilisent ce API pour interroger un grand nombre de segments, en particulier s'ils forcent une actualisation des métadonnées, car cela peut potentiellement constituer un appel « lourd » sur de grands clusters. https://github.com/apache/druid/pull/9965

<a name="19-batch-append" href="#19-batch-append">#</a> Prise en charge native de l'ajout par lots pour le partitionnement de plage et de hachage

En partie correction de bug, en partie nouvelle fonctionnalité, le lot natif Druid (encore une fois) prend en charge l'ajout de nouvelles données aux tranches de temps existantes lorsque ces tranches de temps ont été partitionnées avec des algorithmes de partitionnement « hachage » ou « plage ». Notez qu'actuellement, les segments ajoutés ne prennent en charge que le partitionnement « dynamique », et lors du retour à des versions antérieures, ces segments ajoutés ne seront pas reconnus par Druid après la rétrogradation. Afin de revenir à une version précédente, ces segments ajoutés doivent être compactés avec le reste du morceau de temps afin d'avoir un schéma de partitionnement homogène. https://github.com/apache/druid/pull/10033

<a name="19-bugs" href="#19-bugs">#</a> Corrections de bugs

Druid 0.19.0 contient 65 corrections de bugs, vous pouvez voir la liste complète ici.

<a name="19-partition-non-atomic" href="#19-partition-non-atomic">#</a> Correctif pour les segments partitionnés "dynamiques" ingérés par lots qui ne devenaient pas interrogeables de manière atomique

Druid 0.19.0 corrige un problème important d'exactitude des requêtes, où les segments partitionnés « dynamiques » produits par une tâche d'ingestion par lots ne suivaient pas le nombre total de partitions. Cela impliquait que lorsque ces segments étaient mis en ligne, ils ne le faisaient pas en tant qu'ensemble complet, mais plutôt en tant que segments individuels, ce qui signifie qu'il y aurait des périodes d'échange au cours desquelles les résultats pourraient être interrogés à partir d'un ensemble de partitions incomplet dans un intervalle de temps donné. https://github.com/apache/druid/pull/10025

<a name="19-partition-empty-buckets" href="#19-partition-empty-buckets">#</a> Correction pour permettre aux segments partitionnés 'hash' et 'range' avec des buckets vides d'être désormais interrogeables

Avant 0.19.0, Druid avait un bug lors de l'utilisation du hachage ou du partitionnement à distance où si l'asymétrie des données était telle que l'un des compartiments était « vide » après l'ingestion, les partitions ne seraient jamais reconnues comme « complètes » et ne deviendraient donc jamais interrogeables. Druid 0.19.0 résout ce problème en ajustant le schéma de la spécification de partitionnement. Ces modifications apportées au format json devraient être rétrocompatibles, mais le retour à une version précédente rendra à nouveau ces segments plus interrogeables. https://github.com/apache/druid/pull/10012

<a name="19-bad-balancer" href="#19-bad-balancer">#</a> Comportement incorrect de l'équilibreur

Un bogue dans les versions de Druid antérieures à 0.19.0 permettait un fonctionnement (incorrect) du coordinateur dans le cas où druid.server.maxSize n'était pas défini. Ce bogue permettrait aux segments de se charger et de les équilibrer efficacement de manière aléatoire dans le cluster (quelle que soit la stratégie d'équilibrage réellement configurée) si tous les historiques n'avaient pas cette valeur définie. Ce bug a été corrigé, mais par conséquent, druid.server.maxSize doit être défini sur la somme des tailles d'emplacement du cache de segments pour les historiques, sinon ils ne chargeront pas les segments. https://github.com/apache/druid/pull/10070

<a name="19-upgrading-from-previous" href="#19-upgrading-from-previous">#</a> Mise à niveau vers Druid 0.19.0

Veuillez être conscient des problèmes suivants lors de la mise à niveau du 0.18.1 vers le 0.19.0. Si vous effectuez une mise à jour à partir d'une version antérieure à 0.18.1, veuillez consulter les release note des versions intermédiaires concernées.

<a name="19-server-size" href="#19-server-size">#</a> 'druid.server.maxSize' doit maintenant être défini pour les serveurs historiques

[Un correctif de bug du coordinateur] (#19-bad-balancer) nécessite désormais comme effet secondaire que druid.server.maxSize soit défini pour le chargement des segments. Bien que cette valeur ait dû être définie correctement pour les versions précédentes, assurez-vous que cette valeur est correctement configurée avant de mettre à niveau vos clusters, sinon les segments ne seront pas chargés. https://github.com/apache/druid/pull/10070

<a name="19-sys-segments-payload" href="#19-sys-segments-payload">#</a> La colonne "payload" des tables système 'sys.segments' a été supprimée et remplacée par 'dimensions', 'metrics' et 'shardSpec'.

La suppression de la colonne « charge utile » de la table sys.segments devrait rendre les requêtes sur cette table beaucoup plus efficaces, et les champs les plus utiles de celle-ci, la liste des « dimensions », « métriques » et « shardSpec », ont été divisés et sont donc toujours disponibles pour être consacrés au traitement des requêtes. https://github.com/apache/druid/pull/9883

<a name="19-segment-load-threads" href="#19-segment-load-threads">#</a> Modification du nombre par défaut de threads de chargement de segments

La valeur par défaut de la configuration druid.segmentCache.numLoadingThreads est passée de « nombre de cœurs » à « nombre de cœurs » divisé par 6. Cela devrait rendre les historiques un peu plus corrects dès le départ lors du chargement d'un grand nombre de segments, limitant ainsi l'impact sur les performances des requêtes. https://github.com/apache/druid/pull/9856

<a name="19-broadcast-colocated" href="#19-broadcast-colocated">#</a> Les règles de chargement de diffusion n'ont plus de « sources de données colocalisées »

Un certain nombre de modifications incomplètes visant à faciliter des requêtes de jointure plus efficaces, basées sur l'idée d'utiliser des règles de chargement de diffusion pour propager des sources de données plus petites au sein du cluster afin que les opérations de jointure puissent être transmises au traitement de segments individuels, ont été ajoutées à 0.19.0. Bien qu'il ne s'agisse pas encore d'une fonctionnalité terminée, dans le cadre des modifications apportées pour y parvenir, les règles de chargement de « diffusion » n'ont plus le concept de « sources de données colocalisées », qui tenteraient de diffuser uniquement des segments vers des serveurs comportant des segments de la source de données configurée. Cela n'a pas très bien fonctionné dans la pratique, car ce n'était pas atomique, ce qui signifie que les segments de diffusion seraient en retard par rapport aux chargements et aux suppressions de la source de données colocalisée. Nous avons donc décidé de la supprimer. https://github.com/apache/druid/pull/9971

<a name="19-broadcast-broker-load" href="#19-broadcast-broker-load">#</a> Les courtiers et les tâches en temps réel peuvent désormais être configurés pour charger des segments à partir de sources de données « diffusion »

Autre effet du travail préliminaire mentionné ci-dessus visant à introduire des « jointures de diffusion » efficaces : les courtiers et les tâches d'indexation en temps réel chargeront désormais les segments chargés par les règles de « diffusion », si un cache de segments est configuré. Étant donné que la fonctionnalité n'est pas complète, il y a peu de raisons de le faire dans 0.19.0, et cela n'arrivera pas à moins d'être explicitement configuré. https://github.com/apache/druid/pull/9971

<a name="19-lpad-rpad" href="#19-lpad-rpad">#</a> changement de comportement des fonctions lpad et rpad

Les fonctions lpad et rpad ont subi un léger changement de comportement dans le mode non compatible SQL par défaut de Druid, afin de les rendre cohérentes avec PostgreSQL. Dans le nouveau comportement, si l'expression de remplissage est une chaîne vide, alors le résultat sera les caractères originaux (éventuellement tronqués), plutôt que la chaîne vide étant traitée comme une valeur nulle et forçant les résultats à la valeur nulle. https://github.com/apache/druid/pull/10006

<a name="19-interfaces" href="#19-interfaces">#</a> Les extensions fournissant des expressions Druid personnalisées devraient désormais implémenter les méthodes equals et hashCode

Une modification de l'interface Expr dans Druid 0.19.0 nécessite que toute extension qui fournit des expressions personnalisées via ExprMacroTable doive également implémenter les méthodes equals et hashCode pour fonctionner correctement, en particulier avec les requêtes JOIN, qui s'appuient sur une analyse de filtre et d'expression pour déterminer comment traiter de manière optimale une requête. https://github.com/apache/druid/pull/9830

druid druid-0.19.0

Apache Druid 0.19.0 contains around 200 new features, bug fixes, performance enhancements, documentation improvements, and additional test coverage from 51 contributors. Refer to the complete list of changes and everything tagged to the milestone for further details.

<a name="19-new-features" href="#19-new-features">#</a> New Features

<a name="19-vectorize-default" href="#19-vectorize-default">#</a> GroupBy and Timeseries vectorized query engines enabled by default

Vectorized query engines for GroupBy and Timeseries queries were introduced in Druid 0.16, as an opt in feature. Since then we have extensively tested these engines and feel that the time has come for these improvements to find a wider audience. Note that not all of the query engine is vectorized at this time, but this change makes it so that any query which is eligible to be vectorized will do so. This feature may still be disabled if you encounter any problems by setting druid.query.vectorize to false.

https://github.com/apache/druid/pull/10065

<a name="19-avro" href="#19-avro">#</a> Druid native batch support for Apache Avro Object Container Files

New in Druid 0.19.0, native batch indexing now supports Apache Avro Object Container Format encoded files, allowing batch ingestion of Avro data without needing an external Hadoop cluster. Check out the docs for more details

https://github.com/apache/druid/pull/9671

<a name="19-sql-input-source" href="#19-sql-input-source">#</a> Updated Druid native batch support for SQL databases

An 'SqlInputSource' has been added in Druid 0.19.0 to work with the new native batch ingestion specifications first introduced in Druid 0.17, deprecating the SqlFirehose. Like the 'SqlFirehose' it currently supports MySQL and PostgreSQL, using the driver from those extensions. This is a relatively low level ingestion task, and the operator must take care to manually ensure that the correct data is ingested, either by specially crafting queries to ensure no duplicate data is ingested for appends, or ensuring that the entire set of data is queried to be replaced when overwriting. See the docs for more operational details.

https://github.com/apache/druid/pull/9449

<a name="19-ranger" href="#19-ranger">#</a> Apache Ranger based authorization

A new extension in Druid 0.19.0 adds an Authorizer which implements access control for Druid, backed by Apache Ranger. Please see [the extension documentation]((https://druid.apache.org/docs/0.19.0/development/extensions-core/druid-ranger-security.html) and Authentication and Authorization for more information on the basic facilities this extension provides.

https://github.com/apache/druid/pull/9579

<a name="19-aliyun-oss" href="#19-aliyun-oss">#</a> Alibaba Object Storage Service support

A new 'contrib' extension has been added for Alibaba Cloud Object Storage Service (OSS) to provide both deep storage and usage as a batch ingestion input source. Since this is a 'contrib' extension, it will not be packaged by default in the binary distribution, please see community extensions for more details on how to use in your cluster.

https://github.com/apache/druid/pull/9898

<a name="19-gce-autoscale" href="#19-gce-autoscale">#</a> Ingestion worker autoscaling for Google Compute Engine

Another 'contrib' extension new in 0.19.0 has been added to support ingestion worker autoscaling, which allows a Druid Overlord to provision or terminate worker instances (MiddleManagers or Indexers) whenever there are pending tasks or idle workers, for Google Compute Engine. Unlike the Amazon Web Services ingestion autoscaling extension, which provisions and terminates instances directly without using an Auto Scaling Group, the GCE autoscaler uses Managed Instance Groups to more closely align with how operators are likely to provision their clusters in GCE. Like other 'contrib' extensions, it will not be packaged by default in the binary distribution, please see community extensions for more details on how to use in your cluster.

https://github.com/apache/druid/pull/8987

<a name="19-regexp-like" href="#19-regexp-like">#</a> REGEXP_LIKE

A new REGEXP_LIKE function has been added to Druid SQL and native expressions, which behaves similar to LIKE, except using regular expressions for the pattern.

https://github.com/apache/druid/pull/9893

Druid 0.19 also web console also includes some useful improvements to the lookup table management interface. Creating and editing lookups is now done with a form to accept user input, rather than a raw text editor to enter the JSON spec.

<a name="19-datasource-loadstatus" href="#19-datasource-loadstatus">#</a> New Coordinator per datasource 'loadstatus' API

A coordinator API can make it easier to determine if the latest published segments are available for querying. This is similar to the existing coordinator 'loadstatus' API, but is datasource specific, may specify an interval, and can optionally live refresh the metadata store snapshot to get the latest up to date information. Note that operators should still exercise caution when using this API to query large numbers of segments, especially if forcing a metadata refresh, as it can potentially be a 'heavy' call on large clusters.

https://github.com/apache/druid/pull/9965

<a name="19-batch-append" href="#19-batch-append">#</a> Native batch append support for range and hash partitioning

Part bug fix, part new feature, Druid native batch (once again) supports appending new data to existing time chunks when those time chunks were partitioned with 'hash' or 'range' partitioning algorithms. Note that currently the appended segments only support 'dynamic' partitioning, and when rolling back to older versions that these appended segments will not be recognized by Druid after the downgrade. In order to roll back to a previous version, these appended segments should be compacted with the rest of the time chunk in order to have a homogenous partitioning scheme.

https://github.com/apache/druid/pull/10033

<a name="19-bugs" href="#19-bugs">#</a> Bug fixes

Druid 0.19.0 contains 65 bug fixes, you can see the complete list here.

<a name="19-partition-non-atomic" href="#19-partition-non-atomic">#</a> Fix for batch ingested 'dynamic' partitioned segments not becoming queryable atomically

Druid 0.19.0 fixes an important query correctness issue, where 'dynamic' partitioned segments produced by a batch ingestion task were not tracking the overall number of partitions. This had the implication that when these segments came online, they did not do so as a complete set, but rather as individual segments, meaning that there would be periods of swapping where results could be queried from an incomplete partition set within a time chunk.

https://github.com/apache/druid/pull/10025

<a name="19-partition-empty-buckets" href="#19-partition-empty-buckets">#</a> Fix to allow 'hash' and 'range' partitioned segments with empty buckets to now be queryable

Prior to 0.19.0, Druid had a bug when using hash or ranged partitioning where if data skew was such that any of the buckets were 'empty' after ingesting, the partitions would never be recognized as 'complete' and so never become queryable. Druid 0.19.0 fixes this issue by adjusting the schema of the partitioning spec. These changes to the json format should be backwards compatible, however rolling back to a previous version will again make these segments no longer queryable.

https://github.com/apache/druid/pull/10012

<a name="19-bad-balancer" href="#19-bad-balancer">#</a> Incorrect balancer behavior

A bug in Druid versions prior to 0.19.0 allowed for (incorrect) coordinator operation in the event druid.server.maxSize was not set. This bug would allow segments to load, and effectively randomly balance them in the cluster (regardless of what balancer strategy was actually configured) if all historicals did not have this value set. This bug has been fixed, but as a result druid.server.maxSize must be set to the sum of the segment cache location sizes for historicals, or else they will not load segments.

https://github.com/apache/druid/pull/10070

<a name="19-upgrading-from-previous" href="#19-upgrading-from-previous">#</a> Upgrading to Druid 0.19.0

Please be aware of the following issues when upgrading from 0.18.1 to 0.19.0. If you're updating from an earlier version than 0.18.1, please see the release notes of the relevant intermediate versions.

<a name="19-server-size" href="#19-server-size">#</a> 'druid.server.maxSize' must now be set for Historical servers

A Coordinator bug fix as a side-effect now requires druid.server.maxSize to be set for segments to be loaded. While this value should have been set correctly for previous versions, please be sure this value is configured correctly before upgrading your clusters or else segments will not be loaded.

https://github.com/apache/druid/pull/10070

<a name="19-sys-segments-payload" href="#19-sys-segments-payload">#</a> System tables 'sys.segments' column 'payload' has been removed and replaced with 'dimensions', 'metrics', and 'shardSpec'

The removal of the 'payload' column from the sys.segments table should make queries on this table much more efficient, and the most useful fields from this, the list of 'dimensions', 'metrics', and the 'shardSpec', have been split out, and so are still available to devote to processing queries.

https://github.com/apache/druid/pull/9883

<a name="19-segment-load-threads" href="#19-segment-load-threads">#</a> Changed default number of segment loading threads

The druid.segmentCache.numLoadingThreads configuration has had the default value changed from 'number of cores' to 'number of cores' divided by 6. This should make historicals a bit more well behaved out of the box when loading a large number of segments, limiting the impact on query performance.

https://github.com/apache/druid/pull/9856

<a name="19-broadcast-colocated" href="#19-broadcast-colocated">#</a> Broadcast load rules no longer have 'colocated datasources'

A number of incomplete changes to facilitate more efficient join queries, based on the idea of utilizing broadcast load rules to propagate smaller datasources among the cluster so that join operations can be pushed down to individual segment processing, have been added to 0.19.0. While not a finished feature yet, as part of the changes to make this happen, 'broadcast' load rules no longer have the concept of 'colocated datasources', which would attempt to only broadcast segments to servers that had segments of the configured datasource. This didn't work so well in practice, as it was non-atomic, meaning that the broadcast segments would lag behind loads and drops of the colocated datasource, so we decided to remove it.

https://github.com/apache/druid/pull/9971

<a name="19-broadcast-broker-load" href="#19-broadcast-broker-load">#</a> Brokers and realtime tasks may now be configured to load segments from 'broadcast' datasources

Another effect of the afforementioned preliminary work to introduce efficient 'broadcast joins', Brokers and realtime indexing tasks will now load segments loaded by 'broadcast' rules, if a segment cache is configured. Since the feature is not complete there is little reason to do this in 0.19.0, and it will not happen unless explicitly configured.

https://github.com/apache/druid/pull/9971

<a name="19-lpad-rpad" href="#19-lpad-rpad">#</a> lpad and rpad function behavior change

The lpad and rpad functions have gone through a slight behavior change in Druids default non-SQL compatible mode, in order to make them behave consistently with PostgreSQL. In the new behavior, if the pad expression is an empty string, then the result will be the (possibly trimmed) original characters, rather than the empty string being treated as a null and coercing the results to null.

https://github.com/apache/druid/pull/10006

<a name="19-interfaces" href="#19-interfaces">#</a> Extensions providing custom Druid expressions are now expected to implement equals and hashCode methods

A change to the Expr interface in Druid 0.19.0 requires that any extension which provides custom expressions via ExprMacroTable must also implement equals and hashCode methods to function correctly, especially with JOIN queries, which rely on filter and expression analysis for determining how to optimally process a query.

https://github.com/apache/druid/pull/9830
