druide druide-0.18.0

Apache Druid 0.18.0 contient plus de 200 nouvelles fonctionnalités, améliorations de performances, corrections de bogues et améliorations majeures de la documentation provenant de 42 contributeurs. Consultez la [liste complète des modifications] (https://github.com/apache/druid/compare/0.17.0...0.18.0) et [tout ce qui est associé au jalon] (https://github.com/apache/druid/milestone/37).

<a name="new-features" href="#new-features">#</a> Nouvelles fonctionnalités

<a name="join" href="#join">#</a> Rejoignez le support

Rejoindre est une opération clé dans l’analyse des données. Avant 0.18.0, Druid prenait en charge certaines fonctionnalités liées aux jointures, telles que les recherches ou les semi-jointures dans SQL. Cependant, les cas d'utilisation de ces fonctionnalités étaient assez limités et, pour d'autres cas d'utilisation de jointure, les utilisateurs devaient dénormaliser leurs sources de données lorsqu'ils ingèrent des données au lieu de les rejoindre au moment de la requête, ce qui pouvait entraîner une explosion du volume de données et un long temps d'ingestion. Druid 0.18.0 prend en charge les véritables jointures pour la première fois de son histoire. Druid prend en charge les jointures INNER, LEFT et CROSS pour le moment. Pour les requêtes natives, la source de données join a été nouvellement introduite pour représenter une jointure de deux sources de données. Actuellement, seule la jointure left-deep est autorisée. Cela signifie que seule une source de données table ou une autre source de données join est autorisée pour la source de données de gauche. Pour la bonne source de données, les sources de données lookup, inline ou query sont autorisées. Notez que la jointure des sources de données Druid n'est pas encore prise en charge. Il ne doit y avoir qu'une seule source de données table dans la même requête de jointure. Druid SQL prend également en charge les jointures. Sous les couvertures, les requêtes de jointure SQL sont traduites en une ou plusieurs requêtes natives incluant des sources de données de jointure. Voir Traduction de requêtes pour plus de détails sur la traduction SQL et les meilleures pratiques pour écrire des requêtes efficaces. Lorsqu'une requête de jointure est émise, le courtier évalue d'abord toutes les sources de données, à l'exception de la source de données de base qui est la seule source de données table de la requête. L'évaluation peut inclure l'exécution de sous-requêtes pour les sources de données query. Une fois que le courtier a évalué toutes les sources de données autres que la base, il les remplace par les sources de données inline et envoie la requête réécrite aux nœuds de données (voir la section ci-dessous « Requête intégrée dans les courtiers » pour plus de détails). Les nœuds de données utilisent la jointure par hachage pour traiter les requêtes de jointure. Ils créent une table de hachage pour chaque source de données feuille non principale, à moins qu'elle n'existe déjà. Notez que seule la source de données lookup dispose actuellement d'une table de hachage prédéfinie. Voir Exécution de requête pour plus de détails sur l'exécution de requêtes de jointure. Les jointures peuvent affecter les performances de vos requêtes. En général, toutes les requêtes incluant des jointures peuvent être plus lentes que les requêtes équivalentes sur une source de données dénormalisée. La fonction LOOKUP pourrait être plus performante que les jointures avec des sources de données de recherche. Voir Performances de jointure pour plus de détails sur les performances des requêtes de jointure et les plans futurs d'amélioration des performances. https://github.com/apache/druid/pull/8728 https://github.com/apache/druid/pull/9545 https://github.com/apache/druid/pull/9111

<a name="query-inlining" href="#query-inlining">#</a> Requête en ligne dans les courtiers

Druid est désormais capable d'exécuter une requête imbriquée en incorporant des sous-requêtes. Tout type de sous-requête peut se superposer à n’importe quel type d’un autre, comme dans l’exemple suivant :

             topN
               |
       (join datasource)
         /          \
(table datasource)  groupBy

Pour exécuter cette requête, le courtier évalue d'abord la sous-requête feuille groupBy ; il envoie la sous-requête aux nœuds de données et collecte le résultat. Le résultat collecté est matérialisé dans la mémoire du Broker. Une fois que le courtier a collecté tous les résultats de la requête groupBy, il réécrit la requête topN en remplaçant la feuille groupBy par une source de données en ligne contenant le résultat de la requête groupBy. Enfin, la requête réécrite est envoyée aux nœuds de données pour exécuter la requête topN.

<a name="query-laning" href="#query-laning">#</a> Gestion des requêtes et priorisation

Lorsque vous exécutez plusieurs requêtes de charges de travail hétérogènes à la fois, vous souhaiterez peut-être parfois contrôler l'engagement des ressources pour une requête en fonction de sa priorité. Par exemple, vous souhaiterez limiter les ressources affectées aux requêtes moins importantes, afin que les requêtes importantes puissent être exécutées à temps sans être perturbées par des requêtes moins importantes. Le laning des requêtes vous permet de contrôler l’utilisation de la capacité pour les charges de travail de requêtes hétérogènes. Avec le laning, le courtier examine et classe une requête dans le but de l'attribuer à une « voie ». Les voies ont des limites de capacité, appliquées par le courtier, qui peuvent être utilisées pour garantir que des ressources suffisantes sont disponibles pour d'autres voies ou pour des requêtes interactives (sans voie), ou pour limiter le débit global des requêtes au sein de la voie. La priorisation automatique des requêtes détermine la priorité des requêtes en fonction de la stratégie configurée. La stratégie de priorisation basée sur des seuils a été ajoutée ; il réduit automatiquement la priorité des requêtes qui franchissent l'un des ensemble de seuils configurables, tels que l'ancienneté des données, la taille de l'intervalle couvert par une requête ou le nombre de segments participant à une requête. Voir Priorisation et laning des requêtes pour plus de détails. https://github.com/apache/druid/issues/6993 https://github.com/apache/druid/pull/9407 https://github.com/apache/druid/pull/9493

Nouvelle dimension dans les métriques de requête

Puisqu'une requête native contenant des sous-requêtes peut être exécutée partie par partie, un nouveau subQueryId a été introduit. Chaque sous-requête a des subQueryId différents mais le même queryId. Le subQueryId est disponible en tant que nouvelle dimension dans les métriques de requête.

Nouvelle configuration

Une nouvelle configuration druid.server.http.maxSubqueryRows contrôle le nombre maximum de lignes matérialisées dans la mémoire du Broker. Veuillez consulter Exécution de requête pour plus de détails. https://github.com/apache/druid/pull/9533

<a name="grouping-sets" href="#grouping-sets">#</a> Ensembles de regroupement SQL

GROUPING SETS est désormais pris en charge, vous permettant de combiner plusieurs clauses GROUP BY en une seule clause GROUP BY. Cette clause GROUPING SETS est traduite en interne dans la requête groupBy avec subtotalsSpec. La clause LIMIT est désormais appliquée après subtotalsSpec, plutôt qu'appliquée à chaque ensemble de regroupement. https://github.com/apache/druid/pull/9122

<a name="dynamic-params" href="#dynamic-params">#</a> Paramètres dynamiques SQL

Druid prend désormais en charge les paramètres dynamiques pour SQL. Pour utiliser des paramètres dynamiques, remplacez tout littéral de la requête par un point d'interrogation (?). Ces points d'interrogation représentent les endroits où les paramètres seront liés au moment de l'exécution. Voir Paramètres dynamiques SQL pour plus de détails. https://github.com/apache/druid/pull/6974

<a name="important-changes" href="#important-changes">#</a> Modifications importantes

<a name="limit-push-down" href="#limit-push-down">#</a> applyLimitPushDownToSegments est désactivé par défaut

applyLimitPushDownToSegments a été ajouté dans 0.17.0 pour étendre l'évaluation des limites aux nœuds interrogeables, limitant ainsi les résultats lors de l'analyse de segment pour groupBy v2. Cela peut entraîner une dégradation des performances, comme indiqué dans https://github.com/apache/druid/issues/9689, si de nombreux segments sont impliqués dans le traitement des requêtes. En effet, « limit push down to segment scan » initialise un tampon d'agrégation par segment, dont la surcharge n'est pas négligeable. Activez cette configuration uniquement si votre requête implique un nombre relativement faible de segments par tâche historique ou en temps réel. https://github.com/apache/druid/pull/9711

<a name="default-roaring" href="#default-roaring">#</a> Bitmaps rugissants par défaut

Druid prend en charge deux types de bitmap, à savoir Roaring et CONCISE. Étant donné que les bitmaps Roaring offrent une meilleure expérience prête à l'emploi (vitesse de requête plus rapide en général), le type de bitmap par défaut est désormais remplacé par les bitmaps Roaring. Voir Compression de segment pour plus de détails sur les bitmaps. https://github.com/apache/druid/pull/9548

<a name="complex-metrics" href="#complex-metrics">#</a> Le comportement des métriques complexes change au moment de l'ingestion lorsque la gestion des valeurs nulles compatible SQL est désactivée (mode par défaut)

Lorsque la gestion des valeurs nulles compatible SQL est désactivée, le comportement de l'agrégation de métriques complexes au moment de l'ingestion a désormais changé pour être cohérent avec celui au moment de la requête. Les métriques complexes sont regroupées aux valeurs par défaut 0 pour les valeurs nulles au lieu de les ignorer lors de l'ingestion. https://github.com/apache/druid/pull/9484

<a name="array-expr" href="#array-expr">#</a> Modification de la syntaxe de l'expression du tableau

L'expression Druid prend désormais en charge les constructeurs typés pour la création de tableaux. Les tableaux peuvent être définis avec un type explicite. Par exemple, <LONG>[1, 2, null] crée un tableau de type LONG contenant 1, 2 et null. Notez que vous pouvez toujours créer un tableau sans type explicite. Par exemple, [1, 2, null] reste une syntaxe valide pour créer un tableau équivalent. Dans ce cas, Druid déduira le type de tableau à partir de ses éléments. Cette nouvelle syntaxe s'applique également aux tableaux vides. <STRING>[], <DOUBLE>[] et <LONG>[] créeront respectivement un tableau vide de type STRING, DOUBLE et LONG. https://github.com/apache/druid/pull/9367

<a name="ending-segments-cleanup" href="#ending-segments-cleanup">#</a> Activation par défaut du nettoyage des segments en attente

La table pendingSegments dans le magasin de métadonnées est utilisée pour créer de nouveaux ID de segment uniques pour les tâches d'ajout telles que les tâches d'indexation Kafka/Kinesis ou les tâches par lots en mode ajout. Le nettoyage automatique des segments en attente a été introduit dans 0.12.0, mais a été désactivé par défaut avant 0.18.0. Cette configuration est désormais activée par défaut. https://github.com/apache/druid/pull/9385

<a name="better-split" href="#better-split">#</a> Création de meilleures répartitions d'entrée pour l'indexation parallèle native

La tâche parallèle peut désormais créer de meilleures répartitions. Chaque fractionnement peut contenir plusieurs fichiers d'entrée en fonction de leur taille. Les fichiers vides seront ignorés. La taille du fractionnement est contrôlable avec la nouvelle spécification d'indice de fractionnement. Voir [Spécification des indices partagés] (https://druid.apache.org/docs/0.18.0/ingestion/native-batch.html#split-hint-spec) pour plus de détails. https://github.com/apache/druid/pull/9360 https://github.com/apache/druid/pull/9450

<a name="extension-transform" href="#extension-transform">#</a> Transform est désormais un point d'extension

Transform est un Interface qui représente une transformation à appliquer à chaque ligne au moment de l'ingestion. Cette interface est désormais un point d'extension. Veuillez consulter [Écrire vos propres extensions] (https://druid.apache.org/docs/0.18.0/development/modules.html#writing-your-own-extensions) pour savoir comment ajouter votre Transform personnalisé. https://github.com/apache/druid/pull/9319

<a name="chunk-period" href="#chunk-period">#</a> Le contexte de requête chunkPeriod est supprimé

chunkPeriod est obsolète depuis 0.14.0 en raison de son utilisation limitée (il était parfois utile uniquement pour groupBy v1). Ce contexte de requête est désormais supprimé dans 0.18.0. https://github.com/apache/druid/pull/9216

<a name="java-11" href="#java-11">#</a> Prise en charge expérimentale de Java 11

Druid prend désormais en charge Java 11 à titre expérimental. Vous pouvez exécuter la même distribution binaire Druid avec Java 11 qui est compilée avec Java 8. Nos tests sur Travis incluent :

  • Compilation et exécution de tests unitaires avec Java 11
  • Compilation avec Java 8 et réalisation de tests d'intégration avec Java 11 Les résultats des tests de performances ne sont pas encore disponibles.

Avertissements concernant les accès réfléchissants illégaux lors de l'exécution de Druid avec Java 11

<a name="new-extension" href="#new-extension">#</a> Nouvelle extension

<a name="pac4j" href="#pac4j">#</a> Nouvelle extension Pac4j

Une nouvelle extension est ajoutée dans 0.18.0 pour activer l'authentification basée sur [OpenID Connect] (https://openid.net/connect/) pour les processus Druid. Cela peut être utilisé avec n'importe quel serveur d'authentification qui le prend en charge, par ex. Octa. <a name="ldap-security" href="#ldap-security">#</a> [CVE-2020-1958] Vulnérabilité d'injection LDAP d'Apache Druid

CVE-2020-1958 a été signalé récemment et corrigé dans 0.18.0 et 0.17.1. Lorsque l'authentification LDAP est activée, les appelants des Druid API peuvent contourner la barrière du filtre qualificationsValidator.userSearch ou récupérer toutes les valeurs d'attribut LDAP des utilisateurs qui existent sur le serveur LDAP, à condition que ces informations soient visibles par le serveur Druid. Veuillez consulter la description dans le lien pour plus de détails. Il est fortement recommandé de passer à 0.18.0 ou 0.17.1 si vous utilisez l'authentification LDAP avec Druid. https://github.com/apache/druid/pull/9600

<a name="known-issues" href="#known-issues">#</a> Problèmes connus

<a name="inline-query-multi-value" href="#inline-query-multi-value">#</a> Échec de la requête avec topN ou groupBy sur scan avec des colonnes à valeurs multiples

L'intégration de requêtes dans Brokers est nouvellement introduite dans 0.18.0, mais présente un bogue qui fait que les requêtes avec topN ou groupBy au-dessus de scan échouent si la requête d'analyse sélectionne des dimensions à valeurs multiples. Voir https://github.com/apache/druid/issues/9697 pour plus de détails.

<a name="npe-kafka" href="#npe-kafka">#</a> NullPointerException lors de l'utilisation de l'analyseur Avro avec le service d'indexation Kafka.

L'analyseur Avro ne fonctionne pas avec le service d'indexation Kafka en raison d'une mauvaise vérification nulle. Voir https://github.com/apache/druid/issues/9728 pour plus de détails.

<a name="unavailable-segment-metric" href="#unavailable-segment-metric">#</a> Métrique segment/unavailable/count trompeuse lors du transfert

Cette métrique est censée prendre également en compte le nombre de segments servis par les tâches en temps réel, mais ce n'est pas le cas actuellement. En conséquence, il semble que l'indisponibilité augmente avant que les nouveaux segments ne soient chargés par les historiques, même si tous les segments sont en réalité disponibles en permanence sur une combinaison de tâches et d'historiques en temps réel. https://github.com/apache/druid/issues/9677

<a name="sql-explain" href="#sql-explain">#</a> Légère différence entre le résultat de la requête explain plan for et le plan d'exécution réel

Le résultat de explain plan for peut être légèrement différent de ce que Druid exécute réellement lorsque la requête inclut des jointures ou des sous-requêtes. La différence réside dans le fait que chaque partie du plan de requête serait représentée comme s'il s'agissait de sa propre requête native dans le résultat de explain plan for. Par exemple, pour une jointure d'une source de données d1 et d'une sous-requête groupBy sur la source de données d2, le explain plan for pourrait renvoyer un plan comme ci-dessous

     join
    /    \
scan    groupBy
 |        |
d1       d2

alors que le plan de requête réel que Druid exécuterait est

     join
    /    \
  d1    groupBy
          |
         d2

druid druid-0.18.0

Apache Druid 0.18.0 contains over 200 new features, performance enhancements, bug fixes, and major documentation improvements from 42 contributors. Check out the complete list of changes and everything tagged to the milestone.

<a name="new-features" href="#new-features">#</a> New Features

<a name="join" href="#join">#</a> Join support

Join is a key operation in data analytics. Prior to 0.18.0, Druid supported some join-related features, such as Lookups or semi-joins in SQL. However, the use cases for those features were pretty limited and, for other join use cases, users had to denormalize their datasources when they ingest data instead of joining them at query time, which could result in exploding data volume and long ingestion time.

Druid 0.18.0 supports real joins for the first time ever in its history. Druid supports INNER, LEFT, and CROSS joins for now. For native queries, the join datasource has been newly introduced to represent a join of two datasources. Currently, only the left-deep join is allowed. That means, only a table or another join datasource is allowed for the left datasource. For the right datasource, lookup, inline, or query datasources are allowed. Note that join of Druid datasources is not supported yet. There should be only one table datasource in the same join query.

Druid SQL also supports joins. Under the covers, SQL join queries are translated into one or several native queries that include join datasources. See Query translation for more details of SQL translation and best practices to write efficient queries.

When a join query is issued, the Broker first evaluates all datasources except for the base datasource which is the only table datasource in the query. The evaluation can include executing subqueries for query datasources. Once the Broker evaluates all non-base datasources, it replaces them with inline datasources and sends the rewritten query to data nodes (see the below "Query inlining in Brokers" section for more details). Data nodes use the hash join to process join queries. They build a hash table for each non-primary leaf datasource unless it already exists. Note that only lookup datasource currently has a pre-built hash table. See Query execution for more details about join query execution.

Joins can affect performance of your queries. In general, any queries including joins can be slower than equivalent queries against a denormalized datasource. The LOOKUP function could perform better than joins with lookup datasources. See Join performance for more details about join query performance and future plans for performance improvement.

https://github.com/apache/druid/pull/8728 https://github.com/apache/druid/pull/9545 https://github.com/apache/druid/pull/9111

<a name="query-inlining" href="#query-inlining">#</a> Query inlining in Brokers

Druid is now able to execute a nested query by inlining subqueries. Any type of subquery can be on top of any type of another, such as in the following example:

             topN
               |
       (join datasource)
         /          \
(table datasource)  groupBy

To execute this query, the Broker first evaluates the leaf groupBy subquery; it sends the subquery to data nodes and collects the result. The collected result is materialized in the Broker memory. Once the Broker collects all results for the groupBy query, it rewrites the topN query by replacing the leaf groupBy with an inline datasource which has the result of the groupBy query. Finally, the rewritten query is sent to data nodes to execute the topN query.

<a name="query-laning" href="#query-laning">#</a> Query laning and prioritization

When you run multiple queries of heterogenous workloads at a time, you may sometimes want to control the resource commitment for a query based on its priority. For example, you would want to limit the resources assigned to less important queries, so that important queries can be executed in time without being disrupted by less important ones.

Query laning allows you to control capacity utilization for heterogeneous query workloads. With laning, the broker examines and classifies a query for the purpose of assigning it to a 'lane'. Lanes have capacity limits, enforced by the Broker, that can be used to ensure sufficient resources are available for other lanes or for interactive queries (with no lane), or to limit overall throughput for queries within the lane.

Automatic query prioritization determines the query priority based on the configured strategy. The threshold-based prioritization strategy has been added; it automatically lowers the priority of queries that cross any of a configurable set of thresholds, such as how far in the past the data is, how large of an interval a query covers, or the number of segments taking part in a query.

See Query prioritization and laning for more details.

https://github.com/apache/druid/issues/6993 https://github.com/apache/druid/pull/9407 https://github.com/apache/druid/pull/9493

New dimension in query metrics

Since a native query containing subqueries can be executed part-by-part, a new subQueryId has been introduced. Each subquery has different subQueryIds but same queryId. The subQueryId is available as a new dimension in query metrics.

New configuration

A new druid.server.http.maxSubqueryRows configuration controls the maximum number of rows materialized in the Broker memory.

Please see Query execution for more details.

https://github.com/apache/druid/pull/9533

<a name="grouping-sets" href="#grouping-sets">#</a> SQL grouping sets

GROUPING SETS is now supported, allowing you to combine multiple GROUP BY clauses into one GROUP BY clause. This GROUPING SETS clause is internally translated into the groupBy query with subtotalsSpec. The LIMIT clause is now applied after subtotalsSpec, rather than applied to each grouping set.

https://github.com/apache/druid/pull/9122

<a name="dynamic-params" href="#dynamic-params">#</a> SQL Dynamic parameters

Druid now supports dynamic parameters for SQL. To use dynamic parameters, replace any literal in the query with a question mark (?) character. These question marks represent the places where the parameters will be bound at execution time. See SQL dynamic parameters for more details.

https://github.com/apache/druid/pull/6974

<a name="important-changes" href="#important-changes">#</a> Important Changes

<a name="limit-push-down" href="#limit-push-down">#</a> applyLimitPushDownToSegments is disabled by default

applyLimitPushDownToSegments was added in 0.17.0 to push down limit evaluation to queryable nodes, limiting results during segment scan for groupBy v2. This can lead to performance degradation, as reported in https://github.com/apache/druid/issues/9689, if many segments are involved in query processing. This is because “limit push down to segment scan” initializes an aggregation buffer per segment, the overhead for which is not negligible. Enable this configuration only if your query involves a relatively small number of segments per historical or realtime task.

https://github.com/apache/druid/pull/9711

<a name="default-roaring" href="#default-roaring">#</a> Roaring bitmaps as default

Druid supports two bitmap types, i.e., Roaring and CONCISE. Since Roaring bitmaps provide a better out-of-box experience (faster query speed in general), the default bitmap type is now switched to Roaring bitmaps. See Segment compression for more details about bitmaps.

https://github.com/apache/druid/pull/9548

<a name="complex-metrics" href="#complex-metrics">#</a> Complex metrics behavior change at ingestion time when SQL-compatible null handling is disabled (default mode)

When SQL-compatible null handling is disabled, the behavior of complex metric aggregation at ingestion time has now changed to be consistent with that at query time. The complex metrics are aggregated to the default 0 values for nulls instead of skipping them during ingestion.

https://github.com/apache/druid/pull/9484

<a name="array-expr" href="#array-expr">#</a> Array expression syntax change

Druid expression now supports typed constructors for creating arrays. Arrays can be defined with an explicit type. For example, <LONG>[1, 2, null] creates an array of LONG type containing 1, 2, and null. Note that you can still create an array without an explicit type. For example, [1, 2, null] is still a valid syntax to create an equivalent array. In this case, Druid will infer the type of array from its elements. This new syntax applies to empty arrays as well. <STRING>[], <DOUBLE>[], and <LONG>[] will create an empty array of STRING, DOUBLE, and LONG type, respectively.

https://github.com/apache/druid/pull/9367

<a name="pending-segments-cleanup" href="#pending-segments-cleanup">#</a> Enabling pending segments cleanup by default

The pendingSegments table in the metadata store is used to create unique new segment IDs for appending tasks such as Kafka/Kinesis indexing tasks or batch tasks of appending mode. Automatic pending segments cleanup was introduced in 0.12.0, but has been disabled by default prior to 0.18.0. This configuration is now enabled by default.

https://github.com/apache/druid/pull/9385

<a name="better-split" href="#better-split">#</a> Creating better input splits for native parallel indexing

The Parallel task now can create better splits. Each split can contain multiple input files based on their size. Empty files will be ignored. The split size is controllable with the new split hint spec. See Split hint spec for more details.

https://github.com/apache/druid/pull/9360 https://github.com/apache/druid/pull/9450

<a name="extension-transform" href="#extension-transform">#</a> Transform is now an extension point

Transform is an Interface that represents a transformation to be applied to each row at ingestion time. This interface is now an Extension point. Please see Writing your own extensions for how to add your custom Transform.

https://github.com/apache/druid/pull/9319

<a name="chunk-period" href="#chunk-period">#</a> chunkPeriod query context is removed

chunkPeriod has been deprecated since 0.14.0 because of its limited usage (it was sometimes useful for only groupBy v1). This query context is now removed in 0.18.0.

https://github.com/apache/druid/pull/9216

<a name="java-11" href="#java-11">#</a> Experimental support for Java 11

Druid now experimentally supports Java 11. You can run the same Druid binary distribution with Java 11 which is compiled with Java 8. Our tests on Travis include:

  • Compiling and running unit tests with Java 11
  • Compiling with Java 8 and running integration tests with Java 11

Performance testing results are not available yet.

A new extension is added in 0.18.0 to enable OpenID Connect based Authentication for Druid Processes. This can be used with any authentication server that supports same e.g. Okta. <a name="security" href="#security">#</a> Security Issues

<a name="ldap-security" href="#ldap-security">#</a> [CVE-2020-1958] Apache Druid LDAP injection vulnerability

CVE-2020-1958 has been reported recently and fixed in 0.18.0 and 0.17.1. When LDAP authentication is enabled, callers of Druid APIs can bypass the credentialsValidator.userSearch filter barrier or retrieve any LDAP attribute values of users that exist on the LDAP server, so long as that information is visible to the Druid server. Please see the description in the link for more details. It is strongly recommended to upgrade to 0.18.0 or 0.17.1 if you are using LDAP authentication with Druid.

https://github.com/apache/druid/pull/9600

Kafka client library has been updated to 2.2.2, in which CVE-2019-12399 is fixed.

<a name="known-issues" href="#known-issues">#</a> Known Issues

<a name="inline-query-multi-value" href="#inline-query-multi-value">#</a> Query failure with topN or groupBy on scan with multi-valued columns

Query inlining in Brokers is newly introduced in 0.18.0 but has a bug that queries with topN or groupBy on top of scan fail if the scan query selects multi-valued dimensions. See https://github.com/apache/druid/issues/9697 for more details.

<a name="npe-kafka" href="#npe-kafka">#</a> NullPointerException when using Avro parser with Kafka indexing service.

Avro parser doesn't work with Kafka indexing service because of a wrong null check. See https://github.com/apache/druid/issues/9728 for more details.

<a name="unavailable-segment-metric" href="#unavailable-segment-metric">#</a> Misleading segment/unavailable/count metric during handoff

This metric is supposed to take the number of segments served by realtime tasks into consideration as well, but it isn't now. As a result, it appears that unavailability spikes up before the new segments are loaded by historicals, even if all segments actually are continuously available on some combination of realtime tasks and historicals.

https://github.com/apache/druid/issues/9677

<a name="sql-explain" href="#sql-explain">#</a> Slight difference between the result of explain plan for query and the actual execution plan

The result of explain plan for can be slightly different from what Druid actually executes when the query includes joins or subqueries. The difference can be found in that each part of the query plan would be represented as if it was its own native query in the result of explain plan for. For example, for a join of a datasource d1 and a groupBy subquery on datasource d2, the explain plan for could return a plan like below

     join
    /    \
scan    groupBy
 |        |
d1       d2

whereas the actual query plan Druid would execute is

     join
    /    \
  d1    groupBy
          |
         d2
