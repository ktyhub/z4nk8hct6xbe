<a name="22-new-features" href="#22-new-features">#</a> Nouvelles fonctionnalités

<a name="22-query" href="#22-query">#</a> Moteur de requête

<a name="22-multi-distinct" href="#22-multi-distinct">#</a> Prise en charge de plusieurs agrégateurs distincts dans la même requête

Druid peut désormais prendre en charge plusieurs décomptes « exacts » de DISTINCT en utilisant l'agrégateur de regroupement généralement utilisé avec les ensembles de regroupement. Notez que cela s'applique uniquement aux décomptes exacts - lorsque druid.sql.planner.useApproximateCountDistinct est faux et peut être activé en définissant druid.sql.planner.useGroupingSetForExactDistinct sur true. https://github.com/apache/druid/pull/11014

<a name="22-array-agg" href="#22-array-agg">#</a> Fonctions d'agrégation SQL ARRAY_AGG et STRING_AGG

La fonction d'agrégation ARRAY_AGG a été ajoutée pour permettre d'accumuler des valeurs ou des valeurs distinctes d'une colonne dans un seul résultat de tableau. Cette version ajoute également STRING_AGG, qui est similaire à ARRAY_AGG, sauf qu'il joint les valeurs du tableau en une seule chaîne avec un « délimiteur » fourni et qu'il ignore les valeurs nulles. Ces deux fonctions acceptent un paramètre de taille maximale pour contrôler la taille maximale du résultat et échoueront si cette valeur est dépassée. Voir Documentation SQL pour plus de détails. https://github.com/apache/druid/pull/11157 https://github.com/apache/druid/pull/11241

<a name="22-bitwise" href="#22-bitwise">#</a> Expressions et agrégateurs de fonctions mathématiques au niveau du bit

Plusieurs nouvelles fonctions SQL pour effectuer des mathématiques « au niveau du bit » (avec les expressions natives correspondantes), notamment BITWISE_AND, BITWISE_OR, BITWISE_XOR, etc. De plus, les fonctions d'agrégation BIT_AND, BIT_OR et BIT_XOR ont été ajoutées pour accumuler des valeurs dans une colonne avec la fonction bit à bit correspondante. Pour plus de détails, consultez la Documentation SQL. https://github.com/apache/druid/pull/10605 https://github.com/apache/druid/pull/10823 https://github.com/apache/druid/pull/11280

<a name="22-human-format" href="#22-human-format">#</a> Fonctions de format de nombre lisibles par l'homme

Trois nouvelles fonctions SQL et de format de nombre d'expressions natives ont été ajoutées dans Druid 0.22.0, HUMAN_READABLE_BINARY_BYTE_FORMAT, HUMAN_READABLE_DECIMAL_BYTE_FORMAT et HUMAN_READABLE_DECIMAL_FORMAT, qui permettent de transformer les résultats dans un format de consommation plus convivial pour les résultats de requête. Pour plus d'informations, consultez la Documentation SQL. https://github.com/apache/druid/issues/10584 https://github.com/apache/druid/pull/10635

<a name="22-expr-agg" href="#22-expr-agg">#</a> Agrégateur d'expressions

Druid 0.22.0 ajoute une nouvelle fonction d'agrégation d'expressions de requête « native » JSON, qui vous permet d'utiliser des expressions natives Druid pour effectuer des opérations de « repli » (également appelées « réduction ») afin d'accumuler une certaine valeur sur un nombre quelconque de colonnes d'entrée. Cela ajoute une flexibilité significative à ce qui peut être fait dans un agrégateur Druid, similaire à bien des égards à ce qui était possible avec l'agrégateur Javascript, mais d'une manière beaucoup plus sûre et en mode bac à sable. Les expressions étant désormais capables d'effectuer un "repli" sur les colonnes d'entrée complètent également vraiment les capacités des expressions natives en plus des fonctions précédemment possibles "map" (colonnes virtuelles d'expression), "filtre" (filtres d'expression) et post-transformation (post-agrégateurs d'expression). Étant donné que cela utilise des expressions, les performances ne sont pas encore optimales et ne sont pas encore directement documentées, mais il s'agit de la technologie sous-jacente derrière les fonctions SQL ARRAY_AGG, STRING_AGG et d'agrégation au niveau du bit également ajoutées dans cette version. https://github.com/apache/druid/pull/11104

<a name="22-sql-routing" href="#22-sql-routing">#</a> Améliorations du routage des requêtes SQL

Druid 0.22 ajoute de nouvelles fonctionnalités pour fournir aux rédacteurs d'extensions un contrôle amélioré sur la manière dont les requêtes sont acheminées entre les routeurs et les courtiers Druid. Le premier ajoute une nouvelle stratégie de sélection de courtier manual au routeur Druid, qui permet à une requête de spécifier manuellement à quels courtiers Druid une requête doit être envoyée en fonction d'un paramètre de contexte de requête brokerService à n'importe quel pool de courtiers défini dans druid.router.tierToBrokerMap (cela correspond au « nom de service » de l'ensemble de courtiers, druid.service). La deuxième nouvelle fonctionnalité permet au routeur Druid d'analyser et d'examiner les requêtes SQL afin que les stratégies de sélection de courtier puissent également fonctionner pour les requêtes SQL. Cela peut être activé en définissant druid.router.sql.enable sur true. Cela n'affecte pas les requêtes JDBC, qui utilisent un mécanisme différent pour faciliter les connexions « persistantes » à un seul courtier. https://github.com/apache/druid/pull/11566 https://github.com/apache/druid/pull/11495

<a name="22-proto-jdbc" href="#22-proto-jdbc">#</a> Prise en charge du protobuf Avatica JDBC

Druid prend désormais en charge l'utilisation des connexions JDBC Avatica Protobuf, par exemple pour une utilisation avec le [Pilote Avatica Golang] (https://github.com/apache/calcite-avatica-go), et dispose d'un point de terminaison distinct de l'URI JDBC JSON.

https://github.com/apache/druid/pull/10543

<a name="22-query-error-log" href="#22-query-error-log">#</a> Amélioration de la journalisation des erreurs de requête

Les exceptions de requête ont été modifiées du niveau WARN au niveau ERROR pour inclure des informations supplémentaires dans les journaux afin de faciliter le dépannage des échecs de requête. De plus, un nouvel indicateur de contexte de requête, enableQueryDebugging, a été ajouté. Il inclura les traces de pile dans ces journaux d'erreurs de requête, afin de fournir encore plus d'informations sans qu'il soit nécessaire d'activer les journaux au niveau DEBUG. https://github.com/apache/druid/pull/11519

<a name="22-batch" href="#22-batch">#</a> Ingestion par lots natifs

<a name="22-shuffle-deep-storage" href="#22-shuffle-deep-storage">#</a> Prise en charge de l'utilisation du stockage profond pour les données de lecture aléatoire intermédiaires

Les tâches d'ingestion en 2 phases natives de « cumul parfait » de Druid prennent désormais en charge l'utilisation du stockage profond comme emplacement de lecture aléatoire, comme alternative aux disques locaux sur les gestionnaires intermédiaires ou les indexeurs. Pour utiliser cette fonctionnalité, définissez druid.processing.intermediaryData.storage.type sur deepstore, qui utilise le type de stockage profond configuré. Remarque - Avec le type « deepstore », les données sont stockées dans le répertoire shuffle-data sous le chemin de stockage profond configuré, le nettoyage automatique de ce répertoire n'est pas encore pris en charge. On peut configurer des règles de cycle de vie du stockage cloud pour le nettoyage automatique des données à l'emplacement du préfixe shuffle-data. https://github.com/apache/druid/pull/11507

<a name="22-batch-memory" href="#22-batch-memory">#</a> Amélioration de l'utilisation de la mémoire des tâches d'ingestion par lots natives

L'ingestion par lots native de Druid a reçu une nouvelle option de configuration, druid.indexer.task.batchProcessingMode, qui introduit deux nouveaux modes de fonctionnement qui devraient permettre à l'ingestion par lots de fonctionner avec une empreinte d'utilisation de mémoire tas plus petite et plus prévisible. Le mode CLOSED_SEGMENTS_SINKS est le plus agressif, et devrait avoir la plus petite empreinte mémoire, et fonctionne en éliminant le suivi de la mémoire et le mmap des segments intermédiaires produits lors de la création de segments, mais n'est pas très bien testé à ce stade, donc considéré comme expérimental. CLOSED_SEGMENTS, qui est la nouvelle option par défaut, élimine mmap des segments intermédiaires, mais suit toujours l'ensemble des segments dans le tas, bien qu'il soit relativement bien testé à ce stade et considéré comme stable. OPEN_SEGMENTS utilisera le chemin d'ingestion précédent, qui est partagé avec l'ingestion en streaming et effectuera un mmap sur les segments intermédiaires et créera une chronologie afin que ces segments puissent être interrogeables par des requêtes en temps réel. Cela n'est pas du tout nécessaire pour le traitement par lots, mais le mode OPEN_SEGMENTS peut être sélectionné si des problèmes surviennent avec les 2 modes les plus récents. https://github.com/apache/druid/pull/11123 https://github.com/apache/druid/pull/11294 https://github.com/apache/druid/pull/11536

<a name="22-batch-wait-for-handoff" href="#22-batch-wait-for-handoff">#</a> Autoriser les tâches par lots à attendre le transfert du segment avant de se terminer

Les tâches d'ingestion par lots natives de Druid peuvent désormais être facultativement configurées pour ne se terminer qu'après que les segments ingérés soient complètement chargés par les serveurs historiques. Cela peut être utile dans les scénarios où le compromis consistant à garder un emplacement de tâche supplémentaire occupé vaut la peine d'utiliser l'état de la tâche comme mesure pour savoir si l'ingestion est terminée et si les segments sont disponibles pour l'interrogation. Cela peut être activé en ajoutant awaitSegmentAvailabilityTimeoutMillis au tuningConfig dans la spécification d'ingestion, qui spécifie la durée maximale pendant laquelle une tâche attendra que les segments soient chargés avant de se terminer. Si tous les segments ne sont pas disponibles à l'expiration de ce délai, la tâche réussira quand même. Cependant, dans le rapport d'ingestion, segmentAvailabilityConfirmed sera faux. Cela indique que le transfert n’a pas réussi et que ces segments nouvellement indexés peuvent ne pas être tous disponibles pour les requêtes. En revanche, si tous les segments deviennent disponibles pour les requêtes sur les services historiques avant l'expiration du délai d'attente, la valeur de cette clé dans le rapport sera vraie. Cette valeur tuningConfig n'est pas prise en charge pour les tâches de compactage pour le moment. Si un utilisateur tente de spécifier une valeur pour awaitSegmentAvailabilityTimeoutMillis pour le compactage, la tâche échouera en indiquant à l'utilisateur qu'elle n'est pas prise en charge. https://github.com/apache/druid/pull/10676

<a name="22-compact" href="#22-compact">#</a> Gestion du cycle de vie des données

<a name="22-compact-granularity" href="#22-compact-granularity">#</a> Prise en charge de la gestion de la granularité des segments et des requêtes pour le compactage automatique

Le compactage manuel et automatique de Druid peut désormais être configuré pour modifier la granularité des segments, et le compactage manuel peut également modifier la granularité des requêtes. De plus, le compactage préservera la granularité des segments par défaut. Cela permet aux opérateurs d'exécuter plus facilement des options telles que la modification de données plus anciennes vers des segments plus grands et des granularités de requête en échange d'une taille de données réduite. Voir documents de compactage pour plus de détails. https://github.com/apache/druid/pull/10843 https://github.com/apache/druid/pull/10856 https://github.com/apache/druid/pull/10900 https://github.com/apache/druid/pull/10912 https://github.com/apache/druid/pull/11009

<a name="22-compact-skip-lock" href="#22-compact-skip-lock">#</a> Autoriser le compactage à ignorer temporairement les intervalles verrouillés

Le compactage automatique de Druid ignorera désormais temporairement par défaut les intervalles verrouillés au lieu d'attendre que le verrou se libère, ce qui devrait améliorer la vitesse à laquelle les sources de données peuvent être compactées. Ceci est contrôlé par druid.coordinator.compaction.skipLockedIntervals et peut être défini sur false si ce comportement n'est pas souhaité pour une raison quelconque. https://github.com/apache/druid/pull/11190

<a name="22-config-cleanup" href="#22-config-cleanup">#</a> Prise en charge d'un nettoyage automatique supplémentaire des métadonnées

Vous pouvez configurer le nettoyage automatisé pour supprimer les enregistrements du magasin de métadonnées après avoir supprimé certaines entités de Druid :

  • enregistrements de segments
  • dossiers d'audit
  • dossiers du superviseur
  • enregistrements de règles
  • enregistrements de configuration de compactage
  • enregistrements de source de données créés par les superviseurs Cette fonctionnalité permet de maintenir les performances lorsque vous avez un taux de désabonnement élevé des sources de données, ce qui signifie que vous créez et supprimez fréquemment de nombreuses sources de données de courte durée ou d'autres entités associées. Vous pouvez limiter la durée de conservation des enregistrements de métadonnées inutilisés afin d'éviter que votre magasin de métadonnées ne se remplisse. Consultez la documentation sur le nettoyage automatique pour plus d'informations. https://github.com/apache/druid/pull/11078 https://github.com/apache/druid/pull/11084 https://github.com/apache/druid/pull/11164 https://github.com/apache/druid/pull/11200 https://github.com/apache/druid/pull/11227 https://github.com/apache/druid/pull/11232 https://github.com/apache/druid/pull/11245

<a name="22-data-cleanup" href="#22-data-cleanup">#</a> Suppression de données

Un nouveau paramètre, dropExisting, a été ajouté au ioConfig des tâches d'ingestion et de compactage par lots natifs de Druid. S'il est défini sur vrai (et appendToExist est faux), la tâche d'ingestion marquera de manière transactionnelle tous les segments existants dans l'intervalle comme inutilisés, en les remplaçant par le nouvel ensemble de segments. Cela peut être utile dans les cas d'utilisation de compactage où l'occultation normale ne remplace pas complètement un ensemble de segments dans un intervalle, par exemple lors de la modification de la granularité du segment vers une taille plus petite et où certains des compartiments de granularité les plus petits n'auraient aucune donnée, laissant les segments d'origine seulement partiellement éclipsés. Notez que cette fonctionnalité est encore expérimentale et peut entraîner une indisponibilité temporaire des données pour les données du interval compacté. La modification de cette configuration n’entraîne pas le nouveau compactage des intervalles. De même, markAsUnused a été ajouté en tant qu'option à la tâche Druid kill, qui marquera tous les segments de l'intervalle fourni comme « inutilisés » avant de supprimer tous les segments inutilisés. Ceci est utile pour permettre à la séquence de marquage inutilisé -> supprimer de se produire avec un seul appel API pour l'appelant, ainsi que pour permettre à l'action de démarquage de se produire sous un verrouillage d'intervalle de tâche. https://github.com/apache/druid/pull/11070 https://github.com/apache/druid/pull/11025 https://github.com/apache/druid/pull/11501

<a name="22-coordinator" href="#22-coordinator">#</a> Coordinateur

<a name="22-coord-timeout" href="#22-coord-timeout">#</a> Contrôle du comportement du délai d'expiration du délai de chargement du segment du coordinateur avec la gestion des segments basée sur Apache Zookeeper

Une nouvelle option de configuration dynamique du coordinateur Druid permet de contrôler le comportement chaque fois qu'une action de chargement de segment expire lors de l'utilisation de la gestion de segment basée sur Zookeeper. replicateAfterLoadTimeout lorsqu'il est défini sur true, le coordinateur tentera de répliquer le segment dont le chargement a échoué sur un autre serveur historique. Cela permet d'améliorer la disponibilité du segment s'il existe quelques serveurs historiques lents dans le cluster. Cependant, l'historique lent peut encore charger le segment plus tard et le coordinateur peut devoir émettre des demandes de suppression si le segment est trop répliqué. https://github.com/apache/druid/pull/10213

<a name="22-coord-balance" href="#22-coord-balance">#</a> Équilibrage plus rapide des segments du coordinateur

Une autre nouvelle option de configuration dynamique du coordinateur, useBatchedSegmentSampler, lorsqu'elle est définie sur true, peut potentiellement fournir une augmentation importante des performances en termes de vitesse à laquelle le coordinateur peut traiter la phase d'équilibrage des segments. Cela devrait être particulièrement visible dans les très grandes tailles de cluster avec de nombreux segments, mais est désactivé par défaut par mesure de prudence. https://github.com/apache/druid/pull/11257

<a name="22-coord-replication" href="#22-coord-replication">#</a> Amélioration de l'état de chargement du API pour éventuellement calculer la sous-réplication en fonction de la taille du cluster

L'état de chargement du coordinateur Druid API prend désormais en charge un nouveau paramètre de requête d'URL facultatif, computeUsingClusterView, qui, une fois spécifié, entraînera une sous-réplication de calcul du coordinateur pour les segments en fonction du nombre de serveurs disponibles dans le cluster sur lesquels le segment peut être répliqué, au lieu du nombre de réplications configuré dans la règle de chargement. Par exemple, si les règles de chargement spécifient 2 réplicas, mais qu'il n'y a qu'un seul serveur pouvant contenir des segments, ce API ne sera pas signalé comme sous-répliqué car les segments sont aussi répliqués que possible pour la taille de cluster donnée. https://github.com/apache/druid/pull/11056

<a name="22-coord-rep-limit" href="#22-coord-rep-limit">#</a> Limites facultatives sur le nombre de réplicants non principaux chargés par cycle de coordination

Une nouvelle configuration dynamique du coordinateur, maxNonPrimaryReplicantsToLoad, avec la valeur par défaut de Integer.MAX_VALUE, permet aux opérateurs de définir une limite supérieure stricte sur le nombre de réplicateurs non principaux qui seront chargés dans un seul cycle d'exécution du coordinateur. La valeur par défaut imitera le comportement qui existe aujourd'hui. Exemple d'utilisation : si vous définissez cette configuration sur 1 000, le coordinateur chargera un maximum de 1 000 réplicateurs non principaux à chaque exécution de cycle d'exécution. Cela signifie que si vous ingérez 2 000 segments avec un facteur de réplication de 2, le coordinateur chargera 2 000 réplicateurs principaux et 1 000 réplicateurs non principaux lors de la première exécution. Ensuite, lors de la prochaine exécution, les 1 000 derniers réplicateurs non principaux seront chargés. https://github.com/apache/druid/pull/11135

<a name="22-web-general" href="#22-web-general">#</a> Améliorations générales

L'onglet « Services » de la console Web Druid affichera désormais quels serveurs coordonnateurs et suzerains servent de leader, affichés dans la colonne « Détails » du tableau. <a name="22-web-query" href="#22-web-query">#</a> Vue Requête

La vue des requêtes de la console Web a reçu un certain nombre d'améliorations de « qualité de vie » dans Druid 0.22.0. Premièrement, la vue des requêtes fournit désormais un indicateur du temps d’exécution d’une requête : De plus, les requêtes ne s'exécuteront plus automatiquement lors de l'ouverture d'une nouvelle page, pour éviter que des requêtes obsolètes ne soient exécutées lors de l'ouverture d'un navigateur, la page sera réinitialisée à 0 si le résultat de la requête change et la limite de requête augmentera automatiquement lorsque la dernière page sera chargée en réexécutant la requête. La documentation en ligne devrait désormais également inclure des informations sur le type Druide : et devrait fournir de meilleures suggestions chaque fois qu'une erreur de requête se produit : Enfin, la vue des requêtes de la console Web prend désormais en charge la combinaison de touches de raccourci command + enter (sur Mac) et ctrl + enter sous Windows et Linux. https://github.com/apache/druid/pull/11158 https://github.com/apache/druid/pull/11128 https://github.com/apache/druid/pull/11203 https://github.com/apache/druid/pull/11365

La vue des segments de la console Web a également été améliorée pour, espérons-le, être plus performante lors de l'interaction avec la table sys.segments, notamment en offrant la possibilité de « forcer » la console Web à utiliser uniquement les méthodes natives JSON API pour afficher les informations sur les segments : La vue de recherche a également été améliorée, de sorte que la « période d'interrogation » et le « résumé » soient désormais disponibles sous forme de colonnes dans la vue liste : Nous avons également ajouté une validation pour la période d'interrogation afin d'éviter les erreurs des utilisateurs, et amélioré le rapport d'erreurs : https://github.com/apache/druid/pull/11359 https://github.com/apache/druid/pull/10909 https://github.com/apache/druid/pull/11620

<a name="22-metrics-queue" href="#22-metrics-queue">#</a> ingest/notices/queueSize

ingest/notices/queueSize est une nouvelle métrique ajoutée pour assurer la surveillance de la taille des files d'attente de traitement des messages de contrôle des tâches d'ingestion du superviseur, afin d'aider à déterminer si un superviseur peut être surchargé par un grand volume de ces notifications. Cette métrique est émise par défaut pour chaque superviseur en cours d'exécution. https://github.com/apache/druid/pull/11417

<a name="22-metrics-count" href="#22-metrics-count">#</a> requête/segments/nombre

Cette métrique n'est pas activée par défaut et doit donc être activée via une extension personnalisée pour remplacer les QueryMetrics émis de la même manière que les autres métriques de requête qui ne sont pas émises par défaut. <a name="22-avro-union-by-type" href="#22-avro-union-by-type">#</a> Extraction des champs d'union Avro par type

L'ingestion Avro à l'aide de l'ingestion par lots ou en streaming Druid prend désormais en charge un mécanisme alternatif d'extraction de données pour les types Avro Union. <a name="22-up-batch-lineage" href="#22-up-batch-lineage">#</a> Correctif d'allocation de segments d'ingestion par lots natifs

Druid 0.22.0 inclut une correction de bug importante dans l'indexation par lots native où des échecs transitoires des sous-tâches d'indexation peuvent entraîner des partitions non contiguës dans les segments de résultat, qui ne deviendront jamais interrogeables en raison de la logique qui vérifie l'ensemble « complet ». Ce problème a été résolu dans la dernière version de Druid, mais a nécessité une modification du protocole utilisé par les tâches par lots pour allouer des segments, et cette modification peut entraîner des problèmes lors des rétrogradations si vous décidez de revenir de Druid 0.22.0 à une version antérieure. Pour éviter l'échec d'une tâche lors d'une rétrogradation progressive, définissez

druid.indexer.task.default.context={ "useLineageBasedSegmentAllocation" : false }

dans les propriétés d'exécution d'Overlord et attendez que toutes les tâches dont useLineageBasedSegmentAllocation est défini sur true soient terminées avant de lancer la rétrogradation. Une fois ces tâches terminées, la rétrogradation ne devrait plus poser de problème et le paramètre peut être supprimé de la configuration Overlord (recommandé, car vous souhaiterez que ce paramètre soit activé si vous utilisez Druid 0.22.0 ou une version plus récente). https://github.com/apache/druid/pull/11189

<a name="22-up-sql-buckets" href="#22-up-sql-buckets">#</a> Les séries temporelles SQL n'ignorent plus les buckets vides avec toute la granularité

Avant Druid 0.22, une requête SQL group by qui utilise une seule clé de regroupement universelle (par exemple uniquement des agrégateurs) telle que SELECT COUNT(*), SUM(x) FROM y WHERE z = 'someval' produisait un jeu de résultats vide au lieu de [0, null] que l'on pourrait attendre de cette requête ne correspondant à aucun résultat. En effet, en dessous, cela planifierait une requête de série temporelle avec la granularité « TOUS » et skipEmptyBuckets défini sur true dans le contexte de la requête. Cette dernière option faisait en sorte que les résultats d'une telle requête ne renvoyaient aucun résultat, car il n'y avait pas de compartiments avec des valeurs à agréger et ils étaient donc ignorés, créant ainsi un ensemble de résultats vide au lieu d'un ensemble de résultats « nul ». Ce comportement a été modifié pour se comporter conformément aux autres implémentations SQL, mais le comportement précédent peut être obtenu en définissant explicitement skipEmptyBuckets sur le contexte de requête. https://github.com/apache/druid/pull/11188

<a name="22-up-reingest" href="#22-up-reingest">#</a> Modifications incompatibles avec la réingestion du druide

Les tâches par lots utilisant une source d'entrée « Druid » pour réingérer les données de segment n'accepteront plus les sections « dimensions » et « métriques » de leur spécification de tâche, et utiliseront désormais en interne un nouveau filtre de colonnes pour spécifier quelles colonnes du segment d'origine doivent être conservées. De plus, timestampSpec n'est plus ignoré, ce qui permet à la colonne __time d'être modifiée ou remplacée par une colonne différente. Ces modifications corrigent en outre un bug où les colonnes transformées seraient ignorées et indisponibles sur les nouveaux segments. https://github.com/apache/druid/pull/10267

<a name="22-up-ie11" href="#22-up-ie11">#</a> La console Web Druid ne prend plus en charge IE11 et les autres navigateurs plus anciens

Certaines choses peuvent encore fonctionner, mais elles ne sont plus officiellement prises en charge afin que les nouvelles fonctionnalités du Javascript puissent être utilisées pour développer la console Web. https://github.com/apache/druid/pull/11357

<a name="22-up-ie11" href="#22-up-ie11">#</a> Modification de la taille maximale par défaut de la file d'attente de chargement des segments

La configuration dynamique du coordinateur druide maxSegmentsInNodeLoadingQueue est passée d'illimitée (0) à 100. Cela devrait amener le coordinateur à se comporter de manière beaucoup plus détendue pendant les périodes de volatilité du cluster, comme une mise à niveau continue, mais plafonne le nombre total de segments qui seront chargés dans un cycle de coordinateur donné à 100 par serveur, ce qui peut ralentir la vitesse à laquelle un cluster complètement arrêté est démarré et chargé à partir du stockage profond. https://github.com/apache/druid/pull/11540

druid druid-0.22.0

Apache Druid 0.22.0 contains over 400 new features, bug fixes, performance enhancements, documentation improvements, and additional test coverage from 73 contributors. See the complete set of changes for additional details.

<a name="22-new-features" href="#22-new-features">#</a> New features

<a name="22-query" href="#22-query">#</a> Query engine

<a name="22-multi-distinct" href="#22-multi-distinct">#</a> Support for multiple distinct aggregators in same query

Druid now can support multiple DISTINCT 'exact' counts using the grouping aggregator typically used with grouping sets. Note that this only applies to exact counts - when druid.sql.planner.useApproximateCountDistinct is false, and can be enabled by setting druid.sql.planner.useGroupingSetForExactDistinct to true.

https://github.com/apache/druid/pull/11014

<a name="22-array-agg" href="#22-array-agg">#</a> SQL ARRAY_AGG and STRING_AGG aggregator functions

The ARRAY_AGG aggregation function has been added, to allow accumulating values or distinct values of a column into a single array result. This release also adds STRING_AGG, which is similar to ARRAY_AGG, except it joins the array values into a single string with a supplied 'delimiter' and it ignores null values. Both of these functions accept a maximum size parameter to control maximum result size, and will fail if this value is exceeded. See SQL documentation for additional details.

https://github.com/apache/druid/pull/11157 https://github.com/apache/druid/pull/11241

<a name="22-bitwise" href="#22-bitwise">#</a> Bitwise math function expressions and aggregators

Several new SQL functions functions for performing 'bitwise' math (along with corresponding native expressions), including BITWISE_AND, BITWISE_OR, BITWISE_XOR and so on. Additionally, aggregation functions BIT_AND, BIT_OR, and BIT_XOR have been added to accumulate values in a column with the corresponding bitwise function. For complete details see SQL documentation.

https://github.com/apache/druid/pull/10605 https://github.com/apache/druid/pull/10823 https://github.com/apache/druid/pull/11280

<a name="22-human-format" href="#22-human-format">#</a> Human readable number format functions

Three new SQL and native expression number format functions have been added in Druid 0.22.0, HUMAN_READABLE_BINARY_BYTE_FORMAT, HUMAN_READABLE_DECIMAL_BYTE_FORMAT, and HUMAN_READABLE_DECIMAL_FORMAT, which allow transforming results into a more friendly consumption format for query results. For more information see SQL documentation.

https://github.com/apache/druid/issues/10584 https://github.com/apache/druid/pull/10635

<a name="22-expr-agg" href="#22-expr-agg">#</a> Expression aggregator

Druid 0.22.0 adds a new 'native' JSON query expression aggregator function, that lets you use Druid native expressions to perform "fold" (alternatively known as "reduce") operations to accumulate some value on any number of input columns. This adds significant flexibility to what can be done in a Druid aggregator, similar in a lot of ways to what was possible with the Javascript aggregator, but in a much safer, sandboxed manner.

Expressions now being able to perform a "fold" on input columns also really rounds out the abilities of native expressions in addition to the previously possible "map" (expression virtual columns), "filter" (expression filters) and post-transform (expression post-aggregators) functions.

Since this uses expressions, performance is not yet optimal, and it is not directly documented yet, but it is the underlying technology behind the SQL ARRAY_AGG, STRING_AGG, and bitwise aggregator functions also added in this release.

https://github.com/apache/druid/pull/11104

<a name="22-sql-routing" href="#22-sql-routing">#</a> SQL query routing improvements

Druid 0.22 adds some new facilities to provide extension writers with enhanced control over how queries are routed between Druid routers and brokers. The first adds a new manual broker selection strategy to the Druid router, which allows a query to manually specify which Druid brokers a query should be sent to based on a query context parameter brokerService to any broker pool defined in druid.router.tierToBrokerMap (this corresponds to the 'service name' of the broker set, druid.service).

The second new feature allows the Druid router to parse and examine SQL queries so that broker selection strategies can also function for SQL queries. This can be enabled by setting druid.router.sql.enable to true. This does not affect JDBC queries, which use a different mechanism to facilitate "sticky" connections to a single broker.

https://github.com/apache/druid/pull/11566 https://github.com/apache/druid/pull/11495

<a name="22-proto-jdbc" href="#22-proto-jdbc">#</a> Avatica protobuf JDBC Support

Druid now supports using Avatica Protobuf JDBC connections, such as for use with the Avatica Golang Driver, and has a separate endpoint from the JSON JDBC uri.

String url = "jdbc:avatica:remote:url=http://localhost:8082/druid/v2/sql/avatica-protobuf/;serialization=protobuf";

https://github.com/apache/druid/pull/10543

<a name="22-query-error-log" href="#22-query-error-log">#</a> Improved query error logging

Query exceptions have been changed from WARN level to ERROR level to include additional information in the logs to help troubleshoot query failures. Additionally, a new query context flag, enableQueryDebugging has been added that will include stack traces in these query error logs, to provide even more information without the need to enable logs at the DEBUG level.

https://github.com/apache/druid/pull/11519

<a name="22-streaming" href="#22-streaming">#</a> Streaming Ingestion

<a name="22-streaming-task-autoscaling" href="#22-streaming-task-autoscaling">#</a> Task autoscaling for Kafka and Kinesis streaming ingestion

Druid 0.22.0 now offers experimental support for dynamic Kafka and Kinesis task scaling. The included strategies are driven by periodic measurement of stream lag (which is based on message count for Kafka, and difference of age between the message iterator and the oldest message for Kinesis), and will adjust the number of tasks based on the amount of 'lag' and several configuration parameters. See Kafka and Kinesis documentation for complete information.

https://github.com/apache/druid/pull/10524 https://github.com/apache/druid/pull/10985

<a name="22-avro-proto-stream" href="#22-avro-proto-stream">#</a> Avro and Protobuf streaming InputFormat and Confluent Schema Registry Support

Druid streaming ingestion now has support for Avro and Protobuf in the updated InputFormat specification format, which replaces the deprecated firehose/parser specification used by legacy Druid streaming formats. Alongside this, comes support for obtaining schemas for these formats from Confluent Schema Registry. See data formats documentation for further information.

https://github.com/apache/druid/pull/11040 https://github.com/apache/druid/pull/11018 https://github.com/apache/druid/pull/10314 https://github.com/apache/druid/pull/10839

<a name="22-kafka-groupid" href="#22-kafka-groupid">#</a> Kafka ingestion support for specifying group.id

Druid Kafka streaming ingestion now optionally supports specifying group.id on the connections Druid tasks make to the Kafka brokers. This is useful for accessing clusters which require this be set as part of authorization, and can be specified in the consumerProperties section of the Kafka supervisor spec. See Kafka ingestion documentation for more details.

<a name="22-shuffle-deep-storage" href="#22-shuffle-deep-storage">#</a> Support for using deep storage for intermediary shuffle data

Druid native 'perfect rollup' 2-phase ingestion tasks now support using deep storage as a shuffle location, as an alternative to local disks on middle-managers or indexers. To use this feature, set druid.processing.intermediaryData.storage.type to deepstore, which uses the configured deep storage type.

Note - With "deepstore" type, data is stored in shuffle-data directory under the configured deep storage path, auto clean up for this directory is not supported yet. One can setup cloud storage lifecycle rules for auto clean up of data at shuffle-data prefix location.

https://github.com/apache/druid/pull/11507

<a name="22-batch-memory" href="#22-batch-memory">#</a> Improved native batch ingestion task memory usage

Druid native batch ingestion has received a new configuration option, druid.indexer.task.batchProcessingMode which introduces two new operating modes that should allow batch ingestion to operate with a smaller and more predictable heap memory usage footprint. The CLOSED_SEGMENTS_SINKS mode is the most aggressive, and should have the smallest memory footprint, and works by eliminating in memory tracking and mmap of intermediary segments produced during segment creation, but isn't super well tested at this point so considered experimental. CLOSED_SEGMENTS, which is the new default option, eliminates mmap of intermediary segments, but still tracks the entire set of segments in heap, though it is relatively well tested at this point and considered stable. OPEN_SEGMENTS will use the previous ingestion path, which is shared with streaming ingestion and performs a mmap on intermediary segments and builds a timeline so that these segments can be queryable by realtime queries. This is not needed at all for batch, but OPEN_SEGMENTS mode can be selected if any problems occur with the 2 newer modes.

https://github.com/apache/druid/pull/11123 https://github.com/apache/druid/pull/11294 https://github.com/apache/druid/pull/11536

<a name="22-batch-wait-for-handoff" href="#22-batch-wait-for-handoff">#</a> Allow batch tasks to wait until segment handoff before completion

Druid native batch ingestion tasks can now be optionally configured to not terminate until after the ingested segments are completely loaded by Historical servers. This can be useful for scenarios when the trade-off of keeping an extra task slot occupied is worth using the task state as a measure of if ingestion is complete and segments are available to query.

This can be enabled by adding awaitSegmentAvailabilityTimeoutMillis to the tuningConfig in the ingestion spec, which specifies the maximum amount of time that a task will wait for segments to be loaded before terminating. If not all segments become available by the time this timeout expires, the job will still succeed. However, in the ingestion report, segmentAvailabilityConfirmed will be false. This indicates that handoff was not successful and these newly indexed segments may not all be available for query. On the other hand, if all segments become available for query on the Historical services before the timeout expires, the value for that key in the report will be true.

This tuningConfig value is not supported for compaction tasks at this time. If a user tries to specify a value for awaitSegmentAvailabilityTimeoutMillis for Compaction, the task will fail telling the user it is not supported.

https://github.com/apache/druid/pull/10676

<a name="22-compact-granularity" href="#22-compact-granularity">#</a> Support managing segment and query granularity for auto-compaction

Druid manual and automatic compaction can now be configured to change segment granularity, and manual compaction can also change query granularity. This allows operators to more easily perform options like changing older data to larger segment and query granularities in exchange for decreased data size. See compaction docs for details.

<a name="22-config-cleanup" href="#22-config-cleanup">#</a> Support for additional automatic metadata cleanup

You can configure automated cleanup to remove records from the metadata store after you delete delete some entities from Druid:

  • segments records
  • audit records
  • supervisor records
  • rule records
  • compaction configuration records
  • datasource records created by supervisors

This feature helps maintain performance when you have a high datasource churn rate, meaning you frequently create and delete many short-lived datasources or other related entities. You can limit the length of time to retain unused metadata records to prevent your metadata store from filling up. See automatic cleanup documentation for more information.

<a name="22-data-cleanup" href="#22-data-cleanup">#</a> Dropping data

A new setting, dropExisting has been added to the ioConfig of Druid native batch ingestion tasks and compaction, which if set to true (and appendToExist is false), then the ingestion task will transactionally mark all existing segments in the interval as unused, replacing them with the new set of segments. This can be useful in compaction use cases where normal overshadowing does not completely replace a set of segments in an interval, such as when changing segment granularity to a smaller size and some of the smaller granularity buckets would have no data, leaving the original segments only partially overshadowed.

Note that this functionality is still experimental, and can result in temporary data unavailability for data within the compacted interval. Changing this config does not cause intervals to be compacted again.

Similarly, markAsUnused has been added as an option to the Druid kill task, which will mark any segments in the supplied interval as 'unused' prior to deleting all of the unused segments. This is useful for allowing the mark unused -> delete sequence to happen with a single API call for the caller, as well as allowing the unmark action to occur under a task interval lock.

<a name="22-coordinator" href="#22-coordinator">#</a> Coordinator

<a name="22-coord-timeout" href="#22-coord-timeout">#</a> Control over coordinator segment load timeout timeout behavior with Apache Zookeeper based segment management

A new Druid coordinator dynamic configuration option allows controlling the behavior whenever a segment load action times out when using Zookeeper based segment management. replicateAfterLoadTimeout when set to true, the coordinator will attempt to replicate the segment that failed to load to a different historical server. This helps improve the segment availability if there are a few slow historical servers in the cluster. However, the slow historical may still load the segment later and the coordinator may need to issue drop requests if the segment is over-replicated.

<a name="22-coord-balance" href="#22-coord-balance">#</a> Faster coordinator segment balancing

Another new coordinator dynamic configuration option, useBatchedSegmentSampler, when set to true can potentially provide a large performance increase in the speed which the coordinator can process the segment balancing phase. This should be particularly notable at very large cluster sizes with many segments, but is disabled by default to err on the side of caution.

https://github.com/apache/druid/pull/11257

<a name="22-coord-replication" href="#22-coord-replication">#</a> Improved loadstatus API to optionally compute under-replication based on cluster size

The Druid coordinator load status API now supports a new optional URL query parameter, computeUsingClusterView, which when specified will cause the coordinator compute under-replication for segments based on the number of servers available within cluster that the segment can be replicated to, instead of the configured replication count configured in load rule. For example, if the load rules specify 2 replicas, but there is only 1 server which can hold segments, this API would not report as under-replicated because the segments are as replicated as is possible for the given cluster size.

https://github.com/apache/druid/pull/11056

<a name="22-coord-rep-limit" href="#22-coord-rep-limit">#</a> Optional limits on the number of non-primary replicants loaded per coordination cycle

A new coordinator dynamic configuration, maxNonPrimaryReplicantsToLoad, with default value of Integer.MAX_VALUE, lets operators to define a hard upper limit on the number of non-primary replicants that will be loaded in a single coordinator execution cycle. The default value will mimic the behavior that exists today.

Example usage: If you set this configuration to 1000, the coordinator will load a maximum of 1000 non-primary replicants in each run cycle execution. Meaning if you ingested 2000 segments with a replication factor of 2, the coordinator would load 2000 primary replicants and 1000 non-primary replicants on the first execution. Then the next execution, the last 1000 non-primary replicants will be loaded.

https://github.com/apache/druid/pull/11135

<a name="22-up-batch-lineage" href="#22-up-batch-lineage">#</a> Native batch ingestion segment allocation fix

Druid 0.22.0 includes an important bug-fix in native batch indexing where transient failures of indexing sub-tasks can result in non-contiguous partitions in the result segments, which will never become queryable due to logic which checks for the 'complete' set. This issue has been resolved in the latest version of Druid, but required a change in the protocol which batch tasks use to allocate segments, and this change can cause issues during rolling downgrades if you decide to roll back from Druid 0.22.0 to an earlier version.

To avoid task failure during a rolling-downgrade, set

druid.indexer.task.default.context={ "useLineageBasedSegmentAllocation" : false }

in the overlord runtime properties, and wait for all tasks which have useLineageBasedSegmentAllocation set to true to complete before initiating the downgrade. After these tasks have all completed the downgrade shouldn't have any further issue and the setting can be removed from the overlord configuration (recommended, as you will want this setting enabled if you are running Druid 0.22.0 or newer).

https://github.com/apache/druid/pull/11189

<a name="22-up-sql-buckets" href="#22-up-sql-buckets">#</a> SQL timeseries no longer skip empty buckets with all granularity

Prior to Druid 0.22, an SQL group by query which is using a single universal grouping key (e.g. only aggregators) such as SELECT COUNT(*), SUM(x) FROM y WHERE z = 'someval' would produce an empty result set instead of [0, null] that might be expected from this query matching no results. This was because underneath this would plan into a timeseries query with 'ALL' granularity, and skipEmptyBuckets set to true in the query context. This latter option caused the results of such a query to return no results, as there are no buckets with values to aggregate and so they are skipped, making an empty result set instead of a 'nil' result set. This behavior has been changed to behave in line with other SQL implementations, but the previous behavior can be obtained by explicitly setting skipEmptyBuckets on the query context.

https://github.com/apache/druid/pull/11188

<a name="22-up-reingest" href="#22-up-reingest">#</a> Druid reingestion incompatible changes

Batch tasks using a 'Druid' input source to reingest segment data will no longer accept the 'dimensions' and 'metrics' sections of their task spec, and now will internally use a new columns filter to specify which columns from the original segment should be retained. Additionally, timestampSpec is no longer ignored, allowing the __time column to be modified or replaced with a different column. These changes additionally fix a bug where transformed columns would be ignored and unavailable on the new segments.

https://github.com/apache/druid/pull/10267

<a name="22-up-ie11" href="#22-up-ie11">#</a> Druid web-console no longer supports IE11 and other older browsers

<a name="22-up-ie11" href="#22-up-ie11">#</a> Changed default maximum segment loading queue size

Druid coordinator maxSegmentsInNodeLoadingQueue dynamic configuration has been changed from unlimited (0) to instead to 100. This should make the coordinator behave in a much more relaxed manner during periods of cluster volatility, such as a rolling upgrade, but caps the total number of segments that will be loaded in any given coordinator cycle to 100 per server, which can slow down the speed at which a completely stopped cluster is started and loaded from deep storage.
