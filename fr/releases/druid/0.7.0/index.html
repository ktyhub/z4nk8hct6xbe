druide druide-0.7.0

Mise à jour vers Druid 0.7.0 – Ce qu'il faut savoir

  • Nouvelle spécification d'ingestion Druid 0.7.0 nécessite un nouveau format de spécification d'ingestion. Druid 0.6.172 prend en charge à la fois les anciens et les nouveaux formats d'ingestion et dispose de scripts pour convertir de l'ancien au nouveau format. Ce script peut être exécuté avec 'tools convertSpec' en utilisant le même Main que celui utilisé pour exécuter les nœuds Druid. Vous pouvez mettre à jour votre cluster Druid vers 0.6.172, mettre à jour vos spécifications d'ingestion vers le nouveau format, puis mettre à jour vers Druid 0.7.0. Si vous mettez à jour votre cluster directement vers Druid 0.7.0, assurez-vous que votre pipeline d'ingestion en temps réel comprend la nouvelle spécification.
  • MySQL n'est plus le stockage de métadonnées par défaut Druid intègre désormais par défaut Apache Derby, qui a été choisi principalement à des fins de testabilité. Cependant, nous ne recommandons pas d'utiliser Derby en production. Pour toute autre chose que les tests, veuillez utiliser le stockage de métadonnées MySQL ou PostgreSQL. [Paramètres de configuration pour le stockage des métadonnées] (http://druid.io/docs/0.7.0/Configuration.html#metadata-storage) ont été renommés de druid.db à druid.metadata.storage et un druid.metadata.storage.type=<mysql|postgresql> supplémentaire est requis pour utiliser autre chose que Derby. L'outil convertProps peut vous aider à convertir toutes les propriétés 0.6.x en propriétés 0.7.
  • Druid est désormais sensible à la casse Les noms de colonnes Druid sont désormais sensibles à la casse. Nous avions auparavant essayé de ne pas respecter la casse pour les requêtes et de préserver la casse pour les données, mais nous avons décidé d'effectuer ce changement car il y avait de nombreux bugs liés à divers problèmes de casse. Si vous effectuez une mise à niveau à partir de la version 0.6.x :
    1. Veuillez vous assurer que la casse des colonnes dans vos requêtes correspond à la casse des noms de colonnes dans vos données et mettez à jour vos requêtes en conséquence.
    2. Une chose très importante à noter est que 0.6 met en minuscules en interne tous les noms de colonnes au moment de l'ingestion et au moment de la requête. Dans 0.7, ce n'est plus le cas, cependant, nous vous recommandons toujours fortement d'utiliser des noms de colonnes en minuscules dans 0.7 pour plus de simplicité.
    3. Si vous ingérez actuellement des données avec des noms de colonnes à casse mixte dans le cadre de votre schéma de données ou d'ingestion :
      • pour les données TSV ou CSV, mettez simplement en minuscules les noms de vos colonnes dans votre schéma lorsque vous mettez à jour vers 0.7.0.
      • pour les données JSON avec des champs à casse mixte et si vous ne spécifiiez pas les noms des colonnes, vous pouvez utiliser la jsonLowerCase parseSpec pour mettre les données en minuscules pour vous au moment de l'ingestion et maintenir la compatibilité ascendante. Pour toutes les autres spécifications d'analyse, vous devrez mettre en minuscule le noms de métriques/agrégateurs si vous utilisiez auparavant une casse mixte.
  • L'annonce du segment par lots est désormais la valeur par défaut Druid utilise désormais l'annonce de segment par lots par défaut pour tous les nœuds. Si vous utilisez déjà [annonce de segment par lots] (http://druid.io/docs/0.7.0-rc3/Configuration.html#data-segment-announcer), vous devriez être prêt. Si vous n'avez pas encore mis à jour l'utilisation de l'annonce de segments par lots, veuillez lire [ce guide sur le forum] (https://groups.google.com/forum/#!searchin/druid-development/eric$200.5$20batch$20segment/druid-development/vKV8pTAd0Gg/VgC8ee6XWZ0J) pour savoir comment mettre à jour votre cluster 0.6.x actuel pour utiliser d'abord l'annonce par lots.
  • Kafka 0.7.x supprimé au profit de Kafka 0.8.x Si vous utilisez Kafka 0.7, vous devrez créer l'extension kafka-seven manuellement. Il est commenté dans la version, car Kafka 0.7 n'est pas disponible dans Maven Central. L'extension Kafka 0.8 (kafka-eight) n'est pas affectée.
  • Modifications du point de terminaison du coordinateur De nombreux points de terminaison du coordinateur ont changé. Veuillez vous référer à la [documentation du coordinateur] (http://druid.io/docs/0.7.0-rc3/Coordinator.html#http-endpoints) pour savoir de quoi il s'agit. En particulier:
  1. /info sur le coordinateur a été supprimé.
  2. /health sur les nœuds historiques a été supprimé
  • Pot séparé requis pour com.metamx.metrics.SysMonitor Si vous disposez actuellement de com.metamx.metrics.SysMonitor dans votre configuration druid.monitoring.monitors et que vous souhaitez le conserver, vous devrez ajouter le jar de la bibliothèque SIGAR à votre chemin de classe. Alternativement, vous pouvez simplement supprimer com.metamx.metrics.SysMonitor si vous ne comptez pas sur les métriques sys/.*. Nous avons dû supprimer la dépendance directe sur SIGAR afin de déplacer les artefacts Druid vers Maven Central, car SIGAR n'y est actuellement pas disponible.
  • Procédure de mise à jour Si vous utilisez une version de Druid antérieure à 0.6.172, veuillez d'abord effectuer une mise à niveau vers 0.6.172. Voir les 0.6.172 release notes pour les instructions. Afin de garantir une mise à niveau continue fluide sans temps d'arrêt, les nœuds doivent être mis à jour dans l'ordre suivant :
    1. nœuds historiques
    2. service d'indexation/nœuds en temps réel
    3. les nœuds du routeur (si vous en avez),
    4. nœuds de courtier
    5. Nœuds coordinateurs

Nouvelles fonctionnalités

  • Prise en charge des colonnes métriques longues Jusqu'à présent, Druid stockait toutes les métriques sous forme de valeurs à virgule flottante simple précision, ce qui pouvait introduire des erreurs d'arrondi et des résultats inattendus avec les requêtes utilisant les agrégateurs longSum, en particulier pour les requêtes groupBy.
  • Stockage de métadonnées enfichable MySQL, PostgreSQL et Derby (pour les tests) sont désormais pris en charge immédiatement. Derby ne prend en charge qu'un seul maître ou ne doit pas être utilisé pour une production à haute disponibilité, utilisez le basculement MySQL ou PostgreSQL pour cela.
  • Ingestion de données simplifiée API refaire complètement l'ingestion de données de Druid API.
  • Changer la compression pour les colonnes métriques de LZF à LZ4 Les premiers tests de performances montrent qu'il peut être entre 15 % et 25 % plus rapide et que les segments sont environ 3 à 5 % plus petits sur des ensembles de données typiques.
  • Index bitmap inversés configurables Druid prend désormais en charge les Roaring Bitmaps en plus des Concise Bitmaps par défaut. Les premiers tests de performances montrent que Roaring peut être jusqu'à 20 % plus rapide pour certains types de requêtes, au détriment de segments 20 % plus grands en moyenne.
  • Tests d'intégration Nous avons ajouté un ensemble de tests d'intégration qui utilisent Docker pour lancer un cluster Druid afin d'exécuter une série de tests d'indexation et de requêtes.
  • Nouvelle console Druide Coordinateur Nous avons introduit une nouvelle console Druid qui devrait, espérons-le, fournir un meilleur aperçu de l'état de votre cluster et être un peu plus évolutive si vous avez des centaines de milliers de segments. Nous prévoyons d'étendre cette console pour fournir plus d'informations sur l'état actuel d'un cluster Druid.
  • Contexte du résultat de la requête Les contextes de résultats peuvent signaler des erreurs lors des requêtes dans les en-têtes de requête. Nous utilisons actuellement cette fonctionnalité pour les tentatives internes, mais espérons l'étendre pour rapporter plus d'informations à clients.

Améliorations

  • Vitesse de requête plus rapide De nombreuses améliorations de vitesse grâce à un format de compression plus rapide, de petites optimisations dans la structure des colonnes et des optimisations des requêtes avec plusieurs agrégations, ainsi que de nombreuses améliorations des performances des requêtes groupBy. Dans l'ensemble, certaines requêtes peuvent être jusqu'à deux fois plus rapides en utilisant le nouveau format d'index.
  • Artefacts druidiques dans Maven Central Les artefacts Druid sont désormais disponibles dans Maven Central pour faciliter vos propres builds et déploiements.
  • Fichier de configuration commun Druid dispose désormais d'un common.runtime.properties où vous pouvez déclarer toutes les propriétés globales ainsi que toutes vos dépendances externes. Cela évite une configuration répétée sur plusieurs nœuds et, espérons-le, rendra la configuration d'un cluster Druid un peu moins pénible.
  • Noms d'hôte, noms de port et de service par défaut Les noms d'hôte, de ports et de services par défaut pour tous les nœuds signifient que beaucoup moins de configuration est requise au départ si vous êtes satisfait des valeurs par défaut. Cela signifie également que vous pouvez exécuter tous les types de nœuds sur une seule machine sans vous soucier des conflits de ports.
  • Les noms de colonnes Druide sont désormais sensibles à la casse Mort aux bugs du boîtier. Soyez conscient des dangers liés à la mise à jour vers 0.7.0 si vous avez des colonnes à casse mixte et que vous utilisez 0.6.x. Voir ci-dessus pour plus de détails.
  • Nouvelles tentatives de requête Druid réessayera désormais automatiquement les requêtes pour certaines classes d'échecs.
  • Mise en cache en arrière-plan Pour certains types de requêtes, en particulier celles qui impliquent des comptes distincts (hyperloglog), cela peut améliorer les performances jusqu'à 20 %. La mise en cache en arrière-plan est désactivée par défaut.
  • Utilisation réduite de la mémoire du coordinateur Utilisation réduite de la mémoire du coordinateur (jusqu'à 50 %). Cela résout un problème où un coordinateur perdait parfois son leadership en raison de GC fréquents.
  • Les métriques peuvent désormais être émises vers les points de terminaison SSL
  • Prise en charge supplémentaire des informations d'identification AWS, merci @gnethercutt
  • Mesures de persistance et de limitation supplémentaires pour l'ingestion en temps réel Cela devrait aider à diagnostiquer quand l’ingestion en temps réel est limitée et combien de temps dure la persistance. Ces métriques fournissent une bonne indication du moment où il est temps d’augmenter l’ingestion en temps réel.
  • Point de terminaison d'initialisation du courtier Les courtiers fournissent désormais un point de terminaison d'état dans /druid/broker/v1/loadstatus pour indiquer s'ils sont prêts à être interrogés, ce qui facilite les mises à niveau/redémarrages progressifs.

Corrections de bugs

  • Prise en charge de plusieurs fragments de la même source de données sur le même nœud en temps réel. Merci @zhaown
  • Les journaux de tâches HDFS devraient désormais fonctionner comme prévu. Merci @flowbehappy.
  • Condition de blocage possible corrigée dans le courtier.
  • Divers correctifs pour la compression GZIP lors du renvoi des résultats.
  • druid.host devrait désormais également prendre en charge les adresses IPv6. ##Documents
  • Nouveaux tutoriels.
  • Nouvelle documentation d'ingestion.
  • Nouvelle documentation de configuration.
  • Améliorations de la documentation des règles. Merci @mrijke

Problèmes connus

  • La fusion de segments avec différents types d'index bitmap n'est actuellement pas possible, donc si vous avez les deux types d'index dans votre cluster, vous devez définir druid.coordinator.merge.on sur false. 'false' est la valeur par défaut de la configuration.
  • https://github.com/druid-io/druid/issues/1045 Problème avec les requêtes GoupBy avec des agrégations et post-agrégations complexes utilisant le même nom
  • https://github.com/druid-io/druid-api/pull/38 Si vous utilisez longSum dans votre spécification d'ingestion, la présence de données à virgule flottante peut générer des exceptions.

druid druid-0.7.0

Updating to Druid 0.7.0 – Things to be Aware

  • New ingestion spec

    Druid 0.7.0 requires a new ingestion spec format. Druid 0.6.172 supports both the old and new formats of ingestion and has scripts to convert from the old to the new format. This script can be run with 'tools convertSpec' using the same Main used to run Druid nodes. You can update your Druid cluster to 0.6.172, update your ingestion specs to the new format, and then update to Druid 0.7.0. If you update your cluster to Druid 0.7.0 directly, make sure your real-time ingestion pipeline understands the new spec.

  • MySQL is no longer the default metadata storage

    Druid now defaults to embedding Apache Derby, which was chosen mainly for testability purposes. However, we do not recommend using Derby in production. For anything other than testing, please use MySQL or PostgreSQL metadata storage.

    Configuration parameters for metadata storage were renamed from druid.db to druid.metadata.storage and an additional druid.metadata.storage.type=<mysql|postgresql> is required to use anything other than Derby.

    The convertProps tool can assis you in convertng all 0.6.x properties to 0.7 properties.

  • Druid is now case-sensitive

    Druid column names are now case-sensitive. We previously tried to be case-insensitive for queries and case-preserving for data, but we decided to make this change as there were numerous bugs related to various casing problems.

    If you are upgrading from version 0.6.x:

    1. Please make sure the column casing in your queries matches the casing of your column names in your data and update your queries accordingly.
    2. One very important thing to note is that 0.6 internally lower-cased all column names at ingestion time and query time. In 0.7, this is no longer the case, however, we still strongly recommend that you use lowercase column names in 0.7 for simplicity.
    3. If you are currently ingesting data with mixed case column names as part of your data or ingestion schema:
      • for TSV or CSV data, simply lower-case your column names in your schema when you update to 0.7.0.
      • for JSON data with mixed case fields and if you were not specifying the names of the columns, you can use the jsonLowerCase parseSpec to lower-case the data for you at ingestion time and maintain backwards compatibility.

    For all other parse specs, you will need to lower-case the

    metric/aggregator names if you were using mixed case before.

  • Batch segment announcement is now the default

    Druid now uses batch segment announcement by default for all nodes. If you are already using batch segment announcement, you should be all set.

    If you have not yet updated to using batch segments announcement, please read this guide in the forum on how to update your current 0.6.x cluster to use batch announcement first.

  • Kafka 0.7.x removed in favor of Kafka 0.8.x

    If you are using Kafka 0.7, you will have to build the kafka-seven extension manually. It is commented out in the build, because Kafka 0.7 is not available in Maven Central. The Kafka 0.8 (kafka-eight) extension is unaffected.

  • Coordinator endpoint changes

    Numerous coordinator endpoints have changed. Please refer to the coordinator documentation for what they are.

    In particular:

    1. /info on the coordinator has been removed.
    2. /health on historical nodes has been removed

  • Separate jar required for com.metamx.metrics.SysMonitor

    If you currenly have com.metamx.metrics.SysMonitor as part of your druid.monitoring.monitors configuration and would like to keep it, you will have to add the SIGAR library jar to your classpath.

    Alternatively, you can simply remove com.metamx.metrics.SysMonitor if you do not rely on the sys/.* metrics.

    We had to remove the direct dependency on SIGAR in order to move Druid artifacts to Maven Central, since SIGAR is currently not available there.

  • Update Procedure

    If you are running a version of Druid older than 0.6.172, please upgrade to 0.6.172 first. See the 0.6.172 release notes for instructions.

    In order to ensure a smooth rolling upgrade without downtime, nodes must be updated in the following order:

    1. historical nodes
    2. indexing service/real-time nodes
    3. router nodes (if you have any),
    4. broker nodes
    5. coordinator nodes

New Features

  • Long metric column support

    Until now Druid stored all metrics as single precision floating point values, which could introduce rounding errors and unexpected results with queries using longSum aggregators, especially for groupBy queries.

  • Pluggable metadata storage

    MySQL, PostgreSQL, and Derby (for testing) are now supported out of the box. Derby only supports single master or should not be used for high availability production, use MySQL or PostgreSQL failover for that.

  • Simplified data ingestion API

    completely redo Druid’s data ingestion API.

  • Switch compression for metric colums from LZF to LZ4

    Initial performance tests show it may be between 15% and 25% faster, and results in segments about 3-5% smaller on typical data sets.

  • Configurable inverted bitmap indexes

    Druid now supports Roaring Bitmaps in addition to the default Concise Bitmaps. Initial performance tests show Roaring may be up to 20% faster for certain types of queries, at the expense of segments being 20% larger on average.

  • Integration tests

    We have added a set of integration tests that use Docker to spin up a Druid cluster to run a series of indexing and query tests.

  • New Druid Coordinator console

    We introduced a new Druid console that should hopefully provide a better overview of the status of your cluster and be a bit more scalable if you have hundreds of thousands of segments. We plan to expand this console to provide more information about the current state of a Druid cluster.

  • Query Result Context

    Result contexts can report errors during queries in the query headers. We are currently using this feature for internal retries, but hope to expand it to report more information back to clients.

Improvements

  • Faster query speeds

    Lots of speed improvements thanks to faster compression format, small optimizations in column structure, and optimizations of queries with multiple aggregations, as well as numerous groupBy query performance improvements. Overall, some queries can be up to twice as fast using the new index format.

  • Druid artifacts in Maven Central

    Druid artifacts are now available in Maven Central to make your own builds and deployments easier.

  • Common Configuration File

    Druid now has a common.runtime.properties where you can declare all global properties as well as all of your external dependencies. This avoids repeated configuration across multiple nodes and will hopefully make setting up a Druid cluster a little less painful.

  • Default host names, port and service names

    Default host names, ports, and service names for all nodes means a lot less configuration is required upfront if you are happy with the defaults. It also means you can run all node types on a single machine without fiddling with port conflicts.

  • Druid column names are now case sensitive

    Death to casing bugs. Be aware of the dangers of updating to 0.7.0 if you have mixed case columns and are using 0.6.x. See above for more details.

  • Query Retries

    Druid will now automatically retry queries for certain classes of failures.

  • Background caching

    For certain types of queries, especially those that involve distinct (hyperloglog) counts, this can improve performance up over 20%. Background caching is disabled by default.

  • Reduced coordinator memory usage

    Reduced coordinator memory usage (by up to 50%). This fixes a problem where a coordinator would sometimes lose leadership due to frequent GCs.

  • Metrics can now be emitted to SSL endpoints

  • Additional AWS credentials support, Thanks @gnethercutt

  • Additional persist and throttle metrics for real-time ingestion

    This should help diagnose when real-time ingestion is being throttled and how long persists are taking. These metrics provide a good indication of when it is time to scale up real-time ingestion.

  • Broker initialization endpoint

    Brokers now provides a status endpoint at /druid/broker/v1/loadstatus to indicate whether they are ready to be queried, making rolling upgrades / restarts easier.

Bug Fixes

  • Support multiple shards of the same datasource on the same realtime node. Thanks @zhaown
  • HDFS task logs should now work as expected. Thanks @flowbehappy.
  • Possible deadlock condition fixed in the Broker.
  • Various fixes for GZIP compression in returning results.
  • druid.host should now support IPv6 addresses as well.

Documentation

  • New tutorials.
  • New ingestion documentation.
  • New configuration documentation.
  • Improvements to rule documentation. Thanks @mrijke

Known issues

  • Merging segments with different types of bitmap indices is currently not possible, so if you have both types of indices in your cluster, you must set druid.coordinator.merge.on to false. ‘false’ is the default value of the config.
  • https://github.com/druid-io/druid/issues/1045 Issue with GoupBy queries with complex aggregations and post-aggregations using the same name
  • https://github.com/druid-io/druid-api/pull/38 If you are using longSum in your ingestion spec, having floating point data may throw exceptions.
