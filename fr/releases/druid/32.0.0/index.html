<a name="32.0.0-important-features" href="#32.0.0-important-features">#</a> Fonctionnalités importantes

Cette section contient des informations importantes sur les fonctionnalités nouvelles et existantes.

<a name="32.0.0-important-features-new-overlord-apis" href="#32.0.0-important-features-new-overlord-apis">#</a> Nouveaux Overlord API

Les API permettant de marquer les segments comme utilisés ou inutilisés ont été déplacés du service Coordinateur vers le service Overlord :

  • Marquer tous les segments d'une source de données comme inutilisés : POST /druid/indexer/v1/datasources/{dataSourceName}

  • Marquer tous les segments (non éclipsés) d'une source de données comme étant utilisés : DELETE /druid/indexer/v1/datasources/{dataSourceName}

  • Marquer plusieurs segments comme utilisés POST /druid/indexer/v1/datasources/{dataSourceName}/markUsed

  • Marquer plusieurs segments (non éclipsés) comme inutilisés POST /druid/indexer/v1/datasources/{dataSourceName}/markUnused

  • Marquer un seul segment comme utilisé : POST /druid/indexer/v1/datasources/{dataSourceName}/segments/{segmentId}

  • Marquer un seul segment comme inutilisé : DELETE /druid/indexer/v1/datasources/{dataSourceName}/segments/{segmentId}

Dans le cadre de ce changement, les coordinateurs API correspondants sont obsolètes et seront supprimés dans une prochaine version :

-POST /druid/coordinator/v1/datasources/{dataSourceName} -POST /druid/coordinator/v1/datasources/{dataSourceName}/markUsed -POST /druid/coordinator/v1/datasources/{dataSourceName}/markUnused -POST /druid/coordinator/v1/datasources/{dataSourceName}/segments/{segmentId} -DELETE /druid/coordinator/v1/datasources/{dataSourceName}/segments/{segmentId} -DELETE /druid/coordinator/v1/datasources/{dataSourceName}

Le coordinateur appelle maintenant l'Overlord pour répondre à ces demandes.

<a name="32.0.0-important-features-realtime-query-processing-for-multi-value-strings-" href="#32.0.0-important-features-realtime-query-processing-for-multi-value-strings-">#</a> Traitement des requêtes en temps réel pour les chaînes à valeurs multiples

Le traitement des requêtes en temps réel ne considère plus toutes les chaînes comme des chaînes à valeurs multiples lors du traitement des expressions, corrigeant ainsi un certain nombre de bugs et d'échecs inattendus. Cela devrait également améliorer les performances des requêtes en temps réel des expressions sur les colonnes de chaîne.

Ce changement affecte les requêtes topN pour les segments en temps réel où les lignes de données sont implicitement nulles, comme celles provenant d'une propriété manquante dans un objet JSON.

Avant ce changement, ceux-ci étaient traités comme [] au lieu de null, entraînant une incohérence entre le traitement des segments en temps réel et les segments publiés. Lors du traitement des segments, la valeur était traitée comme [], ce que topN ignore. Après la publication, la valeur est devenue nulle, ce que topN n'ignore pas. La même requête peut avoir des résultats différents avant et après sa persistance

Après ce changement, le moteur topN traite désormais [] comme null lors du traitement des segments en temps réel, ce qui est cohérent avec les segments publiés.

Cette modification n’a pas d’impact sur les colonnes de chaînes à valeurs multiples réelles, qu’elles soient ou non en temps réel.

#17386

<a name="32.0.0-important-features-join-hints-in-msq-task-engine-queries" href="#32.0.0-important-features-join-hints-in-msq-task-engine-queries">#</a> Rejoignez les astuces dans les requêtes du moteur de tâches MSQ

Druid prend désormais en charge les astuces pour les requêtes SQL JOIN qui utilisent le moteur de tâches MSQ. Cela permet aux requêtes de fournir des indications sur le type JOIN qui doit être utilisé à chaque niveau de jointure. Les indices de jointure affectent de manière récursive les sous-requêtes.

<a name="32.0.0-changes-and-deprecations" href="#32.0.0-changes-and-deprecations">#</a> Modifications et dépréciations

<a name="32.0.0-changes-and-deprecations-ansi-sql-compatibility-and-query-results" href="#32.0.0-changes-and-deprecations-ansi-sql-compatibility-and-query-results">#</a> Compatibilité ANSI-SQL et résultats des requêtes

La prise en charge des configurations qui vous permettaient de conserver un comportement plus ancien qui n'était pas conforme à ANSI-SQL a été supprimée :

-druid.generic.useDefaultValueForNull=true -druid.expressions.useStrictBooleans=false -druid.generic.useThreeValueLogicForNativeFilters=false

Ils n'affectent plus les résultats de votre requête. Seul le comportement non hérité conforme à SQL est désormais pris en charge.

Si les configurations sont définies sur le comportement hérité, les services Druid ne pourront pas démarrer.

Si vous souhaitez continuer à obtenir les mêmes résultats sans ces paramètres, vous devez mettre à jour vos requêtes, sinon vos résultats seront incorrects après la mise à niveau.

Pour plus d'informations sur la façon de mettre à jour vos requêtes, consultez le guide de migration.

<a name="32.0.0-changes-and-deprecations-join-hints-in-msq-task-engine-queries" href="#32.0.0-changes-and-deprecations-join-hints-in-msq-task-engine-queries">#</a> Rejoignez les astuces dans les requêtes du moteur de tâches MSQ

Druid prend désormais en charge les astuces pour les requêtes SQL JOIN qui utilisent le moteur de tâches MSQ. Cela permet aux requêtes de fournir des indications sur le type JOIN qui doit être utilisé à chaque niveau de jointure. Les indices de jointure affectent de manière récursive les sous-requêtes.

select /*+ sort_merge */ w1.cityName, w2.countryName
from
(
  select /*+ broadcast */ w3.cityName AS cityName, w4.countryName AS countryName from wikipedia w3 LEFT JOIN wikipedia-set2 w4 ON w3.regionName = w4.regionName
) w1
JOIN wikipedia-set1 w2 ON w1.cityName = w2.cityName
where w1.cityName='New York';

<a name="32.0.0-functional-area-and-related-changes-ingestion" href="#32.0.0-functional-area-and-related-changes-ingestion">#</a> Ingestion

<a name="32.0.0-functional-area-and-related-changes-ingestion-numbers-for-csv-and-tsv-input-formats" href="#32.0.0-functional-area-and-related-changes-ingestion-numbers-for-csv-and-tsv-input-formats">#</a> Numéros pour les formats d'entrée CSV et TSV

Utilisez la nouvelle configuration facultative tryParseNumbers pour les formats d'entrée CSV et TSV afin de contrôler la façon dont les nombres sont traités. S'il est activé, tous les nombres présents dans l'entrée seront analysés de la manière suivante :

  • type de données long pour les types entiers et
  • double pour les nombres à virgule flottante

Par défaut, cette configuration est définie sur false, donc les chaînes numériques seront traitées comme des chaînes.

<a name="32.0.0-functional-area-and-related-changes-ingestion-streaming-ingestion" href="#32.0.0-functional-area-and-related-changes-ingestion-streaming-ingestion">#</a> Ingestion de flux

<a name="32.0.0-functional-area-and-related-changes-ingestion-streaming-ingestion-control-how-many-segments-get-merged-for-publishing" href="#32.0.0-functional-area-and-related-changes-ingestion-streaming-ingestion-control-how-many-segments-get-merged-for-publishing">#</a> Contrôler le nombre de segments fusionnés pour la publication

Vous pouvez désormais utiliser la propriété maxColumnsToMerge dans votre spécification de superviseur pour spécifier le nombre de segments à fusionner en une seule phase lors de la fusion de segments pour la publication. Cette limite affecte le nombre total de colonnes présentes dans un ensemble de segments à fusionner. Si la limite est dépassée, la fusion des segments se produit en plusieurs phases. Druid fusionne au moins 2 segments à chaque phase, quel que soit ce paramètre.

La propriété d'exécution Overlord druid.indexer.tasklock.batchAllocationReduceMetadataIO peut aider à réduire les E/S lors de l'allocation de segments par lots. <a name="32.0.0-important-features" href="#32.0.0-important-features">#</a> Important features

This section contains important information about new and existing features.

<a name="32.0.0-important-features-new-overlord-apis" href="#32.0.0-important-features-new-overlord-apis">#</a> New Overlord APIs

APIs for marking segments as used or unused have been moved from the Coordinator to the Overlord service:

  • Mark all segments of a datasource as unused: POST /druid/indexer/v1/datasources/{dataSourceName}

  • Mark all (non-overshadowed) segments of a datasource as used: DELETE /druid/indexer/v1/datasources/{dataSourceName}

  • Mark multiple segments as used POST /druid/indexer/v1/datasources/{dataSourceName}/markUsed

  • Mark multiple (non-overshadowed) segments as unused POST /druid/indexer/v1/datasources/{dataSourceName}/markUnused

  • Mark a single segment as used: POST /druid/indexer/v1/datasources/{dataSourceName}/segments/{segmentId}

  • Mark a single segment as unused: DELETE /druid/indexer/v1/datasources/{dataSourceName}/segments/{segmentId}

As part of this change, the corresponding Coordinator APIs have been deprecated and will be removed in a future release:

  • POST /druid/coordinator/v1/datasources/{dataSourceName}
  • POST /druid/coordinator/v1/datasources/{dataSourceName}/markUsed
  • POST /druid/coordinator/v1/datasources/{dataSourceName}/markUnused
  • POST /druid/coordinator/v1/datasources/{dataSourceName}/segments/{segmentId}
  • DELETE /druid/coordinator/v1/datasources/{dataSourceName}/segments/{segmentId}
  • DELETE /druid/coordinator/v1/datasources/{dataSourceName}

The Coordinator now calls the Overlord to serve these requests.

#17545

<a name="32.0.0-important-features-realtime-query-processing-for-multi-value-strings-" href="#32.0.0-important-features-realtime-query-processing-for-multi-value-strings-">#</a> Realtime query processing for multi-value strings

Realtime query processing no longer considers all strings as multi-value strings during expression processing, fixing a number of bugs and unexpected failures. This should also improve realtime query performance of expressions on string columns.

This change impacts topN queries for realtime segments where rows of data are implicitly null, such as from a property missing from a JSON object.

Before this change, these were handled as [] instead of null, leading to inconsistency between processing realtime segments and published segments. When processing segments, the value was treated as [], which topN ignores. After publishing, the value became null, which topN does not ignore. The same query could have different results before and after being persisted

After this change, the topN engine now treats [] as null when processing realtime segments, which is consistent with published segments.

This change doesn't impact actual multi-value string columns, regardless of if they're realtime.

#17386

<a name="32.0.0-important-features-join-hints-in-msq-task-engine-queries" href="#32.0.0-important-features-join-hints-in-msq-task-engine-queries">#</a> Join hints in MSQ task engine queries

Druid now supports hints for SQL JOIN queries that use the MSQ task engine. This allows queries to provide hints for the JOIN type that should be used at a per join level. Join hints recursively affect sub queries.

#17541

<a name="32.0.0-changes-and-deprecations" href="#32.0.0-changes-and-deprecations">#</a> Changes and deprecations

<a name="32.0.0-changes-and-deprecations-ansi-sql-compatibility-and-query-results" href="#32.0.0-changes-and-deprecations-ansi-sql-compatibility-and-query-results">#</a> ANSI-SQL compatibility and query results

Support for the configs that let you maintain older behavior that wasn't ANSI-SQL compliant have been removed:

  • druid.generic.useDefaultValueForNull=true
  • druid.expressions.useStrictBooleans=false
  • druid.generic.useThreeValueLogicForNativeFilters=false

They no longer affect your query results. Only SQL-compliant non-legacy behavior is supported now.

If the configs are set to the legacy behavior, Druid services will fail to start.

If you want to continue to get the same results without these settings, you must update your queries or your results will be incorrect after you upgrade.

For more information about how to update your queries, see the migration guide.

#17568 #17609

<a name="32.0.0-changes-and-deprecations-java-support" href="#32.0.0-changes-and-deprecations-java-support">#</a> Java support

Java support in Druid has been updated:

  • Java 8 support has been removed
  • Java 11 support is deprecated

We recommend that you upgrade to Java 17.

#17466

<a name="32.0.0-changes-and-deprecations-hadoop-based-ingestion" href="#32.0.0-changes-and-deprecations-hadoop-based-ingestion">#</a> Hadoop-based ingestion

Hadoop-based ingestion is now deprecated. We recommend that you migrate to SQL-based ingestion.

<a name="32.0.0-changes-and-deprecations-join-hints-in-msq-task-engine-queries" href="#32.0.0-changes-and-deprecations-join-hints-in-msq-task-engine-queries">#</a> Join hints in MSQ task engine queries

Druid now supports hints for SQL JOIN queries that use the MSQ task engine. This allows queries to provide hints for the JOIN type that should be used at a per join level. Join hints recursively affect sub queries.

select /*+ sort_merge */ w1.cityName, w2.countryName
from
(
  select /*+ broadcast */ w3.cityName AS cityName, w4.countryName AS countryName from wikipedia w3 LEFT JOIN wikipedia-set2 w4 ON w3.regionName = w4.regionName
) w1
JOIN wikipedia-set1 w2 ON w1.cityName = w2.cityName
where w1.cityName='New York';

<a name="32.0.0-functional-area-and-related-changes-ingestion" href="#32.0.0-functional-area-and-related-changes-ingestion">#</a> Ingestion

<a name="32.0.0-functional-area-and-related-changes-ingestion-numbers-for-csv-and-tsv-input-formats" href="#32.0.0-functional-area-and-related-changes-ingestion-numbers-for-csv-and-tsv-input-formats">#</a> Numbers for CSV and TSV input formats

Use the new optional config tryParseNumbers for CSV and TSV input formats to control how numbers are treated. If enabled, any numbers present in the input will be parsed in the following manner:

  • long data type for integer types and
  • double for floating-point numbers

By default, this configuration is set to false, so numeric strings will be treated as strings.

<a name="32.0.0-functional-area-and-related-changes-ingestion-streaming-ingestion" href="#32.0.0-functional-area-and-related-changes-ingestion-streaming-ingestion">#</a> Streaming ingestion

<a name="32.0.0-functional-area-and-related-changes-ingestion-streaming-ingestion-control-how-many-segments-get-merged-for-publishing" href="#32.0.0-functional-area-and-related-changes-ingestion-streaming-ingestion-control-how-many-segments-get-merged-for-publishing">#</a> Control how many segments get merged for publishing

You can now use the maxColumnsToMerge property in your supervisor spec to specify the number of segments to merge in a single phase when merging segments for publishing. This limit affects the total number of columns present in a set of segments to merge. If the limit is exceeded, segment merging occurs in multiple phases. Druid merges at least 2 segments each phase, regardless of this setting.

#17030

<a name="32.0.0-functional-area-and-related-changes-ingestion-streaming-ingestion-other-streaming-ingestion-improvements" href="#32.0.0-functional-area-and-related-changes-ingestion-streaming-ingestion-other-streaming-ingestion-improvements">#</a> Other streaming ingestion improvements
  • Druid now fully supports early/late rejection periods when stopTasksCount is configured and streaming tasks run longer than the configured task duration #17442
  • Improved segment publishing when resubmitting supervisors or when task publishing takes a long time #17509

The following fields are deprecated for window queries that use the MSQ task engine: maxRowsMaterializedInWindow and partitionColumnNames. They will be removed in a future release.

#17433

<a name="32.0.0-functional-area-and-related-changes-querying-other-querying-improvements" href="#32.0.0-functional-area-and-related-changes-querying-other-querying-improvements">#</a> Other querying improvements

  • Added automatic query prioritization based on the period of the segments scanned in a query. You can set the duration threshold in ISO format using druid.query.scheduler.prioritization.segmentRangeThreshold #17009
  • Improved error handling for incomplete queries. A trailer header to indicate an error is returned now #16672
  • Improved scan queries to account for column types in more situations #17463
  • Improved lookups so that they can now iterate over fetched data #17212
  • Improved projections so that they can contain only aggregators and no grouping columns #17484
  • Removed microseconds as a supported unit for EXTRACT #17247

<a name="32.0.0-functional-area-and-related-changes-cluster-management" href="#32.0.0-functional-area-and-related-changes-cluster-management">#</a> Cluster management

<a name="32.0.0-functional-area-and-related-changes-cluster-management-reduce-metadata-io" href="#32.0.0-functional-area-and-related-changes-cluster-management-reduce-metadata-io">#</a> Reduce metadata IO

The Overlord runtime property druid.indexer.tasklock.batchAllocationReduceMetadataIO can help reduce IO during batch segment allocation. Setting this flag to true (default value) allows the Overlord to fetch only necessary segment payloads during segment allocation.

#17496

<a name="32.0.0-functional-area-and-related-changes-cluster-management-other-cluster-management-improvements" href="#32.0.0-functional-area-and-related-changes-cluster-management-other-cluster-management-improvements">#</a> Other cluster management improvements

  • Druid can now run non-G1 Garbage Collectors with JAVA_OPTS #17078
  • You no longer have to configure a temporary storage directory on the Middle Manager for durable storage or exports. If it isn't configured, Druid uses the task directory #17015 #17335
  • Improved autoscaling on supervisors so that tasks don't get published needlessly #17335
  • Improved recovery time for Overlord leadership after ZooKeeper are bounced #17535
  • Improved Druid to be more resilient of Druid service leadership changes due to ZooKeeper outages #17546
  • Removed the following unused Coordinator dynamic configs: mergeBytesLimit and mergeSegmentsLimit #17384

<a name="32.0.0-functional-area-and-related-changes-data-management" href="#32.0.0-functional-area-and-related-changes-data-management">#</a> Data management

<a name="32.0.0-functional-area-and-related-changes-data-management-sorting-columns-for-compaction-with-the-msq-task-engine-%28experimental%29" href="#32.0.0-functional-area-and-related-changes-data-management-sorting-columns-for-compaction-with-the-msq-task-engine-%28experimental%29">#</a> Sorting columns for compaction with the MSQ task engine (experimental)

Compaction that uses the MSQ task engine now supports sorting segments with non-time columns. If forceSegmentSortByTime is set in the compaction config or the inferred schema, the following happens:

  • Skip adding __time explicitly as the first column to the dimension schema since it already comes as part of the schema
  • Ensure column mappings propagate __time in the order specified by the schema
  • Set forceSegmentSortByTime in the MSQ query context.

  • Changed compaction tasks to always handle multi-value dimensions as arrays if the column schema is not explicitly specified #17110
