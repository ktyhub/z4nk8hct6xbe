Faits saillants

Nous sommes ravis d'annoncer la sortie de PyTorch® 2.5 ! Cette version comprend un nouveau backend CuDNN pour SDPA, permettant des accélérations par défaut pour les utilisateurs de SDPA sur les H100 ou les GPU plus récents. De plus, la compilation régionale de torch.compile offre un moyen de réduire le temps de démarrage à froid de torch.compile en permettant aux utilisateurs de compiler un nn.Module répété (par exemple une couche de transformateur dans LLM) sans recompilation. Enfin, le backend TorchInductor CPP offre une solide accélération des performances avec de nombreuses améliorations telles que la prise en charge FP16, le wrapper CPP, le mode AOT-Inductor et le mode de réglage automatique maximum. Cette version est composée de 4095 commits de 504 contributeurs depuis PyTorch 2.4. Nous souhaitons sincèrement remercier notre communauté dévouée pour vos contributions. Comme toujours, nous vous encourageons à les essayer et à signaler tout problème à mesure que nous améliorons le 2.5. Plus d'informations sur la façon de démarrer avec la série PyTorch 2 sont disponibles sur notre page [Mise en route] (https://pytorch.org/get-started/pytorch-2.0/). FONCTIONNALITÉS BÊTA

[Bêta] Backend CuDNN pour SDPA

Le backend cuDNN « Fused Flash Attention » a été lancé pour torch.nn.functional.scaled_dot_product_attention. Sur les GPU NVIDIA H100, cela peut fournir jusqu'à 75 % d'accélération par rapport à FlashAttentionV2. Cette accélération est activée par défaut pour tous les utilisateurs de SDPA sur des GPU H100 ou plus récents.

[Beta] torch.compile compilation régionale sans recompilations

Compilation régionale sans recompilations, via torch._dynamo.config.inline_inbuilt_nn_modules qui vaut par défaut True dans 2.5+. Cette option permet aux utilisateurs de compiler un nn.Module répété (par exemple une couche de transformateur dans LLM) sans recompilation. Par rapport à la compilation du modèle complet, cette option peut entraîner des latences de compilation plus faibles avec une dégradation des performances de 1 à 5 % par rapport à la compilation du modèle complet. Consultez le tutoriel pour plus d'informations.

[Bêta] Optimisation du backend du processeur TorchInductor

Cette fonctionnalité fait progresser l'optimisation du backend du processeur d'Inductor, y compris la génération de code backend CPP et les fusions FX avec des noyaux de processeur personnalisés. Le backend du processeur Inductor prend en charge la vectorisation des types de données courants et de toutes les opérations Inductor IR, ainsi que les formes statiques et symboliques. Il est compatible avec les systèmes d'exploitation Linux et Windows et prend en charge le wrapper par défaut Python, le wrapper CPP et le mode AOT-Inductor. De plus, il étend le mode de réglage automatique maximum du modèle GEMM (prototypé dans 2.5), offrant des gains de performances supplémentaires. Le backend prend en charge diverses fusions FX, allant jusqu'à des noyaux personnalisés tels que oneDNN pour les opérations linéaires/Conv et SDPA. Le backend du processeur Inductor atteint systématiquement des accélérations de performances sur trois suites de référence (TorchBench, Hugging Face et timms), surpassant le mode impatient dans 97.5 % des 193 modèles testés.

CARACTÉRISTIQUES DU PROTOTYPE

[Prototype] FlexAttention

Nous avons introduit un API flexible qui permet d'implémenter divers mécanismes d'attention tels que la fenêtre coulissante, le masque causal et le préfixLM avec seulement quelques lignes de code PyTorch idiomatique. Ce API exploite torch.compile pour générer un noyau FlashAttention fusionné, qui élimine l'allocation de mémoire supplémentaire et atteint des performances comparables aux implémentations manuscrites. De plus, nous générons automatiquement la passe arrière à l'aide de la machinerie Autograd de PyTorch. De plus, notre API peut tirer parti de la rareté du masque d'attention, ce qui entraîne des améliorations significatives par rapport aux implémentations d'attention standard. Pour plus d'informations et d'exemples, veuillez vous référer au article de blog officiel et au Attention Gym.

[Prototype] Autograd compilé

Compiled Autograd est une extension de la pile PT2 permettant la capture de l'intégralité de la passe arrière. Contrairement au graphique vers l'arrière tracé par le répartiteur AOT, le traçage Compiled Autograd est différé jusqu'au moment de l'exécution vers l'arrière, ce qui le rend insensible aux ruptures de graphique de passage vers l'avant et lui permet d'enregistrer des crochets vers l'arrière dans le graphique. Veuillez vous référer au tutoriel pour plus d'informations.

[Prototype] Enregistreur de vol

Flight Recorder est un nouvel outil de débogage qui aide à déboguer les tâches bloquées. L'outil fonctionne en capturant en permanence des informations sur les collectifs au fur et à mesure de leur exécution. Lors de la détection d'une tâche bloquée, les informations peuvent être utilisées pour identifier rapidement les rangs/machines qui se comportent mal ainsi que les traces de la pile de codes. Pour plus d'informations, veuillez vous référer au [tutoriel] suivant (https://pytorch.org/tutorials/prototype/flight_recorder_tutorial.html).

[Prototype] Prise en charge du réglage automatique maximum sur le processeur avec le modèle GEMM

Le mode Max-autotune pour le backend du processeur Inductor dans torch.compile profile plusieurs implémentations d'opérations au moment de la compilation et sélectionne la plus performante. Ceci est particulièrement bénéfique pour les opérations liées à GEMM, en utilisant une implémentation GEMM basée sur un modèle C++ comme alternative à l'approche basée sur ATen avec les bibliothèques oneDNN et MKL. Nous prenons en charge les FP32, BF16, FP16 et INT8 avec des fusions épilogues pour les processeurs x86. Nous avons constaté une accélération géomécanique allant jusqu'à 7 % sur les suites de référence Dynamo et une augmentation jusqu'à 20 % de la latence du prochain jeton pour l'inférence LLM. Pour plus d'informations, veuillez vous référer au [tutoriel] (https://pytorch.org/tutorials/prototype/max_autotune_on_CPU_tutorial.html).

[Prototype] Processeur TorchInductor sous Windows

Le backend du processeur Inductor dans torch.compile fonctionne désormais sous Windows. Nous prenons actuellement en charge MSVC (cl), clang (clang-cl) et le compilateur Intel (icx-cl) pour l'inducteur Windows. Voir le tutoriel pour plus de détails.

[Prototype] Prise en charge du FP16 sur le chemin du processeur pour le mode impatient et le backend TorchInductor CPP

Float16 est un type à virgule flottante réduite couramment utilisé pour améliorer les performances dans l'inférence/la formation des réseaux neuronaux. Depuis cette version, float16 pour impatient et TorchInductor est pris en charge sur le chemin CPU.

[Prototype] Extension de périphérique à chargement automatique

PyTorch prend désormais en charge le chargement automatique des extensions de périphériques hors arborescence, rationalisant ainsi l'intégration en éliminant le besoin d'importations manuelles. Cette fonctionnalité, activée via le point d'entrée torch.backends, simplifie l'utilisation en garantissant un chargement transparent de l'extension, tout en permettant aux utilisateurs de la désactiver via une variable d'environnement si nécessaire. Consultez le tutoriel pour plus d’informations.

[Prototype] Prise en charge améliorée des GPU Intel

L'amélioration de la prise en charge des GPU Intel est désormais disponible pour les GPU Intel® Data Center GPU Max Series et Intel® Client (processeurs Intel® Core™ Ultra avec graphiques Intel® Arc™ intégrés et graphiques Intel® Arc™ pour les composants dGPU), ce qui vise à faciliter l'accélération de vos flux de travail d'apprentissage automatique sur les GPU Intel dans la version PyTorch 2.5. Nous avons également activé la prise en charge initiale de PyTorch sur Windows pour les GPU Intel® Client dans cette version.

  • Matrice de prise en charge matérielle du backend PyTorch étendue pour inclure les GPU Intel Data Center et Client.  
  • L'implémentation des noyaux SYCL* pour améliorer la couverture et l'exécution des opérateurs Aten sur les GPU Intel afin d'améliorer les performances en mode impatient de PyTorch.
  • Amélioration du backend GPU Intel de torch.compile pour améliorer les performances d'inférence et de formation pour un large éventail de charges de travail d'apprentissage en profondeur.
    Ces fonctionnalités sont disponibles via l'aperçu PyTorch et les roues PIP binaires nocturnes. Pour plus d'informations sur la prise en charge des GPU Intel, veuillez vous référer à la documentation.

Le torch.onnx._export est un API interne qui n'est pas destiné à la consommation publique. Utilisez plutôt le public torch.onnx.export. Exemple :

L'option dynamo=True et nouvelle logique d'export (#132530, #133743, #134304, #134782, #135378, #135399, #135786, #136162, #135134, #134976, #135367, #135418, #135591, #135520)

Nous introduisons l'option dynamo=True dans torch.onnx.export(). Ceci est recommandé en remplacement de torch.onnx.dynamo_export à partir de PyTorch 2.5. Version2.5 :

onnx_program = torch.onnx.export(model, inputs, kwargs=kwargs, dynamo=True)  
# Use the external_data option to save weights as external data  
onnx_program.save(“model.onnx”, external_data=True)  
# To save without initializers  
onnx_program.save(“model.onnx”, include_initializers=False, keep_initializers_as_inputs=True)

torch.onnx.export(model, args, dynamo=True, report=True, verify=True) exploite torch.export et ONNX IR pour convertir les ExportedProgram capturés en ONNX de manière efficace et robuste. Ce nouveau processus réduit de moitié la consommation de mémoire par rapport au dynamo_export dans le 2.4, tout en préservant la forme riche du tenseur et les informations de trace de pile dans le graphique ONNX. Vous pouvez tirer parti de l'option report=True pour obtenir un rapport de conversion au format markdown afin de diagnostiquer tout problème de conversion. Définissez verify=True pour vérifier numériquement le modèle ONNX avec ONNX Runtime. Lorsque vous utilisez external_data=True pour enregistrer les poids du modèle en tant que données externes dans le fichier .onnx, les poids supérieurs à 1 Mo sont désormais alignés sur des adresses de 64 Ko. Cela permet aux environnements d'exécution de mapper les poids en mémoire pour une meilleure efficacité de la mémoire lors de l'inférence.

[REMARQUE]
L'option dynamo=True ne prend actuellement en charge que l'opset ONNX 18. Les prochaines versions étendront la prise en charge aux opsets plus récents. [REMARQUE]
L'option dynamo=True nécessite les dernières versions des packages onnxscript et onnx.

Highlights

We are excited to announce the release of PyTorch® 2.5! This release features a new CuDNN backend for SDPA, enabling speedups by default for users of SDPA on H100s or newer GPUs. As well, regional compilation of torch.compile offers a way to reduce the cold start up time for torch.compile by allowing users to compile a repeated nn.Module (e.g. a transformer layer in LLM) without recompilations. Finally, TorchInductor CPP backend offers solid performance speedup with numerous enhancements like FP16 support, CPP wrapper, AOT-Inductor mode, and max-autotune mode. This release is composed of 4095 commits from 504 contributors since PyTorch 2.4. We want to sincerely thank our dedicated community for your contributions. As always, we encourage you to try these out and report any issues as we improve 2.5. More information about how to get started with the PyTorch 2-series can be found at our Getting Started page. As well, please check out our new ecosystem projects releases with TorchRec and TorchFix.

BETA FEATURES

[Beta] CuDNN backend for SDPA

The cuDNN "Fused Flash Attention" backend was landed for torch.nn.functional.scaled_dot_product_attention. On NVIDIA H100 GPUs this can provide up to 75% speed-up over FlashAttentionV2. This speedup is enabled by default for all users of SDPA on H100 or newer GPUs.

[Beta] torch.compile regional compilation without recompilations

Regional compilation without recompilations, via torch._dynamo.config.inline_inbuilt_nn_modules which default to True in 2.5+. This option allows users to compile a repeated nn.Module (e.g. a transformer layer in LLM) without recompilations. Compared to compiling the full model, this option can result in smaller compilation latencies with 1%-5% performance degradation compared to full model compilation.

See the tutorial for more information.

[Beta] TorchInductor CPU backend optimization

This feature advances Inductor’s CPU backend optimization, including CPP backend code generation and FX fusions with customized CPU kernels. The Inductor CPU backend supports vectorization of common data types and all Inductor IR operations, along with the static and symbolic shapes. It is compatible with both Linux and Windows OS and supports the default Python wrapper, the CPP wrapper, and AOT-Inductor mode.

Additionally, it extends the max-autotune mode of the GEMM template (prototyped in 2.5), offering further performance gains. The backend supports various FX fusions, lowering to customized kernels such as oneDNN for Linear/Conv operations and SDPA. The Inductor CPU backend consistently achieves performance speedups across three benchmark suites—TorchBench, Hugging Face, and timms—outperforming eager mode in 97.5% of the 193 models tested.

PROTOTYPE FEATURES

[Prototype] FlexAttention

We've introduced a flexible API that enables implementing various attention mechanisms such as Sliding Window, Causal Mask, and PrefixLM with just a few lines of idiomatic PyTorch code. This API leverages torch.compile to generate a fused FlashAttention kernel, which eliminates extra memory allocation and achieves performance comparable to handwritten implementations. Additionally, we automatically generate the backwards pass using PyTorch's autograd machinery. Furthermore, our API can take advantage of sparsity in the attention mask, resulting in significant improvements over standard attention implementations.

For more information and examples, please refer to the official blog post and Attention Gym.

[Prototype] Compiled Autograd

Compiled Autograd is an extension to the PT2 stack allowing the capture of the entire backward pass. Unlike the backward graph traced by AOT dispatcher, Compiled Autograd tracing is deferred until backward execution time, which makes it impervious to forward pass graph breaks, and allows it to record backward hooks into the graph.

Please refer to the tutorial for more information.

[Prototype] Flight Recorder

Flight recorder is a new debugging tool that helps debug stuck jobs. The tool works by continuously capturing information about collectives as they run. Upon detecting a stuck job, the information can be used to quickly identify misbehaving ranks/machines along with code stack traces.

For more information please refer to the following tutorial.

[Prototype] Max-autotune Support on CPU with GEMM Template

Max-autotune mode for the Inductor CPU backend in torch.compile profiles multiple implementations of operations at compile time and selects the best-performing one. This is particularly beneficial for GEMM-related operations, using a C++ template-based GEMM implementation as an alternative to the ATen-based approach with oneDNN and MKL libraries. We support FP32, BF16, FP16, and INT8 with epilogue fusions for x86 CPUs. We’ve seen up to 7% geomean speedup on the dynamo benchmark suites and up to 20% boost in next-token latency for LLM inference.

For more information please refer to the tutorial.

[Prototype] TorchInductor CPU on Windows

Inductor CPU backend in torch.compile now works on Windows. We support MSVC (cl), clang (clang-cl) and Intel compiler (icx-cl) for Windows inductor currently.

See the tutorial for more details.

[Prototype] FP16 support on CPU path for both eager mode and TorchInductor CPP backend

Float16 is a commonly used reduced floating point type for performance improvement in neural network inference/training. Since this release, float16 for both eager and TorchInductor is supported on the CPU path.

[Prototype] Autoload Device Extension

PyTorch now supports autoloading for out-of-tree device extensions, streamlining integration by eliminating the need for manual imports. This feature, enabled through the torch.backends entrypoint, simplifies usage by ensuring seamless extension loading, while allowing users to disable it via an environment variable if needed.

See the tutorial for more information.

[Prototype] Enhanced Intel GPU support

Intel GPUs support enhancement is now available for both Intel® Data Center GPU Max Series and Intel® Client GPUs (Intel® Core™ Ultra processors with built-in Intel® Arc™ graphics and Intel® Arc™ Graphics for dGPU parts), which is to make it easier to accelerate your Machine Learning workflows on Intel GPUs in PyTorch 2.5 release. We also enabled the initial support of PyTorch on Windows for Intel® Client GPUs in this release.

  • Expanded PyTorch hardware backend support matrix to include both Intel Data Center and Client GPUs.  
  • The implementation of SYCL* kernels to enhance coverage and execution of Aten operators on Intel GPUs to boost performance in PyTorch eager mode.
  • Enhanced Intel GPU backend of torch.compile to improve inference and training performance for a wide range of deep learning workloads.

These features are available through PyTorch preview and nightly binary PIP wheels. For more information regarding Intel GPU support, please refer to documentation.

pg: ProcessGroup = ProcessGroup(store, rank, group_size)

ONNX

The dynamo=True option and new export logic (#132530, #133743, #134304, #134782, #135378, #135399, #135786, #136162, #135134, #134976, #135367, #135418, #135591, #135520)

We introduce the dynamo=True option in torch.onnx.export(). This is recommended as a replacement for torch.onnx.dynamo_export starting in PyTorch 2.5.

Version 2.5:

onnx_program = torch.onnx.export(model, inputs, kwargs=kwargs, dynamo=True)  
# Use the external_data option to save weights as external data  
onnx_program.save(“model.onnx”, external_data=True)  
# To save without initializers  
onnx_program.save(“model.onnx”, include_initializers=False, keep_initializers_as_inputs=True)

torch.onnx.export(model, args, dynamo=True, report=True, verify=True) leverages torch.export and ONNX IR to convert captured ExportedPrograms to ONNX efficiently and robustly. This new process reduces memory consumption by half compared to dynamo_export in 2.4, while preserving rich tensor shape and stack trace information in the ONNX graph. You can leverage the report=True option to obtain a conversion report in markdown format to diagnose any conversion issues. Set verify=True to verify the ONNX model numerically with ONNX Runtime.

When using external_data=True to save model weights as external data to the .onnx file, weights larger than 1 MB are now aligned at 64 KB addresses. This allows runtimes to memory-map weights for better memory efficiency during inference.

[NOTE]
The dynamo=True option currently supports only ONNX opset 18. Future releases will expand support to newer opsets.

[NOTE]
The dynamo=True option requires the latest versions of onnxscript and onnx packages.
