Nous avons également 3.14 et 3.14t disponibles en avant-première avec cette version. ## Comportement non défini lorsqu'une sortie d'un opérateur personnalisé partage le stockage avec une entrée Ceci est un rappel que les sorties des opérateurs personnalisés PyTorch (qui sont enregistrés à l'aide des tenseurs `torch.library` ou `TORCH_LIBRARY` API) ne sont pas autorisées à renvoyer des tensors qui partagent le stockage avec des tenseurs d'entrée. La violation de cette condition conduit à un comportement indéfini : parfois le résultat sera correct, parfois ce sera de la foutaise. Après [#163227](https://github.com/pytorch/pytorch/pull/163227), les opérateurs personnalisés qui ont violé cette condition qui renvoyait auparavant des résultats corrects sous `torch.compile` peuvent désormais renvoyer des résultats silencieusement incorrects sous `torch.compile`. Étant donné que cela modifie le comportement d'un comportement non défini, nous ne considérons pas cela comme un bug, mais nous le documentons toujours dans cette section comme un « changement de comportement potentiellement inattendu ». Il s'agit de l'une des conditions vérifiées par [`torch.library.opcheck`](https://docs.pytorch.org/docs/stable/library.html#testing-custom-ops) et est mentionnée dans le [Manuel de l'opérateur personnalisé](https://docs.google.com/document/d/1_W62p8WJOQQUzPsJYa7s701JXt0qf2OfLub2sbkHOaU/edit?tab=t.0#bookmark=id.4c0um7xkba6e) ### Plus de détails Les sorties des opérateurs personnalisés PyTorch ne sont pas autorisées à renvoyer des tenseurs qui partagent le stockage avec les tenseurs d'entrée. Par exemple, les deux opérateurs personnalisés suivants ne sont pas des opérateurs personnalisés valides : ```py @torch.library.custom_op("mylib::foo", mutates_args=()) def foo(x: torch.Tensor) -> torch.Tensor: # the result of `foo` must not directly be an input to foo. return x

@torch.library.custom_op("mylib::bar", mutates_args=()) def bar(x: torch.Tensor) -> torch.Tensor: # the result of bar must not be a view of an input of bar return x.view(-1)

La solution de contournement la plus simple consiste à ajouter un `.clone()` supplémentaire aux sorties :
```py
@torch.library.custom_op("mylib::foo", mutates_args=())
def foo(x: torch.Tensor) -> torch.Tensor:
    return x.clone()

@torch.library.custom_op("mylib::bar", mutates_args=())
def bar(x: torch.Tensor) -> torch.Tensor:
    return x.view(-1).clone()

Une manière courante de se retrouver dans cette situation est pour un utilisateur de vouloir créer un opérateur personnalisé qui mute parfois l'entrée sur place et renvoie parfois un nouveau Tensor, comme dans l'exemple suivant.

@torch.library.custom_op("mylib::baz", mutates_args=["x"])
def baz(x: torch.Tensor) -> torch.Tensor:
    if inplace:
        x.sin_()
        return x
    else:
        return x.sin()

Ce dynamisme n'est pas pris en charge et conduit à un comportement indéfini. La solution de contournement consiste à diviser l'opérateur personnalisé en deux opérateurs personnalisés, un qui mute toujours l'entrée sur place et un autre qui renvoie toujours un nouveau Tensor.

@torch.library.custom_op("mylib::baz_outplace", mutates_args=())
def baz_outplace(x: torch.Tensor) -> torch.Tensor:
    return x.sin()

@torch.library.custom_op("mylib::baz_inplace", mutates_args=["x"])
def baz_inplace(x: torch.Tensor) -> torch.Tensor:
    x.sin_()

def baz(x):
    if inplace:
        baz_inplace(x)
        return x
    else:
        return baz_outplace(x)

Créez des noyaux métalliques de MacOS-14+ et supprimez toute la logique spécifique pré-MacOS-14, nécessite MacOS-14+ à l'avenir (#159733, #159912)

PyTorch MPS n'est pris en charge que sur MacOS-14 ou version ultérieure. Si vous devez utiliser MPS sur MacOS Ventura, évitez de mettre à jour vers Python-3.9 ou une version ultérieure.

Mise à niveau vers DLPack 1.0 (#145000)

Cette mise à niveau apporte les mêmes modifications révolutionnaires que la version DLPack. Les objets dans torch.utils.dlpack ont été mis à jour pour refléter ces modifications, comme DLDeviceType. Consultez le PR pour plus de détails sur les modifications exactes et comment mettre à jour votre code.

Génère les erreurs appropriées dans torch.cat (#158249)

torch.cat génère désormais ValueError, IndexError ou TypeError le cas échéant au lieu du RuntimeError générique. Si votre code détectait ces erreurs, vous pouvez mettre à jour pour détecter le nouveau type d'erreur.

Par défaut, dynamo=True pour l'exportateur ONNX (#159646, #162726)

Auparavant, torch.onnx.export(...) utilisait l'ancien exportateur TorchScript si aucun argument n'était fourni. L'exportateur ONNX utilise désormais par défaut le nouveau pipeline torch.export.export (dynamo=True). Ce changement améliore la fidélité des graphiques et les exportations à l’épreuve du temps, mais peut faire apparaître des erreurs de capture de graphiques qui étaient auparavant masquées ou gérées différemment. Précédemment dans la torche 2.8.0 :

# API calls the legacy exporter with dynamo=False
torch.onnx.export(...)

Maintenant dans la torche 2.9.0 :

# To preserve the original behavior
torch.onnx.export(..., dynamo=False)

# Export onnx model through torch.export.export
torch.onnx.export(...)

Recommandation : essayez d'abord la nouvelle valeur par défaut ; ne reculez que si vous rencontrez des problèmes bloquants et signalez-les en amont. Solution à long terme : corrigez la cause première au lieu de compter sur une solution de secours ou sur un exportateur TorchScript.

Désactivez les assertions d'exécution par défaut dans Export au profit d'une fonction de protection de forme (#160111, #161178, #161794)

Pour activer les assertions d'exécution, utilisez export(..., prefer_deferred_runtime_asserts_over_guards=True). Tue également le drapeau allow_complex_guards_as_runtime_asserts, en le fusionnant avec l'ancienne option. De plus, exported_program.module() générera un appel à un sous-module _guards_fn qui exécutera des vérifications supplémentaires sur les entrées. Les utilisateurs qui ne souhaitent pas ce comportement peuvent soit supprimer cet appel dans le graphe, soit faire exported_program.module(check_guards=False) pour éviter la génération.

Définir l'opset par défaut sur 20 dans ONNX (#158802)

Opset 20 permet des définitions d'opérateurs plus récentes. Si votre outil ou votre runtime en aval prend uniquement en charge l'opset 18, épinglez-le explicitement. Pour les derniers opérateurs ONNX, vous pouvez expérimenter avec l'opset 23. Précédemment dans la torche 2.8.0 :

# opset_version=18
torch.onnx.export(...)

Maintenant dans la torche 2.9.0 :

# To preserve the original behavior
torch.onnx.export(..., opset_version=18)

# New: opset_version=20
torch.onnx.export(...)

# Use the latest supported opset: opset_version=23
torch.onnx.export(..., opset_version=23)

Déposez draft_export dans l'exportateur API (#161454, #162225)

Supprimez le traçage implicite des brouillons du chemin d'exportation par défaut, ce qui permet d'obtenir un comportement plus clair et des échecs plus rapides. Le coûteux chemin de diagnostic torch.export.draft_export n'est plus invoqué automatiquement (ce qui pourrait prendre des heures sur les grands modèles). Vous pouvez toujours opter pour des diagnostics approfondis : Précédemment dans la torche 2.8.0 :

# If both torch.export.export(..., strict=False) and
# torch.export.export(..., strict=True) fail to capture
# the model graph, torch.export.draft_export(...) will be triggered,
# and uses real tensor to trace/export the model.
#
# Inside export_to_onnx.py:
#  ... torch.onnx.export(..., dynamo=True)
python export_to_onnx.py

Maintenant dans la torche 2.9.0 :

# To trigger torch.export.draft_export once
# torch.export.export strict=False/True both
# fail:

TORCH_ONNX_ENABLE_DRAFT_EXPORT=True python export_to_onnx.py

Supprimez torch.onnx.dynamo_export et le backend de compilation de la torche onnxrt (#158130, #158258)

torch.onnx.dynamo_export est supprimé. Veuillez utiliser torch.onnx.export à la place. Le backend de compilation expérimental ONNX Runtime (torch.compile(backend="onnxrt")) n’est plus pris en charge.

Supprimer torch.onnx.enable_fake_mode (#161222)

Le mode dynamo=True utilise par défaut les FakeTensor, ce qui est économe en mémoire.

Certains API de l'utilitaire ONNX public pour l'exportateur basé sur TorchScript sont désormais privés (# 161323)

Les membres obsolètes dans torch.onnx.verification sont supprimés. Les fonctions auparavant privées du torch.onnx.symbolic_opsets* ne seront plus accessibles. Pensez à faire une copie du code source si vous avez besoin d'accéder à des fonctions privées pour des raisons de compatibilité avec l'exportateur basé sur TorchScript.

Supprimer torch.onnx.symbolic_caffe2 (#157102)

La prise en charge de caffe2 dans l'exportateur ONNX a pris fin et est supprimée.

Supprimez l'indicateur /d2implyavx512upperregs qui ralentit la construction (#159431)

Les optimisations AVX512 réintroduites pour les versions Windows VS2022 peuvent provoquer des problèmes avec des versions spécifiques de VS2022, voir #145702

Ajoutez ScalarType à la conversion de cale et stable::Tensor.scalar_type (#160557)

Auparavant, les extensions utilisateur ne pouvaient transmettre que de manière abstraite des types obscurcis apparaissant sous la forme int32_ts. Désormais, les utilisateurs peuvent utiliser en toute confiance torch::headeronly::ScalarType dans leurs extensions pour les principaux types scalaires. Ce PR permet la stabilité de l'ABI en ajoutant une couche de traduction via la cale, de sorte que même si les valeurs de l'énumération ScalarType changent à l'avenir, les extensions utilisateur n'ont pas à craindre. Ce changement ajoute la prise en charge de ScalarType pour les extensions utilisateur et n'est que de peu en rupture avec les types impopulaires : quint*, qint*, Bits*, dummy_uint*, dummy_int*, Float8_e8m0fnu et Float4_e2m1fn_x2 dans le cas d'utilisation où une extension récupère un type Tensor de ce qui précède et le transmet à aoti_torch_call_dispatcher.

Dépréciations

Déprécier le paramètre pin_memory_device dans torch.utils.data.DataLoader (#158323)

Nous déplaçons l'activation de pin_memory à l'intérieur de BaseDataLoaderIter. Ceci est requis pour StatefulDataloader qui exploite directement BaseDataLoaderIter plutôt que l'initialisation de la classe Dataloader.

Déprécier torch.export.export_for_training API au profit de l'équivalent torch.export.export API (#158203)

torch.export.export_for_training existe car nous n'avons pas pu migrer les utilisations internes de l'exportation vers l'IR final. Maintenant que nous avons terminé la migration, nous avons rendu obsolète et supprimé ce API.

Backwards Incompatible Changes

Min supported Python version is now 3.10 (#162310)

The minimum version of Python required for PyTorch 2.9.0 is 3.10. We also have 3.14 and 3.14t available as preview with this release.

Undefined behavior when an output of a custom operator shares storage with an input

This is a reminder that outputs of PyTorch custom operators (that are registered using the torch.library or TORCH_LIBRARY APIs) are not allowed to return Tensors that share storage with input tensors. The violation of this condition leads to undefined behavior: sometimes the result will be correct, sometimes it will be garbage.

After #163227, custom operators that violated this condition that previously returned correct results under torch.compile may now return silently incorrect results under torch.compile. Because this is changing the behavior of undefined behavior, we do not consider this to be a bug, but we are still documenting it in this section as a "potentially unexpected behavior change".

This is one of the conditions checked for by torch.library.opcheck and is mentioned in The Custom Operators Manual

More details

Outputs of PyTorch custom operators are not allowed to return Tensors that share storage with input tensors

For example, the following two custom operators are not valid custom operators:

@torch.library.custom_op("mylib::foo", mutates_args=())
def foo(x: torch.Tensor) -> torch.Tensor:
    # the result of `foo` must not directly be an input to foo.
    return x

@torch.library.custom_op("mylib::bar", mutates_args=())
def bar(x: torch.Tensor) -> torch.Tensor:
    # the result of bar must not be a view of an input of bar
    return x.view(-1)

The easiest workaround is to add an extra .clone() to the outputs:

@torch.library.custom_op("mylib::foo", mutates_args=())
def foo(x: torch.Tensor) -> torch.Tensor:
    return x.clone()

@torch.library.custom_op("mylib::bar", mutates_args=())
def bar(x: torch.Tensor) -> torch.Tensor:
    return x.view(-1).clone()

A common way to get into this situation is for a user to want to create a custom operator that sometimes mutates the input in-place and sometimes returns a new Tensor, like in the following example.

@torch.library.custom_op("mylib::baz", mutates_args=["x"])
def baz(x: torch.Tensor) -> torch.Tensor:
    if inplace:
        x.sin_()
        return x
    else:
        return x.sin()

This dynamism is not supported and leads to undefined behavior. The workaround is to split the custom operator into two custom operators, one that always mutates the input in-place, and another that always returns a new Tensor.

@torch.library.custom_op("mylib::baz_outplace", mutates_args=())
def baz_outplace(x: torch.Tensor) -> torch.Tensor:
    return x.sin()

@torch.library.custom_op("mylib::baz_inplace", mutates_args=["x"])
def baz_inplace(x: torch.Tensor) -> torch.Tensor:
    x.sin_()

def baz(x):
    if inplace:
        baz_inplace(x)
        return x
    else:
        return baz_outplace(x)

This upgrade is doing the same BC-breaking changes as the DLPack release. Objects in torch.utils.dlpack have been updated to reflect these changes, such as DLDeviceType.

Raise appropriate errors in torch.cat (#158249)

torch.cat now raises ValueError, IndexError or TypeError where appropriate instead of the generic RuntimeError. If you code was catching these errors, you can update to catch the new error type.

Default to dynamo=True for ONNX exporter (#159646, #162726)

Previously torch.onnx.export(...) used the legacy TorchScript exporter if no arguments were provied. The ONNX exporter now uses the newer torch.export.export pipeline by default (dynamo=True). This change improves graph fidelity and future-proofs exports, but may surface graph capture errors that were previously masked or handled differently.

Previously in torch 2.8.0:

# API calls the legacy exporter with dynamo=False
torch.onnx.export(...)

Now in torch 2.9.0:

# To preserve the original behavior
torch.onnx.export(..., dynamo=False)

# Export onnx model through torch.export.export
torch.onnx.export(...)

Recommendation: first try the new default; only fall back if you hit blocking issues and report them upstream. Long term solution: fix the root cause instead of relying on fallback or TorchScript exporter.

Switch off runtime asserts by default in Export in favor of a shape guards function (#160111, #161178, #161794)

To enable runtime asserts, use export(..., prefer_deferred_runtime_asserts_over_guards=True). Also kills the allow_complex_guards_as_runtime_asserts flag, merging it into the former option.

Additionally, exported_program.module() will generate a call to a _guards_fn submodule that will run additional checks on inputs. Users who do not want this behavior can either remove this call in the graph, or do exported_program.module(check_guards=False) to avoid the generation.

Set default opset to 20 in ONNX (#158802)

Opset 20 enables newer operator definitions. If your tooling or downstream runtime only supports opset 18, pin it explicitly. For the latest ONNX operators, you can experiment with opset 23.

Previously in torch 2.8.0:

# opset_version=18
torch.onnx.export(...)

Now in torch 2.9.0:

# To preserve the original behavior
torch.onnx.export(..., opset_version=18)

# New: opset_version=20
torch.onnx.export(...)

# Use the latest supported opset: opset_version=23
torch.onnx.export(..., opset_version=23)

Drop draft_export in exporter API (#161454, #162225)

Remove implicit draft tracing from the default exporter path, achieving clearer behaviour and faster failures. The expensive torch.export.draft_export diagnostic path is no longer auto-invoked (which could take hours on large models). You can still opt in for deep diagnostics:

Previously in torch 2.8.0:

# If both torch.export.export(..., strict=False) and
# torch.export.export(..., strict=True) fail to capture
# the model graph, torch.export.draft_export(...) will be triggered,
# and uses real tensor to trace/export the model.
#
# Inside export_to_onnx.py:
#  ... torch.onnx.export(..., dynamo=True)
python export_to_onnx.py

Now in torch 2.9.0:

# To trigger torch.export.draft_export once
# torch.export.export strict=False/True both
# fail:

TORCH_ONNX_ENABLE_DRAFT_EXPORT=True python export_to_onnx.py

Remove torch.onnx.dynamo_export and the onnxrt torch compile backend (#158130, #158258)

torch.onnx.dynamo_export is removed. Please use torch.onnx.export instead. The experimental ONNX Runtime compile backend (torch.compile(backend="onnxrt")) is no longer supported.

Remove torch.onnx.enable_fake_mode (#161222)

The dynamo=True mode uses FakeTensors by default which is memory efficient.

Some public facing ONNX utility APIs for the TorchScript based exporter are now private (#161323)

Deprecated members in torch.onnx.verification are removed. Previously private torch.onnx.symbolic_opsets* functions will no longer be accessible. Consider making a copy of the source code if you need to access any private functions for compatibility with the TorchScript based exporter.

Remove torch.onnx.symbolic_caffe2 (#157102)

Support for caffe2 in the ONNX exporter has ended and is removed.

Remove /d2implyavx512upperregs flag that slows build (#159431)

Re-introduced AVX512 optimizations for Windows VS2022 builds, may cause issues with specific versions of VS2022, see #145702

Add ScalarType to shim conversion and stable::Tensor.scalar_type (#160557)

Before, user extensions could only in abstract pass around obfuscated dtypes appearing as int32_ts. Now, users can confidently use torch::headeronly::ScalarType in their extensions for major scalar types. This PR enables ABI stability by adding a translation layer through the shim, so that even if the ScalarType enum values change in the future, user extensions need not fear.

This change adds ScalarType support for user extensions and is only narrowly BC breaking for unpopular dtypes: quint*s, qint*s, Bits*, dummy_uint*s, dummy_int*s, Float8_e8m0fnu, and Float4_e2m1fn_x2 in the use case where an extension retrieves a Tensor dtype of the above and passes it into aoti_torch_call_dispatcher.
