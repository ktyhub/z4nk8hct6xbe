Faits saillants

Nous sommes ravis d'annoncer la sortie de PyTorch® 2.4 ! PyTorch 2.4 ajoute la prise en charge de la dernière version de Python (3.12) pour torch.compile. Le gel d'AOTInductor offre aux développeurs exécutant AOTInductor davantage d'optimisations basées sur les performances en permettant au sérialisation des poids MKLDNN. De plus, un nouveau backend de serveur TCPStore par défaut utilisant libuv a été introduit. ce qui devrait réduire considérablement les temps d'initialisation pour les utilisateurs exécutant des tâches à grande échelle. Enfin, un nouvel opérateur personnalisé Python API facilite plus qu'avant l'intégration de noyaux personnalisés dans PyTorch, en particulier pour torch.compile. Cette version est composée de 3661 commits et 475 contributeurs depuis PyTorch 2.3. Nous tenons à remercier sincèrement notre communauté dédiée pour vos contributions. Comme toujours, nous vous encourageons à les essayer et à signaler tout problème dès que nous le ferons. améliorer 2.4. Torch.as_strded est une opération de vue existante qui peut être utilisée de manière non compositionnelle : ce qui signifie que lorsque vous appelez x.as_strided(...), as_strided ne fera que tenez compte de la taille de stockage sous-jacente de x et ignorez sa taille/foulée/storage_offset actuelle lors de la création d'une nouvelle vue. Cela rend difficile la fonctionnalisation en toute sécurité des mutations sur des vues d'as_strided qui sont créées de manière non compositionnelle, nous les interdisons donc plutôt que de risquer des problèmes d'exactitude silencieux sous torch.compile. Un exemple d'utilisation non compositionnelle de as_strded suivi d'une mutation sur laquelle nous ferons une erreur est ci-dessous. Vous pouvez éviter ce problème en réécrivant votre utilisation de as_strded afin qu'elle soit compositionnelle (par exemple : soit utilisez un ensemble différent d'opérations de vue au lieu de as_strided, ou appelez as_strided directement sur le tenseur de base au lieu d'une vue existante de celui-ci). ```python @torch.compile def foo(a): e = a.diagonal() # as_strided is being called on an existing view (e), # making it non-compositional. mutations to f under torch.compile # are not allowed, as we cannot easily functionalize them safely f = e.as_strided((2,), (1,), 0) f.add_(1.0) return a ``` #### Nous vérifions désormais les schémas des opérations personnalisées au moment de l'enregistrement (#124520) Auparavant, vous pouviez enregistrer une opération personnalisée via l'enregistrement d'opérateur APIs, mais lui donner un schéma contenant types inconnus du répartiteur PyTorch. À partir du 2.4, nous générerons une erreur au moment de l'enregistrement, lorsque vous enregistrerez pour la première fois le opérateur personnalisé. Vous pouvez obtenir l'ancien comportement en construisant le schéma avec allow_typevars=true. ``` TORCH_LIBRARY(my_ns, m) { // this now raises an error at registration time: bar/baz are unknown types m.def("my_ns::foo(bar t) -> baz"); // you can get back the old behavior with the below flag m.def(torch::schema("my_ns::foo(bar t) -> baz", /*allow_typevars*/ true)); } ``` ### Frontend Autograd #### Supprimer les API torch.autograd.function.traceable (#122817) Le torch.autograd.function.traceable(...) FullyShardedDataParallel v2 (FSDP2)

  • FSDP2 est une nouvelle implémentation parallèle de données entièrement fragmentées qui utilise dim-0 par paramètre basé sur DTensor partitionnement pour une flexibilité améliorée (par exemple, regroupement de types mixtes, aucune contrainte sur require_grad) sans un coût important en termes de performance. Voir le document pour plus de détails et un comparaison avec FSDP1 (#122888, #122907, #123142, #123362, #123491, #123857, #119302, #122908, #123953, #120952, #123988, #124293, #124318, #124319, #120256, #124513, #124955, #125191, #125269, #125394, #126070, #126267, #126305, #126166, #127585, #127776, #127832, #128138, #128117, #128242)

Pipeline

  • Les API de parallélisme de pipeline distribué PyTorch ont été mis en amont du [Projet PiPPy] (https://github.com/pytorch/PiPPy) et sont disponibles sous forme de version prototype dans PyTorch 2.4. Le package se trouve sous torch.distributed.pipelining et se compose de deux parties : une interface de fractionnement et un runtime distribué. L'interface de fractionnement prend votre code de modèle tel quel, le divise en « partitions de modèle » et capture la relation de flux de données. Le moteur d'exécution distribué exécute les étapes du pipeline sur différents appareils en parallèle, gérant des éléments tels que le fractionnement par micro-lots, planification, communication et propagation du gradient. Pour plus d'informations, veuillez consulter le documentation et [tutoriel] (https://pytorch.org/tutorials/intermediate/pipelining_tutorial.html) (#126322, #124776, #125273, #125729, #125975, #126123, #126419, #126539, #126582, #126732, #126653, #127418, #127084, #127673, #127332, #127946, #128157, #128163, #127796, #128201, #128228, #128240, #128236, #128273, #128279, #128276, #128278, #127066)

Tracked Regressions

Subproc exception with torch.compile and onnxruntime-training

There is a reported issue (#131070) when using torch.compile if onnxruntime-training lib is installed. The issue will be fixed (#131194) in v2.4.1. It can be solved locally by setting the environment variable TORCHINDUCTOR_WORKER_START=fork before executing the script.

cu118 wheels will not work with pre-cuda12 drivers

It was also reported (#130684) that the new version of triton uses cuda features that are not compatible with pre-cuda12 drivers. In this case, the workaround is to set TRITON_PTXAS_PATH manually as follows (adapt the code according to the local installation path):

TRITON_PTXAS_PATH=/usr/local/lib/python3.10/site-packages/torch/bin/ptxas  python script.py

Backwards Incompatible Change

Python frontend

Default TreadPool size to number of physical cores (#125963)

Changed the default number of threads used for intra-op parallelism from the number of logical cores to the number of physical cores. This should reduce core oversubscribing when running CPU workload and improve performance. Previous behavior can be recovered by using torch.set_num_threads to set the number of threads to the desired value.

Fix torch.quasirandom.SobolEngine.draw default dtype handling (#126781)

The default dtype value has been changed from torch.float32 to the current default dtype as given by torch.get_default_dtype() to be consistent with other APIs.

Forbid subclassing torch._C._TensorBase directly (#125558)

This is an internal subclass that a user used to be able to create an object that is almost a Tensor in Python and was advertised as such in some tutorials. This is not allowed anymore to improve consistency and all users should subclass torch.Tensor directly.

Composability

Non-compositional usages of as_strided + mutation under torch.compile will raise an error (#122502)

The torch.compile flow involves functionalizing any mutations inside the region being compiled. Torch.as_strided is an existing view op that can be used non-compositionally: meaning when you call x.as_strided(...), as_strided will only consider the underlying storage size of x, and ignore its current size/stride/storage_offset when creating a new view. This makes it difficult to safely functionalize mutations on views of as_strided that are created non-compositionally, so we ban them rather than risking silent correctness issues under torch.compile.

An example of a non-compositional usage of as_strided followed by mutation that we will error on is below. You can avoid this issue by re-writing your usage of as_strided so that it is compositional (for example: either use a different set of view ops instead of as_strided, or call as_strided directly on the base tensor instead of an existing view of it).

@torch.compile
def foo(a):
    e = a.diagonal()
    # as_strided is being called on an existing view (e),
    # making it non-compositional. mutations to f under torch.compile
    # are not allowed, as we cannot easily functionalize them safely
    f = e.as_strided((2,), (1,), 0)
    f.add_(1.0)
    return a

We now verify schemas of custom ops at registration time (#124520)

Previously, you could register a custom op through the operator registration APIs, but give it a schema that contained types unknown to the PyTorch Dispatcher. This behavior came from TorchScript, where “unknown” types were implicitly treated by the TorchScript interpreter as type variables. However, calling such a custom op through regular pytorch would result in an error later. As of 2.4, we will raise an error at registration time, when you first register the custom operator. You can get the old behavior by constructing the schema with allow_typevars=true.

TORCH_LIBRARY(my_ns, m) {
  // this now raises an error at registration time: bar/baz are unknown types
  m.def("my_ns::foo(bar t) -> baz");
  // you can get back the old behavior with the below flag
  m.def(torch::schema("my_ns::foo(bar t) -> baz", /*allow_typevars*/ true));
}

The torch.autograd.function.traceable(...) API, which sets the is_traceable class attribute on a torch.autograd.Function class was deprecated in 2.3 and is now being deleted. Pipelining

  • PyTorch Distributed pipeline parallelism APIs were upstreamed from the PiPPy project and are available as a prototype release in PyTorch 2.4. The package is under torch.distributed.pipelining and consists of two parts: a splitting frontend and a distributed runtime. The splitting frontend takes your model code as-is, splits it up into “model partitions”, and captures the data-flow relationship. The distributed runtime executes the pipeline stages on different devices in parallel, handling things like micro-batch splitting, scheduling, communication, and gradient propagation. For more information please check out the documentation and tutorial (#126322, #124776, #125273, #125729, #125975, #126123, #126419, #126539, #126582, #126732, #126653, #127418, #127084, #127673, #127332, #127946, #128157, #128163, #127796, #128201, #128228, #128240, #128236, #128273, #128279, #128276, #128278, #127066)
