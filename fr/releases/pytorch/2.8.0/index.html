## torch.compile
### Spécialisation d'une forme tensorielle avec `mark_dynamic` appliqué désormais correctement les erreurs (#152661)
Avant 2.8, il était possible qu'une protection sur une forme symbolique soit incorrectement
omise si l'évaluation de la forme symbolique a été préalablement testée avec des protections
supprimé (cela se produit souvent dans le compilateur lui-même). Ceci a été corrigé
dans 2.8 et généralement il "fait ce qu'il faut" en silence et ajoute le bon
garde. Cependant, si la nouvelle garde fait qu'un tenseur marqué `mark_dynamic` devient
spécialisé, cela peut entraîner une erreur. Une solution de contournement consiste à utiliser
`maybe_mark_dynamic` au lieu de `mark_dynamic`.
Voir la discussion dans le numéro 157921 pour en savoir plus
contexte.
Version2.7.0
```python
import torch

embed = torch.randn(2, 8192)
x = torch.zeros(8192)

torch._dynamo.mark_dynamic(x, 0)

@torch.compile
def f(embedding_indices, x):
    added_tokens_mask = torch.where(x > 10000, 1, 0)
    ei = torch.narrow(embedding_indices, 1, 0, x.size(0))
    return ei.clone()

f(embed, x)

Version2.8.0

import torch

embed = torch.randn(2, 8192)
x = torch.zeros(8192)

torch._dynamo.maybe_mark_dynamic(x, 0)

@torch.compile
def f(embedding_indices, x):
    added_tokens_mask = torch.where(x > 10000, 1, 0)
    ei = torch.narrow(embedding_indices, 1, 0, x.size(0))
    return ei.clone()

f(embed, x)

Le code NVTX3 a été déplacé de cmake/public/cuda.cmake à cmake/Dependencies.cmake (#151583)

Il s’agit d’un changement révolutionnaire pour l’interface du système de construction. Projets en aval qui recevaient auparavant NVTX3 via cmake/public/cuda.cmake (c'est-à-dire appeler find_package(TORCH REQUIRED)) devra désormais configurer explicitement la prise en charge de NVTX3 dans la bibliothèque elle-même (c'est-à-dire utiliser USE_SYSTEM_NVTX=1). Le changement consiste à corriger le comportement défectueux où les projets en aval ne pouvaient de toute façon pas trouver NVTX3 en raison de la non-concordance PROJECT_SOURCE_DIR. Version2.7.0 :

  • Un projet en aval utilisant -DUSE_SYSTEM_NVTX serait capable de trouver NVTX3 et torch::nvtx3 via la logique cmake/public/cuda.cmake de PyTorch.
  • Un projet en aval n'utilisant PAS -DUSE_SYSTEM_NVTX rencontrerait des erreurs de construction avec CUDA 12.8 ou supérieur. Version2.8.0 :
  • Un projet en aval utilisant -DUSE_SYSTEM_NVTX ne pourra pas trouver NVTX3 ou torch::nvtx3 via le cmake/public/cuda.cmake de PyTorch. Le projet en aval doit maintenant rechercher explicitement NVTX3 et torch::nvtx3 en implémentant la même logique dans le cmake/Dependences.cmake de PyTorch.
  • Un projet en aval n'utilisant PAS -DUSE_SYSTEM_NVTX poursuivra la construction sans NVTX à moins qu'une autre partie du processus de construction ne réactive NVTX.

Dépréciations

La prise en charge MPS pour MacOS Ventura sera supprimée dans 2.9

PyTorch 2.8 est la dernière version prenant en charge l'accélération GPU sur MacOS Ventura. Dans le prochain (2.9), MacOS Sonoma (publié en septembre 2023) ou supérieur sera requis pour utiliser le MPS back-end.

torch.ao.quantization est obsolète et sera supprimé dans 2.10 (#153892)

Pour migrer :

  • Quantification en mode impatient (torch.ao.quantization.quantize, torch.ao.quantization.quantize_dynamic)
    • Quantification dynamique et poids uniquement : utilisez le mode impatient torchao quantize_.
    • Quantification statique : utilisez la quantification torchao PT2E.
  • Quantification en mode graphique FX (torch.ao.quantization.quantize_fx.prepare_fx, torch.ao.quantization.quantize_fx.convert_fx) : utilisez la quantification torchao PT2E (torchao.quantization.quantize_pt2e.prepare_pt2e, torchao.quantization.quantize_pt2e.convert_pt2e). Notez que la quantification PT2E a été migrée vers torchao (https://github.com/pytorch/ao/tree/main/torchao/quantization/pt2e). Voir https://github.com/pytorch/ao/issues/2259 et https://docs.pytorch.org/ao/main/quick_start.html#pytorch-2-export-quantization pour plus de détails.

L'option dynamo=False (valeur par défaut actuelle) pour torch.onnx.export est obsolète (#152478, #155580)

La valeur par défaut sera dynamo=True à partir de PyTorch 2.9. Nous vous encourageons à migrer pour utiliser l'option dynamo=True dans torch.onnx.export. Cet indicateur fait de torch.export.export le chemin d'exportation par défaut, remplaçant TorchScript. Pour conserver l'ancien comportement, définissez explicitement dynamo=False. Nous vous encourageons également à expérimenter l'option fallback=True qui fera revenir l'exportateur au chemin dynamo=False en cas d'erreurs.

Tracked Regressions

Windows wheel builds with CUDA 12.9.1 stack overflow during build (#156181)

Due to a bug introduced in CUDA 12.9.1, we are unable to complete full Windows wheel builds with this version, as compilation of torch.segment_reduce() crashes the build. Thus, we provide a wheel without torch.segment_reduce() included in order to sidestep the issue. If you need support for torch.segment_reduce(), please utilize a different version.

CUDA Support

Removed support for Maxwell and Pascal architectures with CUDA 12.8 and 12.9 builds (#157517, #158478, #158744)

Due to binary size limitations, support for sm50 - sm60 architectures with CUDA 12.8 and 12.9 has been dropped for the 2.8.0 release. If you need support for these architectures, please utilize CUDA 12.6 instead.

torch.compile

Specialization of a tensor shape with mark_dynamic applied now correctly errors (#152661)

Prior to 2.8, it was possible for a guard on a symbolic shape to be incorrectly omitted if the symbolic shape evaluation was previously tested with guards suppressed (this often happens within the compiler itself). This has been fixed in 2.8 and usually will just silently "do the right thing" and add the correct guard. However, if the new guard causes a tensor marked with mark_dynamic to become specialized, this can result in an error. One workaround is to use maybe_mark_dynamic instead of mark_dynamic.

See the discussion in issue #157921 for more context.

Version 2.7.0

import torch

embed = torch.randn(2, 8192)
x = torch.zeros(8192)

torch._dynamo.mark_dynamic(x, 0)

@torch.compile
def f(embedding_indices, x):
    added_tokens_mask = torch.where(x > 10000, 1, 0)
    ei = torch.narrow(embedding_indices, 1, 0, x.size(0))
    return ei.clone()

f(embed, x)

Version 2.8.0

import torch

x = torch.zeros(8192)

torch._dynamo.maybe_mark_dynamic(x, 0)

@torch.compile
def f(embedding_indices, x):
    added_tokens_mask = torch.where(x > 10000, 1, 0)
    ei = torch.narrow(embedding_indices, 1, 0, x.size(0))
    return ei.clone()

NVTX3 code has been moved from cmake/public/cuda.cmake to cmake/Dependencies.cmake (#151583)

This is a BC-breaking change for the build system interface. Downstream projects that previously got NVTX3 through cmake/public/cuda.cmake (i.e.. calling find_package(TORCH REQUIRED)) will now need to explicitly configure NVTX3 support in the library itself (i.e. use USE_SYSTEM_NVTX=1). The change is to fix the broken behavior where downstream projects couldn't find NVTX3 anyway due to the PROJECT_SOURCE_DIR mismatch.

Version 2.7.0:

  • A downstream project using -DUSE_SYSTEM_NVTX would be able to find NVTX3 and torch::nvtx3 via PyTorch's cmake/public/cuda.cmake logic.
  • A downstream project NOT using -DUSE_SYSTEM_NVTX would encounter build errors with CUDA 12.8 or above.

Version 2.8.0:

  • A downstream project using -DUSE_SYSTEM_NVTX will not be able to find NVTX3 or torch::nvtx3 via PyTorch's cmake/public/cuda.cmake. The downstream project now needs to explicitly find NVTX3 and torch::nvtx3 by implementing the same logic in PyTorch's cmake/Dependences.cmake.
  • A downstream project NOT using -DUSE_SYSTEM_NVTX will proceed building without NVTX unless another part of the build process re-enables NVTX.
