Suppression de la prise en charge de CUDA 12.4, Anaconda dans CI/CD. - Suppression du support CUDA 12.4 dans CI/CD au profit de 12.8 (#148895, #142856, #144118, #145566, #145844, #148602, #143076, #148717) - Suppression du support Anaconda dans CI/CD (#144870, #145015, #147792) - Suppression du support pour Triton < 2.2.0 (versions sans ASTSource) (#143817) ### Extensions C++ `py_limited_api=True` est maintenant construit avec `-DPy_LIMITED_API` (#145764) Nous avons officiellement commencé à respecter le kwarg `py_limited_api=True` dans 2.6 et avons arrêté de lier `libtorch_python.so` lorsque l'indicateur a été spécifié, car libtorch_python.so ne garantit pas l'utilisation des API à partir de la stable Python limitée API. Dans 2.7, nous allons plus loin en spécifiant l'indicateur `-DPy_LIMITED_API` qui imposera que l'extension soit constructible avec le API limité. En raison de cette application, **les extensions personnalisées qui définissent `py_limited_api=True` mais ne respectent pas la limite limitée API peuvent échouer à se créer**. Pour un exemple, voir #152243. Il s'agit d'un comportement strictement meilleur car il est difficile de revendiquer l'agnosticisme de CPython sans l'appliquer avec le drapeau. Si vous rencontrez ce problème, assurez-vous que l'extension que vous créez n'utilise aucun API en dehors du Python limité API, par exemple `pybind`. ### Modifiez `torch.Tensor.new_tensor()` pour qu'il soit sur l'appareil Tensor donné par défaut (#144958) Cette fonction créait toujours le nouveau Tensor sur le périphérique "cpu" et utilisera désormais le même périphérique que l'objet Tensor actuel. Ce comportement est désormais cohérent avec les autres méthodes `.new_*`. ### Utilisez Manylinux 2.28 et CXX11_ABI=1 pour les futures versions de Linux Wheel. Avec la migration vers manylinux_2_28 (basé sur AlmaLinux 8), nous ne pouvons plus prendre en charge les distributions de système d'exploitation avec glibc2_26. Ceux-ci incluent les populaires Amazon Linux 2 et CentOS 7. (#143423, #146200, #148028, #148135, #148195, #148129) ### `torch.onnx.dynamo_export` utilise désormais le chemin logique ExportedProgram (#137296) Les utilisateurs utilisant le `torch.onnx.dynamo_export` API peuvent voir certains `ExportOptions` devenir non pris en charge en raison d'un commutateur interne pour utiliser `torch.onnx.export(..., dynamo=True)` : `diagnostic_options`, `fake_context` et `onnx_registry` sont supprimés/ignorés par `ExportOptions`. Seul `dynamic_shapes` est conservé. Les utilisateurs doivent utiliser l'option `dynamo=True` sur `torch.onnx.export` comme `torch.onnx.dynamo_export` est désormais obsolète. Tirez parti de l'argument [`dynamic_shapes`](https://pytorch.org/docs/stable/export.html#torch.export.export) dans `torch.onnx.export` pour spécifier des formes dynamiques sur le modèle. Version2.6.0 ```python torch.onnx.dynamo_export(model, *args, **kwargs) ``` Version2.7.0 ```python torch.onnx.export(model, args, kwargs=kwargs, dynamo=True) ``` ### Terminez la dépréciation de `LRScheduler.print_lr()` ainsi que du kwarg `verbose` vers le constructeur LRScheduler. (#147301) Les deux API sont obsolètes depuis 2.2. Veuillez utiliser `LRScheduler.get_last_lr()` pour accéder au taux d'apprentissage à la place. `print_lr` et `verbose` prêtaient à confusion, n'étaient pas correctement documentés et étaient peu utilisés, comme décrit dans #99270, nous les avons donc obsolètes dans 2.2. Maintenant, nous terminons la dépréciation en les supprimant complètement. Pour accéder et imprimer le taux d'apprentissage d'un LRScheduler : Version2.6.0 ```python optim = ... lrsched = torch.optim.lr_scheduler.ReduceLROnPlateau(optim, verbose=True) // lrsched will internally call print_lr() and print the learning rate ``` Version2.7.0 ```python optim = ... lrsched = torch.optim.lr_scheduler.ReduceLROnPlateau(optim) print(lrsched.get_last_lr()) ``` ### Les symboles libtorch_python.so sont désormais invisibles par défaut sur toutes les plateformes sauf Apple (#142214) Auparavant, les symboles de libtorch_python.so étaient exposés avec une visibilité par défaut. Nous sommes devenus plus intentionnels sur ce que nous exposons en tant que symboles publics pour notre python API en C++. Après #142214, les symboles publics seront marqués explicitement tandis que tout le reste sera masqué. Certaines extensions utilisant des symboles privés connaîtront des échecs d'éditeur de liens avec ce changement. ### Veuillez utiliser `torch.export.export` au lieu de `capture_pre_autograd_graph` pour exporter le modèle pour la quantification d'exportation de pytorch 2 (#139505) `capture_pre_autograd_graph` était un API temporaire dans `torch.export`. Tracked Regressions

NCCL init hits CUDA failure 'invalid argument' on 12.2 driver

Some users with 12.2 CUDA driver (535 version) report seeing "CUDA driver error: invalid argument" during NCCL or Symmetric Memory initialization. This issue is currently under investigation, see #150852. If you use PyTorch from source, a known workaround is to rebuild PyTorch with CUDA 12.2 toolkit. Otherwise, you can try upgrading the CUDA driver on your system.

Backwards Incompatible Changes

Dropped support for Triton < 2.2.0. Removed Support for CUDA 12.4, Anaconda in CI/CD.

  • Removed CUDA 12.4 support in CI/CD in favor of 12.8 (#148895, #142856, #144118, #145566, #145844, #148602, #143076, #148717)
  • Removed Anaconda support in CI/CD (#144870, #145015, #147792)

C++ Extensions py_limited_api=True is now built with -DPy_LIMITED_API (#145764)

We formally began respecting the py_limited_api=True kwarg in 2.6 and stopped linking libtorch_python.so when the flag was specified, as libtorch_python.so does not guarantee using APIs from from the stable Python limited API. In 2.7, we go further by specifying the -DPy_LIMITED_API flag which will enforce that the extension is buildable with the limited API. As a result of this enforcement, custom extensions that set py_limited_api=True but do not abide by the limited API may fail to build. For an example, see #152243.

This is strictly better behavior as it is sketchy to claim CPython agnosticism without enforcing with the flag. If you run into this issue, please ensure that the extension you are building does not use any APIs which are outside of the Python limited API, e.g., pybind.

Change torch.Tensor.new_tensor() to be on the given Tensor's device by default (#144958)

This function was always creating the new Tensor on the "cpu" device and will now use the same device as the current Tensor object. This behavior is now consistent with other .new_* methods.

Use Manylinux 2.28 and CXX11_ABI=1 for future released Linux wheel builds.

With Migration to manylinux_2_28 (AlmaLinux 8 based), we can no longer support OS distros with glibc2_26. These include popular Amazon Linux 2 and CentOS 7. (#143423, #146200, #148028, #148135, #148195, #148129)

torch.onnx.dynamo_export now uses the ExportedProgram logic path (#137296)

Users using the torch.onnx.dynamo_export API may see some ExportOptions become unsupported due to an internal switch to use torch.onnx.export(..., dynamo=True): diagnostic_options, fake_context and onnx_registry are removed/ignored by ExportOptions. Only dynamic_shapes is retained.

Users should move to use the dynamo=True option on torch.onnx.export as torch.onnx.dynamo_export is now deprecated. Leverage the dynamic_shapes argument in torch.onnx.export for specifying dynamic shapes on the model.

Finish deprecation of LRScheduler.print_lr() along with the verbose kwarg to the LRScheduler constructor. (#147301)

Both APIs have been deprecated since 2.2. Please use LRScheduler.get_last_lr() to access the learning rate instead.print_lr and verbose were confusing, not properly documented and were little used, as described in #99270, so we deprecated them in 2.2. Now, we complete the deprecation by removing them completely. To access and print the learning rate of a LRScheduler:

libtorch_python.so symbols are now invisible by default on all platforms except Apple (#142214)

Previously, the symbols in libtorch_python.so were exposed with default visibility. We have transitioned to being more intentional about what we expose as public symbols for our python API in C++. After #142214, public symbols will be marked explicitly while everything else will be hidden. Some extensions using private symbols will see linker failures with this change.
