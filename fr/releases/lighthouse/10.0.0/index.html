Changements notables

Modifications des scores de performances

Dans la version 8.0, nous avons [décrit le rôle décroissant de TTI] (https://github.com/GoogleChrome/lighthouse/blob/main/docs/v8-perf-faq.md#whats-the-story-with-tti), et aujourd'hui nous avons le suivi. Le temps d'interactivité (TTI) ne contribue plus au score de performance et n'est pas affiché dans le rapport. Cependant, il est toujours accessible dans le résultat Lighthouse JSON. Sans TTI, le poids du Cumulative Layout Shift (CLS) est passé de 15% à 25%. Consultez la documentation pour une description complète de la façon dont le score de performance est calculé dans 10.0 ou jouer avec le calculateur de score.

Types pour le package Node

Lighthouse inclut désormais des déclarations de type ! Notre [exemple de recette TypeScript] (https://github.com/GoogleChrome/lighthouse/tree/main/docs/recipes/type-checking) montre comment obtenir une sécurité de type appropriée avec Lighthouse.

Classification des entités tierces

Depuis Lighthouse 5.3, l'ensemble de données communautaire third-party-web a été utilisé pour résumer la manière dont chaque tiers trouvé sur une page contribue au temps de blocage total de JavaScript, via l'audit third-party-summary. Avec Lighthouse 10.0, nous ajoutons une nouvelle propriété au résultat JSON (entities) pour utiliser davantage cet ensemble de données. Chaque origine rencontrée sur une page est désormais classée comme première partie ou tierce au sein de entities. Dans 10.0, cette classification est utilisée pour alimenter la case à cocher du filtre tiers existant. Dans une future version de Lighthouse, cela sera utilisé pour regrouper les éléments du tableau de chaque audit en fonction de l'entité dont il provient et pour regrouper l'impact des éléments de cette entité spécifique.

🆕 Nouveaux audits

Cache avant/arrière

Le cache arrière/suivant (bfcache en abrégé) est une optimisation du navigateur qui sert des pages à partir d'instantanés entièrement sérialisés lors de la navigation en arrière ou en avant dans l'historique de session. Il existe plus de 100 raisons différentes pour lesquelles une page peut ne pas être éligible à cette optimisation. Pour aider les développeurs, Lighthouse tente désormais de déclencher une réponse bfcache et répertorie tout ce qui a empêché le navigateur d'utiliser le bfcache. #14465 Pour en savoir plus sur bfcache, consultez [l'article web.dev] (https://web.dev/bfcache/). Remarque : Cet audit ne sera initialement pas disponible pour PageSpeed ​​Insights.

Empêcher le collage dans les entrées

L'audit password-inputs-can-be-pasted-into est désormais paste-preventing-inputs. La logique de cet audit fonctionne comme avant, mais plutôt que de simplement considérer les entrées [type=password], elle échoue désormais si n'importe quel élément d'entrée non en lecture seule empêche l'utilisateur de coller. #14313

La documentation Lighthouse est désormais sur Developer.chrome.com

Notre documentation n'est plus hébergée sur web.dev. Pour obtenir les documents d'audit les plus récents, veuillez accéder à developer.chrome.com/docs/lighthouse/

💥 Modifications radicales

Sous le capot, Lighthouse utilise désormais par défaut la nouvelle infrastructure de support du flux utilisateur, même pour les exécutions de navigation traditionnelles. Vous pouvez vous désinscrire en : dans le CLI, utilisez --legacy-navigation ; dans DevTools : cochez « Legacy Navigation » dans le menu des paramètres. Si vous avez un cas d'utilisation qui nécessite cette trappe de secours, veuillez signaler un problème. Nous prévoyons de supprimer ce chemin hérité dans 11.0.

Pour les utilisateurs du résultat Lighthouse JSON (LHR)

URL des pages sur le résultat Lighthouse

Jusqu'à présent, il existait deux champs d'URL pour décrire une exécution Lighthouse :

  • requestedUrl : l'URL donnée par les utilisateurs, vers laquelle Lighthouse demande à Chrome de naviguer
  • finalUrl : l'url après toute redirection HTTP et JS initiée par le serveur Cette taxonomie ne peut pas prendre en compte des scénarios plus complexes, tels que les redirections initiées par JS, l'utilisation de l'historique API ou les navigations logicielles. Ils étaient également mal définis pour les modes de durée et d’instantané. Pour tenir compte de cela, Lighthouse 10.0 dispose désormais de ces champs d'URL :
  • (modifié) requestedUrl : l'URL vers laquelle Lighthouse a initialement accédé avant les redirections. C'est la même chose qu'avant pour le mode de navigation, mais maintenant ce sera undefined en période/instantané.
  • (nouveau) mainDocumentUrl : L'URL du dernier document demandé lors d'une navigation. Il ne prend pas en compte les navigations logicielles ou les événements historiques API effectués après le chargement de la page. Il n'est disponible qu'en mode navigation et ne sera pas défini en modes période de temps et instantané.
  • (nouveau) finalDisplayedUrl : L'URL affichée dans la liste déroulante du navigateur à la fin d'une exécution Lighthouse. Il prend en compte les navigations logicielles et l'historique des événements API. Disponible en modes navigation, intervalle de temps et instantané.
  • (obsolète) finalUrl : même valeur que mainDocumentUrl. #### Modifications d'audit -password-inputs-can-be-pasted-into ->paste-preventing-inputs -preload-lcp-image ->prioritize-lcp-image
  • third-party-summary n'utilise plus de valeur link pour item.entity, mais utilise à la place une valeur brute text
  • full-page-screenshot n'est plus un audit, mais est stocké dans lhr.fullPageScreenshot. Pour supprimer la collecte de la capture d'écran pleine page dans le CLI, vous devez migrer de --skip-audits full-page-screenshot vers --disable-full-page-screenshot.

Pour les utilisateurs de nœuds

  • Le nœud 14 n'est plus supporté, le minimum est désormais le nœud 16
  • Si vous importez des chemins dans le package de nœuds Lighthouse : les dossiers lighthouse-core/ et lighthouse-cli/ sont désormais simplement core/ et cli/.
  • Converti de CommonJS en modules ES. Vous pouvez toujours utiliser Lighthouse dans CommonJS en utilisant une importation dynamique : await import('lighthouse'). Pour accéder uniquement à la fonction lighthouse dans CommonJS, vous pouvez également utiliser require('lighthouse/core/index.cjs')
  • La sortie CSV pour Lighthouse est désormais beaucoup plus utile. Consultez le PR pour [un exemple du nouveau format] (https://github.com/GoogleChrome/lighthouse/pull/13558)
  • LHError est maintenant LighthouseError. Si vous essayez de détecter une erreur générée par Lighthouse, assurez-vous d'en tenir compte !

Modifications du nœud API

La fonction lighthouse dispose désormais d'une [meilleure intégration avec Puppeteer] (https://github.com/GoogleChrome/lighthouse/blob/main/docs/puppeteer.md). Utilisez lighthouse(url, flags, config, page) pour exécuter Lighthouse, en passant un handle Puppeteer.Page existant sous le nom de page. Le flux utilisateur api a été déplacé vers le point d'entrée du nœud de niveau supérieur et peut être importé avec import {startFlow} from 'lighthouse'. Les nouvelles fonctions flow.startNavigation() et flow.endNavigation() vous permettent de définir une navigation déclenchée par l'utilisateur sans aucune fonction de rappel. Consultez la documentation sur le flux utilisateur pour [un exemple] (https://github.com/GoogleChrome/lighthouse/blob/main/docs/user-flows.md#triggering-a-navigation-via-user-interactions). Pour modifier les paramètres d'une étape de flux utilisateur unique, définissez les remplacements de paramètres sur les options d'indicateurs de niveau supérieur flow.snapshot({skipAduits: ['uses-http2']}) plutôt que sur la propriété settingsOverride. Pour attribuer un nom personnalisé à une étape de flux, utilisez flow.snapshot({name: 'Custom name'}). Auparavant, cela se faisait via stepName.

Pour la personnalisation de Lighthouse (configuration personnalisée, rassembleurs, audits)

  • Pour travailler dans Lighthouse 10.0, les rassembleurs personnalisés devront implémenter la nouvelle interface Gatherer (un exemple). Sinon, ils ne fonctionneront qu'en [mode de navigation hérité] (https://github.com/GoogleChrome/lighthouse/blob/main/docs/configuration.md#using-legacy-configs-in-100) et dans les anciennes versions de Lighthouse.
  • Lighthouse ne peut plus utiliser passes pour charger la page plusieurs fois en mode navigation. Si vous devez charger la page plusieurs fois, nous vous recommandons d'utiliser un flux d'utilisateurs. Consultez nos documents de configuration pour obtenir des instructions sur [comment convertir vers le nouveau format de configuration] (https://github.com/GoogleChrome/lighthouse/blob/main/docs/configuration.md#legacy-configs)
  • L'artefact ScriptElements est désormais Scripts, avec une [forme légèrement différente] (https://github.com/GoogleChrome/lighthouse/blob/955586c4e05d501d69a79d4ef0297991b6805690/types/artifacts.d.ts#L317)
  • Audit.makeOpportunityDetails et Audit.makeTableDetails acceptent désormais un objet options comme troisième paramètre. Cela finit par être un changement radical pour seulement Audit.makeOpportunityDetails.

Notable Changes

Performance Score Changes

In the 8.0 release, we described TTI's waning role, and today we have the followup. Time to Interactive (TTI) no longer contributes to the performance score and is not displayed in the report. However, it is still accessible in the Lighthouse result JSON.

Without TTI, the weighting of Cumulative Layout Shift (CLS) has increased from 15% to 25%. See the docs for a complete breakdown of how the Performance score is calculated in 10.0, or play with the scoring calculator.

Types for the Node package

Lighthouse now includes type declarations! Our example TypeScript recipe demonstrates how to achieve proper type safety with Lighthouse.

Third-party Entity classification

Since Lighthouse 5.3, the community-driven third-party-web dataset has been used to summarize how every third-party found on a page contributes to the total JavaScript blocking time, via the third-party-summary audit. With Lighthouse 10.0, we are adding a new property to the JSON result (entities) to make further use of this dataset. Every origin encountered on a page is now classified as first-party or third-party within entities. In 10.0, this classification is used to power the existing third-party filter checkbox.

In a future version of Lighthouse, this will be used to group the table items of every audit based on the entity it originated from, and aggregate the impact of items from that specific entity.

🆕 New Audits

Back/forward cache

The Back/forward cache (bfcache for short) is a browser optimization that serves pages from fully serialized snapshots when navigating back or forwards in session history. There are over 100 different reasons why a page may not be eligible for this optimization, so to assist developers Lighthouse now attempts to trigger a bfcache response and will list anything that prevented the browser from using the bfcache. #14465

For more on bfcache, see the web.dev article.

Note: This audit initially will not be available for PageSpeed Insights.

Preventing pasting to inputs

The audit password-inputs-can-be-pasted-into is now paste-preventing-inputs. This audit's logic works just as before, but rather than just considering [type=password] inputs, it now fails if any non-readonly input element prevents the user from pasting. #14313

Lighthouse documentation is now on developer.chrome.com

Our documentation is no longer hosted on web.dev. For the most up to date audit docs, please go to developer.chrome.com/docs/lighthouse/

💥 Breaking changes

Under the hood, Lighthouse now uses the new user-flow supporting infrastructure by default, even for traditional navigation runs. You can opt out of this by: in the CLI, use --legacy-navigation; in DevTools: check “Legacy Navigation” in the settings menu. If you have a use case that necessitates this escape hatch, please file an issue. We plan to remove this legacy path in 11.0.

For Lighthouse result JSON (LHR) users

Page URLs on the Lighthouse Result

Until now, there were two URL fields to describe a Lighthouse run:

  • requestedUrl: the url given by the users, which Lighthouse instructs Chrome to navigate to
  • finalUrl: the url after any server-initiated HTTP and JS-initiated redirects

This taxonomy cannot account for more complex scenarios, such as JS-initiated redirects, usage of the History API or soft-navigations. They were also ill-defined for timespan and snapshot modes. To account for that, Lighthouse 10.0 now has these URL fields:

  • (changed) requestedUrl: The URL that Lighthouse initially navigated to before redirects. This is the same as it was before for navigation mode, but now it will be undefined in timespan/snapshot.
  • (new) mainDocumentUrl: The URL of the last document requested during a navigation. It does not account for soft navigations or history API events made after the page loads. It is only available in navigation mode, and will be undefined in timespan and snapshot modes.
  • (new) finalDisplayedUrl: The URL displayed in the browser combobox at the end of a Lighthouse run. It accounts for soft navigations and history API events. Available in navigation, timespan, and snapshot modes.
  • (deprecated) finalUrl: Same value as mainDocumentUrl.

Audit changes

  • password-inputs-can-be-pasted-into -> paste-preventing-inputs
  • preload-lcp-image -> prioritize-lcp-image
  • third-party-summary no longer uses a link value for item.entity, instead uses a raw text value
  • full-page-screenshot is no longer an audit, instead it is stored at lhr.fullPageScreenshot. To suppress collection of the full-page screenshot in the CLI, you must migrate from --skip-audits full-page-screenshot to --disable-full-page-screenshot.

For Node users

  • Node 14 is no longer supported, the minimum is now Node 16
  • In case you import paths within the lighthouse node package: lighthouse-core/ and lighthouse-cli/ folders are now simply core/ and cli/
  • Converted from CommonJS to ES modules. You can still use lighthouse in CommonJS by using an dynamic import: await import('lighthouse'). For access to just the lighthouse function in CommonJS, you can also use require('lighthouse/core/index.cjs')
  • The CSV output for Lighthouse is much more useful now. Consult the PR for an example of the new format
  • LHError is now LighthouseError. If you are attempting to catch an error thrown by Lighthouse, be sure to account for this!

Node API changes

The lighthouse function now has better integration with Puppeteer. Use lighthouse(url, flags, config, page) to run Lighthouse, passing an existing Puppeteer.Page handle as page.

The user flow api has moved to the top level node entrypoint and can be imported with import {startFlow} from 'lighthouse'.

New flow.startNavigation() and flow.endNavigation() functions let you define a user triggered navigation without any callback function. See the user flow docs for an example.

To change settings for a single user flow step, define the settings overrides on the toplevel flags options flow.snapshot({skipAduits: ['uses-http2']}) instead of on the settingsOverride property.

To give a flow step a custom name, use flow.snapshot({name: 'Custom name'}). Previously this was done via stepName.

For Lighthouse customization (custom config, gatherers, audits)

  • To work in Lighthouse 10.0, custom gatherers will need to implement the new Gatherer interface (an example). Otherwise, they will only work in legacy navigation mode and older versions of Lighthouse
  • Lighthouse cannot use passes to load the page multiple times in navigation mode anymore. If you need to load the page multiple times, we recommend using a user flow. See our config docs for instructions on how to convert to the new config format
  • The ScriptElements artifact is now Scripts, with a slightly different shape
  • Audit.makeOpportunityDetails and Audit.makeTableDetails now accept an options object as the third parameter. This ends up being a breaking change for just Audit.makeOpportunityDetails.
