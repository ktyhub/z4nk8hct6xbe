mflux v.0.19.0

⚠️ Changements de comportement

  • Un side-car de métadonnées n'empile plus ses LoRA au-dessus de celles de la ligne de commande : --config-from-metadata a restauré lora_paths/lora_scales par concaténation, tandis que toutes les autres clés qu'il restaure s'en remettent aux arguments explicitement donnés. Les adaptateurs du side-car s'appliquaient donc toujours et aucune orthographe ne pouvait les remplacer — --config-from-metadata prior.metadata.json --lora mine.safetensors 0.9 utilisait les deux. Comme une seule des deux listes provenait généralement de la ligne de commande, les décomptes étaient alors en désaccord et resolve_scales a complété ou tronqué la différence derrière un avertissement : --lora-paths cli.safetensors a laissé le nouvel adaptateur sans échelle propre, donc le side-car est allé à l'adaptateur du side-car et le nouveau a été complété à 1.0, et --lora-scales 0.8 sur un side-car à un adaptateur généré à l'échelle du side-car avec le 0.8 rejeté. --lora/--lora-paths remplace désormais les adaptateurs du side-car plutôt que d'en ajouter, --lora-paths sans valeurs est réexécuté sans aucune, et --lora-scales à lui seul conserve les adaptateurs du side-car et applique les nouvelles forces. Tout ce qui est écrit autour du comportement d'empilement doit nommer chaque adaptateur souhaité. Les side-cars enregistrent également le chemin absolu résolu de chaque adaptateur, de sorte que celui transporté entre les machines a échoué sur un chemin qui ne figurait nulle part sur la ligne de commande - et a échoué même lorsque l'utilisateur a nommé sa propre copie, puisque le chemin mort a été fusionné et résolu de toute façon ; cela fonctionne maintenant, et lorsqu'il n'y a pas de remplacement, l'erreur nomme le side-car d'où il vient et dans les deux sens. (#577, #618)
  • --guidance et --scheduler prennent désormais effet sur mflux-upscale-controlnet : les deux ont été enregistrés par l'analyseur puis n'ont jamais été transmis à generate_image, donc tout ce que vous avez tapé a été remplacé par les valeurs par défaut de Flux1Controlnet. Ils sont désormais transmis, ce qui signifie qu'une invocation qui a transmis l'un ou l'autre des indicateurs produit une image différente de celle qu'elle avait auparavant. L'omission de --guidance donne toujours le 4.0 sur lequel l'upscaler a toujours fonctionné, plutôt que ui_defaults.GUIDANCE_SCALE (3.5), donc rien ne change pour une commande qui ne l'a jamais défini. (#577)
  • Les options longues abrégées sont rejetées : chaque mflux CLI nécessite désormais que les drapeaux soient écrits en entier, donc --prom ne remplace plus --prompt. La fourniture d'options est détectée en analysant argv, qui ne peut pas voir les abréviations, et une abréviation qui est sans ambiguïté aujourd'hui commence à se résoudre ailleurs dès qu'un nouveau drapeau est ajouté. Tout ce qui est écrit avec un indicateur raccourci nécessite l'orthographe complète. (#499)

✨ Améliorations

  • twine supprimé des dépendances de mflux : il n'existait que pour prendre en charge le script de publication, mais chaque pip install mflux récupérait la ficelle plus ~24 packages transitifs (cryptography, keyring, rich, readme-renderer, ...). Le téléchargement en mode jeton du script de version est désormais effectué sur uv publish - --check-url réplique le skip_existing de Twine, le jeton passe via UV_PUBLISH_TOKEN afin qu'il n'apparaisse jamais dans les commandes enregistrées et la sémantique des nouvelles tentatives transitoires est inchangée - tandis que twine check dist/* survit via uv tool run twine dans un environnement éphémère. Le chemin de publication trusted de CI est intact (pypa/gh-action-pypi-publish est toujours téléchargé). Corrige également le script appelant uv sous le nom python -m uv, qui nécessite le package uv PyPI que l'environnement de publication n'installe pas ; il appelle désormais le binaire uv de PATH. Ajoute une recette just release qui déclenche le workflow de publication via gh. (#644)
  • Vérification de type migrée de mypy vers astral's ty (épinglé ty==0.0.72 dans les développeurs, pré-commit et CI) : vérifications du projet complet en ~0,4 s contre 2 à 9 s pour mypy. Les violations préexistantes sont considérées comme des règles ignorées dans [tool.ty.rules] (avec décomptes) pour être réactivées et corrigées au coup par coup ; le nouveau code doit respecter toutes les règles non basées sur une base. Ajoute just typecheck. (#597)
  • Chargement LoRA plus silencieux : l'empilement d'un deuxième adaptateur imprimait une ligne 🔀 pour chaque couche fusionnée - des centaines de lignes entre la propre ligne 🔧 du fichier et son résumé ✅ Applied to N layers, qui indique déjà combien de lignes ont atterri. Ces trois messages par couche sont désormais logger.debug, comme le traçage des règles de résolution. (#577)
  • Les options CLI supprimées silencieusement avertissent désormais : une commande qui accepte une option qu'elle ne peut pas honorer le dit au moment de l'analyse au lieu de l'ignorer, par exemple --guidance sur un modèle distillé par guidage. Ajoute mflux-capabilities, un dump lisible par machine de chaque commande génératrice d'image avec ses options, valeurs par défaut, types et l'état de chaque option (honorée, ignorée, conditionnelle ou rejetée), dans JSON, YAML ou Markdown. (#499)

✨ Améliorations

  • Drapeaux --vae-tiling et --vae-tile-size : restaurez le contrôle de l'utilisateur sur le décodage VAE en mosaïque, découplé de --low-ram (auparavant, le seul moyen de l'activer). --vae-tiling permet le décodage en mosaïque avec les mosaïques par défaut de 512 px ; --vae-tile-size 256 réduit les tuiles pour réduire davantage la mémoire de décodage maximale et implique --vae-tiling. Tous deux composent avec --low-ram, dont ils remplacent les paramètres de mosaïque implicites par défaut. Les indicateurs --vae-tiling/--vae-tiling-split d'origine ont été supprimés dans le refactor Z-Image (#284) ; cela restaure la capacité au-dessus du VAETiler généralisé. (#311, #407)

🐛 Corrections de bugs

  • Les poids FLUX ControlNet enregistrés ont été ignorés lors du chargement : FluxInitializer.init_controlnet récupérait toujours le composant ControlNet à partir du référentiel distant, sans jamais consulter le model_path qu'il honore pour tous les autres composants. Le rechargement d'un point de contrôle écrit par mflux-save a échangé silencieusement ses poids ControlNet contre ceux du hub - une sauvegarde -q est revenue avec ce composant non quantifié, un réglage fin a été rejeté et un point de contrôle local par ailleurs complet voulait toujours le réseau. Accessible uniquement depuis que #607 a obligé mflux-save à écrire réellement le composant ControlNet. Un model_path contenant transformer_controlnet/*.safetensors le charge maintenant depuis le disque, la branche que ZImageInitializer avait déjà ; un nom intégré ou un répertoire sans ce composant conserve le chemin du hub. (#610, #642)
  • Un identifiant de dépôt partagé par deux entrées de registre résolu en variante ControlNet : plusieurs racines partagent un model_name avec un dérivé de ControlNet, et le résolveur a renvoyé la première correspondance dans l'ordre priority - ce qui a placé le Z-Image ControlNet avant le turbo simple, donc --model Tongyi-MAI/Z-Image-Turbo a construit une configuration ControlNet dans chaque appelant du résolveur (la génération des CLI et la répartition des mflux-save). Les liens sur un identifiant de dépôt nu préfèrent désormais l'entrée de base, selon la règle selon laquelle une variante dérivée est toujours adressée par sa propre clé ou alias ; les clés et les alias sont résolus exactement comme avant. (#609, #641)
  • Les LoRA défaillants ont été signalés comme appliqués : chaque étape entre la résolution d'un adaptateur et son pliage dans les poids avait un chemin qui imprimait un avertissement et continuait, et l'exécution annonçait ensuite ✅ All LoRA weights applied successfully. Un adaptateur qui n'a pas pu être résolu a été supprimé de la liste - générant à partir du modèle de base intact et, avec plusieurs adaptateurs, déplaçant la balance sur les mauvais alors que resolve_scales complétait la liste raccourcie. Un fichier manquant ou illisible au moment du chargement a imprimé ❌ et renvoyé. Une couche cible que le modèle n'a pas, ou une couche qui s'est avérée non linéaire, a imprimé ❌ par couche et a laissé l'adaptateur appliqué à une partie seulement du modèle. Et la cuisson a détecté toutes les exceptions - y compris une inadéquation entre le poids de base et la forme delta - a imprimé ⚠️ et a renvoyé la couche non cuite, donc mflux-save a écrit un point de contrôle annoncé comme fusionné qui contenait les poids de base d'origine, et la génération ordinaire (qui cuit par défaut) s'est déroulée silencieusement sans l'adaptateur. Tous ces éléments augmentent maintenant. Les erreurs d'initialisation nomment la couche sur laquelle elles ont échoué (blocks.0.attn.wq), et mflux-save prépare chaque composant avant d'écrire un seul fichier, de sorte qu'une incompatibilité est abandonnée au lieu de laisser un demi-point de contrôle sur le disque. Tout ce qui est écrit autour d'un chemin d'adaptateur mal saisi ou manquant se termine désormais au lieu de générer une image sans celui-ci. (#577)
  • boogu et FIBO ont accepté --lora puis l'ont rejeté : mflux-generate-boogu, mflux-generate-fibo et mflux-generate-fibo-edit ont tous déclaré les indicateurs LoRA, donc l'analyseur a résolu chaque adaptateur - en le téléchargeant depuis HuggingFace lorsque le nom était un identifiant de dépôt - et les initialiseurs l'ont ensuite laissé tomber par terre, tandis que mflux-capabilities a signalé "lora": true et rien n'a été averti à aucun moment. mflux n'implémente aucun mappage LoRA pour aucune des deux architectures, donc les indicateurs ont disparu plutôt qu'ignorés : les trois CLI ne les prennent plus, correspondant à mflux-generate-lens, et --help et le vidage des capacités sont désormais en accord avec le code. BooguInitializer/FIBOInitializer et les constructeurs BooguImage/FIBO/FIBOEdit ont perdu leurs paramètres lora_paths/lora_scales/bake_lora inutilisés, donc le Python API cesse d'accepter un adaptateur qu'il ignore, et mflux-save --model boogu --lora ..., qui a filtré les mêmes kwargs par signature et a écrit un point de contrôle non modifié, se termine maintenant avec un message. (#577, #615)
  • --model ignoré silencieusement sur 4 CLI : mflux-generate-krea2, mflux-generate-z-image-turbo, mflux-generate-ernie-image et mflux-generate-ernie-image-turbo ont accepté --model et ont ensuite construit une configuration codée en dur, donc --model dev a exécuté silencieusement Krea-2-Turbo (etc.) tandis que mflux-capabilities a signalé l'option comme honorée. Chacun valide désormais --model via un ConfigResolution.resolve_restricted partagé (le modèle de lentille) : un nom de registre intégré doit être un alias du propre modèle du CLI, sauf erreur. Les chemins de point de contrôle locaux et les identifiants de dépôt HuggingFace – que le parse_args achemine via model_path – sont intacts : ils conservent la propre configuration du CLI et chargent les poids du chemin, comme ils l'ont toujours fait. La validation compare les entrées de registre par identité plutôt que par model_name, donc --model z-image-controlnet – dont l'entrée partage l'identifiant du dépôt Tongyi-MAI/Z-Image-Turbo – est correctement rejetée par le turbo simple CLI ; La vérification en ligne de lens_generate, qui comparait model_name, utilise désormais le même assistant. (#577, #614)
  • mflux-completions plantait à chaque invocation : l'analyseur mflux-upscale-controlnet a ajouté ses arguments LoRA deux fois, donc chaque chemin de construction est mort avec argparse.ArgumentError: conflicting option string: --lora-style (sortie 1) avant d'écrire une seule complétion. Un test de régression construit désormais l'analyseur pour chaque commande connue par mflux-completions. (#577, #613)
  • Résolution de conditionnement Qwen Image Edit : codez les latents de conditionnement d'image du transformateur à la résolution cible d'édition, et non à la résolution de conditionnement du langage de vision (≈384 px par zone), évitant ainsi les artefacts inégaux/en mosaïque dans les sorties d'édition. Cela modifie la sortie d'édition à chaque niveau de quantification, pas seulement -q 4. (#420)
  • Dimensions par défaut de Qwen Image Edit : conserve les premières dimensions de l'image d'entrée par défaut ; Les valeurs explicites --width/--height ou les facteurs d'échelle tels que 2x choisissent toujours le redimensionnement. (#420)
  • Planificateur Qwen Image Edit CLI : transférer --scheduler vers le pipeline d'édition Qwen (précédemment ignoré). (#420)
  • Les configurations de modèle déduites ont perdu leurs paramètres : ConfigResolution a reconstruit les configurations déduites champ par champ, de sorte que tout ce qui est résolu à partir d'un chemin local ou d'un nom de variante (/models/qwen-image-edit-q4) est revenu silencieusement aux valeurs par défaut génériques. Il porte désormais tous les domaines et réécrit uniquement l'identité. Cela restaure le calendrier sigma d'édition Qwen (0.9/8192/0.02 plutôt que 1.15/4096/None), les conseils de formation LoRA d'ERNIE et supports_kv_cache sur flux2-klein-9b-kv. (#420)
  • Par défaut, --steps a ignoré le modèle sur 10 CLI : chaque image CLI qui sélectionne son modèle dans main() plutôt qu'au moment de l'analyse — boogu, krea2, lens, z-image, z-image-turbo, flux2, flux2-edit, qwen, qwen-edit, ideogram4 — a résolu --steps contre un Modèle None et héritage silencieux des 25 de FLUX.1-dev. Cela représente 6 fois le travail sur une distillation en 4 étapes (boogu, lens, klein) et la moitié du travail sur un modèle de base en 50 étapes (image z). La table des étapes est désormais saisie par modèle canonique plutôt que par alias et résolue via AVAILABLE_MODELS, donc --model klein-4b et --model flux2-klein-4b ne sont plus en désaccord, et un CLI déclare son propre modèle à l'analyseur via add_model_arguments(default_model=...). La solution de secours DEFAULT_STEPS = 8 de Krea 2, inaccessible car l'analyseur en fournissait toujours 25, a disparu. Le --steps explicite n’est pas affecté. (#580)
  • --model <name> a échoué pour la plupart des modèles intégrés : les noms acceptés par le CLI étaient une liste entretenue manuellement (ui_defaults.MODEL_CHOICES) qui avait dérivé de AVAILABLE_MODELS, et tout ce qui manquait était traité comme un répertoire de point de contrôle local - mflux-generate-lens --model lens-turbo est mort avec Model not found: 'lens-turbo' sur le nom canonique du seul modèle exécuté par CLI. 16 clés de registre et environ 40 alias ont été affectés, parmi lesquels krea-2-raw, qwen-image et toutes les orthographes klein-*, boogu-*, zimage* et fiboedit*. Les noms acceptés sont désormais dérivés du registre, donc un nouveau modèle ou alias ne nécessite aucune seconde modification. --base-model a également abandonné sa liste d'arguments obsolètes choices=, qui rejetait les noms valides tels que qwen-image ; il est désormais validé par rapport à la propre liste de modèles racine de ConfigResolution, et la vérification couvre également un base_model restauré à partir d'un side-car de métadonnées. (#577)
  • mflux-save a écrit des points de contrôle sous la mauvaise architecture : la classe de modèle a été choisie par une chaîne de sous-chaînes sur la chaîne brute --model se terminant par else: Flux1, donc chaque nom qui n'avait pas été appris a été enregistré en tant que modèle FLUX.1 — lens, lens-turbo, klein-4b/9b/9b-kv et seedvr2* l'étaient tous — alors que fibo-edit* a été enregistré par la classe FIBO txt2img et z-image-controlnet* par plain ZImage. Rien n'a été relevé ; la disparité est apparue plus tard comme un point de contrôle non téléchargeable. La répartition passe désormais par le registre (ConfigResolution.resolve_key), donc les clés canoniques, les alias, les identifiants de dépôt HuggingFace et les orthographes --base-model atterrissent tous sur la classe qui possède ces poids, un nom méconnaissable sort avec un message au lieu de passer par défaut à Flux1, et les deux modèles sans chemin de sauvegarde (Lens, SeedVR2) le disent. Chaque rejet répertorie également les modèles que mflux-save peut écrire, ce que --help n'affiche pas — il répertorie les modèles qui ne peuvent pas être enregistrés. Un test de dérive échoue si un modèle est ajouté au AVAILABLE_MODELS sans classe de sauvegarde. Deux conséquences à noter : --model dev-controlnet-canny/dev-controlnet-upscaler/schnell-controlnet-canny sont désormais sauvegardés via Flux1Controlnet (poids ControlNet inclus) plutôt que sous forme de Flux.1 nu, et mflux-save --model boogu ne meurt plus avec un TypeError sur bake_lora, ce que BooguImage n'accepte pas. (#607)
  • Latents multi-trames ERNIE : pack_latents a indexé l'axe temporel du VAE, de sorte que tout sauf une seule trame a été ignoré en silence ; il échoue maintenant bruyamment. (#577)
  • Contrat de guidage ernie-image-turbo : le modèle a déclaré supports_guidance: true alors que son CLI sort sur tout guidage autre que 1.0, se contredisant dans le dump mflux-capabilities. (#578)
  • Téléchargements partiels de Krea 2 Turbo considérés comme terminés : un instantané mis en cache était vérifié par rapport à ses modèles de téléchargement uniquement lorsque le modèle n'avait besoin d'aucun sous-répertoire. Krea 2 Turbo conserve son transformateur à la racine du dépôt sous le nom turbo.safetensors, donc un téléchargement qui a récupéré vae/ et text_encoder/ puis s'est arrêté s'est signalé terminé. Le téléchargement de réparation de Hugging Face n'a jamais été exécuté et la charge est morte plus tard avec Missing specified weight files in <snapshot>: ['turbo.safetensors'], qui se lit comme un cache corrompu plutôt que comme un transfert interrompu. Les modèles *.safetensors au niveau racine sont désormais également vérifiés dans la branche du sous-répertoire. (#577, #593)
  • Points de contrôle enregistrés chargés tout ce qui se trouvait dans le répertoire : mflux-save écrit un model.safetensors.index.json nommant chaque fragment, et le rechargement a globalisé le répertoire au lieu de le lire. L'enregistrement de -q 4 sur un point de contrôle -q 8 existant dans le même dossier a laissé la queue q8 derrière, et ces tenseurs obsolètes ont écrasé ceux qui viennent d'être écrits alors que les métadonnées en rapportaient toujours 4. Un point de contrôle manquant un fragment, les noms d'index ont chargé le reste et ont échoué. L'index décide désormais quelles partitions sont lues, et une partition nommée qui n'est pas sur le disque apparaît avec les noms de fichiers. Les points de contrôle sans index ou avec un index endommagé continuent à se charger à partir du répertoire. (#577)
  • Les side-cars de métadonnées n'ont pas restauré les dimensions, l'invite négative ou les images d'initialisation : chaque exécution intègre height, width, negative_prompt et image_paths, mais --config-from-metadata n'en a lu aucun, donc une réexécution side-car uniquement d'une génération 1536x768 est sortie à la valeur par défaut de 1024x1024 avec l'invite négative supprimée - une version différente image sur n’importe quel modèle CFG, pas seulement un modèle de taille différente. L'édition CLI ne pouvait pas du tout réexécuter un side-car : --image-paths était required=True, ce que argparse applique avant l'exécution du bloc de restauration, donc mflux-generate-qwen-edit --config-from-metadata prior.metadata.json a quitté 2 images exigeantes que le side-car transportait. Les quatre clés sont maintenant restaurées, chacune s'en remettant à la ligne de commande option par option, et --image-paths est requis après la restauration plutôt que pendant l'analyse. L'image d'initialisation d'un side-car qui n'existe pas sur cette machine comporte désormais des erreurs lors de l'analyse lors du nom du side-car, au lieu de charger d'abord le modèle entier et de mourir sur un FileNotFoundError nu. (#577, #634)
  • Les commandes haut de gamme manquaient dans mflux-capabilities : COMMAND_PREFIXES couvrait uniquement mflux-generate* et mflux-concept*, donc ni mflux-upscale-controlnet ni mflux-upscale-seedvr2 n'apparaissaient dans le dump - c'est ainsi que le bug --metadata ci-dessus est passé inaperçu par les contrôles de contrat qui existent pour détecter exactement cela. Les deux sont maintenant publiés avec une couverture complète, ce qui signifie adopter la convention build_parser() et déclarer ce que leurs configurations codées en dur ne peuvent pas honorer : --base-model est ignoré par les deux, et sur mflux-upscale-controlnet, --negative-prompt est ignoré tandis que --model est conditionnel (un chemin ou un identifiant de dépôt charge des poids, un nom de modèle intégré ne fait rien, puisque la configuration est toujours dev-controlnet-upscaler). Les deux commandes avertissent désormais au moment de l'analyse lorsqu'une option ignorée est passée. (#577)
  • mflux-upscale-seedvr2 --metadata n'a jamais écrit le side-car : le CLI a accepté le drapeau puis l'a enregistré sans le transmettre, donc la mise à niveau s'est terminée et aucun JSON n'est apparu. Son frère mflux-upscale-controlnet dépasse export_json_metadata sur la ligne équivalente. (#577)
  • Quantification de l'idéogramme 4 : mflux-save -q quantifie désormais réellement l'idéogramme 4. Chaque linéaire porteur dans le modèle est un Fp8Linear, qui n'a défini aucun to_quantized et dont les composants étaient marqués skip_quantization, donc -q 4 a écrit un point de contrôle FP8 estampillé quantization_level: 4 et seul le VAE a été touché. Ajoute Fp8Linear.to_quantized, supprime les indicateurs de saut, dérive les bits et la taille du groupe à partir des formes stockées lors de la reconstruction d'un point de contrôle enregistré au lieu de supposer q8/group-64, et reconstruit les plongements quantifiés sous forme de plongements plutôt que linéaires. -q 8 fait 26 Go et -q 4 fait 14 Go, tous deux visuellement impossibles à distinguer du FP8. (#559)

📝Documentation

  • Idéogramme 4 poids fermés : Documentez l'étape HF_TOKEN / hf auth login à côté de la note existante selon laquelle l'accès doit être approuvé sur la carte modèle - l'authentification est la moitié des personnes qui manquent, et sans elle, un compte approuvé échoue toujours avec un simple 401/403. Ajoute une section de quantification couvrant mflux-save -q et chargeant un point de contrôle enregistré avec --model-path. (#559)

🧰DX & Maintenance

  • Workflow de développement : Makefile remplacé par justfile : make <target> a disparu ; utilisez plutôt just <target> (just install, just lint, just format, just check, just test-fast, …). L'exécution nue de just (ou just --list) affiche toutes les recettes avec des descriptions. La sémantique suit le Makefile post-#576 : uv sync s'installe et ruff est épinglé à partir de la dépendance de développement pyproject.toml. Le travail de charpie CI peluche également le fichier justfile lui-même via just --fmt --check, en utilisant l'action composite épinglée just-setup. Nécessite just ≥ 1.50 localement. (#590)

mflux v.0.19.0

⚠️ Behavior Changes

  • A metadata sidecar no longer stacks its LoRAs on top of the command line's: --config-from-metadata restored lora_paths/lora_scales by concatenation, while every other key it restores defers to explicitly given arguments. The sidecar's adapters therefore always applied and no spelling could replace them — --config-from-metadata prior.metadata.json --lora mine.safetensors 0.9 ran both. Since only one of the two lists usually came from the command line, the counts then disagreed and resolve_scales padded or truncated the difference behind a warning: --lora-paths cli.safetensors left the new adapter with no scale of its own, so the sidecar's went to the sidecar's adapter and the new one was padded to 1.0, and --lora-scales 0.8 on a one-adapter sidecar generated at the sidecar's scale with the 0.8 discarded. --lora/--lora-paths now replaces the sidecar's adapters rather than adding to them, --lora-paths with no values re-runs without any, and --lora-scales on its own keeps the sidecar's adapters and applies the new strengths. Anything scripted around the stacking behaviour has to name every adapter it wants. Sidecars also record each adapter's resolved absolute path, so one carried between machines failed on a path that was nowhere on the command line — and failed even when the user named their own copy, since the dead path was merged in and resolved anyway; that now works, and when there is no replacement the error names the sidecar it came from and both ways out. (#577, #618)
  • --guidance and --scheduler now take effect on mflux-upscale-controlnet: both were registered by the parser and then never passed to generate_image, so whatever you typed was replaced by Flux1Controlnet's own defaults. They are forwarded now, which means an invocation that passed either flag produces a different image than it did before. Omitting --guidance still gives the 4.0 the upscaler has always run at, rather than ui_defaults.GUIDANCE_SCALE (3.5), so nothing changes for a command that never set it. (#577)
  • Abbreviated long options are rejected: every mflux CLI now requires flags to be written in full, so --prom no longer stands in for --prompt. Option provision is detected by scanning argv, which cannot see abbreviations, and an abbreviation that is unambiguous today starts resolving elsewhere the moment a new flag is added. Anything scripted with a shortened flag needs the full spelling. (#499)

✨ Improvements

  • twine removed from mflux's dependencies: it only existed to support the release script, but every pip install mflux pulled in twine plus ~24 transitive packages (cryptography, keyring, rich, readme-renderer, ...). The release script's token-mode upload now shells out to uv publish — --check-url replicates twine's skip_existing, the token travels via UV_PUBLISH_TOKEN so it never appears in logged commands, and the transient-retry semantics are unchanged — while twine check dist/* survives via uv tool run twine in an ephemeral environment. CI's trusted-publishing path is untouched (pypa/gh-action-pypi-publish still uploads). Also fixes the script invoking uv as python -m uv, which requires the uv PyPI package that the release environment does not install; it now calls the uv binary from PATH. Adds a just release recipe that triggers the release workflow via gh. (#644)
  • Type checking migrated from mypy to astral's ty (pinned ty==0.0.72 in dev deps, pre-commit and CI): full-project checks in ~0.4s vs mypy's 2–9s. Pre-existing violations are baselined as ignored rules in [tool.ty.rules] (with counts) to be re-enabled and fixed piecemeal; new code must pass all non-baselined rules. Adds just typecheck. (#597)
  • Quieter LoRA loading: stacking a second adapter printed a 🔀 line for every layer it fused — hundreds of lines between the file's own 🔧 line and its ✅ Applied to N layers summary, which already says how many landed. Those three per-layer messages are now logger.debug, like the resolution rules' tracing. (#577)
  • Silently dropped CLI options now warn: a command that accepts an option it cannot honour says so at parse time instead of ignoring it, for example --guidance on a guidance-distilled model. Adds mflux-capabilities, a machine-readable dump of every image-generating command with its options, defaults, types and the status of each option (honored, ignored, conditional or rejected), in JSON, YAML or Markdown. (#499)

✨ Improvements

  • --vae-tiling and --vae-tile-size flags: Restore user-facing control over tiled VAE decoding, decoupled from --low-ram (previously the only way to enable it). --vae-tiling enables tiled decode with the default 512px tiles; --vae-tile-size 256 shrinks the tiles to further reduce peak decode memory and implies --vae-tiling. Both compose with --low-ram, whose implicit tiling defaults they override. The original --vae-tiling/--vae-tiling-split flags were removed in the Z-Image refactor (#284); this restores the capability on top of the generalized VAETiler. (#311, #407)

🐛 Bug Fixes

  • Saved FLUX ControlNet weights were ignored on load: FluxInitializer.init_controlnet always fetched the ControlNet component from the remote repo, never consulting the model_path it honors for every other component. Reloading a checkpoint written by mflux-save silently swapped its ControlNet weights for the hub's — a -q save came back with that component unquantized, a fine-tune was discarded, and an otherwise complete local checkpoint still wanted the network. Only reachable since #607 made mflux-save actually write the ControlNet component. A model_path holding transformer_controlnet/*.safetensors now loads it from disk, the branch ZImageInitializer already had; a builtin name or a directory without that component keeps the hub path. (#610, #642)
  • A repo id shared by two registry entries resolved to the ControlNet variant: several roots share a model_name with a ControlNet derivative, and the resolver returned the first match in priority order — which put the Z-Image ControlNet ahead of plain turbo, so --model Tongyi-MAI/Z-Image-Turbo built a ControlNet config in every resolver caller (the generate CLIs and mflux-save dispatch alike). Ties on a bare repo id now prefer the base entry, on the rule that a derived variant is always addressed by its own key or alias; keys and aliases resolve exactly as before. (#609, #641)
  • Failed LoRAs were reported as applied: every step between resolving an adapter and folding it into the weights had a path that printed a warning and carried on, and the run then announced ✅ All LoRA weights applied successfully. An adapter that could not be resolved was dropped from the list — generating from the untouched base model, and, with several adapters, shifting the scales onto the wrong ones as resolve_scales padded the shortened list back to length. A file that was missing or unreadable at load time printed ❌ and returned. A target layer the model does not have, or one that turned out not to be linear, printed ❌ per layer and left the adapter applied to only part of the model. And baking caught every exception — including a base-weight/delta shape mismatch — printed ⚠️ and returned the layer unbaked, so mflux-save wrote a checkpoint advertised as merged that held the original base weights, and ordinary generation (which bakes by default) quietly ran without the adapter. All of these now raise. Bake errors name the layer they failed at (blocks.0.attn.wq), and mflux-save bakes every component before it writes a single file, so a mismatch aborts instead of leaving half a checkpoint on disk. Anything scripted around a mistyped or missing adapter path now exits instead of generating an image without it. (#577)
  • boogu and FIBO accepted --lora and then discarded it: mflux-generate-boogu, mflux-generate-fibo and mflux-generate-fibo-edit all declared the LoRA flags, so the parser resolved every adapter — downloading it from HuggingFace when the name was a repo id — and the initializers then dropped it on the floor, while mflux-capabilities reported "lora": true and nothing warned at any point. mflux implements no LoRA mapping for either architecture, so the flags are gone rather than ignored: the three CLIs no longer take them, matching mflux-generate-lens, and --help and the capabilities dump now agree with the code. BooguInitializer/FIBOInitializer and the BooguImage/FIBO/FIBOEdit constructors lost their unused lora_paths/lora_scales/bake_lora parameters so the Python API stops accepting an adapter it ignores, and mflux-save --model boogu --lora ..., which filtered the same kwargs away by signature and wrote an unmodified checkpoint, now exits with a message. (#577, #615)
  • --model silently ignored on 4 CLIs: mflux-generate-krea2, mflux-generate-z-image-turbo, mflux-generate-ernie-image and mflux-generate-ernie-image-turbo accepted --model and then constructed a hard-coded config, so --model dev silently ran Krea-2-Turbo (etc.) while mflux-capabilities reported the option as honored. Each now validates --model through a shared ConfigResolution.resolve_restricted (the lens pattern): a builtin registry name must be an alias of the CLI's own model, anything else errors. Local checkpoint paths and HuggingFace repo ids — which parse_args routes through model_path — are untouched: they keep the CLI's own config and load weights from the path, as they always have. Validation compares registry entries by identity rather than model_name, so --model z-image-controlnet — whose entry shares the Tongyi-MAI/Z-Image-Turbo repo id — is correctly rejected by the plain turbo CLI; lens_generate's inline check, which compared model_name, now uses the same helper. (#577, #614)
  • mflux-completions crashed on every invocation: the mflux-upscale-controlnet parser added its LoRA arguments twice, so every build path died with argparse.ArgumentError: conflicting option string: --lora-style (exit 1) before writing a single completion. A regression test now builds the parser for every command mflux-completions knows about. (#577, #613)
  • Qwen Image Edit conditioning resolution: Encode the transformer's image-conditioning latents at the edit target resolution, not the vision-language conditioning resolution (≈384px by area), preventing patchy/tiled artifacts in edit outputs. This changes edit output at every quantization level, not only -q 4. (#420)
  • Qwen Image Edit default dimensions: Preserve the first input image dimensions by default; explicit --width/--height values or scale factors such as 2x still opt into resizing. (#420)
  • Qwen Image Edit CLI scheduler: Forward --scheduler to the Qwen edit pipeline (previously ignored). (#420)
  • Inferred model configs lost their settings: ConfigResolution rebuilt inferred configs field by field, so anything resolved from a local path or variant name (/models/qwen-image-edit-q4) silently fell back to generic defaults. It now carries every field and rewrites only identity. This restores the Qwen edit sigma schedule (0.9/8192/0.02 rather than 1.15/4096/None), ERNIE's LoRA training guidance, and supports_kv_cache on flux2-klein-9b-kv. (#420)
  • Default --steps ignored the model on 10 CLIs: every image CLI that picks its model in main() rather than at parse time — boogu, krea2, lens, z-image, z-image-turbo, flux2, flux2-edit, qwen, qwen-edit, ideogram4 — resolved --steps against a None model and silently inherited FLUX.1-dev's 25. That is 6x the work on a 4-step distillation (boogu, lens, klein) and half the work on a 50-step base model (z-image). The step table is now keyed by canonical model rather than by alias and resolved through AVAILABLE_MODELS, so --model klein-4b and --model flux2-klein-4b no longer disagree, and a CLI declares its own model to the parser via add_model_arguments(default_model=...). Krea 2's DEFAULT_STEPS = 8 fallback, unreachable because the parser always supplied 25, is gone. Explicit --steps is unaffected. (#580)
  • --model <name> failed for most built-in models: the names the CLI accepted were a hand-maintained list (ui_defaults.MODEL_CHOICES) that had drifted from AVAILABLE_MODELS, and anything missing from it was treated as a local checkpoint directory — mflux-generate-lens --model lens-turbo died with Model not found: 'lens-turbo' on the canonical name of the only model that CLI runs. 16 registry keys and roughly 40 aliases were affected, among them krea-2-raw, qwen-image, and every klein-*, boogu-*, zimage* and fiboedit* spelling. The accepted names are now derived from the registry, so a new model or alias needs no second edit. --base-model likewise dropped its stale argparse choices= list, which rejected valid names such as qwen-image; it is now validated against ConfigResolution's own list of root models, and the check also covers a base_model restored from a metadata sidecar. (#577)
  • mflux-save wrote checkpoints under the wrong architecture: the model class was chosen by a substring chain over the raw --model string ending in else: Flux1, so every name it had not been taught was saved as a FLUX.1 model — lens, lens-turbo, klein-4b/9b/9b-kv and seedvr2* all were — while fibo-edit* was saved by the txt2img FIBO class and z-image-controlnet* by plain ZImage. Nothing raised; the mismatch surfaced later as an unloadable checkpoint. Dispatch now goes through the registry (ConfigResolution.resolve_key), so canonical keys, aliases, HuggingFace repo ids and --base-model spellings all land on the class that owns those weights, an unrecognisable name exits with a message instead of defaulting to Flux1, and the two models with no save path (Lens, SeedVR2) say so. Every rejection also lists the models mflux-save can write, which --help does not show — it lists models that cannot be saved. A drift test fails if a model is added to AVAILABLE_MODELS without a save class. Two consequences worth noting: --model dev-controlnet-canny/dev-controlnet-upscaler/schnell-controlnet-canny now save through Flux1Controlnet (ControlNet weights included) rather than as a bare Flux.1, and mflux-save --model boogu no longer dies with a TypeError on bake_lora, which BooguImage does not accept. (#607)
  • ERNIE multi-frame latents: pack_latents indexed the VAE's temporal axis away, so anything but a single frame was silently discarded; it now fails loudly. (#577)
  • ernie-image-turbo guidance contract: the model declared supports_guidance: true while its CLI exits on any guidance other than 1.0, contradicting itself in the mflux-capabilities dump. (#578)
  • Partial Krea 2 Turbo downloads passed as complete: a cached snapshot was checked against its download patterns only when the model needed no subdirectory. Krea 2 Turbo keeps its transformer at the repo root as turbo.safetensors, so a download that fetched vae/ and text_encoder/ and then stopped reported itself complete. Hugging Face's repair download never ran, and the load died later with Missing specified weight files in <snapshot>: ['turbo.safetensors'], which reads like a corrupt cache rather than an interrupted transfer. Root-level *.safetensors patterns are now checked in the subdirectory branch too. (#577, #593)
  • Saved checkpoints loaded whatever was in the directory: mflux-save writes a model.safetensors.index.json naming every shard, and the reload globbed the directory instead of reading it. Saving -q 4 over an existing -q 8 checkpoint in the same folder left the q8 tail behind, and those stale tensors overwrote the ones just written while the metadata still reported 4. A checkpoint missing a shard the index names loaded the rest and came up short. The index now decides which shards get read, and a named shard that is not on disk raises with the filenames. Checkpoints with no index, or with a damaged one, keep loading from the directory. (#577)
  • Metadata sidecars did not restore dimensions, the negative prompt or init images: every run embeds height, width, negative_prompt and image_paths, but --config-from-metadata read none of them back, so a sidecar-only rerun of a 1536x768 generation came out at the 1024x1024 default with the negative prompt dropped — a different image on any CFG model, not just a differently sized one. The edit CLIs could not rerun a sidecar at all: --image-paths was required=True, which argparse enforces before the restore block runs, so mflux-generate-qwen-edit --config-from-metadata prior.metadata.json exited 2 demanding images the sidecar was carrying. All four keys are restored now, each deferring to the command line option by option, and --image-paths is required after the restore rather than during parsing. A sidecar's init image that does not exist on this machine now errors at parse time naming the sidecar, instead of loading the whole model first and dying on a bare FileNotFoundError. (#577, #634)
  • The upscale commands were missing from mflux-capabilities: COMMAND_PREFIXES covered mflux-generate* and mflux-concept* only, so neither mflux-upscale-controlnet nor mflux-upscale-seedvr2 appeared in the dump — which is how the --metadata bug above went unnoticed by the contract checks that exist to catch exactly that. Both are now published with full coverage, which meant adopting the build_parser() convention and declaring what their hardcoded configs cannot honour: --base-model is ignored by both, and on mflux-upscale-controlnet --negative-prompt is ignored while --model is conditional (a path or repo id loads weights, a built-in model name does nothing, since the config is always dev-controlnet-upscaler). Both commands now warn at parse time when an ignored option is passed. (#577)
  • mflux-upscale-seedvr2 --metadata never wrote the sidecar: the CLI accepted the flag and then saved without forwarding it, so the upscale ran to completion and no JSON appeared. Its sibling mflux-upscale-controlnet passes export_json_metadata on the equivalent line. (#577)
  • Ideogram 4 quantization: mflux-save -q now actually quantizes Ideogram 4. Every weight-bearing linear in the model is an Fp8Linear, which defined no to_quantized and whose components were marked skip_quantization, so -q 4 wrote an FP8 checkpoint stamped quantization_level: 4 and only the VAE was touched. Adds Fp8Linear.to_quantized, drops the skip flags, derives bits and group size from the stored shapes when rebuilding a saved checkpoint instead of assuming q8/group-64, and rebuilds quantized embeddings as embeddings rather than linears. -q 8 is 26 GB and -q 4 is 14 GB, both visually indistinguishable from FP8. (#559)

📝 Documentation

  • Ideogram 4 gated weights: Document the HF_TOKEN / hf auth login step alongside the existing note that access must be approved on the model card — authenticating is the half people miss, and without it an approved account still fails with a bare 401/403. Adds a quantization section covering mflux-save -q and loading a saved checkpoint with --model-path. (#559)

🧰 DX & Maintenance

  • Dev workflow: Makefile replaced by justfile: make <target> is gone; use just <target> instead (just install, just lint, just format, just check, just test-fast, …). Running bare just (or just --list) shows all recipes with descriptions. Semantics follow the post-#576 Makefile: uv sync installs and ruff is pinned from the pyproject.toml dev dependency. The CI lint job also lints the justfile itself via just --fmt --check, using the pinned just-setup composite action. Requires just ≥ 1.50 locally. (#590)
