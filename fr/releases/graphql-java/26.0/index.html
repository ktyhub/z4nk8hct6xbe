graphql-java v26.0

Il s'agit de la version 26.0 de graphql-java. Les points saillants sont résumés ci-dessous ; la liste complète des PR fusionnés se trouve à la fin.

⚠️ Modifications radicales

Les limites de complexité des requêtes sont désormais appliquées par défaut

La nouvelle validation QueryComplexityLimits vérifie maxDepth (100 par défaut) et maxFieldsCount (100 000 par défaut) dans le cadre de la validation standard. Les requêtes dépassant ces limites échoueront désormais avec de nouvelles erreurs de validation MaxQueryDepthExceeded / MaxQueryFieldsExceeded.

  • Définissez des limites personnalisées via GraphQLContext en utilisant QueryComplexityLimits.KEY.
  • Désactivez entièrement avec QueryComplexityLimits.NONE.

Introduit dans #4256.

Filtrage des règles de validation API modifié

Dans #4228, le prédicat de filtre de règles est passé de Predicate<Class<?>> à Predicate<OperationValidationRule> dans Validator.validateDocument(...) et ParseAndValidate.parseAndValidate(...). Les appelants filtrés par classe (par exemple rule -> rule != NoUnusedFragments.class) doivent migrer vers l'énumération (rule -> rule != OperationValidationRule.NO_UNUSED_FRAGMENTS). Les classes @Internal AbstractRule et RulesVisitor ont été supprimées.

Gestion des directives intégrées consolidée (#4229)

  • DirectiveInfo a été supprimé. Remplacer les usages : -DirectiveInfo.isGraphqlSpecifiedDirective(...) →Directives.isBuiltInDirective(...) -DirectiveInfo.GRAPHQL_SPECIFICATION_DIRECTIVES →Directives.BUILT_IN_DIRECTIVES -DirectiveInfo.GRAPHQL_SPECIFICATION_DIRECTIVE_MAP →Directives.BUILT_IN_DIRECTIVES_MAP
  • L'ordre des directives est désormais cohérent : les 7 directives intégrées apparaissent en premier, suivies des directives définies par l'utilisateur.
  • GraphQLSchema.Builder.clearDirectives() a été initialement supprimé puis ré-ajouté dans #4276 avec une nouvelle sémantique — il efface tous les additionalDirectives, mais les directives intégrées sont toujours réajoutées automatiquement au moment de la construction.

Validation d'habitabilité OneOf (#4248)

Le nouveau validateur rejette les types d'entrée OneOf qui ne peuvent pas être remplis avec une valeur finie (par exemple input A @oneOf { a: A }). Les schémas précédemment validés peuvent désormais être rejetés.

Validation de champs non nuls pour les schémas construits en code (#4194)

Les schémas créés par le code effectuent désormais la même validation de champ obsolète sur non nul que ceux créés par SDL. Les schémas s'appuyant sur l'écart peuvent désormais échouer à la validation.

GraphQLSchema.getCodeRegistry() n'est plus @Nullable (#4247)

Le type de retour a été incorrectement annoté nullable. Les appelants peuvent désormais supprimer les contrôles nuls redondants ; les outils de nullité en aval refléteront le changement.

Les annotations de nullabilité JSpecify sont largement déployées

Les vagues 2 et 3 (#4184, #4274) ainsi que de nombreux PR individuels ont annoté des centaines de classes dans graphql.analysis, graphql.execution, graphql.language, graphql.schema et d'autres avec @NullMarked/@NullUnmarked/@Nullable. Kotlin et les autres appelants sensibles aux valeurs nulles verront désormais des contrats de nullité plus stricts ; le code qui reposait sur des signatures auparavant permissives peut nécessiter un ajustement.

✨ Nouvelles fonctionnalités

  • GraphQLSchema.FastBuilder (#4197) — un générateur de schéma plus restrictif mais ~5 fois plus rapide qui réduit à la fois le temps et la mémoire pour les schémas volumineux.
  • Limites de complexité des requêtes (#4256) — garde-fous de profondeur/nombre de champs intégrés à la validation (voir les modifications importantes ci-dessus pour le côté application).
  • QueryAppliedDirective sur les opérations et les documents (#4297) — les directives appliquées au niveau des opérations/documents sont désormais exposées en tant que QueryAppliedDirective.
  • Nouveau crochet d'instrumentation pour les résultats de gestion post-exception (#4206, #4207) — observez le DataFetcherResult après que DataFetcherExceptionHandler ait mappé les exceptions aux erreurs. ChainedInstrumentation délègue correctement le nouveau hook.
  • Generic DataFetcherResult.newBuilder(T data) (#4254) — supprime le besoin de témoins de type explicites sur le modèle DataFetcherResult.<T>newResult().data(x)... commun.
  • GraphQLSchema.Builder.clearDirectives() ré-ajouté (#4276) — utile avec GraphQLSchema.transform pour réécrire les directives non intégrées ; les éléments intégrés sont toujours réajoutés.
  • toString() sur les détenteurs de directives AST (#4195).

⚡Performances

  • L'exécution incrémentielle de @defer commence plus tôt (#4174) — commence le traitement des charges utiles différées dès que le premier appel incrémentiel est détecté au lieu d'attendre la fin du résultat initial.
  • Consolidation de validation (#4228) — toutes les règles de validation des opérations s'exécutent en un seul passage OperationValidator, ce qui réduit considérablement les frais de validation.
  • Allocations réduites sur le hot path d'exécution (#4252) :
    • Async$Many.materialisedList() — remplacement de la copie ArrayList par un wrapper Arrays.asList() sans copie.
    • ResultPath.toStringValue — calcul paresseux ; la forme de chaîne n'est construite que sur le premier toString() (généralement uniquement lors du rapport d'erreurs).
    • Nouvelle surcharge GraphQLCodeRegistry.getDataFetcher(String, String, GraphQLFieldDefinition) évitant les allocations FieldCoordinates par récupération (réduction d'environ 54 Ko/opération).
  • FastBuilder pour la construction de schéma (#4197) — voir Nouvelles fonctionnalités.
  • Correction de ShallowTypeRefCollector pour résoudre également les références de type dans les arguments de directive appliqués et les définitions de valeurs d'énumération (#4288) — correctif d'exactitude permettant à FastBuilder d'être utilisé sur plus de schémas.

🐛 Autres changements notables

Exécution / récupération de données

  • Distribution de DataLoader avec plusieurs fragments @defer (#4270) — corrige un cas où les DataLoaders n'étaient pas distribués correctement lorsque plusieurs fragments différés étaient en jeu.
  • Condition de concurrence CompletionStageSubscriber (#4296) — le signal d'achèvement pourrait être perdu si un CompletionStage en vol était résolu simultanément. Fix est soutenu par de nouveaux tests de résistance jcstress.
  • PropertyDataFetcher sur les classes non publiques (#4287) — les propriétés sur les classes non publiques qui implémentent des interfaces publiques (par exemple TreeMap.Entry) sont désormais récupérées correctement sur Java 16+ en recherchant des interfaces publiques.
  • ExecutableNormalizedField respecte GraphqlFieldVisibility (#4204) — les API du jeu de sélection utilisent désormais la visibilité configurée du schéma au lieu d'aller directement au type.
  • Correction ScheduledDataLoaderRegistry "répartir tout" (#4164).
  • Délégation ChainedInstrumentation onExceptionHandled (#4207).

Visibilité du schéma/champ

  • Corrections pour les cas complexes de transformateur de visibilité de champ et de transformation de schéma lors de suppressions en cascade (#4203, #4205, #4208, #4209, #4212, #4213, #4275).
  • Régression de type nul à champs superposés corrigée (#4291).
  • GraphQLTypeCollectingVisitor traverse désormais de manière récursive les références fortes indirectes (#4213).
  • Correction de la signature de surcharge SchemaTraverser::depthFirst (#4165).

Construction / packaging / sécurité

  • Les classes modifiées par bytecode ne sont plus disponibles dans les JAR publiés (#4343) — l'annotation @Generated injectée pour les rapports de couverture fuyait dans les artefacts publiés. Les JAR contiennent désormais une sortie vierge du compilateur.
  • Détection Unicode de source de cheval de Troie/ver de verre (#4344) — le hook de pré-validation et le flux de travail CI rejettent désormais les caractères BiDi/largeur nulle/de contrôle dangereux dans la source.
  • Compatibilité Windows (#4239) — suppression des deux-points des noms de fichiers performance-results/, division du large-schema-5.graphqls surdimensionné, ajout de vérifications pré-commit + CI.

Outillage / DX

  • Limites du type getDataLoader améliorées (#4180).
  • Construire et tester sur Java 25 (#4173, #4330).
  • De nombreuses mises à jour de dépendances (Reactor, Jackson, Kotlin, Groovy, Gradle, ByteBuddy, errorprone, etc.) à travers la version.

graphql-java v26.0

This is the 26.0 release of graphql-java. Highlights are summarized below; the full list of merged PRs is at the end.

⚠️ Breaking Changes

Query complexity limits are now enforced by default

New QueryComplexityLimits validation checks maxDepth (default 100) and maxFieldsCount (default 100,000) as part of standard validation. Queries exceeding these limits will now fail with new MaxQueryDepthExceeded / MaxQueryFieldsExceeded validation errors.

  • Set custom limits via GraphQLContext using QueryComplexityLimits.KEY.
  • Disable entirely with QueryComplexityLimits.NONE.

Introduced in #4256.

Validation rule filtering API changed

In #4228 the rule-filter predicate changed from Predicate<Class<?>> to Predicate<OperationValidationRule> in Validator.validateDocument(...) and ParseAndValidate.parseAndValidate(...). Callers that filtered by class (e.g. rule -> rule != NoUnusedFragments.class) must migrate to the enum (rule -> rule != OperationValidationRule.NO_UNUSED_FRAGMENTS). The @Internal classes AbstractRule and RulesVisitor were removed.

Built-in directive handling consolidated (#4229)

  • DirectiveInfo was removed. Replace usages:
    • DirectiveInfo.isGraphqlSpecifiedDirective(...) → Directives.isBuiltInDirective(...)
    • DirectiveInfo.GRAPHQL_SPECIFICATION_DIRECTIVES → Directives.BUILT_IN_DIRECTIVES
    • DirectiveInfo.GRAPHQL_SPECIFICATION_DIRECTIVE_MAP → Directives.BUILT_IN_DIRECTIVES_MAP
  • Directive ordering is now consistent: all 7 built-in directives appear first, followed by user-defined directives.
  • GraphQLSchema.Builder.clearDirectives() was initially removed then re-added in #4276 with new semantics — it clears all additionalDirectives, but built-in directives are always re-added automatically at build time.

OneOf inhabitability validation (#4248)

New validator rejects OneOf input types that cannot be populated with a finite value (e.g. input A @oneOf { a: A }). Schemas that previously validated may now be rejected.

Non-null field validation for code-built schemas (#4194)

Code-built schemas now perform the same deprecated-on-non-null field validation as SDL-built ones. Schemas relying on the gap may now fail validation.

GraphQLSchema.getCodeRegistry() is no longer @Nullable (#4247)

The return type was incorrectly annotated nullable. Callers may now drop redundant null checks; downstream nullness tooling will reflect the change.

JSpecify nullability annotations rolled out broadly

Waves 2 and 3 (#4184, #4274) plus many individual PRs annotated hundreds of classes across graphql.analysis, graphql.execution, graphql.language, graphql.schema and others with @NullMarked/@NullUnmarked/@Nullable. Kotlin and other null-aware callers will now see stricter nullability contracts; code that relied on previously-permissive signatures may need adjustment.

✨ New Features

  • GraphQLSchema.FastBuilder (#4197) — a more restrictive but ~5× faster schema builder that reduces both time and memory for large schemas.
  • Query complexity limits (#4256) — depth/field-count guardrails baked into validation (see breaking changes above for the enforcement side).
  • QueryAppliedDirective on operations and documents (#4297) — directives applied at the operation/document level are now exposed as QueryAppliedDirectives.
  • New instrumentation hook for post-exception-handling results (#4206, #4207) — observe the DataFetcherResult after DataFetcherExceptionHandler has mapped exceptions to errors. ChainedInstrumentation delegates the new hook correctly.
  • Generic DataFetcherResult.newBuilder(T data) (#4254) — removes the need for explicit type witnesses on the common DataFetcherResult.<T>newResult().data(x)... pattern.
  • Re-added GraphQLSchema.Builder.clearDirectives() (#4276) — useful with GraphQLSchema.transform to rewrite non-built-in directives; built-ins are always re-added.
  • toString() on AST directives holders (#4195).

⚡ Performance

  • Incremental @defer execution starts earlier (#4174) — begins processing deferred payloads as soon as the first incremental call is detected instead of waiting for the initial result to complete.
  • Validation consolidation (#4228) — all operation validation rules run in a single OperationValidator pass, significantly cutting validation overhead.
  • Reduced allocations on the execution hot path (#4252):
    • Async$Many.materialisedList() — replaced ArrayList copy with a zero-copy Arrays.asList() wrapper.
    • ResultPath.toStringValue — lazy computation; the string form is only built on first toString() (typically only during error reporting).
    • New GraphQLCodeRegistry.getDataFetcher(String, String, GraphQLFieldDefinition) overload avoiding per-fetch FieldCoordinates allocations (~54 KB/op reduction).
  • FastBuilder for schema construction (#4197) — see New Features.
  • Fixed ShallowTypeRefCollector to also resolve type refs inside applied directive arguments and enum value definitions (#4288) — correctness fix enabling FastBuilder to be used on more schemas.

🐛 Other Noteworthy Changes

Execution / data fetching

  • DataLoader dispatch with multiple @defer fragments (#4270) — fixes a case where DataLoaders were not dispatched correctly when multiple deferred fragments were in play.
  • CompletionStageSubscriber race condition (#4296) — completion signal could be lost if an in-flight CompletionStage resolved concurrently. Fix is backed by new jcstress stress tests.
  • PropertyDataFetcher on non-public classes (#4287) — properties on non-public classes that implement public interfaces (e.g. TreeMap.Entry) now fetch correctly on Java 16+ by searching public interfaces.
  • ExecutableNormalizedField respects GraphqlFieldVisibility (#4204) — selection-set APIs now use the schema's configured visibility instead of going straight to the type.
  • ScheduledDataLoaderRegistry "dispatch all" fix (#4164).
  • ChainedInstrumentation onExceptionHandled delegation (#4207).

Schema / field visibility

  • Fixes for complex field-visibility transformer cases and schema transformation when deletions cascade (#4203, #4205, #4208, #4209, #4212, #4213, #4275).
  • Overlapping-fields null-type regression fixed (#4291).
  • GraphQLTypeCollectingVisitor now recursively traverses indirect strong references (#4213).
  • SchemaTraverser::depthFirst overload signature fix (#4165).

Build / packaging / security

  • Bytecode-modified classes no longer ship in published JARs (#4343) — the @Generated annotation injected for coverage reporting was leaking into published artifacts. JARs now contain pristine compiler output.
  • Trojan Source / glassworm Unicode detection (#4344) — pre-commit hook and CI workflow now reject dangerous BiDi/zero-width/control characters in source.
  • Windows compatibility (#4239) — removed colons from performance-results/ filenames, split the oversized large-schema-5.graphqls, added pre-commit + CI checks.

Tooling / DX

  • getDataLoader type bounds improved (#4180).
  • Build and test on Java 25 (#4173, #4330).
  • Many dependency updates (Reactor, Jackson, Kotlin, Groovy, Gradle, ByteBuddy, errorprone, etc.) across the release.
