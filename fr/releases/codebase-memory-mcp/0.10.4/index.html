codebase-memory-mcp v0.10.4

Une version d'installation et de diagnostic. Si v0.10.3 a refusé de s'installer ou de démarrer pour vous — en particulier sous Windows ou sur une machine sur laquelle vous avez installé cbm via un gestionnaire de paquets — c'est celui-ci qu'il vous faut.

La plupart de ce qui suit provient de personnes qui ont déposé des rapports précis et, dans plusieurs cas, ont causé le bug avant nous.

Windows : les comptes élevés n'ont pas pu s'installer ou démarrer du tout

L'exécution en tant que compte de groupe d'administrateurs signifiait que install échouait avec activation transaction I/O failed: owner-not-current-user, ou que le serveur MCP se fermait au démarrage avec rien dans le journal mais un transport fermé.

La cause était la nôtre et spécifique : nous avons comparé le propriétaire d'un fichier au SID utilisateur du jeton, mais Windows marque les objets nouvellement créés avec le SID propriétaire du jeton - qui, pour tout membre du groupe Administrateurs, est par défaut BUILTIN\Administrators. Le programme d'installation a donc créé son propre fichier intermédiaire, puis l'a refusé quelques secondes plus tard, car il appartenait à quelqu'un d'autre. Aucun processus de redémarrage ou de fermeture ne pouvait aider, car rien ne fonctionnait.

Nous acceptons désormais également les tampons SID Windows sur ce que nous créons. C'est plus restreint que "trust n'importe quel administrateur" : un fichier appartenant à un compte véritablement différent est toujours refusé. Signalé par @spam0115 et @gotspatel, et c'est très probablement également la cause du #1416 de longue date.

L'installation ne touche plus les éléments qui ne lui appartiennent pas

Deux changements pour les personnes dont nous piétinons la configuration :

Un binaire installé par mise, Homebrew, nix, asdf ou cargo est laissé seul. Auparavant, install déposait une deuxième copie dans ~/.local/bin — en observant celle gérée en fonction de l'ordre PATH — et l'ajoutait à votre fichier shell rc. Maintenant, il configure les agents et laisse le binaire et votre PATH intacts, update refuse honnêtement et nomme la commande qui fonctionnera (mise upgrade, brew upgrade), et PATH n'est modifié que lorsque nous avons effectivement placé le binaire. Rapporté par @SC-CTS.

Vous pouvez choisir quels clients sont configurés. install a écrit la configuration MCP, les agents, les compétences et les hooks pour chaque client détecté, et annuler ceux que vous ne vouliez pas était inutile car la prochaine installation les a recréés. --clients=claude,codex le restreint désormais, et --clients répertorie lui-même tous les jetons pris en charge. Rapporté par @PsyTech-Rob.

Erreurs qui vous indiquent ce qui s'est réellement passé

Trois correctifs d'affilée ici, tous issus de la même plainte : nos messages étaient certainement faux.

  • Un refus d'activation n'indique plus des preuves qu'il n'affiche pas. v0.10.3 a correctement arrêté de blâmer les "sessions CBM actives" pour les échecs qu'aucune session n'a provoqués, mais vous a ensuite demandé de vérifier les erreurs qui n'ont jamais été imprimées. Il nomme désormais le répertoire et la règle qui a refusé.
  • Un serveur qui ne peut pas démarrer explique pourquoi. Les échecs de démarrage du chemin Client ont écrit uniquement sur stderr, ce qu'aucun MCP client ne fait apparaître — donc un refus spécifique et nommable vous est parvenu sous le nom de "transport fermé de manière inattendue". Ces échecs arrivent désormais sous la forme d’une erreur JSON-RPC portant la raison.
  • L'écouteur de l'interface utilisateur peut être désactivé sans modifier JSON. ui_enabled régit un port HTTP de bouclage, et la seule façon de le désactiver était de modifier manuellement config.json ; il était invisible pour config list et rejeté par config set. Lui et ui_port sont désormais des clés de configuration de première classe. Rapporté par @PsyTech-Rob, qui a passé deux sessions de débogage à trouver le commutateur.

Réparation du Codex, OpenCode et des fichiers de configuration

  • Une installation dupliquée n'interrompt plus le Codex de manière permanente (@astandrik). Une affectation de hook en ligne détenue est réconciliée dans le bloc canonique au lieu d'être ignorée et rajoutée à côté ; les entrées de hook étrangères sont préservées intactes et le TOML véritablement ambigu est refusé sans aucune modification du fichier.
  • ~~Les installations d'OpenCode atterrissent dans le fichier qu'OpenCode lit réellement (@iandol).~~ Correction (2026-08-14) : ce n'est qu'à moitié vrai et nous n'aurions pas dû le prétendre d'emblée. Le ciblage est corrigé — nous écrivons maintenant celui des opencode.json / opencode.jsonc qui existe déjà, au lieu de toujours créer un fichier .json qu'OpenCode ignore. Mais l'écriture elle-même échoue toujours sur v0.10.4 avec error: agent_config agent=OpenCode op=mcp_install, signalé à la fois sous Linux et Windows. Suivi en #1630. Il s'agit de la deuxième version en cours d'exécution dans laquelle nous décrivons ce correctif comme étant complet ; désolé, et merci aux journalistes qui n'arrêtaient pas de dire que ce n'était pas le cas.
  • Un marqueur orphelin que nous avons écrit se guérit tout seul. Une installation antérieure pouvait laisser un marqueur de fermeture # <<< sans ouvreur, après quoi chaque installation échouait complètement avec ce client. La suppression supprime désormais la ligne parasite. Une écriture refuse toujours en cas de déséquilibre — avec un seul marqueur, il n'y a pas de région défendable à remplacer.

Exactitude des requêtes et prise en charge de la plateforme

  • OPTIONAL MATCH a arrêté de supprimer silencieusement des lignes (@SEPURI-SAI-KRISHNA). Une fois le tampon de saut saturé, les lignes sans correspondance – exactement ce que WHERE x IS NULL existe pour faire surface – ont été supprimées. Pas de crash, pas d'erreur de mémoire : moins de résultats, sans rien indiquer que la réponse était incomplète.
  • FreeBSD résout son propre chemin d'exécutable (@PR9000), dont dépendent les vérifications d'installation et de propriété, ainsi qu'un correctif de build pour les plates-formes en dehors des trois principales.

Sécurité

Le pipeline de versions épingle et vérifie désormais les outils externes qu'il télécharge avant de les exécuter, plutôt que de trusting quel que soit le projet en amont publié au moment de la construction. La vérification couvre toutes les plateformes sur lesquelles la tâche peut s'exécuter, à partir d'une seule référence épinglée.

Rapporté par Andrew Hundt (#1245).

Fiabilité

Les générations de sous-processus survivent à une machine occupée. v0.10.3 a commencé à réessayer un spawn que le noyau a refusé avec "essayer à nouveau", mais seulement pendant environ 30 ms - assez pour un creux momentané, pas pour une machine qui reste affamée de processus pendant des centaines de millisecondes d'affilée, ce qui est exactement le moment où cela se produit. La nouvelle tentative recule désormais de façon exponentielle jusqu'à environ une demi-seconde avant d'abandonner. Une machine véritablement épuisée échoue toujours rapidement plutôt que de se bloquer, et les erreurs réelles (un binaire manquant, un refus d'autorisation) échouent immédiatement comme avant.

Et le pipeline de versions ne publie plus son entrée de registre avant que la version ne soit publique – le bug qui a fait échouer la propre étape de registre de v0.10.3 avec un 404 contre ses propres actifs.

Mise à niveau

  • Installations binaires : téléchargez ci-dessous ou réexécutez install.sh / install.ps1.
  • Gestionnaires de packages : mettez à jour via eux comme d'habitude — cbm laissera désormais ce binaire tranquille.
  • npm / PyPI : comme d'habitude.
  • Aucune migration d'index, de cache ou de configuration.

Contributeurs

Le code de cette version provient de :

  • @astandrik — Réconciliation des hooks du Codex, avec une gestion fermée en cas d'échec qui laisse une configuration ambiguë identique à l'octet plutôt que de deviner
  • @PR9000 (Pedro Ramos) — résolution native du chemin d'exécution de FreeBSD, plus un correctif de build pour les plates-formes en dehors des trois principales
  • @SEPURI-SAI-KRISHNA — le correctif de perte de lignes OPTIONAL MATCH, y compris l'analyse qui séparait "dans les limites" de "correct"
  • Andrew Hundt — le durcissement du pipeline de libération ci-dessus, co-écrit

Et ces rapports ont révélé des bugs que nous n'aurions pas pu trouver nous-mêmes, plusieurs d'entre eux étant causés par le journaliste avant que nous examinions :

@spam0115 et @gotspatel (comptes Windows élevés) · @SC-CTS (installations du gestionnaire de packages) · @PsyTech-Rob (quatre résultats distincts dans un cycle d'installation) · @listepo (les diagnostics qui ont identifié un refus que nous avions deviné) · @iandol (ciblage de configuration OpenCode)

Merci, en particulier à ceux d'entre vous qui ont continué à signaler des problèmes d'installation au cours de plusieurs versions.

codebase-memory-mcp v0.10.4

codebase-memory-mcp v0.10.4

An install-and-diagnostics release. If v0.10.3 refused to install or start for you — particularly on Windows, or on a machine where you installed cbm through a package manager — this is the one to take.

Most of what follows came from people who filed precise reports and, in several cases, root-caused the bug before we did.

Windows: elevated accounts could not install or start at all

Running as an Administrators-group account meant install failed with activation transaction I/O failed: owner-not-current-user, or the MCP server exited during startup with nothing in the log but a closed transport.

The cause was ours and specific: we compared a file's owner against the token's user SID, but Windows stamps newly-created objects with the token's owner SID — which for any member of the Administrators group defaults to BUILTIN\Administrators. So the installer created its own staging file and then refused it, seconds later, as belonging to someone else. No amount of rebooting or closing processes could help, because nothing was running.

We now also accept the SID Windows actually stamps on what we create. This is narrower than "trust any administrator": a file owned by a genuinely different account is still refused. Reported by @spam0115 and @gotspatel, and it is very likely the cause of the long-running #1416 as well.

Installing no longer touches things it doesn't own

Two changes for people whose setup we were trampling:

A binary installed by mise, Homebrew, nix, asdf or cargo is left alone. Previously install dropped a second copy into ~/.local/bin — shadowing the managed one depending on PATH order — and appended to your shell rc file. Now it configures the agents and leaves the binary and your PATH untouched, update refuses honestly and names the command that will work (mise upgrade, brew upgrade), and PATH is only modified when we actually placed the binary. Reported by @SC-CTS.

You can choose which clients get configured. install wrote MCP config, agents, skills and hooks for every detected client, and reverting the ones you didn't want was pointless because the next install recreated them. --clients=claude,codex now restricts it, and --clients on its own lists every supported token. Reported by @PsyTech-Rob.

Errors that tell you what actually happened

Three fixes in a row here, all from the same complaint: our messages were confidently wrong.

  • An activation refusal no longer points at evidence it doesn't show. v0.10.3 correctly stopped blaming "active CBM sessions" for failures no session caused, but then told you to check errors that were never printed. It now names the directory and the rule that refused.
  • A server that cannot start says why. Client-path startup failures wrote to stderr only, which no MCP client surfaces — so a specific, nameable refusal reached you as "transport closed unexpectedly". Those failures now arrive as a JSON-RPC error carrying the reason.
  • The UI listener can be turned off without editing JSON. ui_enabled governs a loopback HTTP port, and the only way to disable it was hand-editing config.json; it was invisible to config list and rejected by config set. Both it and ui_port are now first-class config keys. Reported by @PsyTech-Rob, who spent two debugging sessions finding the switch.

Codex, OpenCode and config-file repair

  • A duplicated install no longer breaks Codex permanently (@astandrik). An owned inline hook assignment is reconciled into the canonical block instead of being ignored and re-added alongside; foreign hook entries are preserved untouched, and genuinely ambiguous TOML is refused without modifying the file at all.
  • ~~OpenCode installs land in the file OpenCode actually reads (@iandol).~~ Correction (2026-08-14): this is only half true and we should not have claimed it outright. The targeting is fixed — we now write whichever of opencode.json / opencode.jsonc already exists, instead of always creating a .json file OpenCode ignores. But the write itself still fails on v0.10.4 with error: agent_config agent=OpenCode op=mcp_install, reported on both Linux and Windows. Tracked in #1630. This is the second release running in which we have described this fix as complete; sorry, and thank you to the reporters who kept saying it was not.
  • An orphan marker we wrote heals itself. An earlier install could leave a closing # <<< marker with no opener, after which every install failed that client outright. Removal now strips the stray line. A write still refuses on an imbalance — with one marker there is no defensible region to replace.

Query correctness and platform support

  • OPTIONAL MATCH stopped silently dropping rows (@SEPURI-SAI-KRISHNA). Once the hop buffer saturated, the no-match rows — exactly what WHERE x IS NULL exists to surface — were discarded. Not a crash, not a memory error: quietly fewer results, with nothing to indicate the answer was incomplete.
  • FreeBSD resolves its own executable path (@PR9000), which the install and ownership checks depend on, plus a build fix for platforms outside the main three.

Security

The release pipeline now pins and verifies the external tooling it downloads before executing any of it, rather than trusting whatever the upstream project publishes at build time. Verification covers every platform the job may run on, from a single pinned reference.

Reported by Andrew Hundt (#1245).

Reliability

Subprocess spawns survive a busy machine. v0.10.3 started retrying a spawn the kernel refused with "try again", but only for about 30ms — enough for a momentary dip, not for a machine that stays process-starved for hundreds of milliseconds at a stretch, which is exactly when it happens. The retry now backs off exponentially to roughly half a second before giving up. A genuinely exhausted machine still fails fast rather than hanging, and real errors — a missing binary, a permission denial — fail immediately as before.

And the release pipeline no longer publishes its registry entry before the release is public — the bug that made v0.10.3's own registry step fail with a 404 against its own assets.

Upgrade

  • Binary installs: download below, or re-run install.sh / install.ps1.
  • Package managers: update through them as usual — cbm will now leave that binary alone.
  • npm / PyPI: as usual.
  • No index, cache, or config migration.

Contributors

Code in this release came from:

  • @astandrik — Codex hook reconciliation, with fail-closed handling that leaves an ambiguous config byte-identical rather than guessing
  • @PR9000 (Pedro Ramos) — native FreeBSD executable-path resolution, plus a build fix for platforms outside the main three
  • @SEPURI-SAI-KRISHNA — the OPTIONAL MATCH row-loss fix, including the analysis that separated "in bounds" from "correct"
  • Andrew Hundt — the release-pipeline hardening above, co-authored

And these reports found bugs we could not have found ourselves, several of them root-caused by the reporter before we looked:

@spam0115 and @gotspatel (Windows elevated accounts) · @SC-CTS (package-manager installs) · @PsyTech-Rob (four separate findings in one install cycle) · @listepo (the diagnostics that identified a refusal we had been guessing at) · @iandol (OpenCode config targeting)

Thank you — particularly to those of you who kept reporting through several releases of install trouble.
