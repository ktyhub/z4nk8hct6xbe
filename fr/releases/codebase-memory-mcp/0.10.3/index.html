codebase-memory-mcp v0.10.3

codebase-memory-mcp v0.10.3

Une version contenant uniquement des correctifs, et la plupart sont arrivés sous forme de travail terminé de la communauté : six demandes d'extraction contribuées se trouvent ici, ainsi que des réparations pour deux régressions que nous avons nous-mêmes expédiées dans v0.10.2.

Deux choses à savoir avant de procéder à la mise à niveau. Si vous exécutez plusieurs MCP client sur le même projet, cette version corrige un bogue qui pourrait détruire silencieusement un index sain — commencez par la première section. Et si l'installation ou la mise à jour a échoué pour vous, trois causes distinctes sont corrigées ici : une règle d'autorisation qui refusait les répertoires personnels ordinaires, un message d'erreur signalant une raison totalement erronée et le Codex perdant votre répertoire de cache. Plusieurs d’entre eux ont échoué en silence ou ont blâmé la mauvaise chose, c’est pourquoi ils ont survécu à plusieurs versions.

Les instances simultanées ne mettent plus en quarantaine les bases de données des autres

Le pire bug de cette version, corrigé par @LynxBay. Lorsque deux instances CBM s'affrontaient sur le même projet – deux éditeurs, un éditeur plus un appel CLI, un démon et une session parasite – le perdant de la course aux verrous pouvait conclure que la base de données était corrompue et la mettre en quarantaine : renommée, reconstruite à partir de zéro, des heures d'indexation avaient disparu. La base de données était saine ; le contrôle d'intégrité n'a tout simplement pas pu distinguer « endommagé » de « occupé » (#1206).

Le même contrôle présentait également le point mort inverse : une base de données avec des pages véritablement déchirées était réussie tant que sa comptabilité de niveau supérieur semblait correcte, de sorte que les dommages réels passaient inaperçus jusqu'à ce que les requêtes se comportent mal (#1037).

L’intégrité rend désormais un verdict à trois. Seules les quarantaines de corruption confirmées ; une course au verrouillage indique "le projet est occupé ; réessayez après l'indexation" et laisse les données seules ; et un quick_check profond détecte les dommages au niveau de la page que la sonde peu profonde a manqués. Les deux directions effectuent des tests de régression.

Déterminisme graphique, deux fois

Deux contributions de @Studnicky mettent fin à deux sources de longue date de dérive d'exécution en exécution : le comportement "même dépôt, nombre de bords légèrement différent" suivi dans nos problèmes connus depuis le 0.9.1 RC :

  • Lorsque le même arc logique est produit deux fois avec des attributs différents (un appel résolu par LSP et une correspondance textuelle, par exemple), le survivant était celui arrivé en dernier — une fonction de planification des threads. La fusion est désormais un ordre total : une confiance plus élevée l’emporte, les liens se brisent de manière déterministe et le résultat est indépendant de l’ordre d’arrivée par construction.
  • La collection de candidats CONFIGURES n'a rien trié avant d'appliquer son plafond, de sorte que les candidats qui ont survécu dépendent de l'ordre de fusion des travailleurs. Les candidats sont désormais classés d'abord par une clé de contenu pur - notamment pas par identifiant de nœud, qui semble stable mais est lui-même distribué dans l'ordre de fusion.

Windows : fichiers démon créés avec une ACL vide

@Kiborgik en a diagnostiqué et corrigé un problème subtil (#1351) : le répertoire privé du démon combinait une DACL protégée avec un ACE non héritable, ce qui sous Windows signifie que les enfants n'héritent de rien — chaque fichier créé à l'intérieur est né avec une ACL vide et illisible même par son propriétaire. Les répertoires comportent désormais un ACE réservé au propriétaire et pouvant être hérité, de sorte que la posture de sécurité stricte est conservée et que les fichiers fonctionnent réellement. Un correctif complémentaire du même contributeur a fermé un piège dans lequel une machine nommée comme son utilisateur accordait des autorisations à un principal vide ; le test sur une machine non jointe à un domaine a révélé le piège de l'image miroir, de sorte que nos outils de construction identifient désormais le compte par SID et arrêtent complètement de résoudre les noms.

Réparations pour deux régressions v0.10.2

Les deux ont été signalés en quelques heures – merci pour le signal rapide.

  • update --ui a cessé de fonctionner (#1544, @ehendrix23). v0.10.2 a supprimé le sélecteur d'interface utilisateur/standard obsolète et les indicateurs qui le pilotaient, de sorte qu'une commande vivant dans les scripts et la mémoire musculaire est devenue une erreur grave. Les deux drapeaux sont à nouveau acceptés – ils ne font rien, dites-le une fois, et les drapeaux véritablement inconnus échouent toujours.
  • L'extension Pi générée a complètement cassé Pi (#1550, @musichen). Pi charge une extension en appelant son exportation par défaut ; la nôtre a exporté une fonction nommée à la place, et une extension Pi qui ne parvient pas à se charger supprime toutes les commandes pi, y compris pi doctor. L'extension exporte désormais par défaut son usine. Corrigé indépendamment par @musichen et @henri-edh également, dont la description plus précise du chargeur de Pi est le commentaire maintenant dans notre source.

La sortie structurée arrête de laisser tomber les preuves

trace_path(include_evidence: true) a promis des colonnes strategy et confidence par saut et les a livrées – au format arborescent uniquement. Avec format: "json", les deux champs ont disparu silencieusement, ce qui a touché exactement les appelants les plus susceptibles de les vouloir : ceux qui consomment la sortie structurée par programme (#1542, @asemraza). Le chemin JSON contient désormais les deux champs avec la même sémantique, des valeurs nulles se trouvant là où le format arborescent imprime -.

Les générations de sous-processus survivent à une machine occupée

La poursuite d'un flocon de CI a révélé une véritable lacune de robustesse : lorsque le noyau refuse l'apparition d'un processus avec "réessayer" - une table de processus momentanément pleine sur une machine chargée - cbm l'a traité comme un échec permanent. Une sonde git ou un serveur LSP refuserait de démarrer pour une raison invisible pour l'utilisateur. Les échecs d'apparition transitoires réessayent désormais brièvement ; les erreurs réelles (binaires manquants, autorisations) échouent toujours immédiatement avec une sémantique inchangée.

Installation et activation : le refus sur lequel personne ne pouvait agir

Suivi du #1537 (@listepo), et il s'est avéré qu'il s'agissait de deux défauts empilés l'un sur l'autre.

Le démon a refusé de s'exécuter lorsqu'un ancêtre de son répertoire de cache était accessible en écriture en groupe - la même règle que nous avons supprimée du côté de l'installateur dans v0.10.2, dans la vérification des frères et sœurs couverte par cette décision, mais qui n'a jamais été modifiée. Un ~ ou ~/.cache inscriptible en groupe est ordinaire (WSL2 est livré en 0775, ainsi que plusieurs squelettes de distribution et toute machine avec un groupe principal partagé), donc pour ces utilisateurs, le démon était définitivement inutilisable, sans rien à fermer et rien qu'un redémarrage ne corrigerait. Les ancêtres inscriptibles dans le monde entier sont toujours refusés - tout utilisateur local peut échanger un composant de chemin - et le répertoire privé lui-même est toujours forcé d'être réservé au propriétaire, ce qui rend l'admission de l'ancêtre sûre. En dessous de cela, le message d'erreur inventait sa propre preuve : le chemin de refus ne définissait aucun code d'erreur, donc le rapport se contentait d'imprimer ce que errno contenait et remettait au journaliste ENOENT une décision d'autorisation. Ils sont partis à la recherche d'un dossier manquant qui était là tout le temps. Le message nomme désormais le répertoire et la règle qui l'a refusé.

Également dans ce domaine : le gardien d'activation a signalé chaque refus comme "les sessions CBM actives ne pouvaient pas être arrêtées", y compris les échecs où rien ne fonctionnait du tout. Ce sont maintenant des messages séparés, le second dit clairement que rien n'a besoin d'être fermé, et aucun des deux remèdes ne suppose qu'un binaire codebase-memory-mcp est toujours sur PATH – un conseil qui était inutilisable exactement au moment où il a été imprimé, juste après uninstall.

Également corrigé

  • Le Codex n'a vu aucun outil CBM lorsque CBM_CACHE_DIR a été défini (#1562, @anton-matosov). Le Codex transmet uniquement les variables explicitement répertoriées dans un sous-processus MCP, de sorte que le serveur qu'il a généré lit le cache par défaut pendant que le démon utilisait celui configuré ; ils n'étaient pas d'accord et la connexion s'est fermée lors de l'initialisation. La configuration générée transmet désormais la variable.
  • Le fichier de compétences installé n'a pas pu être chargé dans les lecteurs stricts YAML (#1554, @xezzon). Son description contenait Triggers on: sans guillemets, et un espace deux-points dans un scalaire YAML sans guillemets signifie « mappage imbriqué » — les analyseurs ont donc rejeté l'intégralité du document et la compétence n'a jamais été chargée en silence.
  • search_code a renvoyé un limit négatif comme nombre de résultats (#1511, correctif par @lukiod), qui est lu à un agent comme une réponse plutôt que comme un argument rejeté.
  • ~~Les installations OpenCode ont été placées dans le mauvais fichier (@iandol).~~ Correction : cela a été répertorié ici par erreur. Le correctif a fusionné quelques heures après la suppression de la balise v0.10.3, il n'est donc pas dans cette version — il est livré dans v0.10.4. Si votre configuration OpenCode est un fichier .jsonc, la mise à niveau vers v0.10.3 n'aura pas aidé, et nous sommes désolés pour le temps perdu.
  • Les archives de version sont validées avant l'extraction (#1510, @cyphercodes) : un ensemble de membres exact, avec des membres liés symboliquement refusés d'emblée.

Mise à niveau

  • Installations binaires : téléchargez ci-dessous ou réexécutez install.sh / install.ps1 — la réexécution du programme d'installation est la mise à jour.
  • npm / PyPI : mettez à jour via votre gestionnaire de packages comme d'habitude.
  • Aucune migration d'index, de cache ou de configuration.

codebase-memory-mcp v0.10.3

codebase-memory-mcp v0.10.3

A fixes-only release, and most of it arrived as finished work from the community: six contributed pull requests are in here, alongside repairs for two regressions we shipped ourselves in v0.10.2.

Two things worth knowing before you upgrade. If you run more than one MCP client against the same project, this release closes a bug that could silently destroy a healthy index — start with the first section. And if installing or updating has been failing for you, three separate causes are fixed here: a permission rule that refused ordinary home directories, an error message that reported the wrong reason entirely, and Codex losing your cache directory. Several of those failed silently or blamed the wrong thing, which is why they survived multiple releases.

Concurrent instances no longer quarantine each other's databases

The worst bug in this release, fixed by @LynxBay. When two cbm instances raced on the same project — two editors, an editor plus a CLI call, a daemon and a stray session — the loser of the lock race could conclude the database was corrupt and quarantine it: renamed away, rebuilt from scratch, hours of indexing gone. The database was healthy; the integrity check just couldn't tell "damaged" from "busy" (#1206).

The same check had the opposite blind spot too: a database with genuinely torn pages passed as long as its top-level bookkeeping looked right, so real damage went unnoticed until queries misbehaved (#1037).

Integrity now returns a three-way verdict. Only confirmed corruption quarantines; a lock race says "project is busy; retry after indexing" and leaves the data alone; and a deep quick_check catches page-level damage the shallow probe missed. Both directions carry regression tests.

Graph determinism, twice

Two contributions from @Studnicky close two long-standing sources of run-to-run drift — the "same repo, slightly different edge counts" behavior tracked in our known issues since the 0.9.1 RC:

  • When the same logical edge is produced twice with different attributes (an LSP-resolved call and a textual match, say), the survivor was whichever arrived last — a function of thread scheduling. The merge is now a total order: higher confidence wins, ties break deterministically, and the outcome is independent of arrival order by construction.
  • CONFIGURES candidate collection sorted nothing before applying its cap, so which candidates survived depended on worker merge order. Candidates are now ordered by a pure content key first — notably not by node id, which looks stable but is itself handed out in merge order.

Windows: daemon files created with an empty ACL

@Kiborgik diagnosed and fixed a subtle one (#1351): the daemon's private directory combined a protected DACL with a non-inheritable ACE, which on Windows means children inherit nothing — every file created inside was born with an empty ACL and unreadable even by its owner. Directories now carry a properly inheritable owner-only ACE, so the strict security posture is kept and the files actually work. A companion fix from the same contributor closed a trap where a machine named like its user granted permissions to an empty principal; testing that on a non-domain-joined machine surfaced the mirror-image trap, so our build tooling now identifies the account by SID and stops resolving names altogether.

Repairs for two v0.10.2 regressions

Both reported within hours — thank you for the fast signal.

  • update --ui stopped working (#1544, @ehendrix23). v0.10.2 removed the obsolete ui/standard chooser and the flags that drove it, so a command living in scripts and muscle memory became a hard error. Both flags are accepted again — they do nothing, say so once, and genuinely unknown flags still fail.
  • The generated Pi extension broke Pi entirely (#1550, @musichen). Pi loads an extension by calling its default export; ours exported a named function instead, and a Pi extension that fails to load takes every pi command down with it, pi doctor included. The extension now default-exports its factory. Fixed independently by @musichen and @henri-edh as well, whose sharper description of Pi's loader is the comment now in our source.

Structured output stops dropping evidence

trace_path(include_evidence: true) promised per-hop strategy and confidence columns, and delivered them — in tree format only. With format: "json" both fields silently vanished, which hit exactly the callers most likely to want them: the ones consuming structured output programmatically (#1542, @asemraza). The JSON path now carries both fields with the same semantics, nulls standing where the tree format prints -.

Subprocess spawns survive a busy machine

Chasing a CI flake uncovered a real robustness gap: when the kernel refuses a process spawn with "try again" — a momentarily full process table on a loaded machine — cbm treated it as a permanent failure. A git probe or LSP server would refuse to start for a reason invisible to the user. Transient spawn failures now retry briefly; real errors (missing binaries, permissions) still fail immediately with unchanged semantics.

Install and activation: the refusal nobody could act on

Follow-up to #1537 (@listepo), and it turned out to be two defects stacked on each other.

The daemon refused to run when any ancestor of its cache directory was group-writable — the same rule we removed on the installer side in v0.10.2, in the sibling check that decision covers but that never got changed. A group-writable ~ or ~/.cache is ordinary (WSL2 ships 0775, so do several distro skeletons and any machine with a shared primary group), so for those users the daemon was permanently unusable, with nothing to close and nothing a reboot would fix. World-writable ancestors are still refused — any local user could swap a path component — and the private directory itself is still forced to owner-only, which is what makes admitting the ancestor safe.

Underneath that, the error message was inventing its own evidence: the refusal path set no error code, so the reporting fell back to printing whatever errno happened to hold, and handed the reporter ENOENT for a permission decision. They went looking for a missing file that was there the whole time. The message now names the directory and the rule that refused it.

Also in this area: the activation guard reported every refusal as "active CBM sessions could not be stopped", including failures where nothing is running at all. Those are now separate messages, the second says plainly that nothing needs closing, and neither remedy assumes a codebase-memory-mcp binary is still on PATH — advice that was unusable at exactly the moment it printed, right after uninstall.

Also fixed

  • Codex saw no cbm tools when CBM_CACHE_DIR was set (#1562, @anton-matosov). Codex passes only explicitly-listed variables into an MCP subprocess, so the server it spawned read the default cache while the daemon used the configured one; they disagreed and the connection closed during initialization. The generated config now forwards the variable.
  • The installed skill file failed to load in strict YAML readers (#1554, @xezzon). Its description contained Triggers on: unquoted, and a colon-space in an unquoted YAML scalar means "nested mapping" — so parsers rejected the whole document and the skill silently never loaded.
  • search_code echoed a negative limit back as the result count (#1511, fix by @lukiod), which reads to an agent as an answer rather than a rejected argument.
  • ~~OpenCode installs went into the wrong file (@iandol).~~ Correction: this was listed here in error. The fix merged a few hours after the v0.10.3 tag was cut, so it is not in this release — it ships in v0.10.4. If your OpenCode config is a .jsonc file, upgrading to v0.10.3 will not have helped, and we are sorry for the wasted time.
  • Release archives are validated before extraction (#1510, @cyphercodes): an exact member set, with symlinked members refused outright.

Upgrade

  • Binary installs: download below, or re-run install.sh / install.ps1 — re-running the installer is the update.
  • npm / PyPI: update through your package manager as usual.
  • No index, cache, or config migration.
