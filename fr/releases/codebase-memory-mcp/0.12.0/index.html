codebase-memory-mcp v0.12.0

#v0.12.0

Découvrez CBM Lens et un graphique de code qui lit votre documentation.

v0.12.0 est la plus grande version de codebase-memory-mcp à ce jour : 231 demandes d'extraction fusionnées depuis v0.11.0, dont 40 provenant de la communauté.

Quatre titres le définissent.

  1. CBM Lens Beta : le graphe de code, pour les humains. Jusqu'à présent, le pouvoir du graphe n'atteignait les gens qu'à travers leurs agents. Lens est notre nouvelle interface humaine. Il vous apporte directement le graphique de connaissances du code. Il est livré dans le binaire que vous exécutez déjà et écoute uniquement en boucle. Il met côte à côte la source, le graphique, l'architecture, la couverture de l'index et un assistant local de navigateur, et chaque fait affiché indique d'où il vient. Lens est construit sur le travail de @BernhardJackiewicz, qui rejoint désormais le projet pour en être propriétaire.

  2. La documentation rejoint le graphe. Jusqu'à présent, le graphe s'arrêtait là où le code s'arrêtait. Désormais, les commentaires de documents, les documents Markdown, reStructuredText, AsciiDoc et PDF, les enregistrements de décisions d'architecture, les diagrammes et les spécifications OpenAPI en font partie. Chacun est lié aux fonctions, types et fichiers dont il parle. Un agent peut désormais parcourir votre documentation et atterrir sur le code exact décrit par une page, puis revenir d'une fonction à chaque page qui l'explique. Vous aussi, à Lens. La liaison est stricte de par sa conception : une référence ne devient une arête que lorsqu'elle nomme exactement une définition. Les familles de liens qui n'ont pas encore effacé leur barre de précision sont comptées et rapportées, jamais devinées dans le graphique.

  3. Smart CI : le graphique sélectionne les tests. detect_changes peut désormais indiquer sur quels tests un changement peut affecter. Il amorce le graphique à partir du diff, parcourt tout ce qui dépend du code modifié et nomme les tests à la fin de ces chemins, chacun avec sa raison. Lorsque les preuves sont manquantes ou douteuses, il répond « tout exécuter » et explique pourquoi ; il ne se rétrécit jamais silencieusement. Le propre CI de codebase-memory-mcp est le premier utilisateur : les demandes d'extraction exécutent uniquement les pistes de test touchées par leurs modifications, et la sélection de test du graphique s'exécute à côté de chaque PR.

  4. Infrastructure sous forme de code dans le graphique. Les manifestes Kubernetes, les graphiques Helm, les CD Flux et Argo, les fichiers Compose, les fichiers Docker et les scripts, les Makefiles et les tâches CI qui les déploient sont désormais liés. Un service peut être suivi via sa charge de travail, son image et son fichier Docker jusqu'au programme exécuté par le conteneur.

Le graphique de code lui-même est également devenu plus net :

  • Les typesdefs, les macros et les énumérateurs C ont leurs propres identités.
  • Les lancements de processus deviennent des bords SPAWNS.
  • Les correctifs de résolution couvrent C#, C++, TypeScript, Python, PHP, Rust et Go.

Mise à niveau ? Le premier index de chaque projet existant après la mise à niveau est une reconstruction complète, une seule fois. Les détails sont dans [Notes de mise à niveau] (#upgrade-notes). Quelques identités et valeurs par défaut ont également changé ; voir [Modifications avec rupture](#changements avec rupture).

Il explore un projet par le fichier que vous lisez ou le code que vous marquez, par quartier graphique, et par architecture, itinéraires et points chauds. Il explique également la couverture de l'index, modifie l'enregistrement de décision d'architecture du projet et répond aux questions sur votre sélection avec un modèle qui s'exécute dans votre navigateur. Il est intégré au binaire : codebase-memory-mcp --ui=true (#2068).
  • La documentation rejoint le graphique.
    • Les références Doc-commentaires deviennent des arêtes MENTIONS depuis la définition documentée jusqu'au code qu'elles nomment. Neuf langages : C#, Go, Java, Kotlin, Rust, Perl, TypeScript/JavaScript, PHP et C (#2550, #2593).

  • Les décisions architecturales deviennent des nœuds. Les fichiers ADR deviennent des nœuds ADR portant leur statut, leur date, leurs décideurs et la décision elle-même. Un enregistrement qui dit « Remplace ADR-3 » obtient un avantage SUPERSEDES (#2551).
  • Les diagrammes et les spécifications du API entrent dans le graphique.
    • Les diagrammes Mermaid, PlantUML, Graphviz, D2, draw.io et Excalidraw deviennent des nœuds Diagram et DiagramElement reliés par des bords DIAGRAM_ARROW, qu'ils soient intégrés dans un document ou autonomes.
    • Chaque opération OpenAPI/Swagger devient un nœud Route avec la même identité que l'itinéraire enregistré par votre code (#2593).
  • Smart CI, piloté par le graphique.
    • detect_changes avec scope: "tests" répond quels tests un changement peut atteindre et pourquoi. Les preuves incomplètes deviennent une réponse « tout exécuter » qui donne sa raison (#2458).
    • Les nouveaux paramètres de parcours edge_types, fixpoint et via exposent le même parcours de dépendances pour n'importe quel référentiel (#2458).
  • Du service au code. trace_path en mode run parcourt Service → charge de travail → Image → Dockerfile → programme, ainsi que l'environnement du conteneur. Un mode deploy suit ce qui déploie quoi, et un mode topology quoi fait référence à quoi (#2597).
  • Un graphique de code plus net.
    • C et C++ obtiennent des nœuds typedef, des identités distinctes de macro et d'énumérateur et l'accès aux membres résolus via le type de l'objet (#2543, #2458).

    • Les lancements de processus deviennent des bords SPAWNS dans environ 30 langues (#2458).
    • Les commentaires des documents sont capturés en entier : la capture Go full-doc est passée de 35 % à 99.999% et C# de 10 % à 99.8% (#2459).
  • Les index longs survivent aux délais client.
    • Passez index_repository(async: true) pour démarrer un index dans le démon et reprendre le contrôle immédiatement, puis interrogez avec status: true (#2357).
    • index_status vous indique désormais si un projet est réellement regardé, et pourquoi pas s'il ne l'est pas (#2348).
  • Observé vs possible. ingest_traces stocke désormais réellement les chemins d'appel d'exécution que vous lui envoyez. Lens marque les sauts qui ont réellement été exécutés (#2068).

Objectif CBM bêta (#2068)

Les outils MCP sont l'interface de l'agent avec le graphique. CBM Lens Beta est à vous : notre tentative d'apporter la puissance du graphe de connaissances du code aux humains. Il remplace l'interface utilisateur graphique précédente et est intégré au binaire :

codebase-memory-mcp --ui=true --port=9749
  • Explorer : suit le fichier actuel ou la source marquée, avec ses dépendances directes et un résumé de l'impact au niveau du fichier à partir du graphique et des preuves Git locales.
  • Galaxy : recherchez des nœuds, des fichiers et des dossiers, puis développez les relations entrantes ou sortantes par profondeur et type de bord.
  • Architecture : la carte du référentiel, les itinéraires, les hotspots, la structure et le comportement du système.
  • Couverture et système : ce que l'index a manqué et pourquoi, ainsi que l'état du démon, les index, les diagnostics et la configuration MCP.
  • ADR : éditez le document de décision du projet dans le navigateur, partagé avec manage_adr.
  • Ajouter un index de projet (Alt+P) : choisissez un référentiel local, nommez-le et suivez la progression du démon.
  • Chat local : renseignez-vous sur le code que vous avez sélectionné. L'inférence s'exécute dans votre navigateur. Les poids des modèles ne sont pas regroupés ; ils téléchargent depuis Hugging Face uniquement lorsque vous activez un modèle.
  • Preuve d'exécution : les chemins d'appel envoyés via ingest_traces sont stockés et Lens marque les sauts réellement exécutés.

Lens fonctionne en boucle, conserve les fichiers sources en lecture seule et nomme l'origine de chaque fait. Les erreurs frontales sont journalisées sur le serveur, un rapport de bug peut donc les inclure.

Documentation dans le graphique

Liens doc-commentaires (#2550, #2593)

  • C# <see cref>, <seealso cref>, <exception cref> et <inheritdoc cref> sont liés par les propres règles de recherche du compilateur, y compris les utilisations globales MSBuild évaluées à partir de vos fichiers de projet (#2550).
  • Liens Go doc, balises Javadoc et KDoc ({@link}, @see, @throws, {@value}, @sample), liens intra-doc Rust, Perl POD L<>, TypeScript/JavaScript {@link}, PHPDoc @see et Doxygen @ref/@see suivez la même règle (#2593).
  • Chacune des 17 familles de liens doc-commentaires fournies dans le #2593 a passé un audit aveugle sur les référentiels jamais utilisés pour le construire (barre : Wilson 95 % de limite inférieure ≥ 0.90).
  • Les familles toujours en dessous de la barre se résolvent mais restent en dehors du graphique, par exemple TS/JS {@linkcode} et @see, liens de diagramme et liens OpenAPI operationId.
  • index_status gagne un bloc doc_links : le compte MENTIONS, plus les références non résolues comptées par motif (missing, ambiguous, external, …). Passez diagnostics='full' pour les échantillons.

Documents (#2551)

  • Les sections Markdown : renvoient au code qu'elles nomment via des liens, des chemins nus et des étendues de code contenant des chemins ou des noms qualifiés. Une plage de lignes telle que #L3-L9 lie la définition la plus interne qui la contient. Un simple nom n’est jamais un avantage.
  • reStructuredText / Sphinx : un Section par titre, avec des liens depuis les rôles (:class:, :meth:…), les directives objet, autodoc, literalinclude et les littéraux en ligne. Les noms Python sont résolus de la manière dont Sphinx les importe. conf.py est lu sous forme de texte, jamais exécuté.
  • AsciiDoc / Antora : les sections sont liées via les directives include:: et les régions de balises.
  • PDF : chaque page devient un Section dont le texte est consultable, lié aux chemins, noms de fichiers et noms qualifiés qu'il mentionne. L'extracteur est sans dépendance et conçu pour une entrée untrusted : 44 070 PDF mutants amorcés exécutés sous ASan et UBSan avec aucun résultat. Les documents cryptés sont signalés comme tels.
  • ADR : détectés dans Markdown et reST. Leurs faits proviennent du texte préliminaire, des champs d'en-tête ou de la section Statut.
  • Les références fichier à fichier Markdown deviennent également des bords REFERENCES_FILE, donc les centres de documentation apparaissent dans les requêtes fan-in (#1832, merci @cdeust).

Commentaires complets du document (#2459). Les exécutions multilignes de // et ///, les documents au-dessus des attributs et des exportations, les documents de champ et de membre d'énumération, les commentaires du package Go et le POD Perl sont désormais capturés dans leur intégralité, sans coupure de 500 octets. Capture full-doc sur des corpus réels :

Candidats de la section Doc (#2574). La documentation explique souvent une fonction sans la nommer. Pour ces sections, get_code_snippet répertorie désormais les candidats possibly_about (sur une section) et les candidats possibly_described_in (sur une fonction). Chaque candidat porte une probabilité jugée sur des échantillons aveugles. Ce sont des pistes qu'un agent doit vérifier, et non des contours : au mieux, environ la moitié ont raison, et l'outil le dit. get_file_outline répertorie les sections susceptibles de concerner un fichier.

Diagrammes et OpenAPI (#2593)

  • Formats pris en charge :
    • Sirène : organigramme, séquence, classe, ER, état, C4, architecture
    • PlantUML, Graphviz DOT et D2
    • draw.io : brut, compressé et .drawio.svg
    • Excalidraw : .excalidraw, .excalidraw.json et .excalidraw.svg
  • Intégrés ou autonomes : les diagrammes sont lus dans les clôtures Markdown, les directives reST (.. mermaid::, .. uml::, .. graphviz::), les blocs de diagramme Asciidoctor et leurs propres fichiers de diagramme. Les fichiers .drawio.svg et .excalidraw.svg ne sont plus ignorés en tant qu'images.

  • OpenAPI et Swagger : openapi.json, swagger.json et tout fichier YAML ou JSON dont la racine déclare openapi/swagger contribuent à un Route par opération. L'itinéraire de la spécification et l'itinéraire enregistré par votre code se rencontrent dans un seul nœud.

Smart CI : le graphique sélectionne les tests (#2458)

Exécuter chaque test pour chaque modification est lent et coûteux. Une règle écrite à la main pour laquelle les tests doivent être ignorés est une conjecture. Dans cette version, c'est le graphique qui décide.

  • Test d'impact à partir du graphique. detect_changes avec scope: "tests" :

    • épingle le changement, de la base de fusion à HEAD ;
    • amorce le graphique à partir des morceaux modifiés ;
    • parcourt tout ce qui dépend d'eux, à travers les appels, les références, les lectures et les itinéraires, ainsi qu'à travers les en-têtes et leurs macros.

    Les tests, les suites et les points d'entrée des coureurs à la fin de ces chemins sont la réponse, chacun avec la manière dont elle a été atteinte.

  • Jamais un échec silencieux. Des preuves manquantes ou douteuses ne réduisent jamais la sélection. Un changement non analysable, un test non mappé ou un exécuteur de test atteint main transforme la réponse en « tout exécuter », avec la raison nommée.

  • Paramètres de marche pour chaque référentiel. detect_changes prend edge_types, fixpoint et via. Tout projet peut demander la fermeture complète des dépendances entrantes d'une modification et voir le chemin d'accès à chaque accès.

  • Groupes d'équipe. codebase-memory-mcp test-impact publish|select regroupe le graphique gelé d'un commit et sa carte de couverture par test sous forme de bundle. La sélection d'une pull request démarre alors à partir du bundle de sa base de fusion au lieu d'une indexation à partir de zéro.

  • Dogfooded. Les propres demandes d'extraction de codebase-memory-mcp exécutent uniquement les pistes de test touchées par leurs modifications ; les essais à sec et les versions exécutent toujours tout. La sélection de tests du graphique s'exécute également comme une ombre de rapport uniquement sur chaque PR. Cela crée l'enregistrement dont nous avons besoin avant de restreindre les exécutions de tests par défaut.

Aujourd'hui, le modèle de test connaît le propre exécuteur de test C de codebase-memory-mcp. Pour les autres exécuteurs de tests, scope: "tests" répond « tout exécuter » jusqu'à ce que leurs conventions soient mappées. Les paramètres de marche fonctionnent partout.

Infrastructure sous forme de code dans le graphique (#2597, #2643, #2644)

Les éléments d’un graphique d’infrastructure existaient auparavant ; maintenant ils enchaînent. Nous avons mesuré sur 17 référentiels d'infrastructure open source, de kubespray et cluster-api à opentelemetry-demo. Sur eux, un service peut être parcouru jusqu'au code exécuté par son conteneur :

Service → Deployment → Image → Dockerfile → main()
                     └ the container's environment variables

-Kubernetes :

  • Chaque document manifeste est un objet doté d'une identité stable.
  • Les objets sont liés aux ConfigMaps, Secrets, ServiceAccounts et volumes qu'ils nomment, ainsi qu'à leurs références Flux, Argo CD, Cluster API et cert-manager.
  • Un service est lié aux pods sélectionnés par l'ensemble de son sélecteur.
  • Helm : Les manifestes basés sur des modèles deviennent également des objets, les modèles de graphique sont liés aux modèles nommés qu'ils incluent et les dépendances du graphique file:// sont résolues.
  • Chaînes de déploiement : Les bords DEPLOYS proviennent de :
    • Flux Kustomizations et HelmReleases, et applications Argo CD ;
    • kubectl apply, kustomize build et helm install|upgrade|template dans les scripts et Makefiles ;
    • Installateurs Terraform helm_release et Go qui utilisent le Helm SDK.
  • Construire et exécuter :
    • Les fichiers Docker dépendent des images à partir desquelles ils sont construits, et SPAWNS relie chacun à ce que son conteneur exécute.
    • Une nouvelle étiquette Image relie les charges de travail, les services Compose et les commandes de build au fichier Docker qui crée l'image.
    • Les scripts et jobs CI (GitHub Actions, Prow) sont liés aux scripts et programmes qu'ils exécutent, et make TARGET à sa règle.
  • Environnement, sans valeurs : chaque variable définie par un conteneur devient le propre EnvVar de ce conteneur. Les valeurs ne sont jamais stockées et les éléments secrets n'atteignent jamais le graphique.
  • Outils : trace_path gagne les modes run, deploy et topology ; search_graph filtre l'infrastructure par type et espace de noms.
  • Corrections en cours de route :
    • Un commentaire avant un manifeste ne le cache plus.
    • Des fichiers Kustomization sans extension ont été trouvés.
    • Les fichiers OpenTofu .tofu et .tfvars sont indexés.
    • Les bords de la route HANDLES ne dépendent plus de l'ordre des ouvriers (rouf : 6 424 → 44, les faux disparus).
  • Vérifié indépendamment : un lecteur indépendant a vérifié chaque couche des 17 référentiels. Le rappel et la précision étaient de 100 % sur la lunette fermée.
  • Kustomize, Terraform et Ansible rejoignent la chaîne (#2643, #2644) :
    • Les correctifs Kustomize, les variantes helmCharts et namePrefix/nameSuffix sont liés aux objets qu'ils modifient ou déploient (OVERRIDE, DEPLOYS).
    • Les variables d'environnement d'un conteneur atteignent le code à l'intérieur de sa propre image qui les lit (CONFIGURES). Les charges de travail et les services Compose CONNECTS_TO le service auquel leur environnement s'adresse, et curl/wget dans les scripts, les Makefiles et CI créent HTTP_CALLS vers les routes.
  • Terraform, OpenTofu et Terragrunt : var., local., module., data. et références de ressources lien vers le bloc qui les déclare ; les modules locaux sont IMPORTS, les fichiers .tfvars OVERRIDE leurs variables et Terragrunt include/dependency sont liés. Les ressources kubernetes_* deviennent les mêmes objets que les manifestes.
    • Ansible : playbooks, fichiers de tâches et liens de rôles par IMPORTS ; les tâches et les gestionnaires sont des fonctions, notify appelle les gestionnaires qu'ils nomment et les tâches kube/k8s DEPLOYS le modèle qu'elles appliquent.
    • Les charts Helm externes sont identifiés par l'URL qui les publie : un nœud partagé par chart publié dans tous les projets. Un graphique sans URL indiquée reste par projet, et une URL portant un jeton ou des informations d'identification ne fait jamais partie d'un nœud.
    • Les clés de configuration TOML et INI sont liées au code uniquement par nom exact et à l'intérieur du composant du fichier de configuration, ce qui supprime les bords CONFIGURES coïncidents.
    • Un échantillon vérifié manuellement des nouveaux bords était correct à 849 sur 850.

Un graphique de code plus précis

C et C++

  • Typedefs et macros (#2543) :

    • Les typedefs deviennent des nœuds et les agrégats anonymes typedef struct/enum {…} X; sont nommés d'après leur typedef.
    • Un #define NAME ne remplace plus la fonction ou le type appelé NAME ; les macros obtiennent leur propre identité <module>.<NAME>#macro.
    • Les fonctions derrière une macro principale inconnue conservent leur vrai nom.
    • Mesuré : redis a gagné 573 nœuds Type et curl 193 ; les fonctions précédemment perdues au profit d'une macro du même nom ont été restaurées (45 sur redis, 41 sur curl).

  • Accès membre (#2458) : a.b et a->b lient le champ du type réel de l'objet. Lorsque le type est inconnu, ils lient uniquement un nom de membre exactement porté par une structure. Sur ce projet, la part des utilisations du champ C qui atterrissent sur une structure que le fichier nomme est passée de 58.1% à 97.6%.

  • Définitions conditionnelles (#2458) : un nœud par définition qui existe une fois par branche #if, #[cfg] ou balise de build Go, avec l'étendue de chaque variante conservée dans une propriété variants. Les définitions à l'intérieur des blocs conditionnels sont désormais extraites pour C++, C#, Objective-C, Elixir, Fortran et Haskell.

  • Variantes de plate-forme (#2630) : une fonction C/C++ définie une fois par fichier ou répertoire de plate-forme (src/unix/fs.c et src/win/fs.c, arch/x86/... et arch/arm64/...) conserve un nœud par fichier sous son propre chemin, de sorte que chaque implémentation peut être trouvée par son chemin. Les variantes partagent une propriété variant_key, et Smart CI traite un changement dans n'importe quelle variante comme atteignant les tests de chacune d'entre elles.

  • Une définition par site en C/C++ à macro-lourd (#2626, #2629) : lorsque l'analyse brute et l'analyse macro-développée étaient en désaccord sur la portée ou l'orthographe d'une définition, les deux copies étaient utilisées pour atterrir dans le graphique (par exemple bitonic<int64_t, AVX2> et bitonic < int64_t , AVX2 >). Chaque définition est désormais un nœud avec une orthographe : sur dotnet/runtime, les définitions en double passent de 545 groupes dans v0.11.0 à 185.

  • Appels entre fichiers (#2466) :

    • Les appels Class::member sont résolus dans tous les fichiers, notamment X::instance()->m() et auto w = Widget::create(); w->m().
    • qBittorrent a gagné 489 bords CALLS corrects.

  • Macros d'exportation (#2005) : les définitions de types cachées derrière les macros d'exportation sont récupérées (merci @XIYBHK).

  • Types de retour (#2274) : le type de retour d'une fonction de la famille C conserve son pointeur et ses qualificatifs.

  • Définitions enveloppées de macro (#2450) : void FNAME(first)(void) et void Cls::__API_HOOK(Spawn)() portent le nom de l'argument de la macro (first, Spawn). Chaque définition générée par une macro wrapper est utilisée pour partager un seul nœud (#946, #1957). Dans toutes les langues (#2458, #2227)

  • ** Bords SPAWNS. ** subprocess.run, exec.Command, child_process.spawn, posix_spawn, Process.Start, Command::new et leurs parents dans environ 30 langues pointent désormais vers un nœud Process nommé d'après le programme. Auparavant, on devinait les bords CALLS.

  • Aucune supposition de nom multilingue. Une correspondance de nom uniquement ne lie jamais un symbole défini dans une autre langue, et les langages de configuration (Makefile, CMake, YAML) ne se lient plus au code.

  • Les importations Bash sont les fichiers sources d'un script, pas toutes les commandes qu'il exécute.

  • Un fichier et un dossier avec la même racine restent tous les deux (#2624). genproto.sh à côté de genproto/ partageait un nom qualifié, et le module du fichier a été supprimé avec les bords pointant vers lui. Le dossier s'écrit désormais proj.pkg.genproto/ ; où le répertoire est un package Java ou Go, le dossier garde son nom et le module du fichier devient proj.pkg.genproto#sh. Les noms des symboles ne changent pas. Sur 17 référentiels d'infrastructure, 27 Modules perdus → 0.

Déterministe et complet

  • Aucune horloge ne décide de ce qui se retrouve dans le graphique. La marche AST ne s'arrête plus à un budget temps ; un corpus C# qui produisait un nombre d'arêtes différent à chaque exécution produit désormais le même graphique à chaque fois, avec environ 550 arêtes supplémentaires (#2233).
  • L'indexation pendant que les résultats sont stockés sur le disque sous pression mémoire produit le même graphique que l'indexation en mémoire (#2233).
  • Les cibles #include et les liens de résolution ne dépendent plus de l'ordre de fusion des travailleurs (#2227).
  • Chaque fichier est analysé comme si sa dernière ligne était terminée. Un en-tête final, une clôture ou une recette Makefile n'est plus perdu (#2340).
  • Les marcheurs AST grandissent au lieu de coiffer silencieusement leurs corps profonds ou larges (#2375, #2373).
  • Les promenades tronquées sont signalées dans la couverture au lieu de passer comme entièrement indexées (#2233).
  • Les petits référentiels, indexés sur le chemin séquentiel, portent désormais les mêmes arguments d'appel sur HTTP et les bords asynchrones que les grands sur le chemin parallèle. Le graphique ne dépend plus du chemin parcouru (#2520).

    • Les fichiers de projet .NET (.csproj, .props, .targets, .resx, XAML, manifestes d'application) sont indexés au format XML (#2230, merci @yasmoradi).

    • Un .gitignore ne cache jamais un fichier suivi par Git, conformément à la propre règle de Git (#2608).
    • Le cache de vue Blade compilé de Laravel est ignoré (#2325).
    • Les ressources Binary ReScript .res ne bloquent plus l'indexeur (#2352).
    • Les gros dumps SQL sont analysés à moindre coût (#2326).

Relations sémantiques que vous pouvez peser (#2574)

  • L'admission se fait selon le principe du meilleur premier arrivé.
  • TF-IDF compare le vocabulaire au lieu des positions symboliques.

Performances et mémoire

  • Indexation plus rapide à tous les niveaux. Sur dix référentiels de référence, un par langage LSP, un index complet de cette version bat v0.11.0 partout. Médianes de trois exécutions sur un Apple M5 Pro :

    | Référentiel | v0.11.0 | v0.12.0 | Changement | |---|---|---|---| | Perl | 7.0 | 1.1 | −84 % | | PHP | 7.4 | 1.7 | −77 % | | Rust | 8.0 | 1.9 | −76 % | | C | 9.2 | 3.0 | −67 % | | Aller | 45.2 | 18.6 | −59 % | | Kotlin | 11.0 | 4.7 | −57 % | | Python (django) | 11.9 | 6.0 | −50 % | | TypeScript | 33.9 | 21.6 | −36 % | | C# | 132.0 | 120.8 | −8 % | | Java | 76.0 | 72.0 | −5 % |

    La mémoire maximale est inférieure sur neuf des dix, et chaque référentiel a produit le même graphique à chaque exécution.

  • Le noyau Linux, temps d'indexation avec et sans la passe de documentation. Documentation dans le graphique ajoute une nouvelle étape d'indexation : chaque section de documentation est évaluée par rapport au code pour trouver les fonctions et les fichiers dont il s'agit. Il s'exécute par défaut pour les index complets (le mode par défaut) et non pour ceux moderate ou fast ; Le doc_candidates l'allume ou l'éteint pour n'importe quel mode.

    | Noyau Linux, index complet | v0.11.0 | v0.12.0 | |---|---|---| | graphique de code uniquement | 236 s, 21.3 Go crête | 225 s, 14.3 Go crête | | graphique de code + passe de documentation (par défaut) | n/a | 396 s |

    Sur les référentiels inférieurs à environ 100 000 fonctions, la documentation coûte environ une seconde ou moins.

  • Les outils de requête répondent rapidement, sur chaque plate-forme (#2642). Sur macOS et Linux, chaque réponse est identique en octets à celle d'avant ; seule l'heure a changé.

    • search_code analyse les fichiers indexés en cours plutôt que via grep ou PowerShell. Sur Django, une recherche par défaut est passée de 908 ms à 355 ms et une recherche large de 3.8 à 0.7 . Sous Windows sur Arm, une recherche est passée des 1.6-3.4 aux 0.2-0.5 ; sur les Arm runners de GitHub, l'analyse PowerShell avait nécessité jusqu'à 31 s par appel, contre une limite d'analyse de 30 s. Windows correspond désormais exactement comme macOS et Linux (voir Modifications révolutionnaires).
    • query_graph trie, déduplique et regroupe en O(n log n) au lieu de O(n²). Sur les 29 000 méthodes de Django, WITH ... ORDER BY est passé de 41 s à 62 ms, RETURN ... ORDER BY de 2.2 s à 50 ms et WITH DISTINCT de 18 s à 56 ms.
    • Les outils de lecture exécutent leurs recherches de graphiques dans une transaction de lecture SQLite, renouvelée toutes les 100 ms, au lieu de verrouiller le fichier de base de données une fois par recherche. Un count(*) à graphique entier est passé de 508 ms à 184 ms, et sous Windows, où les verrouillages de fichiers coûtent plus cher, des 2.9 aux 0.39.
    • Sur un graphe à l'échelle du noyau (le noyau Linux : 8.5 millions de nœuds, 16.9 millions d'arêtes) :
      • trace_path et les filtres de degré de search_graph parcourent un index de contiguïté en mémoire, construit une fois par version d'index (1.2-1.5 sur le noyau) et imputé au budget mémoire ; un inactif est libéré après 10 minutes. trace_path de schedule est tombé de 7.5 à 22 ms, une recherche de hub de 4.2 à 0.17.
      • query_graph diffuse ses lignes au lieu de conserver chaque correspondance en mémoire. Un count(*) de graphique entier atteignait un pic à 24.9 Go et s'arrêtait à la limite de temps de requête ; il répond désormais en 11 s sur 289 Mo.
      • get_architecture est passé de 9 s à 0.9 s, et une recherche de nom exact ou de préfixe de 1.1 s à 14 ms.
      • search_code est passé de 11.8 à 3.4.
    • La réindexation d'un référentiel inchangé ne copie plus d'abord l'intégralité de la base de données. Sur le noyau qui prenait des 18.4 et écrivait 19 Go ; il prend maintenant des 2.4 et n'écrit rien (django 841 ms à 539 ms).
    • list_projects demande à git uniquement la branche qu'il affiche : deux appels git par projet au lieu de sept (94 ms à 40 ms avec un projet, et l'économie augmente à chaque projet).

  • Démarrage plus rapide à chaque appel. SHA-256 s'exécute désormais sur les instructions ARMv8 SHA2 et x86 SHA-NI. Le début de session du chemin de hook est passé de 1.448 s à 0.376 s sur Apple arm64, avec des résumés identiques (#2575).

  • Beaucoup moins de perte de disque lors des mises à jour incrémentielles. Une modification d'une ligne sur un index Django de 294 Mo a écrit 5.2 GiB dans le WAL SQLite ; il écrit maintenant 0.52 GiB (#2469).

  • A memory budget that respects the machine.

    • Le budget est désormais dimensionné à partir de la mémoire libre, et non plus seulement de la RAM totale : un index noyau sur un hôte occupé de 48 Go se termine au lieu de l'épuiser.
    • Le déversement sur le disque ne démarre jamais en dessous de 10 Go d'espace libre.
    • Les fichiers de déversement disparaissent même si le processus est arrêté (POSIX).
    • Les bases de données de préparation orphelines de chaque projet sont récupérées (#2233).

  • Allocation plus légère. Sur le corpus Go, les allocations sont passées de 245.5 M à 134.8 M, avec une sortie graphique inchangée (#2233).

  • Empreinte mémoire macOS réduite. Les travailleurs d'indexation sur macOS renvoient la mémoire purgée afin que l'empreinte facturée par le système d'exploitation diminue, avec un graphique à octets identiques (#2581).

  • Corrections algorithmiques :

    • Les surfaces LSP décodent en temps linéaire (#2288, merci @JosephStarobinets).
    • Les recherches de chaîne de portée Python sont regroupées en une seule passe (#2252, d'après le travail d'Andrew Hundt).
    • La notation de la section Doc est exacte et moins chère (#2582).
    • Le travail répété du résolveur est limité sans tronquer les fichiers volumineux. Un fichier qui atteint la limite est signalé comme incomplet au lieu d'être silencieusement partiel (#2522, #1527).
    • Les sondes de sous-modules Python et les analyses de classes et de caractères génériques ne parcourent plus l'ensemble du registre (#2532, #2535).

Fiabilité

  • Les grands index ne sont plus corrompus. Le rédacteur SQLite en bloc pourrait terminer un niveau d'arbre B avec une page intérieure vide sur de grands graphiques avec des clés longues ; SQLite then reported the database as malformed. Corrigé (#2330).
  • Settings database (#2650):
    • Correction d'une course au démarrage sur la base de données des paramètres : daemon start --port, --ui=true --port et d'autres commandes pouvaient échouer avec "le démon n'a pas accepté la configuration de l'interface utilisateur" ou "n'a pas pu charger les paramètres d'exécution enregistrés" pendant qu'un autre processus était en train d'écrire les paramètres. Ils attendent maintenant la fin de cette écriture et le démarrage du démon ne réécrit plus les paramètres d'interface utilisateur inchangés.
    • Correction d'un écart de récupération : après l'arrêt d'un processus au milieu d'une écriture de paramètres, chaque commande ultérieure échouait avec "impossible de charger les paramètres d'exécution enregistrés" jusqu'à ce que la base de données des paramètres soit réparée manuellement. Le démarrage annule maintenant l'écriture interrompue et continue.
  • Fewer concurrency and data-loss bugs:
    • Les premières lectures simultanées d'une base de données inactive ne fonctionnent plus (#2561).
    • Une publication atomique échouée enregistre pourquoi (#2259, extrait du travail par @junk151516).
    • Un travailleur d'index qui quitte sans répondre est nommé (#2494).
    • Edge ids stay unique after a parallel phase. Un compteur d'identification abaissé en avait distribué deux fois, ce qui pouvait transformer la suppression d'un nœud en une référence pendante (# 2607).
  • Plus de Git redirigé. Les propres commandes Git de cbm ignorent les variables de redirection du référentiel (GIT_DIR, GIT_WORK_TREE, …) héritées des hooks et des terminaux de l'éditeur (#2341).
  • Corrections de sécurité de la mémoire :
    • une lecture non initialisée dans le scanner de grammaire WIT, révélée par MemorySanitizer (#2596)
    • une lecture d'un octet non écrit dans le texte de la section reST (#2583)
    • une fuite trace_path (#2425)
    • une fuite lorsqu'un modèle Cypher MATCH ne parvient pas à être analysé (#2603)
    • un argument d'appel trop long dépasse son tampon de formatage de 512 octets, et une syntaxe profondément imbriquée pourrait épuiser la pile ; les deux marcheurs sont désormais délimités et itératifs (#2478)

codebase-memory-mcp v0.12.0

v0.12.0

Meet CBM Lens, and a code graph that reads your documentation.

v0.12.0 is the biggest release of codebase-memory-mcp yet: 231 merged pull requests since v0.11.0, 40 of them from the community.

Four headlines define it.

  1. CBM Lens Beta: the code graph, for humans. Until now the graph's power reached people only through their agents. Lens is our new human interface. It brings the code knowledge graph to you directly. It ships inside the binary you already run and listens on loopback only. It puts source, the graph, the architecture, index coverage and a browser-local assistant side by side, and every fact it shows says where it comes from. Lens is built on the work of @BernhardJackiewicz, who now joins the project to own it.

  2. Documentation joins the graph. Until now the graph stopped where the code stopped. Now doc comments, Markdown, reStructuredText, AsciiDoc and PDF documents, architecture decision records, diagrams and OpenAPI specs are part of it. Each is linked to the functions, types and files it talks about. An agent can now traverse your documentation and land on the exact code a page describes, and walk from a function back to every page that explains it. So can you, in Lens. Linking is strict by design: a reference becomes an edge only when it names exactly one definition. Link families that have not yet cleared their accuracy bar are counted and reported, never guessed into the graph.

  3. Smart CI: the graph picks the tests. detect_changes can now say which tests a change can affect. It seeds the graph from the diff, walks everything that depends on the changed code, and names the tests at the end of those paths, each with its reason. When the evidence is missing or doubtful, it answers "run everything" and says why; it never narrows silently. codebase-memory-mcp's own CI is the first user: pull requests run only the test lanes their change touches, and the graph's test selection runs beside every PR.

  4. Infrastructure as code in the graph. Kubernetes manifests, Helm charts, Flux and Argo CD, Compose files, Dockerfiles and the scripts, Makefiles and CI jobs that deploy them now link up. A Service can be followed through its workload, its image and its Dockerfile to the program the container runs.

The code graph itself got sharper too:

  • C typedefs, macros and enumerators get identities of their own.
  • Process launches become SPAWNS edges.
  • Resolution fixes cover C#, C++, TypeScript, Python, PHP, Rust and Go.

Upgrading? The first index of each existing project after the upgrade is a full rebuild, once. Details are in Upgrade notes. A few identities and defaults also changed; see Breaking changes.

CBM Lens Beta (#2068)

The MCP tools are the agent's interface to the graph. CBM Lens Beta is yours: our attempt to bring the power of the code knowledge graph to humans. It replaces the previous graph UI and is built into the binary:

codebase-memory-mcp --ui=true --port=9749
  • Explore: follows the current file or marked source, with its direct dependencies and a file-level impact summary from graph and local Git evidence.
  • Galaxy: search nodes, files and folders, then expand incoming or outgoing relationships by depth and edge type.
  • Architecture: the repository map, routes, hotspots, system structure and behavior.
  • Coverage and System: what the index missed and why, plus daemon status, indexes, diagnostics and MCP configuration.

Documentation in the graph

Doc-comment links (#2550, #2593)

  • C# <see cref>, <seealso cref>, <exception cref> and <inheritdoc cref> bind by the compiler's own lookup rules, including MSBuild global usings evaluated from your project files (#2550).
  • Go doc links, Javadoc and KDoc tags ({@link}, @see, @throws, {@value}, @sample), Rust intra-doc links, Perl POD L<>, TypeScript/JavaScript {@link}, PHPDoc @see and Doxygen @ref/@see follow the same rule (#2593).
  • Each of the 17 doc-comment link families that ship in #2593 passed a blind audit on repositories never used to build it (bar: Wilson 95% lower bound ≥ 0.90).
  • Families still below the bar resolve but stay out of the graph, for example TS/JS {@linkcode} and @see, diagram links and OpenAPI operationId links.
  • index_status gains a doc_links block: the MENTIONS count, plus unresolved references counted by reason (missing, ambiguous, external, …). Pass diagnostics='full' for samples.

Documents (#2551)

  • Markdown: sections link to the code they name through links, bare paths, and code spans holding paths or qualified names. A line range such as #L3-L9 binds the innermost definition that holds it. A bare name is never an edge.
  • reStructuredText / Sphinx: a Section per title, with links from roles (:class:, :meth: …), object directives, autodoc, literalinclude and inline literals. Python names resolve the way Sphinx imports them. conf.py is read as text, never executed.
  • AsciiDoc / Antora: sections link through include:: directives and tag regions.
  • PDF: every page becomes a Section whose text is searchable, linked to the paths, file names and qualified names it mentions. The extractor is dependency-free and built for untrusted input: 44,070 seeded mutant PDFs ran under ASan and UBSan with zero findings. Encrypted documents are reported as such.
  • ADRs: detected in Markdown and reST. Their facts come from front matter, header fields or the Status section.
  • Markdown file-to-file references also become REFERENCES_FILE edges, so documentation hubs show up in fan-in queries (#1832, thanks @cdeust).

Complete doc comments (#2459). Multi-line // and /// runs, docs above attributes and exports, field and enum-member docs, Go package comments and Perl POD are now captured in full, with no 500-byte cut. Full-doc capture on real corpora:

| Language | Before | After | |---|---|---| | Go | 35% | 99.999% | | C# | 10% | 99.8% | | Rust | 7% | 99.9% | | Java | 74% | 99.99% | | TypeScript | 42% | 100% |

Doc-section candidates (#2574). Documentation often explains a function without naming it. For those sections, get_code_snippet now lists possibly_about candidates (on a section) and possibly_described_in candidates (on a function). Each candidate carries a probability judged on blind samples. They are leads for an agent to verify, not edges: at best about half are right, and the tool says so. get_file_outline lists the sections that are likely about a file.

Diagrams and OpenAPI (#2593)

  • Supported formats:
    • Mermaid: flowchart, sequence, class, ER, state, C4, architecture
    • PlantUML, Graphviz DOT and D2
    • draw.io: plain, compressed and .drawio.svg
    • Excalidraw: .excalidraw, .excalidraw.json and .excalidraw.svg
  • Embedded or standalone: diagrams are read in Markdown fences, reST directives (.. mermaid::, .. uml::, .. graphviz::), Asciidoctor diagram blocks and diagram files of their own. .drawio.svg and .excalidraw.svg files are no longer skipped as images.
  • Labels, not syntax: a Markdown section that embeds a diagram keeps the diagram's labels in its searchable text instead of its syntax (-->, participant).
  • OpenAPI and Swagger: openapi.json, swagger.json and any YAML or JSON file whose root declares openapi/swagger contribute one Route per operation. The spec's route and the route your code registers meet in one node.

Smart CI: the graph picks the tests (#2458)

Running every test for every change is slow and expensive. A hand-written rule for which tests to skip is guesswork. In this release, the graph decides.

  • Test impact from the graph. detect_changes with scope: "tests":

    • pins the change, from the merge base to HEAD;
    • seeds the graph from the changed hunks;
    • walks everything that depends on them, over calls, references, reads and routes, and through header includes and their macros.

    The tests, suites and runner entry points at the end of those paths are the answer, each with how it was reached.

  • Never a silent miss. Missing or doubtful evidence never narrows the selection. An unparseable change, an unmapped test, or a reached test-runner main turns the answer into "run everything", with the reason named.

  • Walk parameters for every repository. detect_changes takes edge_types, fixpoint and via. Any project can ask for the full inbound dependency closure of a change and see the path to each hit.

  • Team bundles. codebase-memory-mcp test-impact publish|select packages a commit's frozen graph and its per-test coverage map as a bundle. A pull request's selection then starts from the bundle of its merge base instead of indexing from scratch.

  • Dogfooded. codebase-memory-mcp's own pull requests run only the test lanes their change touches; dry runs and releases still run everything. The graph's test selection also runs as a report-only shadow on every PR. That builds the record we need before it narrows test runs by default.

Today the test model knows codebase-memory-mcp's own C test runner. For other test runners, scope: "tests" answers "run everything" until their conventions are mapped. The walk parameters work everywhere.

Infrastructure as code in the graph (#2597, #2643, #2644)

The pieces of an infrastructure graph existed before; now they chain. We measured on 17 open-source infrastructure repositories, from kubespray and cluster-api to opentelemetry-demo. On them, a Service can be walked to the code its container runs:

Service → Deployment → Image → Dockerfile → main()
                     └ the container's environment variables
  • Kubernetes:
    • Every manifest document is an object with a stable identity.
    • Objects link to the ConfigMaps, Secrets, ServiceAccounts and volumes they name, and to their Flux, Argo CD, Cluster API and cert-manager references.
    • A Service links to the pods its whole selector selects.
  • Helm: templated manifests become objects too, chart templates link to the named templates they include, and file:// chart dependencies resolve.
  • Deploy chains: DEPLOYS edges come from:
    • Flux Kustomizations and HelmReleases, and Argo CD Applications;
    • kubectl apply, kustomize build and helm install|upgrade|template in scripts and Makefiles;
    • Terraform helm_release, and Go installers that use the Helm SDK.
  • Build and run:
    • Dockerfiles depend on the images they build from, and SPAWNS links each to what its container runs.
    • A new Image label joins workloads, Compose services and build commands to the Dockerfile that builds the image.
    • Scripts and CI jobs (GitHub Actions, Prow) link to the scripts and programs they run, and make TARGET to its rule.
  • Environment, without values: each variable a container sets becomes that container's own EnvVar. Values are never stored, and secret material never reaches the graph.
  • Tools: trace_path gains the modes run, deploy and topology; search_graph filters infrastructure by kind and namespace.
  • Fixes along the way:
    • A comment before a manifest no longer hides it.
    • Extensionless Kustomization files are found.

A sharper code graph

C and C++

  • Typedefs and macros (#2543):
    • Typedefs become nodes, and anonymous typedef struct/enum {…} X; aggregates are named after their typedef.
    • A #define NAME no longer replaces the function or type called NAME; macros get their own <module>.<NAME>#macro identity.
    • Functions behind an unknown leading macro keep their real name.
    • Measured: redis gained 573 Type nodes and curl 193; functions previously lost to a same-named macro were restored (45 on redis, 41 on curl).
  • Member access (#2458): a.b and a->b bind the field of the object's actual type. When the type is unknown, they bind only a member name exactly one struct carries. On this project, the share of C field uses that land on a struct the file actually names rose from 58.1% to 97.6%.
  • Conditional definitions (#2458): one node per definition that exists once per #if branch, #[cfg] or Go build tag, with every variant's span kept in a variants property. Definitions inside conditional blocks are now extracted for C++, C#, Objective-C, Elixir, Fortran and Haskell.
  • Platform variants (#2630): a C/C++ function defined once per platform file or directory (src/unix/fs.c and src/win/fs.c, arch/x86/... and arch/arm64/...) keeps one node per file under its own path, so every implementation is findable by its path. The variants share a variant_key property, and Smart CI treats a change in any variant as reaching the tests of all of them.
  • One definition per site in macro-heavy C/C++ (#2626, #2629): where the raw and the macro-expanded parse disagreed about a definition's scope or spelling, both copies used to land in the graph (e.g. bitonic<int64_t, AVX2> and bitonic < int64_t , AVX2 >). Each definition is now one node with one spelling: on dotnet/runtime the duplicate definitions drop from 545 groups in v0.11.0 to 185.
  • Calls across files (#2466):
    • Class::member calls resolve across files, including X::instance()->m() and auto w = Widget::create(); w->m().
    • qBittorrent gained 489 correct CALLS edges.
  • Export macros (#2005): type definitions hidden behind export macros are recovered (thanks @XIYBHK).
  • Return types (#2274): a C-family function's return type keeps its pointer and qualifiers.
  • Macro-wrapped definitions (#2450): void FNAME(first)(void) and void Cls::__API_HOOK(Spawn)() are named after the macro's argument (first, Spawn). Every definition one wrapper macro generates used to share a single node (#946, #1957).

Across languages (#2458, #2227)

Performance and memory

  • Faster indexing across the board. On ten benchmark repositories, one per LSP language, a full index of this release beats v0.11.0 everywhere. Medians of three runs on an Apple M5 Pro:

    | Repository | v0.11.0 | v0.12.0 | Change | |---|---|---|---| | Perl | 7.0 s | 1.1 s | −84 % | | PHP | 7.4 s | 1.7 s | −77 % | | Rust | 8.0 s | 1.9 s | −76 % | | C | 9.2 s | 3.0 s | −67 % | | Go | 45.2 s | 18.6 s | −59 % | | Kotlin | 11.0 s | 4.7 s | −57 % | | Python (django) | 11.9 s | 6.0 s | −50 % | | TypeScript | 33.9 s | 21.6 s | −36 % | | C# | 132.0 s | 120.8 s | −8 % | | Java | 76.0 s | 72.0 s | −5 % |

    Peak memory is lower on nine of the ten, and every repository produced the same graph on every run.

  • The Linux kernel, indexing time with and without the documentation pass. Documentation in the graph adds one new indexing step: every documentation section is scored against the code to find the functions and files it is about. It runs by default for full indexes (the default mode) and not for moderate or fast ones; doc_candidates switches it on or off for any mode.

    | Linux kernel, full index | v0.11.0 | v0.12.0 | |---|---|---| | code graph only | 236 s, 21.3 GB peak | 225 s, 14.3 GB peak | | code graph + documentation pass (default) | n/a | 396 s |

    On repositories below about 100,000 functions the documentation pass costs about a second or less.

  • Query tools answer fast, on every platform (#2642). On macOS and Linux every response is byte-identical to before; only the time changed.

    • search_code scans the indexed files in process instead of through grep or PowerShell. On django a default search fell from 908 ms to 355 ms and a wide one from 3.8 s to 0.7 s. On Windows on Arm a search fell from 1.6-3.4 s to 0.2-0.5 s; on GitHub's Arm runners the PowerShell scan had needed up to 31 s per call, against a 30 s scan limit. Windows now also matches exactly like macOS and Linux (see Breaking changes).
    • query_graph sorts, deduplicates and groups in O(n log n) instead of O(n²). Over django's 29,000 methods, WITH ... ORDER BY fell from 41 s to 62 ms, RETURN ... ORDER BY from 2.2 s to 50 ms and WITH DISTINCT from 18 s to 56 ms.
    • Read tools run their graph lookups in one SQLite read transaction, renewed every 100 ms, instead of locking the database file once per lookup. A whole-graph count(*) fell from 508 ms to 184 ms, and on Windows, where file locks cost more, from 2.9 s to 0.39 s.
    • On a kernel-scale graph (the Linux kernel: 8.5 million nodes, 16.9 million edges):
      • trace_path and the degree filters of search_graph walk an in-memory adjacency index, built once per index version (1.2-1.5 s on the kernel) and charged to the memory budget; an idle one is released after 10 minutes. trace_path from schedule fell from 7.5 s to 22 ms, a hub search from 4.2 s to 0.17 s.
      • query_graph streams its rows instead of holding every match in memory. A whole-graph count(*) used to peak at 24.9 GB and stop at the query time limit; it now answers in 11 s within 289 MB.
      • get_architecture fell from 9 s to 0.9 s, and an exact or prefix name search from 1.1 s to 14 ms.
      • search_code fell from 11.8 s to 3.4 s.
    • Re-indexing an unchanged repository no longer copies the whole database first. On the kernel that took 18.4 s and wrote 19 GB; it now takes 2.4 s and writes nothing (django 841 ms to 539 ms).
    • list_projects asks git only for the branch it shows: two git calls per project instead of seven (94 ms to 40 ms with one project, and the saving grows with every project).

  • Faster startup on every invocation. SHA-256 now runs on ARMv8 SHA2 and x86 SHA-NI instructions. The hook path's session start dropped from 1.448 s to 0.376 s on Apple arm64, with identical digests (#2575).

  • Far less disk churn on incremental updates. A one-line edit on a 294 MB django index wrote 5.2 GiB to the SQLite WAL; it now writes 0.52 GiB (#2469).

  • A memory budget that respects the machine.

    • The budget is now sized from free memory, not just total RAM: a kernel index on a busy 48 GB host finishes instead of exhausting it.
    • Spilling to disk never starts below 10 GB free.
    • Spill files disappear even if the process is killed (POSIX).
    • Orphaned staging databases of every project are reclaimed (#2233).

  • Leaner allocation. On the Go corpus, allocations fell from 245.5 M to 134.8 M, with graph output unchanged (#2233).

Upgrade notes

  • One full rebuild per project. This release changes how C macros, enumerators and fields are identified. It also adds the documentation layer and the infrastructure graph, which moves the index format from 1 to 2. An index written by v0.11.0 or earlier is therefore rebuilt in full, once, the next time it is indexed (#2543, #2550, #2551, #2574, #2597, #2643).
    • Until then, the old graph keeps answering, and index_status points out that the index predates doc links.
    • On a large repository, plan for the time of a first index.
    • Your project's ADR document carries over.
    • Coming from v0.10.x? The index-format boundary introduced in v0.11.0 (#1104) is covered by the same single rebuild.
  • Terraform and Ansible edits re-index in full. A changed Terraform or Ansible file takes a full re-index instead of an incremental one, so cross-file edges never go stale (#2643).
  • Re-run cross-repo linking. A rebuild drops CROSS_* edges and their status together, so run index_repository(mode="cross-repo-intelligence") again for linked projects.
  • Indexes cover more files. PDF, AsciiDoc, diagram files, OpenAPI specs, .NET project files and Sphinx .txt sources are now read, and the documentation layer adds its own tables. Documentation-heavy repositories get larger indexes.
  • Very large repositories: the documentation pass and doc_candidates. Scoring the doc-section candidates (#2574) is the largest extra indexing cost on very large repositories. It runs by default for full indexes and not for moderate or fast ones. On the Linux kernel it adds about three minutes; on repositories below about 100,000 functions, about a second or less. codebase-memory-mcp config set doc_candidates false turns it off for every mode (true turns it on for every mode), and index_repository(doc_candidates: ...) does the same for one index. The code graph is unchanged either way; only the possibly_about / possibly_described_in leads are left out. With it off, the kernel indexes faster than with v0.11.0 (#2610, #2628).
  • Watcher scope, stated precisely. The background watcher follows the project each open MCP session is rooted in. A repository indexed from the CLI or from another project's session is not watched. Nothing changed here, but index_status now says so (#2348).
  • New opt-in settings (all off by default):
    • watch_non_git
    • index_max_files
    • index_max_source_mb
    • CBM_STARTUP_TIMEOUT_MS
    • CBM_WALK_MAX_NODES (restores a node cap on the AST walk if you want one)
  • The previous graph UI is replaced by CBM Lens Beta. It is still started with --ui=true.

    • C-preprocessor macros are now <module>.<NAME>#macro.
    • Enumerators of C enums and unscoped C++/Objective-C enums live in their enclosing scope.
    • A class field that shares its name with a method of the same class is <Owner>.<name>#field.
    • Rust #[cfg] twins are one node instead of name#cfg(...) nodes.
    • Java, C# and Solidity class fields no longer have a duplicate Variable node.
  • Some edge sets changed on purpose:
    • Program launches are SPAWNS edges instead of CALLS.
    • Cross-language name-only CALLS are gone.
    • C member accesses on names several structs share no longer bind to an arbitrary field.
    • SEMANTICALLY_RELATED admission and scores are recalibrated.
  • search_code on Windows matches like macOS and Linux. It used PowerShell Select-String, which matched case-insensitively, used .NET regex syntax and read files containing NUL bytes as text. Now every platform matches case-sensitively, uses extended regular expressions and skips binary files, so the same query gives the same answer on every OS (#2642).
  • uninstall -y keeps project indexes. Add --delete-indexes to remove them (#2517).
  • detect_changes default base. It now compares against origin/HEAD (then main, master, upstream) instead of always main (#2496).
  • Stricter inputs:
    • Cypher rejects a non-numeric SKIP/LIMIT that it used to silently ignore (#2002).
    • Regular expressions that would compile too large are refused (#2475).
    • search_code caps context at 200 lines (#2474).
