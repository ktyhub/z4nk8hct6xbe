Présentation de Dify Agent (Beta) : une nouvelle expérience d'agent dans Dify

[!AVERTISSEMENT] Vous devez fournir les services Dify Agent ⚠️uniquement aux utilisateurs trusted et non malveillants⚠️.

Comme beaucoup d’entre vous le savent, le paradigme des agents LLM basés sur un shell a apporté une avancée majeure dans les capacités des agents et a changé notre façon de penser les agents. Parallèlement, les compétences offrent un moyen standardisé de regrouper et de distribuer des fonctionnalités, facilitant ainsi la création d'agents puissants.

Aujourd'hui, nous lançons Dify Agent. Comme d’autres agents de premier plan, il s’exécute dans un bac à sable Linux. Cette version comprend :

  • Un constructeur pour créer des agents Dify

    • Vous pouvez créer des agents Dify via l'interface utilisateur : définissez une invite de base, téléchargez des compétences et des fichiers, et connectez les outils et les connaissances de l'écosystème Dify.
    • Nous fournissons également un agent qui vous aide à créer des agents Dify. Grâce à la conversation, il peut configurer l'environnement sandbox Linux, installer les packages requis et créer de nouvelles compétences et fichiers que votre agent Dify pourra utiliser ultérieurement.

  • Intégration de Dify Workflow pour Dify Agent

    • Vous pouvez utiliser un agent Dify existant dans un workflow Dify ou créer temporairement un agent Dify en ligne. Il exécutera la tâche définie par le nœud de workflow, générera la sortie requise et la transmettra au nœud suivant.

  • Une nouvelle expérience d'application Web

    • L'agent Dify que vous créez peut être publié et utilisé comme application Web. Bien que l'expérience utilisateur reste familière, elle est désormais optimisée par Dify Agent.

Avis de compatibilité OpenAI GPT-5.6

Le plugin OpenAI utilisait auparavant par défaut le Chat Completions API, qui a été obsolète par OpenAI plus tôt cette année et prend en charge de moins en moins bien les nouvelles séries de modèles. La nouvelle famille GPT-5.6 présente de nombreuses restrictions de combinaison de paramètres inhabituelles et uniques lorsqu'elle est utilisée avec les complétions de chat, car OpenAI ne fournit désormais qu'une prise en charge minimale de compatibilité pour les complétions de chat avec les nouveaux modèles. Ce n'est pas un problème du système Dify.

Le type API par défaut pour les nouvelles configurations a été modifié de Fins de conversation à Réponses. Cependant, les utilisateurs qui ont précédemment enregistré une clé API personnalisée avec l'ancienne valeur par défaut (achèvements de discussion) conserveront ce paramètre, ce qui peut provoquer des erreurs inattendues qui semblent provenir de Dify.

Si vous avez déjà configuré une clé OpenAI API personnalisée, veuillez vérifier votre paramètre de type API et passer à Réponses si elle est toujours définie sur Achèvements de discussion, en particulier lorsque vous utilisez GPT-5.6 ou des modèles ultérieurs.

Nouvelles fonctionnalités

Application Agent (bêta ouverte)

  • L'application Agent entre en version bêta ouverte et est désormais activée par défaut pour tous les utilisateurs. Il introduit un bac à sable intégré pour l'exécution de code et les commandes shell, un système de compétences qui permet aux agents d'appeler des outils et des API, une liste d'agents pour gérer et réutiliser les agents dans un espace de travail, et la prise en charge du référencement de nouveaux agents à partir de nœuds d'agent de workflow.

Génération de flux de travail IA plus intelligente

  • Le générateur de workflow ⌘K → /create et /refine AI a été amélioré de bout en bout : le champ "Sortie idéale" de faible valeur a été supprimé, les exemples de puces statiques ont été remplacés par des suggestions générées par l'IA basées sur le contexte de votre espace de travail et la génération de configuration de nœud est désormais parallélisée pour des résultats plus rapides. Un délai d'attente configurable (WORKFLOW_GENERATION_TIMEOUT_MS, 180 s par défaut) empêche le blocage des générations de longue durée. Mise à niveau du protocole MCP
  • Le serveur workflow-as-MCP prend désormais en charge le protocole MCP 2025-06-18 avec négociation de version et sortie d'outil structurée, tout en restant rétrocompatible avec les anciens clients. Les connexions MCPClient peuvent désormais injecter des en-têtes de requête HTTP dynamiques au moment de l'exécution à l'aide d'espaces réservés (par exemple {{request.headers.X-Custom-Auth}}), permettant ainsi l'authentification par requête.

Personnalisation de l'application Web

  • Les propriétaires d'applications peuvent désormais personnaliser le texte de l'espace réservé de saisie du chat (jusqu'à 64 caractères) pour les applications Web Chatbot, Agent et Chatflow. L'interface utilisateur de personnalisation a été affinée avec une dénomination plus claire (« Custom Frontend » / « Branding ») et une meilleure gestion des étiquettes. Les descriptions des applications sont désormais affichées sur les écrans des applications de chat et de génération de texte avec une vue pliable pour éviter de déplacer le formulaire de saisie hors de l'écran.

Fiabilité et opérations du flux de travail

  • Les archives d'exécution du workflow peuvent désormais être exportées et les exécutions actives sont correctement interrompues lors de l'arrêt à chaud de Celery pour éviter les tâches orphelines. Les connexions Redis sont plus résilientes grâce à la prise en charge TCP keepalive et à une couverture étendue des nouvelles tentatives. Les fournisseurs de modèles reçoivent désormais app_id pour l'attribution des coûts côté fournisseur (par exemple, Bedrock requestMetadata, métadonnées OpenAI, étiquettes Vertex AI). Les flux de connexion OAuth et SSO préservent désormais les URL de redirection de manière plus fiable, avec une vue d'erreur dédiée pour les échecs de SSO.

Améliorations de la sécurité

Cette version inclut plusieurs correctifs de renforcement de la sécurité, dont certains ont été corrigés après la version 1.16.0-rc1 :

  • Injection SQL : correction d'une vulnérabilité d'injection SQL et sécurité améliorée des requêtes SQL avec validation des clés de métadonnées
  • SSRF : Correction d'un contournement SSRF via httpx.get brut dans la récupération du schéma de l'outil API
  • Redirections ouvertes : redirections ouvertes empêchées dans les flux de redirection post-connexion et d'authentification
  • Application du bac à sable : Chatflow API vérifie désormais workflow_id et le plan sandbox ; le plan sandbox n'exécutera pas de flux de travail spéciaux
  • Protection Landlock : répertoire HOME de l'agent protégé par Landlock ; rétrogradé en v1 pour une compatibilité plus large avec le noyau
  • Mises à niveau des dépendances CVE : httplib2, setuptools, wandb ; Moteur python, prise python ; capricieux, oreiller, click

Guide de mise à niveau

Migration des types de modèles

[!IMPORTANT]

Migration unique du type de modèle hérité pour les mises à niveau auto-hébergées

Si ce déploiement a été mis à niveau à partir d'une version de Dify antérieure à 1.15.0 et que cette migration n'a pas déjà été appliquée, exécutez-la après la mise à niveau.

Cette migration n'est pas incluse dans flask db upgrade. Sans cela, les enregistrements de modèles existants peuvent entraîner l'échec des requêtes API liées au modèle avec des erreurs, empêchant ainsi le chargement ou l'utilisation des modèles concernés.

Sauvegardez la base de données avant d'appliquer la migration. La commande s'exécute en mode d'exécution à sec par défaut ; examinez la sortie avant de la réexécuter avec --apply. La migration est idempotente et peut être réexécutée en toute sécurité.

Docker Composer

Exécuté à partir du répertoire docker.

# Apply after reviewing the dry-run output
docker compose exec -T api flask data-migrate legacy-model-types --apply \
  > legacy-model-types-apply.jsonl

Déploiement du code source

Exécutez à partir de la racine du référentiel après avoir terminé flask db upgrade.

# Apply after reviewing the dry-run output
uv run --project api flask data-migrate legacy-model-types --apply \
  > legacy-model-types-apply.jsonl

Après avoir appliqué la migration, exécutez à nouveau la commande d'exécution à sec. S'il ne signale aucune mise à jour ou suppression de lignes supplémentaires, redémarrez les services concernés et vérifiez que les modèles existants peuvent être chargés et appelés avec succès.

dify 1.16.0

Introducing Dify Agent (Beta): A New Agent Experience in Dify

[!WARNING] You should provide Dify Agent services ⚠️only to trusted, non-malicious users⚠️.

As many of you know, the shell-based LLM agent paradigm has brought a major leap in agent capabilities and changed how we think about agents. Meanwhile, Skills provide a standardized way to package and distribute capabilities, making it easier to build powerful agents.

Today, we are launching Dify Agent. Like other leading agents, it runs in a Linux sandbox. This release includes:

  • A builder for creating Dify Agents

    • You can build Dify Agents through the UI: set a base prompt, upload Skills and files, and connect tools and knowledge from the Dify ecosystem.
    • We also provide an agent that helps you build Dify Agents. Through conversation, it can configure the Linux sandbox environment, install required packages, and create new Skills and files that your Dify Agent can use later.

  • Dify Workflow integration for Dify Agent

    • You can use an existing Dify Agent in a Dify Workflow, or temporarily create an inline Dify Agent. It will execute the task defined by the workflow node, generate the required output, and pass it to the next node.

  • A new web app experience

    • The Dify Agent you build can be published and used as a web app. While the user experience remains familiar, it is now powered by Dify Agent.

Docs: https://docs.dify.ai/en/self-host/use-dify/build/new-agent/overview

OpenAI GPT-5.6 Compatibility Notice

The OpenAI plugin previously defaulted to using the Chat Completions API, which was deprecated by OpenAI earlier this year and has increasingly poor support for newer model series. The newly released GPT-5.6 family has many unusual and unique parameter combination restrictions when used with Chat Completions, because OpenAI now provides only minimal compatibility support for Chat Completions with new models. This is not a Dify system issue.

The default API type for new configurations has been changed from Chat Completions to Responses. However, users who previously saved a custom API key with the old default (Chat Completions) will retain that setting, which may cause unexpected errors that appear to originate from Dify.

If you have previously configured a custom OpenAI API key, please check your API type setting and switch to Responses if it is still set to Chat Completions, especially when using GPT-5.6 or later models.

New Features

Agent App (Open Beta)

  • Agent App enters open beta and is now enabled by default for all users. It introduces a built-in sandbox for code execution and shell commands, a skill system that lets agents call tools and APIs, an agent roster for managing and reusing agents across a workspace, and support for referencing new agents from workflow agent nodes.

Smarter AI Workflow Generation

  • The ⌘K → /create and /refine AI workflow generator has been enhanced end-to-end: the low-value "Ideal output" field was removed, static example chips replaced with AI-generated suggestions grounded in your workspace context, and node config generation is now parallelized for faster results. A configurable timeout (WORKFLOW_GENERATION_TIMEOUT_MS, default 180s) prevents long-running generations from hanging.

MCP Protocol Upgrade

  • The workflow-as-MCP server now supports MCP protocol 2025-06-18 with version negotiation and structured tool output, while remaining backward compatible with older clients. MCPClient connections can now inject dynamic HTTP request headers at runtime using placeholders (e.g. {{request.headers.X-Custom-Auth}}), enabling per-request authentication passthrough.

Web App Customization

  • App owners can now customize the chat input placeholder text (up to 64 chars) for Chatbot, Agent, and Chatflow web apps. The customization UI has been refined with clearer naming ("Custom Frontend" / "Branding") and better label handling. App descriptions are now displayed on chat and text-generation app screens with a collapsible view to avoid pushing the input form off screen.

Workflow Reliability & Operations

  • Workflow run archives can now be exported, and active runs are properly aborted during Celery warm shutdown to prevent orphaned tasks. Redis connections are more resilient with TCP keepalive support and expanded retry coverage. Upgrade Guide

Model Type Migration

[!IMPORTANT]

One-time legacy model type migration for self-hosted upgrades

If this deployment was upgraded from a Dify version earlier than 1.15.0 and this migration has not already been applied, run it after upgrading.

This migration is not included in flask db upgrade. Without it, legacy model records can cause model-related API requests to fail with errors, preventing affected models from being loaded or used.

Back up the database before applying the migration. The command runs in dry-run mode by default; review the output before rerunning it with --apply. The migration is idempotent and can be safely rerun.

Docker Compose

Run from the docker directory.

# Apply after reviewing the dry-run output
docker compose exec -T api flask data-migrate legacy-model-types --apply \
  > legacy-model-types-apply.jsonl

Source Code Deployment

Run from the repository root after completing flask db upgrade.

# Apply after reviewing the dry-run output
uv run --project api flask data-migrate legacy-model-types --apply \
  > legacy-model-types-apply.jsonl

After applying the migration, run the dry-run command again. If it reports no additional row updates or deletions, restart the relevant services and verify that existing models can be loaded and invoked successfully.

[!IMPORTANT]

  • This release includes 8 new database migrations. Run database migrations as part of the upgrade.
  • 28 new environment variables, 1 removed, and 1 modified. Review the Environment Variable Changes section and update your .env accordingly.
  • Docker Compose configuration changed significantly: two new services (agent_backend, local_sandbox) were added. If you maintain a customized docker-compose.yaml, review the changes and re-apply local customizations carefully.
  • DIFY_AGENT_SERVER_SECRET_KEY ships with a development default. You must replace it in production with a securely generated key: python -c 'import secrets; print(secrets.token_urlsafe(32))'
  • ENABLE_AGENT_V2 has been renamed to NEXT_PUBLIC_ENABLE_AGENT_V2 and now defaults to true. Remove the old variable from your env files.
  • OpenAI GPT-5.6 users: If you have previously configured a custom OpenAI API key, verify your API type is set to Responses (not Chat Completions). See the Known Issues section above.

Docker Compose Deployments

  1. Back up your customized docker-compose YAML and env files.

    cd docker
cp docker-compose.yaml docker-compose.yaml.$(date +%s).bak
cp .env .env.$(date +%s).bak 2>/dev/null || true

  2. Get the latest code from the release branch or tag.

    git fetch --tags
git checkout 1.16.0

  3. Stop the service. Please execute in the docker directory.

    docker compose down

  4. Back up data.

    tar -cvf volumes-$(date +%s).tgz volumes

  5. Review the new environment variables (especially DIFY_AGENT_SERVER_SECRET_KEY) and update your .env file. Re-apply any local customizations.

  6. Upgrade services.

    docker compose up -d

  1. Stop the API server, Worker, and Web frontend Server.

  2. Get the latest code from the release tag.

    git fetch --tags
git checkout 1.16.0

  3. Update Python dependencies.

    cd api
uv sync

  4. Run the migration script.

    uv run flask db upgrade

  5. Configure the new Agent backend service. Refer to the dify-agent section in docker/envs/core-services/dify-agent.env.example for required environment variables.

  6. Restart the API server, Worker, and Web frontend Server.
