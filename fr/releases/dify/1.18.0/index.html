dify 1.18.0

Mineure Publié23 oct. 2026 Sourcelanggenius/dify Anglais original

modifier 1.18.0

Dify 1.18.0 apporte des agents qui acheminent les flux de travail, des packages d'applications portables, une visibilité plus approfondie des exécutions de flux de travail imbriquées et l'expérience facultative Base de connaissances des agents. OpenAPI et le nouveau difyctl élargissent la façon dont vous créez et gérez des applications à partir de la ligne de commande.

[!IMPORTANT] Lisez le guide de mise à niveau ci-dessous avant le déploiement. Mettez à niveau ensemble les images du API, des Workers, du backend de l'agent et du runtime de l'agent. Les sandbox de l'agent local nécessitent un jeton d'authentification non vide et le backend de l'agent utilise un nouveau protocole d'exécution. Les installations sources nécessitent Python 3.13. Installez le nouveau difyctl client et reconnectez-vous. Conservez votre configuration PASSWORD_PEPPER existante.

Points forts de la version

Agents qui choisissent l'étape suivante

Laissez un agent décider quelle branche de workflow prendre. Activez Routes de sortie, attribuez à chaque route une condition de sélection et connectez-la à l'étape suivante, par exemple résoudre une demande directement ou la transmettre à un spécialiste. La sortie switch en lecture seule expose l'itinéraire choisi. (#42599)

Configuration des routes de sortie avec deux branches dans l'éditeur de workflow.

Les nœuds Plain Agent v2 diffusent également le texte au fur et à mesure de sa génération. Les résultats structurés, les résultats routés et les nœuds utilisant la gestion des erreurs par valeur par défaut restent mis en mémoire tampon. (#43986)

Applications portables dans un seul package

Déplacez une application avec ses ressources prises en charge dans un seul package .ifpkg. Les packages Workflow et Chatflow contiennent des agents, des compétences et leurs fichiers en ligne ; les importations recréent ces ressources dans l’espace de travail de destination et remapper les références. Les importations de fichiers et d'URL prennent en charge à la fois les packages et YAML, et l'exportation explicite YAML reste disponible. (#42066, #42579, #42626, #42863)

Aperçu de l'importation .ifpkg de Studio.

Voir les exécutions de workflow imbriquées

Ouvrez un appel de Workflow Tool à partir de l'historique d'exécution et inspectez les étapes individuelles du workflow enfant. Les outils imbriqués s'exécutent désormais sous forme de graphiques enfants avec des sorties coordonnées de pause, de reprise, d'arrêt et de fichier. Les contrôles d'accès protègent les détails de l'application source. (#40277, #42819, #42820, #42821, #42822)

Retracez l'exploration d'un appel réussi de Workflow Tool.

L'utilisation imbriquée et les totaux d'étapes peuvent toujours être approximatifs, en particulier après une pause ou un arrêt. L'exploration de la console et l'exportation de traces externes ont des portées différentes ; voir les détails complets des fonctionnalités ci-dessous.

Base de connaissances des agents · Bêta

Créez un espace de connaissances pour vos agents, ajoutez des fichiers ou connectez des sources, et inspectez le traitement des documents, les métadonnées, les traces de récupération et les évaluations de qualité en un seul endroit. Le nouveau nœud de récupération de connaissances et les intégrations d'agent partagent des espaces KnowledgeFS à accès contrôlé. Les connaissances classiques restent disponibles. Il s'agit d'une intégration facultative avec un service et une base de données distincts ; consultez les exigences de déploiement ci-dessous. (#44165)

Sera bientôt disponible sur cloud.dify.ai

Pleins feux sur les développeurs

Créez et gérez des applications avec OpenAPI et difyctl. Le CLI découvre les commandes du catalogue d'opérations du serveur, avec une aide consultable et une prise en charge de la création de flux de travail et de chatflow, de l'importation/exportation DSL, des paramètres, des variables d'environnement, de la publication et de la restauration de version. Les brouillons de hachage protègent les modifications simultanées. (#42487, #42608, #43067)

Installez la compétence fournie pour les agents qui créent des applications Dify :

difyctl install skills <dir>

Le nouveau client nécessite une nouvelle connexion ; consultez les instructions de déploiement ci-dessous. (#43819)

Guide de mise à niveau

Compatibilité et déploiement

  1. Sauvegardez d'abord. Conservez la base de données, les données du magasin vectoriel, les fichiers téléchargés, le stockage des instantanés/espace de travail de l'agent, ainsi que tous les secrets de déploiement et les fichiers d'environnement. Utilisez une fenêtre de maintenance pour une mise à niveau à pile unique.
  2. Mettez à niveau les composants de l'agent ensemble. /runs accepte désormais la composition v2 et rejette les requêtes v1. Les instantanés de session existants sont convertis lors de la lecture et enregistrés au format v2 ; les anciens environnements d'exécution ne peuvent pas lire les instantanés v2 nouvellement enregistrés. Les intégrations Direct Agent Backend doivent mettre à jour leur format de demande. L'ancien outil AskHuman spécifique à l'agent et le chemin de reprise différée sont supprimés : les formulaires d'agent historiques ne reprennent plus l'exécution, tandis que les nœuds de saisie humaine de workflow partagés restent pris en charge. (#43833)
  3. Retirez les anciens consommateurs de flux de travail avant d'admettre le trafic de la nouvelle version. Laissez les exécutions en cours se terminer, puis remplacez les anciens travailleurs/consommateurs de reprise afin qu'ils ne puissent pas traiter la file d'attente partagée sans les nouvelles protections d'annulation. Les anciens ID de tâches suspendues peuvent être récupérés à partir d'instantanés d'appel enregistrés valides dans la portée d'accès existante ; les instantanés manquants ou non valides nécessitent une récupération séparée. Les totaux d'utilisation imbriqués conservent la limitation indiquée ci-dessus. (#40277)
  4. Configurez le jeton sandbox local avant le redémarrage. Fournissez un secret à haute entropie via la source d'interpolation Compose partagée. L'image d'exécution 1.17.1 ne prend pas en charge le nouvel indicateur --require-auth-token ; déployez les images correspondantes du backend de l'agent 1.18.0 et du bac à sable local. (#44152)
  5. Conserver la configuration de hachage du mot de passe. Les installations existantes sans pepper doivent laisser PASSWORD_PEPPER vide. La configuration d'un nouveau pepper lors de la mise à niveau n'est pas une migration transparente et nécessite un plan explicite de réinitialisation du mot de passe. Conservez tout pepper configuré inchangé dans toutes les instances et restaurez-le avec la base de données.
  6. Vérifiez la limite du proxy. L'ensemble Nginx remplace X-Forwarded-For par son adresse résolue client, ​​et Compose permet la gestion des en-têtes transférés. Limitez l'accès direct au API aux appelants trust. Si un équilibreur de charge ou Cloudflare se trouve avant Nginx, configurez-y la gestion de l'adresse IP réelle du trusted ; sinon, les visiteurs peuvent partager la tranche de limite de débit du proxy. Voir Proxies client IP et trusted.
  7. Activez KnowledgeFS délibérément. Les installations de Compose par défaut le désactivent ; Le développement de l'édition communautaire locale nécessite l'adhésion explicite au développement communautaire. Configurez sa base de données et ses migrations distinctes, le vérificateur public Capability v2, les clés de signature Dify, le profil de modèle (intégration, raisonnement et reclassement) et les portes de basculement de Workspace avant d'activer le trafic. Le service optionnel doit réussir /ready, pas seulement /health. Les images Dify API standard ne contiennent pas le moteur KnowledgeFS distinct utilisé par le profil de moteur-travailleur facultatif ; l'image KnowledgeFS API par défaut publiée est actuellement uniquement amd64. Suivez le [Guide de déploiement et de récupération KnowledgeFS] (https://github.com/langgenius/dify/blob/laipz8200/release-1.18.0/docker/README.md#knowledgefs-integration-service).

Docker Composer

Gardez les migrations de bases de données activées (MIGRATION_ENABLED=true) pour le démarrage du API ou exécutez-les via votre processus de migration géré avant de démarrer de nouveaux travailleurs. uv sync --project api --frozen
uv run --directory api flask db upgrade
pnpm install --frozen-lockfile

Reconstruisez l'application Web et redémarrez les services API, Worker, Planificateur et Agent à partir de la même version. Si vous déployez Agent Backend séparément de la source, actualisez également ses dépendances server verrouillées.

Modifications détaillées

<détails>

<summary><strong>Nouvelles fonctionnalités · capacités et disponibilité complètes</strong></summary>

Base de connaissances des agents et KnowledgeFS

  • Ajoutez l'expérience de l'espace de connaissances bêta avec un aperçu du téléchargement local, la gestion des sources connectées, la disponibilité et les métadonnées des documents, l'historique/la recherche de récupération et l'évaluation de la qualité. Les paramètres contrôlent l'accès à l'application, à l'agent et au service API. Classic Knowledge reste pris en charge à ses côtés. (#44165)
  • Les liaisons de connaissances Knowledge Retrieval v2 et Agent utilisent des fonctionnalités étendues ; publié Explore exécute la réutilisation des liaisons publiées sans que les utilisateurs ordinaires aient besoin de reconfigurer l'accès. (#44165)
  • Les mises à niveau de l'ensemble de données classique disposent de points de contrôle durables, d'un rapprochement disponibilité/métadonnées, d'une protection contre les nouvelles tentatives et d'une récupération via Beat. Exécutez le programme de mise à niveau dédié avec le pool de préfork et les limites de tâches documentés ; appliquez b9d3f7a5c102 avant de redémarrer API/workers/Beat. L'inscription au service ne migre pas automatiquement tous les ensembles de données Classic. (#44165)

Forfaits d'applications portables

  • Les exportations d'applications sont désormais par défaut vers .ifpkg, regroupant la configuration de l'application et ses ressources prises en charge dans un seul package portable. L'exportation explicite YAML reste disponible et les importations acceptent les deux formats de fichiers ou d'URL. (#42066, #42189, #42425, #42552)
  • Les packages Workflow et Chatflow incluent les agents en ligne, leurs compétences et les fichiers de l'instantané de configuration lié à chaque nœud. Les importations recréent ces agents dans l'espace de travail de destination et remappent leurs ressources. Les icônes d'application, les paramètres du site et les dépendances du plug-in de nœud sont inclus dans le flux d'exportation. Les ressources manquantes sont signalées lors de l'importation. (#42579, #42626, #42816, #42863, #42913)
  • Les exports d'agent peuvent cibler une version publiée. Les menus de la version de l'agent proposent désormais la restauration, et les sauvegardes en attente se terminent avant la restauration afin que la sauvegarde automatique ne puisse pas écraser la configuration restaurée. La duplication et l'exportation des compétences utilisent le dernier brouillon de contenu enregistré. (#42485, #42567, #42424, #42502)

Outils de flux de travail imbriqués et analyse des traces

  • Les outils de workflow appelés s'exécutent en tant que graphiques enfants sous le moteur de workflow, avec des sorties coordonnées de pause, de reprise, d'arrêt et de fichier. Les graphiques sources sont capturés avant l'exécution, donc la republication d'un outil ne modifie pas une exécution en cours, y compris les appels dans les boucles et les itérations. (#40277, #42820)
  • Les vues Workflow, Chatflow et historique peuvent ouvrir un appel d'outil particulier et parcourir ses traces d'exécution internes. L'accès à chaque application source est requis avant que ses détails ne soient renvoyés. Les formulaires de saisie humaine sont suivis par identité d'exécution, y compris les invocations répétées du même nœud. (#42819, #42821, #42822)
  • Les journaux d'agent imbriqués et les enregistrements d'utilisation conservent leur identité de flux de travail source et leur relation avec l'exécution externe. L'utilisation imbriquée et les totaux d'étapes peuvent toujours être approximatifs, en particulier après des pauses ou des arrêts. (#42824, #42820)

Routes de sortie et streaming de l'agent

  • Les nœuds Agent v2 peuvent sélectionner une branche de workflow dans le cadre de l'exécution de leur tâche. Activez les itinéraires de sortie, définissez au moins deux branches et leurs conditions de sélection, et utilisez la sortie switch en lecture seule pour inspecter l'itinéraire choisi. Avec le routage désactivé, la prise de succès normale reste disponible. Les nœuds routés prennent en charge l'arrêt en cas d'erreur ou la prise d'une branche en échec ; La gestion des valeurs par défaut au niveau du nœud n'est pas disponible avec les routes activées. (#42599)
  • Les nœuds Plain Agent v2 diffusent le texte au fur et à mesure de sa génération. Les résultats structurés ou routés restent mis en mémoire tampon, et les nœuds utilisant la gestion des erreurs par valeur par défaut restent mis en mémoire tampon afin que la solution de repli configurée puisse toujours remplacer un résultat ayant échoué. (#43986)

Créez et gérez des applications avec OpenAPI et difyctl

  • /openapi/v1 édite un catalogue d'exploitation du serveur. difyctl découvre les commandes et leurs champs de saisie à partir de ce catalogue, fournit une aide consultable et suit les étapes suivantes fournies par le serveur. La création de Workflow et Chatflow couvre désormais la création d'applications, l'importation/exportation DSL, les paramètres, les variables d'environnement, la publication et la restauration de version. Les brouillons de hachage protègent les importations contre l’écrasement des modifications simultanées. (#42487, #42608, #43067)
  • Le CLI comprend une compétence difyctl pour les agents créant des applications Dify. Installez-le avec difyctl install skills <dir>. La connexion à l'appareil prend en charge --no-wait et --resume, et les téléchargements de dossiers envoient une partie en plusieurs parties par fichier. (#43819, #44356)
  • Les propriétaires d'espace de travail peuvent créer des jetons d'accès aux ressources liés aux applications ou bases de connaissances sélectionnées. Les jetons fonctionnent avec les itinéraires du service API pris en charge et les opérations d'application dans difyctl ; ils n'accordent pas l'administration de l'espace de travail. L'entrée Paramètres est activée via NEXT_PUBLIC_ENABLE_ACCESS_TOKEN, qui est par défaut false. (#42293, #44422)

Modifier les invites de l'agent depuis le bac à sable

  • dify-agent config prompt pull [--to PATH] et push [PATH|-] lisent ou remplacent l'invite système brute, en préservant l'UTF-8, les espaces et les marqueurs de mention. Un texte vide l'efface. Seule la version préliminaire inscriptible du compte actuel peut être modifiée ; les demandes ultérieures utilisent l'invite enregistrée. (#44561)

Traçage de l'exécution des agents

  • Les applications d'agent et les nœuds Workflow Agent v2 peuvent exporter leurs arborescences d'exécution d'agent, de modèle et d'outil via les fournisseurs de traçage existants. La surveillance ajoute la configuration du traçage partagé, l'état de livraison, les contrôles de nouvelle tentative et les liens vers la trace appartenant à l'exécution sélectionnée. Les agents référencés par un Workflow héritent de la politique de traçage de l'appelant. (#44144, #44186)
  • Le suivi des applications est facultatif sur le API et l'Agent Backend. Un exportateur de trajectoire OTLP distinct à l’échelle du déploiement est également disponible, indépendamment du traçage du système. (#42651, #44144)
  • Les nœuds internes appelés Workflow Tools sont exclus des exportations externes car ces exportations n'ont pas d'identité de spectateur pour les contrôles d'accès à l'application source. Les agents à l'intérieur de ces outils sont également exclus de la nouvelle exportation de l'arborescence d'exécution pour le moment ; L’exploration autorisée de la console reste disponible. (#42823, #44144)

Backend OpenShell Sandbox et collection d'utilisations E2B

  • L'exécution de l'agent peut utiliser une passerelle NVIDIA OpenShell auto-hébergée avec DIFY_AGENT_RUNTIME_BACKEND=openshell. Chaque liaison possède son propre bac à sable, avec un accès au shell authentifié, des instantanés d'accueil sur un volume partagé géré par l'opérateur et une liste d'autorisation de sortie facultative. La passerelle OpenShell 0.0.106 ou plus récente et une image d'exécution compatible sont requises. (#41076)
  • La version de bail OpenShell ferme la connexion mais laisse le bac à sable en cours d'exécution. Il n’y a pas de TTL d’arrêt automatique au ralenti ou de bac à sable ; les opérateurs doivent gérer ces ressources. Les déploiements multi-locataires nécessitent des espaces de travail OpenShell et des volumes d'instantanés distincts par locataire. Consultez le Guide de déploiement OpenShell.
  • La collecte facultative d'utilisation E2B enregistre la durée d'exécution du fournisseur et la taille des ressources via Celery Beat et la file d'attente ops_trace. La collecte démarre à partir d’une heure d’activation configurée et ne remplit pas les exécutions antérieures. Les indicateurs de mesure du API et de l'agent Backend sont désactivés par défaut. (#42554)

Contrôles d'accès au cloud, modèles et gestion des archives

  • Les groupes d'accès réseau réutilisables permettent aux déploiements Cloud pris en charge de partager des règles IP entre les applications, avec des contrôles d'autorisation, l'état de la politique effective et des aperçus trusted client-IP. L'application dépend du service de stratégie Cloud et de la passerelle ; il ne s'agit pas d'un pare-feu Community Edition autonome. (#41025, #44464)
  • Les utilisateurs du cloud peuvent prévisualiser et essayer les modèles d'agent publiés avant de les importer. L'agent « Créer à partir d'un modèle » est masqué dans les éditions Community et Enterprise, car sa source de données de modèle est uniquement Cloud. (#42837, #44035)
  • Dans Cloud Workflow Log Archives, les propriétaires d'espace de travail peuvent supprimer définitivement un mois sélectionné, avec confirmation, progression et réessayer. L'action supprime les objets archivés et les téléchargements ZIP préparés ; les enregistrements en direct exécutés par le flux de travail sortent de son champ d'application. Les tâches de suppression ayant échoué entrent désormais dans la stratégie de nouvelle tentative au lieu de signaler la réussite. (#44052, #44061, #44203)

dify 1.18.0

Dify 1.18.0 brings Agents that route workflows, portable app packages, deeper visibility into nested workflow runs, and the opt-in Agent Knowledge Base experience. OpenAPI and the new difyctl expand how you build and manage apps from the command line.

[!IMPORTANT] Read the upgrade guide below before deploying. Upgrade the API, workers, Agent Backend, and Agent runtime images together. Local Agent sandboxes require a non-empty authentication token, and Agent Backend uses a new run protocol. Source installations require Python 3.13. Install the new difyctl client and sign in again. Preserve your existing PASSWORD_PEPPER configuration.

Release highlights

Agents that choose the next step

Let an Agent decide which workflow branch to take. Enable Output Routes, give each route a selection condition, and connect it to the next step—such as resolving a request directly or handing it to a specialist. The read-only switch output exposes the chosen route. (#42599)

Output Routes configuration with two branches in the workflow editor.

Plain Agent v2 nodes also stream text as it is generated. Structured results, routed results, and nodes using default-value error handling remain buffered. (#43986)

Portable apps in one package

Move an app with its supported resources in a single .ifpkg package. Workflow and Chatflow packages carry inline Agents, Skills, and their files; imports recreate those resources in the destination workspace and remap references. File and URL imports support both packages and YAML, and explicit YAML export remains available. (#42066, #42579, #42626, #42863)

Studio's .ifpkg import preview.

See inside nested workflow runs

Open a Workflow Tool invocation from the run history and inspect the child workflow's individual steps. Nested tools now run as child graphs with coordinated pause, resume, stop, and file outputs. Access checks protect the source app's details. (#40277, #42819, #42820, #42821, #42822)

Trace drilldown into a successful Workflow Tool invocation.

Nested usage and step totals can still be approximate, particularly after a pause or stop. Console drilldown and external trace export have different scopes; see the full feature details below.

Agent Knowledge Base · Beta

Create a knowledge space for your agents, add files or connect sources, and inspect document processing, metadata, retrieval traces, and quality evaluations in one place. The new Knowledge Retrieval node and Agent integrations share access-controlled KnowledgeFS spaces. Classic Knowledge remains available. This is an opt-in integration with a separate service and database; see the deployment requirements below. (#44165)

Will soon be available on cloud.dify.ai

Developer spotlight

Build and manage apps with OpenAPI and difyctl. The CLI discovers commands from the server's operation catalog, with searchable help and support for Workflow and Chatflow creation, DSL import/export, settings, environment variables, publishing, and version restoration. Draft hashes protect concurrent edits. (#42487, #42608, #43067)

Install the bundled skill for agents building Dify apps:

difyctl install skills <dir>

The new client requires a fresh sign-in; see the deployment instructions below. (#43819)

Upgrade guide

Compatibility and Rollout

  1. Back up first. Retain the database, vector-store data, uploaded files, Agent snapshot/workspace storage, and all deployment secrets and env files. Use a maintenance window for a single-stack upgrade.
  2. Upgrade the Agent components together. /runs now accepts composition v2 and rejects v1 requests. Existing session snapshots are converted on read and saved as v2; old runtimes cannot read newly saved v2 snapshots. Direct Agent Backend integrations must update their request format. The old Agent-specific AskHuman tool and deferred resume path are removed: historical Agent forms no longer resume execution, while shared Workflow Human Input nodes remain supported. (#43833)
  3. Retire old workflow consumers before admitting new-version traffic. Let in-flight runs finish, then replace legacy workers/resume consumers so they cannot process the shared queue without the new cancellation guards. Legacy paused task IDs can be recovered from valid saved invocation snapshots within the existing access scope; missing or invalid snapshots require separate recovery. Nested usage totals retain the limitation noted above. (#40277)
  4. Configure the Local sandbox token before restart. Supply a high-entropy secret through the shared Compose interpolation source. The 1.17.1 runtime image does not support the new --require-auth-token flag; deploy the matching 1.18.0 Agent Backend and Local sandbox images. (#44152)
  5. Preserve password hashing configuration. Existing installations without a pepper should leave PASSWORD_PEPPER empty. Setting a new pepper during the upgrade is not a transparent migration and requires an explicit password-reset plan. Keep any configured pepper unchanged across all instances and restore it with the database.
  6. Review the proxy boundary. Bundled Nginx replaces X-Forwarded-For with its resolved client address, and Compose enables forwarded-header handling. Keep direct API access restricted to trusted callers. If a load balancer or Cloudflare sits before Nginx, configure trusted real-IP handling there; otherwise visitors may share the proxy’s rate-limit bucket. See client IP and trusted proxies.
  7. Enable KnowledgeFS deliberately. Default Compose installations keep it off; local Community Edition development requires the explicit Community development opt-in. Configure its separate database and migrations, Capability v2 public verifier, Dify signing keys, model profile (embedding, reasoning, and rerank), and Workspace cutover gates before enabling traffic. The optional service must pass /ready, not only /health. Standard Dify API images do not contain the separate KnowledgeFS engine used by the optional engine-worker profile; the published default KnowledgeFS API image is currently amd64 only. Follow the KnowledgeFS deployment and recovery guide.

Agent Knowledge Base and KnowledgeFS

  • Add the Beta knowledge-space experience with local upload preview, connected-source management, document availability and metadata, retrieval history/research, and quality evaluation. Settings control app, Agent, and Service API access. Classic Knowledge remains supported alongside it. (#44165)

Run the dedicated upgrade worker with the documented prefork pool and task limits; apply b9d3f7a5c102 before restarting API/workers/Beat. Opting into the service does not automatically migrate all Classic datasets. (#44165)

Portable App Packages

  • App exports now default to .ifpkg, bringing the application configuration and its supported resources into one portable package. Explicit YAML export remains available, and imports accept both formats from files or URLs. (#42066, #42189, #42425, #42552)
  • Workflow and Chatflow packages include inline Agents, their Skills, and files from each node’s bound configuration snapshot. Imports recreate those Agents in the destination workspace and remap their resources. App icons, Site settings, and node plugin dependencies are included in the export flow. Missing resources are reported during import. (#42579, #42626, #42816, #42863, #42913)
  • Agent exports can target a published version. Agent version menus now offer Restore, and pending draft saves finish before restoration so autosave cannot overwrite the restored configuration. Skill duplication and export use the latest saved draft content. (#42485, #42567, #42424, #42502)

Nested Workflow Tools and Trace Drilldown

  • Called Workflow Tools run as child graphs under the workflow engine, with coordinated pause, resume, stop, and file outputs. Source graphs are captured before execution, so republishing a tool does not change an in-flight run, including calls inside loops and iterations. (#40277, #42820)
  • Workflow, Chatflow, and history views can open a particular tool invocation and navigate its internal execution traces. Access to each source application is required before its details are returned. Human Input forms are tracked by execution identity, including repeated invocations of the same node. (#42819, #42821, #42822)
  • Nested Agent logs and usage records retain their source workflow identity and their relationship to the outer run. Nested usage and step totals can still be approximate, particularly after pauses or stops. (#42824, #42820)

Agent Output Routes and Streaming

  • Agent v2 nodes can select a workflow branch as part of completing their task. Enable Output Routes, define at least two branches and their selection conditions, and use the read-only switch output to inspect the chosen route. With routing disabled, the normal success outlet remains available. Routed nodes support stopping on error or taking a failure branch; node-level default-value handling is unavailable with routes enabled. (#42599)
  • Plain Agent v2 nodes stream text as it is generated. Structured or routed results remain buffered, and nodes using default-value error handling stay buffered so the configured fallback can still replace a failed result. (#43986)

Build and Manage Apps with OpenAPI and difyctl

  • /openapi/v1 publishes a server operation catalog. difyctl discovers commands and their input fields from that catalog, provides searchable help, and follows server-provided next steps. Workflow and Chatflow authoring now covers app creation, DSL import/export, settings, environment variables, publishing, and version restoration. Draft hashes protect imports from overwriting concurrent edits. (#42487, #42608, #43067)
  • The CLI includes a difyctl skill for agents building Dify apps. Install it with difyctl install skills <dir>. Device login supports --no-wait and --resume, and folder uploads send one multipart part per file. (#43819, #44356)
  • Workspace owners can create resource access tokens bound to selected apps or knowledge bases. Tokens work with the supported Service API routes and app operations in difyctl; they do not grant workspace administration. The Settings entry is opt-in through NEXT_PUBLIC_ENABLE_ACCESS_TOKEN, which defaults to false. (#42293, #44422)

Edit Agent Prompts from the Sandbox

  • dify-agent config prompt pull [--to PATH] and push [PATH|-] read or replace the raw system prompt, preserving UTF-8, whitespace, and mention markers. Empty text clears it. Only the current account’s writable build draft can be changed; later requests use the saved prompt. (#44561)

Agent Execution Tracing

  • Agent apps and Workflow Agent v2 nodes can export their Agent, model, and tool execution trees through the existing tracing providers. Monitoring adds shared tracing configuration, delivery status, retry controls, and links to the trace belonging to the selected execution. Agents referenced by a Workflow inherit the caller’s tracing policy. (#44144, #44186)
  • Application tracing is opt-in on both the API and Agent Backend. A separate deployment-wide OTLP trajectory exporter is also available, independently of system tracing. (#42651, #44144)
  • Called Workflow Tools’ internal nodes are excluded from external exports because those exports have no viewer identity for source-app access checks. Agents inside those called tools are also excluded from the new execution-tree export for now; authorized Console drilldown remains available. (#42823, #44144)

OpenShell Sandbox Backend and E2B Usage Collection

  • Agent execution can use a self-hosted NVIDIA OpenShell gateway with DIFY_AGENT_RUNTIME_BACKEND=openshell. Each Binding has its own sandbox, with authenticated shell access, Home Snapshots on an operator-managed shared volume, and an optional egress allowlist. OpenShell gateway 0.0.106 or newer and a compatible runtime image are required. (#41076)
  • OpenShell lease release closes the connection but leaves the sandbox running. There is no automatic idle-stop or sandbox TTL; operators must manage those resources. Multi-tenant deployments require separate OpenShell workspaces and snapshot volumes per tenant. See the OpenShell deployment guide.
  • Optional E2B usage collection records provider execution duration and resource sizes through Celery Beat and the ops_trace queue. Collection starts from a configured activation time and does not backfill earlier executions. Both the API and Agent Backend metering flags default to off. (#42554)

Cloud Access Controls, Templates, and Archive Management

  • Reusable network access groups let supported Cloud deployments share IP rules across apps, with permission checks, effective-policy status, and trusted client-IP previews. Enforcement depends on the Cloud policy service and Gateway; this is not a standalone Community Edition firewall. (#41025, #44464)
  • Cloud users can preview and try published Agent templates before importing them. Agent “Create from Template” is hidden in Community and Enterprise editions because its template data source is Cloud-only. (#42837, #44035)
  • In Cloud Workflow Log Archives, workspace owners can permanently delete a selected month, with confirmation, progress, and retry. The action removes archived objects and prepared ZIP downloads; live workflow-run records are outside its scope. Failed deletion jobs now enter the retry policy instead of reporting success. (#44052, #44061, #44203)
