Nouvelles fonctionnalités

difyctl — pilotez Dify à partir de la ligne de commande (Docs)

  • difyctl est un client en ligne de commande pour Dify : vous pouvez désormais exécuter des applications et des workflows directement depuis votre terminal, afin que les agents personnels, les scripts et les pipelines CI puissent appeler les workflows Dify sans ouvrir l'interface utilisateur Web (#37036)
  • Installez-le sur n'importe quelle plateforme (macOS, Linux, Windows) avec une seule commande et sans jeton d'accès — les binaires sont publiés sous forme de versions publiques avec vérification de la somme de contrôle (#37036, #37454)
  • Transmettez les variables d'environnement étendues aux exécutions de l'outil CLI et obtenez des messages d'erreur plus clairs et cohérents (y compris une gestion conviviale des limites de débit) à la fois sur difyctl et sur le /openapi/v1 API (#37324, #37285, #37313, #36896)

Voir CoT dans Workflow & Chatflow & CLI

  • Chat Flow/Workflow peut désormais diffuser le raisonnement du modèle dans un panneau de « réflexion » en direct dédié tout en gardant la réponse finale claire et lisible. Le raisonnement est conservé afin qu'il soit toujours là après une actualisation de la page, et le même raisonnement est visible dans CLI et les aperçus d'exécution du flux de travail (#37460, #37828)

Formulaires Human-in-the-Loop plus riches

  • Lorsqu'un flux de travail s'arrête pour demander une contribution à une personne, le formulaire peut désormais inclure des sélections déroulantes et des téléchargements de fichiers/multi-fichiers - pas seulement du texte libre - afin que les utilisateurs puissent répondre avec des choix structurés et des pièces jointes (#36322)

Prise en charge des modèles lents et de longue durée

  • Les workflows peuvent désormais utiliser des modèles de génération qui mettent beaucoup de temps à répondre (comme la génération d'images ou de vidéos) via un mécanisme d'interrogation : le nœud attend patiemment le résultat final au lieu d'expirer (#37462)

Connaissances issues de feuilles de calcul plus riches

  • Les images intégrées dans les fichiers Excel sont désormais extraites lors de l'importation des connaissances, de sorte que le contenu des feuilles de calcul qui repose sur des images (schémas, captures d'écran, graphiques) n'est plus perdu (#37104)

Observabilité plus approfondie

  • Définissez votre propre identifiant de session de trace pour Phoenix afin que les traces s'alignent sur les sessions de votre application et suivez les étapes de récupération de documents dans les traces pour comprendre comment les résultats RAG ont été produits (#37056, #37283)

Peaufinage de la création de workflow

  • Un nœud de démarrage actualisé rend plus clair le début d'un flux de travail, et un nœud de sortie plus intelligent vous donne plus de contrôle sur ce qu'un flux de travail renvoie (#37348, #35511)
  • Des erreurs plus conviviales lorsqu'un ID d'application ou d'espace de travail est mal formé, au lieu d'échecs déroutants (# 37212)

Installations de plugins plus rapides dans certaines régions

  • Le démon du plugin détecte désormais automatiquement votre région au démarrage et, lorsque la connectivité réseau à PyPI est mauvaise, sélectionne automatiquement un miroir de package à proximité - l'installation des plugins est donc plus rapide et plus fiable sans aucune configuration manuelle. Vous pouvez toujours épingler un miroir spécifique si vous préférez (dify-plugin-daemon#750)

Mises à jour de sécurité

Cette version corrige un problème de traversée de chemin dans le transfert de plugin-daemon (cve-2026-41948).

Corrections de bugs

  • HTTP sortant renforcé avec des délais d'attente limités pour les requêtes Firecrawl, Jina, Watercrawl, Nacos et Marketplace, et une sortie proxy SSRF par défaut renforcée (#37638, #37637, #37515, #37444, #37424, #36332)
  • Correction des erreurs du magasin de vecteurs Lindorm causées par la mise à jour opensearch-py (#37862) et la compatibilité des informations d'identification Tongyi (#37942)
  • Cache d'identifiants invalidé après l'actualisation OAuth (#37630)
  • Amélioration de la gestion des erreurs d'exécution du flux de travail, conversations validées avec impatience pour éviter les blocages et prévention des arrêts hérités d'interrompre les exécutions de GraphEngine (# 37919, # 37224, # 37129)
  • Résolution de DetachedInstanceError via la refactorisation de la gestion de session (#37847) et hydratation de l'état de déploiement stabilisé (#37818)
  • Correction de la validation de la longueur de la description des variables de conversation pour empêcher la troncature de varchar(255) (#33038) et stockage du chinois au format Unicode pour que la recherche fonctionne (#37446).
  • De nombreuses corrections de finition de l'interface utilisateur Web et de l'accessibilité/de la bague de mise au point

Améliorations

  • Gestion des sessions refactorisée entre les services pour accepter explicitement db.session via l'injection de dépendances pour plus de cohérence (#37639, #37832, #37695, #37694 et associés)
  • Typage modernisé (suppression des type: ignore/cast redondants, conversion des ABC en Protocol, remplacement des chaînes isinstance par match-case)
  • Réduction de la latence de démarrage du workflow pour Chatflow (#36773) et réduction de la latence de fin du workflow afin que l'arrêt d'une exécution prenne effet plus rapidement (#37106, #37129)
  • Dépendances mises à niveau pour les correctifs CVE (Bleach, PyJWT, starlette, groupe de stockage) (#37860, #37008, #37076, #37861)

Guide de mise à niveau

Migration des types de modèles

[!IMPORTANT]

Migration unique du type de modèle hérité pour les mises à niveau auto-hébergées

Si ce déploiement a été mis à niveau à partir d'une version de Dify antérieure à 1.15.0 et que cette migration n'a pas déjà été appliquée, exécutez-la après la mise à niveau.

Cette migration n'est pas incluse dans flask db upgrade. Sans cela, les enregistrements de modèles existants peuvent entraîner l'échec des requêtes API liées au modèle avec des erreurs, empêchant ainsi le chargement ou l'utilisation des modèles concernés.

Sauvegardez la base de données avant d'appliquer la migration. La commande s'exécute en mode d'exécution à sec par défaut ; examinez la sortie avant de la réexécuter avec --apply. La migration est idempotente et peut être réexécutée en toute sécurité.

Docker Composer

Exécuté à partir du répertoire docker.

# Apply after reviewing the dry-run output
docker compose exec -T api flask data-migrate legacy-model-types --apply \
  > legacy-model-types-apply.jsonl

Déploiement du code source

Exécutez à partir de la racine du référentiel après avoir terminé flask db upgrade.

# Apply after reviewing the dry-run output
uv run --project api flask data-migrate legacy-model-types --apply \
  > legacy-model-types-apply.jsonl

Après avoir appliqué la migration, exécutez à nouveau la commande d'exécution à sec. S'il ne signale aucune mise à jour ou suppression de lignes supplémentaires, redémarrez les services concernés et vérifiez que les modèles existants peuvent être chargés et appelés avec succès.

[!IMPORTANT]

  • Cette version inclut de nouvelles migrations de bases de données. Exécutez-les dans le cadre de la mise à niveau.
  • La mise à niveau automatique du plugin est désormais configurée par catégorie de plugin. Après avoir exécuté flask db upgrade, vous DEVEZ également exécuter flask backfill-plugin-auto-upgrade pour migrer les paramètres de mise à niveau automatique des locataires existants vers le nouveau modèle de catégorie. Si vous ignorez cette étape, les paramètres de mise à niveau automatique du plugin précédemment configurés par les utilisateurs peuvent cesser de prendre effet.
  • Variables d'environnement modifiées (19 ajoutées, 2 supprimées, 1 modifiée). Consultez la section Modifications des variables d'environnement et mettez à jour votre .env en conséquence.
  • Docker Les fichiers de configuration de Compose ont été modifiés. Si vous conservez un docker-compose.yaml personnalisé, examinez les modifications et réappliquez soigneusement les personnalisations locales.

    docker compose up -d

New Features

difyctl — drive Dify from the command line (Docs)

  • difyctl is a command-line client for Dify: you can now run apps and workflows straight from your terminal, so personal agents, scripts, and CI pipelines can invoke Dify workflows without opening the web UI (#37036)
  • Install it on any platform (macOS, Linux, Windows) with a single command and no access token — binaries are published as public releases with checksum verification (#37036, #37454)
  • Pass scoped environment variables to CLI tool runs, and get clearer, consistent error messages (including friendly rate-limit handling) across both difyctl and the /openapi/v1 API (#37324, #37285, #37313, #36896)

See CoT in Workflow & Chatflow & CLI

  • Chat Flow / Workflow can now stream the model's reasoning into a dedicated live "thinking" panel while keeping the final answer clean and readable. The reasoning is preserved so it's still there after a page refresh, and the same reasoning is visible in CLI and workflow run previews (#37460, #37828)

Richer Human-in-the-Loop forms

  • When a workflow pauses to ask a person for input, the form can now include dropdown selects and file / multi-file uploads — not just free text — so people can answer with structured choices and attachments (#36322)

Support for slow, long-running models

  • Workflows can now use generation models that take a long time to respond (such as image or video generation) via a polling mechanism: the node patiently waits for the final result instead of timing out (#37462)

Knowledge from richer spreadsheets

  • Images embedded inside Excel files are now extracted during knowledge import, so spreadsheet content that relies on pictures (diagrams, screenshots, charts) is no longer lost (#37104)

Deeper observability

  • Set your own trace session id for Phoenix so traces line up with your application's sessions, and follow document-retrieval steps in traces to understand how RAG results were produced (#37056, #37283)

Workflow authoring polish

  • A refreshed start node makes it clearer how a workflow begins, and a smarter output node gives you more control over what a workflow returns (#37348, #35511)
  • Friendlier errors when an app or workspace ID is malformed, instead of confusing failures (#37212)

Faster plugin installs in certain regions

  • The plugin daemon now auto-detects your region at startup and, where network connectivity to PyPI is poor, automatically picks a nearby package mirror — so installing plugins is faster and more reliable without any manual setup. You can still pin a specific mirror if you prefer (dify-plugin-daemon#750)

Security Updates

This release fixes a path traversal issue in plugin-daemon forwarding (cve-2026-41948).

Upgrade Guide

Model Type Migration

[!IMPORTANT]

One-time legacy model type migration for self-hosted upgrades

If this deployment was upgraded from a Dify version earlier than 1.15.0 and this migration has not already been applied, run it after upgrading.

This migration is not included in flask db upgrade. Without it, legacy model records can cause model-related API requests to fail with errors, preventing affected models from being loaded or used.

Back up the database before applying the migration. The command runs in dry-run mode by default; review the output before rerunning it with --apply. The migration is idempotent and can be safely rerun.

Docker Compose

Run from the docker directory.

# Apply after reviewing the dry-run output
docker compose exec -T api flask data-migrate legacy-model-types --apply \
  > legacy-model-types-apply.jsonl

Source Code Deployment

Run from the repository root after completing flask db upgrade.

# Apply after reviewing the dry-run output
uv run --project api flask data-migrate legacy-model-types --apply \
  > legacy-model-types-apply.jsonl

After applying the migration, run the dry-run command again. If it reports no additional row updates or deletions, restart the relevant services and verify that existing models can be loaded and invoked successfully.

[!IMPORTANT]

  • This release includes new database migrations. Run them as part of the upgrade.
  • Plugin auto-upgrade is now configured per plugin category. After running flask db upgrade, you MUST also run flask backfill-plugin-auto-upgrade to migrate existing tenants' auto-upgrade settings into the new category-scoped model. If you skip this step, plugin auto-upgrade settings users previously configured may stop taking effect.
  • Environment variables changed (19 added, 2 removed, 1 modified). Review the Environment Variable Changes section and update your .env accordingly.
  • Docker Compose configuration files changed. If you maintain a customized docker-compose.yaml, review the changes and re-apply local customizations carefully.

Docker Compose Deployments

  1. Back up your customized docker-compose YAML and env files. 
    cd dockercp docker-compose.yaml docker-compose.yaml.$(date +%s).bakcp .env .env.$(date +%s).bak 2>/dev/null || true
  2. Get the latest code for the 1.15.0 release. 
    git fetch --tagsgit checkout 1.15.0
  3. Stop the services (run inside the docker directory). 
    docker compose down
  4. Back up data. 
    tar -cvf volumes-$(date +%s).tgz volumes
  5. Review any env file changes and re-apply local customizations.
  6. Upgrade services. 
    docker compose up -d
  7. Backfill category-scoped plugin auto-upgrade strategies (required). 
    docker compose exec api flask backfill-plugin-auto-upgrade

Source Code Deployments

  1. Stop the API server, Worker, and Web frontend server.
  2. Get the latest code for the 1.15.0 release. 
    git fetch --tagsgit checkout 1.15.0
  3. Update Python dependencies. 
    cd apiuv sync
  4. Run database migrations. 
    uv run flask db upgrade
  5. Backfill category-scoped plugin auto-upgrade strategies (required). 
    uv run flask backfill-plugin-auto-upgrade
  6. Restart the API server, Worker, and Web frontend server.
