🚀 Nouvelles fonctionnalités

Humain dans la boucle (HITL)

Nous introduisons le nœud Human Input, une mise à jour majeure qui transforme la façon dont l'IA et les humains collaborer au sein des workflows Dify.

Contexte

Auparavant, les flux de travail étaient binaires : soit entièrement automatisés, soit entièrement manuels. Cela a créé un « espace trust » dans des scénarios à enjeux élevés où la vitesse de l’IA est nécessaire mais le jugement humain est essentiel. Avec HITL, nous faisons h la surveillance humaine est une partie native de l'architecture du flux de travail, vous permettant d'intégrer passez en revue les étapes directement dans le graphique d’exécution.

Capacités clés

  • Pause native du flux de travail : Insérez un nœud « Entrée humaine » pour suspendre l'exécution du flux de travail aux points de décision critiques.
  • Réviser et modifier : Le nœud génère une interface utilisateur dans laquelle les humains peuvent examiner les sorties de l'IA et modifier les variables (par exemple, modifier un brouillon ou corriger des données) avant que le processus ne continue.
  • Routage basé sur les actions : configurez des boutons personnalisés (comme « Approuver », « Rejeter » ou « Escalader ») qui déterminent le chemin suivant du flux de travail.
  • Méthodes de livraison flexibles : Les formulaires de saisie humaine peuvent être envoyés via Webapp ou Email. Dans les environnements cloud, la disponibilité de la livraison des e-mails peut dépendre des paramètres du forfait/des fonctionnalités.

🛠 Mises à jour de l'architecture

Pour prendre en charge le mécanisme de pause/reprise avec état requis par HITL et fournir des API d'abonnement aux événements, nous avons refactorisé le moteur d'exécution : Les exécutions en streaming basées sur un workflow et les exécutions Advanced Chat s'exécutent désormais dans les Workers Celery, tandis que les exécutions WORKFLOW sans streaming s'exécutent toujours dans le processus API. Tous les chemins de pause/reprise (par exemple, HITL) sont repris via Celery et les événements sont renvoyés via Redis Pub/Sub.

Pour les déploiements importants et les utilisateurs auto-hébergés :

Nous avons introduit une nouvelle file d'attente Céleri nommée workflow_based_app_execution. Même si les configurations standard fonctionnent immédiatement, les environnements à haut débit doivent envisager les optimisations suivantes pour garantir la stabilité et les performances :

  1. Scale Workers : ajustez le nombre de nœuds de calcul consommant la file d'attente workflow_based_app_execution en fonction de votre charge de travail spécifique.
  2. Redis dédié (facultatif) : Pour les déploiements à grande échelle, nous vous recommandons de configurer la nouvelle variable d'environnement PUBSUB_REDIS_URL pour pointer vers une instance Redis dédiée. L'utilisation du mode Cluster Redis avec Sharded PubSub est fortement conseillée pour garantir l'évolutivité horizontale.

⚠️ Remarque importante sur la mise à niveau

Nouvelle file d'attente de céleri requise : workflow_based_app_execution

Veuillez vous assurer que votre configuration de déploiement (Docker Compose, Helm Chart, etc.) inclut les nœuds de calcul écoutant la nouvelle file d'attente workflow_based_app_execution.
Cette file d'attente est requise pour les exécutions de streaming basées sur des workflows et pour tous les flux de reprise (par exemple, HITL) ; sinon, les exécutions en streaming et les tâches de reprise ne seront pas traitées.

🔧 Note opérationnelle

File d'attente supplémentaire pour le céleri : api_token

Si ENABLE_API_TOKEN_LAST_USED_UPDATE_TASK=true, assurez-vous que votre déploiement comporte également des collaborateurs qui écoutent api_token. Cette file d'attente est utilisée par la tâche de mise à jour par lots planifiée pour les horodatages du jeton API last_used_at.

⚙️ Modifications de configuration

Nous avons introduit plusieurs nouvelles variables d'environnement pour prendre en charge les changements architecturaux. Les déploiements à grande échelle doivent accorder une attention particulière aux configurations PubSub Redis pour garantir l'évolutivité.

  • PUBSUB_REDIS_URL (Critique) : Spécifie l'URL Redis utilisée pour la communication PubSub entre les travailleurs API et Celery. S'il est laissé vide, il correspond par défaut à la configuration standard REDIS_*.
  • PUBSUB_REDIS_CHANNEL_TYPE (Critique) : définit le type de canal pour les événements en streaming. Les options sont pubsub (par défaut) ou sharded. Nous recommandons fortement d'utiliser sharded pour les environnements à haut débit.
  • PUBSUB_REDIS_USE_CLUSTERS (Critique) : défini sur true pour activer le mode cluster Redis pour PubSub. Combiné avec PubSub fragmenté, cela est essentiel pour la mise à l'échelle horizontale.

Autres ajouts :

  • WEB_FORM_SUBMIT_RATE_LIMIT_MAX_ATTEMPTS : nombre maximum de soumissions de formulaires Web autorisées par IP dans la fenêtre de limite de débit (par défaut : 30).
  • WEB_FORM_SUBMIT_RATE_LIMIT_WINDOW_SECONDS : Fenêtre de temps en secondes pour la limitation du taux de soumission des formulaires Web (par défaut : 60).
  • HUMAN_INPUT_GLOBAL_TIMEOUT_SECONDS : nombre maximal de secondes pendant lesquelles une exécution de flux de travail peut rester en pause en attendant une intervention humaine avant l'expiration du délai global (par défaut : 604800, 7 jours).
  • ENABLE_HUMAN_INPUT_TIMEOUT_TASK : active la tâche en arrière-plan qui vérifie les demandes d'entrée humaine expirées (par défaut : true).
  • HUMAN_INPUT_TIMEOUT_TASK_INTERVAL : définit l'intervalle (en minutes) pour la tâche de vérification du délai d'attente (par défaut : 1).
  • ENABLE_API_TOKEN_LAST_USED_UPDATE_TASK : active la tâche périodique en arrière-plan qui met à jour par lots les horodatages du jeton API last_used_at (par défaut : true).
  • API_TOKEN_LAST_USED_UPDATE_INTERVAL : définit l'intervalle (en minutes) pour la mise à jour par lots des horodatages du jeton API last_used_at (par défaut : 30).
  • SANDBOX_EXPIRED_RECORDS_CLEAN_BATCH_MAX_INTERVAL : délai aléatoire maximum (en millisecondes) entre les lots de nettoyage de rétention pour réduire les pics de pression de la base de données (par défaut : 200).

📌 Points forts supplémentaires du Changelog

Fiabilité et exactitude

  • Ajout de la déduplication au moment de la migration et d'une contrainte unique pour les modèles par défaut des locataires afin d'éviter les enregistrements de modèle par défaut en double.
  • Correction d'un cas limite de suppression d'outils causé par une incompatibilité de type d'ID de fournisseur.
  • Correction d'une régression d'intégration FastOpenAPI où les utilisateurs authentifiés pouvaient être résolus comme anonymes dans les fichiers distants API.
  • Correction de la détection du type d'événement de message pour les réponses liées aux fichiers et masquage de l'action d'invitation à l'espace de travail pour les utilisateurs non-gestionnaires.

Performances et évolutivité

  • Réduction de la charge du backend et de la latence de la console grâce à la pré-cache du manifeste du plugin et aux optimisations des requêtes AppListApi.
  • Amélioration de la stabilité des tâches de données volumineuses avec des sessions de base de données fractionnées, l'exécution de nettoyages par lots, le réglage des index et une limitation inter-lots configurable pour les tâches de nettoyage par rétention.

API et capacités de la plateforme

  • Ajout d'un point de terminaison de service API pour la recherche d'utilisateur final avec application de la portée du locataire/de l'application.
  • Amélioration du comportement d'actualisation de l'historique d'exécution du flux de travail lors des transitions d'état d'exécution.
  • Intégration améliorée de l'outil MCP en extrayant et en signalant les métadonnées d'utilisation (par exemple, les champs de jeton/coût) à partir des réponses MCP.

Sécurité

  • Suppression de l'évaluation dynamique new Function de l'analyse ECharts et renvoi désormais des erreurs d'analyse explicites pour le code de graphique non pris en charge.

Localisation

  • Ajout de la prise en charge de la langue néerlandaise (nl-NL) dans les ressources de mappage linguistique back-end et de localisation Web.

Docker Composer Déploiements

  1. Sauvegardez votre fichier docker-compose YAML personnalisé (facultatif)

    cd docker
cp docker-compose.yaml docker-compose.yaml.$(date +%s).bak

  2. Obtenez le dernier code de la branche principale

    git checkout main
git pull origin main

  3. Arrêtez le service. Veuillez exécuter dans le répertoire docker

    docker compose down

  4. Sauvegarder les données

    tar -cvf volumes-$(date +%s).tgz volumes

  5. Services de mise à niveau

    docker compose up -d

dify 1.13.0

🚀 New Features

Human-in-the-Loop (HITL)

We are introducing the Human Input node, a major update that transforms how AI and humans collaborate within Dify workflows.

Background

Previously, workflows were binary: either fully automated or fully manual. This created a "trust gap" in high-stakes scenarios where AI speed is needed but human judgment is essential. With HITL, we are making h uman oversight a native part of the workflow architecture, allowing you to embed review steps directly into the execution graph.

Key Capabilities

  • Native Workflow Pausing: Insert a "Human Input" node to suspend workflow execution at critical decision points.
  • Review & Edit: The node generates a UI where humans can review AI outputs and modify variables (e.g., editing a draft or correcting data) before the process continues.
  • Action-Based Routing: Configure custom buttons (like "Approve," "Reject," or "Escalate") that determine the subsequent path of the workflow.
  • Flexible Delivery Methods: Human input forms can be delivered via Webapp or Email. In cloud environments, Email delivery availability may depend on plan/feature settings.

🛠 Architecture Updates

To support the stateful pause/resume mechanism required by HITL and provide event‑subscription APIs, we refactored the execution engine: Workflow‑based streaming executions and Advanced Chat executions now run in Celery workers, while non‑streaming WORKFLOW runs still execute in the API process. All pause/resume paths (e.g., HITL) are resumed via Celery, and events are streamed back through Redis Pub/Sub.

For Large Deployments & Self-Hosted Users:

We have introduced a new Celery queue named workflow_based_app_execution. While standard setups will work out of the box, high-throughput environments should consider the following optimizations to ensure stability and performance:

  1. Scale Workers: Adjust the number of workers consuming the workflow_based_app_execution queue based on your specific workload.
  2. Dedicated Redis (Optional): For large-scale deployments, we recommend configuring the new PUBSUB_REDIS_URL environment variable to point to a dedicated Redis instance. Using Redis Cluster mode with Sharded PubSub is strongly advised to ensure horizontal scalability.

⚠️ Important Upgrade Note

New Celery Queue Required: workflow_based_app_execution

Please ensure your deployment configuration (Docker Compose, Helm Chart, etc.) includes workers listening to the new workflow_based_app_execution queue.
This queue is required for workflow‑based streaming executions and all resume flows (e.g., HITL); otherwise, streaming executions and resume tasks will not be processed.

🔧 Operational Note

Additional Celery Queue: api_token

If ENABLE_API_TOKEN_LAST_USED_UPDATE_TASK=true, ensure your deployment also has workers listening to api_token. This queue is used by the scheduled batch update task for API token last_used_at timestamps.

⚙️ Configuration Changes

We have introduced several new environment variables to support the architectural changes. Large deployments should pay special attention to the PubSub Redis configurations to ensure scalability.

  • PUBSUB_REDIS_URL (Critical): Specifies the Redis URL used for PubSub communication between the API and Celery workers. If left empty, it defaults to the standard REDIS_* configuration.
  • PUBSUB_REDIS_CHANNEL_TYPE (Critical): Defines the channel type for streaming events. Options are pubsub (default) or sharded. We highly recommend using sharded for high-throughput environments.
  • PUBSUB_REDIS_USE_CLUSTERS (Critical): Set to true to enable Redis cluster mode for PubSub. Combined with sharded PubSub, this is essential for horizontal scaling.

Other Additions:

  • WEB_FORM_SUBMIT_RATE_LIMIT_MAX_ATTEMPTS: Maximum number of web form submissions allowed per IP within the rate limit window (Default: 30).
  • WEB_FORM_SUBMIT_RATE_LIMIT_WINDOW_SECONDS: Time window in seconds for web form submission rate limiting (Default: 60).
  • HUMAN_INPUT_GLOBAL_TIMEOUT_SECONDS: Maximum seconds a workflow run can stay paused waiting for human input before global timeout (Default: 604800, 7 days).
  • ENABLE_HUMAN_INPUT_TIMEOUT_TASK: Enables the background task that checks for expired human input requests (Default: true).
  • HUMAN_INPUT_TIMEOUT_TASK_INTERVAL: Sets the interval (in minutes) for the timeout check task (Default: 1).
  • ENABLE_API_TOKEN_LAST_USED_UPDATE_TASK: Enables the periodic background task that batch-updates API token last_used_at timestamps (Default: true).
  • API_TOKEN_LAST_USED_UPDATE_INTERVAL: Sets the interval (in minutes) for batch-updating API token last_used_at timestamps (Default: 30).
  • SANDBOX_EXPIRED_RECORDS_CLEAN_BATCH_MAX_INTERVAL: Maximum random delay (in milliseconds) between retention cleanup batches to reduce DB pressure spikes (Default: 200).

📌 Additional Changelog Highlights

Reliability & Correctness

  • Added migration-time deduplication and a unique constraint for tenant default models to prevent duplicate default model records.
  • Fixed a tools-deletion edge case caused by provider ID type mismatch.
  • Fixed a FastOpenAPI integration regression where authenticated users could be resolved as anonymous in remote file APIs.
  • Fixed message event type detection for file-related responses, and hid the workspace invite action for non-manager users.

Performance & Scalability

  • Reduced backend load and console latency with plugin manifest pre-caching and AppListApi query optimizations.
  • Improved large-data task stability with split DB sessions, batched cleanup execution, index tuning, and configurable inter-batch throttling for retention cleanup jobs.

API & Platform Capabilities

  • Added a Service API endpoint for end-user lookup with tenant/app scope enforcement.
  • Improved workflow run history refresh behavior during run state transitions.
  • Enhanced MCP Tool integration by extracting and reporting usage metadata (for example, token/cost fields) from MCP responses.

Security

  • Removed dynamic new Function evaluation from ECharts parsing and now return explicit parsing errors for unsupported chart code.

Localization

  • Added Dutch (nl-NL) language support across backend language mapping and web localization resources.

Upgrade Guide

[!IMPORTANT] If you use custom CELERY_QUEUES, make sure workflow_based_app_execution is included.
If ENABLE_API_TOKEN_LAST_USED_UPDATE_TASK=true, also include api_token.

For background and details, see ⚠️ Important Upgrade Note and 🔧 Operational Note above.

Docker Compose Deployments

  1. Back up your customized docker-compose YAML file (optional)

    cd docker
cp docker-compose.yaml docker-compose.yaml.$(date +%s).bak

  2. Get the latest code from the main branch

    git checkout main
git pull origin main

  3. Stop the service. Please execute in the docker directory

    docker compose down

  4. Back up data

    tar -cvf volumes-$(date +%s).tgz volumes

  5. Upgrade services

    docker compose up -d
