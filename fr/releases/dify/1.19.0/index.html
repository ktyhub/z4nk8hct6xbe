modifier 1.19.0

Dify 1.19.0 apporte le traçage de flux de travail imbriqué à vos outils d'observabilité. Suivez un flux de travail dans les outils de flux de travail qu'il appelle, inspectez les étapes à l'intérieur de chaque appel et conservez le contexte LLM à côté de l'arborescence d'exécution.

Cette version rend également Workflow Tools portables avec les packages d'applications, ajoute l'automatisation du Skill Hub et facilite le téléchargement et la prévisualisation des fichiers d'agent. Le démon du plugin fourni est mis à niveau vers 0.6.14-local.

Points forts de la version · Guide de mise à niveau · Modifications détaillées

<a id="release-highlights"></a>

Points forts de la version

Traçage des flux de travail imbriqués

Découvrez ce qui se passe dans un outil de workflow, jusqu'à ses appels LLM.

S'appuyant sur l'exploration de la console introduite dans 1.18.0, de nouvelles traces externes incluent désormais les étapes d'exécution persistantes à l'intérieur appelées Workflow Tools. Les étapes enfants apparaissent sous l'étendue d'outils qui les a invoquées, préservant ainsi la hiérarchie entre les appels imbriqués et répétés. (#44673)

Du workflow externe à un appel LLM imbriqué : l'arborescence d'exécution et les messages formatés, ensemble dans Langfuse. Capture d'écran de #44673.

  • Suivez la hiérarchie. Développez appelé Workflow Tools pour voir leurs étapes d'exécution internes sous l'étendue de l'outil appelant.
  • Comprendre chaque invocation. Les appels répétés et les échecs conservent leur place dans la trace.
  • Conservez le contexte LLM. Inspectez les invites et les réponses formatées, l'utilisation des jetons et les liens de projet, de trace et d'observation.

[!NOTE] Vos paramètres de fournisseur enregistrés continuent de fonctionner. La hiérarchie plus riche s'applique aux nouvelles exécutions ; les traces historiques ne sont pas remblayées. Les exécutions de flux de travail imbriquées indépendamment restent des traces distinctes liées par des identifiants parents. Pour les déploiements continus, suivez la transition de la file d'attente de traçage ci-dessous.

Emportez des outils de workflow avec vos applications

Exportez une application et emportez avec elle les workflows derrière ses outils de workflow. Les packages .ifpkg incluent ces flux de travail dans leurs versions liées, y compris les dépendances transitives. Import réutilise les outils déjà présents dans l'espace de travail de destination et recrée, publie et enregistre ceux manquants, en remapping leurs références. (#44592)

Toutes les exportations d'applications Dify utilisent désormais le format de package v2, y compris les applications sans outils de workflow. Les importations v1 existantes et l'exportation explicite YAML restent prises en charge. Consultez le guide de mise à niveau avant d'importer de nouveaux packages dans des installations plus anciennes. (#45353)

Téléchargez ensemble. Aperçu en place.

Sélectionnez ou déposez plusieurs fichiers de configuration d'agent et téléchargez-les en parallèle. Les téléchargements réussis sont liés dans un seul lot atomique, les sauvegardes simultanées de Composer préservent les derniers fichiers et les téléchargements d'invite conservent la position du curseur lors de l'insertion de plusieurs références. (#44947)

Lisez les PDF en ligne, inspectez les fichiers sources avec la coloration syntaxique et voyez quand le texte a été tronqué. Les aperçus couvrent les fichiers configurés, les membres de compétence et les fichiers du répertoire de travail, avec une action de téléchargement lorsqu'un PDF ne peut pas être chargé. (#45032, #45045)

Ces opérations nécessitent l'activation d'un compte appelant, des autorisations d'espace de travail correspondantes et des compétences. L'importation ne publie pas. L'importation sur une compétence existante est classée comme destructrice ; le catalogue d'opérations et le CLI aident à distinguer les opérations de lecture, d'écriture et destructrices. <a id="upgrade-guide"></a>

Guide de mise à niveau

[!IMPORTANT] Lisez le guide de mise à niveau avant le déploiement. Docker Compose nécessite désormais v2.35.0 ou version ultérieure. Conservez les fichiers d'environnement existants, mettez à niveau les composants Dify ensemble et utilisez la nouvelle file d'attente de traçage lors des déploiements continus. Les nouveaux packages d’applications utilisent le format v2 et nécessitent un importateur de destination compatible. Le démon du plugin fourni est déplacé vers 0.6.14-local.

Compatibilité et déploiement

  1. Sauvegardez d'abord. Conservez la base de données, les données du magasin vectoriel, les fichiers téléchargés, le stockage des instantanés/espace de travail de l'agent, les secrets de déploiement et les fichiers d'environnement. Utilisez une fenêtre de maintenance pour une mise à niveau à pile unique.
  2. Mettez à niveau les composants ensemble. Utilisez les images correspondantes 1.19.0 API, Worker, Web, Agent Backend et Local Sandbox, avec le démon de plug-in 0.6.14-local. Conservez le jeton d'authentification du bac à sable local existant et tout PASSWORD_PEPPER configuré inchangé. Si vous effectuez une mise à niveau avant 1.18.0, suivez également le [Guide de mise à niveau 1.18.0] (https://github.com/langgenius/dify/releases/tag/1.18.0).
  3. Utilisez Docker Compose 2.35.0 ou version ultérieure. Il s'agit de la version minimale prise en charge pour les remplacements racine .env qui doivent avoir la priorité lorsque Compose résout les valeurs par défaut du service. Vérifiez votre version installée avec docker compose version. (#45359)
  4. Gardez les valeurs par défaut suivies séparément des remplacements locaux. Les fichiers docker/envs/**/*.defaults groupés se chargent automatiquement. Personnalisez un service via son fichier .env local correspondant, en utilisant le chemin de remplacement documenté dans le fichier par défaut ; la racine docker/.env contient les entrées de déploiement et les remplacements explicites. Conservez les fichiers .env existants et modifiez-les sur place. Examinez les affectations accidentellement vides et les valeurs épinglées par d’anciennes copies de modèles avant la mise à niveau. (#45359, #45376)
  5. Les fichiers shared.env existants restent pris en charge. Les personnalisations communes API, Worker et Beat appartiennent désormais à docker/envs/core-services/api-worker.env. Compose lit toujours l'ancien docker/envs/core-services/shared.env en premier, puis api-worker.env, donc api-worker.env gagne lorsque les deux définissent des valeurs contradictoires. La racine docker/.env a priorité sur les deux. Une copie inchangée de api-worker.defaults préserve les personnalisations existantes de shared.env. Consultez le [Guide de configuration du Docker] (https://github.com/langgenius/dify/blob/laipz8200/release-1.19.0/docker/README.md#review-configuration-after-an-upgrade). (#45376)
  6. Files d'attente de traçage séparées lors d'une mise à niveau continue. Les nouvelles tâches sont par défaut OPS_TRACE_QUEUE=ops_trace_v2 ; API, les travailleurs et Beat doivent être d'accord. Les listes personnalisées CELERY_QUEUES, CELERY_WORKER_QUEUES ou --queues doivent inclure la nouvelle file d'attente. Conservez les anciens travailleurs de traçage sur ops_trace jusqu'à ce que les anciens producteurs et tous leurs travaux en file d'attente, actifs, réservés, planifiés et de nouvelle tentative soient terminés. Ne purgez pas l’ancienne file d’attente et ne demandez pas au nouveau gestionnaire retiré d’exporter les messages hérités. Consultez le [guide de déploiement du traçage] (https://github.com/langgenius/dify/blob/laipz8200/release-1.19.0/api/providers/trace/README.md#rolling-upgrade-from-the-previous-pipeline). (#44673)
  7. Mettez à niveau les destinations des packages avant d'importer de nouveaux packages d'applications. Les nouveaux packages d'applications utilisent toujours le format v2. Les importateurs plus anciens, y compris les versions avec la règle stricte v2 précédente, peuvent les rejeter. Les importations de la version 1 restent prises en charge sur 1.19.0. L'exportation explicite YAML reste disponible, mais ne comporte pas de dépendances groupées de Workflow Tool. (#44592, #45353)

<summary><strong>Instructions de déploiement · Docker Composer, sourcer et modifier</strong></summary>

Docker Composer

Une fois la balise de version et les images 1.19.0 publiées, arrêtez progressivement un déploiement à pile unique, passez à la version, conservez et examinez la configuration, puis extrayez et démarrez les nouvelles images :

cd dify/docker
docker compose stop -t -1
git fetch --tags
git checkout 1.19.0
# Merge required configuration changes into existing env files here.
docker compose pull
docker compose up -d

Gardez les migrations de démarrage API activées (MIGRATION_ENABLED=true) ou appliquez la chaîne de migration complète via votre processus de migration géré avant de démarrer de nouveaux travailleurs. Pour les déploiements continus, suivez la séquence de file d'attente de suivi distincte au lieu de mélanger les anciens et les nouveaux consommateurs.

Configurez les informations d'identification du plugin partagé, PLUGIN_DAEMON_KEY et PLUGIN_DIFY_INNER_API_KEY, dans la racine docker/.env afin que le démon et ses clients reçoivent les valeurs correspondantes. Les ports, les chemins de volume, les profils et la planification des contrôles de santé restent également des entrées de configuration racine. Consultez le [Guide de configuration du Docker] (https://github.com/langgenius/dify/blob/laipz8200/release-1.19.0/docker/README.md#configure-dify). (#45359)

Déploiements sources

Utilisez Python 3.13, Node.js 24.22.1 ou version ultérieure dans la ligne 24.x et pnpm 12.16.1. pnpm ne provisionne plus Node.js pour l'espace de travail, installez donc le runtime Node.js requis séparément. (#44976, #45094)

Depuis la racine du référentiel :

uv sync --project api --frozen
uv run --directory api flask db upgrade
pnpm install --frozen-lockfile

Reconstruisez l'application Web et redémarrez les services API, Worker, Planificateur et Agent à partir de la même version. Actualisez les dépendances server verrouillées du backend d'agent autonome lors du déploiement séparé.

difficile

Installez le 1.19.0 client correspondant et utilisez difyctl help pour découvrir le catalogue de serveur actuel. Actualisez les compétences des agents installés avec difyctl install skills <dir>. L’automatisation des workflows et des chatflows doit utiliser l’opération stop.run révisée ; les applications basées sur des messages utilisent stop.task.

<summary><strong>Migrations de bases de données et données existantes</strong></summary>

La mise à niveau à partir de 1.18.0 applique six révisions de migration, se terminant à 53c10126d551. Appliquez la chaîne complète via le coureur de migration normal.

Les changements opérationnels à planifier comprennent :

  • Index de nettoyage de stockage (d7e9a1c3f502). Ajoutez des index de référence sur message_files.upload_file_id, workflow_node_execution_offload.file_id et workflow_draft_variable_files.upload_file_id. PostgreSQL les crée simultanément, mais la construction d'index analyse toujours les données et consomme des E/S. Les mises à niveau en ligne réutilisent les index sains correspondants et rejettent les définitions contradictoires ou invalides. Examinez une build invalide interrompue avant de réessayer ; ne supprimez pas les index sains en tant que récupération de routine. (#44982)
  • Traçage de l'unicité de la configuration (53c10126d551). Conservez une configuration par application/fournisseur et ajoutez un index unique. Lorsqu'il existe des doublons, la ligne la plus récemment mise à jour l'emporte, l'ID rompant les liens d'horodatage. Les lignes remplacées sont supprimées ; la rétrogradation de l'index ne les restaure pas. Conservez une sauvegarde de la base de données. (#44673)
  • Les modifications d'extraction affectent le contenu nouvellement traité. Réimportez ou réindexez les documents dont le contenu stocké a été affecté par les correctifs EPUB, EML, DOCX, CSV, Markdown ou Notion. Le correctif d'aperçu PDF répété empêche les nouveaux éléments en double pour les téléchargements source ; il ne supprime pas les doublons déjà stockés. (#44836, #44953, #44905, #43505, #43434, #45053, #44684)
  • L'historique de suivi n'est pas reconstruit. Les données existantes du registre de trace de l'agent restent lisibles, mais les traces précédemment exportées n'acquièrent pas les nouvelles étendues imbriquées. (#44673)

Modifications détaillées

<détails>

<summary><strong>Nouvelles fonctionnalités · traçage, packages et compétences</strong></summary>

Traçage et intégrations de fournisseurs

  • Consolidez la livraison via l'interface de fournisseur partagée pour Langfuse, LangSmith, Opik, Weave, Arize, Phoenix, Aliyun, MLflow, Databricks et Tencent. Les exportations réessayables renvoient la même unité de trace avec des identifiants déterministes. (#44673)
  • Inclure les cadres d'exécution persistants appelés Workflow Tools dans les exportations externes, sous leurs étendues d'outils d'appel. Les exécutions de flux de travail imbriquées indépendamment restent des traces distinctes liées par des identifiants parents. (#44673)
  • Conservez les informations d'identification de trace en écriture seule. Les secrets vides ou omis préservent les valeurs stockées ; la modification d'un hôte de destination, d'un point de terminaison ou d'une URL nécessite de saisir à nouveau ses secrets. (#44673)

Forfaits d'applications portables

  • Regroupez les workflows derrière appelés Workflow Tools, y compris les dépendances transitives, avec un maximum par défaut de 20 workflows d'outils groupés. Les outils de destination manquants sont recréés et publiés ; les outils existants sont réutilisés. La création d'outils manquants nécessite une autorisation de gestion des outils et un quota d'applications suffisant. Les packages nécessitant une confirmation de version DSL sont rejetés dans ce flux et les applications créées avant un échec d'importation sont nettoyées. (#44592)
  • Émettez toujours le format v2 pour les packages d'application, y compris les packages imbriqués et les packages sans outils de workflow. Cela ne modifie pas le format séparé du package liste-agent. (#45353)
  • Les ID de workflow et d'outil API ne deviennent plus de fausses dépendances du plugin langgenius/<uuid> lors de l'exportation. (#44592)

Compétences et OpenAPI

  • Exportez des brouillons ou des versions de compétences publiées, importez des dossiers et publiez via des opérations d'espace de travail authentifiées par le compte. Une importation avec un ID de compétence remplace le brouillon de cette compétence ; le nom SKILL.md importé doit correspondre. Les vérifications facultatives draft_hash rejettent les remplacements obsolètes, mais utilisent des horodatages de deuxième résolution et ne détectent pas les modifications effectuées dans la même seconde. (#44941)
  • L'importation de compétences supprime les fichiers indésirables du système d'exploitation, rejette les chemins dangereux ou en double, applique les limites de fichier/taille, réutilise les actifs binaires identiques et supprime les actifs écrits par une importation ayant échoué. Les tirets littéraux à l’intérieur du thème des compétences sont conservés. (#44941, #43602)
  • Le catalogue des opérations publie l'effet de chaque opération et l'aide du CLI l'affiche. L’arrêt du workflow/chatflow utilise la propriété et l’état des exécutions stockées ; les exécutions inconnues renvoient 404, et les exécutions terminées ou non arrêtables renvoient 409. L’arrêt de l’application de message conserve sa sémantique d’ID de tâche. (#44587, #45314)
  • Ajoutez le package expérimental @dify/openapi-content-mapper pour les appels API typés et les assistants de requête déduits des sources OpenAPI, avec des types de schéma/entrée/sortie réutilisables et des sous-chemins de type compatibles avec les contrats opt-in. Il s’agit d’un travail préparatoire au développement ; ces modifications ne migrent pas les appels de la console de production ou du marché vers leurs clients existants. (#44627, #44915)

(#44621, #43869, #44638, #44650, #44593, #44755, #44772, #44589, #45036, #45375)

(#44618, #44623, #44643, #44646, #44698, #44736, #44743, #44810, #44825, #44788, #44715, #44652, #44838, #44830)
  • Commentaires plus clairs : les erreurs de champ et les notifications persistantes apparaissent à proximité des contrôles qu'ils concernent, avec une présentation des alertes partagées entre les applications, les flux de travail, les connaissances, la facturation et les compétences. La facturation cloud utilise des invites localisées pour les erreurs réessayables et spécifiques à une action. (#45151, #45264, #45266, #45267, #45268, #45192)
  • Affichage précis des quotas Cloud : distingue les comptes illimités des quotas d'exécution et de déclenchement d'applications à capacité nulle, et interprète les dates de réinitialisation en secondes Unix. Les données d'affichage des prix ne servent plus de limites d'utilisation en direct. (#45117, #45115)

  • Réutilisation des connexions : La durée de conservation configurable de Gunicorn est définie par défaut sur 10 secondes, réduisant ainsi les échecs causés par la réutilisation des connexions après la fenêtre d'inactivité plus courte du serveur. (#44839)

<summary><strong>Améliorations de la sécurité</strong></summary>
  • Contrôles de l'espace de travail : l'activation ou la désactivation des modèles de fournisseur nécessite un propriétaire ou un administrateur. Les vérifications de disponibilité des e-mails nécessitent l’admission au compte. (64fe95667b, 76979a1e24)
  • Cookies à l'échelle de la requête : les SSRF clients regroupés conservent les cookies de réponse uniquement dans la requête sortante actuelle et ses redirections, empêchant les requêtes ultérieures d'hériter des cookies d'une autre requête. (#44672)
  • Portée du jeton d'ensemble de données : les jetons d'accès aux ressources peuvent répertorier uniquement leurs ensembles de données actifs explicitement liés ; include_all=true ne peut pas élargir cette portée. Les clés API de l’ensemble de données d’espace de travail hérité conservent le comportement à l’échelle du locataire sans hériter des filtres de visibilité personnels d’un propriétaire injecté. (#44840)
  • Paramètres d'accès aux applications : l'importation DSL sur une application existante préserve son mode d'accès Web App, et la conversion d'une application hérite du mode d'accès source. (#44700, #44857)
  • Traçage des secrets et des sorties : les lectures de configuration ne renvoient plus les informations d'identification enregistrées, les modifications de destination nécessitent une nouvelle saisie du secret et le trafic du fournisseur utilise la stratégie sortante partagée. (#44673)
  • Renforcement des dépendances : mettez à jour Authlib vers 1.9.1, nécessitez LiteLLM 1.100.4 ou une version ultérieure dans sa version majeure prise en charge, déplacez Agent Pydantic AI vers 2.53.0 et Pillow vers 13.0.0, mettez à jour pypdf vers 6.21.4 et actualisez Werkzeug, GitPython et d'autres correctifs de dépendances. L'agent autonome épingle filelock 4.2.1 ; Les outils de construction Docker sont mis à jour uv vers 0.13.4. Ces mises à jour de source ne prétendent pas résoudre tous les résultats dans les images de base externes ou d'entreprise. (#44606, #44793, #44868, #44871, #44886, #45041, #45104, #45215, #45259, #45214, #45260)

</détails>

<summary><strong>Corrections de bogues · workflows, agents, connaissances, API et application Web</strong></summary>

Flux de travail et exécution

  • Restaurez le secours de sortie structurée pour les modèles sans prise en charge native et conservez les booléens JSON au lieu de les convertir en chaînes. (#44962)
  • Respectez les valeurs par défaut des fichiers et des listes de fichiers configurés dans Studio, les applications publiées et l'exécution du API. La suppression explicite reste distincte de l'omission, la réinitialisation des conversations restaure les valeurs par défaut et l'enregistrement des valeurs par défaut des fichiers n'envoie plus les objets Blob du navigateur qui provoquent des erreurs 415. (#44780, #45042)
  • Conservez le zéro numérique dans les entrées et les aperçus Studio requis, et conservez à la fois zéro et faux dans les instructions d'ouverture. Les charges utiles de référence de fichier non-objet reviennent à la référence d'origine au lieu d'échouer de manière inattendue. (#45005, #44833, #45088)
  • Admettez les demandes de flux de travail et de chatflow en streaming une seule fois par rapport aux limites de simultanéité des applications, de sorte qu'une limite d'un accepte la seule demande active. dify 1.19.0

Dify 1.19.0 brings nested workflow tracing to your observability tools. Follow a workflow into the Workflow Tools it calls, inspect the steps inside each invocation, and keep the LLM context alongside the execution tree.

This release also makes Workflow Tools portable with App packages, adds Skill Hub automation, and makes Agent files easier to upload and preview. The bundled plugin daemon is upgraded to 0.6.14-local.

Release highlights · Upgrade guide · Detailed changes

<a id="release-highlights"></a>

Release highlights

Nested workflow tracing

See what happens inside a Workflow Tool, all the way down to its LLM calls.

Building on the Console drilldown introduced in 1.18.0, new external traces now include the persisted execution steps inside called Workflow Tools. Child steps appear beneath the Tool span that invoked them, preserving the hierarchy across nested and repeated calls. (#44673)

From the outer workflow to a nested LLM call: the execution tree and formatted messages, together in Langfuse. Screenshot from #44673.

  • Follow the hierarchy. Expand called Workflow Tools to see their internal execution steps under the invoking Tool span.
  • Understand each invocation. Repeated calls and failures retain their place in the trace.
  • Keep the LLM context. Inspect formatted prompts and responses, token usage, and project, trace, and observation links.

[!NOTE] Your saved provider settings continue to work. The richer hierarchy applies to new executions; historical traces are not backfilled. Independently nested workflow runs remain separate traces linked by parent identifiers. For rolling deployments, follow the tracing queue transition below.

Take Workflow Tools with your apps

Export an app and bring the workflows behind its Workflow Tools with it. .ifpkg packages include those workflows at their bound versions, including transitive dependencies. Import reuses tools already in the destination workspace and recreates, publishes, and registers missing ones, remapping their references. (#44592)

All Dify app exports now use package format v2, including apps without Workflow Tools. Existing v1 imports and explicit YAML export remain supported. See the upgrade guide before importing new packages into older installations. (#45353)

Upload together. Preview in place.

Select or drop multiple Agent configuration files and upload them in parallel. Successful uploads are bound in one atomic batch, concurrent Composer saves preserve the latest files, and Prompt uploads keep the cursor position while inserting multiple references. (#44947)

Read PDFs inline, inspect source files with syntax highlighting, and see when text has been truncated. Previews cover configured files, Skill members, and working-directory files, with a download action when a PDF cannot be loaded. (#45032, #45045)

<a id="upgrade-guide"></a>

Upgrade guide

[!IMPORTANT] Read the upgrade guide before deploying. Docker Compose now requires v2.35.0 or later. Preserve existing environment files, upgrade the Dify components together, and use the new tracing queue during rolling deployments. New App packages use format v2 and require a compatible destination importer. The bundled plugin daemon moves to 0.6.14-local.

Compatibility and rollout

  1. Back up first. Retain the database, vector-store data, uploaded files, Agent snapshot/workspace storage, deployment secrets, and environment files. Use a maintenance window for a single-stack upgrade.
  2. Upgrade the components together. Use matching 1.19.0 API, worker, web, Agent Backend, and Local sandbox images, with plugin daemon 0.6.14-local. Keep the existing Local sandbox authentication token and any configured PASSWORD_PEPPER unchanged. If upgrading from before 1.18.0, also follow the 1.18.0 upgrade guide.
  3. Use Docker Compose 2.35.0 or later. This is the minimum supported version for root .env overrides to take precedence when Compose resolves service defaults. Check your installed version with docker compose version. (#45359)
  4. Keep tracked defaults separate from local overrides. Bundled docker/envs/**/*.defaults files load automatically. Customize a service through its matching local .env file, using the override path documented in the defaults file; root docker/.env holds deployment inputs and explicit overrides. Preserve existing .env files and edit them in place. Review accidentally empty assignments and values pinned by older template copies before upgrading. (#45359, #45376)
  5. Existing shared.env files remain supported. Common API, worker, and Beat customizations now belong in docker/envs/core-services/api-worker.env. Compose still reads legacy docker/envs/core-services/shared.env first, then api-worker.env, so api-worker.env wins when both set conflicting values. Root docker/.env takes precedence over both. An unchanged copy of api-worker.defaults preserves existing shared.env customizations. See the Docker configuration guide. (#45376)
  6. Separate tracing queues during a rolling upgrade. New tasks default to OPS_TRACE_QUEUE=ops_trace_v2; API, workers, and Beat must agree. Custom CELERY_QUEUES, CELERY_WORKER_QUEUES, or --queues lists must include the new queue. Keep old tracing workers on ops_trace until old producers and all their queued, active, reserved, scheduled, and retry work have finished. Do not purge the old queue or ask the new retired handler to export legacy messages. See the tracing rollout guide. (#44673)
  7. Upgrade package destinations before importing new App packages. New app packages always use format v2. Older importers, including builds with the earlier strict v2 rule, may reject them. Version 1 imports remain supported on 1.19.0. Explicit YAML export remains available, but does not carry bundled Workflow Tool dependencies. (#44592, #45353)
