Changements importants

Pandas 3 modifie la façon dont les DataFrame XCom sont stockés et relus (#71169)

pandas 3 expose ses classes publiques à partir de l'espace de noms pandas, donc un DataFrame est qualifié de pandas.DataFrame instead of pandas.core.frame.DataFrame. Les XComs enregistrent ce nom à côté du valeur sérialisée, donc le nom écrit dans la base de données de métadonnées dépend de la version pandas du composant qui a poussé la valeur. Airflow enregistre les deux noms et un DataFrame écrit par l'un ou l'autre La version pandas peut être lue par l'un ou l'autre - aucun changement de configuration n'est nécessaire et les XCom existants restent lisible.

Ce que vous devriez faire :

  • Déployez cette version d'Airflow sur chaque composant avant que Pandas 3 n'atteigne l'un d'entre eux -- Workers en particulier. Un composant antérieur à cette modification ne peut pas lire un DataFrame XCom écrit sous pandas 3, et échoue le pull avec :

    .. bloc de code :: texte

    ImportError : pandas.DataFrame est introuvable dans la liste verte pour les importations de désérialisation.
Pour l'autoriser, ajoutez-le à Allowed_deserialization_classes dans la configuration

    Le message pointe vers la configuration, mais la liste verte n'en est pas la cause et sa modification ne le fait pas. aider. Les lignes ne sont pas corrompues : elles redeviennent lisibles dès la mise à jour du lecteur.

  • Traitez un déclassement comme une porte à sens unique pour ces XComs. Revenir à une version Airflow sans ce changement bloque tout DataFrame XCom écrit sur pandas 3, avec la même erreur, jusqu'à ce que vous avancer à nouveau.

  • Revoir les Dags qui inspectent le dtypes d'un DataFrame extrait. La version pandas du reader détermine à quoi ressemble un DataFrame extrait, pas la version qui l'a écrit. Sous pandas 3, un la colonne de chaînes revient sous la forme str rather than object, et ses valeurs manquantes revenez sous le nom de « nan`` rather than ``None ». Les valeurs sont inchangées, mais le code en aval qui bifurque sur dtype == "object", checks cells with is None, ou compare avec un cadre de référence avec DataFrame.equals() peut se comporter différemment après la mise à niveau.

Correction d'un échec de mise à niveau 2.x vers 3.0+ lorsqu'un bundle Dag personnalisé est configuré (#70994)

La migration 0082_3_1_0_make_bundle_name_not_nullable a attribué chaque ligne héritée bundle_name='dags-folder', so triggering a DagRun raised Le paquet demandé 'dags-folder' est non configuré. on any deployment that uses a bundle other than the default dags-folder. DagFileProcessorManager exécute désormais un remplissage unique et au mieux au démarrage qui achemine chacun affecté Dag au bon bundle en fonction de son chemin de fichier ; Des Dags inégalés s'auto-guérissent le prochain analyse réussie (ou exécutez airflow dags reserialize pour la forcer immédiatement).

Les valeurs de l'équipe des options enregistrées comme sensibles sont désormais masquées (#71099)

Les options de configuration sont enregistrées comme sensibles dans leur section de base, donc jusqu'à présent, seules les options l'orthographe de base d'une option était masquée. Un remplacement de portée d'équipe - défini dans un [<team>=<section>] section du fichier de configuration, ou via une variable d'environnement AIRFLOW__<TEAM>___<SECTION>__<KEY> -- n'a pas été reconnu comme la même option et a été restitué dans son intégralité.

La sensibilité est maintenant décidée après avoir résolu l'orthographe de l'équipe à l'option de base, donc un la valeur de l'équipe est masquée exactement comme la valeur de base l'était déjà.

Changements de comportement :

  • AirflowConfigParser.as_dict(display_sensitive=False), GET /config, GET /config/section/{section}/option/{option} and airflow config list revient maintenant < hidden > pour une valeur de portée d'équipe d'une option enregistrée comme sensible. Des déploiements qui lire la valeur réelle d'une équipe à travers l'un d'entre eux recevra désormais le masque ; utiliser display_sensitive=True où une valeur réelle est requise et appropriée.
  • L'équipe a défini _cmd and _secret entries are replaced with < hidden > en place, plutôt plutôt que d'être résolus dans leur valeur et supprimés tels qu'ils sont dans une section de base. Les résoudre n'est pas pris en charge pour une équipe, donc la chaîne de commande ou le chemin secret n'est plus affiché non plus.
  • La configuration hors équipe n'est pas affectée et display_sensitive=True continue de revenir réel valeurs.

airflow 3.3.1

Highlights

  • Pandas 3 XCom compatibility and rollout order (#71169) — pandas 3 qualifies DataFrames as pandas.DataFrame instead of pandas.core.frame.DataFrame; Airflow now registers both names, so an XCom written under either version is readable by either with no config change and existing rows stay readable. But rollout order is the trap: upgrade every component to 3.3.1 before pandas 3 reaches any of them — workers especially — because an older reader throws a misleading ImportError telling you to add allowed_deserialization_classes when the allow list is not the cause and changing it does nothing; the rows simply become readable again once the reader is upgraded. Rolling back is a one-way door for XComs written under pandas 3 — they stay unreadable until you roll forward. Audit DAGs that branch on dtype == "object", check cells with is None, or use DataFrame.equals(): the reader's pandas version now determines the pulled frame's shape (string columns come back as str, missing values as nan, not None), so downstream logic can silently change behavior.

  • 2.x→3.x upgrade unblocked for custom DAG bundles (#70994) — migration 0082 hard-coded bundle_name='dags-folder' on all legacy rows, so any deployment using a non-default bundle hit Requested bundle 'dags-folder' is not configured when triggering DAG runs. DagFileProcessorManager now runs a one-shot, best-effort startup backfill that routes each affected DAG to the right bundle by file path; unmatched DAGs self-heal on the next successful parse, or force it immediately with airflow dags reserialize. If a custom bundle is why you were stuck on 3.0, 3.3.1 is the target.

  • Team-scoped sensitive config values are now masked (#71099) — sensitivity is resolved after mapping a [<team>=<section>] override (or AIRFLOW__<TEAM>___<SECTION>__<KEY> env var) back to its base option, so AirflowConfigParser.as_dict(display_sensitive=False), GET /config, the per-option config endpoint, and airflow config list now return < hidden > for team-scoped secrets that previously leaked in cleartext. Anything reading a team's real value through those paths will start receiving the mask — switch to display_sensitive=True where a real value is genuinely needed. Team-scoped _cmd/_secret entries are masked in place instead of being resolved-and-removed as in a base section. Non-team config is unchanged.

  • Breaking for plugin authors: ResumableJobMixin is now abstract (#70810) — subclasses must implement its previously optional methods, so audit any custom jobs inheriting it before upgrading or instantiation will fail. Pair this with the new docs on state-store cleanup in that mixin (#70792).

  • Security hardening across secrets and redirects — several disclosure paths are closed: a crafted key could make a team-scoped secret lookup return another team's secret (#71041), secrets appeared unmasked in the audit log for bulk Variable/Connection updates (#71043), JSON-list Variable values and values nested in lists/tuples/sets escaped masking (#71069, #70189), and the Rendered Templates view exposed secrets under KubernetesPodOperator (#70756). An open-redirect via malformed URLs is also rejected (#70515). Prioritize this if the UI/API is shared across teams.

  • Behavioral changes to test: deferrable retries, email backends, and observability — deferrable tasks failing via a trigger-emitted TaskFailedEvent now honor retries instead of failing terminally (#71163), and email_on_failure/email_on_retry finally respect a custom [email] email_backend rather than always routing through SmtpNotifier; an unimportable backend now errors loudly instead of silently falling back to SMTP (#70129). New telemetry includes a task.execute OpenTelemetry span (#69359) and a run_type tag on dagrun.duration.failed (#70731). Dependency floors also rise to structlog>=26.1.0 and croniter>=6.2.2 to fix memory leaks (#70749) — check pinned constraint files.

Significant Changes

Pandas 3 changes how DataFrame XComs are stored and read back (#71169)

pandas 3 exposes its public classes from the pandas namespace, so a DataFrame is qualified as pandas.DataFrame instead of pandas.core.frame.DataFrame. XComs record that name alongside the serialized value, so the name written into the metadata database depends on the pandas version of the component that pushed the value. Airflow registers both names, and a DataFrame written by either pandas version can be read by either -- no configuration change is needed, and existing XComs stay readable.

What you should do:

  • Roll this Airflow version out to every component before pandas 3 reaches any of them -- workers in particular. A component that predates this change cannot read a DataFrame XCom written under pandas 3, and fails the pull with:

    .. code-block:: text

    ImportError: pandas.DataFrame was not found in allow list for deserialization imports.
To allow it, add it to allowed_deserialization_classes in the configuration

    The message points at configuration, but the allow list is not the cause and changing it does not help. The rows are not corrupt: they become readable again as soon as the reader is upgraded.

  • Treat a downgrade as a one-way door for those XComs. Rolling back to an Airflow version without this change strands any DataFrame XCom written while on pandas 3, with the same error, until you roll forward again.

  • Review Dags that inspect the dtypes of a pulled DataFrame. The pandas version of the reader determines what a pulled DataFrame looks like, not the version that wrote it. Under pandas 3, a column of strings comes back as str rather than object, and its missing values come back as nan rather than None. Values are unchanged, but downstream code that branches on dtype == "object", checks cells with is None, or compares against a reference frame with DataFrame.equals() can behave differently after the upgrade.

Fix 2.x to 3.0+ upgrade failure when a custom Dag bundle is configured (#70994)

The 0082_3_1_0_make_bundle_name_not_nullable migration assigned every legacy row bundle_name='dags-folder', so triggering a DagRun raised Requested bundle 'dags-folder' is not configured. on any deployment that uses a bundle other than the default dags-folder. DagFileProcessorManager now runs a one-shot, best-effort backfill at startup that routes each affected Dag to the correct bundle based on its file path; unmatched Dags self-heal on the next successful parse (or run airflow dags reserialize to force it immediately).

Team scoped values of options registered as sensitive are now hidden (#71099)

Configuration options are registered as sensitive under their base section, so until now only the base spelling of an option was masked. A team scoped override -- set in a [<team>=<section>] config file section, or through an AIRFLOW__<TEAM>___<SECTION>__<KEY> environment variable -- was not recognized as the same option and was returned in full.

Sensitivity is now decided after resolving the team scoped spelling back to the base option, so a team scoped value is masked exactly as the base value already was.

Behaviour changes:

  • AirflowConfigParser.as_dict(display_sensitive=False), GET /config, GET /config/section/{section}/option/{option} and airflow config list now return < hidden > for a team scoped value of an option registered as sensitive. Deployments that read a team's real value through any of these will now receive the mask; use display_sensitive=True where a real value is required and appropriate.
  • Team scoped _cmd and _secret entries are replaced with < hidden > in place, rather than being resolved into their value and removed as they are in a base section. Resolving them is not supported for a team, so the command string or secret path is no longer shown either.
  • Non team configuration is unaffected, and display_sensitive=True continues to return real values.
