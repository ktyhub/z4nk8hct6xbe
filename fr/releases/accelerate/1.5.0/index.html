accelerate v1.5.0

Highlights

  • HPU joins the accelerator roster — PR #3378 adds first-class Habana Processing Unit (Gaudi) support, so HPU users can finally use Accelerate's standard Accelerator API instead of maintaining custom distributed-training glue. If you're on Gaudi hardware, this is the headline: upgrade to consolidate your training loop onto the same accelerate launch workflow every other backend already enjoys. Watch for backend-specific coverage gaps at launch — new accelerator integrations typically land with core support first and edge-case features (specific schedulers, checkpoint formats) following in later patches.

  • A second new backend: Tecorigin SDAA — PR #3330 lands support for Tecorigin's SDAA accelerator. Combined with HPU, this release broadens Accelerate's hardware story beyond the usual CUDA/ROCm/mps/XPU set. Treat these as opt-in backends — validate your exact model and mixed-precision configuration on the target silicon before committing, since new integrations tend to be exercised primarily on reference workloads.

  • CLI flags now beat the config file — PR #3409 fixes precedence so command-line arguments override values in the config file. This is a meaningful behavioral change for anyone with a committed accelerate config: overrides you pass to accelerate launch will now win where they previously might have been shadowed. It's the intuitive behavior, but re-check any automation that relied on config winning — reproducibility scripts and CI jobs that encode machine settings in the config are the ones most likely to shift.

  • Quantized-training device mapping corrected — PR #3408 fixes a device-index bug when training models loaded with bitsandbytes. If you do QLoRA or other 4-bit/8-bit fine-tuning, this matters: incorrect device indexing can silently misplace layers or scatter quantized weights across the wrong GPUs, producing subtle correctness or OOM failures. Worth upgrading specifically if you've seen odd device-placement behavior in multi-GPU quantized runs.

  • Forward-compatible RNG seeding — PR #3420 adds device=torch.get_default_device() to torch.Generator construction, addressing PyTorch's move toward requiring explicit devices for generators. This is largely a compatibility/determinism fix that prevents future deprecation warnings and keeps reproducible seeding working as PyTorch evolves. Low-risk change, but relevant if you pin the seed for deterministic training and plan to move to newer PyTorch versions.

No breaking changes in this release.
