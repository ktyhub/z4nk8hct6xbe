nightingale v9.1.0

#rossignol v9.1.0

Ce qui a changé

  • exploit : base de données de séries chronologiques intégrée — les métriques poussées par Categraf sont stockées localement, donc aucun Prometheus / VictoriaMetrics externe n'est requis pour démarrer ; une source de données Prometheus nommée embedded-tsdb est automatiquement enregistrée au premier démarrage. Les configurations existantes sont respectées : si une source de données Prometheus activée est déjà présente, la source de données n'est pas créée automatiquement — les échantillons sont toujours écrits localement et vous pouvez ajouter une source de données Prometheus pointant vers la TSDB intégrée pour les interroger (#3283)
  • exploit : importer des sources de données de Grafana dans un click, avec un résumé des résultats par source de données (#3295)
  • exploit : refonte de la page de la source de données – après avoir enregistré une source de données, Nightingale la sonde avec des métriques sentinelles pour signaler quels modèles de règles de tableau de bord/d'alerte intégrés contiennent déjà des données et vous guide vers votre première requête (#3301)
  • exploit : enregistrements d'évaluation d'alerte par cycle — chaque évaluation de règle conserve ce qu'elle a demandé et comment elle a jugé sur le disque local du moteur d'alerte, inspectable depuis un tiroir sur la page de règle d'alerte (#3305)
  • exploit : les configurations des canaux de notification peuvent être testées et les modèles de messages prévisualisés avant d'être enregistrés (#3302)
  • exploit : Assistant de collecte de configuration Categraf — un nouveau point de terminaison /agents/categraf/collect.sh sert le script d'application, avec des modèles de plugin et une vérification des métriques dans la console (#3286)
  • exploit : le pipeline d'événements prend en charge les événements simulés lors de l'exécution, le filtrage par plage de temps sur les enregistrements d'exécution, l'activation/désactivation par lots et une nouvelle modification API (#3281, #3285)
  • exploit : modèles de règles d'alerte intégrés dans les intégrations considérablement étendus et révisés, avec en_US i18n (#3282)
  • exploit : les sources de données MySQL peuvent ajouter des paramètres supplémentaires au DSN (#3299)
  • exploit : les sources de données Doris prennent en charge doris.internal_addr pour que le processus Edge atteigne FE MySQL (#3298)
  • exploit : la liste des règles d'alerte prend en charge le filtrage par type de déclencheur
  • exploit : la liste des événements d'alerte actifs affiche la valeur au moment du déclenchement, ajoute des balises à trois états et mémorise le panneau de filtrage, l'intervalle d'actualisation automatique et la plage de temps entre les visites
  • exploit : l'explorateur de journaux ajoute un bouton de requête de document pour Loki et VictoriaLogs, vous permet d'ajouter un filtre de champ directement à partir de la visionneuse de journaux et prend en charge l'exploration BCE BLS.
  • exploit : le panneau TableNG du tableau de bord prend en charge un tiroir de détail de ligne
  • exploit : intégration de la page hôte – pack de surveillance d'hôte one-click, action d'alerte de test et cartes des prochaines étapes
  • exploit : le proxy de la source de données et l'accès aux requêtes de journal sont désormais écrits dans le journal d'audit avec l'utilisateur et la charge utile
  • exploit : Edge réessaye la persistance de l'événement au centre, avec un délai d'attente par requête resserré
  • exploit : nouveau API pour vérifier si une notification a déjà été envoyée avec succès (#3300)
  • perf : accélère les requêtes d'enregistrement de notification et le nettoyage quotidien, soutenu par deux nouveaux index notification_record créés en ligne au démarrage (#3311)
  • correctif : copie complète des événements avant de les placer dans la file d'attente, afin qu'un événement de récupération n'écrase plus un événement déclencheur non encore consommé en place
  • correctif : une configuration d'application DingTalk vierge n'interrompt plus les notifications de robot de groupe (#3309)
  • correctif : épingler des types de colonnes explicites sur les modèles ai_* pour arrêter la dérive du schéma AutoMigrate, qui avait échoué lors de la migration de ces tables
  • correctif : prise en charge de max_completion_tokens pour les modèles OpenAI plus récents (#3306)
  • Correction : garde les noms d'étiquettes invalides dans la règle d'alerte event_relabel_config (#3287, #3296)
  • correctif : accepter le contenu YAML pour collecter les charges utiles intégrées (#3307)
  • correctif : autoriser la sauvegarde forcée d'une source de données dont la vérification de l'état échoue (#3304)
  • correctif : sondez la source de données globale par défaut par rapport à la liste complète des sources de données avant le filtrage du cluster par moteur, afin qu'une source de données par défaut appartenant à un autre cluster ne soit plus effacée
  • correctif : corriger les unités de règle d'alerte
  • correctif : réparer la compétence intégrée YAML et exposer les outils de recherche de code dans le chat
  • correctif : donnez à la migration de table asynchrone sa propre session gorm, afin qu'une instruction ayant échoué n'empoisonne plus le reste

Nouvelle fonctionnalité V9

  • exploit : introduction de Nightingale AI – assistant IA intégré, marché des compétences, gestion de la configuration LLM, avec des recommandations rapides spécifiques à la page
  • exploit : base de données de séries chronologiques intégrée - fonctionne immédiatement, aucun Prometheus / VictoriaMetrics externe n'est nécessaire pour les configurations à petite échelle
  • exploit : menu de navigation repensé, disposition globale et interface utilisateur des tableaux
  • exploit : gestion refactorisée des canaux de notification
  • exploit : Nouvelle page de suivi de l'exécution du pipeline d'événements avec vue détaillée de l'exécution

Note de mise à niveau ⚠️

  • Le nouvel assistant AI s'appuie sur Redis Streams, donc Redis 5.0 ou version ultérieure est requis (Redis 7.0+ recommandé aux utilisateurs de cluster pour activer Pub/Sub fragmenté).
  • Les enregistrements d'évaluation des alertes sont activés par défaut. Le moteur d'alerte les écrit sur son disque local à ./evallog, conservé pendant 8 jours et plafonné à 20 Go. Réglez ou désactivez-le avec la section [Alert.EvalLog] – voir le nouveau etc/config.toml.
  • Le TSDB intégré n'est pas activé par une mise à niveau binaire sur place : [EmbeddedTSDB] n'existe que dans le nouveau etc/config.toml, donc un fichier de configuration transféré d'une version antérieure le laisse de côté. Copiez la section pour l'activer. Il est géré uniquement par le processus central (n9e-edge / n9e-alert / n9e-pushgw l'ignore) et il stocke les données sur le disque local de cette instance centrale, il s'adapte donc aux déploiements à instance unique - avec plusieurs répliques centrales, utilisez plutôt une TSDB externe.

nightingale v9.1.0

What's Changed

  • feat: built-in time series database — metrics pushed by Categraf are stored locally, so no external Prometheus / VictoriaMetrics is required to get started; a Prometheus datasource named embedded-tsdb is auto-registered on first start. Existing setups are respected: if any enabled Prometheus datasource is already present, the datasource is not auto-created — samples are still written locally, and you can add a Prometheus datasource pointing at the built-in TSDB to query them (#3283)
  • feat: import datasources from Grafana in one click, with a per-datasource result summary (#3295)
  • feat: datasource page revamp — after saving a datasource, Nightingale probes it with sentinel metrics to report which built-in dashboard / alert rule templates already have data, and guides you to your first query (#3301)
  • feat: per-cycle alert evaluation records — each rule evaluation persists what it queried and how it judged to the alert engine's local disk, inspectable from a drawer on the alert rule page (#3305)
  • feat: notification channel configs can be tested, and message templates previewed, before they are saved (#3302)
  • feat: Categraf collect-config wizard — a new /agents/categraf/collect.sh endpoint serves the applier script, with plugin templates and metric verification in the console (#3286)
  • feat: event pipeline supports mock events in try-run, time-range filtering on execution records, batch enable/disable, and a new change API (#3281, #3285)
  • feat: built-in alert rule templates in integrations greatly expanded and revised, with en_US i18n (#3282)
  • feat: MySQL datasources can append extra params to the DSN (#3299)
  • feat: Doris datasources support doris.internal_addr for the edge process to reach FE MySQL (#3298)
  • feat: alert rule list supports filtering by trigger type
  • feat: active alert event list shows the value at trigger time, adds three-state tags, and remembers filter panel, auto-refresh interval and time range across visits
  • feat: log explorer adds a query doc button for Loki and VictoriaLogs, lets you append a field filter straight from the logs viewer, and supports BCE BLS drilldown
  • feat: dashboard TableNG panel supports a row detail drawer
  • feat: host page onboarding — one-click host monitoring pack, test alert action, and next-steps cards
  • feat: datasource proxy and log query access are now written to the audit log with the user and the payload
  • feat: edge retries event persistence to center, with a tightened per-request timeout
  • feat: new API to check whether any notification was ever delivered successfully (#3300)
  • perf: speed up notification record queries and the daily cleanup, backed by two new notification_record indexes created online at startup (#3311)
  • fix: deep copy events before pushing them to the queue, so a recovery event no longer overwrites a not-yet-consumed trigger event in place
  • fix: a blank DingTalk app config no longer breaks group robot notifications (#3309)
  • fix: pin explicit column types on the ai_* models to stop AutoMigrate schema drift, which had been failing the migration of those tables
  • fix: support max_completion_tokens for newer OpenAI models (#3306)
  • fix: guard invalid label names in alert rule event_relabel_config (#3287, #3296)
  • fix: accept YAML content for collect builtin payloads (#3307)
  • fix: allow force-saving a datasource that fails its health check (#3304)
  • fix: probe the global default datasource against the full datasource list before per-engine cluster filtering, so a default datasource owned by another cluster is no longer cleared
  • fix: correct alert rule units
  • fix: repair builtin skill YAML frontmatter and expose code search tools in chat
  • fix: give the async table migration its own gorm session, so one failed statement no longer poisons the rest

V9 new feature

  • feat: Introduce Nightingale AI — built-in AI assistant, Skills marketplace, LLM config management, with page-specific prompt recommendations
  • feat: Built-in time series database — works out of the box, no external Prometheus / VictoriaMetrics needed for small-scale setups
  • feat: Redesigned navigation menu, global layout, and table UI
  • feat: Refactored notification channel management
  • feat: New event pipeline execution tracking page with detailed execution view

Upgrade note ⚠️

  • The new AI assistant relies on Redis Streams, so Redis 5.0 or later is required (Redis 7.0+ recommended for Cluster users to enable sharded Pub/Sub).
  • Alert evaluation records are enabled by default. The alert engine writes them to its local disk at ./evallog, retained for 8 days and capped at 20GB. Tune or turn this off with the [Alert.EvalLog] section — see the new etc/config.toml.
  • The built-in TSDB is not enabled by an in-place binary upgrade: [EmbeddedTSDB] only exists in the new etc/config.toml, so a config file carried over from an earlier version leaves it off. Copy the section over to enable it. It is handled by the center process only (n9e-edge / n9e-alert / n9e-pushgw ignore it), and it stores data on the local disk of that one center instance, so it fits single-instance deployments — with multiple center replicas, use an external TSDB instead.
