Formation au-delà de 1 million de jetons

<img width="1672" height="941" alt="image" src="https://github.com/user-attachments/assets/806f9153-d098-4a45-bef4-5d4119b7ef25" /> Un nouveau [guide à contexte long] (https://huggingface.co/docs/trl/long_context_training) plus un exemple exécutable qui entraîne une séquence de la longueur d'un livre par étape sur un seul nœud 8 × H100. Mesuré : **Qwen3-8B à 1 048 576 jetons, 380 s/pas, 56.2 Go par GPU** (bf16, `per_device_train_batch_size=1`, `loss_type="chunked_nll"`). Fonctionne de bout en bout et enregistre. Le guide documente les leviers dans l'ordre dans lequel vous les appuyez (`chunked_nll`, point de contrôle de gradient `offload`, YaRN RoPE) et les contraintes (pleine attention uniquement, pas d'emballage). Nécessite `transformers >= 5.16` pour le point de contrôle `offload`. * Documentez la formation 1M-token et ajoutez un exemple de contexte-parallélisme par @qgallouedec dans https://github.com/huggingface/trl/pull/6846 * Réécrivez le long guide contextuel de @qgallouedec dans https://github.com/huggingface/trl/pull/7003 ### La projection Chunked-CE `lm_head` s'exécute désormais sur des cœurs tenseurs La boucle interne du `loss_type="chunked_nll"` par défaut faisait `h.float() @ w.float().t()`. Les deux opérandes sont déjà bf16, donc le upcast n'a acheté aucune information : il a déplacé le GEMM des noyaux tenseurs sur le chemin fp32 SIMT et a matérialisé une copie fp32 de l'ensemble du poids `lm_head` (2.03 Go pour un vocabulaire de 248 Ko), reconstruite pour chaque morceau et encore à chaque recalcul de point de contrôle de gradient. Dans un profil 8 × H100 de `trl sft` sur Qwen3.6-35B-A3B, ces deux SIMT GEMM fp32 représentaient **21.6% de tout le temps du noyau GPU**. Sous accélération de la précision mixte, les chiffres sont identiques en termes de bits (la diffusion automatique rediffusait déjà les opérandes vers le bas) ; sans diffusion automatique sur la projection, le GEMM passe aux noyaux tenseurs bf16, ce qui est exactement ce que fait déjà `loss_type="nll"`. par @qgallouedec dans https://github.com/huggingface/trl/pull/6863 ### Pertes linéaires fusionnées vendues dans `trl.losses` La seule importation de TRL depuis `liger-kernel` était `liger_kernel.chunked_loss` (les pertes linéaires fusionnées DPO / KTO / GRPO / JSD). Ce module est du pur PyTorch, et la plupart des variantes GRPO et DPO qu'il contient ont été écrites pour TRL. Les révisions en amont étaient au point mort, donc le code revient à la maison sous la forme `trl.losses` : `FusedLinearDPOLoss`, `FusedLinearKTOLoss`, `FusedLinearGRPOLoss`, `FusedLinearJSDLoss` (copié à partir du Liger-Kernel v0.8.2, avis BSD-2 conservé, identique au niveau du bit au Liger installé sur des entrées aléatoires). Pas de nouvel indicateur de configuration : `use_liger_kernel=True` continue de sélectionner la perte fusionnée exactement comme avant et nécessite toujours l'installation de `liger-kernel` car le https://github.com/huggingface/trl/pull/7145 ## Rupture ### ⚠️ Le PPO est supprimé `PPOTrainer`, `PPOConfig` et `modeling_value_head.py` (`PreTrainedModelWrapper`, `AutoModelForCausalLMWithValueHead`, `AutoModelForSeq2SeqLMWithValueHead`) ont disparu, avec leurs tests, leur page de documentation et leurs exemples. Petit moment pour TRL : `PPOTrainer` est antérieur à chaque PR de ce dépôt. Il a atterri dans `dfb6a580` le 2020-03-28, le commit qui a ajouté pour la première fois la bibliothèque, à l'époque où le package s'appelait `lm_ppo`. C'était la chose la plus ancienne de TRL et le dernier élément de la base de code originale. Pourquoi maintenant : non maintenu (aucune fonctionnalité n'a fonctionné depuis plus d'un an, chaque commit PPO depuis #4482 est un correctif drive-by), le seul entraîneur jamais aligné sur le format d'entrée (il fallait toujours un `input_ids` tokenisé), une utilisation enregistrée proche de zéro et un aimant pour les chasseurs de bugs automatisés qui déposent de vrais rapports sur le code que personne n'exécute. Personne ne perd rien : `from trl import PPOTrainer` a déjà cessé de fonctionner dans v1.10, donc toute personne exécutant réellement PPO est épinglée sur un ancien TRL et ces installations continuent de se résoudre exactement comme elles le font aujourd'hui. `create_reference_model` reste (BCO, A2PO et Online DPO l'utilisent). par @qgallouedec dans https://github.com/huggingface/trl/pull/7020 ## Correctifs * **Correction du gradient d'entropie manquant dans `_ChunkedLogProbFunction` vers l'arrière** — `backward` a accepté `grad_entropy` mais ne l'a jamais utilisé, donc toute perte se propageant via la sortie `entropy` a silencieusement obtenu un gradient nul à partir de ce terme, sans erreur ni avertissement. Training beyond 1M tokens

A new long-context guide plus a runnable example that trains a book-length sequence per step on a single 8×H100 node.

Measured: Qwen3-8B at 1,048,576 tokens, 380 s/step, 56.2 GB per GPU (bf16, per_device_train_batch_size=1, loss_type="chunked_nll"). Runs end to end and saves. The guide documents the levers in the order you hit them (chunked_nll, gradient-checkpointing offload, YaRN RoPE) and the constraints (full attention only, no packing). Needs transformers >= 5.16 for checkpointing offload.

  • Document 1M-token training and add a context-parallelism example by @qgallouedec in https://github.com/huggingface/trl/pull/6846
  • Rewrite the long context guide by @qgallouedec in https://github.com/huggingface/trl/pull/7003

Chunked-CE lm_head projection now runs on tensor cores

The inner loop of the default loss_type="chunked_nll" was doing h.float() @ w.float().t(). Both operands are already bf16, so the upcast bought no information: it moved the GEMM off the tensor cores onto the fp32 SIMT path and materialized an fp32 copy of the whole lm_head weight (2.03 GB for a 248k vocabulary), rebuilt for every chunk and again on every gradient-checkpoint recompute. In an 8×H100 profile of trl sft on Qwen3.6-35B-A3B those two fp32 SIMT GEMMs were 21.6% of all GPU kernel time.

One chunk, 256 tokens × vocab 248,320 × hidden 2048, 1×H100, bf16, fwd+bwd:

| | fwd+bwd | peak mem | | --- | --- | --- | | before | 23.37 ms | 5.99 GB | | after | 3.86 ms (6.0×) | 3.03 GB |

End to end, 16,384 tokens per step, tokens/s/GPU:

| model | mode | before | after | | | --- | --- | --- | --- | --- | | gemma-3-270m (vocab 262k) | full FT, 1×H100 | 24036 | 31609 | 1.32× | | Qwen3-0.6B (vocab 152k) | full FT, 1×H100 | 21276 | 26641 | 1.25× | | Qwen3-8B | full FT, 2×H100 FSDP2 | 3554 | 6009 | 1.69× | | Qwen3-8B | LoRA r16, 2×H100 FSDP2 | 4531 | 7125 | 1.57× | | Qwen3-30B-A3B (MoE) | LoRA attn, 2×H100 FSDP2 | 4251 | 5101 | 1.20× |

Same fix applied to the distillation trainers (which paid it twice per chunk, student and teacher). Under accelerate mixed precision the numerics are bit-identical (autocast was already casting the operands back down); without autocast over the projection the GEMM moves to bf16 tensor cores, which is exactly what loss_type="nll" already does.

by @qgallouedec in https://github.com/huggingface/trl/pull/6863

Fused linear losses vendored into trl.losses

TRL's only import from liger-kernel was liger_kernel.chunked_loss (the fused linear DPO / KTO / GRPO / JSD losses). That module is pure PyTorch, and most of the GRPO and DPO variants in it were written for TRL. Upstream reviews had stalled, so the code comes home as trl.losses: FusedLinearDPOLoss, FusedLinearKTOLoss, FusedLinearGRPOLoss, FusedLinearJSDLoss (copied from Liger-Kernel v0.8.2, BSD-2 notice kept, bitwise identical to the installed Liger on random inputs).

No new config flag: use_liger_kernel=True keeps selecting the fused loss exactly as before, and still needs liger-kernel installed because transformers' Trainer patches the model kernels with it.

Breaking

⚠️ PPO is removed

PPOTrainer, PPOConfig, and modeling_value_head.py (PreTrainedModelWrapper, AutoModelForCausalLMWithValueHead, AutoModelForSeq2SeqLMWithValueHead) are gone, along with their tests, doc page, and examples.

Bit of a moment for TRL: PPOTrainer predates every PR in this repo. It landed in dfb6a580 on 2020-03-28, the commit that first added the library, back when the package was called lm_ppo. It was the oldest thing in TRL and the last piece of the original codebase.

Why now: unmaintained (no feature work in over a year, every PPO commit since #4482 a drive-by fix), the only trainer never aligned on the input format (it still took tokenized input_ids), near-zero recorded usage, and a magnet for automated bug hunters filing real reports against code nobody runs. Nobody loses anything: from trl import PPOTrainer already stopped working in v1.10, so anyone actually running PPO is pinned to an older TRL and those installs keep resolving exactly as they do today.

create_reference_model stays (BCO, A2PO and Online DPO use it).

by @qgallouedec in https://github.com/huggingface/trl/pull/7020
