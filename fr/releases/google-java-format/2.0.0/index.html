format-google-java v2.0.0

google-java-format 2.0.0 remplace le moteur de mise en page du formateur et apporte quelques améliorations au formatage lambda (#19). Cette version ajoute également une passe de nettoyage facultative qui apporte de petites modifications autres que des espaces, qui est activée par défaut.

En raison de ces changements, 2.0.0 reformate plus de code existant qu'une version classique. Nous vous recommandons de reformater votre base de code en un seul commit lors de la mise à niveau.

Modifications du formatage

  • Un lambda qui est le seul argument d'un appel est désormais conservé sur la même ligne que l'appel, au lieu de commencer sur une nouvelle ligne avec un niveau d'indentation supplémentaire (#19) :

    executor.submit(() -> {
  doSomething();
});

  • Les blocs de texte sont désormais indentés dans le cadre de la passe de formatage principale, leur indentation est donc correcte même avec --skip-reflowing-long-strings.

  • Correction de l'indentation des commentaires après assert, des constantes d'énumération, des initialiseurs for, des ressources try, des clauses multi-catch et des arguments de type.

Nettoyages

  • Ajout d'un indicateur --cleanup, activé par défaut, pour les petites modifications autres que des espaces :

    • suppression des points-virgules redondants
    • suppression des parenthèses d'annotation vides (@Foo() → @Foo)
    • suppression des parenthèses autour d'un seul paramètre lambda non typé ((x) -> ... → x -> ...) (#762)

    Les nettoyages s'appliquent uniquement aux plages en cours de formatage. Utilisez --cleanup=false pour modifier uniquement les espaces (et les indicateurs --skip-sorting-imports, --skip-removing-unused-imports et --skip-reordering-modifiers existants pour les autres modifications non-espaces).

  • Lors du formatage d'une plage avec --lines ou --offset et les nettoyages activés, les instructions non formatées en dehors de la plage sont réindentées pour correspondre à la sortie formatée, de sorte qu'une modification qui ajoute ou supprime un niveau d'imbrication ne laisse pas le code environnant mal aligné. Les lignes vides laissées par les nettoyages sont supprimées.

##Configuration

  • --max-line-length=N définit la limite de colonne (par défaut 100) (#425). (Cet indicateur a été introduit dans v1.37.0)

Prise en charge linguistique

  • Prise en charge des classes de valeurs et des enregistrements de valeurs (JEP 401 : Objets de valeur (aperçu))

Javadoc

  • Supprimez les astérisques avant */ (#67).
  • Préserver l'indentation relative dans les blocs <pre>{@code ...} sans *.
  • Joignez les mots avec trait d'union répartis sur les lignes.

Longues chaînes

  • Lors du formatage d'une plage avec --lines ou --offset, seuls les littéraux de chaîne longue dans la plage demandée sont redistribués (#1114).
  • Les barres obliques inverses échappées (par exemple \\t dans un chemin Windows ou une expression régulière) ne sont plus divisées lors de la redistribution de chaînes littérales longues (#1186, #1253, #1439).
  • Les échecs lors de la redistribution de longues chaînes sont signalés comme des erreurs au lieu de planter ou de suspendre le CLI (#1439).

Autres correctifs

  • Correction du formatage dans le plugin Eclipse, qui échouait avec NoClassDefFoundError depuis 1.36.0 car le plugin ne regroupait pas commonmark (#1428).
  • L'erreur de combinaison de --dry-run avec --replace nomme désormais le drapeau de droite (#1094).

Modifications API

  • JavaFormatterOptions.Builder.cleanup(boolean) contrôle la nouvelle passe de nettoyage et est par défaut true. Cela signifie que Formatter.formatSource effectue désormais par défaut les modifications autres que les espaces répertoriées ci-dessus. Intégrations qui formatent le code que l'utilisateur modifie, par ex. formatage lors de la sauvegarde dans un IDE, doit définir cleanup(false) ; le plugin IntelliJ fait cela.
  • Formatter.getFormatReplacements est désormais strictement réservé aux espaces : il ne réorganise plus les modificateurs et n'applique jamais de nettoyage. Utilisez Formatter.formatSource(String, Collection<Range<Integer>>) pour formater des plages de caractères avec réorganisation des modificateurs.
  • JavaFormatterOptions.Style est devenu un disque dans 1.37.0. Les méthodes compatibles avec l'énumération, telles que Style.valueOf(String), ont été restaurées pour des outils comme Spotless qui les appelaient (#1478).
  • Les classes du moteur de mise en page précédent (com.google.googlejavaformat.Doc, OpsBuilder et types associés) ne sont plus utilisées pour formater Java, mais sont toujours incluses pour les autres formateurs qui s'appuient sur elles.

google-java-format v2.0.0

google-java-format 2.0.0 replaces the formatter's layout engine, and makes some improvements to lambda formatting (#19). This release also adds an optional cleanup pass that makes small non-whitespace changes, which is enabled by default.

Because of these changes, 2.0.0 reformats more existing code than a typical release. We recommend reformatting your codebase in a single commit when upgrading.

Formatting changes

  • A lambda that is the only argument of a call is now kept on the same line as the call, instead of starting on a new line with an extra level of indentation (#19):

    executor.submit(() -> {
  doSomething();
});

  • Text blocks are now indented as part of the main formatting pass, so their indentation is correct even with --skip-reflowing-long-strings.

  • Fixed indentation of comments after assert, enum constants, for initializers, try resources, multi-catch clauses, and type arguments.

Cleanups

  • Added a --cleanup flag, enabled by default, for small non-whitespace changes:

    • removing redundant semicolons
    • removing empty annotation parentheses (@Foo() → @Foo)
    • removing parentheses around a single untyped lambda parameter ((x) -> ... → x -> ...) (#762)

    Cleanups only apply to the ranges being formatted. Use --cleanup=false to only change whitespace (and the existing --skip-sorting-imports, --skip-removing-unused-imports, and --skip-reordering-modifiers flags for the other non-whitespace changes).

  • When formatting a range with --lines or --offset and cleanups enabled, unformatted statements outside the range are re-indented to match the formatted output, so an edit that adds or removes a level of nesting doesn't leave the surrounding code misaligned. Blank lines left behind by cleanups are removed.

Configuration

  • --max-line-length=N sets the column limit (default 100) (#425). (This flag was introduced in v1.37.0)

Language support

  • Support value classes and value records (JEP 401: Value Objects (Preview))

Javadoc

  • Strip trailing asterisks before */ (#67).
  • Preserve relative indentation in <pre>{@code ...} blocks without leading *.
  • Join hyphenated words broken across lines.

Long strings

  • When formatting a range with --lines or --offset, only long string literals in the requested range are reflowed (#1114).
  • Escaped backslashes (e.g. \\t in a Windows path or a regular expression) are no longer split when reflowing long string literals (#1186, #1253, #1439).
  • Failures while reflowing long strings are reported as errors instead of crashing or hanging the CLI (#1439).

Other fixes

  • Fixed formatting in the Eclipse plugin, which failed with NoClassDefFoundError since 1.36.0 because the plugin didn't bundle commonmark (#1428).
  • The error for combining --dry-run with --replace now names the right flag (#1094).

API changes

  • JavaFormatterOptions.Builder.cleanup(boolean) controls the new cleanup pass, and defaults to true. This means Formatter.formatSource now makes the non-whitespace changes listed above by default. Integrations that format code the user is editing, e.g. format-on-save in an IDE, should set cleanup(false); the IntelliJ plugin does this.
  • Formatter.getFormatReplacements is now strictly whitespace-only: it no longer reorders modifiers, and never applies cleanups. Use Formatter.formatSource(String, Collection<Range<Integer>>) to format character ranges with modifier reordering.
  • JavaFormatterOptions.Style became a record in 1.37.0. The enum-compatible methods, such as Style.valueOf(String), have been restored for tools like Spotless that called them (#1478).
  • The previous layout engine's classes (com.google.googlejavaformat.Doc, OpsBuilder, and related types) are no longer used to format Java, but are still included for other formatters that build on them.

Full Changelog: https://github.com/google/google-java-format/compare/v1.37.0...v2.0.0
