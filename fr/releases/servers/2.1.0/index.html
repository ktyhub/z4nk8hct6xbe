# serveurs v2.1.0

Correctifs de sécurité

v2.1.0 corrige huit vulnérabilités sur trois serveurs. Mise à niveau @modelcontextprotocol/server-filesystem et @modelcontextprotocol/server-everything à 2.0.1 et mcp-server-fetch à 2026.10.24. | Forfait | Affecté | Corrigé dans | | --- | --- | --- | | @modelcontextprotocol/server-filesystem | 1.0.0 à 2.0.0 et versions de date à 2026.8.31 | 2.0.1 | | @modelcontextprotocol/server-everything | 1.0.0 à 2.0.0, et versions de date 2025.9.24 à 2026.8.31 | 2.0.1 | | mcp-server-fetch | via 2026.10.19 | 2026.10.24 |

@modelcontextprotocol/server-filesystem 2.0.1

  • Les écritures restent dans le répertoire qui a été vérifié (Linux et macOS). Un répertoire parent échangé contre un lien symbolique entre le contrôle d'accès et l'écriture ne peut plus rediriger write_file, edit_file, create_directory ou la destination move_file en dehors des répertoires autorisés. Sous Windows, ce problème n'est que partiellement résolu ; l'avis indique ce qui est encore exposé et comment configurer autour de cela (GHSA-53mr-w429-c597)
  • Les chemins sont vérifiés exactement comme ils sont utilisés. La vérification d'accès ne supprime plus les guillemets de fin ou les espaces que l'opération sur le fichier conserve, donc un répertoire frère nommé d'après un répertoire autorisé avec ce suffixe n'est plus accessible (GHSA-7rgq-gccq-qphx)
  • Un lien symbolique orthographié dans une casse différente ne réussit plus la vérification du lien symbolique pour un nouveau chemin sur un volume insensible à la casse, tel que celui par défaut de macOS. Il s'agissait d'une régression dans 2026.8.31 (GHSA-4gxg-m5jx-9j57)
  • list_directory_with_sizes vérifie chaque entrée avant de lire sa taille, donc un lien symbolique à l'intérieur d'un répertoire autorisé ne révèle plus la taille et l'heure de modification d'un fichier en dehors de celui-ci (GHSA-hhwq-wxfx-cj7g) ###@modelcontextprotocol/server-everything2.0.1
  • Les transports HTTP et SSE refusent les requêtes provenant d'autres origines Web. Ils vérifient désormais l'en-tête Origin et n'envoient plus Access-Control-Allow-Origin: *, donc une page Web visitée par l'utilisateur ne peut plus appeler les outils du serveur (tels que get-env) ou lire leurs résultats (GHSA-mvf5-2qqv-rg3c) ###mcp-server-fetch2026.10.24
  • La vérification de l'adresse et la connexion utilisent le même nom d'hôte. Pour un nom d'hôte internationalisé (IDNA), le serveur utilisé pour vérifier une forme du nom et se connecter à une autre, qui pourrait atteindre une adresse interne (GHSA-v38p-wf49-hx2j)
  • Les adresses NAT64 sont jugées par l'adresse IPv4 qu'elles portent. Une adresse dans 64:ff9b::/96 qui encapsule une adresse IPv4 privée, de bouclage ou de lien local est désormais refusée, comme l'était déjà une adresse mappée IPv4 (GHSA-66qx-2266-pmj6)
  • robots.txt est vérifié à nouveau après chaque redirection, pas seulement pour l'URL demandée en premier (GHSA-3jqg-r5pp-rmp2)

Mise à niveau à partir d'une version npm avec version datée

Les serveurs TypeScript sont passés des versions de date (2025.x, 2026.x) aux versions sémantiques dans 1.0.0. Les gestionnaires de packages classent 2.0.1 en dessous de chaque version 2025.x et 2026.x, ils ne le proposeront donc pas comme mise à niveau. Si vous êtes sur une version date, installez explicitement 2.0.1, par exemple npm install @modelcontextprotocol/server-filesystem@2.0.1.

servers v2.1.0

Security fixes

v2.1.0 fixes eight vulnerabilities in three servers. Upgrade @modelcontextprotocol/server-filesystem and @modelcontextprotocol/server-everything to 2.0.1, and mcp-server-fetch to 2026.10.24.

| Package | Affected | Fixed in | | --- | --- | --- | | @modelcontextprotocol/server-filesystem | 1.0.0 through 2.0.0, and date versions through 2026.8.31 | 2.0.1 | | @modelcontextprotocol/server-everything | 1.0.0 through 2.0.0, and date versions 2025.9.24 through 2026.8.31 | 2.0.1 | | mcp-server-fetch | through 2026.10.19 | 2026.10.24 |

@modelcontextprotocol/server-filesystem 2.0.1

  • Writes stay inside the directory that was checked (Linux and macOS). A parent directory swapped for a symlink between the access check and the write can no longer redirect write_file, edit_file, create_directory or the move_file destination outside the allowed directories. On Windows this is only partly fixed; the advisory says what is still exposed and how to configure around it (GHSA-53mr-w429-c597)
  • Paths are checked exactly as they are used. The access check no longer strips a trailing quote or whitespace that the file operation keeps, so a sibling directory named after an allowed one with that suffix is no longer reachable (GHSA-7rgq-gccq-qphx)
  • A symlink spelled in a different letter case no longer passes the symlink check for a new path on a case-insensitive volume, such as macOS's default. This was a regression in 2026.8.31 (GHSA-4gxg-m5jx-9j57)
  • list_directory_with_sizes checks each entry before reading its size, so a symlink inside an allowed directory no longer reveals the size and modification time of a file outside it (GHSA-hhwq-wxfx-cj7g)

@modelcontextprotocol/server-everything 2.0.1

  • The HTTP and SSE transports refuse requests from other web origins. They now check the Origin header and no longer send Access-Control-Allow-Origin: *, so a web page the user visits can no longer call the server's tools (such as get-env) or read their results (GHSA-mvf5-2qqv-rg3c)

mcp-server-fetch 2026.10.24

  • The address check and the connection use the same host name. For an internationalized (IDNA) host name, the server used to check one form of the name and connect to another, which could reach an internal address (GHSA-v38p-wf49-hx2j)
  • NAT64 addresses are judged by the IPv4 address they carry. An address in 64:ff9b::/96 that wraps a private, loopback or link-local IPv4 address is now refused, as an IPv4-mapped one already was (GHSA-66qx-2266-pmj6)
  • robots.txt is checked again after every redirect, not only for the URL first requested (GHSA-3jqg-r5pp-rmp2)

Upgrading from a date-versioned npm release

The TypeScript servers moved from date versions (2025.x, 2026.x) to semantic versions in 1.0.0. Package managers rank 2.0.1 below every 2025.x and 2026.x version, so they won't offer it as an upgrade. If you are on a date version, install 2.0.1 explicitly, for example npm install @modelcontextprotocol/server-filesystem@2.0.1.
