#claude-mem v15.18.5

Correctifs critiques

  • Le tree-sitter CLI s'installe sur des réseaux où son script de téléchargement continue d'échouer (#6110, merci @rigel905, ferme le #6109). Sur certains réseaux, le install.js du tree-sitter-cli a vu sa requête réinitialisée à chaque fois, ou est sorti à 0 sur un fichier tronqué. La vérification SHA-256 épinglée a correctement refusé le fichier, mais rien n'a été récupéré par la suite, donc smart_search, smart_outline, smart_unfold et File Read Gate sont restés désactivés à chaque démarrage du travailleur et npx claude-mem repair a été abandonné. Désormais, lorsque le script échoue ou laisse autre chose que l'exécutable épinglé, claude-mem récupère directement le même actif de version, une fois, dans le même budget de temps d'installation, et ne l'exécute qu'après l'avoir décompressé sur le même SHA-256 épinglé. Le script s'exécute toujours en premier, donc HTTPS_PROXY continue de fonctionner. Un script qui a utilisé tout le budget ne peut pas faire l'objet d'une seconde tentative.
  • Une collection Chroma corrompue est supprimée une fois, pas une fois par remplissage parallèle (#6115, merci @mohitdixit02 et @0xABCD01, ferme le #6113). Lorsque le segment HNSW d'une grande collection était corrompu, chaque remplissage parallèle par projet qui le frappait passait la vérification "drop only once" avant la fin de la première suppression et mettait en file d'attente sa propre suppression contre chroma-mcp. Dans le numéro 6113, qui a exécuté 19 gouttes à la fois et a poussé chroma-mcp à une empreinte mémoire de 312 Go, bloquant un Mac de 32 Go. Les appelants rejoignent désormais le drop déjà en cours pour cette collecte et partagent son résultat. Un abandon échoué coûte une tentative du budget de nouvelle tentative, et non une par appelant, et les différentes collections sont toujours abandonnées indépendamment. Les demandes restantes de ce rapport (une mémoire liée à chroma-mcp, l'arrêt des écritures lorsqu'une chute ne peut pas être confirmée, la mesure de l'empreinte sur macOS) sont suivies dans #3610.

Correctifs

  • --help affiche l'aide au lieu d'exécuter la commande (#6142, merci @liuyinchu). npx claude-mem mcp --help démarrait le serveur stdio, et status, doctor et hook entraient dans leurs chemins d'exécution ; t3code et ses pseudonymes ont rejeté le drapeau. -h et --help sont désormais traités avant expédition pour ces commandes. Plain mcp démarre toujours le serveur.

Documents

  • Guide de rappel OmO Native (#6087, merci @mschoi0411). Comment connecter OmO Native au travailleur local via le serveur MCP stdio existant : découverte d'outils, rappel par projet et ID d'observation, dépannage et déconnexion.

claude-mem v15.18.5

Critical fixes

  • The tree-sitter CLI installs on networks where its download script keeps failing (#6110, thanks @rigel905, closes #6109). On some networks tree-sitter-cli's own install.js had its request reset every time, or exited 0 on a truncated file. The pinned SHA-256 check correctly refused the file, but nothing recovered after that, so smart_search, smart_outline, smart_unfold and the File Read Gate stayed off on every worker start, and npx claude-mem repair aborted. Now, when the script fails or leaves anything but the pinned executable, claude-mem fetches the same release asset directly, once, inside the same install time budget, and runs it only after it unpacks to the same pinned SHA-256. The script still runs first, so HTTPS_PROXY keeps working. A script that used up the whole budget gets no second attempt.
  • A corrupt Chroma collection is dropped once, not once per parallel backfill (#6115, thanks @mohitdixit02 and @0xABCD01, closes #6113). When the HNSW segment of a large collection was corrupt, every parallel per-project backfill that hit it passed the "drop only once" check before the first delete finished, and queued its own delete against chroma-mcp. In #6113 that ran 19 drops at once and pushed chroma-mcp to a 312 GB memory footprint, stalling a 32 GB Mac. Callers now join the one drop already running for that collection and share its outcome. A failed drop costs one attempt from the retry budget, not one per caller, and different collections still drop independently. The remaining asks from that report (a memory bound on chroma-mcp, stopping writes when a drop can't be confirmed, measuring footprint on macOS) are tracked in #3610.

Fixes

  • --help prints help instead of running the command (#6142, thanks @liuyinchu). npx claude-mem mcp --help used to start the stdio server, and status, doctor and hook entered their runtime paths; t3code and its aliases rejected the flag. -h and --help are now handled before dispatch for these commands. Plain mcp still starts the server.

Docs

  • OmO Native recall guide (#6087, thanks @mschoi0411). How to connect OmO Native to the local worker through the existing stdio MCP server: tool discovery, recall by project and observation ID, troubleshooting and disconnect.
