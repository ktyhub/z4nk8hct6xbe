Nouveaux pipelines pour la génération vidéo

Wan 2.1

Wan2.1 est une suite complète et ouverte de modèles de base vidéo qui repousse les limites de la génération vidéo. La version du modèle comprend 4 variantes de modèle différentes et trois pipelines différents pour le texte vers la vidéo, l'image vers la vidéo et la vidéo vers la vidéo. -Wan-AI/Wan2.1-T2V-1.3B-Diffusers -Wan-AI/Wan2.1-T2V-14B-Diffusers -Wan-AI/Wan2.1-I2V-14B-480P-Diffusers -Wan-AI/Wan2.1-I2V-14B-720P-Diffusers Consultez la documentation [ici] (https://huggingface.co/docs/diffusers/main/en/api/pipelines/wan) pour en savoir plus.

Vidéo LTX 0.9.5

LTX Video 0.9.5 est la version mise à jour de la série de modèles LTX Video ultra-rapides. Le dernier modèle introduit des options de conditionnement supplémentaires, telles que l'animation basée sur des images clés et l'extension vidéo (à la fois avant et arrière). Pour prendre en charge ces entrées de conditionnement supplémentaires, nous avons introduit les objets LTXConditionPipeline et LTXVideoCondition. Pour en savoir plus sur l'utilisation, consultez la documentation [ici] (https://huggingface.co/docs/diffusers/main/en/api/pipelines/ltx_video).

Image Hunyuan en vidéo

Hunyuan utilise un modèle multimodal de langage étendu (MLLM) pré-entraîné avec une architecture de décodeur uniquement comme encodeur de texte. L'image d'entrée est traitée par le MLLM pour générer des jetons d'image sémantique. Ces jetons sont ensuite concaténés avec les jetons vidéo latents, permettant un calcul complet et complet sur les données combinées et intégrant de manière transparente les informations de l'image et de sa légende associée. Pour en savoir plus, consultez la documentation [ici] (https://huggingface.co/docs/diffusers/main/en/api/pipelines/hunyuan_video).

Nouveaux pipelines pour la génération d'images

Sana-Sprint

SANA-Sprint est un modèle de diffusion efficace pour la génération ultra-rapide de texte en image. SANA-Sprint est construit sur un modèle de base pré-entraîné et complété par une distillation hybride, réduisant considérablement les étapes d'inférence de 20 à 1-4, rivalisant avec la qualité de modèles comme Flux. Omnigène

OmniGen est un modèle de génération d'images unifié qui peut gérer plusieurs tâches, notamment la conversion texte-image, l'édition d'images, la génération axée sur le sujet et diverses tâches de vision par ordinateur dans un seul cadre. Le modèle se compose d'un VAE et d'un seul transformateur basé sur Phi-3 qui gère l'encodage du texte et des images ainsi que le processus de diffusion. ### Déchargement de groupe
Le déchargement de groupe est le juste milieu entre le déchargement séquentiel et le déchargement de modèle. Il fonctionne en déchargeant des groupes de couches internes (`torch.nn.ModuleList` ou `torch.nn.Sequential`), ce qui utilise moins de mémoire que le déchargement au niveau du modèle. Il est également plus rapide que le déchargement au niveau séquentiel car le nombre de synchronisations d’appareils est réduit. 
Sur les appareils CUDA, nous avons également la possibilité d'activer l'utilisation de la prélecture de couche avec [CUDA Streams] (https://pytorch.org/docs/stable/generated/torch.cuda.Stream.html). La couche suivante à exécuter est chargée sur le dispositif accélérateur pendant que la couche actuelle est en cours d'exécution, ce qui rend l'inférence beaucoup plus rapide tout en maintenant les exigences de VRAM très faibles. Avec cela, nous introduisons l’idée de chevauchement du calcul avec le transfert de données.
Une chose à noter est que l’utilisation de flux CUDA peut entraîner une augmentation considérable de l’utilisation de la RAM du processeur. Veuillez vous assurer que la RAM CPU disponible est 2 fois la taille du modèle si vous choisissez de définir `use_stream=True`. Vous pouvez réduire l'utilisation de la RAM du processeur en définissant `low_cpu_mem_usage=True`. Cela devrait limiter la RAM du processeur utilisée à peu près à la même taille que la taille du modèle, mais introduira une légère latence dans le processus d'inférence.  
Vous pouvez également utiliser `record_stream=True` lorsque vous utilisez `use_stream=True` pour obtenir davantage d'accélérations au détriment d'une utilisation de la mémoire légèrement accrue.

Présentation de l'inférence mise en cache pour les DiT

L'inférence mise en cache pour les modèles de transformateur de diffusion est une optimisation des performances qui accélère considérablement le processus de débruitage en mettant en cache les valeurs intermédiaires. ### Chargement amélioré pour les points de contrôle `uintx` TorchAO avec `torch>=2.6`
Les points de contrôle TorchAO doivent actuellement être sérialisés à l'aide de pickle. Pour certains types de quantification utilisant le format `uintx`, tels que `uint4wo`, cela implique de sauvegarder les objets Tensor TorchAO sous-classés dans le fichier modèle. Cela a rendu le chargement des modèles directement avec les diffuseurs un peu délicat puisque nous n'autorisons pas la désérialisation d'objets artbitaires Python à partir de fichiers pickle.    
Torch 2.6 permet d'ajouter les Tensors attendus aux globaux sécurisés de Torch, ce qui nous permet de charger directement les points de contrôle TorchAO avec ces objets.

LoRA

Nous avons apporté quelques améliorations sur le front LoRA dans cette version. 🚨 Couverture améliorée pour le chargement des points de contrôle LoRA non-diffuseurs pour Flux Prenez note du changement radical introduit dans ce PR 🚨 Nous vous suggérons de mettre à niveau votre installation peft vers la dernière version - pip install -U peft, en particulier lorsqu'il s'agit de Flux LoRA. Prise en charge de torch.compile() lors du remplacement à chaud des LoRA sans déclencher la recompilation Un cas d'utilisation courant lors de la fourniture de plusieurs adaptateurs consiste à charger d'abord un adaptateur, à générer des images, à charger un autre adaptateur, à générer davantage d'images, à charger un autre adaptateur, etc. Ce flux de travail nécessite normalement d'appeler load_lora_weights(), set_adapters() et éventuellement delete_adapters() pour économiser de la mémoire. De plus, si le modèle est compilé à l'aide de torch.compile, l'exécution de ces étapes nécessite une recompilation, ce qui prend du temps. Pour mieux prendre en charge ce flux de travail courant, vous pouvez « hotswap » un adaptateur LoRA, pour éviter l'accumulation de mémoire et, dans certains cas, la recompilation. Cela nécessite qu'un adaptateur soit déjà chargé et que les nouveaux poids de l'adaptateur soient remplacés sur place par l'adaptateur existant. New Memory Optimizations

Layerwise Casting

PyTorch supports torch.float8_e4m3fn and torch.float8_e5m2 as weight storage dtypes, but they can’t be used for computation on many devices due to unimplemented kernel support.

However, you can still use these dtypes to store model weights in FP8 precision and upcast them to a widely supported dtype such as torch.float16 or torch.bfloat16 on-the-fly when the layers are used in the forward pass. This is known as layerwise weight-casting. This can potentially cut down the VRAM requirements of a model by 50%.  

<details> <summary>Code</summary> 
import torch
from diffusers import CogVideoXPipeline, CogVideoXTransformer3DModel
from diffusers.utils import export_to_video

model_id = "THUDM/CogVideoX-5b"

# Load the model in bfloat16 and enable layerwise casting
transformer = CogVideoXTransformer3DModel.from_pretrained(model_id, subfolder="transformer", torch_dtype=torch.bfloat16)
transformer.enable_layerwise_casting(storage_dtype=torch.float8_e4m3fn, compute_dtype=torch.bfloat16)

# Load the pipeline
pipe = CogVideoXPipeline.from_pretrained(model_id, transformer=transformer, torch_dtype=torch.bfloat16)
pipe.to("cuda")

prompt = (
    "A panda, dressed in a small, red jacket and a tiny hat, sits on a wooden stool in a serene bamboo forest. "
    "The panda's fluffy paws strum a miniature acoustic guitar, producing soft, melodic tunes. Nearby, a few other "
    "pandas gather, watching curiously and some clapping in rhythm. Sunlight filters through the tall bamboo, "
    "casting a gentle glow on the scene. The panda's face is expressive, showing concentration and joy as it plays. "
    "The background includes a small, flowing stream and vibrant green foliage, enhancing the peaceful and magical "
    "atmosphere of this unique musical performance."
)
video = pipe(prompt=prompt, guidance_scale=6, num_inference_steps=50).frames[0]
export_to_video(video, "output.mp4", fps=8)

Group Offloading

Group offloading is the middle ground between sequential and model offloading. It works by offloading groups of internal layers (either torch.nn.ModuleList or torch.nn.Sequential), which uses less memory than model-level offloading. It is also faster than sequential-level offloading because the number of device synchronizations is reduced.

On CUDA devices, we also have the option to enable using layer prefetching with CUDA Streams. The next layer to be executed is loaded onto the accelerator device while the current layer is being executed which makes inference substantially faster while still keeping VRAM requirements very low. With this, we introduce the idea of overlapping computation with data transfer.

One thing to note is that using CUDA streams can cause a considerable spike in CPU RAM usage. Please ensure that the available CPU RAM is 2 times the size of the model if you choose to set use_stream=True. You can reduce CPU RAM usage by setting low_cpu_mem_usage=True. This should limit the CPU RAM used to be roughly the same as the size of the model, but will introduce slight latency in the inference process.

You can also use record_stream=True when using use_stream=True to obtain more speedups at the expense of slightly increased memory usage.

<details> <summary>Code</summary> 
import torch
from diffusers import CogVideoXPipeline
from diffusers.utils import export_to_video

# Load the pipeline
onload_device = torch.device("cuda")
offload_device = torch.device("cpu")
pipe = CogVideoXPipeline.from_pretrained("THUDM/CogVideoX-5b", torch_dtype=torch.bfloat16)

# We can utilize the enable_group_offload method for Diffusers model implementations
pipe.transformer.enable_group_offload(
	onload_device=onload_device, 
	offload_device=offload_device, 
	offload_type="leaf_level", 
	use_stream=True
)

prompt = (
    "A panda, dressed in a small, red jacket and a tiny hat, sits on a wooden stool in a serene bamboo forest. "
    "The panda's fluffy paws strum a miniature acoustic guitar, producing soft, melodic tunes. Nearby, a few other "
    "pandas gather, watching curiously and some clapping in rhythm. Sunlight filters through the tall bamboo, "
    "casting a gentle glow on the scene. The panda's face is expressive, showing concentration and joy as it plays. "
    "The background includes a small, flowing stream and vibrant green foliage, enhancing the peaceful and magical "
    "atmosphere of this unique musical performance."
)
video = pipe(prompt=prompt, guidance_scale=6, num_inference_steps=50).frames[0]
# This utilized about 14.79 GB. It can be further reduced by using tiling and using leaf_level offloading throughout the pipeline.
print(f"Max memory reserved: {torch.cuda.max_memory_allocated() / 1024**3:.2f} GB")
export_to_video(video, "output.mp4", fps=8)
</details>

Improved loading for uintx TorchAO checkpoints with torch>=2.6

TorchAO checkpoints currently have to be serialized using pickle. For some quantization dtypes using the uintx format, such as uint4wo this involves saving subclassed TorchAO Tensor objects in the model file. This made loading the models directly with Diffusers a bit tricky since we do not allow deserializing artbitary Python objects from pickle files.

Torch 2.6 allows adding expected Tensors to torch safe globals, which lets us directly load TorchAO checkpoints with these objects.

- state_dict = torch.load("/path/to/flux_uint4wo/diffusion_pytorch_model.bin", weights_only=False, map_location="cpu")
- with init_empty_weights():
-     transformer = FluxTransformer2DModel.from_config("/path/to/flux_uint4wo/config.json")
- transformer.load_state_dict(state_dict, strict=True, assign=True)
+ transformer = FluxTransformer2DModel.from_pretrained("/path/to/flux_uint4wo/")

LoRAs

We have shipped a couple of improvements on the LoRA front in this release.

🚨 Improved coverage for loading non-diffusers LoRA checkpoints for Flux

Take note of the breaking change introduced in this PR 🚨 We suggest you upgrade your peft installation to the latest version - pip install -U peft especially when dealing with Flux LoRAs.

torch.compile() support when hotswapping LoRAs without triggering recompilation

A common use case when serving multiple adapters is to load one adapter first, generate images, load another adapter, generate more images, load another adapter, etc. This workflow normally requires calling load_lora_weights(), set_adapters(), and possibly delete_adapters() to save memory. Moreover, if the model is compiled using torch.compile, performing these steps requires recompilation, which takes time.

To better support this common workflow, you can “hotswap” a LoRA adapter, to avoid accumulating memory and in some cases, recompilation. It requires an adapter to already be loaded, and the new adapter weights are swapped in-place for the existing adapter.

Check out the docs to learn more about this feature.
