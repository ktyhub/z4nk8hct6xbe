Nouvelles méthodes

Optimiseur LoRA riemannien-préconditionnel

L'optimiseur LoRA préconditionné riemannien (#3382), contribué par @smellslikeml, est un nouvel optimiseur spécifique à LoRA similaire à LoRA-FA ou LoRA+ qui applique un préconditionnement riemannien sur les gradients pour améliorer l'apprentissage des fonctionnalités et éviter un réglage séparé des taux d'apprentissage pour les matrices A et B de LoRA.

Variante LoRA : Adaptation à valeur singulière basée sur la connaissance (KaSA)

KaSA vise à identifier des valeurs singulières conscientes des connaissances à partir du poids de base. Il supprime ensuite les connaissances bruitées de ces poids et entraîne spécifiquement les valeurs singulières les plus pertinentes pour la tâche. Implémenté dans #3446 par @robbiebusinessacc et @iambogeumkim.

Super-Tuning (#3518)

[Super-Tuning] (https://huggingface.co/docs/peft/main/en/package_reference/supertuning) utilise un score d'amplitude sans calibrage pour allouer un budget de réglage clairsemé. Avec la sélection BottomK, Super adapte les poids de faible amplitude, motivés par l'idée qu'ils offrent des degrés de liberté pour apprendre une nouvelle tâche tout en laissant intacts les poids pré-entraînés de plus grande ampleur. Supra ajoute LoRA en plus de cette mise à jour clairsemée. C'est un bon choix pour explorer la parcimonie parallèlement à une adaptation de rang supérieur, en particulier pour les tâches de réglage fin nécessitant beaucoup de raisonnement. Merci à @smellslikeml.

ShadowPEFT (#3354)

ShadowPEFT exécute un petit réseau fantôme parallèlement au modèle de base gelé. Cet état fantôme est mis à jour à chaque couche de décodeur, de sorte que l'adaptation est partagée sur toute la pile au lieu d'une mise à jour distincte de bas rang sur chaque couche linéaire ciblée (comme LoRA). C'est un bon choix lorsque vous vous souciez des performances en aval ou OOD et que vous souhaitez rester dans la même plage de paramètres entraînables que LoRA, ou lorsque vous souhaitez la petite ombre sur le bord et la base gelée dans le cloud. Cela fonctionne mieux si le modèle fantôme part d'un petit modèle pré-entraîné. Contribué par @SeanLee97.

Améliorations

  • Accélérer le calcul des paramètres cibles MoE (#3577) : pour le cas d'utilisation courant d'un adaptateur actif, le calcul du poids et du delta MoE LoRA est intégré en une seule opération baddbmm. Attendez-vous à de légères différences numériques dans ce cas.

  • Prend en charge torchao v0.18.0 en prenant en charge les nouvelles sous-classes de tenseurs Int8Tensor, Float8Tensor, etc.

  • [Réglage fin du sous-espace orthogonal] (https://huggingface.co/docs/peft/main/en/package_reference/osf) a reçu une mise à jour importante dans #3524 réduisant l'empreinte mémoire de 22 % et le temps de formation de 46 % selon le benchmark MetaMathQA tout en gardant la précision des tâches et la stabilité de l'oubli. Attendez-vous à de légères différences numériques, en particulier dans fp16, bf16.

  • https://github.com/huggingface/peft/pull/3639: Grâce à @amogh-nagri-11, des méthodes d'apprentissage rapide permettent désormais de supprimer un adaptateur. Pour l'invite d'adaptation, l'ajout ou le chargement d'un deuxième adaptateur ne l'active plus automatiquement, conformément à la façon dont les autres méthodes PEFT gèrent cela.

Modifications

Gestion des dicts d'état refactorisés (#3490)

Un changement interne a déplacé l'état du dict de chargement/sauvegarde des chemins de code spécifiques à la méthode vers les tuners respectifs. Cela devrait être transparent pour l'utilisateur final et a été testé de manière approfondie et devrait fonctionner exactement de la même manière que précédemment, mais si vous pensez que le modèle se comporte différemment, faites-le nous savoir.

Entraînement de l'adaptateur préservé pendant l'injection (#3495)

Auparavant, lors du chargement ou de l'ajout d'un deuxième, troisième, etc. adaptateur, cela pouvait affecter le requires_grad de l'adaptateur existant (ou du modèle de base), en fonction de la valeur de is_trainable. Cela ne devrait plus être le cas grâce à @DaoyuanLi2816.

Corrections de bugs pour la combinaison d'adaptateurs LoRA (#3111)

La combinaison d'adaptateurs LoRA à l'aide de add_weighted_adapter présentait un bug dans le chemin SVD qui conduisait à l'application de la mise à l'échelle LoRA deux fois. Ceci est maintenant corrigé.

OFT utilise un backend de quantification générique (#3355)

Nous avons déplacé OFT d'un backend de quantification spécifique à une méthode vers un backend de quantification générique. Cela affecte les bits et octets, GPT-Q, etc. Cela ne devrait pas affecter les points de contrôle existants, mais veuillez nous informer si vous rencontrez des problèmes.

Contrôles plus stricts sur la gestion des adaptateurs

  • #3667 : inject_adapter_in_model rejette désormais les méthodes PEFT qui ont un état partagé qui vivrait sur le modèle parent (comme VeRA), car aucun modèle parent de ce type n'existe. Contribué par @CoralGarden52.

  • #3534 : Grâce à @LK-maker-007, le PEFT renvoie désormais une erreur lors de l'ajout d'un deuxième adaptateur au modèle PEFT à l'aide de add_adapter qui cible des couches inexistantes. Avant, l’adaptateur n’adaptait rien mais restait silencieux à ce sujet. peft_model.targeted_module_names et peft_model.targeted_parameter_names ne contiennent plus de doublons. Ils sont toujours triés par ordre d'insertion (et non par ensembles). Pour supprimer les erreurs potentielles, capturez peft.PeftError.

  • #3504 : Lors de la suppression d'un adaptateur, il y a désormais une vérification si l'adaptateur est fusionné. S'il est fusionné, une erreur est générée, car sa suppression ne supprimerait pas son effet. Ceci a été contribué par @DaoyuanLi2816.

New methods

Riemannian-preconditional LoRA optimizer

Riemannian-preconditioned LoRA optimizer (#3382), contributed by @smellslikeml, is a new LoRA-specific optimizer similar to LoRA-FA or LoRA+ that applies a Riemannian pre-conditioning on the gradients to improve feature learning and avoiding separate tuning of learning rates for LoRA's A and B matrices.

LoRA variant: Knowledge-Aware Singular-Value Adaption (KaSA)

KaSA aims at identifying knowledge aware singular values from the base weight. It then removes noisy knowledge from those weights and specifically trains the singular values most relevant to the task. Implemented in #3446 by @robbiebusinessacc and @iambogeumkim.

Super-Tuning (#3518)

Super-Tuning uses calibration-free magnitude scoring to allocate a sparse tuning budget. With BottomK selection, Super adapts low-magnitude weights, motivated by the idea that they provide degrees of freedom for learning a new task while leaving larger-magnitude pretrained weights untouched. Supra adds LoRA on top of this sparse update. It is a good fit for exploring sparsity alongside higher-rank adaptation, particularly on reasoning-heavy fine-tuning tasks. Thanks to @smellslikeml.

ShadowPEFT (#3354)

ShadowPEFT runs a small shadow network alongside the frozen base model. That shadow state gets updated at every decoder layer, so adaptation is shared across the stack instead of a separate low-rank update on each targeted linear layer (like LoRA). It’s a good choice when you care about downstream or OOD performance and want to stay in the same trainable-parameter range as LoRA, or when you want the small shadow on the edge and the frozen base in the cloud. This works best if the shadow model starts from a small, pretrained model. Contributed by @SeanLee97.

Enhancements

  • Speed up MoE target parameter computation (#3577): For the common use case of one active adapter, weight and MoE LoRA delta computation is folded into a single baddbmm operation. Expect slight numerical differences in this case.

  • Support torchao v0.18.0 by supporting the newer Int8Tensor, Float8Tensor, etc. tensor subclasses.

  • Orthogonal Subspace Fine-tuning received a significant update in #3524 reducing the memory footprint by 22% and the training time by 46% according to the MetaMathQA benchmark while keeping task accuracy and forgetting stable. Expect slight numerical differences, especially in fp16, bf16.

  • https://github.com/huggingface/peft/pull/3639: Thanks to @amogh-nagri-11, prompt learning methods now allow to delete an adapter. For adaption prompt, adding or loading a second adapter no longer automatically activates it, in line with how other PEFT methods handle this.

Changes

Refactored state dict handling (#3490)

An internal change moved state dict loading/saving method-specific code paths to the respective tuners. This should be transparent to the end-user and was extensively tested and should work exactly the same as previously, but if you suspect that the model behaves differently, let us know.

Preserved adapter trainablity during injection (#3495)

Previously, when loading or adding a second, third etc. adapter, this could affect the requires_grad of the existing adapter (or base model), depending on the value of is_trainable. This should no longer be the case thanks to @DaoyuanLi2816.

Bug fixes for LoRA adapter combining (#3111)

Combining LoRA adapters using add_weighted_adapter had a bug in the SVD path which led to the LoRA scaling being applied twice. This is now fixed.

OFT uses generic quantization backend (#3355)

We moved OFT from a method-specific quantization backend to the generic quantization backend. This affects bitsandbytes, GPT-Q, etc. This should not affect existing checkpoints, but please let us know if you run into issues.

Stricter checks on adapter handling

  • #3667: inject_adapter_in_model now rejects PEFT methods that have shared state that would live on the parent model (like VeRA), as no such parent model exists. Contributed by @CoralGarden52.

  • #3534: Thanks to @LK-maker-007, the PEFT now throws an error when adding a second adapter to the PEFT model using add_adapter that targets non-existing layers. Before, the adapter would just not adapt anything but be silent about it. peft_model.targeted_module_names and peft_model.targeted_parameter_names no longer contain duplicates. They are still sorted by insertion order (not sets). To suppress potential errors, catch peft.PeftError.

  • #3504: When deleting an adapter, there is now a check if the adapter is merged. If it's merged, an error is raised, since deleting it would not remove its effect. This was contributed by @DaoyuanLi2816.
