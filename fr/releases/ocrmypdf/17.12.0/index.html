OCRmonPDF v17.12.0

Modifications

  • OCRmyPDF nécessite désormais pikepdf 10.2 ou version ultérieure, à partir de pikepdf 10. C'est le première version qui fournit pikepdf.NamePath, la famille Object.as_int() d'accesseurs de type sécurisé et un explicit_conversion() local au thread. OCRmonPDF utilise les trois pour lire les valeurs facultatives des fichiers PDF qu'il n'a pas écrits.
  • La prise en charge des entrées HEIF/HEIC est désormais un supplément optionnel, ocrmypdf[heic], au lieu de une dépendance par défaut. Le package pi-heif dont nous dépendions auparavant est abandonné; son successeur pillow-heif regroupe libheif, libde265 et x265 dans ses roues, ce qui rend la roue dans son ensemble sous licence GPLv2, donc nous ne le faisons pas installez-le par défaut. Installez ocrmypdf[heic] si vous envoyez des images HEIC à OCRmonPDF. L'image et le snap Docker ne l'incluent pas. {issue}1746
  • Un PDF balisé qui est refusé car il semble contenir du vrai texte maintenant sort avec le code 6 (already_done_ocr) au lieu du code 2 (input_file), faire correspondre le code de sortie d'un PDF avec une OCR préalable. Scripts qui vérifient la sortie le code 2 sur les PDF balisés doit être mis à jour. Merci @BetterAndBetterII. {issue}1551
  • Le package snap est désormais construit et publié à partir de notre CI plutôt que Launchpad, de sorte que les pistes de la chaîne stable soient à nouveau libérées au lieu d'être congelé à v16.4.2. Il est basé sur core26 et comprend un encodeur JBIG2.

Corrections

  • Le texte copié ou recherché dans un fichier --output-type pdfa est sorti comme un déchet (une substitution stable de caractères sans rapport, ou rien du tout) lorsque le La conversion PDF/A s'est déroulée via Ghostscript 9.56 via 10.04.x, qui inclut le Ghostscript dans Ubuntu 24.04. fpdf2 écrit le ToUnicode de chaque police CMap comme un seul bloc bfchar, mais la spécification CMap autorise au plus 100 entrées par bloc, et ces versions de Ghostscript suppriment toute la carte quand un bloc est plus grand. Toute page comportant plus de 100 glyphes distincts était affecté, ce qui représente presque chaque page de prose. Polices à clé CFF CID telles que Noto Sans CJK a le même problème dans son Encoding CMap, où ceux-ci Les versions de Ghostscript dessinent alors également les mauvais glyphes. OCRmyPDF se divise désormais chaque bloc CMap à 100 entrées au fur et à mesure que fpdf2 l'écrit, pour chaque version de fpdf2. fpdf2 2.8.9 divisera lui-même les blocs ToUnicode mais pas l'encodage bloque, donc le correctif reste en place. Merci @olafure pour l'analyse ({issue}1747, numéro fpdf2 py-pdf/fpdf2#1952).
  • Mots contenant fi, ff, fl et paires similaires extraits avec le lettres manquantes (con dentiality, e ects) dans les fichiers --output-type pdfa lorsque la conversion PDF/A s'est déroulée via Ghostscript 10.05.0 jusqu'à 10.06.x. Ces versions de Ghostscript suppriment les entrées ToUnicode qui s'étendent à plus de un caractère (bug Ghostscript 709030, corrigé dans 10.07.0), et le fpdf2 HarfBuzz shaping du moteur de rendu formait des ligatures latines facultatives dont les entrées font exactement cela. Texte invisible dans les scripts qui n'ont pas besoin de shaping est maintenant codé un glyphe par caractère, donc aucune entrée de ce type n'existe à perdre. Les scripts complexes sont toujours mis en forme et OCRmyPDF vous avertit désormais lorsqu'un fichier est affecté. Ghostscript est utilisé, car leurs mappages conjoints peuvent toujours être supprimés. Merci @kmn5 ({issue}1744).
  • Un PDF mal formé qui stocke autre chose qu'un dictionnaire à un clé structurelle - /Resources, /Resources /XObject, /Root /AcroForm, /Root /MarkInfo, /Root /Names, /Root /PieceInfo, /A d'une annotation, ou le /SMask d'une image -- est désormais toléré partout plutôt que dans le une poignée d'endroits qui avaient été durcis individuellement. Un tel fichier est lu comme bien que la clé manquât, ce que faisaient déjà les sentiers bien gardés.
  • Une image XObject sans /Subtype ne sort plus de l'optimiseur.
  • PdfInfo n'abandonne plus sur un /MarkInfo << /Marked 1 >>, où un producteur a écrit un drapeau sous forme d'entier au lieu de booléen. Merci @linhongyu510 ({issue}1742).
  • Une page /UserUnit écrite en PDF Real est désormais lue exactement plutôt que via virgule flottante binaire, donc les chiffres écrits par le fichier sont les chiffres utilisés.
  • --sidecar refuse désormais toute orthographe du fichier d'entrée ou de sortie, pas seulement un un octet identique. ocrmypdf in.pdf out.pdf --sidecar ./in.pdf a été accepté puis j'ai écrasé silencieusement le PDF d'entrée avec le texte OCR. Les chemins sont maintenant comparé après avoir résolu ., .., les liens symboliques et le cas du système de fichiers. Merci @linhongyu510.
  • --deskew et --rotate-pages préviennent désormais qu'ils n'auront aucun effet lorsque combiné avec --ocr-engine none, puisque l'inclinaison et l'orientation sont mesurées par le moteur OCR. Les autres options de traitement d’image ne sont pas affectées. Merci @Anai-Guo. {issue}1735
  • Documentation d'installation actualisée pour les plateformes actuelles : Ubuntu 26.04 et Fedora 43/44 ajouté, Ubuntu 20.04 supprimé et uv tool install affiché dans lieu de pip.
  • Documentation : correction de la liste des plateformes qui embarquent un encodeur JBIG2, qui inclut désormais Debian et Ubuntu. Merci @lcorbasson.
  • Processus de publication et améliorations de CI.

OCRmyPDF v17.12.0

Highlights

  • pikepdf 10.2 is now a hard floor — More than a version bump: v17.12 builds on three new pikepdf APIs — NamePath, the Object.as_int() family of type-safe accessors, and thread-local explicit_conversion() — to read optional values from PDFs it did not write. Pinning or vendoring an older pikepdf will now fail at install time, so update lockfiles before upgrading; the payoff is safer reads of third-party and malformed PDFs instead of brittle ad-hoc coercion.

  • HEIF/HEIC support is now opt-in (ocrmypdf[heic]) — The old pi-heif dependency is discontinued, and its successor pillow-heif bundles libheif, libde265 and x265 in its wheels, pulling a GPLv2 license into the dependency tree. The project therefore stopped installing it by default (#1746). If your pipeline feeds HEIC images you must install ocrmypdf[heic] explicitly — and note that the Docker image and snap deliberately omit it, so containerized deployments need their own build step.

  • Tagged-PDF exit code changes from 2 to 6 — A Tagged PDF refused for appearing to contain real text now exits with already_done_ocr (6) instead of input_file (2), matching ordinary prior-OCR files (#1551). This is a behavioral break for automation: any wrapper or CI check that treats exit code 2 as "bad input" will silently misclassify these files, so audit those checks before rolling out.

  • Silent text corruption in PDF/A output is fixed — Arguably the most important fix here: with Ghostscript 9.56–10.04.x (including Ubuntu 24.04's), ToUnicode CMaps with bfchar blocks larger than 100 entries were discarded wholesale, turning copied/searched text into garbage on essentially any page of prose; CID-keyed CJK fonts such as Noto Sans CJK also drew wrong glyphs. OCRmyPDF now splits every CMap block to 100 entries as fpdf2 writes it (#1747, fpdf2#1952). If you shipped PDF/A files through an affected Ghostscript, treat earlier output as suspect and re-OCR it.

  • Ligature-related dropped letters fixed in PDF/A — Ghostscript 10.05.0–10.06.x discards ToUnicode entries that expand to more than one character (Ghostscript bug 709030, fixed in 10.07.0), so words with fi/ff/fl came out as con dentiality and e ects (#1744). Invisible text is now encoded one glyph per character so those entries never exist; complex scripts are still shaped, and OCRmyPDF now warns when an affected Ghostscript is in use because conjunct mappings can still be lost — keep an eye on non-Latin output until you move to Ghostscript 10.07+.

  • Robustness and safety hardening — --sidecar now rejects any path resolving to the input or output file (after ./.., symlink and case normalization), closing a real data-loss bug where --sidecar ./in.pdf silently overwrote the source PDF with OCR text. Parsing now uniformly tolerates non-dictionary values at structural keys (/Resources, /Root /AcroForm, /MarkInfo, /SMask, etc.), PdfInfo no longer aborts on /Marked 1 written as an integer (#1742), and --deskew/--rotate-pages now warn that they do nothing with --ocr-engine none since those measurements come from the OCR engine (#1735).

Changes

  • OCRmyPDF now requires pikepdf 10.2 or later, up from pikepdf 10. This is the first release that provides pikepdf.NamePath, the Object.as_int() family of type-safe accessors, and a thread-local explicit_conversion(). OCRmyPDF uses all three to read optional values out of PDFs it did not write.
  • HEIF/HEIC input support is now an opt-in extra, ocrmypdf[heic], instead of a default dependency. The pi-heif package we previously depended on is discontinued; its successor pillow-heif bundles libheif, libde265 and x265 in its wheels, making the wheel as a whole GPLv2-licensed, so we do not install it by default. Install ocrmypdf[heic] if you feed HEIC images to OCRmyPDF. The Docker image and snap do not include it. {issue}1746
  • A Tagged PDF that is refused because it appears to contain real text now exits with code 6 (already_done_ocr) instead of code 2 (input_file), matching the exit code for a PDF with prior OCR. Scripts that check for exit code 2 on tagged PDFs need updating. Thanks @BetterAndBetterII. {issue}1551
  • The snap package is now built and published from our CI rather than Launchpad, so the stable channel tracks releases again instead of being frozen at v16.4.2. It is based on core26 and includes a JBIG2 encoder.

Fixes

  • Text copied or searched in a --output-type pdfa file came out as garbage (a stable substitution of unrelated characters, or nothing at all) when the PDF/A conversion ran through Ghostscript 9.56 through 10.04.x, which includes the Ghostscript in Ubuntu 24.04. fpdf2 writes each font's ToUnicode CMap as a single bfchar block, but the CMap specification allows at most 100 entries per block, and those Ghostscript releases discard the whole map when a block is larger. Any page with more than 100 distinct glyphs was affected, which is nearly every page of prose. CFF CID-keyed fonts such as Noto Sans CJK have the same problem in their Encoding CMap, where those Ghostscript releases then also draw the wrong glyphs. OCRmyPDF now splits every CMap block to 100 entries as fpdf2 writes it, for every fpdf2 release. fpdf2 2.8.9 will split the ToUnicode blocks itself but not the Encoding blocks, so the fix stays in place. Thanks @olafure for the analysis ({issue}1747, fpdf2 issue py-pdf/fpdf2#1952).
  • Words containing fi, ff, fl and similar pairs extracted with the letters missing (con dentiality, e ects) from --output-type pdfa files when the PDF/A conversion ran through Ghostscript 10.05.0 through 10.06.x. Those Ghostscript releases drop ToUnicode entries that expand to more than one character (Ghostscript bug 709030, fixed in 10.07.0), and the fpdf2 renderer's HarfBuzz shaping had been forming optional Latin ligatures whose entries do exactly that. Invisible text in scripts that do not need shaping is now encoded one glyph per character, so no such entries exist to lose. Complex scripts still get shaped, and OCRmyPDF now warns when an affected Ghostscript is in use, since their conjunct mappings can still be dropped. Thanks @kmn5 ({issue}1744).
  • A malformed PDF that stores something other than a dictionary at a structural key -- /Resources, /Resources /XObject, /Root /AcroForm, /Root /MarkInfo, /Root /Names, /Root /PieceInfo, an annotation's /A, or an image's /SMask -- is now tolerated everywhere rather than in the handful of places that had been hardened individually. Such a file is read as though the key were absent, which is what the well-guarded paths already did.
  • An image XObject with no /Subtype no longer raises out of the optimizer.
  • PdfInfo no longer aborts on a /MarkInfo << /Marked 1 >>, where a producer wrote a flag as an integer instead of a Boolean. Thanks @linhongyu510 ({issue}1742).
  • A page /UserUnit written as a PDF Real is now read exactly rather than via binary floating point, so the digits the file wrote are the digits used.
  • --sidecar now refuses any spelling of the input or output file, not just a byte-identical one. ocrmypdf in.pdf out.pdf --sidecar ./in.pdf was accepted and then silently overwrote the input PDF with the OCR text. Paths are now compared after resolving ., .., symlinks and filesystem case. Thanks @linhongyu510.
  • --deskew and --rotate-pages now warn that they will have no effect when combined with --ocr-engine none, since skew and orientation are measured by the OCR engine. Other image processing options are unaffected. Thanks @Anai-Guo. {issue}1735
  • Installation documentation refreshed for current platforms: Ubuntu 26.04 and Fedora 43/44 added, Ubuntu 20.04 dropped, and uv tool install shown in place of pip.
  • Documentation: corrected the list of platforms that ship a JBIG2 encoder, which now includes Debian and Ubuntu. Thanks @lcorbasson.
  • Release process and CI improvements.
