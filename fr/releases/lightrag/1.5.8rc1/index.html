LightRAG v1.5.8rc1

Remarques importantes

v1.5.8rc1 est une version candidate. Veuillez le tester sur une copie de vos données avant de mettre à niveau la production.

Faits saillants

1. Stockage de configuration : LightRAG se souvient désormais du modèle d'intégration qui a construit vos vecteurs

Dans les versions antérieures, la modification de EMBEDDING_MODEL ou EMBEDDING_DIM sur un déploiement existant échouait silencieusement. En fonction du backend, LightRAG a soit conservé les anciens vecteurs et renvoyé les mauvais voisins, soit ouvert un nouveau conteneur de vecteurs vide (Milvus / Qdrant / PostgreSQL) et a servi un graphe de connaissances sans aucun vecteur.

v1.5.8 ajoute un stockage de configuration. Il s'agit d'un petit espace de noms KV (config) qui contient les lignes de base d'intégration de chaque espace de travail : pour chaque cible vectorielle (entités, relations, morceaux), l'espace d'intégration dans lequel ses vecteurs ont été écrits. Le démarrage vérifie les lignes de base par rapport à la configuration d'intégration actuelle. Si l'espace a changé, le serveur refuse de démarrer et nomme la cible et la sortie, au lieu de fournir de mauvais résultats.

  • Backends : JsonKVStorage, PGKVStorage, MongoKVStorage et OpenSearchKVStorage, sélectionnés avec LIGHTRAG_CONFIG_STORAGE. Lorsqu'il n'est pas défini, il suit LIGHTRAG_KV_STORAGE, la plupart des déploiements ne nécessitent donc aucun nouveau paramètre. RedisKVStorage n'est pas admis, donc les déploiements Redis sont par défaut JsonKVStorage, avec un avertissement de démarrage.
  • Aucune préparation nécessaire. Au premier démarrage du v1.5.8, un déploiement existant enregistre lui-même ses lignes de base. Une référence est enregistrée uniquement sur la base de preuves : une sonde d'adoption réintègre quelques enregistrements stockés (jusqu'à 8 par cible) et les compare avec les vecteurs stockés, ou le conteneur est confirmé vide. Une sonde qui ne peut pas s'exécuter (par exemple, le service d'intégration est en panne) n'enregistre rien et est réessayée au prochain démarrage.
  • Ancre de déploiement. Le premier démarrage lie également le déploiement au conteneur de configuration qu'il a ouvert, dans WORKING_DIR/config_storage_anchor.json (type backend + UUID du conteneur). Chaque démarrage ultérieur refuse un conteneur d'un autre type ou d'un autre UUID. Un LIGHTRAG_KV_STORAGE modifié, une base de données différente ou un volume remplacé ne déplace donc plus silencieusement votre configuration.
  • Nouveaux outils hors ligne :
    • lightrag-rebuild-vdb réintègre un espace de travail avec le modèle actuel et enregistre les nouvelles lignes de base. C’est la solution après un changement intentionnel de modèle.
    • lightrag-migrate-config déplace le stockage de configuration vers un backend d'un autre type, par exemple des fichiers JSON vers PostgreSQL.
    • lightrag-clear-storage efface un espace de travail hors ligne, enregistrements de configuration inclus.
  • Plusieurs serveurs, un WORKING_DIR : pris en charge lorsque chaque serveur possède son propre WORKSPACE et son propre port. Un deuxième serveur sur le même espace de travail est refusé lorsque le système de fichiers prend en charge les verrous de fichiers.

Pour plus d'informations, voir :

  • docs/LightRAG-API-Server.md : Migration du stockage de configuration entre les types de backend
  • lightrag/tools/README_REBUILD_VDB.md, README_MIGRATE_CONFIG.md, README_CLEAR_STORAGE.md
  • docs/design/ConfigurationStorageDesign.md : l'aperçu de la conception

2. Écritures de graphiques et suppression de documents plus sûres

  • Les modifications manuelles des graphiques (créer/modifier/supprimer/fusionner des entités et des relations, insert_custom_kg) sont désormais sérialisées les unes par rapport aux autres et par rapport au pipeline d'ingestion sur NetworkXStorage.
  • L'ordre des validations pour la création, la modification, la fusion et le renommage d'entités/relations a été retravaillé pour éviter la perte de données lorsqu'une opération est interrompue.
  • Les suppressions de documents interrompues sont visibles et réessayables.
  • Le nouvel outil lightrag-repair-chunk-tracking supprime les lignes de suivi des morceaux orphelins laissées par une suppression interrompue.

3. Paramètres de stockage par défaut du PostgreSQL L'assistant de configuration génère désormais PostgreSQL à partir de l'image officielle pgvector/pgvector et propose PGTableGraphStorage (tableaux simples, pas d'Apache AGE) pour le graphique. PGGraphStorage (AGE) et les stockages Redis (RedisKVStorage, RedisDocStatusStorage) sont obsolètes. Ils continuent de fonctionner et enregistrent un avertissement au démarrage.

4. Renforcement de la sécurité et nouveau fournisseur

  • Les routes /api/* compatibles Ollama sont protégées par LIGHTRAG_API_KEY (voir Dernières modifications).
  • L'extraction PDF exécute pypdf dans un processus enfant aux ressources limitées.
  • Les lignes d'erreur diffusées en continu ne font plus écho au texte d'exception brut du fournisseur.
  • Nouvelle liaison openai_responses LLM pour OpenAI Responses API.

Modifications radicales

  • Python 3.11 ou version ultérieure est requis. Python 3.10 n'est plus pris en charge. Les images Docker (Python 3.12) ne sont pas affectées.
  • La modification du modèle d'intégration sur un espace de travail existant refuse désormais le démarrage, alors qu'il donnait auparavant des résultats erronés ou vides. Soit restaurez le précédent EMBEDDING_MODEL / EMBEDDING_DIM, soit exécutez lightrag-rebuild-vdb pour le réintégrer avec le nouveau modèle.
  • La modification de LIGHTRAG_KV_STORAGE après le premier démarrage du v1.5.8 est refusée alors que LIGHTRAG_CONFIG_STORAGE n'est pas défini, car le stockage de configuration se déplacerait silencieusement avec lui. Soit définissez explicitement LIGHTRAG_CONFIG_STORAGE sur le backend ancré, soit déplacez la configuration avec lightrag-migrate-config.
  • Les routes Ollama nécessitent la clé API. Lorsque LIGHTRAG_API_KEY est défini et que WHITELIST_PATHS n'est pas défini, les requêtes /api/* sans la clé obtiennent désormais HTTP 403. Dans Open WebUI, le modèle lightrag:latest disparaît de la liste. Correctif : entrez la clé comme clé API de la connexion Ollama (envoyée comme Authorization: Bearer <key>), ou définissez WHITELIST_PATHS=/health,/api/* pour conserver l'ancien comportement.
  • POST /documents/clear_cache est supprimé. Utilisez plutôt DELETE /documents?clear_llm_cache=true. La suppression du cache LLM s'effectue désormais en même temps que la suppression destructrice.
  • Les noms d'espace de travail commençant par $ sont réservés. Le serveur utilisé pour servir WORKSPACE=$team sous le nom de _team. Définissez WORKSPACE=_team (le nom sous lequel vos données sont déjà stockées) et aucune donnée ne bouge.

Notes de mise à niveau

  1. Sauvegardez d'abord, puis arrêtez chaque ancienne instance avant de démarrer v1.5.8. Cela inclut tous les travailleurs, les serveurs partageant le stockage et les outils de maintenance. Le premier démarrage crée le conteneur de configuration et lie l'ancre. N'effectuez pas de mise à niveau continue qui laisse un ancien graveur en marche.
  2. WORKING_DIR doit persister, même si chaque stockage est une base de données. Il contient désormais config_storage_anchor.json, et pour la configuration JSON également <workspace>/kv_workspace_config.json. Dans Docker, conservez-le sur un volume monté. Dans Helm, conservez persistence.enabled: true. Un WORKING_DIR éphémère perd l'ancre et la configuration JSON à chaque redémarrage. Incluez-le dans vos sauvegardes.
  3. Le service d'intégration doit être accessible lors du premier démarrage, afin que la sonde d'adoption puisse enregistrer les lignes de base. Vérifiez le journal de démarrage d'un WARNING pour indiquer qu'une ligne de base n'a pas pu être établie. Si le démarrage refuse en raison d'une incompatibilité d'espace d'intégration, vos vecteurs stockés ne correspondent pas au modèle configuré : corrigez la configuration ou exécutez lightrag-rebuild-vdb.
  4. Utilisateurs de Redis : avec LIGHTRAG_KV_STORAGE=RedisKVStorage, le stockage de configuration est par défaut les fichiers JSON dans WORKING_DIR (voir note 2). Le stockage Redis est obsolète ; planifier un déménagement vers PostgreSQL.
  5. Utilisateurs PGGraphStorage : votre déploiement continue de fonctionner et l'assistant conserve l'image compatible AGE pour celui-ci. Pour quitter AGE, migrez d'abord le graphique (python -m lightrag.tools.migrate_graph_storage --apply, aucune réindexation nécessaire), puis passez à PGTableGraphStorage et à l'image pgvector.
  6. Facultatif : pour conserver la configuration dans votre base de données au lieu des fichiers JSON, exécutez lightrag-migrate-config --target-backend PGKVStorage (ou MongoKVStorage / OpenSearchKVStorage) avec chaque serveur arrêté. Ensuite, définissez LIGHTRAG_CONFIG_STORAGE sur ce backend.
  7. Pour recommencer avec un nouveau modèle d'intégration, utilisez lightrag-clear-storage plutôt que de supprimer les fichiers manuellement. Si vous supprimez des fichiers manuellement, supprimez également kv_workspace_config.json et config_storage_anchor.json. Sinon, la ligne de base enregistrée refuse le nouveau modèle.
  8. TOKEN_SECRET doit être une valeur aléatoire d'au moins 32 octets (par exemple, openssl rand -hex 32). Le PyJWT mis à niveau met en garde contre les secrets plus courts.
  9. Les messages d'erreur diffusés sont génériques. Un échec au milieu d'un flux sur /query/stream, /api/generate ou /api/chat lit désormais Internal server error (error_id: …) et ne contient plus le texte d'exception du fournisseur LLM. Le format du flux est inchangé. Recherchez les détails dans le journal du serveur à l'aide de ce error_id. Un client qui a analysé le texte d'erreur du fournisseur à partir du flux (par exemple, pour détecter les limites de débit) doit être mis à jour.

LightRAG v1.5.8rc1

Important Notes

v1.5.8rc1 is a release candidate. Please test it on a copy of your data before upgrading production.

Highlights

1. Configuration storage: LightRAG now remembers which embedding model built your vectors

In earlier releases, changing EMBEDDING_MODEL or EMBEDDING_DIM on an existing deployment failed silently. Depending on the backend, LightRAG either kept the old vectors and returned wrong neighbours, or opened a new, empty vector container (Milvus / Qdrant / PostgreSQL) and served a knowledge graph with no vectors at all.

v1.5.8 adds a configuration storage. It is a small KV namespace (config) that holds each workspace's embedding baselines: for every vector target (entities, relationships, chunks), the embedding space its vectors were written in. Startup checks the baselines against the current embedding configuration. If the space has changed, the server refuses to start and names the target and the way out, instead of serving bad results.

  • Backends: JsonKVStorage, PGKVStorage, MongoKVStorage and OpenSearchKVStorage, selected with LIGHTRAG_CONFIG_STORAGE. Left unset, it follows LIGHTRAG_KV_STORAGE, so most deployments need no new setting. RedisKVStorage is not admitted, so Redis deployments default to JsonKVStorage, with a startup warning.
  • No preparation needed. On the first start of v1.5.8, an existing deployment records its baselines on its own. A baseline is recorded only on evidence: an adoption probe re-embeds a few stored records (up to 8 per target) and compares them with the stored vectors, or the container is confirmed empty. A probe that cannot run (for example, the embedding service is down) records nothing and is retried on the next start.
  • Deployment anchor. The first start also binds the deployment to the configuration container it opened, in WORKING_DIR/config_storage_anchor.json (backend type + container UUID). Every later start refuses a container of another type or another UUID. A changed LIGHTRAG_KV_STORAGE, a different database or a replaced volume therefore no longer silently moves your configuration.
  • New offline tools:
    • lightrag-rebuild-vdb re-embeds a workspace with the current model and records the new baselines. This is the way out after an intentional model change.
    • lightrag-migrate-config moves the configuration storage to a backend of another type, for example from JSON files to PostgreSQL.
    • lightrag-clear-storage clears a workspace offline, configuration records included.
  • Several servers, one WORKING_DIR: supported when each server has its own WORKSPACE and port. A second server on the same workspace is refused where the filesystem supports file locks.

For more information, see:

  • docs/LightRAG-API-Server.md: Configuration Storage Migration Between Backend Types
  • lightrag/tools/README_REBUILD_VDB.md, README_MIGRATE_CONFIG.md, README_CLEAR_STORAGE.md
  • docs/design/ConfigurationStorageDesign.md: the design overview

2. Safer graph writes and document deletion

  • Manual graph edits (create / edit / delete / merge entities and relations, insert_custom_kg) are now serialized against each other and against the ingestion pipeline on NetworkXStorage.
  • Commit ordering for entity/relation create, edit, merge and rename was reworked to prevent data loss when an operation is interrupted.
  • Interrupted document deletions are visible and retryable.
  • New lightrag-repair-chunk-tracking tool removes orphan chunk-tracking rows left behind by an interrupted deletion.

3. PostgreSQL storage defaults

The setup wizard now generates PostgreSQL from the official pgvector/pgvector image and offers PGTableGraphStorage (plain tables, no Apache AGE) for the graph. PGGraphStorage (AGE) and the Redis storages (RedisKVStorage, RedisDocStatusStorage) are deprecated. They keep working and log a warning at startup.

4. Security hardening and new provider

  • The Ollama-compatible /api/* routes are protected by LIGHTRAG_API_KEY (see Breaking Changes).
  • PDF extraction runs pypdf in a resource-limited child process.
  • Streamed error lines no longer echo raw provider exception text.
  • New openai_responses LLM binding for the OpenAI Responses API.

Breaking Changes

  • Python 3.11 or later is required. Python 3.10 is no longer supported. The Docker images (Python 3.12) are not affected.
  • Changing the embedding model on an existing workspace now refuses startup, where it used to serve wrong or empty results. Either restore the previous EMBEDDING_MODEL / EMBEDDING_DIM, or run lightrag-rebuild-vdb to re-embed with the new model.
  • Changing LIGHTRAG_KV_STORAGE after the first v1.5.8 start is refused while LIGHTRAG_CONFIG_STORAGE is unset, because the configuration storage would silently move with it. Either set LIGHTRAG_CONFIG_STORAGE to the anchored backend explicitly, or move the configuration with lightrag-migrate-config.
  • Ollama routes require the API key. When LIGHTRAG_API_KEY is set and WHITELIST_PATHS is unset, /api/* requests without the key now get HTTP 403. In Open WebUI, the lightrag:latest model disappears from the list. Fix: enter the key as the API key of the Ollama connection (sent as Authorization: Bearer <key>), or set WHITELIST_PATHS=/health,/api/* to keep the old behaviour.
  • POST /documents/clear_cache is removed. Use DELETE /documents?clear_llm_cache=true instead. Clearing the LLM cache now happens together with the destructive clear.
  • Workspace names starting with $ are reserved. The server used to serve WORKSPACE=$team as _team. Set WORKSPACE=_team (the name your data is already stored under), and no data moves.

Upgrade Notes

  1. Back up first, then stop every old instance before starting v1.5.8. That includes all workers, servers sharing the storage, and maintenance tools. The first start creates the configuration container and binds the anchor. Do not do a rolling upgrade that leaves an old writer running.
  2. WORKING_DIR must persist, even if every storage is a database. It now holds config_storage_anchor.json, and for JSON configuration also <workspace>/kv_workspace_config.json. In Docker, keep it on a mounted volume. In Helm, keep persistence.enabled: true. An ephemeral WORKING_DIR loses the anchor and the JSON configuration on every restart. Include it in your backups.
  3. The embedding service must be reachable during the first start, so the adoption probe can record the baselines. Check the startup log for a WARNING that a baseline could not be established. If the start refuses with an embedding-space mismatch, your stored vectors do not match the configured model: fix the configuration, or run lightrag-rebuild-vdb.
  4. Redis users: with LIGHTRAG_KV_STORAGE=RedisKVStorage, the configuration storage defaults to JSON files in WORKING_DIR (see note 2). Redis storage is deprecated; plan a move to PostgreSQL.
  5. PGGraphStorage users: your deployment keeps working, and the wizard keeps the AGE-enabled image for it. To leave AGE, migrate the graph first (python -m lightrag.tools.migrate_graph_storage --apply, no re-indexing needed), then switch to PGTableGraphStorage and the pgvector image.
  6. Optional: to keep the configuration in your database instead of JSON files, run lightrag-migrate-config --target-backend PGKVStorage (or MongoKVStorage / OpenSearchKVStorage) with every server stopped. Then set LIGHTRAG_CONFIG_STORAGE to that backend.
  7. To start over with a new embedding model, use lightrag-clear-storage rather than deleting files by hand. If you do delete files by hand, also remove kv_workspace_config.json and config_storage_anchor.json. Otherwise the recorded baseline refuses the new model.
  8. TOKEN_SECRET should be a random value of at least 32 bytes (for example, openssl rand -hex 32). The upgraded PyJWT warns about shorter secrets.
  9. Streamed error messages are generic. A failure in the middle of a stream on /query/stream, /api/generate or /api/chat now reads Internal server error (error_id: …), and no longer contains the LLM provider's exception text. The stream format is unchanged. Look up the details in the server log by that error_id. A client that parsed provider error text from the stream (for example, to detect rate limits) needs to be updated.
